## 走读 ①：打开登录页，点「登录」

### 第 1 步：浏览器为什么显示的是登录页？

你访问 `http://localhost`。前端里有个**守门人**，它一看你**没登录**，就把你送到登录页。

**打开** `src/permission.js`**，看第 36 行往后**：

```js
} else if (getToken()) {          // 有 token 吗？
   ...
} else {
    // 没有 token
    if (whiteList.indexOf(to.path) !== -1) {
      next()                       // 在白名单里（/login /register…），放行
    } else {
      next(`/login?redirect=${to.fullPath}`)   // ★ 否则踢回登录页
    }
}
```

**读作**：`getToken()` 从 Cookie 里找 `Admin-Token`。找不到 → 走 `else` → 你不在白名单 → 被重定向到 `/login`。

`getToken` 在哪？**打开** `src/utils/auth.js`：

```js
const TokenKey = 'Admin-Token'
export function getToken() {
  return Cookies.get(TokenKey)     // 从浏览器 Cookie 里取
}
```

> 🧠 **关键认识**：**token 存在浏览器 Cookie 里，键名固定叫 `Admin-Token`**。
> M0-T10 验收要看的「Application → Cookies 里有 Admin-Token」，就是这一行造成的。
> 现在你第一次登录，Cookie 是空的，所以必然被送到 `/login`。

**下一步去哪**：`/login` 这个路径对应哪个文件？**打开** `src/router/index.js`，看第 44-48 行：

```js
{
  path: '/login',
  component: () => import('@/views/login'),   // ★ 路径 → 文件
  hidden: true
},
```

**读作**：`/login` → `@/views/login` → 打开 `src/views/login.vue`。（`@` = `src/`）

`getCode()`（第 204-213 行）：

```js
getCode() {
  getCodeImg().then((res) => {
    this.captchaOnOff = res.data.captchaOnOff === undefined ? true : res.data.captchaOnOff
    if (this.captchaOnOff) {
      this.codeUrl = 'data:image/gif;base64,' + res.data.img   // ★ 图片塞进 <img :src="codeUrl">
      this.loginForm.uuid = res.data.uuid                       // ★ 后端给的 uuid，登录时要带回去

```

> 🧠 **这里有个重要设计**：验证码不是前端生成的，是**后端生成图片 + 存 Redis + 发给你一个 uuid**。
> 你提交登录时，把 `code`（用户输入的答案）和 `uuid` 一起送回后端，后端用 `uuid` 去 Redis 取出正确答案比对。
> **为什么要 uuid？** 因为后端同时服务很多人，得知道"你填的这个验证码对应的是哪一张图"。

`getCodeImg` 从哪来？看文件顶部第 132 行：


**打开** `src/api/login.js`，看第 63-72 行：

### 第 3 步：点「登录」按钮

读作：点击 → 执行 `handleLogin`；`loading` 为 true 时文字变"登录中…"。

**`handleLogin`（第 227-271 行）**：

```js
handleLogin() {
  this.$refs.loginForm.validate((valid) => {     // ① 先校验表单
    if (valid) {
      this.loading = true                        // ② 按钮转圈
      if (this.loginForm.rememberMe) { ... }     // ③ 记住密码就写 Cookie
      if (!this.loginForm.tenantId) {            // ④ 没选租户 → 先查这个账号属于哪些租户
        getTenantList(this.loginForm.username).then((response) => {
          if (response.data.length == 0) { this.$modal.msgError('账户信息不存在...'); return }
          else if (response.data.length == 1) { this.loginForm.tenantId = response.data[0].tenantId }
          else { this.tenantList = response.data; this.$modal.msgWarning('请选择账户所属租户'); return }
          this.login()                           // 一个租户，直接登
        })
      } else {
        this.login()                             // 已选租户，直接登
      }
    }
  })
}
```

> 🧠 **多租户是怎么体现的**：同一个登录名可能属于多个租户（公司）。
> 前端先 `getTenantList` 问后端"这个账号属于哪些租户"：0 个 → 报错；1 个 → 自动选上；多个 → 弹下拉框让你选。选完才真正登录。
> **本项目只有一个租户 `00000000`，所以这条分支你平时看不到效果，但代码一直在跑。**

`login()`（第 272-284 行）：

```js
login() {
  this.$store.dispatch('Login', this.loginForm)     // ★ 把表单交给 store 去登录
    .then(() => {
      this.$router.push({ path: this.redirect || '/' }).catch(() => {})   // 成功后跳首页
    })
    .catch(() => {
      this.loading = false
      if (this.captchaOnOff) { this.getCode() }      // 失败刷新验证码
    })
}
```

> 🧠 `this.$store.dispatch('Login', ...)` 的意思是：**"呼叫 store 里那个叫 `Login` 的动作，参数是表单"**。
> `$store` 是全局状态仓库（下篇 §9 详讲），你可以把它当成**一个全局的单例**，任何页面都能 `this.$store.dispatch(...)` 调它的方法。

### 第 4 步：`dispatch('Login')` 之后发生了什么（带你去 store）

**打开** `src/store/modules/user.js`，找 `actions` 里的 `Login`（第 49-64 行）：

```js
Login({ commit }, userInfo) {
  const username = userInfo.username.trim()
  const password = userInfo.password
  const code = userInfo.code
  const uuid = userInfo.uuid
  const tenantId = userInfo.tenantId
  return new Promise((resolve, reject) => {
    login(username, password, code, uuid, tenantId).then(res => {   // ★ 真正发请求
      setToken(res.data.token)      // ① 写进 Cookie
      commit('SET_TOKEN', res.data.token)   // ② 写进 store（内存）
      resolve()
    }).catch(error => { reject(error) })
  })
},
```

**读作**：
1. 调 `login(...)` 发 `POST /login`（就是 `api/login.js` 第 5-21 行那个函数）。
2. 后端返回 `{code:200, data:{token:'eyJ...'}}`。
3. **`setToken(...)` 把 token 写进 Cookie**（`Admin-Token`），**`commit('SET_TOKEN', ...)` 把它写进 store**。
   → **两处都存**：Cookie 是为了刷新页面还在（持久）；store 是为了页面里用着方便（内存）。

> 🧠 `commit('SET_TOKEN', xxx)` 是什么？`commit` 是"提交一次状态变更"，`SET_TOKEN` 是变更的名字（在 `mutations` 里定义，第 18-20 行）。
> Vuex 的分工是：**`mutations` 负责"怎么改"**（纯改状态，一个变更一个名字）；**`actions` 负责"改之前要做的准备"**（可以先调接口、拿到结果后一次或多次 `commit`）。
> 规矩是：**改状态只能走 `mutations`**，页面里不直接碰 store 里的值。

> 🧠 **这条线走完，你该记住三件事**：
> 1. **验证码的答案在后端 Redis 里**，前端只是把答案+uuid 送回来。

## 走读 ②：登录成功后，左侧菜单是怎么冒出来的

这一步是**前端最"魔法"的一段**——菜单不是前端写死的，是**后端给的**。

### 第 1 步：`router.push('/')` 之后，守门人又拦了一次

登录成功后 `login.vue` 执行了 `this.$router.push({ path: '/' })`。
**每次跳路由，`permission.js` 的 `router.beforeEach` 都会跑一遍**。这次的情况是：**有 token 了**。

**打开** `src/permission.js`，看第 36-84 行：

```js
} else if (getToken()) {                        // ★ 这次有 token 了
  if (to.path === '/login') { next({ path: '/' }) }
  else {
    if (store.getters.roles.length === 0) {      // ← roles 是空的（第一次进）
      isRelogin.show = true
      store.dispatch('GetInfo').then(() => {                 // ① 拉用户信息 + 权限
        isRelogin.show = false
        store.dispatch('GenerateRoutes').then(accessRoutes => {  // ② 拉菜单，生成路由
          router.addRoutes(accessRoutes)                     // ③ 动态注册路由
          next({ ...to, replace: true })
        })
        // ... 水印、公司配置等
      })
    } else {
      next()                                     // roles 已经有值 → 直接放行
    }
  }
}
```

**读作**（**这三步是整个前端的核心，务必记牢**）：

| 步 | 动作 | 作用 |
|---|---|---|
| ① | `dispatch('GetInfo')` | 问后端"我是谁、我有什么权限" |
| ② | `dispatch('GenerateRoutes')` | 问后端"我该有哪些菜单"，把菜单**变成前端路由** |
| ③ | `router.addRoutes(...)` | **把路由动态注册进来** |

> 🧠 **为什么第一次进要判断 `roles.length === 0`**？因为 `GetInfo`/`GenerateRoutes` 只需要在**登录后拉一次**，
> 之后在页面间跳来跳去，`roles` 已有值，就直接 `next()` 放行了——**不会每次都去请求后端**。
> 这也是「后端改了权限，前端要重新登录才生效」的原因：拉过一次就缓存在内存里了。

### 第 2 步：`GetInfo` 拉到了什么

**打开** `src/store/modules/user.js`，看 `GetInfo`（第 67-95 行）：

```js
GetInfo({ commit, state }) {
  return new Promise((resolve, reject) => {
    getInfo().then(res => {
      const user = res.data.user
      if (res.data.roles && res.data.roles.length > 0) {
        commit('SET_ROLES', res.data.roles)              // ★ 角色存进 store
        commit('SET_PERMISSIONS', res.data.permissions)  // ★ 权限码存进 store
      } else {
        commit('SET_ROLES', ['ROLE_DEFAULT'])
      }
      commit('SET_USERINFO', user)
      commit('SET_NAME', user.userName)
      commit('SET_NICKNAME', user.nickName)
      // ...
      resolve(res)
    })
  })
},
```

对应后端：`SysLoginController.java` **第 110 行** `getInfo()`。

> 🧠 **`roles` 和 `permissions` 的区别**：
> - `roles`：角色（比如 `admin`），用于 `v-hasRole` / 路由的 `roles` 判断。
> - `permissions`：**权限码**（比如 `conf:signingSubject:add`），用于 `v-hasPermi` 和按钮显隐。
> **你登录的是超管 `zxcmAdmin`，后端会返回 `permissions: ["*:*:*"]`**，一个通配符代表"全部权限"。

### 第 3 步：`GenerateRoutes` —— 菜单是怎么变成路由的

这是**整个前端最值得读懂的一段**。**打开** `src/store/modules/permission.js`，看 `GenerateRoutes`（第 33-51 行）：

```js
GenerateRoutes({ commit }) {
  return new Promise(resolve => {
    getRouters().then(res => {                         // ★ 问后端要菜单
      const sdata = JSON.parse(JSON.stringify(res.data))   // 深拷贝两份（一份给侧边栏，一份给路由）
      const rdata = JSON.parse(JSON.stringify(res.data))
      const sidebarRoutes = filterAsyncRouter(sdata)          // 处理成"侧边栏用的"
      const rewriteRoutes = filterAsyncRouter(rdata, false, true) // 处理成"路由表用的"
      rewriteRoutes.push({ path: '*', redirect: '/404', hidden: true })  // 兜底 404
      commit('SET_ROUTES', rewriteRoutes)
      commit('SET_SIDEBAR_ROUTERS', constantRoutes.concat(sidebarRoutes))  // ★ 侧边栏数据源
      resolve(rewriteRoutes)
    })
  })
}
```

再看 `filterAsyncRouter`（第 56-81 行）里最关键的一句：

```js
if (route.component) {
  if (route.component === 'Layout') { route.component = Layout }
  else if (route.component === 'ParentView') { route.component = ParentView }
  else { route.component = loadView(route.component) }   // ★ 字符串 → 真实组件
}
```

而 `loadView`（第 124-131 行）：

```js
export const loadView = (view) => {
  if (process.env.NODE_ENV === 'development') {
    return (resolve) => require([`@/views/${view}`], resolve)   // ★ 字符串拼成文件路径
  } else {
    return () => import(`@/views/${view}`)
  }
}
```

> 🔑 **这就是「菜单 → 页面」的机关**：后端 `sys_menu.COMPONENT` 的值（比如 `conf/signingSubject/index`）→ `loadView` 拼成 `@/views/conf/signingSubject/index` → **变成真实页面组件**。
> **所以「加一个新页面」在后端要做的只是**：在 `sys_menu` 插一条记录、`COMPONENT` 填路径，**前端一行代码都不用改**。这就是"页面能自动长出来"的原因。
>
> 📌 `COMPONENT` 的三个**保留字**（`Layout` / `ParentView` / `InnerLink`，它们不是文件路径）和完整的 `COMPONENT` 对照表，**归口在 [E1 · §3 约定 1](E1-zxcm-ui工程结构.md#约定-1菜单--页面靠一个字符串)** —— 本文不重复列。

### 第 4 步：侧边栏怎么把菜单画出来

上一步 `commit('SET_SIDEBAR_ROUTERS', ...)` 把菜单存进了 store。
**打开** `src/layout/components/Sidebar/index.vue`，看第 31-36 行：

```js
submitForm() {
  this.$refs['form'].validate((valid) => {          // ① 校验；不过就不提交
    if (valid) {
      this.buttonLoading = true
      this.form.contacts = JSON.stringify(this.form.contactsArray)   // ★ 数组 → JSON 字符串
      this.form.bankJson = JSON.stringify(this.form.bankJsonArray)
      if (this.form.id != null) {
        updateSigningSubject(this.form).then(() => {                 // ② 有 id → 修改
          this.$modal.msgSuccess('修改成功'); this.open = false; this.getList()
        }).finally(() => { this.buttonLoading = false })
      } else {
        addSigningSubject(this.form).then(() => {                    // ③ 没 id → 新增
          this.$modal.msgSuccess('新增成功'); this.open = false; this.getList()
        }).finally(() => { this.buttonLoading = false })
      }
    }
  })
},
```

**三个关键点**：

1. **`this.$refs['form'].validate(...)`**：调 `<el-form ref="form">` 的自带校验（对应模板第 221-227 行的 `:rules="rules"`）。不通过就 `valid=false`，请求一个都不发。**它拦在"点确定"的那一刻，是前端的体验层防线**（真正的安全校验在后端）。
2. **`JSON.stringify`**：把「财务信息/联系人」这两个**动态数组**压成 JSON 字符串再上送。
   → 因为数据库里这两列是**一个 JSON 文本字段**（`bankJson` / `contacts`），不是一个子表。
3. **新增/修改共用一个 `submitForm`**：靠 `this.form.id` 有没有值来分。这也是**为什么「修改」要先 `getSigningSubject(id)` 查详情**——得先把 id 和旧数据回填进 `form`。

`handleUpdate`（第 770-791 行）就是干这个的：

```js
handleUpdate(row) {
  const id = row.id || this.ids
  getSigningSubject(id).then((response) => {
    response.data.bankJsonArray = JSON.parse(response.data.bankJson)   // ★ JSON 字符串 → 数组
    response.data.contactsArray = JSON.parse(response.data.contacts)
    this.form = response.data
    this.open = true
    this.title = '修改签约主体'
  })
},
```

> 💡 **注意这对"对称操作"**：存的时候 `JSON.stringify`，取的时候 `JSON.parse`。
> **数据库存的是字符串，界面用的是数组**，中间靠这两行转换。这是个很容易被忽略、但很关键的细节。

|---|---|---|

| 修改 | 第 159-160 行 `@PutMapping()` | `edit(...)` |

```js
  { path: '/system/user-auth', component: Layout, hidden: true,
    permissions: ['system:user:edit'],           // ★ 有这权限才加载
    children: [... authRole ...] },
  // ...
]
```

| | `constantRoutes` | `dynamicRoutes` |
|---|---|---|
| 谁定义 | **前端写死** | 前端写死**框架**，但**按权限过滤** |
| 例子 | 登录页、404、首页 | 分配角色、分配用户页 |
| 什么时候加载 | 一开始就注册 | `permission.js` 拉完权限后过滤注册 |

> 🧠 **注意：业务页面（签约主体、合同草拟……）不在这里！**
> 它们连"写死"都没有——**完全由后端菜单动态生成**（走读 ② 讲的那个机制）。
> 路由表里只有**框架自带的、不挂在菜单上的**特殊页面。

### ② 最后一行，把路由实例造出来（第 209-213 行）

```js
export default new Router({
  mode: 'history',                        // 去掉 URL 里的 #
  scrollBehavior: () => ({ y: 0 }),       // 切页面自动回到顶部
  routes: constantRoutes                  // 初始只有公共路由
})
```

> 🧠 **`mode: 'history'`** 决定 URL 长这样：`http://localhost/conf/signingSubject`（而不是 `/#/conf/signingSubject`）。
> 代价是**刷新页面 404**——因为浏览器真去请求 `/conf/signingSubject` 这个路径，而服务器没这个文件；
> 生产环境要在 Nginx 配 `try_files` 兜底。开发环境靠 `vue.config.js` 的 `historyApiFallback`。

**下一步去哪**：路由造好了，但"谁能进哪个页面"还没管。去看守门人。

## `permission.js`：守门人

**打开** `src/permission.js`（100 行，全文不长，**建议整篇读**）。它是**全局路由守卫**——每次切路由都跑。

### ① 白名单（第 12 行）

```js
const whiteList = ['/login', '/auth-redirect', '/bind', '/register', '/wxLogin', '/wxCallback']
```

**读作**：这几个路径**不需要登录**就能进。其他一切都要 token。

> ⚠️ **这份白名单和后端 `application.yml` 里的 `security.excludes` 是两套独立的名单**。
> 改一个不影响另一个——**前端管"能不能进页面"，后端管"能不能调接口"**。

### ② 守卫主体（第 14 行起）

```js
router.beforeEach((to, from, next) => {
  NProgress.start()                          // 顶部加载进度条
  if (to.path === '/sso') { ... }            // 单点登录特殊处理（本项目用不到）
  else if (getToken()) {                     // ★ 有 token
    if (to.path === '/login') { next({ path: '/' }) }   // 已登录还去登录页 → 弹回首页
    else {
      if (store.getters.roles.length === 0) {           // 第一次进：拉信息 + 生成路由
        store.dispatch('GetInfo').then(() => { store.dispatch('GenerateRoutes').then(...) })
      } else { next() }                                 // 之后：直接放行
    }
  } else {                                   // ★ 没 token
    if (whiteList.indexOf(to.path) !== -1) { next() }   // 在白名单 → 放行
    else { next(`/login?redirect=${to.fullPath}`) }     // 否则踢回登录页（记下来路）
  }
})
```

**四个 `next(...)` 的含义**（`next` 就是"接下来放行去哪"）：

| 写法 | 含义 |
|---|---|
| `next()` | 放行，进入目标页面 |
| `next('/login')` | 不放行，改去登录页 |
| `next({ path: '/' })` | 不放行，改去首页 |
| `next({ ...to, replace: true })` | **放行目标页，但替换历史记录**（避免返回键死循环） |

> ⚠️ **面试常考：前端路由守卫不是安全措施**。
> 它只是"体验优化"（不让没权限的人误入页面）。**手改前端、或者直接用 curl 打接口，照样绕过去**。
> 真正的安全边界在后端每个 Controller 方法上的 `@SaCheckPermission`。
> 所以「前端把按钮藏起来」≠「接口安全了」。

**下一步去哪**：守卫里反复出现 `store`，去看它是啥。

## `store/`：前端的内存数据库

**打开** `src/store/index.js`（如果行数少，就是组装各个模块）和 `src/store/modules/` 下的文件。

**一句话理解 Vuex**：**前端没有 session，登录用户、权限、菜单都缓在内存里，这就是 store。**
它像后端的**一个全局单例 + 内存缓存**。任何页面都能 `this.$store` 读写。

### 六个模块（`src/store/modules/`）

| 模块 | 存什么 | 对应后端 |
|---|---|---|
| **`user.js`** | token、用户信息、**roles**、**permissions** | `getInfo` 的返回 |
| **`permission.js`** | **菜单路由**（`sidebarRouters` 等） | `getRouters` 的返回 |
| `app.js` | 侧边栏折叠、设备类型、尺寸 | 纯界面状态 |
| `tagsView.js` | 打开过的页签、缓存过的页面 | 纯界面状态 |
| `settings.js` | 标题、主题色、公司配置 | 界面状态 |
| `notify.js` | 未读消息数 | 界面状态 |

### `store/getters.js`：快捷访问层

**打开** `src/store/getters.js`（23 行）：

```js
const getters = {
  token: state => state.user.token,
  roles: state => state.user.roles,
  permissions: state => state.user.permissions,
  sidebarRouters: state => state.permission.sidebarRouters,
  // ...
}
```

**读作**：给 store 里的值起**短名字**，方便页面读。有了它，页面里可以写 `this.$store.getters.roles`，也可以配合 `mapGetters` 直接写 `roles`。

> 🧠 **四块东西，记牢分工**：
> | | 作用 | 什么时候用 |
> |---|---|---|
> | `state` | 存数据 | 这里放值本身 |
> | `getters` | **读**数据（可加工、可起短别名） | 页面要读时走它 |
> | `mutations` | **改**数据（同步、一个变更一个名字） | 唯一能改 `state` 的地方 |
> | `actions` | **业务动作**（可异步、可调接口、改前先做准备） | 复杂流程、要发请求时用 |
>
> 页面里：`this.$store.dispatch('Login', ...)` 调 **actions**；`commit('SET_TOKEN', ...)` 调 **mutations**；
> `this.$store.getters.roles` 读 **getters**。

**下一步去哪**：数据齐了、路由有了，界面怎么搭起来？看外壳。

## `utils/request.js`：所有请求的总管

**打开** `src/utils/request.js`。**每一行代码你都在走读 ③ 见过它的效果**，这里集中讲清。

### ① 建一个 axios 实例（第 19-24 行）

```js
const service = axios.create({
  baseURL: process.env.VUE_APP_BASE_API,   // ★ = '/dev-api'
  timeout: 10000
})
```

> 🧠 `VUE_APP_BASE_API` 定义在 `.env.development`（第 5 行左右）：`VUE_APP_BASE_API = '/dev-api'`。
> 所以所有请求都发往 `/dev-api/xxx`，再被 `vue.config.js` 的代理转发到 `localhost:8080/xxx`。
> **这个 `/dev-api` 前缀是开发环境专用的"暗号"，让代理知道"这个请求该转给后端"。**

### ② 请求拦截器：出门前统一加料（第 27-68 行）

```js
service.interceptors.request.use(config => {
  const isToken = (config.headers || {}).isToken === false
  if (getToken() && !isToken) {
    config.headers['token'] = 'Bearer ' + getToken()    // ★ 自动加 token
  }
  if (config.method === 'get' && config.params) {        // GET 参数拼成 query string
    let url = config.url + '?' + tansParams(config.params)
    ...
  }
  if (!isRepeatSubmit && (config.method === 'post' || config.method === 'put')) {
    // 防重复提交：1 秒内相同 URL + 相同参数 → 直接 reject
  }
  return config
})
```

**两个行为要记住**：
- **自动加 token**：所以页面里从不手写 token。登录接口特殊——它在 `api/login.js` 里加了 `headers: { isToken: false }`，**主动说"我这个请求别加 token"**（因为还没登录）。
- **防重复提交**：连点两次"确定"，第二次会被拦下（`repeatSubmit` 可关）。

### ③ 响应拦截器：回程统一处理（第 71-132 行）

```js
service.interceptors.response.use(res => {
  const code = res.data.code || 200
  if (code === 401) {                       // 未登录/过期 → 弹"重新登录"
    MessageBox.confirm('登录状态已过期...').then(() => { store.dispatch('LogOut') })
    return Promise.reject('无效的会话...')
  } else if (code === 500) {                // 业务错误 → 红条提示
    Message({ message: msg, type: 'error' })
  } else if (code !== 200) {                // 其他非 200 → 通知
    Notification.error({ title: msg })
  } else {
    return res.data                         // ★ 200 才把 data 返回给页面
  }
})
```

> 🔑 **两条重要认识**：
> 1. **RuoYi 把业务状态码放在响应体里（`res.data.code`），不是 HTTP 状态码**。
>    所以「HTTP 200 但 body 里 code=401」是正常的——**判断接口成功与否要看 `code`**。
> 2. **页面里从不用写 `if (code === 200)`**——这里统一处理了。所以 `getList` 里直接 `response.rows` 就行。

### ④ 通用的下载方法（第 135-159 行）

`handleExport` 里用的 `this.download(...)` 就是这里导出的。

## `components/`：可复用的零件

**打开** `src/components/`。里面是**被很多页面共用的组件**。

### 全局注册的（`main.js` 第 93-106 行注册，直接用不用 import）

| 组件 | 作用 | 你在哪见过 |
|---|---|---|
| **`Pagination`** | 分页条 | 每个列表页底部 |
| **`RightToolbar`** | 右上角"刷新/显隐搜索/显隐列" | 每个列表页工具行 |

### 局部引用的（用到才 import）

`TreeSelect`、`Transfer`、`OrgSelect`、`workflow/`（流程设计器）等。

> 💡 **看到 `Zn` 前缀 = 本项目（山西肇新）自研**，不是 RuoYi 框架自带。

**组件间怎么通信**（以 `<pagination>` 为例）：

```html
<!-- 父页面写的 -->
<pagination
  :total="total"                        ← 父把 total 传进去
  :page.sync="queryParams.pageNum"      ← 双向：子能改父的 pageNum
  @pagination="getList"                 ← 子喊 pagination 时，父执行 getList
/>
```

```
父 → 子：props（属性）往下传     ← 像构造方法传参
子 → 父：$emit（事件）往上喊      ← 像回调
```

`.sync` 是语法糖：`:page.sync="X"` = `:page="X"` **加上** `@update:page="X = $event"`。
所以子组件内部 `$emit('update:page', 2)` 的那一刻，**父页面的 `queryParams.pageNum` 就被改成 2 了**。

> 🧠 **为什么要有 `.sync`**：组件**不能直接改父组件的数据**（改了会警告）。
> 想改，只能 `$emit` 请父组件改。`.sync` 就是这条"合法通道"的简写。
