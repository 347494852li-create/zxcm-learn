# 第 8 章 · 操作日志与登录日志

> **第 7 章讲"数据怎么进数据库"，本章讲"人干了什么怎么被记下来"。** 只要在方法上写一个 `@Log(title = "签约主体", businessType = BusinessType.INSERT)`，**这次操作的时间、人、IP、URL、参数、结果、耗时**就自动落进 `sys_oper_log` 表——**业务代码一行都不用写。**
>
> **本章第一次讲透**：① **操作日志（`sys_oper_log`）** 和 **登录日志（`sys_logininfor`）** 的区别与各自记录什么；② `@Log` 注解 + `LogAspect` 切面怎么做到"**零侵入记录**"；③ 为什么日志要**异步写**、异步线程池怎么配；④ **登录失败也记日志**（安全审计的关键）；⑤ 日志里的**参数截断、文件过滤**这些容易被忽略的工程细节。

## 一、这部分是做什么的？

### 1.0 零基础先补概念（第一次读先看这里）

| 概念 | 大白话 | 本章的真实例子 |
|---|---|---|
| **注解** | 贴在类/方法上的一张"小标签"，本身不干活，等框架来读它 | `@Log(title = "签约主体")`（`Log.java:26` 说明它只能贴在方法/参数上） |
| **AOP（面向切面编程）** | 不改业务方法，在方法"返回后/抛异常时"自动插一段代码 | `LogAspect` 用 `@AfterReturning`（`LogAspect.java:57`）在 `add()` 返回后记日志 |
| **异步（`@Async`）** | 把活交给另一条线程，主线程不等它先返回 | `OperLogService.recordOper` 上的 `@Async`（`OperLogService.java:26`） |
| **ThreadLocal** | 每个线程自己的"小柜子"；换了线程就看不到原线程的东西 | 异步线程拿不到登录人，所以 `tenantId` 要在主线程取出后**传参**（`LogAspect.java:97`） |

**先记住一句话**：本章的"零侵入"= **注解负责声明、切面负责采集、异步线程负责落库**。三件事拆开看，代码就不难读了。

### 1.1 两类日志，两个表

| | 操作日志 | 登录日志 |
|---|---|---|
| 表 | **`sys_oper_log`**（`zxcm_init.sql:4213`） | **`sys_logininfor`**（`zxcm_init.sql:3953`） |
| 记什么 | **登录后**干了什么（增删改、导出、授权…） | **登录这件动作本身**（成功/失败/退出） |
| 谁触发 | `@Log` 注解（**手动标**） | 登录服务（**自动记**） |
| 核心字段 | 模块、业务类型、操作人、URL、参数、返回、异常、耗时 | 用户名、IP、状态、提示消息 |
| 典型用途 | **追责**："这条合同是谁删的？" | **安全**："谁在暴力破解密码？" |

**一句话区分**：**操作日志回答"你进来之后做了什么"，登录日志回答"你怎么进来的、进来几次"。**

### 1.2 操作日志记了哪些字段

以 `SysOperLog` 实体为例（类声明在 `ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/domain/SysOperLog.java:42`），一份记录大致包含：

| 字段 | 内容 | 从哪来 |
|---|---|---|
| `title` | 模块名（如"签约主体"） | `@Log(title=...)` |
| `businessType` | 业务类型（新增/修改/删除/导出…） | `@Log(businessType=...)` |
| `operatorType` | 操作人类别（后台用户/手机端） | `@Log(operatorType=...)` |
| `operName` | **操作人用户名** | `LoginHelper.getUsername()` |
| `operIp` | 客户端 IP | `ServletUtils.getClientIP()` |
| `operUrl` | 请求地址 | `request.getRequestURI()` |
| `requestMethod` | HTTP 方法（GET/POST…） | `request.getMethod()` |
| `method` | 执行的 Java 方法（类名.方法名()） | `joinPoint` |
| `operParam` | **请求参数**（截断 2000 字符） | 参数序列化 |
| `jsonResult` | **返回结果**（截断 2000 字符） | 返回值序列化 |
| `status` | 成功 / 失败 | 有无异常 |
| `errorMsg` | 异常信息（截断 2000 字符） | `e.getMessage()` |
| `operTime` | 操作时间 | `new Date()` |
| `tenantId` | 租户 ID | `LoginHelper.getTenantId()` |

### 1.3 "零侵入"是这一章的核心卖点

**记录日志最笨的做法**：在每个方法里手动写 `insert into sys_oper_log (...)`。**问题**：重复、易漏、污染业务代码。

**本项目的做法**：**在方法上标一个 `@Log`，切面自动接管。**

```java
@Log(title = "签约主体", businessType = BusinessType.INSERT)     // ← 就这一行
@PostMapping()
public R<Void> add(@Validated @RequestBody TSigningSubjectBo bo) { ... }
```

**业务方法里一行日志代码都没有**，但这次操作被完整记录。**这就是 AOP（面向切面）的价值。**

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么要有"操作日志"？

**因为"企业系统"和"个人项目"的根本区别是：企业要为"谁做了什么"负责。** 具体三类需求：

| 需求 | 场景 | 操作日志怎么满足 |
|---|---|---|
| **审计 / 追责** | "这份合同被谁删了？什么时候？" | 记了 `operName` / `operTime` / `method` / 参数 |
| **安全排查** | "这个 IP 为什么能改系统配置？" | 记了 `operIp` / `operUrl` |
| **问题定位** | "用户说保存失败了，报什么错？" | 记了 `errorMsg` / `jsonResult` |

**没有操作日志的系统，出了问题只能"猜"。** 这是**生产系统的基本配置**，也是**等保合规**的硬性要求。

### 2.2 为什么用"注解 + AOP"而不是"手动写"？

看 `@Log` 注解（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/annotation/Log.java:29-53`）的五个属性：

```java
@Target({ElementType.PARAMETER, ElementType.METHOD})       // :26 可以标在方法上
@Retention(RetentionPolicy.RUNTIME)
public @interface Log {
    String title() default "";                              // :33 模块名
    BusinessType businessType() default BusinessType.OTHER; // :38 业务类型
    OperatorType operatorType() default OperatorType.MANAGE;// :43 操作人类别
    boolean isSaveRequestData() default true;               // :48 存不存请求参数
    boolean isSaveResponseData() default true;              // :53 存不存返回结果
}
```

**注解式的三个好处**：

1. **声明清晰**：一眼看出"这个接口要记日志、属于哪个模块、什么类型"；
2. **业务零侵入**：日志逻辑全在切面里，**业务方法只管业务**；
3. **可开关**：`isSaveRequestData()` / `isSaveResponseData()` 能按方法关闭（**涉及密码等敏感参数的接口应该关掉**）。

**`businessType` 的值**（`BusinessType.java:21-76`）：`OTHER` / `INSERT` / `UPDATE` / `DELETE` / `GRANT` / `EXPORT` / `IMPORT` / `FORCE`（强退）/ `GENCODE`（生成代码）/ `CLEAN`（清空）/ `DOWNLOAD`。**这套枚举让日志能"按类型筛选"**（前端监控页可以只看"删除"操作）。

### 2.3 为什么写日志要"异步"？

**因为写日志是"额外开销"，不该拖慢用户请求。** 用户点"保存"，主流程是"写业务表"，**日志是搭便车**。如果同步写日志：

- **多一次数据库往返**（用户等待变长）；
- **日志写失败会连累业务**（日志表锁了，业务也失败了——这就本末倒置了）。

**异步写**：**主流程写完业务就返回，日志丢给别的线程去写。** 用户感知不到日志的存在。

**本项目怎么实现异步？** 看 `OperLogService`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/service/OperLogService.java:24-28`）：

```java
public interface OperLogService {
    @Async                                    // :26 ★ 异步
    void recordOper(OperLogDTO operLogDTO, String tenantId);
}
```

**`@Async` 让这个方法的执行"另起一个线程"**——调用方**不等它执行完就返回**。

**异步靠什么启用？** `AsyncConfig`（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/AsyncConfig.java:38`）：

```java
@EnableAsync                                  // :35 ★ 开启异步
@Configuration
public class AsyncConfig extends AsyncConfigurerSupport {

    @Autowired
    @Qualifier("scheduledExecutorService")
    private ScheduledExecutorService scheduledExecutorService;

    @Override
    public Executor getAsyncExecutor() {
        return scheduledExecutorService;      // :48-50 ★ 用系统线程池跑 @Async
    }

    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {  // :56
        return (throwable, method, objects) -> {
            log.error("异步任务执行异常", throwable);      // :58 ★ 异步任务出异常也记日志
            ...
        };
    }
}
```

**两个关键点：**

1. **`@Async` 用的线程池是 `scheduledExecutorService`**（`:48-50`）——**不是 Spring 默认的 `SimpleAsyncTaskExecutor`**（那个每次都新建线程，不适合生产）。本项目**统一用系统的线程池**（第 14 章会看到这个池怎么配）。
2. **异步任务异常有专门处理器**（`:56-67`）——因为**异步线程抛异常不会传给调用方**，没人处理就"静默失败"了，所以这里**统一记 `log.error`**。

> 📌 **顺带一个"异步的坑"**：`@Async` **对"同一个类内部自调用"不生效**（因为不走 Spring 代理）。所以调用方是**通过注入的 Bean 调用**，而不是 `this.recordOper(...)`。

### 2.4 为什么日志要"截断 2000 字符"？

看 `LogAspect.handleLog`（`LogAspect.java:86`、`:126`、`:140`）：

```java
operLog.setErrorMsg(StringUtils.substring(e.getMessage(), 0, 2000));                        // :86
operLog.setJsonResult(StringUtils.substring(JsonUtils.toJsonString(jsonResult), 0, 2000));   // :126
operLog.setOperParam(StringUtils.substring(params, 0, 2000));                                // :140
```

**每个大字段都截断到 2000 字符。** 为什么？

- **防止"巨型参数撑爆日志表"**：用户可能提交一个 10MB 的富文本，**不截断就会把 `operParam` 写成 10MB**；
- **防止"日志表成为性能瓶颈"**：日志是高频写的表，**单条太大直接拖垮数据库**；
- **2000 是经验值**：足够看清"改了什么"，又不至于过大。

**这是"日志表要能扛住高频写"的工程直觉**——**很多人写日志时不注意，上线后才被大字段坑。**

### 2.5 为什么"登录失败"也要记日志？

看 `SysLoginService` 里调用登录日志的地方（`SysLoginService.java`）——**成功和失败都记**：

- **失败**：密码错误（`:117`）、**登录错误次数超限被锁**（`:100`/`:112`）、验证码过期/错误（`:202`/`:206`）；
- **成功**：登录成功（`:156`/`:181`）、退出登录（`:187`）、注册（`SysRegisterService.java:78`）。

> 注意 `:167` 不是"第三方登录失败"：它是 `loginByThird` 里**错误次数已超限、直接拒绝登录**时记的一条失败日志（`SysLoginService.java:166-169`）。第三方登录查到用户为空时是直接抛异常（`:172-173`），并没有调 `recordLogininfor`。

**"记成功"是审计，"记失败"是安全。** 一次两次失败正常，**同一个用户名/IP 短时间内大量失败 = 正在被暴力破解**。**登录日志是"发现攻击"的第一手数据。**

**这也解释了第 2 章的登录锁定机制**：错误次数写进 Redis（`LOGIN_ERROR` key），**同时通过 `recordLogininfor` 落一条登录日志**——**一个用于"实时拦截"，一个用于"事后审计"。**

### 2.6 为什么 `LogAspect` 里用 `SpringUtils.getBean(...)` 而不是注入？

看 `LogAspect.java:97`：

```java
SpringUtils.getBean(OperLogService.class).recordOper(operLog, LoginHelper.getTenantId());
```

**切面是 Spring Bean，按理可以直接 `@Autowired` 注入 `OperLogService`。** 为什么用静态工具取 Bean？

**原因**：`OperLogService` 的实现类在 `ruoyi-system` 模块，而 `LogAspect` 在 `ruoyi-framework` 模块。**如果 `framework` 直接依赖 `system` 的类做自动注入，会加重模块耦合**（回忆第 0 章的依赖方向：`framework` 不该依赖业务，`system` 是被 `framework` 之上层依赖的）。**用 `SpringUtils.getBean(接口.class)`，只依赖"接口"（在 `ruoyi-common`），运行期再从容器取实现**——**优雅绕开了编译期依赖。**

> 📌 **这是一个很漂亮的"依赖倒置"实例**：**依赖接口（`OperLogService`，在 `common`），运行时由容器提供实现（`SysOperLogServiceImpl`，在 `system`）。** 面试聊到"模块解耦"时，这是一个绝佳例子。

### 2.7 为什么"方法名、URL"也要记？

`LogAspect.java:89-93`：

```java
String className = joinPoint.getTarget().getClass().getName();
String methodName = joinPoint.getSignature().getName();
operLog.setMethod(className + "." + methodName + "()");        // :91 如 com.ruoyi.conf.controller.TSigningSubjectController.add()
operLog.setRequestMethod(ServletUtils.getRequest().getMethod());  // :93
```

**记"Java 方法全名"而不只是"URL"**，是因为**排查问题要能直达代码**——看到 `com.ruoyi.conf.controller.TSigningSubjectController.add()`，**开发者一眼知道该看哪个文件的哪个方法**。**URL 可能被路由改，Java 方法名不会。**

## 四、功能具体怎么实现（带着你读懂）

### 4.1 怎么用：标一个 `@Log`

```java
@Log(title = "签约主体", businessType = BusinessType.INSERT)
@PostMapping()
public R<Void> add(@Validated @RequestBody TSigningSubjectBo bo) { ... }
```

**常用写法对照**：

| 场景 | 写法 |
|---|---|
| 新增 | `@Log(title = "合同", businessType = BusinessType.INSERT)` |
| 修改 | `@Log(title = "合同", businessType = BusinessType.UPDATE)` |
| 删除 | `@Log(title = "合同", businessType = BusinessType.DELETE)` |
| 导出 | `@Log(title = "合同", businessType = BusinessType.EXPORT)` |
| 导入 | `@Log(title = "合同", businessType = BusinessType.IMPORT)` |
| 强退用户 | `@Log(title = "在线用户", businessType = BusinessType.FORCE)` ← 第 5 章见过（`SysUserOnlineController.java:96`）|
| **不存请求参数** | `@Log(title = "用户", businessType = BusinessType.UPDATE, isSaveRequestData = false)` ← **改密码这类接口必须关** |

### 4.2 `LogAspect`：切面怎么工作

`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/LogAspect.java:50`：

```java
@Slf4j
@Aspect                          // :48 ★ 声明切面
@Component
public class LogAspect {

    @AfterReturning(pointcut = "@annotation(controllerLog)", returning = "jsonResult")   // :57 ★ 正常返回
    public void doAfterReturning(JoinPoint joinPoint, Log controllerLog, Object jsonResult) {
        handleLog(joinPoint, controllerLog, null, jsonResult);      // :59 无异常
    }

    @AfterThrowing(value = "@annotation(controllerLog)", throwing = "e")                  // :68 ★ 抛异常
    public void doAfterThrowing(JoinPoint joinPoint, Log controllerLog, Exception e) {
        handleLog(joinPoint, controllerLog, e, null);               // :70 带异常
    }
```

**两个通知，一个核心方法**：

- **`@AfterReturning`（:57）**：方法**正常返回**后触发；
- **`@AfterThrowing`（:68）**：方法**抛异常**时触发；
- 两者都调 **`handleLog`（:73）**，区别只是"有没有异常"。

**为什么用 `@AfterReturning` / `@AfterThrowing` 而不是 `@Around`？** 因为**要拿到"返回值"或"异常"**，这两种通知语义最清晰。（`@Around` 要自己 `proceed()` + try/catch，更麻烦。）

**核心方法 `handleLog`（:73-103）**：

```java
protected void handleLog(JoinPoint joinPoint, Log controllerLog, Exception e, Object jsonResult) {
    try {
        OperLogDTO operLog = new OperLogDTO();
        operLog.setStatus(BusinessStatus.SUCCESS.ordinal());                  // :77 默认成功
        operLog.setOperIp(ServletUtils.getClientIP());                        // :80 IP
        operLog.setOperUrl(ServletUtils.getRequest().getRequestURI());        // :81 URL
        operLog.setOperName(LoginHelper.getUsername());                       // :82 ★ 操作人

        if (e != null) {                                                      // :84 有异常
            operLog.setStatus(BusinessStatus.FAIL.ordinal());                 // :85 → 失败
            operLog.setErrorMsg(StringUtils.substring(e.getMessage(), 0, 2000));  // :86 错误信息
        }
        // Java 方法全名
        String className = joinPoint.getTarget().getClass().getName();        // :89
        String methodName = joinPoint.getSignature().getName();               // :90
        operLog.setMethod(className + "." + methodName + "()");               // :91
        operLog.setRequestMethod(ServletUtils.getRequest().getMethod());      // :93
        // 读注解、装配参数/结果
        getControllerMethodDescription(joinPoint, controllerLog, operLog, jsonResult);   // :95
        // ★ 异步落库
        SpringUtils.getBean(OperLogService.class).recordOper(operLog, LoginHelper.getTenantId());  // :97
    } catch (Exception exp) {
        log.error("==前置通知异常==");                                        // :100 切面自己出错别影响业务
        log.error("异常信息:{}", exp.getMessage());
    }
}
```

**逐行读 `handleLog`（`LogAspect.java:73-103`）**：

| 行 | 代码在干什么 | 为什么这么写 |
|---|---|---|
| `73` | 方法签名收 4 样东西：切点、`@Log` 注解、异常、返回值 | 正常返回和异常两条路都汇到这一个方法，避免写两套采集逻辑 |
| `74` | `try {` 开始 | 从这一行到 `:98` 的 `catch`，保证"记日志自身出错"不会冒泡给业务 |
| `77` | 先默认 `status = SUCCESS` | 大多数请求是成功的；只有 `:84` 发现异常才改成失败 |
| `80-81` | 从当前请求取 IP、URI | IP 用于安全排查，URI 用于知道"访问了哪个接口" |
| `82` | `LoginHelper.getUsername()` 取操作人 | 依赖登录态；所以登录接口本身不能用 `@Log`（那时还没有登录人） |
| `84-86` | 有异常 → `status = FAIL`、`errorMsg = 截断后的异常信息` | 失败操作也要留痕；`StringUtils.substring(..., 0, 2000)` 防止异常信息过长 |
| `89-91` | 拼出 `类全名.方法名()` | 比 URL 更稳定，排查时能直接定位到 Java 方法 |
| `93` | 记录 HTTP 方法（GET/POST…） | 后面 `setRequestValue` 要靠它决定"从 body 还是从 URL 取参数" |
| `95` | 调 `getControllerMethodDescription(...)` 读注解 | 把 `title/businessType/operatorType/参数/返回值` 一次性补齐 |
| `97` | `SpringUtils.getBean(OperLogService.class).recordOper(...)` | 取的是**代理后的 Bean**，`@Async` 才会生效；同时把 `tenantId` 当参数传过去 |
| `98-101` | 捕获切面自身异常，只打本地 `log.error` | 日志是旁路：它失败，业务照常返回 |

**三个必须注意的点：**

1. **整个 `handleLog` 包在 `try/catch` 里**（`:74`/`:98`）——**"记录日志失败绝不能连累业务"**。切面出错只打本地 error 日志，**业务照常返回**。**这是"日志是旁路"的正确态度。**
2. **`operName` 来自 `LoginHelper.getUsername()`**（`:82`）——**依赖登录态**。所以**未登录的接口（如登录本身）不能用 `@Log` 记录**（拿不到用户名）。**这是为什么"登录日志"是另一套机制**（§4.5）。
3. **`getControllerMethodDescription`（:112）** 负责读注解：

```java
operLog.setBusinessType(log.businessType().ordinal());      // :114 业务类型的序号
operLog.setTitle(log.title());                             // :116
operLog.setOperatorType(log.operatorType().ordinal());     // :118

```

> 📌 **`businessType.ordinal()` 是"枚举的下标"**——`OTHER=0, INSERT=1, UPDATE=2, ...`（`BusinessType.java:25-75`）。**存的是数字**，前端拿数字对照枚举显示（"新增/修改/删除"）。**注意：如果中途往枚举中间插值，历史数据的含义会错位**——**枚举用于持久化时，稳妥做法是显式指定 code，别依赖 `ordinal()`**（坦白点）。

### 4.3 请求参数的取法：POST 取 body，GET 取路径变量

看 `setRequestValue`（`:136-145`）：

```java
private void setRequestValue(JoinPoint joinPoint, OperLogDTO operLog) throws Exception {
    String requestMethod = operLog.getRequestMethod();
    if (HttpMethod.PUT.name().equals(requestMethod) || HttpMethod.POST.name().equals(requestMethod)) {
        String params = argsArrayToString(joinPoint.getArgs());      // :139 POST/PUT → 序列化方法参数
        operLog.setOperParam(StringUtils.substring(params, 0, 2000));// :140
    } else {
        Map<?, ?> paramsMap = (Map<?, ?>) ServletUtils.getRequest()
                .getAttribute(HandlerMapping.URI_TEMPLATE_VARIABLES_ATTRIBUTE);  // :142 GET → 取 URL 路径变量
        operLog.setOperParam(StringUtils.substring(paramsMap.toString(), 0, 2000));  // :143
    }
}
```

**为什么 GET 和 POST 取法不同？**

- **POST/PUT** 的参数在**请求体**里，Spring 已解析成方法参数 → 直接 `joinPoint.getArgs()` 序列化；
- **GET** 的参数在 **URL 路径**里（如 `/contract/draft/{id}` 的 `id`）→ 从 Spring 的 `URI_TEMPLATE_VARIABLES_ATTRIBUTE` 属性里取。

**"过滤掉不该记的参数"** —— `isFilterObject`（`:173-191`）：

```java
public boolean isFilterObject(final Object o) {
    Class<?> clazz = o.getClass();
    if (clazz.isArray())      return clazz.getComponentType().isAssignableFrom(MultipartFile.class);  // 文件数组
    else if (Collection...)   // 集合里的文件
    else if (Map...)          // Map 里的文件
    ...
    return o instanceof MultipartFile            // 文件
        || o instanceof HttpServletRequest        // 请求对象
        || o instanceof HttpServletResponse       // 响应对象
        || o instanceof BindingResult;            // 校验结果
}
```

**过滤掉四类"不该进日志"的对象**：**上传的文件（`MultipartFile`）、`HttpServletRequest`/`Response`、`BindingResult`**。

**为什么？** ——**① 文件序列化会炸（或超大）**；**② 请求/响应对象含大量内部状态，序列化无意义且可能循环引用**；**③ `BindingResult` 是校验容器，没有业务信息**。**这是"日志参数要筛"的工程细节**——**不筛就等着日志里出现一堆乱码/异常。**

> ⚠️ **坦白点（上传文件的日志里看不到参数）**：因为 `MultipartFile` 被过滤，**上传/导入这类接口的 `operParam` 里看不到任何东西**（文件被跳过了）。**如果业务上需要"谁上传了什么文件名"，得在业务代码里手动记**——`@Log` 帮不了。

### 4.4 异步落库

**接口层声明异步**（`OperLogService.java:26`）：

```java
public interface OperLogService {

    void recordOper(OperLogDTO operLogDTO, String tenantId);

```

**实现层真正落库**（`SysOperLogServiceImpl.java:47`）：

```java
@RequiredArgsConstructor
@Service
public class SysOperLogServiceImpl implements ISysOperLogService, OperLogService {

    private final SysOperLogMapper baseMapper;

    @Async                                                          // :56
    @Override
    public void recordOper(final OperLogDTO operLogDTO, String tenantId) {   // :58
        SysOperLog operLog = BeanUtil.toBean(operLogDTO, SysOperLog.class);
        // operLog.setOperLocation(AddressUtils.getRealAddressByIP(operLog.getOperIp()));  // :61 注释掉了
        operLog.setTenantId(tenantId);                              // :62 ★ 补上租户

    @Override
    public void insertOperlog(SysOperLog operLog) {                 // :97
        operLog.setOperTime(new Date());                            // :98
        baseMapper.insert(operLog);
    }
}
```

**关键理解**：

1. **为什么要显式传 `tenantId`？**（`:58` 的第二个参数）—— 因为 **`@Async` 方法在"另一个线程"里执行**，**那个线程没有登录态**（`LoginHelper.getLoginUser()` 拿不到，`ThreadLocal` 不跨线程！）。**所以必须在"主线程"里先把 `tenantId` 取出来当参数传进去**，异步线程才能用它。
   > 📌 **这是"异步 + ThreadLocal"的经典坑**：**`ThreadLocal` 不跨线程**，任何异步/线程池场景都要**把 ThreadLocal 里的值"显式传参"过去**。
2. **`operTime` 在插入时设**（`:98`）——**"真正落库的时间"**，而不是"切面触发的时间"（异步会有一点延迟）。
3. **`operLocation` 被注释掉了**（`:61`）——**IP 归属地解析本项目没启用**（和第 5 章 `loginLocation` 是同一个坦白点）。

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：你们的操作日志怎么实现的？**

**注解 + AOP + 异步**。方法上标 `@Log(title=..., businessType=...)`（`Log.java:29`）；`LogAspect`（`LogAspect.java:50`）用 `@AfterReturning`（`:57`）和 `@AfterThrowing`（`:68`）拦截，`handleLog`（`:73`）装配信息（操作人、IP、URL、方法、参数、结果、异常），最后通过 `SpringUtils.getBean(OperLogService.class).recordOper(...)`（`:97`）**异步落进 `sys_oper_log`**。

**追问：`@Async` 方法如果被同一个类里的 `this.recordOper(...)` 调用，还会异步吗？**
**不会。** `@Async` 依赖 Spring 生成的代理对象；`this` 调用绕过了代理，直接执行原方法，等同于普通同步调用。所以这里特意用 `SpringUtils.getBean(...)` 拿到代理 Bean 再调。

**Q2：为什么日志要异步写？**

**不拖慢主流程、不连累业务**。写日志是"额外开销"，同步写会多一次数据库往返、用户等待变长；而且**日志表出问题不该导致业务失败**。`OperLogService.recordOper` 标了 `@Async`（`OperLogService.java:26`），`AsyncConfig`（`@EnableAsync`，`AsyncConfig.java:35`）统一用系统线程池执行。

**Q3：★ 异步方法里怎么拿到"当前租户"？（ThreadLocal 的坑）**

**`ThreadLocal` 不跨线程**，异步线程里 `LoginHelper.getLoginUser()` 拿不到登录态。**所以必须在主线程里先把 `tenantId` 取出来、当参数传给异步方法**——看 `recordOper(operLog, LoginHelper.getTenantId())`（`LogAspect.java:97`）和 `SysOperLogServiceImpl.recordOper(..., String tenantId)`（`:58`）里 `setTenantId(tenantId)`（`:62`）。**这是所有"异步 + 上下文"场景的通用解法：值要显式传参，不能靠 ThreadLocal。**

**Q4：日志记录失败了会影响业务吗？**

**不会。** `handleLog` 整个包在 `try/catch` 里（`LogAspect.java:74/98`），切面出错只打本地 error 日志（`:100`），**业务照常返回**。**"日志是旁路，绝不能反噬主流程"**——这是日志组件的铁律。

**Q5：操作日志和登录日志有什么区别？**

两张表、两套机制。**操作日志**（`sys_oper_log`）记"登录后干了什么"，用 `@Log` 注解触发；**登录日志**（`sys_logininfor`）记"登录这件事本身"，在 `SysLoginService` 里**显式调用** `recordLogininfor`（`SysLogininforServiceImpl.java:63`）。**关键区别**：登录那一刻**还没有"操作人上下文"给切面用**，所以登录日志不能靠 `@Log`，只能显式记。

**Q6：登录失败为什么要记日志？**

**安全审计**。一次两次失败正常，**同一用户名/IP 短时间大量失败 = 暴力破解**。本项目在 `SysLoginService` 里登录失败、密码错误、**错误次数超限被锁**、验证码错误（`:100/:112/:117/:202/:206`）**都记登录日志**。**"记失败"比"记成功"更有安全价值**——它是发现攻击的第一手数据。

**追问：登录失败的日志会不会把用户输入的密码也记下来？**
**不会。** `recordLogininfor` 的入参只有 `tenantId/username/status/message/request/args`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/service/LogininforService.java:25-26`），密码根本没有进入日志链路；`message` 是"验证码错误""密码错误次数过多"这类文案。

**Q7：日志里的参数会不会泄露敏感信息？**

**有风险，靠两个手段控制**：① **`@Log(isSaveRequestData = false)`**（`Log.java:48`）——**改密码、改敏感配置的接口必须关掉参数记录**；② **截断 2000 字符**（`LogAspect.java:126/:140`）。**但坦白说，普通接口的请求参数是原样记的**——**如果业务参数里含密码/身份证，得靠开发在注解上关掉，框架不会自动识别。**

**Q8：日志表会不会越来越大？**

**会。** 所以有 `cleanOperLog`（`SysOperLogServiceImpl.java:154`，**清空操作日志**）和删除接口，前端监控页可以手动清。**更规范的做法是"定时归档 + 分区表 + TTL"**——**坦白说本项目只提供了"手动清空"，没有自动归档策略**。

**Q9：为什么不直接在切面里 `@Autowired` 注入 `OperLogService`？**

**模块解耦**。`LogAspect` 在 `ruoyi-framework`，`OperLogService` 的实现（`SysOperLogServiceImpl`）在 `ruoyi-system`。**`framework` 不该依赖 `system` 的实现类**（回忆第 0 章依赖方向）。所以用 **`SpringUtils.getBean(接口.class)`（`:97`）运行期取 Bean**——**只依赖接口（在 `ruoyi-common`），依赖倒置。**

**Q10：为什么 URL 之外还要记"Java 方法名"？**

**为了排查能直达代码**。`com.ruoyi.conf.controller.TSigningSubjectController.add()`（`LogAspect.java:91`）能让开发者**直接定位到文件和行**；URL 会随路由调整而变，Java 方法名不会。**"日志要能指引到代码"是好日志的标准。**

### 本章答辩卡（追问级）

**追问组 1：接口没有抛异常、只是返回了 `R.fail`，操作日志的 `status` 记成功还是失败？**

- **10 秒答案**：记**成功**。`handleLog` 只根据"方法有没有抛异常"来判断（`e != null`），返回 `R.fail` 属于正常返回，走的是 `@AfterReturning`，所以 `status` 先被设成 `SUCCESS` 后不会再改。
- **证据**：`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/LogAspect.java:57`（正常返回通知）、同文件 `:77`（默认成功）、`:84-86`（只有异常才改失败）。
- **一句话总结**：`sys_oper_log.status` 表示"接口有没有崩"，不表示"业务有没有成功"。

**追问组 2：异步写日志失败了，会不会把业务事务一起回滚？**

- **10 秒答案**：**不会**。日志落库在另一条线程、另一个事务里执行；主线程的 `handleLog` 只是把任务提交给代理对象，而且外层还有 `try/catch` 兜住。代价是日志可能"静默缺失"，只能靠异步异常处理器记一条 error。
- **证据**：`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/service/OperLogService.java:26-27`（`@Async`）、`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/LogAspect.java:74` 与 `:98`（try/catch）、`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/AsyncConfig.java:56-58`（异常只记日志）。
- **一句话总结**：异步隔离了故障，也隔离了"你发现日志没写进去"的能力。

**追问组 3：`@Async` 为什么必须通过注入的 Bean 调用，不能 `this.recordOper(...)`？**

- **10 秒答案**：`@Async` 是 Spring 通过**代理对象**加上的能力；`this` 调用绕过代理，直接执行原方法，异步注解等于没写。本项目用 `SpringUtils.getBean(OperLogService.class)` 取到代理 Bean 再调用，所以 `@Async` 生效。
- **证据**：`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/LogAspect.java:97`（从容器取 Bean 再调）、`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/service/OperLogService.java:26`（接口方法上的 `@Async`）、实现类 `ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysOperLogServiceImpl.java:56`（实现方法上也标了 `@Async`）。
- **一句话总结**：注解是给代理看的，不是给 `this` 看的。

## 七、选型对比：日志方案

### 7.1 操作日志的实现方式

| 方式 | 做法 | 侵入性 | 漏记录风险 | 本项目 |
|---|---|---|---|---|
| 手写插入 | 每个方法里 `insert log` | **高** | **高（必漏）** | ✗ |
| **注解 + AOP（本项目）** | `@Log` + 切面 | **低（一行注解）** | 低（标了就有） | **✔** |
| 数据库触发器 | 表上触发器记录 | 无 | — | ✗（拿不到"用户"上下文） |
| 网关/中间件 | 网关层统一记 | 无 | — | ✗（拿不到业务语义） |

**结论**：**"注解 + AOP"在"业务语义"和"低侵入"之间平衡最好**——**能记"模块/业务类型"这种业务信息，又不用改业务代码。**

### 7.2 日志写入方式

| 方式 | 用户等待 | 业务风险 | 本项目 |
|---|---|---|---|
| 同步写 | **加长** | **日志失败连累业务** | ✗ |
| **异步写（本项目）** | **无感知** | 隔离 | **✔** |
| 消息队列 | 无感知 | 隔离 + 削峰 | ✗（单体系统过度设计） |

**结论**：**异步足矣**；**高并发场景才会引入 MQ 削峰**（本项目单体，`@Async` 够用）。

### 7.3 日志存储

| 方案 | 查询 | 实时性 | 本项目 |
|---|---|---|---|
| **数据库表（本项目）** | 页面可按条件查 | 好 | **✔** |
| 文件 + ELK | 强大（全文检索） | 好 | ✗（本项目 `log.info` 也打了，但没接 ELK） |
| 只用文件 | 弱 | 好 | ✗ |

**结论**：**业务要"页面查日志"，就必须落库**；**文件日志是补充**（本项目登录日志两者都写，`:76`）。

## 本章小结 & 下一步

- **两类日志**：**操作日志**（`sys_oper_log`，`@Log` 触发，记"干了什么"）+ **登录日志**（`sys_logininfor`，显式调用，记"怎么进来的"）。
