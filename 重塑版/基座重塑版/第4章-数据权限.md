# 第 4 章 · 数据权限 ★

> **第 3 章回答「你能不能调这个接口」，本章回答「调了之后你能看见哪些行」。** 同样是 `GET /contract/book/list`（合同台账列表），销售只能看到自己部门的合同，财务能看到全公司——**SQL 语句被人"偷偷改了一笔"，业务代码完全不知情**。
>
> **本章是整套基座里最值得讲的一块**，因为它是本项目对开源框架**最重的一处定制**：标准轨（`@DataPermission` + `DataScopeType`）之外，又加了一条**按业务模块分列的定制轨**（`ContractPermission` + 反射读 `sys_role` 上的 10 个列）。面试时能把这套设计讲清楚，基本就站在「看懂过真实生产代码」这一档了。
>
> **本章第一次讲透**：① 数据权限和接口权限的本质区别（行级 vs 接口级）；② `@DataPermission` 注解 + SpEL 模板 + **JSqlParser 无痕改写 SQL** 的机制；③ 标准轨 5 码 vs 定制轨 7 码的**双轨设计**；④ 为什么本项目要**给 `sys_role` 加 10 个业务列**、靠反射去读；⑤ `#user.deptId`（单数）和 `LoginUser.deptIds`（数组）这个**本项目特有的不一致**。

## 一、这部分是做什么的？

> ### 零基础先补概念
>
> 这一章会出现 4 个"没学过也正常"的词，先用大白话说清：
>
> 1. **注解（Annotation）**：写在 Java 方法/类上面的"标签"，本身不执行代码，但程序可以在运行时读到它。本项目的 `@DataPermission` 就是贴在 Mapper 方法上的标签，意思是"这个方法要加数据权限"（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/annotation/DataPermission.java:29-32`）。
> 2. **SpEL（Spring Expression Language）**：Spring 自带的"小型表达式语言"，能写 `#{#user.userId}` 这种占位符，运行时再替换成真实值。本项目的权限条件模板就是 SpEL，例如 `#{#userId} IN ( #{@sdss.getDeptUser( #user )} )`（`ContractPermission.java:46`）。
> 3. **SQL 解析 / 改写**：把一条 SQL **字符串**先解析成"语法树"（程序能读懂的树形结构），在树上加一个 `WHERE` 条件，再转回字符串。本项目用 JSqlParser 做这件事，入口在 `PlusDataPermissionInterceptor.java:46`。
> 4. **反射（Reflection）**：Java 在运行时按"名字"去读对象的字段，比如 `ReflectUtil.getFieldValue(role, "contractPermission")`——名字是字符串，所以可以按数据库列名动态取值（`PlusDataPermissionHandler.java:141`）。

### 1.1 数据权限 vs 接口权限

| | 接口权限（第 3 章） | 数据权限（本章） |
|---|---|---|
| 拦在哪 | 方法入口（拦截器） | **SQL 执行前（SQL 改写）** |
| 拦什么 | 这个接口**能不能调** | 这条 SQL 里**能查到哪些行** |
| 粒度 | 接口级 / 按钮级 | **行级（row-level）** |
| 类比 | 能不能进这栋楼 | 进了楼**只能进自己那几间办公室** |

**一个具体场景**：`GET /contract/book/list`（合同台账列表，`ContractBookController.java:82-98`）这个接口，**所有销售都能调**（接口权限没问题）。但：
- 张三（销售一部）调，返回**销售一部**的合同；
- 李四（销售二部）调，返回**销售二部**的合同；
- 王五（总经理）调，返回**全公司**的合同。

**同一个接口、同一个 SQL、不同的人看到不同的行**——这就是数据权限。它在 SQL 层做，**业务 Service 里一行判断都不用写**。

### 1.2 七种"数据范围"

所有数据权限系统，最后都要回答「这个人能看哪些数据」，本项目把它归纳成**几个档次**（码值越大不一定越宽，要看具体语义）：

| 码 | 含义 | 典型角色 | 出自哪条轨 |
|---|---|---|---|
| 1 全部数据 | 不限制 | 总经理、超管 | 两条轨都有 |
| 2 自定义数据 | 手选几个部门/人 | 特殊情况 | 两条轨都有 |
| 3 本部门数据 | 只看自己所在部门 | 部门主管 | 两条轨都有 |
| 4 本部门及以下 | 自己部门 + 所有子部门 | 大区经理 | 两条轨都有 |
| 5 仅本人数据 | 只看自己录的 | 普通销售 | 两条轨都有 |
| 6 我负责的部门 | 我是负责人/助理的部门里的人 + 我本人 | 部门负责人 / 部门助理 | **仅定制轨**（`MYDEPT`） |
| 7 我负责的部门及以下 | 上面这些部门 + 它们的子部门 | 部门负责人（要看下级） | **仅定制轨**（`MYDEPT_AND_CHILD`） |

前 5 个是 RuoYi 系框架的"标配"；**第 6、7 个（`MYDEPT` / `MYDEPT_AND_CHILD`）是本项目加的**——注意它们不是"本部门+子部门+本人"的同义词，而是"**我作为 leader/助理负责的部门**"这一维度，后面 §2.5 讲清。

### 1.3 关键结论：数据权限是"改 SQL"，不是"筛结果"

新手最容易想到的做法是「先把全部查出来，在 Java 里 `if` 过滤掉不该看的」。**这是错的**，因为：

1. **分页会错**：你先查 100 条再过滤剩 10 条，分页总数就不对了；
2. **性能差**：本来数据库只需返回 10 行，你却先捞了 100 行；
3. **易漏**：几十个查询方法，你要挨个写过滤逻辑。

**本项目的做法**：拦截 MyBatis 的 SQL，**在"数据权限字段"上拼一个 WHERE 条件**，让数据库自己去过滤。业务代码**完全无感**。

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么要在 SQL 层做，而不是 Service 层？

**因为"看不见的数据"必须连"存在"都不能泄露。** 假如在 Service 层过滤，恶意用户改一下分页参数或直接调别的接口，就可能把别人的数据翻出来。**在 SQL 层加 `WHERE`，是"从根上不给"，不是"拿回来了再藏起来"。**

而且 SQL 层能做**分页正确**——`count` 和 `list` 用的是同一套 `WHERE`，总数天然对齐。

### 2.2 怎么"改 SQL"却不碰业务代码？—— MyBatis 拦截器 + JSqlParser

思路分三步：

1. **拦截**：注册一个 MyBatis 拦截器，在 SQL 真正执行前拿到它；
2. **解析**：用 **JSqlParser**（一个 Java 的 SQL 解析库）把 SQL 字符串解析成**语法树（AST）**；
3. **改写**：在语法树上找到 `WHERE` 节点，**`AND` 上一个数据权限条件**，再转回 SQL 字符串扔给数据库。

**为什么用 JSqlParser 而不是拼字符串？** 因为 `WHERE` 有无、`AND`/`OR` 优先级、子查询、`JOIN`……情况太多，**字符串拼接必崩**。解析成语法树后，插入条件是**结构化操作**，稳。

> ⚠️ **它不是"整个 SQL 重写"，而是精准地往 WHERE 里塞一个条件。** 这就是 §5 流程图里那句「SQL 被无痕改写」的含义。

### 2.3 权限条件从哪来？—— SpEL 模板 + 注解

看核心枚举 `DataScopeType.java`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/DataScopeType.java`）：

```java
public enum DataScopeType {
    ALL("1", "", ""),                                                       // :40 全部
    CUSTOM("2", " #{#deptName} IN ( #{@sdss.getRoleCustom( #user.roleId )} ) ", ""),  // :45 自定义
    DEPT("3", " #{#deptName} = #{#user.deptId} ", ""),                       // :50 本部门
    DEPT_AND_CHILD("4", " #{#deptName} IN ( #{@sdss.getDeptAndChild( #user.deptId )} )", ""), // :55 本部门及以下
    SELF("5", " #{#userName} = #{#user.userId} ", " 1 = 0 ");                // :60 仅本人
    private final String code;            // 存进 sys_role.data_scope 的值（:62）
    private final String sqlTemplate;     // ★ SpEL 模板（:67）
    private final String elseSql;         // 兜底 SQL（:72）
    public static DataScopeType findCode(String code) { ... }   // :74
}
```

**这串 `sqlTemplate` 是 SpEL（Spring 表达式）**，不是 SQL。它里面有几个约定：

| 写法 | 含义 | 谁来填 |
|---|---|---|
| `#{#deptName}` / `#{#userId}` / `#{#userName}` | **SpEL 变量名**——对应 `@DataColumn.key()`（默认 `deptName`） | 注解决定 |
| `#{#user.deptId}` | 当前登录用户的部门 ID（注意：本项目的 `LoginUser` 只有 `deptIds` 数组，没有这个字段，见 §2.5 坦白点） | `LoginUser` |
| `#{#user.roleId}` | 当前角色 ID——注意它是 handler 在循环里 `user.setRoleId(role.getRoleId())` 临时塞进去的（`PlusDataPermissionHandler.java:137-138`） | `RoleDTO` 转存 |
| `#{@sdss.xxx(...)}` | **调用 Spring 容器里名为 `sdss` 的 Bean**（`SysDataScopeServiceImpl`，`@Service("sdss")`） | 容器 |

**`@DataColumn` 的两个属性别搞混**：`key` 是 SpEL 里的变量名（`DataColumn.java:32`，默认 `deptName`），`value` 才是真正拼进 SQL 的列名（`DataColumn.java:37`，默认 `dept_id`）。本项目**实际业务代码用的是 `key = "userId"`**，例如 `@DataColumn(key = "userId", value = "drafter_id")`（`ContractDraftMapper.java:42`），所以定制轨模板里写的是 `#{#userId}`。

**为什么要用 SpEL 而不是写死 SQL？** 因为"本部门及以下"这种条件**不是一个常量**——它得先查"我部门的所有子部门有哪些"。SpEL 让模板可以**调用 Java 方法**（例如定制轨的 `@sdss.getDeptAndChildUser`），把「动态查出来的部门/用户 ID 列表」拼进 SQL。**这就是"模板 + 回调"的组合。**

### 2.4 ★ 本项目的双轨设计：为什么给 `sys_role` 加了 10 个列？

**这是全章最该讲的一点。**

**标准轨**（框架自带）：`sys_role.data_scope` **一个列**，存一个"数据范围码"（1-5）。**一个角色一个数据范围。**

但本项目有一个业务现实：**同一个角色，在不同业务模块下需要的可见范围不一样。** 举个例子：

> 「销售主管」这个角色——在**合同模块**要能看到**本部门**的合同；但在**台账/计划模块**可能只想看**自己的**；在**印章模块**又要看**本部门及以下**的。

如果只有 `data_scope` 一个列存不下这些差异。于是本项目**给 `sys_role` 表加了 10 个业务列**：

`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/DataPermissionResource.java:22-32`：

```java
public enum DataPermissionResource {
    base("base", "默认"),                                      // :22 ★ 标准轨，读 sys_role.data_scope
    draftPermission("draftPermission", "草拟中的合同权限"),      // :23 以下为定制轨，各读 sys_role 上同名列
    contractPermission("contractPermission", "审批完成的合同权限"), // :24
    dashboardPermission("dashboardPermission", "仪表盘权限"),    // :25
    collabPermission("collabPermission", "协同权限"),           // :26
    ledgerPermission("ledgerPermission", "台账权限"),           // :27
    stampPermission("stampPermission", "用印权限"),             // :28
    planPermission("planPermission", "计划权限"),               // :29
    comparePermission("comparePermission", "合同比对数据权限"),  // :30
    partnerPermission("partnerPermission", "相对方数据权限"),    // :31
    workPermission("workPermission", "工作交接数据权限");        // :32
    // 注释（:18-21）明确说：index 需要和 role 表的字段名一一对应
}
```

对应到 `SysRole.java:144-153`，`sys_role` 表上真有这 10 个列（数据库里列名是大写，如 `CONTRACT_PERMISSION`，见 `zxcm_init.sql:4365-4374`）：

```java
private String draftPermission;      // :144
private String contractPermission;   // :145
private String dashboardPermission;  // :146
private String collabPermission;     // :147
private String ledgerPermission;     // :148
private String stampPermission;      // :149
private String planPermission;       // :150
private String comparePermission;    // :151
private String partnerPermission;    // :152
private String workPermission;       // :153
```

**所以本项目有两条轨：**

| | 标准轨 | 定制轨 |
|---|---|---|
| 注解写法 | `@DataPermission`（`resource` 默认 `base`） | `@DataPermission(resource = DataPermissionResource.contractPermission)` |
| 数据范围码存在哪 | `sys_role.data_scope`（框架列） | `sys_role.contractPermission` 等 **10 个业务列** |
| 码表 | `DataScopeType`（5 码：ALL/CUSTOM/DEPT/DEPT_AND_CHILD/SELF） | `ContractPermission`（**7 码**：多出 `MYDEPT` / `MYDEPT_AND_CHILD`） |
| 怎么取值 | `role.getDataScope()`（直接 getter） | **反射**：`ReflectUtil.getFieldValue(role, resource.getIndex())` |

**为什么定制轨要用"反射"？** 因为 `PlusDataPermissionHandler` 是**通用代码**，它不知道 `contractPermission` 这个列对应 `SysRole` 的哪个 getter。用反射 `getFieldValue(role, "contractPermission")` 就能**按列名动态取值**——新增一个业务列，**Handler 一行都不用改**。这是"用列名当索引"的设计。

> 📌 **面试价值**：这一段是"我读过真实项目定制代码"的铁证。能讲清楚「为什么要多轨」「为什么要用反射」「加了哪 10 个列」，比背八股强得多。

### 2.5 为什么定制轨多出两个码？

`ContractPermission.java:31-91` 定制轨码表：

```java
ALL("1", "", ""),                                             // :36 全部
CUSTOM("2", " 1=0 ", ""),                                     // :41 自定义（本项目未实现，写死"看不到"）
DEPT("3", " #{#userId} IN #{@sdss.getDeptUser( #user )} ", ""), // :46 我所在部门的人（注意：模板里 IN 后面没有括号）
DEPT_AND_CHILD("4", " #{#userId} IN ( #{@sdss.getDeptAndChildUser( #user )} )", ""), // :51 我所在部门及以下的人
SELF("5", " #{#userId} = #{#user.userId} ", " 1 = 0 "),       // :56 仅本人
MYDEPT("6", " #{#userId} IN ( #{@sdss.getMyDeptUser( #user )} )", " 1 = 0 "), // :62 ★ 本项目新增：我负责的部门里的人
MYDEPT_AND_CHILD("7", " #{#userId} IN ( #{@sdss.getMyDeptAndChildUser( #user )} )", " 1 = 0 "); // :66 ★ 本项目新增
```

> ⚠️ **读代码时发现的一个细节**：码 3（`DEPT`）的模板是 `#{#userId} IN #{@sdss.getDeptUser(...)}`，而 `getDeptUser` 返回的是 `'101','102'` 这种**带引号、不带括号**的字符串（`SysDataScopeServiceImpl.java:143-148`）。拼出来会变成 `user_id IN '101','102'`，**缺少一对括号**。种子数据里没有角色把某列配成 `'3'`（`zxcm_init.sql:4391-4401` 能看到的是 1/2/4/5/7），所以这条码大概率没被真正跑过。**别把它当成"验证过的功能"讲。**

**`MYDEPT` / `MYDEPT_AND_CHILD` 是本项目加的，但它们解决的不是"用户有多个部门"**——那件事定制轨的 3/4 码已经解决了：

- `DEPT` / `DEPT_AND_CHILD` 调用的 `getDeptUser` / `getDeptAndChildUser`（`SysDataScopeServiceImpl.java:132` / `:78`）**查的是 `sys_user_dept` 表**：一个用户在几张部门关联表里，就取几个部门，**天然支持多部门**。
- `MYDEPT` / `MYDEPT_AND_CHILD` 调用的 `getMyDeptUser` / `getMyDeptAndChildUser`（`SysDataScopeServiceImpl.java:159` / `:185`）**查的是"我负责的部门"**——`SysDeptServiceImpl.getMyDept` 的条件是 `leader = 当前用户` 或 `assistant = 当前用户`（`SysDeptServiceImpl.java:453-459`），再把"负责人本人"额外加进去（`SysDataScopeServiceImpl.java:168-170` / `:202-204`）。**这是"部门负责人/助理"视角，不是"成员的部门"视角。**

一句话区分：**3/4 码 = "我在哪些部门，就看这些部门的人"；6/7 码 = "我管哪些部门，就看这些部门的人"。**

> ⚠️ **坦白点（标准轨在本项目里是"框架遗产"）**：标准轨的 `DEPT` / `DEPT_AND_CHILD` 模板用的是 `#{#user.deptId}`（`DataScopeType.java:50` / `:55`），**但本项目的 `LoginUser` 根本没有 `deptId` 字段，只有 `deptIds` 数组**（`LoginUser.java:45`）。而且 `SELF` 模板用的是 `#{#userName}`（`DataScopeType.java:60`），默认 `@DataColumn.key()` 却是 `deptName`。**也就是说：标准轨的这几条模板如果真跑到本项目上，变量根本对不上。** 本项目的实际做法是：**业务模块都走定制轨**（所以才有那 10 个列），标准轨只是"框架遗产"。面试若被追问「多部门怎么处理数据权限」，答「定制轨的 3/4 码查 `sys_user_dept` 天然多部门；6/7 码处理'我负责的部门'」即可，别硬说标准轨也支持。

### 2.6 谁是 `sdss`？—— 数据范围服务实现

`ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysDataScopeServiceImpl.java`：

```java
@Service("sdss")                                              // :43 ★ SpEL 里的 @sdss 就是它
public class SysDataScopeServiceImpl implements ISysDataScopeService {

    public String getRoleCustom(Long roleId) { ... }          // :53 自定义角色选的部门
    public String getDeptAndChild(Long deptId) { ... }        // :63 本部门及以下
        // :65 关键 SQL：find_in_set({0}, ancestors)  ← 用 ancestors 路径一次性捞全部子孙部门
    public List<Long> getDeptAndChildUser(SysUser user) { ... } // :78
    public List<Long> getDeptUser(SysUser user) { ... }       // :132 本部门所有人
    public List<Long> getMyDeptUser(SysUser user) { ... }     // :159 ★ 多部门版
    public List<Long> getMyDeptAndChildUser(SysUser user) { ... } // :185 ★ 多部门版
}
```

**`getDeptAndChild` 是这里的明星**（`:63-65`）：查"本部门及以下"，不用递归，而是利用 `sys_dept.ancestors`（一张表存着"1,3,7"这种祖先路径）一路 `find_in_set`——**一条 SQL 捞出全部子孙部门**。这是**空间换时间**的经典做法。

## 四、功能具体怎么实现（带着你读懂）

### 4.1 怎么用：一个 Mapper 方法要做的三件事

**第一步：在 Mapper 方法上打 `@DataPermission`**

```java
// ContractDraftMapper.java:42-46
@DataPermission(value = {@DataColumn(key = "userId", value = "drafter_id")},
    resource = DataPermissionResource.draftPermission)   // ★ 定制轨：读 sys_role.DRAFT_PERMISSION
@Select("SELECT * FROM contract_draft ${ew.customSqlSegment}")
Page<ContractDraft> selectDraftPage(Page<ContractDraft> page,
    @Param(Constants.WRAPPER) Wrapper<ContractDraft> queryWrapper);
```

如果**不写 `resource`**，就是标准轨（读 `sys_role.data_scope`）。写法是只给 `value`：

```java
@DataPermission({ @DataColumn(key = "deptName", value = "d.dept_id") })
```

但本项目源码里**标准轨的例子都被注释掉了**（`SysUserMapper.java:59-62`），实际在跑的业务方法全都显式写了 `resource = ...`——这也是 §2.5 说的"标准轨是框架遗产"。

**第二步：用 `@DataColumn` 指定"拼在哪个字段上"**

`@DataColumn`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/annotation/DataColumn.java:27-39`）有两个属性：

```java
String key()   default "deptName";   // :32 对应 SpEL 模板里的变量名 #{#deptName}
String value() default "dept_id";    // :37 ★ 实际拼进 SQL 的列名
```

本项目**实际用的是 `key = "userId"`**——因为定制轨的模板写的是 `#{#userId}`（`ContractPermission.java:46/51/56/62/66`）。所以 `ContractDraftMapper.java:42` 这一行会把模板里的 `#{#userId}` 替换成 `drafter_id`。

**注意 `@DataPermission.value()` 没有默认值**（`DataPermission.java:31`），也就是说 `@DataColumn` **必须写**：哪怕只想用默认列名，也得写 `@DataPermission({@DataColumn(...)})`。网上有些教程写 `@DataPermission` 光秃秃一个注解，那是别的版本，**在本项目会编译不过**。

**换成别的过滤字段，只需改 `value`**。比如合同台账按"合同负责人"过滤：

```java
// ContractDraftMapper.java:160-161
@DataPermission(value = {@DataColumn(key = "userId", value = "a.contract_charge_id")},
    resource = DataPermissionResource.ledgerPermission)
```

同一个数据范围码，`#{#userId}` 就被替换成 `a.contract_charge_id`——**过滤字段变了，权限逻辑没变**。这就是为什么 Mapper 上到处是 `a.xxx` 带表别名的写法：SQL 里有 JOIN，不写别名会"列名歧义"。

> ⚠️ **注解只标在"主表查询"的方法上**。像 `selectById`、`selectOne` 这种单条查询**一般不标**——否则关联查询会因为过滤条件查不到数据。**这是实际项目里最容易踩的坑**：标多了会因为 JOIN 表没有对应列而报错。

**第三步：什么都不用做**——Service、Controller 照常写，**过滤是自动发生的**。

### 4.2 ★ 核心：`PlusDataPermissionHandler` 怎么改写 SQL

`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/handler/PlusDataPermissionHandler.java`（`:64-239`）。这是全项目的"最硬核"文件，我们分步拆。

**（1）入口：`getSqlSegment`（`:87`）**

```java
public Expression getSqlSegment(Expression where, String mappedStatementId, boolean isSelect) { // :87
    DataPermission dataPermission = findAnnotation(mappedStatementId);            // :88
    if (dataPermission == null || ArrayUtil.isEmpty(dataPermission.value())) {    // :89
        inavlidCacheSet.add(mappedStatementId);                                   // :90
        return where;                                                             // :91 没注解→原样返回
    }
    LoginUser currentUser = DataPermissionHelper.getVariable("user");             // :93
    // ……为空则取当前登录用户并放进变量（:94-97）……
    if (LoginHelper.isTenantAdmin()) { return where; }                            // :98-101 租户管理员放行
    String dataFilterSql = buildDataFilter(dataPermission, isSelect);             // :102 生成条件字符串
    if (StringUtils.isBlank(dataFilterSql)) { return where; }                     // :103-105 空→原样返回
    Expression expression = CCJSqlParserUtil.parseExpression(dataFilterSql);      // :107 字符串→语法树
    Parenthesis parenthesis = new Parenthesis(expression);                        // :109 套一层括号
    if (ObjectUtil.isNotNull(where)) {
        return new AndExpression(where, parenthesis);                             // :111 原有条件 AND 数据权限
    } else {
        return parenthesis;                                                       // :113 原来没 WHERE，直接用
    }
}
```

**（2）构建条件：`buildDataFilter`（`:123`）**

```java
private String buildDataFilter(DataPermission dataPermission, boolean isSelect) {  // :123
    StringBuilder sqlString = new StringBuilder();                                // :124
    String joinStr = isSelect ? " OR " : " AND ";                                 // :126 ★ 见下
    // ……准备 SpEL context、取出 user（:127-130）……
    for (DataColumn dataColumn : dataPermission.value()) {                        // :132
        context.setVariable(dataColumn.key(), dataColumn.value());                // :134 #{#userId} → drafter_id
    }
    for (RoleDTO role : user.getRoles()) {                                        // :137 每个角色一条条件
        user.setRoleId(role.getRoleId());                                         // :138 供 #{#user.roleId} 用
        if (!dataPermission.resource().equals(DataPermissionResource.base)) {     // :139 ★ 定制轨
            String resourceP = (String) ReflectUtil.getFieldValue(
                    role, dataPermission.resource().getIndex());                  // :141 反射取列值
            if (StringUtils.isEmpty(resourceP)) { return ""; }                    // :142-143 ★ 空列=不加条件
            ContractPermission type = ContractPermission.findCode(resourceP);     // :145 7 码
            if (type == ContractPermission.ALL) { return ""; }                    // :150-152 全部→不加条件
            String sql = parser.parseExpression(type.getSqlTemplate(), parserContext)
                    .getValue(context, String.class);                             // :156 SpEL 求值
            sqlString.append(joinStr).append(sql);                                // :157 拼到总条件
            isSuccess = true;                                                     // :158 ★ 恒 true
            if (!isSuccess) { sqlString.append(joinStr).append(type.getElseSql()); } // :161-163 ★ 走不到
        } else {                                                                  // :166 ★ 标准轨
            DataScopeType type = DataScopeType.findCode(role.getDataScope());     // :168 getter 取 data_scope
            if (type == DataScopeType.ALL) { return ""; }                         // :176-178
            String sql = parser.parseExpression(type.getSqlTemplate(), parserContext)
                    .getValue(context, String.class);                             // :182
            sqlString.append(joinStr).append(sql);                                // :183
            isSuccess = true;                                                     // :184
        }
    }
    if (StringUtils.isNotBlank(sqlString.toString())) {
        return sqlString.substring(joinStr.length());                             // :194 去掉开头的 OR/AND
    }
    return "";                                                                    // :196
}
```

**逐行读：这个方法是全章最值得逐行看的一段**

| 行号 | 这一行在干什么 | 为什么这么写 |
|---|---|---|
| `:123` | 方法返回 `String`，不是 `Expression` | 先把"条件"拼成 SQL 字符串，再统一交给 JSqlParser 解析成语法树；拼错了在这里，解析在 `:107` |
| `:126` | 查询用 `OR` 连多角色，增删改用 `AND` | 查询要"并集"（多角色能看的合起来）；写操作要"交集"（更严格） |
| `:132-134` | 把注解里的 `key/value` 灌进 SpEL 变量 | `key` 是模板占位符名，`value` 是列名；这一步之后 `#{#userId}` 才有值 |
| `:137` | 遍历用户的所有角色 | 一个用户可能挂多个角色，每个角色各有一套权限范围 |
| `:138` | 把当前循环到的 `roleId` 塞回 `LoginUser` | 因为模板里可能写 `#{#user.roleId}`，而 `#user` 是同一个 `LoginUser` 对象 |
| `:141` | 反射按 `resource` 的列名取值 | `resource.getIndex()` 就是 `"contractPermission"` 这样的字符串，用字符串取字段名，新增模块列不用改 handler |
| `:142-143` | **列值为空 → 直接 `return ""`** | 注意：`""` 在 `:103-105` 会被当成"没有条件"，等于**放行全部**——这是安全上的"默认放行"，与"默认拒绝"相反（见 §4.4 坦白点） |
| `:145` | 找定制轨码表 | 7 个码；找不到会抛 `ServiceException`（`:146-148`） |
| `:150-152` | 码是"全部" → `return ""` | 不拼任何条件 |
| `:156-157` | SpEL 求值并拼到总条件 | 多个角色之间用 `:126` 的 `joinStr` 连接 |
| `:158` | `isSuccess = true` | **紧跟上一行，恒为 true**，导致 `:161-163` 的 `elseSql` 兜底永远走不到（见 §4.4） |
| `:168` | 标准轨直接 getter 取 `data_scope` | 和 `:141` 的反射形成"双轨"的唯一区别 |
| `:194` | 去掉开头多出来的 `" OR "` / `" AND "` | 拼接时每条前面都加了连接词，最后要砍掉第一个 |
| `:196` | 没拼出任何条件就返回空串 | 上层 `:103-105` 原样返回原 SQL |

**两个关键点：**

**① `joinStr` 为什么查是 `OR`、写是 `AND`？**（`:126`）——因为**用户有多个角色时，查询的数据权限取"并集"**：角色 A 能看本部门、角色 B 能看本部门及以下，合起来就是"能看本部门及以下"。所以多个角色的条件是 **OR**。而写操作（`AND`）是为了**更严格**——写的时候必须同时满足，谨慎。

**② 每个角色怎么算条件？—— 分两条轨**（`:137-190`）：标准轨和定制轨，核心区别就是**一行 getter vs 一行反射**——`role.getDataScope()`（`:168`）和 `ReflectUtil.getFieldValue(role, resource.getIndex())`（`:141`）。**这就是"双轨"在代码层面的全部代价**，非常轻。

**（3）`findAnnotation`（`:199-231`）**：它先把 `mappedStatementId`（如 `com.ruoyi.contract.mapper.ContractDraftMapper.bookPage`）拆成类名+方法名（`:200-203`），找方法上的注解（`:205-219`），找不到再找**类上的注解**（`:220-229`）。所以注解既可以标方法，也可以标整个 Mapper 接口。

**（4）改写结果**：最终 `where` 节点上被 `AND` 上一个 `( ... )` 这样的括号表达式——**注意加了括号**（`:109` 的 `Parenthesis`），避免和原有条件优先级冲突。

### 4.3 SpEL 怎么把 "模板" 变成 "真 SQL 片段"

以定制轨的「本部门及以下」（码 4）为例，模板是（`ContractPermission.java:51`）：

```
 #{#userId} IN ( #{@sdss.getDeptAndChildUser( #user )} )
```

假设合同台账的 Mapper 写的是 `@DataColumn(key = "userId", value = "a.contract_charge_id")`（真实写法见 `ContractDraftMapper.java:160-161`），运行过程：

1. `#{#userId}` → 被 `:134` 的 `context.setVariable("userId", "a.contract_charge_id")` 替换成列名；
2. `#{#user}` → 取当前 `LoginUser`（SpEL 变量，见 `PlusDataPermissionHandler.java:93-97`）；
3. `#{@sdss.getDeptAndChildUser(#user)}` → **调用 Spring Bean** `sdss.getDeptAndChildUser(...)`，它先按 `sys_user_dept` 找"我所在的部门"，再按 `ancestors` 找子孙部门，最后返回这些部门里的用户 ID 串，例如 `'101','102','103'`（`SysDataScopeServiceImpl.java:78-124`）；
4. 最终表达式求值 → `a.contract_charge_id IN ( '101','102','103' )`。

> 📌 对比一下标准轨的同一个概念（`DataScopeType.java:55`）：它写的是 `#{#deptName} IN ( #{@sdss.getDeptAndChild( #user.deptId )} )`，**变量名 `deptName` 和属性 `deptId` 都对不上本项目的 `LoginUser`**——所以 §2.5 才说标准轨是"框架遗产"，真实业务看定制轨即可。

**关键理解**：SpEL 在这里扮演了"**模板引擎**"的角色——它把「固定部分（`dept_id IN (...)`）」和「动态部分（@sdss 查出来的部门串）」黏在一起。**如果没有 SpEL，你就得在每个枚举项里写 Java 代码来拼字符串**，那就没有"配置化"可言了。

**`#user` 是什么？** 是 SpEL 上下文里放进去的当前 `LoginUser`。它从 `LoginUser` 上能取 `deptId`、`roleId` 等（`RoleDTO` 上还有 `roleId`）。

### 4.4 `<elseSql>` 是什么？——设计意图 vs 代码现实

看 `DataScopeType.java:60` 的 SELF（仅本人）：

```java
SELF("5", " #{#userName} = #{#user.userId} ", " 1 = 0 "),
                                            ↑ elseSql
```

`elseSql` 的**设计意图**是"模板算不出结果时的兜底"。比如「自定义数据」——如果这个角色**一个自定义部门都没配**，那 `@sdss.getRoleCustom` 返回空，**这时不能放行（那就等于"全部数据"了！）**，而应**兜底成 `1 = 0`（查不到任何数据）**。

**但必须如实说：这个兜底机制在当前代码里跑不到。** `PlusDataPermissionHandler.buildDataFilter` 里：

- 定制轨 `:158` 和标准轨 `:184` 都是**求值成功后立刻 `isSuccess = true`**；
- 紧接着 `:161-163` / `:187-189` 才判断 `if (!isSuccess)`——**条件恒为 false**，`elseSql` 永远不会被拼进 SQL。

**那"配置缺失"时实际会发生什么？**

| 场景 | 真实行为 | 证据 |
|---|---|---|
| 定制轨：角色某个模块列**为空** | `return ""` → 上层视为"无附加条件" → **放行全部** | `PlusDataPermissionHandler.java:142-143`，再由 `:103-105` 返回原 `where` |
| 定制轨：码是 `CUSTOM(2)` | 模板本身写死 `1=0`，确实查不到 | `ContractPermission.java:41` |
| 定制轨：码是 `ALL(1)` | `return ""` → 放行全部（符合语义） | `PlusDataPermissionHandler.java:150-152` |
| 标准轨：`CUSTOM(2)` 没配部门 | SpEL 得到 `IN ( null )` 一类结果，`elseSql` 不会兜底 | `DataScopeType.java:45` + `:158-163` |

> ⚠️ **坦白点（安全默认值方向反了）**：定制轨的"列值为空"落到的是**默认放行**，而不是默认拒绝。**正确的安全设计应反过来：配置缺失必须收敛到最小权限（空集），绝不能放行。** 本项目目前靠"数据初始化时就给这些列填了默认值（`zxcm_init.sql:4365-4374`：前 9 个业务列 `DEFAULT '5'`，即仅本人；`WORK_PERMISSION` 为 `NULL`）"来降低风险，但代码层面并没有强制。**面试若问「数据权限怎么保证不漏」，可以先答设计原则「缺失→最小权限」，再主动指出本项目 elseSql 实际未生效、空列会放行的缺口**——这比背一句"兜底 1=0"更真实、更能加分。

### 4.5 谁调用了 `getSqlSegment`？—— MyBatis 拦截器链

`PlusDataPermissionHandler` 本身不是拦截器，它被一个 MyBatis 的 `InnerInterceptor` 调用。本项目的 MyBatis-Plus 插件链在 `ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/MybatisPlusConfig.java:44-57`（第 6 章 §2.7、第 7 章 §4.1 会细讲），实际顺序是：

```
多租户插件 → 数据权限插件 → 分页插件 → 乐观锁插件
（MybatisPlusConfig.java:47 / :51 / :53 / :55）
```

**数据权限插件**（`PlusDataPermissionInterceptor`）在 SQL 解析后，调用 `PlusDataPermissionHandler.getSqlSegment(where, msId, true)` 拿到条件，套进语法树。**这就是"SQL 被改写"发生的确切位置。**

```
     SELECT a.* FROM CONTRACT_DRAFT a LEFT JOIN ...
      WHERE a.contract_status IN (...)
        AND tenant_id = '00000000'                        ← 第 6 章
        AND ( a.contract_charge_id IN ('101','102','103') )  ← 数据权限条件
     LIMIT 0,10
  │
  ▼ MySQL 只返回张三该看的台账
  │
  ▼ 前端拿到列表（张三永远不知道"别人的合同"存在）
```

> 📌 这里**故意没写 `del_flag='0'`**：`bookPage` 是自定义 `@Select`（`ContractDraftMapper.java:162`），MyBatis-Plus 的逻辑删除**不会自动加到手写 SQL 上**（第 7 章 §4.4 讲了这个坑）。台账是否排除已删草稿，取决于它的查询条件有没有自己写——**读代码时别默认"框架会兜底"**。

**关键理解**：**张三对这一切毫无感知**——他调的是同一个接口，前端代码一模一样，Service 代码一模一样，**只有最后那条 SQL 不同**。

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：数据权限和接口权限的区别是什么？**

接口权限（第 3 章）拦在**方法入口**，回答「能不能调这个接口」；数据权限拦在 **SQL 执行前**，回答「这条 SQL 能查到哪些行」。前者是**接口级/按钮级**，后者是**行级（row-level）**。

**Q2：你们的数据权限怎么实现的？**

用 MyBatis 拦截器 + JSqlParser。在 Mapper 方法上打 `@DataPermission`，MyBatis 执行前用 JSqlParser 把 SQL 解析成语法树，**在 WHERE 节点上 AND 一个数据权限条件**，再转回 SQL。条件是 SpEL 模板（`DataScopeType` / `ContractPermission`）算出来的，模板里可以调 Spring Bean（`@sdss`）去查动态部门。**业务代码零侵入。**

**Q3：为什么不在 Service 层过滤，非要改 SQL？**

三个原因：① **分页正确**（count 和 list 用同一套 WHERE）；② **性能**（数据库直接少返回，不是捞回来再扔）；③ **不漏**（几十个方法不用逐个写，且"看不见的数据"连存在都不泄露——在 SQL 层是"从根上不给"）。

**Q4：★ 你们的数据权限为什么是"双轨"？**

因为**同一个角色在不同业务模块需要的可见范围不一样**。标准轨只有 `sys_role.data_scope` 一个列，装不下这种差异。所以给 `sys_role` **加了 10 个业务列**（`contractPermission` / `ledgerPermission` / `stampPermission` 等），每个模块读自己那一列。**真实注解写法**是 `@DataPermission(value = {@DataColumn(key = "userId", value = "a.contract_charge_id")}, resource = DataPermissionResource.ledgerPermission)`（`ContractDraftMapper.java:160-161`）——`resource` 选模块，`value` 选列。**定制轨用反射按列名取值**（`ReflectUtil.getFieldValue(role, resource.getIndex())`），所以加新列时 Handler 一行不用改。

**Q5：为什么要用反射取角色数据范围？**

因为 `PlusDataPermissionHandler` 是**通用代码**，编译期不知道 `contractPermission` 对应哪个 getter。用**列名当索引**反射取值，就能"新增一个业务列，Handler 不动"。这是**用反射换扩展性**的权衡。

**Q6：`#user.deptId`（单数）和 `LoginUser.deptIds`（数组）对不上，怎么解释？**

**坦白说：标准轨在本项目是先天不完备的**。`DataScopeType.DEPT` 模板用的是**单数** `#{#user.deptId}`（`DataScopeType.java:50`），但本项目的 `LoginUser` **根本没有 `deptId` 字段，只有 `deptIds` 数组**（`LoginUser.java:45`）。所以**本项目的业务模块实际都走定制轨**：定制轨的 3/4 码查 `sys_user_dept`，天然支持多部门（`SysDataScopeServiceImpl.java:132/78`）；6/7 码再补"我负责的部门"这个维度（`:159/185`，判断条件是 `leader/assistant`，见 `SysDeptServiceImpl.java:453-457`）。**标准轨是"框架遗产"，业务不用它。**

**追问：那定制轨的 DEPT 和 MYDEPT 到底差在哪？** 一句话：**DEPT 是"我所在的部门"，MYDEPT 是"我负责的部门"**——前者查 `sys_user_dept`，后者查 `sys_dept.leader/assistant`。

**Q7：数据权限"自定义"（CUSTOM）如果没配部门，会怎样？**

要分两条轨答：**定制轨的 `CUSTOM(2)` 模板直接写死 `1=0`**（`ContractPermission.java:41`），所以确实查不到；**但标准轨 `CUSTOM(2)` 并不是靠 `elseSql` 兜底**——handler 里 `isSuccess = true` 是写死的（`PlusDataPermissionHandler.java:158/184`），`:161-163` 的 `elseSql` 分支实际走不到。**设计原则应该是"配置缺失→最小权限（空集）"，但本项目的代码现实是：定制轨列值为空时会 `return ""`，等于放行全部（`:142-143`）。** 这个缺口要如实说，不要背"兜底 1=0"。

**追问：那为什么种子数据没出问题？** 因为 `sys_role` 的业务列大多有 `DEFAULT '5'`（仅本人，`zxcm_init.sql:4365-4374`），初始化时就把"空值"填掉了——**靠数据默认值兜住了代码的默认放行**。

**Q8：`joinStr` 为什么查询是 OR、写入是 AND？**

（`PlusDataPermissionHandler.java:126`）用户有**多个角色**时，数据权限取**并集**，所以角色条件用 **OR** 连（角色 A 本部门 + 角色 B 本部门及以下 = 能看本部门及以下）。写操作（`AND`）更严格，谨慎为上。

**Q9：`@DataPermission` 是不是每个 Mapper 方法都要标？**

**不是。** 一般只标在**主表的列表/分页查询**上。`selectById`、`selectOne` 这种单条查询**不标**——因为关联查询时被 JOIN 的表可能没有权限列，硬拼会报错或查空。**标错了是实际项目最常见的坑。** 所以本项目对"哪些方法标了注解"要心里有数。

## 七、选型对比：数据权限的几种实现路线

### 7.1 实现层次

| 层次 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| Service 层过滤 | 查完在 Java 里 `if` 筛 | 简单、好懂 | **分页错、性能差、易漏** |
| **SQL 拦截改写（本项目）** | MyBatis 拦截 + JSqlParser | **分页对、零侵入、不漏** | 实现复杂、调试难 |
| 视图 / 权限表 JOIN | 每条 SQL 手动 JOIN 权限表 | 直观 | 每个方法都要写、易漏 |
| 数据库行级安全（RLS） | PostgreSQL RLS / Oracle VPD | 最彻底 | 依赖特定数据库、MySQL 无 |

**结论**：**MySQL + MyBatis 场景下，"拦截改写"是事实标准。** 本项目采用，且做了双轨定制。

### 7.2 数据范围码的存储：单列 vs 每模块一列

| 方案 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| 单列（标准轨） | `sys_role.data_scope` | 简单 | **装不下"同一角色不同模块不同范围"** |
| **每模块一列（本项目定制轨）** | `sys_role` 加 10 个列 | **颗粒度到模块**、反射动态取值 | 列会随模块增多、加列要改表 |
| 权限表（`role_id`+`module`+`scope`） | 独立表 | **最规范、可无限扩展** | 查询多一次 JOIN |

**本项目的选择是"每模块一列"**——用**10 个列**换来"模块级颗粒度"，并用**反射**规避"每加一列就改 Handler"。**代价是 `sys_role` 变宽了**（坦白点）。**更规范的做法是第二种表格化**，本项目为了简单选了列。

### 7.3 SpEL 模板 vs 硬编码

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **SpEL 模板（本项目）** | 枚举里写 `#{#userId} IN ( #{@sdss.xxx(...)} )` | **配置化、加码不改代码** | 模板难调试、报错不直观 |
| 硬编码 | 每个码写一段 Java 拼 SQL | 直观、好调试 | 加码必改代码、易分散 |

**结论**：本项目用 SpEL 换来"码表可扩展"（加 `MYDEPT` 只加枚举项），代价是**调试时得把 SpEL 求值结果打出来看**。

## 本章小结 & 下一步

- **数据权限 = 行级过滤**，做在 **SQL 层**（不是 Service 层），靠 **MyBatis 拦截器 + JSqlParser** 改写 WHERE。
- **注解**：`@DataPermission(value={@DataColumn(...)}, resource=...)` 声明走哪条轨（`resource` 默认 `base` 标准轨）；`@DataColumn(key, value)` 里 `key` 是 SpEL 变量名、`value` 才是 SQL 列名。
- **★ 双轨**：标准轨读 `sys_role.data_scope`（5 码 `DataScopeType`）；**定制轨读 `sys_role` 上 10 个业务列**（7 码 `ContractPermission`），用**反射**按列名取值。
- **SpEL 模板**：`#{#userId}` 等（`@DataColumn.key` 定义的变量）/ `#{#user.xxx}`（用户属性）/ `#{@sdss.xxx}`（调 Bean 查动态部门）。
- **安全兜底（重要更正）**：`elseSql` 的**设计意图**是"算不出就 `1=0`"，但**当前 handler 里 `isSuccess` 恒为 true，兜底分支走不到**；定制轨列值为空时 `return ""` 等于**放行全部**。这是本项目真实的安全缺口，答题时要如实说。
- **坦白点**：`DataScopeType.DEPT` 用 `#{#user.deptId}`，而本项目 `LoginUser` **没有 `deptId` 字段，只有 `deptIds` 数组**——**标准轨先天跑不通，业务都走定制轨**；定制轨 3/4 码查 `sys_user_dept`（多部门），6/7 码查"我负责的部门"（leader/assistant）。
