# 第 11 章 · 异常体系与统一返回

> **前 10 章都在讲"顺利的时候"怎么走，本章讲"出错的时候"怎么收场。**
>
> 假设你是前端：后端可能返回**登录过期**、**没权限**、**参数不合法**、**用户名已存在**、**数据库连接断了**、**代码空指针了**……**这六种错，前端要写六种不同的处理逻辑吗？** 显然不行。
>
> **本章第一次讲透**：① **`R<T>` 统一返回体**——为什么所有接口都返回 `{code, msg, data}` 这三个字段；② **`GlobalExceptionHandler` 全局异常处理器**——`@RestControllerAdvice` 怎么**一网打尽**从 Controller 抛出的任何异常；③ **异常家族**（`BaseException` / `ServiceException` / `UserException` / Sa-Token 的认证鉴权异常）怎么分工；④ 一个**必须警惕的坑**：**`@Async` 异步方法里抛的异常，全局处理器根本管不着**。

---

## 一、这部分是做什么的？

### 1.0 零基础先补概念（第一次读先看这里）

| 概念 | 大白话 | 本章的真实例子 |
|---|---|---|
| **受检 / 非受检异常** | 受检异常编译器逼你 `try/catch`；非受检异常（`RuntimeException`）不强制 | 本项目的业务异常都继承 `RuntimeException`，所以业务代码只 `throw`、不强制 catch（`ServiceException.java:21`） |
| **统一返回体** | 所有接口都长成 `{code, msg, data}`，前端只认 `code` | `R<T>`（`R.java:31`） |
| **全局异常处理器** | 一个"总捕手"，接住从 Controller 冒出来的异常并翻译成统一返回 | `@RestControllerAdvice` 标在 `GlobalExceptionHandler` 上（`GlobalExceptionHandler.java:52-53`） |
| **HTTP 状态码 vs 业务 code** | HTTP 200 表示"请求送到了"；body 里的 `code` 才表示"业务成没成" | 用户名已存在也返回 HTTP 200，body `{"code":500,...}` |

**先记住一条链路**：**业务代码 `throw` 有语义的异常 → Spring MVC 在 Controller 出口找最匹配的 `@ExceptionHandler` → 处理器返回 `R.fail(...)` → 前端只看 body 的 `code`。**

### 1.1 没有"统一返回"的世界有多乱

**如果每个接口各自为政**：

```java
// 接口 A 成功返回
{ "userName": "张三", "age": 18 }

// 接口 B 失败返回一个字符串
"用户名已存在"

// 接口 C 失败直接抛 500 页面（HTML）
<Whitelabel Error Page> ...

// 接口 D 返回 null
```

**前端会疯掉**：同一个 axios 拦截器，**怎么判断这次请求是成功还是失败？** 靠 HTTP 状态码？**但很多"业务失败"（用户名已存在）HTTP 状态码是 200**。靠猜字段？**太脆弱**。

**结论：后端必须约定一个"所有接口长得一样"的返回格式。**

### 1.2 本项目的答案：`R<T>`

```java
{ "code": 200, "msg": "操作成功", "data": {...} }   // 成功
{ "code": 500, "msg": "用户名已存在", "data": null }  // 失败
```

**前端只需要看 `code`**：`200` → 成功，用 `data`；非 `200` → 失败，弹 `msg`。**一个拦截器搞定所有接口。** 分页接口则用 `TableDataInfo`（多一个 `total` 和 `rows`）。

### 1.3 那"出错"怎么变成这个格式？

**业务代码里不会到处写 `return R.fail(...)`**——那样太啰嗦，而且**很多错误是"意外"（空指针、超时、SQL 语法错），根本不给你 return 的机会**。

**本项目的答案：抛异常 + 全局兜底。**

```java
// 业务代码只负责"抛"（一行，语义清晰）
if (userExists(username)) {
    throw new ServiceException("用户名已存在");
}

// 至于"怎么变成 JSON 返回给前端"——不用管
```

**`GlobalExceptionHandler` 会在"异常冒出 Controller 的那一刻"接住它，统一转成 `R.fail(...)`。** 这就是"**全局异常处理器**"。

### 1.4 三个层次的分工

| 层次 | 干什么 | 关键类 |
|---|---|---|
| **返回体** | 定义"接口长什么样" | `R<T>`、`TableDataInfo<T>` |
| **异常类型** | 定义"错误的语义"（业务错？权限错？系统错？） | `ServiceException`、`UserException`、`NotLoginException`… |
| **异常处理器** | 把"异常"翻译成"返回体" | `GlobalExceptionHandler` |

**一句话串起来**：**业务代码 `throw` 一个有语义的异常 → 全局处理器 `catch` 住 → 翻译成 `R.fail` → 前端只认 `code`。**

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么不用 HTTP 状态码，而用 body 里的 `code`？

这是**新手最容易疑惑的点**：既然有 HTTP 状态码（200 成功、401 未认证、403 无权限、500 服务器错），**为什么还要在 JSON body 里再塞一个 `code`？**

**本项目的做法**：**看 `GlobalExceptionHandler`——所有 handler 返回的都是 `R.fail(...)`，HTTP 状态码始终是 200**（`HttpStatus.HTTP_FORBIDDEN`、`HTTP_UNAUTHORIZED` 这些值是塞进 **body 的 `code` 字段**，不是塞进 HTTP 响应头）。

**为什么这么选？** 三个现实原因：

1. **HTTP 状态码不够用**：HTTP 只有那么几十个标准码。**"用户名已存在""密码错 3 次锁定""验证码失效"——这些业务错误没有对应的 HTTP 码**。**必须自己定义 code**。
2. **统一处理更简单**：前端一个 axios 拦截器，**只看 body 的 `code` 就够了**，不用同时处理"HTTP 层 401 怎么跳登录页、HTTP 层 500 怎么弹错误、HTTP 层 200 但 body code 是 401 又怎么办"这三种情况。
3. **避免浏览器/网关误介入**：**某些网关、代理、浏览器会对 4xx/5xx 做特殊处理**（比如自动重试、显示错误页、CORS 报错）。**业务失败用 200 + body code，行为最可控。**

**代价（要坦白的）**：**监控系统（APM）默认按 HTTP 状态码统计错误率**——**本项目里"业务失败"和"系统崩溃"在 HTTP 层看都是 200，APM 分不出来**。所以**要区分"业务错"和"系统错"，得自己看 body code**。**这是"约定统一"换来的一点监控代价。**

### 2.2 为什么用 `@RestControllerAdvice`？

**核心思想：把"异常处理"从"每个 Controller 里 try-catch"抽成"全局的横切关注点"。**

**没有它的话**：

```java
@PostMapping("/user")
public R<Void> add(@RequestBody SysUser user) {
    try {
        userService.insert(user);
        return R.ok();
    } catch (ServiceException e) {
        return R.fail(e.getMessage());       // 每个接口都要写这一坨
    } catch (Exception e) {
        return R.fail("系统错误");            // 而且写法还容易不一致
    }
}
```

**有它之后**：**Controller 干净到只有业务，`throw` 出去就行**。

**技术落点**：`@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`。Spring MVC **在 `DispatcherServlet` 处理请求的最后一步**，如果 Controller 抛了异常，**会去"通知（Advice）"里找匹配的 `@ExceptionHandler`**——**这就是"全局异常处理器"的实现机制。**

### 2.3 异常为什么要分这么多种？

看本项目的异常家族，**每种异常对应一种"语义"和一种"处理方式"**：

| 异常 | 语义 | 谁抛 | 处理器给的 code |
|---|---|---|---|
| `ServiceException` | **业务错误**（用户能看懂） | 业务代码手动抛 | 500（或自定义 code） |
| `UserException`（及子类） | **用户/登录相关错误** | 登录、注册逻辑 | **500**（走 RuntimeException 兜底，见 §4.8 坦白点） |
| `NotLoginException` | **没登录**（Sa-Token 抛） | 认证拦截器 | **401** |
| `NotPermissionException` / `NotRoleException` | **没权限**（Sa-Token 抛） | `@SaCheckPermission` 等 | **403** |
| `BindException` / `ConstraintViolationException` / `MethodArgumentNotValidException` | **参数校验失败** | Bean Validation | 500 + 拼接错误消息 |
| `SQLException` / `MyBatisSystemException` / `BadSqlGrammarException` | **数据库错** | MyBatis / JDBC | 500 + "执行数据库操作失败" |
| `RuntimeException` | **兜底：没预料到的运行时错** | 任何地方 | 500 + 原始 message |
| `Exception` | **终极兜底** | 任何地方 | 500 + 原始 message |
| `DemoModeException` | **演示模式不允许操作** | 演示环境 | 500 + "演示模式，不允许操作" |

**设计要点**：

- **"业务错"和"系统错"要能分开**——`ServiceException` 的 message 是**给用户看的**（"用户名已存在"）；**SQL 异常的 message 是给运维看的**（不该暴露给用户），所以处理器里**返回的是"执行数据库操作失败，请联系管理员"这种通用话术**，**真实报错只写日志**（`log.error`）。
- **越具体的异常，处理器越具体**——这是 §2.4 要讲的。
- **安全考虑**：**系统异常的 message 不能原样返回给前端**（可能泄漏表名、SQL、路径）。**但本项目 `handleRuntimeException` 返回值里用了 `e.getMessage()`（§4.8 坦白点）**——**这是一个"信息泄漏"的口子。**

### 2.4 处理器怎么选？（Spring 的"最具体匹配"）

一个 `NotLoginException` 抛出来，**它也是 `RuntimeException` 的子类**——**那 Spring 到底用哪个 handler？**

**规则：Spring 找"和异常类型最匹配"的那个**——**优先精确类型，找不到再往父类找**。

```
NotLoginException 抛出
   ├─ 有 @ExceptionHandler(NotLoginException.class) 吗？→ 有！用它 → code 401
   └─（如果没有）→ 找父类 …→ RuntimeException → 用它
```

**所以顺序很重要**：**`handleRuntimeException`（`:159`）虽然是"兜底"，但因为 `NotLoginException` 有专属 handler（`:98`），它永远不会被兜底抢走。**

**这也解释了为什么本项目的 handler 要写这么多**——**每多一个专属 handler，就多一种"精确控制 code 和文案"的能力**；剩下的"没照顾到的"才落到 `RuntimeException` / `Exception` 兜底。

### 2.5 为什么要有 i18n（国际化）？

看 `BaseException`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/exception/base/BaseException.java:30`）：

```java
@Override
public String getMessage() {                                  // :77
    String message = null;
    if (!StringUtils.isEmpty(code)) {
        message = MessageUtils.message(code, args);          // :80  ★用"消息码"去查翻译
    }
    if (message == null) {
        message = defaultMessage;                            // :84  查不到才用兜底文案
    }
    return message;
}
```

**注意它不存"文案"，存的是"消息码"**（比如 `user.password.not.match`），**真正的中文/英文文案放在 `messages.properties` / `messages_en_US.properties` 里**，靠 `MessageUtils`（底层是 Spring 的 `MessageSource`）**按当前语言查出来**。

**为什么要这样？**

- **多语言**：同一份代码，**中文环境查 `messages_zh_CN.properties`，英文环境查 `messages_en_US.properties`**；
- **文案集中管理**：**所有错误提示在一个文件里**，改文案不用翻代码；
- **避免硬编码**：**不在 Java 里写死中文字符串**。

**本项目实际用的语言包**：`ruoyi-admin/src/main/resources/i18n/messages.properties`（默认，中文），另有 `messages_zh_CN.properties` / `messages_en_US.properties`。

## 四、功能具体怎么实现（带着你读懂）

### 4.1 `R<T>`：一个"三字段"的泛型盒子

（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/R.java`）

```java
@Data
@NoArgsConstructor
@ApiModel("请求响应对象")
public class R<T> implements Serializable {              // :31  ★T = data 的类型
    public static final int SUCCESS = 200;               // :37
    public static final int FAIL = 500;                  // :42

    private int code;                                    // :45  状态码
    private String msg;                                  // :48  提示信息
    private T data;                                      // :51  ★业务数据（泛型）
    ...
}
```

**三个字段就是全部**。**`T` 泛型**让 `R<SysUser>`、`R<List<SysDept>>`、`R<Void>` 都能用同一个类——**`R<Void>`（Void）专门表示"没有数据、只要成功与否"的接口**（比如新增/删除）。

**静态工厂一览**（`:53-95`）：

```java
R.ok()                    // {200, "操作成功", null}
R.ok(data)                // {200, "操作成功", data}
R.ok(msg)                 // {200, msg, null}
R.ok(msg, data)           // {200, msg, data}

R.fail()                  // {500, "操作失败", null}
R.fail(msg)               // {500, msg, null}
R.fail(data)              // {500, "操作失败", data}
R.fail(msg, data)         // {500, msg, data}
R.fail(code, msg)         // {code, msg, null}   ★自定义 code（异常处理器用这个）
```

**所有工厂最终都汇聚到 `restResult`**（`:89`）：

```java
private static <T> R<T> restResult(T data, int code, String msg) {   // :89
    R<T> r = new R<>();
    r.setCode(code);
    r.setData(data);
    r.setMsg(msg);
    return r;
}
```

**读懂设计**：**"一堆静态工厂 + 一个私有构造方法"**——**这是"具名构造器"模式**，让 `R.ok(data)` 比 `new R(200, "操作成功", data)` 可读得多，而且**参数顺序不会搞错**（如果直接 `new R(...)`，`code` 和 `msg` 位置容易写反）。

### 4.2 `TableDataInfo<T>`：分页专用返回体

（类声明在 `ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/page/TableDataInfo.java:36`）

```java
@Data
@ApiModel("分页响应对象")
public class TableDataInfo<T> implements Serializable {
    private long total;        // :43  总记录数
    private List<T> rows;      // :49  当前页数据
    private int code;          // :55
    private String msg;        // :61

    public static <T> TableDataInfo<T> build(IPage<T> page) {    // :74  ★从 MyBatis-Plus 的 IPage 直接构建
        TableDataInfo<T> rspData = new TableDataInfo<>();
        rspData.setCode(200);
        rspData.setMsg("查询成功");
        rspData.setRows(page.getRecords());      // 当前页记录
        rspData.setTotal(page.getTotal());       // 总数
        return rspData;
    }
}
```

**为什么列表接口不直接用 `R<List<T>>`？** 因为**分页必须带 `total`（总数）**，前端分页组件要显示"共 100 条"。`R<List<T>>` 只有一个数组、放不下 `total`。**所以给分页单开一个 `TableDataInfo`**（`rows` + `total`）。

**`build(IPage<T> page)` 的价值**：**一行把 MyBatis-Plus 的分页对象转成前端要的格式**。Service 层用 `Page<SysUser>` 分页查询，Controller 层 `TableDataInfo.build(page)` 一转就返回——**字段名（`records`→`rows`）由这个方法统一映射**。

> **本项目有一个值得注意的细节**：`com.ruoyi.common.core.page.TableDataInfo` **这个类在项目里出现了两次**——`ruoyi-base/ruoyi-common` 里一个（上面这个，泛型版，类声明在 `TableDataInfo.java:36`），`zxcm-workflow` 里还有一个（非泛型的老版，类声明在 `zxcm-workflow/src/main/java/com/ruoyi/common/core/page/TableDataInfo.java:24`）。**两个类包名完全相同**，只是在不同 Maven 模块里。**这是"模块复制粘贴"留下的隐患**（详见 §4.8 坦白点）。

### 4.3 异常家族图谱

**先把继承关系理清楚**（这是理解"处理器怎么匹配"的前提）：

```
RuntimeException（JDK）
 ├── ServiceException                 ← 业务异常（全项目 298 处使用，最主力）
 ├── BaseException                    ← 基础异常（带 module/code/args，走 i18n）
 │    └── UserException               ← 用户/登录异常（子类：CaptchaException / CaptchaExpireException / UserPasswordNotMatchException）
 ├── GlobalException                  ← 全局异常（★ 全项目未使用，见坦白点）
 ├── UtilException                    ← 工具类异常
 ├── DemoModeException                ← 演示模式异常
 └── （Sa-Token 的 NotLoginException 等，也继承自 RuntimeException）

Exception（JDK）
 └── 各种受检异常（IOException / SQLException ...）
```

**逐个看**：

**`ServiceException`**（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/exception/ServiceException.java:21`）

```java
public final class ServiceException extends RuntimeException {     // :21  ★final，不可继承
    private Integer code;                                          // :27  可选自定义 code
    private String message;                                        // :32  ★自己存 message 字段
    private String detailMessage;                                  // :39  内部调试信息

    public ServiceException(String message) { this.message = message; }                    // :47
    public ServiceException(String message, Integer code) { ... }                          // :51  ★带 code 的重载

    @Override
    public String getMessage() { return message; }                 // :61  ★重写了 getMessage
}
```

**读懂几点**：

- **`final`**：**不允许业务再继承出"更细的业务异常"**——本项目**"业务异常"就一种，靠 message 区分**。这是"简单直接"的选择（对比：有的项目会 `OrderException extends ServiceException` 做细分）。
- **重写 `getMessage()`（`:61`）**：**为什么？** 因为 `ServiceException` 构造函数**没有调 `super(message)`**（你看构造方法里只有 `this.message = message`）。**如果不重写 `getMessage()`，父类 `RuntimeException` 里的 message 会是 null。** 重写后**返回的是自己存的 `message`**。**这是"自己管 message"的写法**（好处：可以用 `setMessage` 链式改文案，`:69`）。
- **`message` 不走 i18n**：和 `BaseException` 不同，**`ServiceException` 的文案是业务代码传进来的原始字符串**（如 `throw new ServiceException("用户名已存在")`）——**不做国际化**。**这是"业务异常"和"用户异常"的一个实际差异。**

**`BaseException` + `UserException`**（走 i18n 的一支）

```java
// BaseException.java
public class BaseException extends RuntimeException {              // :30
    private String module;      // 所属模块
    private String code;        // ★ 消息码（不是文案）
    private Object[] args;      // 消息参数
    private String defaultMessage;

    @Override
    public String getMessage() {                                   // :77
        String message = null;
        if (!StringUtils.isEmpty(code)) {
            message = MessageUtils.message(code, args);            // :80  按码查 i18n 文案
        }
```

**逐行读这组 handler（`GlobalExceptionHandler.java:58-103`）**：

|---|---|---|
| `58` | `@ExceptionHandler(NotPermissionException.class)` | 声明"我专门接权限码异常"；Spring 按类型找 handler 时优先精确匹配 |
| `59` | 方法签名接收异常和 `HttpServletRequest` | 要异常信息，也要请求 URI 来打日志 |

**这三行就是"401/403"的落点**：

**第二组：业务异常**

```java
@ExceptionHandler(MethodArgumentNotValidException.class)                  // :203  ★@RequestBody 对象校验失败
```

**为什么是三个 handler？** 因为 **Bean Validation 在不同场景抛不同的异常**：

| 场景 | 触发方式 | 抛的异常 |
|---|---|---|
| `@RequestBody` 对象上的 `@NotBlank` 等 | `@Valid` / `@Validated` + JSON body | **`MethodArgumentNotValidException`** `:203` |
| 表单/查询参数绑定 | 参数对象（无 `@RequestBody`） | **`BindException`** `:179` |
| **类上 `@Validated` + 方法参数上的 `@NotBlank`** | 直接标在方法参数上 | **`ConstraintViolationException`** `:191` |

**这三个都必须收**，**否则漏一个，"参数校验失败"就会掉进 `RuntimeException` 兜底、返回一堆技术细节给用户**。

### 4.6 兜底的两个 handler

```java
@ExceptionHandler(RuntimeException.class)                   // :159  ★运行时异常兜底
public R<Void> handleRuntimeException(RuntimeException e, HttpServletRequest request) {
    log.error("请求地址'{}',发生未知异常.", requestURI, e);      // :162  ★完整堆栈进日志
    return R.fail(e.getMessage());                          // :163  ★但 message 原样返回前端（坦白点）
}

@ExceptionHandler(Exception.class)                          // :169  ★受检异常终极兜底
public R<Void> handleException(Exception e, HttpServletRequest request) {
    log.error("请求地址'{}',发生系统异常.", requestURI, e);
    return R.fail(e.getMessage());
}
```

**"两级兜底"的意义**：**`RuntimeException` 收"运行时错"（空指针、类型转换、非法参数……），`Exception` 收"受检错"（IOException 等）。** **有了这两级，任何异常都不会漏网**——**最坏情况也是返回一个 `{code:500, msg:...}`，而不是给用户一个 Tomcat 的错误页面。**

### 4.7 ★ 坑：`@Async` 里的异常，全局处理器管不着

**这是本章最"反直觉"、也最容易踩的坑。**

**先理解为什么**：`GlobalExceptionHandler` 靠的是 **`@RestControllerAdvice`**，而它只在 **"Spring MVC 处理 HTTP 请求的那条线程"** 里生效。**一个 HTTP 请求 = 一条线程 = 一次 MVC 处理 = 一次 `@ExceptionHandler` 的机会。**

**但 `@Async` 方法跑在"另一条线程"（线程池）上**：

```java
@Async
public void recordLogininfor(...) {      // 这条线程不是 MVC 请求线程
    ...
    // 如果这里抛异常 → 没有 MVC 上下文 → 全局处理器收不到！
}
```

**异常去哪了？** 看 `AsyncConfig`（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/AsyncConfig.java:38`）：

```java
@EnableAsync
@Configuration
public class AsyncConfig extends AsyncConfigurerSupport {              // :38  ★继承这个基类

    @Override
    public Executor getAsyncExecutor() {                               // :48  ★@Async 用哪个线程池
        return scheduledExecutorService;
    }

    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {   // :56  ★异步异常处理器
        return (throwable, method, objects) -> {
            log.error("异步任务执行异常", throwable);                    // :58  ★能做的：记日志
            StringBuilder sb = new StringBuilder();
            sb.append("Exception message - ").append(throwable.getMessage())
                .append(", Method name - ").append(method.getName());
            if (ArrayUtil.isNotEmpty(objects)) {
                sb.append(", Parameter value - ").append(Arrays.toString(objects));
            }
            throw new ServiceException(sb.toString());                 // :65  ★★ 这里"再抛"其实没用……
        };
    }
}
```

**逐点读懂**：

1. **`AsyncConfigurerSupport` + `getAsyncUncaughtExceptionHandler()`**：**这是 Spring 给 `@Async` 准备的"异常兜底钩子"**——**当 `@Async` 方法抛了没被 catch 的异常，Spring 会调它**。
2. **它能做的**：**记日志**（`:58`）——**这是它真正有用的地方。异常至少进了日志文件，不会被静默吞掉。**
3. **★ `:65` 那句 `throw new ServiceException(...)` 是"无效操作"**——**因为此时已经在"异步异常处理线程"里了，**这个 `throw` 不会再被任何 `@ExceptionHandler` 接住**，只会变成"处理器自己抛了个异常"。**这行代码是"看起来想上报、实际上没有出口"的典型**（§4.8 坦白点）。

**给业务的启示**：**凡是 `@Async` 方法（比如第 8 章的 `recordOper` / `recordLogininfor`），它的异常"前端永远看不到"**——**因为等它执行时，HTTP 请求早就返回了**。**所以：① 异步方法内部要尽量 try-catch 兜住（第 8 章的日志方法就是这么做的）；② 别指望"异步任务失败会通知用户"——那是不可能的。**

> **对比第 8 章**：第 8 章讲"日志记录用 `@Async`，因为不能拖慢主流程"；**本章从异常角度补充了代价**——**异步让"错误可见性"变差了**。**这是同一个技术选择的两个侧面，考试/答辩时能把两面都说清，就是"真懂"。**

### 4.8 ★★ 坦白点（本章有四个）

**坦白点一：`UserException` / `BaseException` 没有专属处理器，登录失败 code 是 500**

**事实**：`GlobalExceptionHandler` **只处理 `ServiceException`（`:119`）、没有 `BaseException` / `UserException` 的 handler**。**用户/登录异常只能落到 `handleRuntimeException`（`:159`），code 固定 500。**

**后果**：**"验证码错误""密码错误 3 次""账号被禁用"这些"用户可预期的业务失败"，和"系统崩了"（空指针）返回的是同一个 code 500。** 前端**无法仅凭 code 区分"用户输错了"和"服务器出故障了"**——**只能靠 msg 文案或者干脆都弹同一套提示。**

**怎么修**：加一个 handler：

```java
@ExceptionHandler(BaseException.class)
public R<Void> handleBaseException(BaseException e, HttpServletRequest request) {
    log.error("请求地址'{}',业务异常'{}'", request.getRequestURI(), e.getMessage());
    return R.fail(e.getMessage());     // 或者定义一个更精确的 code，比如 400
}
```

**答辩时怎么说**："我们的用户异常继承自 `BaseException`，但**全局处理器没有给 `BaseException` 加 handler**，所以登录失败落在了 `RuntimeException` 兜底、code 是 500。**功能不受影响（前端弹 msg 照常），但 code 语义不够精确**——如果让我优化，我会加一个 `BaseException` 的 handler，给用户级错误一个独立 code。" ——**能指出并给出修法，说明你是真读懂了处理器匹配机制。**

**坦白点二：系统异常的原始 message 被返回给前端（信息泄漏风险）**

**事实**：`handleRuntimeException`（`:163`）和 `handleException`（`:173`）**都 `return R.fail(e.getMessage())`**——**把异常的原始 message 原样返回给前端**。

**风险**：**如果是数据库相关异常（`SQLException` 虽有专属 handler 返回通用话术，但其他库抛的运行时异常未必），原始 message 可能包含表名、字段名、SQL 片段、甚至文件路径**——**这些都属于"不该给外部看到的信息"**。

**对照**：**项目里对 `SQLException`（`:129`）、`MyBatisSystemException`（`:78`）、`BadSqlGrammarException`（`:149`）都做了"返回通用话术、真实报错只写日志"的处理**——**说明作者知道这个原则，但 `RuntimeException` / `Exception` 兜底这两处没照做**（可能是"兜底就随便点"的疏忽）。

**怎么修**：兜底 handler 也改成 `R.fail("系统繁忙，请稍后重试")`，**真实 message 只写日志**。

**坦白点三：`GlobalException` 是"死代码"**

**事实**：`com.ruoyi.common.exception.GlobalException` **定义了完整的类（构造方法 `:40`/`:43`、`getMessage` 等），但全项目除它自己外零引用**（`grep` 只匹配到它自己的构造函数）。

**这是从 RuoYi 原版带过来的遗留类**——**原版可能用它，本项目的 `ServiceException` 已经取代了它。** **属于"没有清理的遗留代码"。**

**坦白点四：`TableDataInfo` 同名类在项目里有两份**

**事实**：`com.ruoyi.common.core.page.TableDataInfo` **在 `ruoyi-base/ruoyi-common` 和 `zxcm-workflow` 两个模块里各有一个**，**包名完全相同、实现不同**（一个泛型版、一个非泛型老版）。

**风险**：**如果某个模块同时依赖了两者，加载哪个取决于"classpath 上的先后"——可能出现"编译过了，运行时行为却不是你想要的"的诡异问题。** 本项目目前没炸，**但这是"复制粘贴建新模块"留下的技术债**——**正确做法是让 `zxcm-workflow` 删掉自己那份，直接依赖 `ruoyi-common` 的。**

> **加分项**：**面试时"你们项目异常怎么处理的？"是高频题**。**能把"我们有一处用户异常没被精确处理、系统异常 message 泄漏风险、还有个 GlobalException 死代码"这几条主动说出来，比背一遍 handler 列表强得多**——**因为它证明你不是"看了文档"，而是"读了代码"。**

**第二个场景（对照）：登录过期**

```
① SaTokenConfig 的 SaRouteInterceptor 在 check() 里调 LoginHelper.getUserId()
      ↓  未登录 → StpUtil 抛 NotLoginException
② GlobalExceptionHandler 匹配到 handleNotLoginException(:98)
      ↓
③ HTTP 200 + body { "code": 401, "msg": "认证失败，无法访问系统资源" }
      ↓
④ 前端拦截器看到 code=401 → 清 token、跳登录页
                          （看到 code=403 → 只提示"没权限"）
```

**两个场景对照的收获**：

| | 业务异常 | 认证异常 |
|---|---|---|
| 谁抛的 | **业务代码**（`throw`） | **框架拦截器**（Sa-Token） |
| 走哪个 handler | `handleServiceException` `:119` | `handleNotLoginException` `:98` |
| code | **500** | **401** |
| 前端动作 | 弹 msg | **清 token + 跳登录** |

**关键认知**：**不管是"业务代码主动抛的"还是"框架自动抛的"，最终都汇到同一个 `GlobalExceptionHandler`。** **"统一出口"是这套设计的最大价值**——**你在 Controller 里永远不用写 try-catch，前端永远只认 `code`。**

### 5.1 动手验证：亲眼看统一返回和异常处理

## 六、面试官高频问题 + 答案

**Q1：你们项目的统一返回格式是什么？为什么这么设计？**

**A**：统一返回体是 `R<T>`，三个字段：`code`（状态码）、`msg`（提示）、`data`（业务数据，泛型）。**列表接口用 `TableDataInfo`**（多 `total`/`rows`，因为分页要总数）。
**为什么**：**让前端一个拦截器搞定所有接口**——只看 `code` 判断成败。**而且业务失败不用 HTTP 状态码、用 body 里的 code**，因为 **HTTP 标准码不够表达业务语义（"用户名已存在"没有对应码），且避免网关/浏览器对 4xx/5xx 做特殊处理**。**代价是 APM 按 HTTP 码统计错误率时，业务失败和系统故障分不出来。**

**Q2：异常是怎么统一处理的？**

**A**：用 `@RestControllerAdvice` + `@ExceptionHandler` 的 `GlobalExceptionHandler`。**任何从 Controller 冒出来的异常**，Spring MVC 都会去找"类型最匹配"的 handler，**翻译成 `R.fail`**。**业务代码只管 `throw`，不用 try-catch。**
**我们按语义分了组**：Sa-Token 的认证/鉴权异常 → **401/403**；`ServiceException` → 500（或自定义 code）；参数校验的三个异常（`BindException` / `ConstraintViolationException` / `MethodArgumentNotValidException`）→ 拼接校验消息；数据库异常 → **返回通用话术，真实报错只写日志**；最后 `RuntimeException` / `Exception` 两级兜底。

**Q3：`@ExceptionHandler` 怎么决定用哪个？子类异常会不会被父类 handler 抢走？**

**A**：**按"最具体匹配"**。Spring 优先找异常类型的精确匹配，找不到才往父类走。所以 `NotLoginException`（虽然也是 `RuntimeException` 子类）**会被 `handleNotLoginException` 接住，不会被 `handleRuntimeException` 抢走**——**因为有更精确的 handler 存在**。**这也是为什么 handler 写得越多，"精确控制"能力越强**；剩下的才落兜底。

**Q4：`ServiceException` 和 `BaseException` 有什么区别？**

**A**：**`ServiceException` 存的是"硬编码文案"**（`throw new ServiceException("用户名已存在")`），**不支持国际化**，是**业务异常主力（全项目 298 处）**。**`BaseException` 存的是"i18n 消息码"**（如 `user.password.not.match`），**文案从 `messages.properties` 按语言查**，`UserException` 是它的子类、专用于用户/登录错误。
**一个事实**：**我们的 `BaseException` 系列没有专属 `@ExceptionHandler`**，落到了 `RuntimeException` 兜底，code 是 500——**这是我读代码时发现的一个可以优化的点。**

**追问：既然 `BaseException` 没有专属 handler，为什么登录失败还要用它，而不直接 `throw new ServiceException("密码错误")`？**
因为它的设计目标是**用消息码走 i18n**：`BaseException.getMessage()`（`BaseException.java:77`）会拿 `code` 去 `messages.properties` 查当前语言文案（`:80`），同一行代码在中英文环境自动切换；`ServiceException` 存的是硬编码字符串，做不到这一点。**代价就是目前缺一个专属 handler，code 不够精确。**

**Q5：`ServiceException.getMessage()` 为什么重写了？**

**A**：因为它**没有调 `super(message)`**，只是把 message 存进自己的字段。**如果不重写，父类 `RuntimeException` 的 message 是 null**，`getMessage()` 就取不到值。重写后返回自己的字段——**这种写法还支持 `setMessage` 链式修改文案。**

**Q6：`@Async` 方法里抛异常会被全局处理器接住吗？**

**A**：**不会。** `GlobalExceptionHandler` 依赖 `@RestControllerAdvice`，**只在"处理 HTTP 请求的那条线程"里生效**。而 `@Async` 方法跑在**线程池的另一条线程**上，**没有 MVC 上下文，异常进不了全局处理器**。
**它的异常走 `AsyncConfigurer` 的 `getAsyncUncaughtExceptionHandler`**（`AsyncConfig.java:56`）——**那里只能记日志**。**所以 `@Async` 方法必须自己 try-catch 兜住**（第 8 章的日志记录方法就是这么做的），**而且前端永远不会看到异步任务的错误**（请求早返回了）。

**Q7：401 和 403 有什么区别？你们怎么实现的？**

**A**：**401 = 未认证（没登录/登录过期）**，前端应**跳登录页**；**403 = 已认证但无权限**，前端应**提示没权限**。
**实现**：**Sa-Token 的拦截器在认证/鉴权阶段抛不同异常**——`NotLoginException` → `handleNotLoginException` 返回 401；`NotPermissionException` / `NotRoleException` → 返回 403。**放在 body 的 code 字段里。**

**Q8：参数校验失败怎么处理？为什么有三个 handler？**

**A**：**Bean Validation 在不同场景抛不同异常**：`@RequestBody` 对象校验失败抛 `MethodArgumentNotValidException`；表单/参数对象绑定失败抛 `BindException`；**类上 `@Validated` + 方法参数上的校验注解**失败抛 `ConstraintViolationException`。**三个都收，才能保证"参数错"被翻译成人话返回，而不是掉进兜底返回技术细节。**

**Q9：异常文案为什么要用 i18n，不直接写中文？**

**A**：**多语言 + 集中管理 + 不硬编码**。`BaseException` 存消息码、`MessageUtils`（底层 Spring `MessageSource`）按当前语言查 `messages_*.properties`。**同一行 `throw new CaptchaException()` 在中英文环境自动出不同文案**，改文案也不用翻 Java 代码。**不过 `ServiceException` 走的是硬编码文案**——**项目里两条路并存**。

**Q10：让你优化异常处理，你会改什么？**

**A**：**四处**：① 给 `BaseException` 加专属 handler，让用户异常有更精确的 code（现在都落 500）；② 兜底 handler 不要 `return R.fail(e.getMessage())`——**系统异常原样返回 message 有信息泄漏风险**，改成通用话术 + 只写日志；③ 删掉零引用的 `GlobalException` 死代码；④ `zxcm-workflow` 里重复的 `TableDataInfo` 删掉、复用 `ruoyi-common` 的。**① 是准确性、② 是安全、③④ 是整洁度。**

### 本章答辩卡（追问级）

**追问组 1：`RuntimeException` 和 `Exception` 两个兜底 handler 都在，为什么不冲突？**

- **10 秒答案**：Spring 按"最具体匹配"选。`RuntimeException` 是 `Exception` 的子类，所以运行时异常优先命中 `handleRuntimeException`（`:159`）；只有受检异常（如 `IOException`）才会落到 `handleException`（`:169`）。两个 handler 是"分级兜底"，不是"重复"。
- **证据**：`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/web/exception/GlobalExceptionHandler.java:159`（`RuntimeException`）、`:169`（`Exception`）。
- **一句话总结**：越具体的类型越优先，父类只收"没人认领的"。

**追问组 2：Filter 里抛的异常，`@RestControllerAdvice` 能接住吗？**

- **10 秒答案**：**接不住**。`@RestControllerAdvice` 属于 Spring MVC，只在 `DispatcherServlet` 处理 handler 的链路上生效；Filter 在 `DispatcherServlet` **之前**执行，那里抛出的异常还没进入 MVC，自然到不了 `@ExceptionHandler`。所以 XSS 过滤器、请求包装器自身出错，只能靠容器错误页或 Filter 内部的 try/catch。
- **证据**：`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/web/exception/GlobalExceptionHandler.java:52-53`（Advice 定义）；`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/filter/XssFilter.java:48-57`（Filter 在 MVC 之前执行，且自身没有 try/catch）。
- **一句话总结**：Advice 的边界是 DispatcherServlet，不是整个 Web 容器。

**追问组 3：`ServiceException` 为什么要声明成 `final`？**

- **10 秒答案**：**不允许再派生子类**。项目选择"业务异常只有一种，用 message 区分语义"，处理器只需要一个 `handleServiceException`（`:119`）；如果允许继承，就会冒出 `OrderException`、`UserBizException` 等各种分支，handler 也要跟着膨胀。代价是**类型上无法区分业务错误种类**，只能看 message 或自定义 `code`。
- **证据**：`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/exception/ServiceException.java:21`（`final class`）、`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/web/exception/GlobalExceptionHandler.java:119`（唯一的业务异常 handler）。
- **一句话总结**：用"一个类型 + 文案/码"换简单，牺牲的是类型表达力。

## 七、选型对比

### 7.1 "统一返回"用什么承载错误码

| 方案 | 前端处理 | 语义表达力 | 本项目 |
|---|---|---|---|
| 纯 HTTP 状态码 | 拦截 4xx/5xx | **弱**（业务错没码） | ✗ |
| **HTTP 200 + body code（本项目）** | **只看 body code** | **强（自定义 code）** | **✔** |
| HTTP 状态码 + body code 双写 | 两处都要处理 | 强 | ✗（易不一致） |
| 无统一格式，各接口自定义 | 每个接口单独处理 | 无 | ✗ |

**结论**：**"HTTP 200 + body code"是国内后台管理系统的主流约定**（RuoYi、若依系列、大量中台都这么干）。**优点是前端处理极简、业务码自由；代价是 APM/网关按 HTTP 码看，业务失败被算成"成功"。** 本项目选了这条路。

### 7.2 异常处理的实现方式

| 方式 | 优点 | 缺点 | 本项目 |
|---|---|---|---|
| **`@RestControllerAdvice`（本项目）** | **全局、零侵入、Controller 干净** | 异步/非 MVC 线程管不着 | **✔** |
| 每个 Controller try-catch | 简单直观 | **重复、写法易不一致、易漏** | ✗ |
| Filter 层 catch | 能覆盖更外层 | 拿不到"具体异常类型" | ✗ |
| AOP 环绕通知 | 灵活 | 比 Advice 重 | ✗ |

**结论**：**`@RestControllerAdvice` 是 Spring MVC 下异常统一处理的"标准答案"**——**声明式、集中、不侵入业务。** **唯一要警惕的是它的作用域边界**：**只在 MVC 线程内有效**（§4.7 的坑）。

### 7.3 异常文案：i18n 还是硬编码

| 方案 | 多语言 | 集中管理 | 复杂度 | 本项目 |
|---|---|---|---|---|
| **i18n 消息码（`BaseException`）** | **✔** | **✔** | 高（要维护 properties） | 用户/登录异常 |
| **硬编码文案（`ServiceException`）** | ✗ | ✗（散在代码里） | 低 | **业务异常主力** |

**结论**：**两者是"规范 vs 效率"的权衡**。**用户可见的固定文案（验证码、登录失败）适合 i18n；业务代码里一次性、带上下文的文案适合硬编码。** 本项目**两条路并存**——**不统一，但实用。**

## 本章小结 & 下一步

- **统一返回**：`R<T>`（`code`/`msg`/`data`，`SUCCESS=200 :37`、`FAIL=500 :42`）+ 分页 `TableDataInfo<T>`（`build(IPage) :74`）。**静态工厂 + 私有构造**（`restResult :89`）——**具名构造器模式**。
- **约定**：**HTTP 状态码恒为 200，业务码放 body 里**——前端一个拦截器看 `code` 搞定。**代价**：APM 分不出业务失败与系统故障。
- **异常统一处理**：`GlobalExceptionHandler`（`@RestControllerAdvice :52`）——**Sa-Token 认证/鉴权异常 → 401（`:102`）/ 403（`:62`/`:92`）**；`ServiceException` → 500 或自定义 code（`:123`）；参数校验三种异常 → 拼接消息；数据库异常 → 通用话术 + 日志；`RuntimeException`（`:159`）/ `Exception`（`:169`）**两级兜底**。
- **匹配规则**：**Spring 选"最具体"的 handler**——所以专属 handler 优先，兜底只收"没人管的"。
- **异常家族**：`ServiceException`（硬编码文案，298 处主力，`final`）vs `BaseException`/`UserException`（i18n 消息码，`getMessage() :77` 查 `messages.properties`）。
- **★ 核心坑**：**`@Async` 异常进不了全局处理器**（跑在别的线程）——走 `AsyncConfig.getAsyncUncaughtExceptionHandler(:56)`，**只能记日志**；`:65` 那个 `throw new ServiceException` **是无效的重抛**。
- **坦白点**：① **`BaseException`/`UserException` 无专属 handler，登录失败 code 是 500**（和系统错混在一起）；② **兜底 handler 把原始 `e.getMessage()` 返回前端**（`:163`/`:173`，信息泄漏风险）；③ **`GlobalException` 是零引用死代码**；④ **`TableDataInfo` 同名类存在两份**（`ruoyi-common` 与 `zxcm-workflow`，classpath 隐患）。
- **可迁移的思维**：**"把横切关注点从业务里抽出来"**（Advice）、**"错误分语义分级"**（401/403/500）、**"日志记真相、返回记人话"**（安全原则）。
