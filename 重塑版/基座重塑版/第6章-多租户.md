# 第 6 章 · 多租户

> **前五章讲的都是"一个人"的事**：怎么认证、怎么授权、能看哪些行、能登录几处。**本章换一个维度**——**"一整个客户和另一个客户之间怎么隔离"**。
>
> **"多租户（multi-tenant）"的意思是**：一套系统、一份代码、一个数据库，**同时服务多个客户（租户）**，但**A 客户永远看不到 B 客户的任何数据**。这在本项目里是**硬需求**——合同系统是卖给不同公司的（每个公司一个租户）。
>
> **本章第一次讲透**：① 多租户的三种数据库方案，本项目选了哪种、为什么；② `tenant_id` 是怎么被**自动加进每一条 SQL** 的（MyBatis-Plus `TenantLineInnerInterceptor` + `CommonTenantHandler`）；③ 哪些表**必须"免隔离"**（菜单、字典这些系统级共享表）；④ 没有登录上下文时（定时任务、第三方回调）租户从哪来；⑤ 第 2 章的 `loginId` 为什么必须带 `tenantId` 前缀——**这一章给你答案**。

---

## 一、这部分是做什么的？

> ### 零基础先补概念
>
> 1. **租户（tenant）**：一套系统里的一个"客户公司"。本项目的租户 ID 是字符串，默认 `"00000000"`（`TenantProperties.java:30`）。
> 2. **租户列（`tenant_id`）**：每张业务表都多一列，存这条数据属于哪个租户。项目里列名由 `TenantProperties.getColumn()` 返回（`TenantProperties.java:35`，值为 `tenant_id`）。
> 3. **SQL 自动改写**：开发写 `SELECT * FROM contract_draft`，MyBatis-Plus 插件自动补成 `... WHERE tenant_id = '00000000'`。入口是 `TenantLineInnerInterceptor`（`MybatisPlusConfig.java:47-49`）。
> 4. **ThreadLocal**：Java 的"线程内共享变量"。同一个请求线程里，任何方法都能取到同一份数据；不同线程互不干扰。本项目的 `LoginHelper.currentTenantId` 就是用它（`LoginHelper.java:49`），解决"MyBatis 回调里没有租户参数"的问题。

### 1.1 什么是"租户"

**租户（tenant）= 一个"使用这套系统的客户/组织"。** 在 SaaS 语境里，就是"一家用了你系统的公司"。

**多租户要解决的唯一问题**：**A 公司的数据，B 公司绝不能看到——哪怕他们用的是同一个数据库、同一套表。**

**这和"数据权限"（第 4 章）的区别：**

| | 数据权限（第 4 章） | 多租户（本章） |
|---|---|---|
| 隔离谁和谁 | **同一个租户内**的不同部门/人 | **不同租户之间** |
| 典型问题 | 销售一部看不到二部的合同 | 甲公司看不到乙公司的合同 |
| 谁管 | 角色的数据范围 | **租户 ID** |
| 层级 | 租户**内部**的事 | 租户**之间**的事 |

**顺序上，租户隔离是"更外层"的隔离**——先保证"你只能在这一家公司里活动"，再在"这家公司里"讲数据权限。

### 1.2 三种多租户数据库方案

| 方案 | 结构 | 隔离强度 | 成本 | 适合 |
|---|---|---|---|---|
| **独立数据库** | 每个租户一个库 | 最强 | 最贵（N 套库、N 套运维） | 金融、政府（强合规） |
| **独立 Schema** | 同库、每租户一个 schema | 中 | 中 | 中型 SaaS |
| **共享表 + 租户列（本项目）** | **一张表，多一列 `tenant_id`** | 最弱（靠代码保证） | **最低** | **中小型 SaaS、后台系统** |

**本项目的选择：共享表 + `tenant_id` 列。** 每张业务表都有 `tenant_id` 列，每条 SQL 都被自动加上 `tenant_id = 'xxx'` 条件。

### 1.3 一句话说清本项目的租户机制

> **`tenant_id` 自动加进每条 SQL 的 WHERE 里，靠的是 MyBatis-Plus 的"租户插件"，业务代码完全无感。**

**这与第 4 章的数据权限是"同一套机制、两层叠加"**——都是"拦截 SQL → 往 WHERE 里塞条件"。**区别只是塞的是 `tenant_id`，还是数据权限的部门列/人员列（如 `drafter_id`、`a.contract_charge_id`）。**

### 1.4 租户 ID 从哪来？—— 又是 loginId

第 2 章讲过，本项目的 `loginId = tenantId:userType:userId`（`LoginUser.java:135-137` 的 `getLoginId()`）。**当时你可能觉得"为什么要带租户前缀"**——**本章就是答案**：

看 `CommonTenantHandler.getTenantId()`（`ruoyi-base/ruoyi-tenant/src/main/java/com/ruoyi/tenant/CommonTenantHandler.java:44`）：

```java
return new StringValue(LoginHelper.getTenantId());   // :44 从当前登录用户取租户
```

**而 `LoginHelper.getTenantId()` 就是从 `LoginUser.tenantId` 取的**。`LoginUser.tenantId` 是登录时 `buildLoginUser` 从用户记录里赋进去的（`SysLoginService.java:245`：`loginUser.setTenantId(user.getTenantId())`），而 `loginId` 的前缀用的也是同一个 `tenantId`（`LoginUser.java:135-137`）。**所以整条链是**：

```
登录时：前端选/传 tenantId → 按该租户查出 SysUser → buildLoginUser 写入 LoginUser.tenantId
   ↓
同时：loginId = "00000000:sys_user:101"（前缀就是同一个 tenantId）
   ↓
每次查库：CommonTenantHandler.getTenantId() → LoginHelper.getTenantId() → "00000000"
   ↓
SQL 自动变成：WHERE tenant_id = '00000000'
```

**"loginId 带租户前缀"不是装饰，而是"每次查库都能知道该用哪个租户"的根。** 这就是第 2 章那个设计在本章的兑现。

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么选"共享表 + tenant_id"，而不是独立库？

**因为成本。** 独立库/独立 Schema 的隔离最彻底，但代价是：

- 每来一个客户要**建库/建 schema、跑初始化脚本**；
- **升级要升级 N 次**（改表结构要改所有库）；
- 运维复杂度随客户数**线性增长**。

**共享表方案**：所有租户在一张表里，靠 `tenant_id` 区分。**升级一次全租户生效，加客户只是插一条 `sys_tenant` 记录。**

**代价是什么？** ——**"隔离靠代码保证"**：一旦某条 SQL 忘了加 `tenant_id` 条件，就会**串数据**。**所以本项目的关键不是"选了什么方案"，而是"怎么保证每条 SQL 都不漏"。** 答案就是下一节的"自动拦截改写"。

> 📌 **面试点**：说得清"共享表方案最大的风险是漏加条件，所以我们用 MyBatis 拦截器**强制自动加**，而不是靠开发手写"——这是真正懂行的人的回答。

### 2.2 为什么用"插件自动改写"而不是"每个 Mapper 手写"？

**手写 `WHERE tenant_id = ?` 的问题**：

1. **一定会漏**——几十上百个 Mapper 方法，靠人记着写，必然出事；
2. **一旦漏就是生产事故**——串数据是**最严重的 bug 之一**（A 公司看到 B 公司合同）；
3. **改起来痛苦**——租户列改名要改所有地方。

**自动改写的价值**：**把"安全约束"从"开发的自律"变成"框架的强制"**。开发写 `SELECT * FROM contract_draft WHERE contract_status='...'`，**框架自动补成 `... AND tenant_id='xxx'`**。**开发"想漏都漏不掉"。**

**这就是"用基础设施保证正确性"的思路**——**不依赖人的自觉，依赖机制。**

### 2.3 但不是所有表都该隔离——"免隔离表"

有些表**是全系统共享的**，**不该有 `tenant_id`**。看 `TenantProperties.getInstance()`（`TenantProperties.java:46-88`）里硬编码的免隔离表清单：

```java
list.add("sys_menu");              // :50 菜单 —— 所有租户用同一套菜单定义
list.add("sys_config");            // :51 参数配置
list.add("sys_dict_data");         // :52 字典数据
list.add("sys_dict_type");         // :53 字典类型
list.add("gen_table");             // :54 代码生成器（系统级工具）
list.add("gen_table_column");      // :55
list.add("sys_business_module");   // :56 业务模块定义
list.add("sys_business_module_menu");  // :57
list.add("sys_tenant_module");     // :58 租户开通了哪些模块
list.add("sys_oss_config");        // :59 文件存储配置
list.add("notify_template");       // :60 通知模板
// 然后是 22 张 Activiti 工作流引擎自带表（ACT_*）    :63-84
list.add("ACT_GE_BYTEARRAY");      // ...
list.add("ACT_RU_VARIABLE");       // :84
```

**为什么这些表免隔离？** 分三类：

| 类型 | 例子 | 为什么免隔离 |
|---|---|---|
| **系统元数据** | `sys_menu` / `sys_dict_*` / `sys_config` | **所有租户共用一套**（菜单结构、字典项公司间一致） |
| **系统工具表** | `gen_table` / `sys_business_module` | 代码生成器、模块定义是**平台级**的，不属于某个租户 |
| **第三方引擎表** | `ACT_*`（Activiti 22 张） | **工作流引擎的表结构不由我们控制**，而且引擎自己管理隔离 |

**关键理解**：**"免隔离"不等于"不隔离"，而是"这张表的隔离维度不是租户"**——菜单用 `tenantFlag` 字段另做区分（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/entity/SysMenu.java:138`；第 1 章讲过）。

> ⚠️ **坦白点（清单硬编码在 Java 里）**：这份"免隔离表清单"是**硬编码在 `TenantProperties.getInstance()` 里的**（`:49-85`），**不是配置项**。也就是说**新增一张系统级共享表，必须改 Java 代码重新发版**。更灵活的做法是放 `application.yml` 或数据库。本项目选了"写死"——**简单、可控，但不够灵活**，这是要把话说透的地方。

### 2.4 有些查询要"临时"跳过租户——`@InterceptorIgnore`

除了"整张表免隔离"，还有"**某一次查询**免隔离"的需求。比如：

- 登录时**还没登录**，要按用户名**跨租户**查这个用户属于哪些租户；
- 用户管理部门时，要能查到**所有租户**的部门树。

本项目的做法是 `@InterceptorIgnore(tenantLine = "true")` 注解。全项目用了至少 17 处，举几个：

| 位置 | 为什么跳过租户 |
|---|---|
| `SysUserMapper.java:113/:116/:119/:129` | 登录/查用户要**跨租户**找 |
| `SysTenantMapper.java:29`（**类级**） | 租户表本身**不能按租户过滤**（否则查不到别的租户） |
| `SysTenantModuleMapper.java:30`（类级） | 同上，租户-模块关系表 |
| `SysMenuMapper.java:52` | 菜单是共享表，但要手动控制 |
| `ISysRoleService.java:58`（接口上的注解） | 角色查询某些场景要跨租户 |
| `GenTableMapper.java:29` | 代码生成器（系统级） |
| `NotifyLogMapper.java:33` | 通知日志 |
| `ContractDraftMapper.java:215/:219`、`ContractDraftStatMapper.java:322`、`ContractDraftFilesMapper.java:65`、`ConfFileMapper.java:26` | 具体业务里**需要跨租户统计/取文件**的场景 |

**注意 `sys_tenant` 表是"类级"注解**（`SysTenantMapper.java:29` 打在接口上）——因为**整个 Mapper 的查询都不该被租户过滤**（否则管理员根本看不到其他租户）。**这是"租户表自己不能按租户隔离"的自洽性要求。**

### 2.5 没有登录上下文时，租户从哪来？

**问题**：定时任务、启动初始化、第三方回调……**这些场景没有"当前登录用户"**，那 `getTenantId()` 取不到租户，SQL 就不知道该加什么条件。

本项目给了两个 `ThreadLocal` 兜底（`LoginHelper.java:47-58`）：

```java
//设置无需登录，默认admin
public static final ThreadLocal<Boolean> noLogin = new ThreadLocal<Boolean>();       // :48
public static final ThreadLocal<String> currentTenantId = new ThreadLocal<String>(); // :49
public static void setIsNoLogin() { noLogin.set(true); }                             // :51
public static void setCurrentTenantId(String tenantId) { currentTenantId.set(tenantId); }  // :57
```

看 `CommonTenantHandler.getTenantId()`（`CommonTenantHandler.java:34-49`）怎么用它们：

```java
public Expression getTenantId() {
    try {
        if (new Boolean(true).equals(LoginHelper.noLogin.get())) {          // :36 无登录态？
            String tenantId = LoginHelper.currentTenantId.get();            // :37 手动指定了租户？
            if (StringUtils.isEmpty(tenantId)) {
                return new StringValue(TenantProperties.getInstance().getDefaultTenantId());  // :39 用默认租户
            } else {
                return new StringValue(tenantId);                           // :41 用手动指定的
            }
        } else {
            return new StringValue(LoginHelper.getTenantId());              // :44 正常：从登录用户取
        }
    } catch (Exception e) {
        return new StringValue(TenantProperties.getInstance().getDefaultTenantId());  // :47 异常兜底
    }
}
```

**逻辑树：**

```
有登录态？ ── 是 → 用 LoginHelper.getTenantId()（登录用户的租户）
     │
     └─ 否（定时任务/回调）→ noLogin 标记生效
            ├─ currentTenantId 手动设了？ → 用它
            └─ 没设 → 用默认租户 "00000000"
     （任何异常）→ 兜底默认租户 "00000000"
```

**逐行读：`getTenantId()` 这十几个分支在防什么**

| 行号 | 这一行在干什么 | 为什么这么写 |
|---|---|---|
| `:35` | `try { ... }` | 下面 `LoginHelper.getTenantId()` 要取登录用户，无登录态时可能抛异常；整段包住避免插件把 SQL 搞崩 |
| `:36` | 判断 `noLogin` 标记 | 这是"我明确知道现在没有登录用户"的开关，不是靠猜 |
| `:37` | 读 `currentTenantId` | 定时任务可以手动告诉插件"这次按哪个租户查" |
| `:38-42` | 有值用它，没值用默认 | 手动指定优先于默认值 |
| `:43-45` | 正常请求：从 `LoginUser.tenantId` 取 | 这就是 loginId 带租户前缀的最终兑现 |
| `:46-48` | 任何异常都退回默认租户 | 保证 `getTenantId()` **永远能返回一个值**，不会让 SQL 生成失败 |

> 📌 **注意一个容易误解的点**：`noLogin` 不是"跳过租户"，而是"**换一种方式取租户**"——它仍然会拼 `tenant_id`，只是值来自 `currentTenantId` 或默认租户。**"跳过租户"是 `@InterceptorIgnore` / 免隔离表的事，两者别混。**

**默认租户 `"00000000"`**（`TenantProperties.java:30`）——**所有"无上下文"的场景都归到这个租户**。

> ⚠️ **坦白点（默认租户是"安全默认值"还是"风险默认值"？）**：`"00000000"` 这个默认租户，在 `SysLoginController.java:83`（**登录时没传租户就用它**）和 `ThirdAuthController.java:110/:153/:195`（**第三方登录**）都被用到。
> **这意味着"没指定租户"一律进 `00000000`。** 好处是"永不空租户"（不会因为取不到租户而报错）；**风险是**："本该属于别的租户的操作，如果忘了设 `currentTenantId`，就会落到 `00000000`"——**在 `00000000` 里就可能看到该租户的数据**。**所以 `00000000` 必须是"内部/系统租户"，不能是某个真实客户。** 这是**必须守住的一条线**。

**为什么用 `ThreadLocal` 而不是方法参数？** 因为要**在"没有方法能传参"的地方也拿到租户**——比如 `CommonTenantHandler` 是被 MyBatis 回调的，**它没有"租户"参数**，只能从线程上下文取。**`ThreadLocal` + 请求线程绑定**是唯一能"跨层传递、又不改所有方法签名"的办法。

### 2.6 `TenantProperties` 为什么是个"单例"而不是 `@ConfigurationProperties`？

看 `TenantProperties.java:26-88`——它**没有 `@ConfigurationProperties` 注解**，而是自己实现了单例：

```java
private static TenantProperties instance;                    // :26
private TenantProperties() { }                               // :43 私有构造
public static TenantProperties getInstance() {               // :46
    if (instance == null) {
        instance = new TenantProperties();
        // ... 初始化 ignoreTables 清单 ...
    }
    return instance;
}
```

**为什么自己写单例？** 因为它**需要在"Spring 容器之外"被使用**：

- `CommonTenantHandler` 是 `new` 出来的（`MybatisPlusConfig.java:48`：`new CommonTenantHandler()`），**不是 Spring Bean**；
- 它拿不到 Spring 注入的 `@ConfigurationProperties` Bean，**只能用静态单例**。

**这是一个"框架约束逼出来的设计"**——**很有教学价值**：**不是所有配置都能用 `@ConfigurationProperties`，当消费方在容器外时，静态单例是简单粗暴的解。**

> ⚠️ **坦白点（单例的线程安全）**：`getInstance()`（`:46-88`）**没有加锁**——理论上并发首次调用可能 `new` 两次。但由于初始化很轻（就是填几个 list），**实践中几乎无影响**。**严谨写法应加 `synchronized` 或静态初始化块**。面试若被追问"你发现这段单例有什么问题"，答这个。

### 2.7 ★ 插件链顺序：租户在数据权限之前

看 `MybatisPlusConfig.java:44-57`：

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();

    TenantLineInnerInterceptor tenantLineInnerInterceptor = new TenantLineInnerInterceptor();  // :47
    tenantLineInnerInterceptor.setTenantLineHandler(new CommonTenantHandler());                // :48
    interceptor.addInnerInterceptor(tenantLineInnerInterceptor);                               // :49 ★ 第 1 个

    interceptor.addInnerInterceptor(dataPermissionInterceptor());     // :51 ★ 第 2 个（第 4 章）
    interceptor.addInnerInterceptor(paginationInnerInterceptor());     // :53 ★ 第 3 个（分页）
    interceptor.addInnerInterceptor(optimisticLockerInnerInterceptor());  // :55 ★ 第 4 个（乐观锁）
    return interceptor;
}
```

**顺序是**：**租户 → 数据权限 → 分页 → 乐观锁**。

**为什么这个顺序重要？** MyBatis-Plus 的 `InnerInterceptor` 是**按添加顺序执行的链**。想象一条原始 SQL：

```
SELECT * FROM contract_draft WHERE contract_status='...'
```

1. **租户插件**先加：`... WHERE contract_status='...' AND tenant_id='00000000'`
2. **数据权限插件**再加：`... AND (drafter_id IN ('101','102','103'))`（以草稿列表为例，第 4 章）
3. **分页插件**最后包一层：`... LIMIT 0,10`（并对 count 用同样条件）
4. 乐观锁插件处理 `UPDATE ... SET version=version+1`（本项目暂未找到 `@Version` 字段，实际未启用，见第 7 章 §4.1 坦白点）

**为什么租户必须在最前？** ——因为**分页的 count 查询、数据权限的条件**都基于"已经带上租户条件的 SQL"。**租户是最外层的隔离，必须最先落地。**

> 📌 **这是本章最该记住的一句话**：**"租户 → 数据权限 → 分页 → 乐观锁，四道改写依次叠加，最终 SQL 是四层条件的叠加。"** 第 4 章讲的"数据权限改写"只是这条链的**第二环**。

## 三、需要哪些技术？

| 技术 / 机制 | 在本章里具体指什么 | 精确定位 | 详解在哪 |
|---|---|---|---|

## 四、功能具体怎么实现（带着你读懂）

### 4.1 插件注册（回顾 §2.7）

`MybatisPlusConfig.java:44-57` 注册了四层插件，**租户插件排第一**。这是整个多租户机制的"开关"。

### 4.2 `CommonTenantHandler` 的三个方法

`ruoyi-base/ruoyi-tenant/src/main/java/com/ruoyi/tenant/CommonTenantHandler.java`（`:26-74`），实现 MyBatis-Plus 的 `TenantLineHandler`：

**① `getTenantId()`（`:34`）** —— **"这条 SQL 该加哪个租户"**。返回一个 JSqlParser 的 `Expression`（`new StringValue("00000000")`）。逻辑见 §2.5。

**② `getTenantIdColumn()`（`:57`）** —— **"租户列叫什么"**：

```java
public String getTenantIdColumn() {
    return TenantProperties.getInstance().getColumn();    // :58 → "tenant_id"
}
```

**③ `ignoreTable(tableName)`（`:68`）** —— **"这张表要不要隔离"**：

```java
public boolean ignoreTable(String tableName) {
    if (!TenantProperties.getInstance().getEnable()) {    // :69 全局关了 → 全不隔离
        return true;
    }
    return TenantProperties.getInstance().getIgnoreTables().contains(tableName);  // :72
}
```

**返回 `true` = "忽略这张表"（不隔离）**。所以**两种表不隔离**：① 全局 `enable=false`（全关）；② 在免隔离清单里的表。

> ⚠️ **注意 `ignoreTables.contains(tableName)` 是"精确匹配表名"**（`:72`）——写 `sys_menu` 只匹配 `sys_menu`，不会匹配 `sys_menu_xxx`。**大小写敏感**（Java `List.contains` 用 `equals`）。如果 SQL 里表名带别名或反引号，要小心——**这是实际调优时可能踩的坑**。

### 4.3 免隔离表清单（回顾 §2.3）

`TenantProperties.java:49-85` 硬编码了 **11 张系统表 + 22 张 Activiti 表**。工作流引擎表（`ACT_*`）**全部免隔离**，因为是**第三方引擎的固定表结构**，我们改不了、也不该改。

### 4.4 手动跳过：`@InterceptorIgnore`

```java
@InterceptorIgnore(tenantLine = "1")     // SysTenantMapper.java:29（类级）
public interface SysTenantMapper extends BaseMapperPlus<SysTenantMapper, SysTenant, SysTenantVo> { ... }
```

**类的注解打在接口上 = 整个 Mapper 都不隔离**（`sys_tenant` 表本身不能按租户过滤）。方法级则只影响那一个方法。

> 📌 **`@InterceptorIgnore` 还有个 `dataPermission` 属性**——`GenTableMapper.java:29` 同时写了 `@InterceptorIgnore(dataPermission = "true", tenantLine = "true")`，**意思是"租户和数据权限都跳过"**。**说明这个注解是"多层拦截器"的通用开关**，不只是租户。

### 4.5 无登录上下文的租户（回顾 §2.5）

`noLogin` + `currentTenantId` 两个 `ThreadLocal`。**典型用法**：定时任务开始时 `LoginHelper.setIsNoLogin(true); LoginHelper.setCurrentTenantId("xxx");`，任务结束要 **`remove()`**（否则污染线程池里的下一个请求）。

> ⚠️ **坦白点（ThreadLocal 泄漏风险）**：`noLogin` / `currentTenantId` 是 `ThreadLocal`，**用完必须 `remove()`**。本项目里 `clearCache()`（`LoginHelper.java:113`）只清了 `LOGIN_CACHE`，**没有清这两个**。如果某个定时任务设了 `currentTenantId` 却没清，**在线程池复用线程时，下一个任务可能"继承"上一个任务的租户**——这是一个**潜在的多租户串数据风险**。**排查多租户串数据时，第一个要看的就是"ThreadLocal 有没有清"**。

### 4.6 是不是每个查询都自动加租户？

**是的，只要走了 MyBatis-Plus 的自动 SQL**（`BaseMapper` 的方法、`BaseMapperPlus` 的方法、以及 XML 里没标 `@InterceptorIgnore` 的查询）。**手写的 `@Select` 原生 SQL 也会被拦截**（因为是插件层解析 SQL）。

**唯一的例外**：① 表在免隔离清单里；② 方法/类标了 `@InterceptorIgnore`；③ 全局 `enable=false`。

### 4.7 登录时怎么知道租户？—— `getTenants`

看 `SysLoginController.java:148-151`：

## 五、一个操作的完整生命流程：一条 SQL 被加四层条件

以「张三查合同草稿列表」为例（真实接口 `GET /contract/contractDraft/list`，`ContractDraftController.java:77/:148`；假设他在租户 `00000000`）：

```
GET /contract/contractDraft/list
  │
  ▼ 第 3 章两道拦截器通过 → 第 4 章数据权限已由 handler 接管
  │
  ▼ Service → Mapper: selectDraftPage(...)（ContractDraftMapper.java:45）→ 原始 SQL（条件由 Wrapper 拼）：
     SELECT * FROM contract_draft WHERE contract_status = '...'
  │
  ▼ ┌─ MybatisPlusInterceptor 插件链（MybatisPlusConfig.java:45）──────────
    │
    │ ① TenantLineInnerInterceptor（:47）★
    │    ├─ ignoreTable("contract_draft")？ 不在免隔离清单 → false（要隔离）
    │    ├─ getTenantId()  → CommonTenantHandler.java:34
    │    │     noLogin 为空 → LoginHelper.getTenantId() → LoginUser.tenantId = "00000000"
    │    └─ 改写：... WHERE contract_status = '...' AND tenant_id = '00000000'
    │    （若这个 Mapper 标了 @InterceptorIgnore(tenantLine="1") → 跳过本步）
    │
    │ ② PlusDataPermissionInterceptor（:51）  ← 第 4 章
    │    └─ 读 @DataPermission → 改写：... AND (drafter_id IN ('101','102','103'))
    │
    │ ③ PaginationInnerInterceptor（:53）
    │    └─ 包分页：... LIMIT 0,10   （count SQL 用同样的 WHERE）
    │
    │ ④ OptimisticLockerInnerInterceptor（:55）
    │    └─ 只管 UPDATE，这里不涉及
    └────────────────────────────────────────────────────────────────
  │
  ▼ 最终 SQL（四层叠加、业务代码零感知）：
     SELECT * FROM contract_draft
      WHERE contract_status = '...'
        AND tenant_id = '00000000'               ← 租户隔离（本章）
        AND (drafter_id IN ('101','102','103'))  ← 数据权限（第4章，按草拟人过滤）
      LIMIT 0,10                            ← 分页
  │
  ▼ MySQL 返回"本租户 + 张三可见范围"的草稿
```

**一句话**：**租户隔离在最外，数据权限在内，分页最后包。三层条件叠加，原始 SQL 被"翻译"成了安全 SQL。**

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：你们的多租户是怎么实现的？**

**共享表 + `tenant_id` 列**方案。用 MyBatis-Plus 的 `TenantLineInnerInterceptor`（`MybatisPlusConfig.java:47`）自动给每条 SQL 的 WHERE 加 `tenant_id = 当前租户`。租户 ID 由 `CommonTenantHandler.getTenantId()`（`CommonTenantHandler.java:34`）提供——正常从登录用户 (`LoginUser.tenantId`) 取，**无登录上下文时用 `noLogin` + `currentTenantId` 兜底，最终默认 `"00000000"`**。业务代码零侵入。

**Q2：为什么不用独立数据库/独立 Schema？**

**成本**。独立库隔离最强，但每加一个客户要建库、每次升级要升级 N 次、运维随客户数线性增长。**共享表方案升级一次全租户生效、加客户只插一条记录**。**代价是"隔离靠代码保证"——所以我们用拦截器强制自动加条件，而不是让开发手写。**

**Q3：所有表都要加 `tenant_id` 吗？**

**不是。** 系统级共享表**必须免隔离**——`sys_menu` / `sys_config` / `sys_dict_*`（所有租户共用一套）、`gen_table`（代码生成器）、`sys_business_module`、`sys_oss_config`、`notify_template`，以及 **22 张 Activiti 工作流引擎表**（`ACT_*`，第三方引擎固定表结构）。清单在 `TenantProperties.getInstance()`（`:49-85`）里硬编码。**怎么判断一张表要不要隔离？看它的"隔离维度是不是租户"。**

**Q4：有些查询需要跨租户怎么办？**

用 `@InterceptorIgnore(tenantLine = "true")`。**最典型的是 `sys_tenant` 表本身**（`SysTenantMapper.java:29` 类级注解）——**查租户表不能加租户过滤**，否则只能查到自己、看不到其他租户，逻辑死锁。还有 `SysUserMapper`（登录要跨租户找用户）、`GenTableMapper` 等。

**Q5：★ 插件链的顺序是什么？为什么重要？**

**租户 → 数据权限 → 分页 → 乐观锁**（`MybatisPlusConfig.java:47/51/53/55`）。MyBatis-Plus 的 `InnerInterceptor` 是**按添加顺序执行的链**。**租户必须在最前**，因为它是最外层的隔离，后面的数据权限条件、分页 count 都建立在"已经带上租户条件的 SQL"上。**顺序错了会导致 count 查询漏租户条件等隐蔽 bug。**

**Q6：定时任务/异步线程里，租户从哪来？**

用两个 `ThreadLocal`：`LoginHelper.noLogin`（标记"无登录态"）和 `LoginHelper.currentTenantId`（手动指定租户）（`LoginHelper.java:48-49`）。`CommonTenantHandler` 在 `noLogin=true` 时优先用 `currentTenantId`，没有就用默认租户 `"00000000"`（`CommonTenantHandler.java:36-48`）。

**Q7：`loginId` 为什么要带 `tenantId` 前缀？（跨第 2 章的连环问）**

**因为每次查库都要知道"当前是哪个租户"。** `loginId = tenantId:userType:userId`（`LoginUser.java:135-137` 的 `getLoginId()`），登录时 `buildLoginUser` 把 `SysUser.tenantId` 写进 `LoginUser.tenantId`（`SysLoginService.java:245`），之后 `CommonTenantHandler.getTenantId()` 就能从登录态取到租户，**给每条 SQL 加正确的条件**。**不带租户前缀，就无法在无请求参数的 MyBatis 回调里拿到租户。**

**Q8：多租户有没有串数据的风险？怎么防？**

有。**三个主要风险点**：① **忘了配 `@DataPermission` 之类的自动拦截**（本项目用插件强制，规避了）；② **免隔离表清单漏了某张该隔离的业务表**（漏配就串）；③ **`ThreadLocal` 没清**——`noLogin`/`currentTenantId` 用完不清，**线程池复用时会"继承"上一个任务的租户**。**本项目 `clearCache()`（`LoginHelper.java:113`）只清了 `LOGIN_CACHE`，没清这两个**（坦白点），排查串数据时**先查 ThreadLocal。**

**Q9：默认租户 `"00000000"` 有什么用？有风险吗？**

`TenantProperties.java:30` 定义。用于**登录没传租户**（`SysLoginController.java:83`）、**第三方登录**（`ThirdAuthController.java:110` 等）、**任何取不到租户的异常兜底**（`CommonTenantHandler.java:47`）。**好处是"永不空租户"**；**风险是"本该属于其他租户的操作，若忘了设 `currentTenantId`，会落到 `00000000`，可能看到该租户数据"**。**所以 `00000000` 必须是"内部/系统租户"，不能是真实客户。**

## 七、选型对比：多租户隔离方案

### 7.1 数据隔离方案

| 方案 | 隔离强度 | 成本 | 升级成本 | 跨租户统计 |
|---|---|---|---|---|
| 独立数据库 | ★★★★★ | 高 | 高（N 套） | 难 |
| 独立 Schema | ★★★★ | 中 | 中 | 中 |
| **共享表 + 列（本项目）** | ★★（靠代码） | **低** | **低（一次）** | **易** |

**结论**：**中小型 SaaS + 后台系统，共享表是性价比最优解**；**共享表的关键是"强制自动加条件"，本项目用 MyBatis 拦截器实现。**

### 7.2 "加租户条件"的实现方式

| 方式 | 做法 | 漏配风险 | 维护成本 |
|---|---|---|---|
| 开发手写 | 每个 SQL 自己写 `tenant_id=?` | **高（必漏）** | 改列名要改全部 |
| **MyBatis 拦截器自动（本项目）** | `TenantLineInnerInterceptor` | **低（强制）** | **一处配好** |
| 数据库 RLS | PostgreSQL Row Level Security | 低 | 依赖特定库（MySQL 无） |

**结论**：**MySQL + MyBatis-Plus 场景，"拦截器自动"是事实标准。**

### 7.3 免隔离表的管理方式

| 方式 | 本项目 | 优点 | 缺点 |
|---|---|---|---|
| Java 硬编码 | ✔（`TenantProperties.java:49-85`） | 简单、可控、编译期可见 | **加表要改代码发版** |
| 配置文件 | ✗ | 改配置即可 | 需保证配置加载顺序（容器外访问者要另想办法） |
| 数据库表 | ✗ | 最灵活、可运行时改 | 多一次查询 |

**本项目选了"硬编码"**——**简单胜于灵活**（坦白点：不够灵活，加系统表要发版）。

## 本章小结 & 下一步

- **多租户 = 租户之间的数据隔离**；本项目用 **共享表 + `tenant_id` 列**，靠 **MyBatis-Plus `TenantLineInnerInterceptor` 自动改写 SQL**。
- **租户来源**：正常从 `LoginUser.tenantId`（来自 loginId 的 `tenantId:` 前缀）；无登录态用 `noLogin` + `currentTenantId`；兜底默认租户 **`"00000000"`**。
- **免隔离表**（11 张系统表 + 22 张 `ACT_*`）硬编码在 `TenantProperties.getInstance()`；**单次跳过**用 `@InterceptorIgnore(tenantLine="true")`。
- **插件链顺序**：**租户 → 数据权限 → 分页 → 乐观锁**（`MybatisPlusConfig.java:47/51/53/55`）——租户最外，必须最先。
- **坦白点**：① 免隔离清单**硬编码在 Java**，加表要发版；② `TenantProperties.getInstance()` **无锁**（并发首次可能 new 两次，影响小）；③ `clearCache()` **只清 `LOGIN_CACHE`，没清 `noLogin`/`currentTenantId`**，线程池复用有串租户风险；④ 默认租户 `00000000` 是**双刃剑**（永不空租户 vs 误落该租户看到数据）。

**下一章（第 7 章 · ORM 支撑：MyBatis-Plus 插件链）**：本章和上一章都在讲"插件怎么改写 SQL"，**第 7 章把这条插件链完整讲一遍**——`CreateAndUpdateMetaObjectHandler`（自动填创建人/创建时间）、**逻辑删除**（`del_flag`）、**雪花 ID**（集群防重复）、`BaseEntity` / `BaseMapperPlus`、以及乐观锁。**本章的插件链只是"上一半"，第 7 章补全"下一半"。**
