## 一、这部分是做什么的？

### 零基础先补概念（30 秒）

> **① Maven 模块**：一个大项目拆成多个小工程，每个小工程有自己的 `pom.xml`；根 `pom.xml` 用 `<modules>` 把子模块列出来（`pom.xml:323-336`）。`ruoyi-base` 只是「聚合 pom」，自己不含代码，负责把 5 个子模块打包在一起（`ruoyi-base/pom.xml:13-26`）。
>
> **② Spring Boot 自动配置**：Spring Boot 启动时看到 classpath 里有哪些依赖，就自动帮你装配对应组件。不想要某个自动配置，就在启动类 `exclude` 掉——本项目排除 Spring Security，就是因为鉴权改用 Sa-Token 了（`RuoYiApplication.java:31-37`）。
>
> **③ Web 容器**：真正监听 8080 端口、接收 HTTP 请求的「服务器程序」。**这里有个容易踩的坑**：`application.yml:35-47` 写了一段 Undertow 调优配置，但 `ruoyi-base/ruoyi-framework/pom.xml:26-31`（排除 Tomcat）和 `:38-41`（引入 Undertow）**两段依赖配置都被注释掉了**，所以实际生效的是 `spring-boot-starter-web` 默认带的 **Tomcat**；那段 `server.undertow` 配置目前是「留着备用、未生效」。
>
> **④ 脚手架**：别人写好的一整套后台管理系统骨架（登录、菜单、权限、代码生成都有）。本项目基于 RuoYi-Vue-Plus，但它是 **4.0.1s 血统**，不是网上常见的 5.x（`pom.xml:8-9`）。

### 1.1 一句话：什么叫「基座」

打开答案册根目录，你会看到一堆 `zxcm-*` 目录和一个 `ruoyi-*` 目录。**`ruoyi-*` 就是基座，`zxcm-*` 是业务。**

- **业务**解决「合同怎么审批、模板怎么拼」——只有这个项目才有。
- **基座**解决「用户怎么登录、谁能点哪个按钮、日志怎么记、Excel 怎么导」——**任何**一个后台管理系统都要，所以它被抽出来沉淀成一层，供业务模块复用。

一句话概括基座的作用：**业务模块只管写业务，剩下「登录、鉴权、日志、缓存、异常、导入导出……」全部由基座提供。**

### 1.2 基座 = 哪些代码

| 模块 | 全路径 | 职责 |
|---|---|---|
| **ruoyi-admin** | `ruoyi-admin/` | **启动入口** + Web 控制层（系统管理的 Controller）。打包产物 `zxcm-admin.jar` |
| ruoyi-common | `ruoyi-base/ruoyi-common/` | 通用工具、注解、异常、基础类（`R` / `BaseEntity` / `LoginHelper`…） |
| ruoyi-framework | `ruoyi-base/ruoyi-framework/` | **框架配置与切面**（Sa-Token、Redis、MyBatis-Plus、AOP、WebSocket、异步） |
| ruoyi-system | `ruoyi-base/ruoyi-system/` | 系统管理（用户 / 角色 / 菜单 / 字典 / 部门 / 岗位） |
| ruoyi-tenant | `ruoyi-base/ruoyi-tenant/` | 多租户隔离 |
| ruoyi-generator | `ruoyi-base/ruoyi-generator/` | 代码生成器 |

> **权限、多点登录的代码全在 `ruoyi-framework` 和 `ruoyi-common` 里**——这也是为什么本卷把「读懂 framework / common」当成主线。

### 1.3 本卷要学的四件事（按重要度排）

1. **权限控制**（重点）：认证（你是谁）→ 鉴权（你能不能调这个接口）→ 数据权限（你能看到哪些行数据）。
2. **多点登录**（重点）：同一账号能否多设备同时在线、能否顶人下线、在线用户怎么管。
3. **支撑能力**：多租户、ORM 插件链、操作日志、防重限流、脱敏、异常、缓存字典、文件与 Excel、WebSocket 与异步。
4. **怎么基于基座写新模块**：把上面的「接入点」串起来。

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么要拆「基座 + 业务」两层？

因为**在一个后台系统里，业务代码通常只占三成，剩下七成是可复用的通用能力**。如果把这些通用能力和业务代码混在一起：

- 想给「所有接口」加一层操作日志，得改几十个地方；
- 想升级鉴权方案，业务代码跟着一起动；
- 换一个业务场景（比如从合同系统换成工单系统），通用能力没法复用。

所以架构师把通用能力**下移**成基座，业务模块通过依赖**上移**获得能力。这就是 `ruoyi-admin` → `zxcm-*` → `ruoyi-framework` → `ruoyi-system`/`ruoyi-common` 这条**依赖方向**（`ARCHITECTURE.md:46`）的含义：**只能业务依赖框架，不能框架依赖业务**。

### 2.2 为什么直接基于 RuoYi-Vue-Plus，而不从零写？

这是**最重要的一条设计决策**，也是面试容易被问到的：

> 一个后台管理系统最不缺的就是「造轮子的机会」——登录、菜单权限、字典、代码生成、导入导出，**每家公司的实现都大同小异**。花三个月从零写，不如花三天基于成熟脚手架改造，把时间投在**真正有差异化**的业务上（比如本项目的「合同智能比对」「拼装式起草」「流程设计器」）。

代价是**要接受脚手架的既有设计**：它用什么鉴权框架、怎么组织模块、代码风格如何，你得跟着来。**这是「站在巨人肩膀上」的必然成本，也是所有企业项目的常态。**

### 2.3 为什么基座内部还要再拆 common / framework / system？

| 层 | 回答的问题 | 例子 |
|---|---|---|
| `ruoyi-common` | 「**纯工具**」——不依赖 Spring Web、拿来即用 | `R`、`StringUtils`、`LoginHelper`、实体类 |
| `ruoyi-framework` | 「**框架装配**」——把第三方框架接进 Spring | `SaTokenConfig`、`MybatisPlusConfig`、`RedisConfig` |
| `ruoyi-system` | 「**系统管理业务**」——用户/角色/菜单的增删改查 | `SysUserServiceImpl`、`SysRoleServiceImpl` |

拆分的判断标准是**「依赖了什么」**：`common` 尽量不引入 Web 依赖（所以最底层、能被所有模块引）；`framework` 才引入 Spring Web / 各种 Starter（因为它要装配这些框架）。**依赖越少的模块越靠下**——这是分层的基本功。

## 四、功能具体怎么实现（带着你读懂）

### 4.1 Maven 模块树

根 `pom.xml:323-336` 声明的模块：

```
ruoyi-vue-plus (root, pom)                    ← pom.xml:8-9
├── ruoyi-admin          启动入口 + Web 控制层  ← pom.xml:325
├── ruoyi-base           基础框架聚合（pom）    ← pom.xml:328
│   ├── ruoyi-common     通用工具/注解/异常/基础类
│   ├── ruoyi-tenant     多租户
│   ├── ruoyi-framework  框架配置（Sa-Token/Redis/MP/AOP）
│   ├── ruoyi-system     系统管理（用户/角色/菜单/字典/部门）
│   └── ruoyi-generator  代码生成器
├── zxcm-contract        ★ 合同核心业务
├── zxcm-form            动态表单
├── zxcm-workflow        工作流
├── zxcm-notify          消息通知
└── zxcm-third           第三方（Excel / 钉钉同步）
（zxcm-ui 前端是独立 Vue 工程，不在 Maven 里）
```

`ruoyi-base` 是个**聚合 pom**（`ruoyi-base/pom.xml:13` 的 `<packaging>pom</packaging>`），它的子模块列在 `ruoyi-base/pom.xml:20-26`。

**读法**：看到 `ruoyi-base/ruoyi-framework/...` 就知道「这是框架装配层」；看到 `zxcm-contract/...` 就知道「这是业务代码」。**目录名就是分层。**

### 4.2 依赖方向（一条铁律）

```
ruoyi-admin  ──依赖──▶  zxcm-*（业务）
     │                     │
     └──────────┬──────────┘
                ▼
        ruoyi-framework ──▶ ruoyi-system ──▶ ruoyi-common
```

- **业务模块通过 `ruoyi-framework` 间接获得框架依赖**（`ARCHITECTURE.md:46`）——注意是「依赖传递」，不是「禁止直接使用」。实际业务代码会直接 `import` Sa-Token 的注解和工具类，例如 `zxcm-contract/src/main/java/com/ruoyi/conf/controller/TSigningSubjectController.java:57-58`（`import cn.dev33.satoken...`）、`:144`（`@SaCheckPermission`）。这是因为业务模块依赖了 `ruoyi-framework`，Maven 把 Sa-Token 传递到了 classpath。**「不直接 import Sa-Token」不是本项目的硬约束**；通用登录态读取仍封装在 `LoginHelper` 里。
- **反向依赖是不允许的**：`ruoyi-common` 里绝不会有 `import com.ruoyi.conf.xxx`（引用了某个业务类）。你读懂这条，就能一眼判断「一个类该放 common 还是放业务模块」。

### 4.3 启动类干了什么

启动类是 `ruoyi-admin/src/main/java/com/ruoyi/RuoYiApplication.java:40`：

```java
@SpringBootApplication(exclude = {                 // ① 排除若干自动配置
    DataSourceAutoConfiguration.class,             //    数据源交给 dynamic-datasource 管
    MongoAutoConfiguration.class,
    org.activiti.spring.boot.SecurityAutoConfiguration.class,
    SecurityAutoConfiguration.class,               //    鉴权交给 Sa-Token，不用 Spring Security
    ManagementWebSecurityAutoConfiguration.class
})
@ComponentScan(basePackages = {"com.ruoyi"})       // ② 扫描 com.ruoyi 下所有 Bean
@EnableScheduling                                   // ③ 开启 Spring 定时任务
public class RuoYiApplication {
    public static void main(String[] args) {
        System.setProperty("spring.devtools.restart.enabled", "false");
        SpringApplication application = new SpringApplication(RuoYiApplication.class);
        application.setApplicationStartup(new BufferingApplicationStartup(2048));
        application.run(args);                      // ④ 启动
    }
}
```

（源码在 `RuoYiApplication.java:31-52`，核心逻辑到 `:48` 的 `application.run(args)`）

#### 逐行读：启动类每一行在干什么

| 行号 | 代码 | 白话解释 |
|---|---|---|
| `:31` | `@SpringBootApplication(exclude = {` | 一个组合注解，等于「配置类 + 自动配置 + 组件扫描」三合一。括号里是「不要自动装配哪些东西」。 |
| `:32` | `DataSourceAutoConfiguration.class` | 不要 Spring Boot 自己建数据源——数据源交给 `dynamic-datasource`（`pom.xml:36` 引入）管。 |
| `:33` | `MongoAutoConfiguration.class` | 本项目不用 MongoDB，直接排除，免得它找不到连接配置报错。 |
| `:34` | `org.activiti.spring.boot.SecurityAutoConfiguration.class` | 排除 Activiti 自带的安全自动配置，避免和本项目的鉴权体系打架。 |
| `:35-36` | `SecurityAutoConfiguration` / `ManagementWebSecurityAutoConfiguration` | 排除 Spring Security 的两条自动配置：一条管普通请求，一条管 actuator 监控端点。两行要一起排，否则监控端点仍会被 Spring Security 拦。 |
| `:38` | `@ComponentScan(basePackages = {"com.ruoyi"})` | 让 Spring 去 `com.ruoyi` 包下找所有 `@Component/@Service/@Configuration`。启动类自己就在 `com.ruoyi`（`:14`），默认也会扫这个包；显式写出来是把「所有模块统一在 com.ruoyi 下」这条约定摆到明面上。 |
| `:39` | `@EnableScheduling` | 打开 Spring 自带的 `@Scheduled` 定时任务能力（第 14 章还会讲项目里的线程池/定时任务）。 |
| `:45` | `System.setProperty("spring.devtools.restart.enabled", "false")` | 关掉 devtools 的自动重启。开发时热部署是双刃剑，启动脚本里先关掉，避免改一个文件就重启整个应用。 |
| `:47` | `new BufferingApplicationStartup(2048)` | 记录启动过程的 2048 个步骤，方便启动慢时排查「卡在哪一步」。 |
| `:48` | `application.run(args)` | 真正启动 Spring 容器和 Web 容器；跑完这一行，8080 端口才开始监听。 |

**三个细节值得记**：

1. **排除 `SecurityAutoConfiguration`（`:35`）**——这一行就是「本项目用 Sa-Token 不用 Spring Security」的铁证。Spring Security 一进来就会给**所有**路径套上登录校验，而本项目的鉴权全交给 Sa-Token 的拦截器（`SaTokenConfig.java:55/79`）。
2. **排除 `DataSourceAutoConfiguration`（`:32`）**——因为用的是 `dynamic-datasource`，数据源由它接管。
3. **`@ComponentScan("com.ruoyi")`（`:38`）**——把所有模块的 Bean 一次性扫进来。所以 `ruoyi-framework` 里的 `SaTokenConfig`、`ruoyi-system` 里的各种 Service，只要在 `com.ruoyi` 包下就会被装配。

### 4.4 配置体系

主配置 `ruoyi-admin/src/main/resources/application.yml`，几个关键点：

| 配置 | 值 | 位置 |
|---|---|---|
| 应用名 | `zxcm`（`${ruoyi.name}`） | `application.yml:2-4, 58-59` |
| HTTP 端口 | **8080** | `application.yml:28-30` |
| 激活 Profile | `@profiles.active@`（Maven 占位，编译时替换） | `application.yml:66-67` |
| Web 容器 | 配置里写了 **undertow**（IO 线程 8 / worker 888），但依赖未启用，实际是 **Tomcat** | 配置 `application.yml:35-47`；依赖 `ruoyi-base/ruoyi-framework/pom.xml:22-41` |
| Sa-Token | `token-name: token`、`timeout: 186400`、**`is-concurrent: true`**、**`is-share: false`** | `application.yml:101-125` |
| 免登录白名单 | `security.excludes`（`/login`、`/captchaImage`…） | `application.yml:154-191` |

**Profile 机制**：根 `pom.xml:410-444` 定义了 `local` / `dev` / `prod` 三个 profile，`dev` 是默认（`pom.xml:432` 的 `<activeByDefault>true</activeByDefault>`）。编译时 `@profiles.active@` 被替换成 `dev,workflow`，于是 Spring 会加载 `application-dev.yml` + `application-workflow.yml`。**这就是为什么改 Maven profile 能切换环境。**

### 4.5 「框架 vs 业务」边界判定法（本卷最实用的一条）

拿到一个类，怎么判断它属于基座还是业务？

| 判据 | 属于基座 | 属于业务 |
|---|---|---|
| **换个项目还能用吗** | 能（登录、日志、导入导出） | 不能（合同审批） |
| **包路径** | `com.ruoyi.framework.*` / `com.ruoyi.common.*` / `com.ruoyi.system.*` | `com.ruoyi.contract.*` / `com.ruoyi.conf.*`… |
| **依赖方向** | 不 import 任何 `zxcm-*` | 可以 import 基座 |
| **有没有业务名词** | 无（`SysUser` / `SysRole`） | 有（`Contract` / `Template`） |

**面试时如果被问「你们这套框架的可复用性怎么样」**，你可以用这条判据回答：「凡是不含业务名词、且不反向依赖业务模块的，都沉在 `ruoyi-base` 里，换项目能直接拿走。」

### 4.6 动手验证：把这套「版本坐标」跑一遍

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：你这个项目为什么用现成的脚手架，而不是自己从零搭？**

因为后台系统的通用能力（鉴权、权限、字典、代码生成、导入导出）行业标配、高度雷同，从零写投入产出比极低。基于成熟的 RuoYi-Vue-Plus 改造，能把时间投在真正有差异化的业务上（本项目的合同智能比对、拼装式起草、流程设计器）。**代价是要适配脚手架既有设计**——这是有意识的工程取舍，不是能力不足。（依据：`pom.xml:7-9` 声明基于 `ruoyi-vue-plus`；`RuoYiApplication.java:9-11` 的 MIT 授权注释）

**Q2：你们后端一共几个 Maven 模块？依赖方向是什么？**

两类：**基座**（`ruoyi-admin` / `ruoyi-base` 下的 `common`、`tenant`、`framework`、`system`、`generator`）和**业务**（`zxcm-contract` / `zxcm-form` / `zxcm-workflow` / `zxcm-notify` / `zxcm-third`）。依赖方向单向：`ruoyi-admin` → 业务模块 → `ruoyi-framework` → `ruoyi-system` / `ruoyi-common`，**业务依赖框架，框架绝不反向依赖业务**。（`pom.xml:323-336`、`ruoyi-base/pom.xml:20-26`）

**Q3：为什么要排除 Spring Security 的自动配置？**

因为本项目鉴权用 Sa-Token。Spring Security 的自动配置一生效，就会给所有路径套上它自己的登录校验，与 Sa-Token 的拦截器冲突。所以在启动类显式排除 `SecurityAutoConfiguration`（`RuoYiApplication.java:35`），把鉴权权完全交给 `SaTokenConfig` 的两道拦截器（`SaTokenConfig.java:55/79`）。

> **追问：只排除 `SecurityAutoConfiguration` 行不行？** 不够。actuator 监控端点由另一条 `ManagementWebSecurityAutoConfiguration` 保护，所以 `RuoYiApplication.java:36` 把两条一起排除；否则 `/actuator/**` 仍可能被 Spring Security 拦成 401。

**Q4：`ruoyi-common` 和 `ruoyi-framework` 的区别是什么？**

`ruoyi-common` 是**纯工具层**（`R`、`BaseEntity`、`LoginHelper`、实体类），尽量不引入 Web 依赖，所以能被所有模块依赖；`ruoyi-framework` 是**框架装配层**（`SaTokenConfig`、`MybatisPlusConfig`、`RedisConfig`），要引入各种 Spring Boot Starter 把第三方框架接进来。**判断标准是「依赖了什么」**——依赖越少的越靠下。

**Q5：网上 RuoYi-Vue-Plus 的教程能直接照抄吗？**

**不能直接抄代码，但能学设计思想。** 网上主流是 **5.x**（Spring Boot 3 / JDK 17 / 包名 `org.dromara` / `jakarta.*`），本仓库是 **4.0.1s**（Spring Boot 2.6.4 / JDK 11 / 包名 `com.ruoyi` / `javax.*`）。概念（数据权限靠 JSqlParser 改写 SQL、同端互斥要指定设备类型）通用，代码必须落回本仓库。**能主动说出这个版本差异，本身就是加分项**——说明你不只是抄教程，而是真读了源码。

**Q6：你们用的是 Tomcat 还是 Undertow？`application.yml` 里的 Undertow 配置为什么没生效？**

**先纠正一个常见误读：当前仓库实际跑的是 Tomcat，不是 Undertow。** `ruoyi-base/ruoyi-framework/pom.xml:22-32` 用的是 `spring-boot-starter-web`，其中「排除 Tomcat」的 `<exclusions>` 被注释掉了；`:37-41` 的 `spring-boot-starter-undertow` 也被整段注释。因此 `application.yml:35-47` 那段 `server.undertow` 调优（IO 线程 8、worker 线程 888、`direct-buffers: true`）**当前不会生效**。

面试里可以这样答：**「源码保留了 Undertow 的切换方案和调优参数，但依赖没有启用，实际容器是 Spring Boot 默认的 Tomcat。要启用 Undertow，需要放开两段注释：排除 `spring-boot-starter-tomcat`、引入 `spring-boot-starter-undertow`。」** 这样既讲清了 Undertow 的优点（JBoss 出品、内存占用低、并发表现好），又不会被源码打脸。

### 本章答辩卡（追问级）

**卡 1：启动类上的 `@ComponentScan("com.ruoyi")` 不写行不行？**

**10 秒答案**：默认扫描规则是「启动类所在包及子包」，启动类本身就在 `com.ruoyi` 下（`RuoYiApplication.java:14`），所以不写通常也能扫到。显式写出来是为了把「所有模块统一放在 `com.ruoyi` 包下」这条约定固定住，防止以后有人把启动类挪到更深的子包导致扫描范围缩小。

**证据**：`ruoyi-admin/src/main/java/com/ruoyi/RuoYiApplication.java:14`（`package com.ruoyi;`）、`:38`（`@ComponentScan`）。

**卡 2：`@profiles.active@` 是谁替换成 `dev,workflow` 的？Spring 认这个语法吗？**

**10 秒答案**：不是 Spring 认，是 **Maven 的资源过滤**在打包时替换的。根 `pom.xml` 对 `application*` 开启 `filtering`，`dev` profile 里定义了 `profiles.active=dev,workflow`，于是编译后 `application.yml` 里的占位符变成真实值，Spring 再按这个值加载 `application-dev.yml` 和 `application-workflow.yml`。

**证据**：`pom.xml:366-376`（资源过滤配置）、`pom.xml:425`（dev profile 的值）、`application.yml:66-67`（占位符位置）。

**卡 3：为什么启动类里要关掉 devtools 的 restart？**

**10 秒答案**：devtools 默认在 classpath 变化时自动重启应用，调试代码时容易「刚打的断点还没看就重启了」。启动入口先把 `spring.devtools.restart.enabled` 设成 `false`（`RuoYiApplication.java:45`），把重启时机交回给开发者；热部署依赖仍然保留，只是不自动触发。

**证据**：`ruoyi-admin/src/main/java/com/ruoyi/RuoYiApplication.java:45`、`ruoyi-admin/pom.xml:31-35`（devtools 依赖被声明为 optional）。

## 七、选型对比：为什么不选其他方案

### 7.1 脚手架：为什么是 RuoYi-Vue-Plus？

| 方案 | 优点 | 本项目的顾虑 |
|---|---|---|
| 从零自研 | 完全可控、无历史包袱 | 半年起步，通用能力重复造轮子 |
| 原生 RuoYi（`ruoyi-vue`） | 用户基数最大、教程最多 | 用 Spring Security（配置重）；无多租户；数据权限弱 |
| **RuoYi-Vue-Plus（选用）** | **Sa-Token + JWT（轻量）**、多租户、MyBatis-Plus、代码生成 | 版本迭代快，需锁版本 |

**结论**：Plus 版相比原版，把鉴权从 Spring Security 换成了 Sa-Token、补齐了多租户、把数据权限做成 MyBatis-Plus 插件——这三点正好是后台系统的核心诉求。所以选 Plus。

### 7.2 鉴权框架：为什么 Sa-Token 不用 Spring Security？

| 方案 | 优点 | 顾虑 |
|---|---|---|
| Spring Security | 生态最强、企业主流 | 概念多（FilterChain / UserDetailsService）、配置重，对「登录 + 菜单权限」场景**过度设计** |
| Shiro | 轻量老牌 | 与 Spring Boot 整合不如 Sa-Token 顺 |
| **Sa-Token（选用）** | **API 极简**（`StpUtil.login()` / `@SaCheckPermission`），注解式鉴权 | 生态小于 Spring Security |

**结论**：合同系统是典型「后台管理系统」，要的就是「登录 + 菜单权限 + 按钮权限」，Sa-Token 用最少代码搞定。**若是有 OAuth2 授权服务器、微服务网关统一鉴权这类复杂需求，才轮到 Spring Security。**（这条会在第 3 章展开）

### 7.3 持久层：为什么 MyBatis-Plus？

| 方案 | 优点 | 顾虑 |
|---|---|---|
| 原生 MyBatis | SQL 完全可控 | 大量样板代码（每个表都要写 CRUD XML） |
| JPA / Hibernate | 面向对象、自动建表 | 复杂报表 SQL 别扭；本项目大量联表查询 |
| **MyBatis-Plus（选用）** | **BaseMapper 白得 CRUD**、条件构造器、**插件链（数据权限 / 分页 / 自动填充）** | 深度定制需懂其扩展点 |

**结论**：本项目「动态条件查询 + 复杂报表 + 无痕数据权限」三个诉求，MyBatis-Plus 都能满足，尤其是**把数据权限做成插件**这一点（第 4 章）是决定性的。
