# 第 2 章 · 认证：登录全链路

> **认证（Authentication）只回答一个问题：你是谁。** 登录成功后，系统给你一个 token，之后每次请求带着它，后端就能还原出「你是哪个租户、哪种用户类型、哪个用户」。
>
> **本章第一次讲透**：① 从 `POST /login` 到 token 落进 Redis 的每一跳；② `LoginUser` 里到底装了什么、为什么要装这些；③ Sa-Token 的**存储交给谁**（`PlusSaTokenDao`）；④ 本书的**多级缓存**设计（`LoginHelper` 的 ThreadLocal + TokenSession）；⑤ 本项目在标准登录上**加的两道业务闸**（3 个月未登录、临时密码过期）。

---

## 一、这部分是做什么的？

### 零基础先补概念（30 秒）

> **① token（令牌）**：登录成功后服务端发给你的一串字符。之后每次请求把它放进请求头（本项目是 `token: Bearer xxx`，`application.yml:119`），服务端凭它认出你。
>
> **② 会话（Session）**：服务端保存的「这个 token 对应哪个人」的记录。本项目不放在 Tomcat 内存里，而是放 **Redis**（一个内存键值数据库），这样多台后端实例都能读到同一份登录状态。落地类就是 `PlusSaTokenDao.java:32`。
>
> **③ Redis 的 key → value**：你可以把它想成超大的 `Map<String, Object>`，还能给每个 key 设过期时间。Sa-Token 用 `satoken:login:token:<token>` 这类 key 保存 token 与会话的对应关系。
>
> **④ 密码哈希（BCrypt）**：数据库里**不存密码原文**，只存一串「算不回去」的指纹。登录时把用户输入的密码用同样算法再算一次，比对指纹（`SysLoginService.java:106`）。

### 1.1 认证要解决什么

登录接口要干三件事：

1. **校验凭证**：账号密码对不对（还要不要验证码）。
2. **组装身份**：这个人是谁、属于哪个租户、有哪些角色和权限码、能看哪些部门。
3. **签发凭证**：生成一个 token 交给前端；以后就用它认人。

### 1.2 登录成功后的两个产物

登录不是「返回一个 token」就完了，**服务端同时要留下「这个 token 对应什么身份」的记录**：

| 产物 | 放在哪 | 作用 |
|---|---|---|
| **token** | 返回给前端；前端用 `js-cookie` 存进 Cookie，key 为 `Admin-Token`（`zxcm-ui/src/utils/auth.js:3-7`） | 每次请求带在请求头 `token: Bearer xxx` |
| **会话（Session）** | **Redis**（Sa-Token 默认 key 形如 `satoken:login:token:xxx`） | 服务端凭 token 查回 `LoginUser` |

**一句话**：token 是「钥匙」，Redis 里的会话是「房间里存的档案」。钥匙丢了档案还在，但进不去；档案被删了，钥匙就失效。

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么用 Sa-Token，不用自己写 token 逻辑？

因为**「生成 token、存会话、校验、续期、踢人、多端」这一整套，Sa-Token 已经做完了**，而且 API 极简：

```java
StpUtil.login(loginId);          // 登录：生成 token，写会话
StpUtil.getTokenValue();         // 拿 token
StpUtil.logout();                // 登出
StpUtil.getTokenSession();       // 拿这个 token 的会话，往里塞东西
```

自己写至少要处理「token 怎么生成、会话存哪、怎么过期、怎么续期、怎么在集群下共享」——**每一个都是坑**。用 Sa-Token，这些东西一行搞定。（选型对比见 §七）

### 2.2 为什么不用「服务端 Session + Cookie」，而要 token？

| 方案 | 会话存哪 | 多端 / 前后端分离 |
|---|---|---|
| 传统 Session + Cookie | 服务端内存（Tomcat Session） | 前后端同源还行，**多端（App/小程序）难** |
| **token + Redis 会话（本项目）** | **Redis（集中式）** | **天然支持多端**、天然支持集群 |

**关键点**：token 方案把「身份」从**单台服务器的内存**挪到了**客户端持有 + 服务端 Redis 集中存**。好处是**应用实例本身不用保存会话**——多台后端实例共享 Redis，谁都能校验，不用粘性会话。**严格说这不是「无状态」**（登录状态仍集中存在 Redis），但应用实例可以随意扩容、重启，这才是它相对传统 Session 的价值。

### 2.3 为什么 token 用 JWT 风格？

看 `SaTokenConfig.java:82-86`：

```java
@Bean
public StpLogic getStpLogicJwt() {
    // Sa-Token 整合 jwt (Style模式)
    return new StpLogicJwtForStyle();
}
```

Sa-Token 默认的 token 是个随机字符串（`token-style: uuid`，`application.yml:121`），**服务端必须查会话才知道你是谁**。切到 **JWT 风格（`StpLogicJwtForStyle`）**后，token 本身变成 JWT 格式（带签名，能解析出 loginId 等信息），但 **Style 模式仍然是有状态的**：完整的 `LoginUser`（权限码、角色、部门）还是从 TokenSession / Redis 读，不能像纯 JWT 那样在无会话时还原全部身份。

**所以本项目是"JWT 风格"而不是"纯 JWT 无状态"**：会话依然落在 Redis（见 §4.5）——因为需要「踢人下线 / 强制注销」这些**必须能主动失效 token**的能力，纯无状态 JWT 做不到。**这是"既要 JWT 的格式便利、又要会话的可控"的折中**。

### 2.4 为什么 `loginId` 要拼成 `租户:用户类型:用户id`？

看 `LoginUser.java:135-137`：

```java
public String getLoginId() {
    return tenantId + LoginHelper.JOIN_CODE + userType + LoginHelper.JOIN_CODE + userId;
}
```

`JOIN_CODE` 是 `":"`（`LoginHelper.java:43`）。所以一个 loginId 长这样：`00000000:sys_user:10001`（默认租户 id 是 `00000000`，`ruoyi-base/ruoyi-tenant/src/main/java/com/ruoyi/tenant/TenantProperties.java:30`）。

**为什么不用裸 userId？** 因为 loginId 要承载的不只是「人」，还有「在哪个租户、用哪套用户体系」：

- **多租户**：loginId 里带 `tenantId`，会话与权限才能按租户区分。注意：本仓库 `sys_user` 的主键是全局唯一的 `USER_ID`（建表语句 `script/sql/zxcm_init.sql:4929-4963`），**当前不会出现「同 id 跨租户」**；带 `tenantId` 是让设计不依赖这个前提，也方便做租户隔离。
- **多用户体系**：`user_type` 枚举预留了 `sys_user`（后台用户）/ `app_user` / `wxmini_user`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/UserType.java:33/38/42`），**当前仓库只实现了 `sys_user`**；`SaInterfaceImpl.java:34-36` 的 `APP_USER` 分支还是空实现（注释写着「自行根据业务编写」）。

**把这三段拼进 loginId，Sa-Token 的世界里就是唯一的**，一套 Sa-Token 同时管多租户多体系（将来接入 App 端时不用改 key 结构）。**面试里这是一个很亮的点：`loginId` 不是「用户 id」，而是「（租户，体系，用户）三元组的字符串表示」；同时要如实说清：当前只落地了 `sys_user` 这一套。**

### 2.5 为什么密码校验用 BCrypt？

`SysLoginService.java:106` 是 `BCrypt.checkpw(password, user.getPassword())`。BCrypt 是**自带 salt、可调计算强度**的密码哈希算法——比 MD5 安全得多（MD5 可彩虹表爆破、且同密码哈希相同）。**存密码永远存哈希，永不存明文**，这是底线。

### 2.6 本项目在标准登录上"加闸"：3 个月未登录 / 临时密码过期

这是本项目对标准 RuoYi 登录的**业务扩展**（`SysLoginService.java:121-148`）：

- **非管理员**用户，**超过 3 个月未登录** → 直接拒绝，提示联系管理员重置密码（`:132-134`）；
- 用户处于「需要改密码」状态（`passwordChange == "1"`），且**距上次重置超过 5 天** → 临时密码过期，拒绝（`:138-147`）。

**为什么？** 合同系统涉及敏感商业信息，「长期不用的僵尸账号」和「长期有效的临时密码」都是安全风险。**把安全策略做成业务规则写进代码**，是这类系统的常见做法。

### 4.3 `buildLoginUser`：`LoginUser` 里装了什么

`SysLoginService.java:236-254`：

```java
public LoginUser buildLoginUser(SysUser user) {
    LoginUser loginUser = new LoginUser();
    loginUser.setUserId(user.getUserId());
    loginUser.setDeptIds(user.getDeptIds());          // 多个部门（本项目扩展）
    loginUser.setDeptNames(user.getDeptNames());
    loginUser.setUsername(user.getUserName());
    loginUser.setUserType(user.getUserType());
    loginUser.setMenuPermission(permissionService.getMenuPermission(user));   // ★ 权限码集合
    loginUser.setRolePermission(permissionService.getRolePermission(user));   // ★ 角色标识集合
    loginUser.setTenantId(user.getTenantId());
    loginUser.setSystemAdmin(user.getSystemAdmin());
    loginUser.setTenantAdmin(user.getTenantAdmin());
    List<RoleDTO> roles = BeanUtil.copyToList(user.getRoles(), RoleDTO.class); // ★ 角色对象（数据权限要用）
    loginUser.setRoles(roles);
    loginUser.setSecretLevel(user.getSecretLevel());   // 合同阅读密级（业务扩展）
    loginUser.setNickName(user.getNickName());
    loginUser.setAvatar(user.getAvatar());
    return loginUser;
}
```

**为什么要把这些"塞进"登录态？** 因为它们**每次请求都要用**，但**每次请求都查库太重**。所以在登录时一次性算好、存进会话：

| 装进去的东西 | 谁用 | 章节 |
|---|---|---|
| `menuPermission` | 鉴权：`@SaCheckPermission` 比对 | 第 3 章 |
| `rolePermission` | 鉴权：`@SaCheckRole` 比对 | 第 3 章 |
| `roles`（RoleDTO 列表） | 数据权限：遍历角色算数据范围 | 第 4 章 |
| `tenantId` / `systemAdmin` / `tenantAdmin` | 多租户、管理员绕过 | 第 4、6 章 |
| `deptIds` | 数据权限：部门范围 | 第 4 章 |

> 📌 **注意 `LoginUser` 里 `roles` 是 `List<RoleDTO>` 而不是 `Set`**——因为**同一用户可能有多个角色**（`LoginUser.java:110`），而**数据权限要向每个角色分别取范围再合并**（`PlusDataPermissionHandler.java:137` 的 `for (RoleDTO role : user.getRoles())`）。
>
> 📌 **`data_scope` 和按模块权限列不在 `LoginUser` 里**——它们在 `RoleDTO` 上（`RoleDTO` 是角色的精简副本）。**这一点第 4 章会讲透**。

### 4.4 `LoginHelper.loginByDevice`：登录态怎么存

`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/helper/LoginHelper.java:41`：

```java
public static void loginByDevice(LoginUser loginUser, DeviceType deviceType) {
    LOGIN_CACHE.set(loginUser);                                        // ① 一级缓存：ThreadLocal
    StpUtil.login(loginUser.getLoginId(), deviceType.getDevice());     // ② Sa-Token 登录（带设备类型）
    setLoginUser(loginUser);                                           // ③ 二级缓存：TokenSession → Redis
}

public static void setLoginUser(LoginUser loginUser) {
    StpUtil.getTokenSession().set(LOGIN_USER_KEY, loginUser);          // 塞进 token 会话
}
```

（`LoginHelper.java:78-89`）

#### 逐行读：`loginByDevice` 与 `setLoginUser`

| 行号 | 代码 | 这一行在干什么、为什么这么写 |
|---|---|---|
| `:79` | `LOGIN_CACHE.set(loginUser);` | 把 `LoginUser` 放进**当前线程**的 `ThreadLocal`（定义在 `LoginHelper.java:46`）。同一请求后续任何地方调 `getLoginUser()` 都直接拿内存对象，不再读 Redis。 |
| `:80` | `StpUtil.login(loginUser.getLoginId(), deviceType.getDevice());` | 真正「登录」：Sa-Token 生成 token，把「token → loginId」的映射写进持久层；第二个参数 `"pc"` 是设备类型，参与多端会话的 key 组成（第 5 章）。**顺序很关键**：必须先有 token，下一行才能拿到这个 token 的会话。 |
| `:81` | `setLoginUser(loginUser);` | 进入 `setLoginUser`（`:87-89`），执行 `StpUtil.getTokenSession().set("loginUser", loginUser)`：把整个 `LoginUser` 塞进 **Token-Session**，最终由 `PlusSaTokenDao` 写进 Redis。 |
| `:88` | `StpUtil.getTokenSession()` | 取「当前 token 对应的会话」。它依赖 Sa-Token 在 `login` 后把 token 放进了请求上下文；如果在 `login` 之前调用，会拿不到有效 token。 |
| `:88` | `.set(LOGIN_USER_KEY, loginUser)` | `LOGIN_USER_KEY` 是字符串 `"loginUser"`（`:44`）。存进去的不是 token，而是**身份对象**；以后凭 token 反查会话，就能还原「我是谁、有哪些权限」。 |

**一句话**：三行分别负责「本次请求用」「Sa-Token 认 token」「Redis 长期存」，任何一行顺序错了，轻则缓存不命中，重则登录态写不进去。

**这是本书的「多级缓存」设计**：

| 级别 | 存哪 | 生命周期 | 位置 |
|---|---|---|---|
| 一级 | `ThreadLocal<LoginUser>` | **一次请求** | `LoginHelper.java:46` |
| 二级 | `StpUtil.getTokenSession()` → Redis | token 有效期 | `LoginHelper.java:88` |

**为什么搞两级？** 因为**一次请求里可能几十次调 `LoginHelper.getLoginUser()`**（每个 Service 都可能要用当前用户）。如果每次都反序列化 Redis 里的对象，开销大。**一级缓存让「同一次请求」只读一次 Redis**——读完就放 ThreadLocal，后续直接拿。

**读取时（`LoginHelper.java:94-100`）**：
```java
public static LoginUser getLoginUser() {
    LoginUser loginUser = LOGIN_CACHE.get();              // 先看 ThreadLocal
    if (loginUser != null) return loginUser;
    return (LoginUser) StpUtil.getTokenSession().get(LOGIN_USER_KEY);  // 没有再读 Redis
}
```

**⚠️ ThreadLocal 必须清理！** 因为线程会被复用（本项目实际是 Tomcat 线程池，见第 0 章 §3.1），不清理会把 A 用户的身份泄漏给下一个请求。所以 `SaTokenConfig.java:75-77` 在 `afterCompletion` 里调 `LoginHelper.clearCache()`——**请求一结束就清掉一级缓存**。这是**ThreadLocal 使用的标准姿势**，面试很爱问。

### 4.5 `PlusSaTokenDao`：Sa-Token 的存储在 Redis

Sa-Token 通过 SPI 接口 `SaTokenDao` 抽象「会话存哪」。本项目用 Redis 实现（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/satoken/dao/PlusSaTokenDao.java:32`）：

```java
@Component
public class PlusSaTokenDao implements SaTokenDao {
    @Override public String get(String key) { return RedisUtils.getCacheObject(key); }
    @Override public void set(String key, String value, long timeout) {
        if (timeout == 0 || timeout <= SaTokenDao.NOT_VALUE_EXPIRE) return;
        if (timeout == SaTokenDao.NEVER_EXPIRE) RedisUtils.setCacheObject(key, value);
        else RedisUtils.setCacheObject(key, value, Duration.ofSeconds(timeout));   // 带 TTL
    }
    @Override public long getTimeout(String key) { ... }   // 查剩余存活时间
    @Override public void updateTimeout(String key, long timeout) { ... }   // 续期
    @Override public List<String> searchData(String prefix, String keyword, int start, int size) { ... }
}
```

**关键点**：这个类是**存储层唯一**需要把 Sa-Token 接进本框架的地方——**换存储只改这一个类**（比如换成 `SaTokenDaoRedisJackson` 官方实现）。拦截器/JWT 风格的装配另有 `SaTokenConfig`（`SaTokenConfig.java:44`）；这就是**面向接口编程**的价值。

> 📌 `set` 里的三种情况处理（`:47/:51/:54`）值得看：**「不该过期（timeout=0 或负）→ 不写」；「永不过期（NEVER_EXPIRE）→ 不带 TTL」；「普通过期 → 带 TTL」**。不处理「不该过期」会在 Redis 里留下一堆垃圾 key。

### 4.6 拿到 token 之后：`getInfo` / `getRouters`

前端登录成功后**立刻**再调两个接口：

- `GET /getInfo`（`SysLoginController.java:109-127`）→ 返回 `user / roles / permissions`。**前端把 permissions 存进 Vuex**，`v-hasPermi` 指令靠它隐藏按钮。
  > 注意这里**又查了一次** `permissionService.getMenuPermission(user)`（`:115`）——它与会话里的 `menuPermission` 是**同源**的（都来自 `SysPermissionService`）。**登录那一刻**两者一致；但如果登录后管理员改了角色权限，`getInfo` 会因为重新查库而变，会话里的旧集合不变——这就是「改权限要重新登录」的由来（第 3 章 §4.2）。
- `GET /getRouters`（`SysLoginController.java:135-140`）→ 返回**动态路由**（菜单树）。**前端据此生成路由**——这就是「后端控制菜单、前端动态挂路由」的机制（前端卷有专章）。

### 4.7 登出

`POST /logout`（`SysLoginController.java:93-101`）：
```java
try {
    loginService.logout(LoginHelper.getUsername());   // 记登出日志
    StpUtil.logout();                                 // Sa-Token 注销当前 token
} catch (NotLoginException e) { }                     // 未登录也当"退出成功"
return R.ok("退出成功");
```
**`catch (NotLoginException)` 空吞**是一个刻意的宽容设计——重复登出不该报错。

### 4.8 动手验证：登录一次，盯住 Redis

> 前提：后端已在 8080 启动；Redis 地址/密码见 `application-dev.yml`。下面的 Redis 命令以本机 `redis-cli` 为例，若 Redis 在虚拟机里，换成 `redis-cli -h 192.168.56.10 -a root`。

1. **确认验证码开关**（初始化数据默认是开，`script/sql/zxcm_init.sql:3476`）：

   ```sql
   SELECT CONFIG_KEY, CONFIG_VALUE FROM sys_config
   WHERE CONFIG_KEY = 'sys.account.captchaOnOff';
   ```

   预期：`true`。代码在 `ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysConfigServiceImpl.java:104` 读取；查不到时默认也返回 `true`（`:105-107`）。

2. **拿验证码，记下 `uuid` 和答案**：

   ```bash
   curl -s http://localhost:8080/captchaImage
   redis-cli GET "captcha_codes:<上一步返回的 uuid>"
   ```

   预期：第一个命令的 JSON 里有 `data.uuid` 和 `data.img`（`ruoyi-admin/src/main/java/com/ruoyi/web/controller/common/CaptchaController.java:113-114`）；第二个命令返回这道算术题的答案（验证码生成时就把答案写进 Redis，`CaptchaController.java:112`），形如 `"12"`（RedisUtils 用 Redisson 的 `JsonJacksonCodec`，字符串会带 JSON 引号，`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/RedisConfig.java:69`）。**注意字段名是 `captchaOnOff`，不是 `captchaEnabled`。**

3. **登录**：

   ```bash
   curl -s -X POST http://localhost:8080/login \
     -H "Content-Type: application/json" \
     -d '{"username":"zxcmAdmin","password":"123456","code":"<答案>","uuid":"<uuid>"}'
   ```

   预期：响应体 `code=200`，`data.token` 是一长串 JWT 风格字符串（`SysLoginController.java:86-89`）。不传 `tenantId` 时用默认租户 `00000000`（`SysLoginController.java:81-84`、`TenantProperties.java:30`）。如果返回「验证码错误」，说明过期或已被前一次请求消费——验证码是**一次性**的（`SysLoginService.java:200`）。

4. **在 Redis 里看见会话**：

   ```bash
   redis-cli --scan --pattern "satoken:login:*"
   redis-cli TTL "satoken:login:token:<token>"
   ```

   预期：能看到 `satoken:login:token:<token>`（token → loginId）以及对应的 token-session key；`TTL` 应为正数，上限对应 `timeout: 186400` 秒（`application.yml:105`）。这是 Sa-Token 默认 key 规则，本项目只是把存储实现换成了 `PlusSaTokenDao`。

5. **带着 token 调 `getInfo`**：

   ```bash
   curl -s http://localhost:8080/getInfo -H "token: Bearer <token>"
   ```

   预期：`data.user`、`data.roles`、`data.permissions` 三个字段（`SysLoginController.java:122-126`）。`getInfo` 会**重新查库**算权限；它和会话里的 `menuPermission` 只在登录那一刻同源，之后改了角色权限，这里会先变、会话要重新登录才变。

6. **登出后会话消失**：

   ```bash
   curl -s -X POST http://localhost:8080/logout -H "token: Bearer <token>"
   redis-cli EXISTS "satoken:login:token:<token>"
   ```

   预期：登出返回「退出成功」（`SysLoginController.java:100`）；再查 key 应返回 `0`。如果没有删除，检查 `StpUtil.logout()`（`:97`）是否执行到。

7. **断点位置**：`SysLoginService.java:84`（登录入口）→ `:106`（BCrypt 比对）→ `:152`（组装 LoginUser）→ `:154`（`loginByDevice`）→ `LoginHelper.java:80`（`StpUtil.login`）→ `PlusSaTokenDao.java:46`（真正写 Redis）。按这个顺序单步，就能把「一次登录」走完。

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：你们的登录流程是怎样的？**

`POST /login` 收账号密码（多租户还要选租户）→ 校验验证码（可开关）→ 查用户是否存在/停用 → `BCrypt` 校验密码 → 非管理员再过「3 个月未登录 / 临时密码过期」两道业务闸 → 组装 `LoginUser`（含权限码集合、角色列表、租户、部门）→ `LoginHelper.loginByDevice` 生成 token 并写会话 → 返回 token。前端拿到 token 后再调 `getInfo` 拿权限、`getRouters` 拿菜单。

**Q2：token 存在哪？为什么不用纯 JWT 无状态？**

token 由前端持有（Cookie，`zxcm-ui/src/utils/auth.js:3-7`），**服务端会话存 Redis**（`PlusSaTokenDao` 实现 `SaTokenDao`）。token 本身是 **JWT 风格**（`StpLogicJwtForStyle`，`SaTokenConfig.java:85`），loginId 等信息编码在 token 里；但 Style 模式**会话依然落 Redis**，完整 `LoginUser` 仍从会话读，因为要支持**踢人下线 / 强制注销**这些「主动让 token 失效」的能力——**纯无状态 JWT 签发后无法撤销**。这是「JWT 格式便利 + 会话可控」的折中。

**Q3：为什么会有「多级缓存」？ThreadLocal 怎么保证不串号？**

`LoginHelper` 用两级：一次请求内用 **ThreadLocal** 缓存 `LoginUser`，未命中才读 **Redis 的 TokenSession**（`LoginHelper.java:46/94-100`）。目的是**避免同一请求内反复反序列化 Redis**。**必须清理**：线程池会复用线程，不清就会把 A 的身份泄漏给 B 的请求——所以 `SaTokenConfig.java:75-77` 在请求结束的 `afterCompletion` 里 `clearCache()`。

**Q4：`loginId` 为什么不是用户 id？**

因为它要同时表达**「租户 + 用户体系 + 用户」三元组**（`LoginUser.java:135-137`，默认租户下拼成 `00000000:sys_user:10001`）。原因：loginId 带 `tenantId` 才能让会话按租户区分；`UserType` 枚举又预留了 `sys_user` / `app_user` / `wxmini_user` 三种体系（`UserType.java:33/38/42`）。**用三元组做 loginId，一套 Sa-Token 同时管多租户多体系。** 要如实补充：本仓库 `sys_user` 的 `USER_ID` 全局唯一，当前只落地了 `sys_user`，`app_user` 分支是空的。（默认租户 id 见 `ruoyi-base/ruoyi-tenant/src/main/java/com/ruoyi/tenant/TenantProperties.java:30`）

**Q5：登录接口怎么防暴力破解？**

两层：① 验证码（`SysLoginService.java:88-90`，可开关）；② **错误次数锁定**——密码错一次，Redis 计数 +1，达到上限锁定一段时间（`:97-119`），登录成功清零（`:151`）。key 是 `login_error:<租户>:<用户名>`（`Constants.java:116` 的前缀 + `SysLoginService.java:97` 的拼接；`Constants.java` 全路径见本章 §4.2）。

> **追问：错误次数 key 里为什么要带租户？** 因为不同租户可以有同名账号；不带租户会把 A 租户的输错次数算到 B 租户头上，锁错人（`SysLoginService.java:97`）。

**Q6：密码怎么存的？**

**BCrypt 哈希**（`SysLoginService.java:106` 的 `BCrypt.checkpw`）。BCrypt 自带 salt、计算强度可调，比 MD5/SHA 安全。**永远不存明文，也不用可逆加密。**

**Q7：登录成功后为什么还要调 getInfo？会话里不是已经有权限了吗？**

会话里的 `menuPermission` 是给**后端拦截器**用的；`getInfo` 返回的 `permissions` 是给**前端 `v-hasPermi` 指令**用的（存进 Vuex 隐藏按钮）。两者**同源**（都来自 `SysPermissionService`），但**用途不同、消费方不同**，所以各拿一份。

**Q8：本项目登录有什么"非标准"的地方？**

四处明显定制：① 登录前要**选租户**（`getTenants`）；② 多部门——部门是**数组**（`sys_user_dept` 扩展表）；③ 非管理员有**两道业务闸**（3 个月未登录、临时密码过期，`SysLoginService.java:121-148`）；④ 设备类型**写死为 PC**（`:154`），没做真正的多端区分（第 5 章展开）。

### 本章答辩卡（追问级）

**卡 1：`LoginUser` 是对象，Sa-Token 怎么把它塞进 Redis？给 `LoginUser` 加字段后旧会话会怎样？**

**10 秒答案**：Token-Session 里的数据最终由 `SaTokenDao.setObject` 持久化；本项目在 `PlusSaTokenDao.java:120-130` 用 `RedisUtils` 写对象（带 TTL）。旧会话里存的是**旧结构的序列化数据**，反序列化后不会自动多出新字段，所以加字段后要重新登录（或刷新会话）才拿得到。

**证据**：`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/satoken/dao/PlusSaTokenDao.java:119-130`、`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/helper/LoginHelper.java:87-89`。

**卡 2：`token-prefix: Bearer` 配了以后，前端传裸 token 行不行？**

**10 秒答案**：不行。Sa-Token 会按配置去掉请求头 `token` 的 `Bearer ` 前缀再匹配；前端 `request.js:32-34` 就是拼成 `'Bearer ' + getToken()` 再发。传裸 token 会被当成另一个 token，表现为「未登录」。

**证据**：`ruoyi-admin/src/main/resources/application.yml:118-119`、`zxcm-ui/src/utils/request.js:32-34`。

**卡 3：「3 个月未登录」这道闸为什么用 30 天近似，而不是日历年？**

**10 秒答案**：代码注释写得很直白——`TimeUnit.MILLISECONDS.toDays(...) / 30`，按「30 天一个月」简化（`SysLoginService.java:129-130`）。它不是精确日历月：2 月、31 天的月份边界会有几天偏差。面试时主动承认这是简化，比硬说「精确 3 个月」更可信；要精确应改用 `LocalDate.plusMonths(3)`。

**证据**：`ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/service/SysLoginService.java:126-134`。

## 七、选型对比：登录认证的几条路

### 7.1 鉴权框架：Sa-Token vs Spring Security vs Shiro

| 方案 | token 方案 | 学习成本 | 对本项目的适配 |
|---|---|---|---|
| Spring Security | 需自己配 OAuth2/JWT | **高**（FilterChain / UserDetailsService / Provider…） | 对「登录+菜单权限」过度设计 |
| Shiro | 自己配 | 中 | 与 Spring Boot 整合不如 Sa-Token 顺 |
| **Sa-Token（选用）** | **内置（含 JWT 风格、多端、踢人）** | **低**（`StpUtil.login()` 一行） | 开箱即用 |

**结论**：后台管理系统要的就是「登录 + 菜单权限 + 按钮权限 + 踢人下线」，Sa-Token 用最少代码全覆盖。**只有需要 OAuth2 授权服务器 / 微服务网关统一鉴权时，才轮到 Spring Security。**

### 7.2 会话存储：内存 Session vs Redis vs 纯 JWT

| 方案 | 多实例共享 | 可主动失效 | 适用 |
|---|---|---|---|
| 服务端内存 Session | ❌（要粘性会话） | ✅ | 单机小系统 |
| **Redis 会话（本项目）** | ✅ | ✅ | 集群、多端 |
| 纯 JWT 无状态 | ✅ | ❌ | 短生命周期、无踢人需求 |

**本项目选 Redis 会话**：既要集群共享，又要能踢人（第 5 章的多点登录、强制注销都依赖它）。

### 7.3 密码存储：BCrypt vs MD5 vs 可逆加密

| 方案 | 安全性 | 结论 |
|---|---|---|
| MD5 / SHA | ❌ 彩虹表可破、同密码哈希相同 | 淘汰 |
| **BCrypt（选用）** | ✅ 自带 salt、可调强度 | 标准做法 |
| 可逆加密（AES） | ❌ 能解出来就不是"哈希" | 绝不用于密码 |

## 本章小结 & 下一步

- **认证链路**：`/login` → `SysLoginService`（验证码→错误次数→查用户→BCrypt→业务闸→组装 LoginUser）→ `LoginHelper.loginByDevice` → `PlusSaTokenDao` 写 Redis → 返回 token。
- **`LoginUser` 是登录态的载体**，装的是「后面每次请求都要用、但每次查库太重」的东西：权限码集合、角色列表、租户、部门。
- **多级缓存**：ThreadLocal（一次请求）+ TokenSession（Redis）；**请求结束必须 `clearCache()`**。
- **`loginId` = 租户 + 用户类型 + 用户 id**，一套 Sa-Token 管多租户多体系。
- **`PlusSaTokenDao` 是存储层唯一把 Sa-Token 接进本框架的地方**，换存储只改它；拦截器与 JWT 风格由 `SaTokenConfig` 装配。

**下一章（第 3 章 · 鉴权：接口权限）**：登录之后，`@SaCheckPermission("xxx")` 是怎么被拦截器扫描、怎么和 `LoginUser` 里的权限码比对的——包括 `SaRouteInterceptor` 与 `SaAnnotationInterceptor` 两道拦截器的分工。
