# 第 3 章 · 鉴权：接口权限

> **认证回答「你是谁」，鉴权回答「你能不能调这个接口」。** 第 2 章登录时算好的权限码集合，在这一章终于派上用场——`@SaCheckPermission("conf:signingSubject:add")` 到底怎么被拦截、怎么和你的权限集合比对。
>
> **本章第一次讲透**：① 两道拦截器的分工（`SaRouteInterceptor` 管登录与白名单、`SaAnnotationInterceptor` 管注解权限）；② 权限码集合**从哪来**（`SysPermissionService` → `SaInterfaceImpl` 回调）；③ 管理员的 `*:*:*` 通配是怎么放行的；④ 没权限时为什么是 **403**、没登录为什么是 **401**。

---

## 一、这部分是做什么的？

### 零基础先补概念（30 秒）

> **① 拦截器（Interceptor）**：Spring MVC 在「请求到达 Controller 方法之前」插入的一道检查代码。可以注册多道，按注册顺序执行。本项目的两道拦截器在 `ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/SaTokenConfig.java:55/79`。
>
> **② 注解（Annotation）**：写在类/方法上、以 `@` 开头的标签，运行时可以用反射读出来。本项目用 `@SaCheckPermission("conf:signingSubject:add")` 贴在方法上，表示「调这个方法需要这串权限码」（真实例子：`zxcm-contract/src/main/java/com/ruoyi/conf/controller/TSigningSubjectController.java:144`）。
>
> **③ 权限码与通配符 `*`**：权限码是普通字符串；Sa-Token 比对时支持 `*` 通配。管理员登录时只放一个 `*:*:*`（`SysPermissionService.java:62`），就能匹配任意三段式权限码。
>
> **④ 401 / 403**：401 表示「没登录或 token 失效」，403 表示「登录了但没有这个权限」。**注意**：本项目把这两个数字放在**响应体的 `code` 字段**里，HTTP 状态码仍是 200（原因见 §4.5）；前端读的是 `res.data.code`（`zxcm-ui/src/utils/request.js:73/80`）。

### 1.1 鉴权与认证的分工

| | 认证（第 2 章） | 鉴权（本章） |
|---|---|---|
| 问题 | 你是谁？ | 你能不能干这件事？ |
| 时机 | 登录时 | **每个请求** |
| 失败返回 | 响应体 `code=401`（认证失败，去登录） | 响应体 `code=403`（没有权限，找管理员授权） |
| 载体 | token + 会话 | token 里的权限码集合 |

**顺序**：先认证、后鉴权。没登录 → 响应体 `code=401`；登录了但没这个权限 → 响应体 `code=403`。**再次强调：不是 HTTP 401/403**，`GlobalExceptionHandler` 返回的是 `R.fail(code, msg)`，只改响应体，不改 HTTP 状态（§4.5 有验证方法）。

### 1.2 权限字符串长什么样

本项目权限码是**三段式**：`模块:资源:操作`，例如：

```
conf:signingSubject:add      新增签约主体
conf:signingSubject:query    查询签约主体
conf:signingSubject:remove   删除签约主体
contract:subjectAll:search   检索全部签约主体（第 1 章 §2.3 那个"半公开"接口）
```

- **第 1 段**：模块（`conf` 配置域 / `contract` 合同域）；
- **第 2 段**：资源（`signingSubject` 签约主体）；
- **第 3 段**：操作（`add` / `query` / `remove` / `edit` / `export`…）。

**这套命名约定不是强制的，但行业高度统一**——好处是一眼看出「哪个模块、什么东西、什么操作」，便于按前缀批量授权（后面会看到 `*:*:*` 和前缀匹配）。

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么是「两道拦截器」而不是一道？

看 `SaTokenConfig.java:52-80`，注册了两道拦截器：

```java
// 第一道：路由拦截器 —— 管"登录了吗"
registry.addInterceptor(new SaRouteInterceptor((request, response, handler) -> {
    SaRouter.match("/**")                                  // 拦所有路径
        .notMatch(securityProperties.getExcludes())        // 放行白名单
        .check(() -> {
            Long userId = LoginHelper.getUserId();          // 拿不到就抛未登录异常
        });
}){ ... }).addPathPatterns("/**");

// 第二道：注解拦截器 —— 管"有这个权限吗"
registry.addInterceptor(new SaAnnotationInterceptor()).addPathPatterns("/**");
```

**为什么要分两道？** 因为「登录校验」和「权限校验」是**两个不同粒度**的检查：

| 拦截器 | 粒度 | 检查什么 | 适用范围 |
|---|---|---|---|
| `SaRouteInterceptor` | **路径级** | 这个路径需不需要登录？白名单直放 | 所有请求（除了白名单） |
| `SaAnnotationInterceptor` | **方法级** | 这个方法上的 `@SaCheckPermission` 满不满足 | **只对有注解的方法生效** |

**路由拦截器是"大门"**——所有请求都要过，但它只判断「你有没有登录」。**注解拦截器是"房间里的一道道门禁"**——只有标了 `@SaCheckPermission` 的方法才有门禁，没标的方法（比如查字典、查自己的信息）就自由通行。

**这样设计的价值**：**绝大多数接口只需要"登录"，只有敏感接口才需要"额外权限"**。如果只用一道注解拦截器，那每个接口都得标注解，累且易漏；只用一道路由拦截器，又做不了方法级权限。**两层叠加，各司其职。**

### 2.2 为什么权限判定要「回调」`StpInterface`？

Sa-Token 是个**通用框架**——它不知道你的权限存在哪（数据库？配置？LDAP？）。所以它设计了一个 **SPI 接口 `StpInterface`**：你实现它，告诉 Sa-Token「这个用户有哪些权限」。

本项目实现类是 `SaInterfaceImpl`（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/satoken/service/SaInterfaceImpl.java:26`）：

```java
@Component
public class SaInterfaceImpl implements StpInterface {
    @Override
    public List<String> getPermissionList(Object loginId, String loginType) {
        LoginUser loginUser = LoginHelper.getLoginUser();
        UserType userType = UserType.getUserType(loginUser.getUserType());
        if (userType == UserType.SYS_USER) {
            return new ArrayList<>(loginUser.getMenuPermission());   // ★ 直接返回登录态里的权限码集合
        } else if (userType == UserType.APP_USER) {
            // app端权限返回 自行根据业务编写
        }
        return new ArrayList<>();
    }
    @Override
    public List<String> getRoleList(Object loginId, String loginType) { ... getRolePermission() ... }
}
```

**关键点**：`getPermissionList` **不查数据库**，而是直接从 `LoginUser`（登录态）里拿 `menuPermission`（第 2 章登录时算好的）。**这就是"鉴权不查库"的秘密**——权限集合在登录时算好缓存在会话里，每次鉴权只是内存比对。

**为什么用 SPI 而不是把权限判断写进拦截器？** 因为**框架与数据源解耦**：Sa-Token 只负责「怎么比对、怎么抛异常」，**「权限从哪来」由使用方决定**。你换一套权限存储，只改 `SaInterfaceImpl`，框架代码不动。

### 2.3 为什么管理员放行用 `*:*:*`？

看 `SysPermissionService.java:58-66`：

```java
public Set<String> getMenuPermission(SysUser user) {
    Set<String> perms = new HashSet<String>();
    if (user.isAdmin()) {
        perms.add("*:*:*");                              // ★ 管理员：一个通配符搞定
    } else {
        perms.addAll(menuService.selectMenuPermsByUserId(user.getUserId(), user.getTenantId()));
    }
    return perms;
}
```

**管理员不逐个查权限，直接塞一个 `*:*:*`**。Sa-Token 的权限比对**支持通配符**——`*:*:*` 匹配任意 `模块:资源:操作`，所以管理员天然拥有所有权限。

同理，角色那边管理员塞 `"admin"`（`SysPermissionService.java:44-45`），配合 `@SaCheckRole("admin")` 用。

**为什么这么设计？** 有两个好处：

1. **省一次查库**：管理员不用去查 `sys_role_menu`（管理员本来也不走角色）。
2. **安全性**：管理员的权限**不依赖数据库里勾了哪些菜单**——即使菜单表被误删，管理员依然能进系统去修，**不会把自己锁在门外**。这是**「防呆」设计**。

### 2.4 为什么「前端隐藏按钮」不算安全措施？

第 1 章提过前端 `v-hasPermi` 只是「把没权限的按钮从页面上删除」，**是体验优化，不是安全边界**——因为用户完全可以：

- 打开浏览器开发者工具，手动调 `POST /conf/signingSubject`；
- 或者直接用 Postman 打接口。

**所以每个接口都必须在后端标 `@SaCheckPermission`。** 前端的隐藏只防「误点」，后端的注解才防「越权」。**这是面试高频题，一定要答得出。**

## 四、功能具体怎么实现（带着你读懂）

### 4.1 拦截器注册与执行

`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/SaTokenConfig.java:44`：

```java
@RequiredArgsConstructor
@Slf4j
@Configuration
public class SaTokenConfig implements WebMvcConfigurer {          // :44

    private final SecurityProperties securityProperties;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {   // :52
        // ① 路由拦截器：登录校验 + 白名单
        registry.addInterceptor(new SaRouteInterceptor((request, response, handler) -> {
            SaRouter.match("/**")                                  // :59 拦所有
                .notMatch(securityProperties.getExcludes())        // :61 放行白名单
                .check(() -> {
                    Long userId = LoginHelper.getUserId();         // :63 拿不到会抛 NotLoginException
                });
        }) {
            @Override
            public void afterCompletion(...) {                     // :75
                LoginHelper.clearCache();                          // ★ 清 ThreadLocal（第 2 章 §4.4）
            }
        }).addPathPatterns("/**");                                  // :78

        // ② 注解拦截器：方法级权限校验
        registry.addInterceptor(new SaAnnotationInterceptor())      // :79
                .addPathPatterns("/**");
    }

    @Bean
    public StpLogic getStpLogicJwt() {                              // :82
        return new StpLogicJwtForStyle();                           // JWT 风格（第 2 章 §2.3）
    }
}
```

#### 逐行读：拦截器注册的 8 个关键点

| 行号 | 代码 | 这一行在干什么、为什么这么写 |
|---|---|---|
| `:52` | `public void addInterceptors(InterceptorRegistry registry)` | Spring MVC 启动时会调用这个方法，我们把拦截器注册进去；`registry` 就是「拦截器登记表」。 |
| `:55` | `registry.addInterceptor(new SaRouteInterceptor((request, response, handler) -> {` | 注册**第一道**：路由拦截器。后面那一大段 lambda 是「每个请求进来时要执行的检查逻辑」。 |
| `:59` | `.match("/**")` | 匹配所有路径——默认全都要检查。 |
| `:61` | `.notMatch(securityProperties.getExcludes())` | 从「全部」里挖掉白名单。白名单从 `application.yml` 的 `security.excludes` 绑定到 `SecurityProperties`（`:27-28`）。 |
| `:62-63` | `.check(() -> { Long userId = LoginHelper.getUserId(); ... })` | 真正的登录检查：`getUserId()` 会读 token 会话；拿不到有效登录态时，Sa-Token 抛 `NotLoginException`。**这就是 401 的来源**。 |
| `:72-78` | `new SaRouteInterceptor(...) { afterCompletion(...) { LoginHelper.clearCache(); } }` | 用匿名子类重写 `afterCompletion`：请求结束（无论成功还是抛异常）都清掉 ThreadLocal，防止线程复用串号（第 2 章 §4.4）。`.addPathPatterns("/**")` 让这道拦截器覆盖所有路径。 |
| `:79` | `registry.addInterceptor(new SaAnnotationInterceptor()).addPathPatterns("/**");` | 注册**第二道**：注解拦截器。它只对贴了 `@SaCheckPermission` / `@SaCheckRole` 的方法做权限比对，没注解的方法直接放行。 |
| `:82-86` | `@Bean public StpLogic getStpLogicJwt()` | 把 Sa-Token 默认的随机字符串 token 换成 JWT 风格（`StpLogicJwtForStyle`），让 token 自身携带更多信息（第 2 章 §2.3）。 |

**执行顺序**：请求进来 → **路由拦截器**（过不了就响应体 401）→ **注解拦截器**（过不了就响应体 403）→ Controller 方法。注册顺序就是执行顺序，所以第一道必须在第二道前面。

> 📌 **`clearCache()` 放在 `SaRouteInterceptor` 的 `afterCompletion` 里**（`:75-77`）——这保证了**任何过了第一道拦截器的请求，结束时都会清 ThreadLocal**。为什么放这里而不是别处？因为这里是「所有请求的必经之路」，放这里最不容易漏。

### 4.2 权限码从哪来：`SysPermissionService` → LoginUser → `SaInterfaceImpl`

**第一步：登录时算权限集合**（`ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/service/SysPermissionService.java:30`）

```java
public Set<String> getMenuPermission(SysUser user) {              // :58
    Set<String> perms = new HashSet<String>();
    if (user.isAdmin()) {
        perms.add("*:*:*");                                        // :62 管理员通配
    } else {
        perms.addAll(menuService.selectMenuPermsByUserId(          // :64 查 sys_role_menu → sys_menu.perms
            user.getUserId(), user.getTenantId()));
    }
    return perms;
}
```

**第二步：塞进 `LoginUser`**——第 2 章 `buildLoginUser` 里 `loginUser.setMenuPermission(permissionService.getMenuPermission(user))`（`SysLoginService.java:243`）。

**第三步：鉴权时回调 `SaInterfaceImpl.getPermissionList()` 取出来**（`SaInterfaceImpl.java:29-38`）。

**查权限的 SQL 逻辑**（`selectMenuPermsByUserId`，完整 SQL 在 `ruoyi-base/ruoyi-system/src/main/resources/mapper/system/SysMenuMapper.xml:288-300`）：以 `sys_menu` 为主表，依次左连 `sys_role_menu`、`sys_user_role`、`sys_role`，只保留 `m.status='0'`（菜单正常）且 `r.status='0'`（角色正常）的记录，最后 `select distinct m.perms`。

> ⚠️ **它并没有按 `menuType` 过滤**。`sys_menu` 里的 `M/C/F` 都会被查出来；`M` 目录一般没配 `perms`，返回 `NULL`。真正的清理在 Java 层：`ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysMenuServiceImpl.java:101-109` 会丢掉空值，并把一行里用逗号分隔的多个权限码拆开后再放进 `Set`。
>
> ⚠️ **注意角色也要 `status='0'`**（`SysMenuMapper.xml:298`）：被停用的角色，其权限不生效。这是「角色停用」的实际含义。

### 4.3 注解怎么写

**单权限**（最常用）：
```java
@SaCheckPermission("conf:signingSubject:add")
@PostMapping()
public R<Void> add(@Validated(AddGroup.class) @RequestBody TSigningSubjectBo bo) { ... }
```

**多权限，满足其一（OR）**：
```java
@SaCheckPermission(value = {"conf:signingSubject:add", "conf:signingSubject:edit"}, mode = SaMode.OR)
```

**多权限，必须全部（AND）**：
```java
@SaCheckPermission(value = {"contract:audit:approve", "contract:audit:seal"}, mode = SaMode.AND)
```

**角色校验**：
```java
@SaCheckRole("admin")
```

**只要求登录（任何登录用户可调）**：不标注解即可——因为路由拦截器已经保证「登录才能进」。**但如果这个接口在**（不被路由拦截器拦的）**白名单里**，又想要求登录，就得显式标 `@SaCheckLogin`。

**类 vs 方法**：`@SaCheckPermission` 可以标在**类**上（该类所有方法都要这个权限）或**方法**上（只这个接口要）。**一般标方法**，因为粒度更细。

### 4.4 白名单：哪些接口不用登录

白名单来自 `ruoyi-admin/src/main/resources/application.yml:154-191` 的 `security.excludes`（下面是完整列表，不是节选）：

```yaml
security:
  excludes:
    - /login                              # 登录
    - /logout                             # 登出（未登录也允许调）
    - /register                           # 注册
    - /captchaImage                       # 验证码
    - /getTenants                         # 登录前选租户
    - /system/dict/data/type/*            # 字典数据
    - /common/config                      # 公共配置
    - /common/temp/resource               # 文件对比
    - /profile/**                         # 本地文件预览
    - /*.html                             # 静态页面
    - /**/*.html
    - /**/*.css
    - /**/*.js
    - /doc.html                           # Knife4j 文档
    - /swagger-resources/**
    - /webjars/**
    - /*/api-docs
    - /druid/**                           # Druid 监控
    - /wpsCallback/**                     # WPS 回调
    - /onlyofficeCallback/**              # OnlyOffice 回调
    - /openApi/**                         # 开放接口
    - /qywx/login/**                      # 企业微信
    - /qywx/config
    - /conf/file/qywx/download/**
    - /wps-v3/**
    - /syncData/oauth/**                  # 钉钉 OAuth 回调
    - /websocket/message/**               # WebSocket
```

绑定到 `SecurityProperties`（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/properties/SecurityProperties.java:27-28`，`@ConfigurationProperties(prefix = "security")`），在 `SaTokenConfig.java:61` 的 `notMatch` 里使用。

**白名单里都是什么？** 四类：

| 类型 | 例子 | 为什么放行 |
|---|---|---|
| 登录相关 | `/login` `/logout` `/captchaImage` `/getTenants` | 还没登录，怎么可能先登录再调它们 |
| 静态资源与文档 | `/*.html` `/profile/**` `/doc.html` `/swagger-resources/**` `/druid/**` | 页面、图片、接口文档本身不需要业务权限 |
| 公共数据 | `/system/dict/data/type/*` `/common/config` | 登录页、下拉框就要用 |
| 第三方回调 / 开放接口 | `/wpsCallback/**` `/onlyofficeCallback/**` `/syncData/oauth/**` `/qywx/login/**` `/websocket/message/**` | 调用方是外部系统，通常带不了本系统的 token；具体改用签名、令牌或来源校验，**要看各回调自己的实现** |

> ⚠️ **白名单是安全敏感点**。`/common/temp/resource`（`application.yml:165`，注释写"文件对比"）这种**看起来像文件访问的路径被放行**，要小心——加白名单前一定问「这个接口真的不需要登录吗」。第三方回调类路径更危险：放行给公网后，必须确认回调本身有签名/令牌校验，否则等于把接口裸奔在公网上。

### 4.5 没权限时返回什么：`GlobalExceptionHandler`

Sa-Token 校验失败会抛异常，由全局异常处理器接住（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/web/exception/GlobalExceptionHandler.java:53`）：

| 异常 | 触发的场景 | 响应体 `code` | 返回文案 | 位置 |
|---|---|---|---|---|
| `NotLoginException` | 没登录 / token 失效 | **401** | 认证失败，无法访问系统资源 | `GlobalExceptionHandler.java:98-103` |
| `NotPermissionException` | 缺权限码 | **403** | 没有访问权限，请联系管理员授权 | `GlobalExceptionHandler.java:58-63` |
| `NotRoleException` | 缺角色 | **403** | 没有访问权限，请联系管理员授权 | `GlobalExceptionHandler.java:88-93` |

> ⚠️ **这里是「响应体 code」，不是 HTTP 状态码。** `R.fail(code, msg)` 只是把数字塞进 JSON 的 `code` 字段（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/R.java:85-95`），方法上没有 `@ResponseStatus`，也没有返回 `ResponseEntity`，所以 **HTTP 状态仍然是 200**。前端 axios 拦截器读的也是 `res.data.code`（`zxcm-ui/src/utils/request.js:73`），不是 `res.status`。面试时说「HTTP 401/403」会被追问穿帮，说「业务码 401/403」才准确。

```java
@ExceptionHandler(NotPermissionException.class)
public R<Void> handleNotPermissionException(NotPermissionException e, HttpServletRequest request) {
    log.error("请求地址'{}',权限码校验失败'{}'", request.getRequestURI(), e.getMessage());
    return R.fail(HttpStatus.HTTP_FORBIDDEN, "没有访问权限，请联系管理员授权");   // 403
}
```

**前端读到响应体 `code=401` 会跳登录页**（因为 token 没了），**读到 `code=403` 只弹个提示**（权限不够，重登也没用）。**这个区分很关键**——前端的 axios 拦截器就是靠 `res.data.code` 分流的（`request.js:80/104`，前端卷有专章）。

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：你们的权限校验是怎么做的？**

两层拦截器。**路由拦截器** `SaRouteInterceptor`（`SaTokenConfig.java:55`）做路径级登录校验并放行白名单；**注解拦截器** `SaAnnotationInterceptor`（`:79`）扫描方法上的 `@SaCheckPermission` 做方法级权限校验。权限比对时会回调 `StpInterface` 实现（`SaInterfaceImpl`），它返回登录态里的权限码集合。

**Q2：权限码集合是从数据库查的吗？每次都查？**

**不查库**——**登录时算好存进会话**（`LoginUser.menuPermission`，`SysLoginService.java:243`），鉴权时直接从会话取（`SaInterfaceImpl.java:33`）。所以鉴权是**内存比对**。代价是：**改了角色权限要重新登录才生效**。

**Q3：管理员为什么不用配权限？**

因为 `SysPermissionService.getMenuPermission`（`:62`）给管理员直接塞 **`*:*:*`**，Sa-Token 通配符匹配一切。好处是**省一次查库 + 防呆**（管理员权限不依赖数据库，不会把自己锁在门外）。

**Q4：`@SaCheckPermission` 支持"或"和"与"吗？**

支持。`@SaCheckPermission(value = {...}, mode = SaMode.OR)` 满足其一即可；`mode = SaMode.AND` 必须全满足。默认是 AND（多个权限码时必须都有）。

**Q5：前端已经把按钮藏了，后端还要校验吗？**

**必须要。** 前端 `v-hasPermi` 只是「把按钮从 DOM 删掉」，是**体验优化、不是安全边界**——用户可以用 Postman / 浏览器控制台直接调接口。**真正的拦截必须在后端**，每个接口都要标 `@SaCheckPermission`。

**Q6：没登录和没权限，返回有什么区别？**

**响应体 `code` 401（认证失败）vs 403（权限不足）**。`NotLoginException` → body `code=401`（`GlobalExceptionHandler.java:98-103`），前端读到后跳登录页；`NotPermissionException` / `NotRoleException` → body `code=403`（`:58-63` / `:88-93`），前端只弹提示。**注意 HTTP 状态码本身仍是 200**；区分 body 里的 code 才能让前端做正确的降级处理。

**Q7：白名单是怎么配的？有什么风险？**

白名单在 `ruoyi-admin/src/main/resources/application.yml:154-191` 的 `security.excludes`，绑定到 `SecurityProperties`（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/properties/SecurityProperties.java:27-28`），在 `SaTokenConfig.java:61` 的 `notMatch` 里放行。**风险是"白名单加多了"**——比如把某个本该鉴权的接口误加进去，就成了安全漏洞。所以**加白名单前一定问「这个接口真的不需要登录吗」**。

> **追问：白名单里的 `*` 和 `**` 有什么区别？** `*` 只匹配一层路径段，`**` 匹配多层。例如 `/*.html` 只放行根路径下的 html，`/**/*.html` 才放行任意层级；写错层级会「以为放行了其实没放」，或反过来放行了不该放的路径（配置位置 `application.yml:169-172`）。

**Q8：把权限判断写成 SPI（`StpInterface`）有什么好处？**

**框架与数据源解耦**。Sa-Token 只负责「怎么比对、怎么抛异常」，**「权限从哪来」交给使用方**（本项目从 `LoginUser` 取）。换权限存储只改 `SaInterfaceImpl`，框架代码不动。

### 本章答辩卡（追问级）

**卡 1：你们说的「返回 401/403」，到底是 HTTP 状态码还是响应体字段？**

**10 秒答案**：是**响应体里的 `code` 字段**，HTTP 状态码仍是 200。全局异常处理器只是 `return R.fail(401/403, msg)`，没有改 HTTP 状态；前端 axios 读的也是 `res.data.code`。如果面试官追问「为什么不用 HTTP 状态」，可以答：这是这套脚手架的统一返回风格，所有业务错误都走 `R` 包装，前端只需在一处判断。

**证据**：`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/web/exception/GlobalExceptionHandler.java:58-63`、`:98-103`；`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/R.java:85-95`；`zxcm-ui/src/utils/request.js:73`。

**卡 2：`sys_menu.perms` 里一行写了多个逗号分隔的权限码，会怎样？**

**10 秒答案**：SQL 查回来的是一整串（如 `a,b`），**Sa-Token 不会自动拆**。本项目在 Java 层用 `perm.trim().split(",")` 拆开再放进 `Set`（`SysMenuServiceImpl.java:104-107`），所以一行多码是支持的。如果你自己写代码直接从 Mapper 取，别忘了这一步，否则集合里只有 `"a,b"` 这个整体，鉴权永远匹配不上。

**证据**：`ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysMenuServiceImpl.java:101-109`、`ruoyi-base/ruoyi-system/src/main/resources/mapper/system/SysMenuMapper.xml:288-300`。

**卡 3：`clearCache()` 为什么放在路由拦截器的 `afterCompletion`，而不是 Controller 的 `finally`？**

**10 秒答案**：因为路由拦截器是「所有请求的必经之路」，而 Controller 可能有几十个，写在每个 `finally` 里既重复又容易漏。`afterCompletion` 在请求处理完（包括 Controller 抛异常）后执行，能保证**凡是进过第一道拦截器的请求**都会清 ThreadLocal。前提是 `preHandle` 已通过——这也是为什么把它放在第一道路由拦截器上最稳。

**证据**：`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/SaTokenConfig.java:72-78`；`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/helper/LoginHelper.java:110-115`。

## 七、选型对比：鉴权的几种写法

### 7.1 权限校验方式

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 手动判断 | 在方法里 `if (!StpUtil.hasPermission(...)) throw ...` | 灵活 | 每个方法都写、易漏、业务被污染 |
| **注解式（本项目）** | `@SaCheckPermission` + 拦截器 | **声明清晰、业务零侵入、一处注解** | 动态规则不灵活 |
| 网关统一鉴权 | 在网关层校验 | 微服务友好 | 本系统单体，杀鸡用牛刀 |

**结论**：单体后台系统，注解式是最优解。

### 7.2 权限粒度：路径级 vs 方法级

| 粒度 | 优点 | 缺点 |
|---|---|---|
| 路径级（路由拦截器） | 统一、不漏 | 太粗，做不了方法级权限 |
| **方法级（注解），叠加路径级（本项目）** | 粗做登录、细做权限 | 两道拦截器要理解清楚 |

### 7.3 权限存储：代码硬编码 vs 数据库

见第 1 章 §7.2。本项目的选择是「**接口要求**写代码、**授权关系**存数据库」，兼顾可追溯与可运维。
