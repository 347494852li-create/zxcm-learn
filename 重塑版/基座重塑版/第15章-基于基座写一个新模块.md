# 第 15 章 · 基于基座写一个新模块

> **本章是「综合实战」**：前面 14 章把基座的每一块拆开讲透了，**这一章把它们合起来用**——假设你要在这个基座上**从零加一个「印章管理」模块**，完整走一遍：**设计表 → 写 SQL（建表 + 菜单权限）→ 建 Maven 模块 → Entity/BO/VO → Mapper（挂数据权限）→ Service → Controller（挂权限码 + 日志 + 防重）→ 前端页面 → 接菜单**。

## 一、这部分是做什么的？

### 1.1 一句话：什么叫「在基座上写一个模块」

**你不再从零搭框架**，而是**「填空」**——基座（`ruoyi-base` + `ruoyi-admin`）已经把「登录、鉴权、日志、缓存、异常、分页、导入导出、数据权限」全备好了，**你要做的只是**：

> 定义「我的业务对象长什么样」（表 + Entity），**然后把它挂到基座预留好的「接入点」上**。

### 1.1.1 零基础先补概念

| 概念 | 大白话 | 在本项目里长什么样 |
|---|---|---|
| **Maven 多模块** | 一个父工程下面挂很多"子工程"，每个子工程能单独编译、单独被依赖。根 `pom.xml` 的 `<modules>` 就是"子工程名单" | 根 `pom.xml:323-336`；业务模块如 `zxcm-contract` 在 `:331` |
| **Entity / BO / VO** | Entity 对着数据库表；BO 接前端传来的入参（带校验）；VO 是返回给前端的出参（带展示/Excel 注解） | `ConfBillRule extends BaseEntity`（`zxcm-contract/src/main/java/com/ruoyi/conf/domain/ConfBillRule.java:35`）；BO 在 `zxcm-contract/src/main/java/com/ruoyi/conf/domain/bo/ConfBillRuleBo.java:41`；VO 在 `zxcm-contract/src/main/java/com/ruoyi/conf/domain/vo/ConfBillRuleVo.java:37` |
| **依赖方向** | "业务依赖基座"可以，"基座依赖业务"不行。否则基座就没法单独复用了 | 业务模块 pom 依赖 `ruoyi-framework`/`ruoyi-system`/`ruoyi-common`，反向没有 |
| **权限码** | 一个字符串，比如 `seal:info:add`。后端用它拦接口，前端用它控制按钮显示 | 存在 `sys_menu.PERMS`，后端 `@SaCheckPermission("...")`，前端 `v-hasPermi` |

**一句话串起来**：新建一个 Maven 模块 → 写 Entity/BO/VO 三个类 → Controller 上挂权限码 → 让基座的拦截器、日志、数据权限自动接管。

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么是「Entity / BO / VO」三层，而不是一个实体类用到底？

这是**本项目最典型的代码组织方式**（第 0 章引的 `zxcm-contract` 全部模块都这么写）。三个类各管一件事：

| 类 | 面向谁 | 职责 | 例子 |
|---|---|---|---|
| **Entity**（`SealInfo`） | **数据库** | 和表一一对应，`@TableName` 标表名 | 含 `delFlag`、`createBy` |
| **BO**（`SealInfoBo`） | **前端→后端**（入参） | 带**校验注解**（`@NotBlank` + 分组） | 新增/修改用不同校验 |
| **VO**（`SealInfoVo`） | **后端→前端**（出参） | 带**展示注解**（`@ExcelProperty`）、可含计算字段 | 可带上「保管人姓名」 |

**为什么不合并**？因为**三者「变化的方向」不一样**：

- **表加了一列** → 只动 Entity。
- **前端要多传一个字段做校验** → 只动 BO。
- **页面要多显示一个翻译后的字段** → 只动 VO。

**合并成一个类的代价**：你会被迫在「数据库字段」上挂「前端校验注解」和「Excel 导出注解」，同时把「不能暴露给前端的字段」（如 `delFlag`、`tenantId`）也暴露出去。**三个类是为了「让每类变化只影响一处」**——这正是第 0 章 §4.2 那条「依赖方向」思想在**类级别**的体现。

### 2.2 为什么要继承 `BaseEntity` / `BaseMapperPlus`，而不是自己写？

| 基类 | 白得的能力 | 源码 |
|---|---|---|
| **`BaseEntity`** | `createBy`/`createTime`/`updateBy`/`updateTime` **自动填充**、`params`（给动态查询用的扩展参数）、`searchValue` | `ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/BaseEntity.java:33`（`createBy :49`、`createTime :56`、`updateBy :63`、`updateTime :70`） |
| **`BaseMapperPlus<M,T,V>`** | **`selectVoById` / `selectVoList` / `selectVoPage`**——直接返回 VO，省掉手写「Entity→VO」的转换 | `ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/mapper/BaseMapperPlus.java:49`（`:150`/`:210`/`:225`） |

**关键**：`BaseEntity` 里的 `@TableField(fill = FieldFill.INSERT)`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/BaseEntity.java:48`）意味着**你永远不用手写 `setCreateBy(...)`**——基座的 `CreateAndUpdateMetaObjectHandler`（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/handler/CreateAndUpdateMetaObjectHandler.java:36`，第 7 章）会在 insert 前自动帮你填上当前登录人。**你只要继承，就白得这一点。**

### 2.3 为什么「先建表、再写代码」？

因为**表结构是「地基」，代码是「地基上的房子」**：

- 表的**字段类型**决定了 Entity 的类型（`bigint`→`Long`、`datetime`→`Date`）；
- 表的**唯一约束**决定了你在 `validEntityBeforeSave` 里该查什么（见 §4.9）；
- 表的**业务含义**决定了数据权限该挂在哪一列（§4.7：印章要按「保管人」做数据权限）。

**反过来先写代码、再改表**，就会陷入「Entity 改了、SQL 忘了改、上线才发现列不存在」的经典事故。**所以顺序一定是：想清楚表 → 写 SQL → 写代码。**

### 2.4 为什么新模块要单独建 Maven 模块？

**不是必须**，但**推荐**。理由和「基座拆 common/framework/system」完全一样（第 0 章 §2.3）：**让「一个模块」=「一个可独立编译、可独立摘除的单元」**。

- 单独建模块 → 想砍掉印章功能，只需从根 pom 去掉一行 `<module>zxcm-seal</module>`，**不碰任何已有代码**。
- 塞进 `zxcm-contract` 里 → 砍的时候要在一堆文件里找。

**代价**：多一个 `pom.xml`、根 pom 多一行。**对于「一个完整的业务域」（印章、档案、公告各算一个），这个代价完全值得。**

### 4.1 第一步：想清楚表（学习者视角）

> **这里用「学习者视角」讲**（参见记忆里「讲表和代码用学习者视角」的偏好）：**先问「这张表谁设计的、为什么需要、我什么时候真正用到」，再谈字段。**

**印章管理是干什么的？**
在合同系统里，**签合同常常要盖章**。一个规范的企业，印章不是谁都能碰的——**「合同专用章」由法务保管、「公章」由行政保管、「财务章」由财务保管**。所以系统要**登记「我们公司有哪些章、每种章归谁管、现在能不能用」**，以后「用印申请」流程就能查「这个章该找谁、有没有停用」。

**谁设计、为什么需要**（3+1 种身份视角）：

| 视角 | 关心什么 | 对应到表设计 |
|---|---|---|
| **业务方（行政/法务）** | 「有哪些章、归谁管」 | `seal_name`、`seal_type`、`keeper_id` |
| **开发（你）** | 「谁建的、什么时候改的」 | 交给 `BaseEntity` 自动填充，**不用自己设计** |
| **系统/运维** | 「删了能不能恢复、多租户怎么隔离」 | `del_flag`（逻辑删除）、`tenant_id`（多租户） |
| **+1 权限管理员** | 「谁能看到哪些章」 | `keeper_id` + 数据权限（§4.7） |

**「我什么时候真正用到」**：**在做「用印申请」时，下拉框列出「当前生效的章」**——所以要有 `status`（是否停用）；**在「我的印章」页面**，只能看到自己保管的——所以 `keeper_id` 要挂数据权限。

**表设计（终稿）**：

```sql
CREATE TABLE `zxcm_seal_info` (
  `seal_id`        bigint       NOT NULL                COMMENT '印章ID',
  `seal_name`      varchar(100) NOT NULL                COMMENT '印章名称',
  `seal_type`      char(1)      NOT NULL DEFAULT '0'    COMMENT '印章类型（字典 seal_type）',
  `keeper_id`      bigint       NULL                    COMMENT '保管人用户ID',
  `keeper_dept_id` bigint       NULL                    COMMENT '保管部门ID',
  `status`         char(1)      NOT NULL DEFAULT '0'    COMMENT '状态（0正常 1停用）',
  `del_flag`       char(1)      NOT NULL DEFAULT '0'    COMMENT '删除标志（0存在 2删除）',
  `tenant_id`      varchar(20)  NULL                    COMMENT '租户编号',
  -- ↓ 以下 4 列是 BaseEntity 的字段，表里必须有，代码里不用重复声明
  `create_by`      varchar(64)  NULL                    COMMENT '创建者',
  `create_time`    datetime     NULL                    COMMENT '创建时间',
  `update_by`      varchar(64)  NULL                    COMMENT '更新者',
  `update_time`    datetime     NULL                    COMMENT '更新时间',
  PRIMARY KEY (`seal_id`) USING BTREE,
  KEY `idx_keeper` (`keeper_id`)                        COMMENT '数据权限按保管人过滤，加索引'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb3 COMMENT='印章信息表';
```

**三处设计细节值得讲**（面试能加分）：

1. **`create_by`/`create_time`/`update_by`/`update_time` 四列必须有**——因为 Entity 继承 `BaseEntity`（§4.4），MyBatis-Plus 会自动读写这四列。**建表漏了会报「Unknown column」。**
2. **`del_flag` + `@TableLogic`**——本项目用**逻辑删除**（第 7 章），删印章**不会真删行**，只是把 `del_flag` 置 `2`。好处是**历史数据可追溯、外键不会断**。
3. **`keeper_id` 上建索引**——因为它要参与数据权限的 `WHERE` 改写（§4.7 会把它变成 `AND keeper_id IN (...)`），**过滤列必须建索引**。

### 4.2 第二步：SQL（建表 + 菜单权限 + 字典）

#### ① 建表

把 §4.1 的 `CREATE TABLE` 存成增量脚本（**不要改 `script/sql/zxcm_init.sql` 原始文件**，另建 `script/sql/zxcm_seal.sql`——**该文件当前不存在，属于待新建**）。

#### ② 菜单与权限码（这是「接入点 2」）

**权限码怎么落到系统里**？本项目是 **RBAC**（第 1 章）：`sys_user` —(user_id)— `sys_role` —(role_id)— `sys_role_menu` —(menu_id)— `sys_menu`。**菜单表 `sys_menu` 同时管两件事**：**显示层级**（`MENU_TYPE='M'/'C'`）和**权限码**（`PERMS` 列 + `MENU_TYPE='F'` 按钮）。

`sys_menu` 表结构（`script/sql/zxcm_init.sql:3988`）关键列：

| 列 | 含义 | 取值 |
|---|---|---|
| `MENU_ID` | 主键 | 新模块要挑一个**不冲突的号段**（见下） |
| `MENU_NAME` | 菜单名 | 「印章管理」 |
| `PARENT_ID` | 父菜单 | 挂到某个目录下（如「系统管理」） |
| `MENU_TYPE` | 类型 | `M`目录 / `C`菜单 / **`F`按钮** |
| `PERMS` | **权限码** | `seal:info:list` 等 |
| `PATH` / `COMPONENT` | 前端路由 / 组件 | `info` / `seal/info/index` |
| `TENANT_FLAG` | 租户可见性 | `0`租户 `1`管理 `2`两者 |

```java
package com.ruoyi.seal.domain;

import com.baomidou.mybatisplus.annotation.TableId;
import com.baomidou.mybatisplus.annotation.TableLogic;
import com.baomidou.mybatisplus.annotation.TableName;
import com.ruoyi.common.core.domain.BaseEntity;
import lombok.Data;
import lombok.EqualsAndHashCode;

/**
 * 印章信息对象 zxcm_seal_info
 */
@Data                                        // ← Lombok：getter/setter/toString
@EqualsAndHashCode(callSuper = true)         // ← 必须 true，否则 equals 忽略父类字段
@TableName("zxcm_seal_info")                 // ← 真实表名
public class SealInfo extends BaseEntity {   // ← 继承基座，白得 createBy/updateTime/params

    private static final long serialVersionUID = 1L;

    /** 印章ID */
    @TableId(value = "seal_id")              // ← 主键列名
    private Long sealId;

    /** 印章名称 */
    private String sealName;

    /** 印章类型（字典 seal_type） */
    private String sealType;

    /** 保管人用户ID（数据权限按它过滤） */
    private Long keeperId;

    /** 保管部门ID */
    private Long keeperDeptId;

    /** 状态（0正常 1停用） */
    private String status;

    /** 删除标志（0代表存在 2代表删除） */

    private String delFlag;

    /** 租户编号 */

```

**看懂了什么？**

- **`extends BaseEntity`** → `createBy`/`createTime`/`updateBy`/`updateTime`/`params` **全部白得**（`BaseEntity.java:33`），**你不用再声明一遍**，声明了反而和父类冲突。
- **`@TableName`** → 告诉 MyBatis-Plus「这个类对应哪张表」。**类名 `SealInfo` 和表名 `zxcm_seal_info` 不一致，所以必须显式写。**（如果类名叫 `ZxcmSealInfo` 且开了驼峰转下划线，才能省略。）
- **`@TableId(value = "seal_id")`** → 主键列名。**注意本项目主键列习惯是 `表名_id`**（`seal_id`），而不是统一的 `id`（`ConfBillRule` 用的是 `id`，两种风格都在，**以实际表为准**）。
- **`@TableLogic`** → **本项目逻辑删除的实现**（第 7 章）：配合 `application.yml` 里配的 `logic-delete-value: 2` / `logic-not-delete-value: 0`，**所有 `deleteById` 都自动变成 `UPDATE ... SET del_flag=2`，所有 `select` 都自动加 `WHERE del_flag=0`**。你就当「删了」写代码，基座帮你兜住。

**★ 核心机制：校验分组（`groups`）**

**这是本项目（也是 RuoYi-Vue-Plus）校验的精髓**，也是面试常问点：

@Validated(AddGroup.class)  ... add(WebSealInfoBo bo)      // 走 AddGroup 校验

**★ 进阶版：挂数据权限**

现在问自己一个问题：**「张三只能看到自己保管的章，李四只能看到自己保管的章」——这个「行级过滤」在哪做？**

答案是**在 Mapper 上挂 `@DataPermission`**（这就是第 4 章讲的那个「无痕改写 SQL」的钩子）。**照抄 `ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/mapper/SysUserMapper.java:48` 和 `zxcm-contract/src/main/java/com/ruoyi/contract/mapper/ContractDraftMapper.java:42`**：

```java
import com.ruoyi.common.annotation.DataColumn;
import com.ruoyi.common.annotation.DataPermission;
import com.ruoyi.common.enums.permissionType.DataPermissionResource;
import com.baomidou.mybatisplus.core.conditions.Wrapper;
import com.ruoyi.common.core.domain.PageQuery;
import com.baomidou.mybatisplus.extension.plugins.pagination.Page;
import com.baomidou.mybatisplus.core.toolkit.Constants;
import org.apache.ibatis.annotations.Param;

public interface SealInfoMapper extends BaseMapperPlus<SealInfoMapper, SealInfo, SealInfoVo> {

    /**
     * 带数据权限的分页查询：按「保管人」过滤
     * key = "userId"    → 对应 ContractPermission 模板里的 #{#userId} 占位符
     * value = "keeper_id" → 占位符最终被替换成这个真实列名
     */
    @DataPermission(value = {@DataColumn(key = "userId", value = "keeper_id")},
        resource = DataPermissionResource.stampPermission)     // ← ★ 用「用印权限」维度
    Page<SealInfo> selectPageWithStamp(@Param("page") Page<SealInfo> page,
                                       @Param(Constants.WRAPPER) Wrapper<SealInfo> queryWrapper);
}
```

**逐步拆解这段注解（第 4 章的核心）**：

1. **`@DataPermission`** 是挂在 **Mapper 方法**上的注解（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/annotation/DataPermission.java:29-32` 声明 `DataColumn[] value()` + `resource()`）。**只有被它标了的查询方法**才会走数据权限改写——这是**显式开启、不误伤**的设计。
2. **`@DataColumn(key = "userId", value = "keeper_id")`**：`key` 是**占位符名**，`value` 是**真实列名**。执行时，框架把 `key` 当变量名、`value` 当变量值塞进 SpEL 上下文（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/handler/PlusDataPermissionHandler.java:134` 就是这行 `context.setVariable(dataColumn.key(), dataColumn.value())`）。
3. **`resource = DataPermissionResource.stampPermission`**：这是本项目**在标准数据权限之外扩展的自定义维度**（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/DataPermissionResource.java:16-32` 共定义 11 个枚举值：`base` + `draftPermission`/`contractPermission`/`stampPermission` 等 10 个业务维度）。它决定了「按哪个字段去读角色的数据范围」——`stampPermission`（`DataPermissionResource.java:28`）对应 `RoleDTO` 的 `stampPermission` 字段（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/dto/RoleDTO.java:56`）。
4. **模板在哪？** 在 `ContractPermission` 枚举里（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/ContractPermission.java:31`，模板常量在 `:46`/`:56`）：

   ```java
   SELF("5", " #{#userId} = #{#user.userId} ", " 1 = 0 "),          // :56 仅本人
   DEPT("3", " #{#userId} IN #{@sdss.getDeptUser( #user )} ", ""),  // :46 本部门
   ```

   **执行时，`#{#userId}` 被替换成 `keeper_id`，`#{#user.userId}` 被替换成当前登录人 ID**——最终 SQL 末尾被追加 `AND keeper_id = 123`（仅本人）或 `AND keeper_id IN (1,2,3)`（本部门）。

> **★ 这就是「无痕数据权限」的全貌**：**你的 SQL / `LambdaQueryWrapper` 里一个字都不用写**，MyBatis-Plus 的分页/dynamic 拦截器在 SQL 执行前，**按注解把 `WHERE` 条件"缝"进去**。业务代码对此**完全无感**——这正是第 4 章反复强调的「解耦」。

**⚠️ 重要提醒（第 4 章的坑）**：`key = "userId"` 必须和模板里的占位符名**严格一致**。如果你写成 `key = "sealOwner"`，模板里根本没有 `#{#sealOwner}`，**替换会静默失效（不报错，但条件没生效）**——**这是数据权限最危险的坑：权限没生效却不报错。** 改完务必**开 SQL 日志看一眼真实 SQL**。

```java
package com.ruoyi.seal.service.impl;

import java.util.Collection;
import java.util.List;

import org.springframework.stereotype.Service;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.baomidou.mybatisplus.core.toolkit.Wrappers;
import com.baomidou.mybatisplus.extension.plugins.pagination.Page;
import com.ruoyi.common.core.domain.PageQuery;
import com.ruoyi.common.core.page.TableDataInfo;
import com.ruoyi.common.utils.StringUtils;
import com.ruoyi.seal.domain.SealInfo;
import com.ruoyi.seal.domain.bo.SealInfoBo;
import com.ruoyi.seal.domain.vo.SealInfoVo;
import com.ruoyi.seal.mapper.SealInfoMapper;
import com.ruoyi.seal.service.ISealInfoService;

import cn.hutool.core.bean.BeanUtil;
import lombok.RequiredArgsConstructor;

@Service
@RequiredArgsConstructor                        // ← Lombok：给 final 字段生成构造器注入
public class SealInfoServiceImpl implements ISealInfoService {

    private final SealInfoMapper baseMapper;    // ← 构造器注入，不用 @Autowired

    @Override
    public SealInfoVo queryById(Long sealId) {
        return baseMapper.selectVoById(sealId);
    }

    @Override
    public TableDataInfo<SealInfoVo> queryPageList(SealInfoBo bo, PageQuery pageQuery) {
        LambdaQueryWrapper<SealInfo> lqw = buildQueryWrapper(bo);
        Page<SealInfoVo> result = baseMapper.selectVoPage(pageQuery.build(), lqw);
        return TableDataInfo.build(result);
    }

    @Override
    public List<SealInfoVo> queryList(SealInfoBo bo) {
        LambdaQueryWrapper<SealInfo> lqw = buildQueryWrapper(bo);
        return baseMapper.selectVoList(lqw);
    }

    /** 把 BO 里的查询条件，翻译成 MyBatis-Plus 的条件构造器 */
    private LambdaQueryWrapper<SealInfo> buildQueryWrapper(SealInfoBo bo) {
        LambdaQueryWrapper<SealInfo> lqw = Wrappers.lambdaQuery();
        lqw.like(StringUtils.isNotBlank(bo.getSealName()), SealInfo::getSealName, bo.getSealName());
        lqw.eq(StringUtils.isNotBlank(bo.getSealType()), SealInfo::getSealType, bo.getSealType());
        lqw.eq(bo.getKeeperId() != null, SealInfo::getKeeperId, bo.getKeeperId());
        lqw.eq(StringUtils.isNotBlank(bo.getStatus()), SealInfo::getStatus, bo.getStatus());
        lqw.orderByDesc(SealInfo::getUpdateTime);
        return lqw;
    }

    @Override
    public Boolean insertByBo(SealInfoBo bo) {
        SealInfo add = BeanUtil.toBean(bo, SealInfo.class);      // ← BO → Entity
        validEntityBeforeSave(add);
        boolean flag = baseMapper.insert(add) > 0;
        if (flag) {
            bo.setSealId(add.getSealId());                       // ← 回填主键，供前端下一步用
        }
        return flag;
    }

    @Override
    public Boolean updateByBo(SealInfoBo bo) {
        SealInfo update = BeanUtil.toBean(bo, SealInfo.class);
        validEntityBeforeSave(update);
        return baseMapper.updateById(update) > 0;
    }

    /** 保存前的数据校验（唯一约束等业务规则放这里） */
    private void validEntityBeforeSave(SealInfo entity) {
        // 示例：同一租户下印章名不允许重复
        Long count = baseMapper.selectCount(Wrappers.<SealInfo>lambdaQuery()
            .eq(SealInfo::getSealName, entity.getSealName())
            .ne(entity.getSealId() != null, SealInfo::getSealId, entity.getSealId()));
        if (count > 0) {
            throw new ServiceException("印章名称已存在：" + entity.getSealName());
        }
    }

    @Override
    public Boolean deleteWithValidByIds(Collection<Long> ids, Boolean isValid) {
        if (isValid) {
            // 业务校验：比如"有未完成的用印申请就不许删"
        }
        return baseMapper.deleteBatchIds(ids) > 0;               // ← 逻辑删除，实为 UPDATE del_flag=2
    }
}

**逐行读 `SealInfoServiceImpl` 的核心四段**（文件待新建；写法对照 `zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/ConfBillRuleServiceImpl.java:60-124`）：

| 代码段 | 这一行/这一段在干什么 | 为什么这么写 |
|---|---|---|
| `@RequiredArgsConstructor` + `private final SealInfoMapper baseMapper` | Lombok 为 `final` 字段生成构造器，Spring 用构造器注入 Mapper | 字段注入（`@Autowired`）在单元测试里不好替换；构造器注入可以直接 `new` 时传 mock |
| `queryById` → `baseMapper.selectVoById(sealId)` | 按主键查，直接返回 VO | `BaseMapperPlus` 已经把"查 Entity → 拷到 VO"封装好了（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/mapper/BaseMapperPlus.java:150`） |
| `buildQueryWrapper(bo)` | 把 BO 里的查询字段逐个翻译成 `like`/`eq` 条件 | 每个条件前面都有 `StringUtils.isNotBlank(...)`：**条件为 false 时 MyBatis-Plus 自动忽略这一项**，所以一个方法就能应付"传了就查、没传就查全部" |
| `lqw.orderByDesc(SealInfo::getUpdateTime)` | 默认按更新时间倒序 | 后台列表通常"最近改过的排前面"，省得用户翻页找 |
| `insertByBo`：`BeanUtil.toBean(bo, SealInfo.class)` | BO → Entity | BO 面向入参、Entity 面向表，两者字段同名时一行拷贝即可 |
| `validEntityBeforeSave(add)` | 保存前做"同租户下印章名不重复"校验 | 数据库唯一索引之外再给用户一个友好提示；**这类跨行/跨表规则放 Service，不放 Controller** |
| `baseMapper.insert(add) > 0` | 执行插入，用"影响行数"判断成功 | MyBatis-Plus 的 `insert` 返回受影响行数，`> 0` 才是真的成功 |
| `bo.setSealId(add.getSealId())` | 把数据库生成的主键回填给 BO | 前端新增后能立刻拿到新 ID，不用刷新列表 |
| `deleteWithValidByIds` → `baseMapper.deleteBatchIds(ids)` | 批量删除 | Entity 上有 `@TableLogic`（§4.4），**实际执行的是 `UPDATE ... SET del_flag='2'`，不是物理删除** |

**下面把其中最关键的五个细节展开——能讲出来就是内行**：

1. **`@RequiredArgsConstructor` + `private final SealInfoMapper baseMapper`** → Lombok 生成**构造器注入**。**这是本项目的统一风格**（`ConfBillRuleServiceImpl`、`SysUserServiceImpl` 都是），比 `@Autowired` 字段注入**更利于单元测试**（能 new 时塞 mock）。
2. **`buildQueryWrapper` 的 `StringUtils.isNotBlank(x)` 前缀** → **「条件成立才拼进 SQL」**。`lqw.like(false, ...)` 时 MyBatis-Plus **自动忽略该条件**。这样**一个方法就能应付「传了 sealName 就按名字查、没传就查全部」**——不用写一堆 if。
3. **`insert` 后 `bo.setSealId(add.getSealId())`** → **把自增/雪花主键回填给 BO**。因为 `SealInfo` 插入后主键才生成，回填给前端能让它「不刷新就拿到新记录 ID」。
4. **`throw new ServiceException(...)`** → 抛出去，**基座的 `GlobalExceptionHandler` 会接住并包成 `R.fail(msg)`**（第 11 章）。**你在 Service 里只管抛，不用管怎么返回给前端。**
5. **`deleteBatchIds` 是逻辑删除** → 因为 Entity 上标了 `@TableLogic`（§4.4），**这行代码实际执行的是 `UPDATE zxcm_seal_info SET del_flag='2' WHERE seal_id IN (...)`**，不是真删。

#### ★ `@SaCheckPermission("seal:info:add")`——接口鉴权（第 3 章）

- **它做什么**：Sa-Token 的**注解拦截器**（`SaTokenConfig.java:79` 注册的 `SaAnnotationInterceptor`）会扫描 Controller 方法上的 `@SaCheckPermission`，**比对「当前登录用户是否拥有 `seal:info:add` 权限码」**，没有就抛 `NotPermissionException` → 全局异常处理器返回 **403**（第 11 章）。
- **权限码从哪来**：**就是 §4.2 插进 `sys_menu.PERMS` 的那些字符串**。**这里 Ctrl+C / Ctrl+V，两边必须一字不差。**（拼错 = 所有人都被拦 = 接口 403）
- **命名规范 `模块:功能:操作`**：`seal`（模块）`:info`（功能）`:add`（操作）。**全项目统一**（`conf:billRule:add`、`system:user:add`）。

#### ★ `@Log(title = "印章管理", businessType = BusinessType.INSERT)`——操作日志（第 8 章）

- **它做什么**：`LogAspect`（AOP 切面）**在方法执行后**，把「谁、什么时候、调了哪个接口、参数是什么、成功还是失败」写一条进 `sys_oper_log`。
- **`businessType`** 取值来自 `BusinessType` 枚举（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/BusinessType.java:21`）：`OTHER`/`INSERT`/`UPDATE`/`DELETE`/`GRANT`/`EXPORT`/`IMPORT`/`FORCE`/`GENCODE`/`CLEAN`/`DOWNLOAD`。**查询接口（list/getInfo）不记日志**——因为查询太频繁，记日志会爆表。**只有「写操作 + 导出导入」才记。**
- **⚠️ 默认只记「成功的操作」**：`@Log` 有 `isSaveResponseData` 等属性，且**异常时不记**——想记失败操作要额外配置（第 8 章的坦白点）。

#### ★ `@RepeatSubmit()`——防重提交（第 9 章）

- **它做什么**：在**同一用户 + 同一参数 + 短时间（默认 5 秒）内重复请求**时，**第二次直接拒绝**，返回「不允许重复提交」。
- **为什么加在 add/edit 上**：**防「用户手抖点两下」导致插入两条数据**。这是**「网络慢时用户狂点提交按钮」的经典问题**的兜底。
- **加在哪类接口**：**写操作（add/edit/import）**。**查询不需要**（重复查无害）。

#### ★ `extends BaseController` + `toAjax(...)`

`BaseController`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/controller/BaseController.java:26`）提供：

| 方法 | 作用 | 行号 |
|---|---|---|
| `toAjax(int rows)` | `rows > 0 ? R.ok() : R.fail()` | `BaseController.java:34` |
| `toAjax(boolean)` | 同上，接受布尔 | `:44` |
| `getLoginUser()` / `getUserId()` / `getUsername()` | 拿当前登录人 | `:58`/`:65` |

**为什么继承它？** 因为 `toAjax` 把「影响行数 → 统一返回 `R`」这个**每个写接口都要做**的动作封装了一次。**不继承你也能写 `return rows>0?R.ok():R.fail();`，但继承是团队约定。**

#### ★ `@Validated(AddGroup.class)` / `@Validated(EditGroup.class)`

**这是 §4.5 那个「校验分组」的「触发点」**：
- `add` 用 `AddGroup.class` → 只校验标了 `AddGroup` 的字段（`sealName`/`sealType`/`keeperId`），**不校验 `sealId`**。
- `edit` 用 `EditGroup.class` → **额外校验 `sealId` 不能为空**。

**校验失败的后果**：Spring 抛 `MethodArgumentNotValidException` → 基座的 `GlobalExceptionHandler` 接住 → **返回 `R.fail("印章名称不能为空")`**（把 `@NotBlank(message=...)` 里的文案原样带给前端）。**你只写 `message`，不用写任何 try-catch。**

### 4.12 第十二步：前端页面 + 接菜单（接入点 10/11）

#### ① 页面 `zxcm-ui/src/views/seal/info/index.vue`（**待新建**）

**这个文件当前不存在**，是本章要新建的页面。**本项目的前端 CRUD 页有「标准模板」**——`zxcm-ui/src/views/system/notice/index.vue` 是最干净的一版。**你的印章页 = 把 notice 页的「公告」字段换成「印章」字段**，结构完全一样：

```

  ├── <el-form>  搜索区       ← 印章名称/类型/状态 三个搜索条件
  ├── 工具栏      新增/修改/删除/导出 按钮   ← 每个按钮用 v-hasPermi 控制显隐

      └── <el-form>  表单字段  ← 印章名称/类型(下拉字典)/保管人(选人)/状态

**三个关键点**（前端重塑版会细讲，这里点到）：

1. **按钮权限 `v-hasPermi`**：

   ```html
   <el-button v-hasPermi="['seal:info:add']" @click="handleAdd">新增</el-button>
   ```

   **`v-hasPermi` 是前端指令**——它读取当前用户的权限码列表（登录时后端返回），**没权限的按钮直接不渲染**。**这和后端 `@SaCheckPermission` 是「双保险」**：前端防「误点」，后端防「绕过」（用户直接调 API）。**两者都要有，缺一不可。**

2. **字典翻译**：

   ```javascript
   dicts: ['seal_type'],   // 声明本页要用 seal_type 字典（框架自动请求）
   ```

   ```html
   <el-table-column label="印章类型" prop="sealType">
     <template #default="scope">
       <dict-tag :options="dict.type.seal_type" :value="scope.row.sealType"/>
     </template>
   </el-table-column>
   ```

   **`dict.type.seal_type` 就是 §4.2 插进 `sys_dict_data` 的那份数据**——框架在页面加载时自动拉取。**列表展示、下拉框、Excel 导出（§4.6）三处翻译，共用同一份字典配置。**

3. **`handleAdd` / `handleUpdate` / `handleDelete` / `handleExport` 四个标准方法**——分别调 `addSeal` / `updateSeal` / `delSeal` / `download`（§4.11 的 api）。

> **前端零基础也没关系**：**这个页面「照抄 notice 页、只换字段名和字典名」就能跑。** 本项目的 CRUD 页高度模板化，**这正是「基座化」在前端的体现**——页面骨架是现成的，你只填「你的字段」。

#### ② 接菜单（这一步实际上 §4.2 的 SQL 已经做了）

**菜单不能只靠 SQL**——**Vue 的路由必须在 `sys_menu` 里配**，因为**本项目用「动态路由」**：用户登录后，后端根据「他的角色能看到哪些菜单」，**动态生成前端路由**（第 1 章讲过）。

所以 §4.2 里的那条 `INSERT INTO sys_menu ... COMPONENT='seal/info/index' ...` **就是「路由配置」**：
- `PATH='seal'` → 路由 `/seal`
- `COMPONENT='seal/info/index'` → 对应 `zxcm-ui/src/views/seal/info/index.vue`（**待新建**）
- `PERMS='seal:info:list'` → 有这个权限的用户才能看到这个菜单

**验证「菜单接对了没有」**：登录一个**拥有 `seal:info:list` 权限的角色**，左侧菜单应出现「印章管理」，点进去能加载出列表。**看不到 = 菜单/权限没配对**（回去查 `sys_role_menu` 有没有给这个角色授权 `20000`）。

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：你在项目里加过一个新模块吗？完整流程说一遍。**

有。以我加的「印章管理」为例，**11 个接入点**：① 设计表 `zxcm_seal_info` → ② 插 `sys_menu` 配菜单和 `seal:info:*` 权限码、配 `seal_type` 字典 → ③ 建 Maven 模块 `zxcm-seal` 并注册进根 pom、让 `ruoyi-admin` 依赖它 → ④ 写 `SealInfo extends BaseEntity` → ⑤ 写带校验分组的 `SealInfoBo` → ⑥ 写带 `@ExcelDictFormat` 的 `SealInfoVo` → ⑦ 写 `SealInfoMapper extends BaseMapperPlus` 并挂 `@DataPermission` → ⑧⑨ 写 Service 的 5 个标准方法 → ⑩ 写 Controller，挂 `@SaCheckPermission` + `@Log` + `@RepeatSubmit` → ⑪ 写前端 api + vue 页 + 接菜单。**做完跑 12 项自测清单**（权限、数据权限、日志、防重、逻辑删除、字典、租户…）。（依据：框架骨架照抄 `ConfBillRule`；权限码机制见第 1/3 章；数据权限见第 4 章）

**Q2：为什么 Entity/BO/VO 要分三个类，不能合并吗？**

**因为三者变化方向不同**：Entity 面向表（表加列只动它）、BO 面向入参（加校验只动它）、VO 面向出参（加展示字段只动它）。合并成一个类的代价是——**要在数据库字段上挂前端校验注解，还会把 `delFlag`/`tenantId` 这类不该暴露的字段泄给前端**。分三个类是「让每类变化只影响一处」。

**Q3：新模块怎么接权限？前端和后端权限是怎么分工的？**

**后端**：Controller 每个方法挂 `@SaCheckPermission("seal:info:add")`，权限码存在 `sys_menu.PERMS`，通过 `sys_role_menu` 授权给角色。**Sa-Token 的 `SaAnnotationInterceptor` 在方法执行前校验**（`SaTokenConfig.java:79`），没有就抛 `NotPermissionException` → 403。
**前端**：按钮挂 `v-hasPermi="['seal:info:add']"`，没权限的按钮**不渲染**。
**这是「双保险」**：前端防「误点」，后端防「绕过前端直接调 API」。**前端权限只是体验，后端权限才是安全**——不能只做前端。

**Q4：数据权限是怎么挂到新表上的？**

在 **Mapper 方法**上挂 `@DataPermission(value = {@DataColumn(key="userId", value="keeper_id")}, resource = DataPermissionResource.stampPermission)`。执行时，`PlusDataPermissionHandler` 把角色配置的数据范围（`ContractPermission` 枚举里的 SpEL 模板，如「仅本人」`#{#userId} = #{#user.userId}`）解析后**追加到 SQL 的 WHERE 里**（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/handler/PlusDataPermissionHandler.java:134`）——`#{#userId}` 被替换成 `keeper_id`，`#{#user.userId}` 被替换成当前登录人。**业务 SQL 一个字不动**。（第 4 章详解）

**Q5：新增接口为什么要加 `@RepeatSubmit`？加了 `@SaCheckPermission` 还不够吗？**

不够，**两者防的是完全不同的东西**：`@SaCheckPermission` 防「**没权限的人调**」，`@RepeatSubmit` 防「**有权限的人重复调**」——典型是**网络慢时用户连点两次提交，插了两条数据**。`@RepeatSubmit` 在「同用户+同参数+5 秒内」拒绝第二次。**它和幂等键是不同层次的方案**，本项目用的是时间窗 + 请求指纹。

**Q6：加一个 Maven 模块，最容易踩的坑是什么？**

**「加了 `<module>` 却忘了让 `ruoyi-admin` 依赖它」**。因为 `@ComponentScan("com.ruoyi")` 只扫 classpath 上的类——模块不被启动模块依赖，它的 jar 不进 classpath，**Controller/Service 永远不被扫描到**，你会遇到「代码编译通过、接口却 404」的诡异现象。**记住：加模块 = 根 pom 加 `<module>` + `ruoyi-admin` 加依赖，两处都要改。**

> **追问：如果两处 pom 都改了还是 404，下一步查什么？**
> **一句话答**：按"类在不在 classpath → 包名在不在 `com.ruoyi` 扫描范围 → Controller 的 `@RequestMapping` 拼出来的 URL 对不对 → Sa-Token 拦截器是不是把请求拦了"的顺序查。启动类上的扫描配置在 `ruoyi-admin/src/main/java/com/ruoyi/RuoYiApplication.java:38`。

**Q7：新模块的表，为什么必须有 `create_by`/`create_time` 这四列和 `del_flag`？**

因为 Entity 继承 `BaseEntity`，MyBatis-Plus 的**自动填充**（CREATE/UPDATE 时写 `createBy`/`updateTime`）和**逻辑删除**（`@TableLogic` 把 `del_flag` 当删除标记）都要读写这几列。**建表漏了会直接报「Unknown column」**。这是「继承基类」带来的**隐式契约**——**基座的便利是有前提的，前提就是表要配合。**

**Q8：字典为什么不写死在代码里？**

**加一种印章类型，写死在代码里要改代码 + 重新部署；用字典只需在「字典管理」页加一行。** 而且字典是**一处配置、多处生效**：前端列表翻译、前端下拉框、后端 Excel 导出（`@ExcelDictFormat`）全都读同一份字典。**这是「配置驱动优于硬编码」。**

### 本章答辩卡（3 组追问级问答）

**卡 1｜问：新模块接口 404，你怎么按顺序排查？**

- **10 秒答案**：先看「模块在不在 classpath」——根 `pom.xml:323-336` 有没有 `<module>zxcm-seal</module>`，`ruoyi-admin/pom.xml:73` 附近有没有加依赖；再看「包名在不在扫描范围」——启动类是 `@ComponentScan(basePackages = {"com.ruoyi"})`（`ruoyi-admin/src/main/java/com/ruoyi/RuoYiApplication.java:38`），所以包名必须是 `com.ruoyi.seal`；最后核对 `@RequestMapping("/seal/info")` 和请求 URL。
- **证据**：根 `pom.xml:323-336`、`ruoyi-admin/pom.xml:73`、`RuoYiApplication.java:38`。

**卡 2｜问：`@DataPermission` 加了却没过滤，为什么？**

- **10 秒答案**：三个高频原因：① 注解要挂在 Mapper 的**接口方法**上（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/annotation/DataPermission.java:29-32`）；② `key` 必须和模板里的占位符同名，模板是 `#{#userId}` 就必须写 `key="userId"`，写成别的会静默不生效；③ 角色对应维度的数据范围没配。验证方法：打开 SQL 日志（`application.yml:239`），在 `PlusDataPermissionHandler.java:134` 下断点，看变量有没有塞进去。
- **证据**：`DataPermission.java:29-32`、`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/handler/PlusDataPermissionHandler.java:134`、`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/ContractPermission.java:56`。

**卡 3｜问：加一个模块，对基座代码的侵入到底有多大？怎么保证能整块摘掉？**

- **10 秒答案**：代码层面只动两个 `pom.xml`——根 `pom.xml:323-336` 加 `<module>`，`ruoyi-admin/pom.xml:73` 附近加依赖；基座任何 Java 代码都不用改。因为约定"业务依赖基座、基座不依赖业务"，摘除时删掉这两个 pom 条目和 `zxcm-seal/` 目录即可，不会留下对基座的引用。
- **证据**：根 `pom.xml:323-336`、`ruoyi-admin/pom.xml:73`、依赖方向说明见第 0 章 §4.2。

## 七、选型对比：新模块怎么造，有哪些路

### 7.1 手写 vs 代码生成器（`ruoyi-generator`）

| 方案 | 速度 | 理解深度 | 适用 |
|---|---|---|---|
| **手写（本章路线）** | 慢 | **深（你必须搞懂每个接入点）** | 学习、要深度定制的模块 |
| **代码生成器** | **快（建表后一键生成）** | **浅（生成完你不一定懂）** | 标准 CRUD、赶工期 |

**代码生成器在哪？** 项目里有 `ruoyi-base/ruoyi-generator` 模块，前端「系统工具 → 代码生成」（`zxcm-ui/src/views/tool/gen`）。它的原理就是**读你的表结构 → 按模板吐出 Entity/BO/VO/Mapper/Service/Controller/vue/菜单 SQL**——**吐出来的东西，和本章手写的骨架是同一套**。

**结论**：**实际工作里用生成器提效，但你必须先「手写过一遍」**——否则生成出来了你也不知道哪里该改、权限码该挂哪、数据权限该挂哪列。**这正是本章先讲手写的原因。**

### 7.2 独立 Maven 模块 vs 塞进现有模块的包

| 方案 | 隔离性 | 成本 | 何时选 |
|---|---|---|---|
| **独立 Maven 模块**（本章做法） | **强（可整块摘除）** | 多一个 pom + 根 pom 一行 | 一个完整业务域（印章、档案、公告） |
| **塞进 `zxcm-contract` 的子包** | 弱 | 零 | 紧贴现有业务的附加功能（合同的一个子表） |

**判断标准**：**「它能不能单独讲清楚、能不能单独砍掉」**——能，就独立成模块。**印章管理是独立业务域，所以独立成模块。**

### 7.3 数据权限：用标准维度还是自定义维度

| 方案 | 配置位置 | 适用 |
|---|---|---|
| **标准 `DataScopeType`**（`base` 资源） | 角色的 `data_scope` 字段 | 通用（全部/本部门/仅本人） |
| **自定义 `ContractPermission`**（如 `stampPermission`） | 角色的扩展字段（`RoleDTO.java:56`） | **业务定制的维度**（合同/草稿/台账/用印各自的权限） |

**本项目两者都用**：系统管理用标准 `DataScopeType`，**合同业务用自定义维度**——因为「合同草稿的数据权限」和「用印的数据权限」是**两种不同的规则**，用一个 `data_scope` 表达不了。**印章模块用 `stampPermission`，是这个设计的自然延伸。**

## 本章小结 & 下一步

- **新模块的本质 = 把「业务对象」挂到基座预留的 11 个接入点上**：
  1. 建表 → 2. 菜单权限码 + 字典 → 3. Maven 模块（根 pom + admin 依赖） → 4. Entity（`extends BaseEntity`） → 5. BO（校验分组） → 6. VO（`@ExcelDictFormat`） → 7. Mapper（`extends BaseMapperPlus` + `@DataPermission`） → 8. Service 5 方法 → 9. ServiceImpl → 10. Controller（`@SaCheckPermission`+`@Log`+`@RepeatSubmit`） → 11. 前端 api + vue + 菜单。
- **三层对象（Entity/BO/VO）**：面向表 / 面向入参 / 面向出参，**各自独立变化**。
- **★ 三件套注解**：`@SaCheckPermission`（鉴权，第 3 章）+ `@Log`（操作日志，第 8 章）+ `@RepeatSubmit`（防重，第 9 章）——**新模块的「必备动作」**。
- **★ 数据权限**：Mapper 方法挂 `@DataPermission(key→占位符, value→真实列)`，**业务 SQL 一字不改**，`WHERE` 被无痕缝进去（第 4 章）。
- **★ 校验分组**：一个 BO，`@Validated(AddGroup)` / `@Validated(EditGroup)` 两种校验视角（§4.5）。
- **★ 字典**：一处 SQL 配置，前端列表 + 下拉框 + 后端 Excel 翻译**全部自动生效**（第 12 章）。
- **加模块的两个必改点**：根 pom 的 `<module>` + `ruoyi-admin` 的 `<dependency>`，**少一个就 404**。
- **12 项自测清单**：权限、数据权限、日志、防重、逻辑删除、字典、租户、自动填充……**每加一个模块跑一遍，全绿才算写完**。
- **可迁移的思维**：**「基座提供钩子、业务填钩子」**、**「配置驱动优于硬编码」**（字典/菜单）、**「前端权限是体验、后端权限是安全」**、**「照着已有模块写，永远比从零想快」**。
