# 第 5 章 · 多点登录 ★

> **第 2 章讲"一次登录怎么发生"，本章讲"一个账号能有几次登录、这些登录之间是什么关系"。** 你可能关心：**同一个账号能不能同时开三个浏览器？在 A 电脑登录会不会把 B 电脑顶掉？管理员怎么把某个用户强制踢下线？**
>
> **这是用户点名要学的第二个重点。** 它是"认证"这个话题的下半场——上半场是"怎么登录"，下半场是"登录态怎么共存、怎么管理"。
>
> **本章第一次讲透**：① Sa-Token 三个开关 `is-concurrent` / `is-share` / `max-login-count` 的**确切语义**（这三个开关组合起来才是"多点登录策略"）；② **每一份 token 落进 Redis 的两个 key**（`token:login:token:` 和 `online_tokens:`）分别干什么；③ `DeviceType` 设备维度和"**同端互斥**"；④ 在线用户监控（`/monitor/online/list`）与**强制踢人**怎么实现；⑤ `UserActionListener` 作为"登录事件监听器"的作用。

## 一、这部分是做什么的？

> ### 零基础先补概念
>
> 1. **token（令牌）**：登录成功后服务器发给客户端的一串随机字符串。之后每次请求都带着它，服务器靠它认出"你是谁"。本项目的 token 风格是 uuid（`application.yml:121`），传输时放在请求头 `token: Bearer <值>`（前端 `zxcm-ui/src/utils/request.js:33`）。
> 2. **Sa-Token**：本项目用的登录鉴权框架。`StpUtil.login(...)` 负责发 token，`StpUtil.kickoutByTokenValue(...)` 负责踢人（`SysUserOnlineController.java:100`）。
> 3. **Redis 里的 key**：token 不是只存在浏览器里——服务端也要存一份。本项目每次登录至少写两条：`token:login:token:<token>` → 登录 ID（认证用），`online_tokens:<token>` → 在线信息（监控用），见 `Constants.java:91` / `:96`。
> 4. **监听器（Listener）**：框架在"登录/注销/被踢"这些时刻会回头调用你写的类。本项目的 `UserActionListener` 实现 `SaTokenListener`，专门负责维护 `online_tokens:`（`UserActionListener.java:46`）。

### 1.1 什么是"多点登录"？

**"多点登录"（多端登录 / 多设备登录）指：同一个账号，在不同的设备/浏览器上分别登录。** 这里有三个独立的问题要分开答：

| 问题 | 谁决定 | 本项目答案 |
|---|---|---|
| 允许同一个账号**并发**登录吗？ | `sa-token.is-concurrent` | **允许**（`true`） |
| 多次登录**共用**一个 token 吗？ | `sa-token.is-share` | **不共用**（`false`，每次新 token） |
| 最多能同时登录**几处**？ | `sa-token.max-login-count` | 未配置，走框架默认 |

**三个开关组合，才是"多点登录策略"。** 本项目 = **允许并发 + 每次新 token** → 即"**同一个账号可以在多台设备上各自登录，互不影响**"。

### 1.2 "顶下线" vs "踢下线" vs "注销"

三个词经常被混用，本章严格区分：

| 说法 | 英文/API | 触发者 | 触发场景 |
|---|---|---|---|
| **注销** | `StpUtil.logout()` | **用户自己** | 点"退出登录" |
| **踢下线** | `StpUtil.kickoutByTokenValue(token)` | **管理员** | 在线用户监控里"强退" |
| **顶下线** | （框架自动）`doReplaced` | **系统** | 并发策略不允许时，新登录顶掉旧的 |

**本项目因为 `is-concurrent: true`，正常情况不会发生"顶下线"**——新登录不会踢旧的。**"顶下线"只在用户数超过 `max-login-count` 时才由框架触发。**

### 1.3 一份 token，在 Redis 里存成两个 key

这是理解本章的**关键**。每次登录，Redis 里都会有**两条相关记录**：

| key 前缀 | 定义位置 | 存什么 | 谁写 | 谁读 |
|---|---|---|---|---|
| `token:login:token:` | `Constants.LOGIN_TOKEN_KEY`（`Constants.java:91`） | token → **loginId** 的映射（Sa-Token 维护） | `PlusSaTokenDao`（第 2 章） | Sa-Token 自己校验 token 时 |
| `online_tokens:` | `Constants.ONLINE_TOKEN_KEY`（`Constants.java:96`） | token → **UserOnlineDTO**（IP、浏览器、OS、登录时间） | **`UserActionListener.doLogin`** | **在线用户监控**（`/monitor/online/list`） |

**为什么是两个？** ——**职责分离**：

- `token:login:token:` 是 **Sa-Token 框架的"命根子"**，用来把 token 还原成 loginId，**认证必须用**；
- `online_tokens:` 是**"给管理员看的业务数据"**——IP、浏览器、登录时间这些**框架不关心**，是**本项目为了"在线用户监控"页面自己加的**。

> 📌 **这是"框架能力"和"业务增强"的一次漂亮配合**：Sa-Token 只负责认证，**"谁在线、什么设备、什么时候登的"这种运营信息由本项目的监听器补上**。

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么本项目选"允许并发登录"？（`is-concurrent: true`）

看 `application.yml:109`：

```yaml
# 是否允许同一账号并发登录 (为true时允许一起登录, 为false时新登录挤掉旧登录)
is-concurrent: true
```

**这个开关是"业务决策"，不是技术决策。** 两种取值代表两种产品思路：

| 取值 | 效果 | 适合谁 |
|---|---|---|
| `false`（新登录挤掉旧） | 一个账号**同时只能在线一处** | 银行、支付（安全优先，防账号共享） |
| **`true`（本项目）** | 一个账号**可多处同时在线** | 办公系统（**人在手机和电脑上都要用**） |

**为什么合同系统选 `true`？** 因为办公场景**天然多端**：销售可能在公司电脑上看合同、在手机 App 上审批、在公司大屏上看板——**如果只允许一处，用户每次切换设备都要重新登录，体验极差**。所以办公系统**默认允许并发**。

**代价是什么？** 账号可能被共享（一人账号多人用）。本项目用**登录日志**（第 8 章）来事后审计，而不是用"禁止并发"来堵——**这是"办公系统重体验、轻安全强约束"的取舍**。

### 2.2 为什么还要 `is-share: false`？—— 并发 ≠ 共用

很多人以为"允许并发"就是"共用一个 token"，**这是错的**。`is-concurrent` 和 `is-share` 是**两个正交的开关**：

看 `application.yml:111`：

```yaml
# 在多人登录同一账号时, 是否共用一个token (为true时所有登录共用一个token, 为false时每次登录新建一个token)
is-share: false
```

**四个组合的含义：**

| is-concurrent | is-share | 效果 |
|---|---|---|
| `false` | `true` | 只能一处在线（旧的被顶），且共用 token |
| `false` | `false` | 只能一处在线，每次登录换新 token（旧的失效） |
| **`true`** | **`true`** | 可多处在线，但**大家共用一个 token**（A 退出会导致 B 也退出） |
| **`true`** | **`false`（本项目）** | **可多处在线，且每处一个独立 token** |

**为什么本项目要 `is-share: false`？** 因为**如果共用 token**：

- 用户在浏览器 A 登录拿到 token X，又在手机 App 登录 —— **如果共用，手机拿到的还是 token X**；
- 这样**"强制踢掉手机"就没法单独踢**——一踢就把浏览器也踢了；
- 而且**"在线用户列表"会看着很怪**（多个设备同一个 token，没法区分）。

**`is-share: false` 让"每个登录 = 一个独立 token"**，于是：

1. 在线用户监控里**每条记录对应一次真实登录**（能精确踢某一次）；
2. 退出登录只影响自己那一处（A 退出 B 不受影响）；
3. 手机 App 和浏览器**互不干扰**。

**结论**：**"允许并发"决定"能不能多处登录"，"不共用 token"决定"多处登录是不是彼此独立"。** 本项目两个都要——**多处登录 + 每一处独立可管**。

### 2.3 `max-login-count`：并发的"上限闸门"

**本项目 `application.yml` 里没有配置 `max-login-count`**（你可以自己 grep 确认，`sa-token` 段只有 :101-125 那几项）。所以走 **Sa-Token 的框架默认值**（Sa-Token 默认 `maxLoginCount = 12`，即同一账号最多同时 12 个登录，超过后**最早的被顶下线**；设为 `-1` 表示不限）。

> ⚠️ **坦白点（配置与需求）**：本项目**没显式设这个值**，意味着"同一账号最多 12 处在线"这个限制是**隐式继承框架默认**的，产品文档里大概率没提。**如果业务要求"最多 3 台设备"，这里就得显式配 `max-login-count: 3`。** 面试若被问"你们限制最多几台设备同时在线"，**正确答法是"未显式限制，走框架默认；如需限制可在此配置"**，别硬编一个数字。

### 2.4 为什么要有 `DeviceType` 设备维度？

`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/DeviceType.java:27-47`：

```java
public enum DeviceType {
    PC("pc"),        // :32 电脑端
    APP("app"),      // :37 手机 App
    WXMINI("wxMini"),// :41 微信小程序
    API("api"),      // :43 接口调用
    QYWX("qywx");    // :45 企业微信
    private final String device;
}
```

**设备维度解决什么问题？** ——**"同端互斥"**。设想一个常见需求：**"同一账号，PC 端只允许同时在线一个（新登录顶掉旧的），但 PC 和手机可以共存"**。

Sa-Token 的做法是：**登录时带上 `device` 参数**，框架按 **`loginId + device`** 组合管理 token。看 `LoginHelper.loginByDevice`（`LoginHelper.java:78-82`）：

```java
public static void loginByDevice(LoginUser loginUser, DeviceType deviceType) {
    LOGIN_CACHE.set(loginUser);
    StpUtil.login(loginUser.getLoginId(), deviceType.getDevice());   // ★ 带上 device="pc"
    setLoginUser(loginUser);
}
```

**`StpUtil.login(loginId, device)`** 就是"以某设备身份登录"。配上框架的设备级策略，就能实现"PC 端互斥、跨端共存"。

> ⚠️ **坦白点（本项目 DeviceType 实际只用了 PC）**：`SysLoginService` 里两处登录**写死了 `DeviceType.PC`**（`SysLoginService.java:154` 和 `:179`）：
> ```java
> LoginHelper.loginByDevice(loginUser, DeviceType.PC);   // :154 账号密码登录
> LoginHelper.loginByDevice(loginUser, DeviceType.PC);   // :179 第三方登录
> ```
> 也就是说 **`APP` / `WXMINI` / `API` / `QYWX` 四个枚举值在本项目里"定义了但没被用到"**。**本项目是纯 PC 端系统**（前端 `zxcm-ui` 就是 PC 管理后台），多端登录在**配置上"允许"**，但**业务上只有 PC 一种设备**。**面试时若问"你们多端怎么区分"，如实答"目前只有 PC 端，`DeviceType` 是为将来预留的"**，别说没有的功能。
>
> **另有一处例外**：`LoginHelper.login(user)`（不带 device 的版本，`LoginHelper.java:66`）被 **OnlyOffice 文档回调**用了两次（`OnlyofficeCallbackController.java:87` 和 `:119`）——因为那是**服务端回调**（WPS 服务器回调进来），没有"设备"概念，就用普通登录。

### 2.5 为什么要有"在线用户监控"？

因为**"允许并发登录"带来一个管理需求**：**管理员得能看到"现在谁在线、在哪些设备上、什么时候登的"，并且能"强制踢人"。**

看 `ruoyi-admin/src/main/java/com/ruoyi/web/controller/monitor/SysUserOnlineController.java`：

```java
@SaCheckPermission("monitor:online:list")                      // :52 要权限
@GetMapping("/list")
public TableDataInfo<SysUserOnline> list(String ipaddr, String userName) {   // :54
    String tenantId = getLoginUser().getTenantId();            // :55 ★ 只看本租户
    // ① 扫出所有未过期的 token
    List<String> keys = StpUtil.searchTokenValue("", -1, 0);   // :57
    for (String key : keys) {
        String token = key.replace(Constants.LOGIN_TOKEN_KEY, "");          // :60
        // ② 已过期的跳过（懒清理）
        if (StpUtil.stpLogic.getTokenActivityTimeoutByToken(token) < 0) {   // :62
            continue;
        }
        // ③ 从 online_tokens: 里取出登录信息
        userOnlineDTOList.add(RedisUtils.getCacheObject(Constants.ONLINE_TOKEN_KEY + token));  // :65
    }
    // ④ 按租户 / IP / 用户名过滤 ...
}
```

**三个点值得注意**：

1. **`StpUtil.searchTokenValue("", -1, 0)`（:57）** 是**全库扫 token**（底层走第 2 章的 `PlusSaTokenDao.searchData` → `RedisUtils.keys`）。这在**在线用户量大时是性能隐患**（Redis `keys` 命令会阻塞）——**坦白点**。
2. **租户隔离（:55/:70）**：**只看得到本租户的在线用户**。这是多租户系统的基本要求（第 6 章）。
3. **过期懒清理（:62）**：扫到已过期的 token 就跳过——**说明 `online_tokens:` 里的记录可能残留**（TTL 到期前不会自动从列表里消失）。

**强制踢人**（`:98-104`）：

```java
@SaCheckPermission("monitor:online:forceLogout")    // :95
@Log(title = "在线用户", businessType = BusinessType.FORCE)   // :96 记操作日志
@DeleteMapping("/{tokenId}")
public R<Void> forceLogout(@PathVariable String tokenId) {
    try {
        StpUtil.kickoutByTokenValue(tokenId);       // :100 ★ 按 token 值踢人
    } catch (NotLoginException e) {
        // 已经不在线了，忽略
    }
    return R.ok();
}
```

**`StpUtil.kickoutByTokenValue(tokenId)`（:100）** 就是"踢下线"。它会让**那一个 token**失效（因为 `is-share: false`，**只踢这一处，不影响其他设备**）。

### 2.6 `UserActionListener`：登录事件的"监听者"

`online_tokens:` 里的数据是**谁、什么时候**写进去的？答案是一个实现 `SaTokenListener` 的监听器——`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/listener/UserActionListener.java:46`：

```java
@Component
public class UserActionListener implements SaTokenListener {          // :46
    private final SaTokenConfig tokenConfig;                          // :48 读配置（拿 timeout）

    @Override
    public void doLogin(String loginType, Object loginId, SaLoginModel loginModel) {  // :54
        UserType userType = UserType.getUserType(loginId.toString()); // :55
        if (userType == UserType.SYS_USER) {                          // :56
            UserAgent userAgent = null;
            String ip = "";
            try {                                                     // :59 非 Web 环境可能没有 request
                userAgent = UserAgentUtil.parse(
                    ServletUtils.getRequest().getHeader("User-Agent"));  // :60
                ip = ServletUtils.getClientIP();                      // :61
            } catch (Exception e) { }                                 // :62-64 解析失败就留空
            LoginUser user = LoginHelper.getLoginUser();              // :66
            String tokenValue = StpUtil.getTokenValueByLoginId(loginId);  // :67
            UserOnlineDTO dto = new UserOnlineDTO();
            dto.setIpaddr(ip);                                        // :69
            dto.setBrowser(userAgent == null ? "" : userAgent.getBrowser().getName()); // :71
            dto.setOs(userAgent == null ? "" : userAgent.getOs().getName());           // :72
            dto.setLoginTime(System.currentTimeMillis());             // :73
            dto.setTokenId(tokenValue);                               // :74
            dto.setUserName(user.getUsername());                      // :75
            dto.setTenantId(loginId.toString().split(LoginHelper.JOIN_CODE)[0]);  // :77 ★ 从 loginId 抠租户
            // ★ 写进 Redis，TTL 和 token 的绝对有效期一样
            RedisUtils.setCacheObject(Constants.ONLINE_TOKEN_KEY + tokenValue, dto,
                                      Duration.ofSeconds(tokenConfig.getTimeout()));   // :78
            log.info("user doLogin, useId:{}, token:{}", loginId, tokenValue);        // :79
        }
    }

    @Override public void doLogout(...)   { RedisUtils.deleteObject(ONLINE_TOKEN_KEY + tokenValue); }  // :90 注销
    @Override public void doKickout(...)  { RedisUtils.deleteObject(ONLINE_TOKEN_KEY + tokenValue); }  // :99 被踢
    @Override public void doReplaced(...) { RedisUtils.deleteObject(ONLINE_TOKEN_KEY + tokenValue); }  // :108 被顶
    // 还有 doDisable / doUntieDisable / doCreateSession / doLogoutSession（本项目留空）
}
```

**逐行读：`doLogin` 这 20 多行到底在干什么**

| 行号 | 这一行在干什么 | 为什么这么写 |
|---|---|---|
| `:55` | 从 loginId 里解析用户类型 | loginId 形如 `租户:sys_user:用户ID`，先判断是不是后台用户 |
| `:56` | 只处理 `SYS_USER` | 项目里还有 `APP_USER` 分支（`:80-82`，留空），不同用户体系分开处理 |
| `:59-64` | 用 try/catch 包住 Request 解析 | 登录可能发生在**非 Web 线程**（如服务端回调），此时拿不到 `HttpServletRequest`，不能让它把登录搞崩 |
| `:66` | 取当前 `LoginUser` | 后面要拿用户名；它来自 token-session（第 2 章） |
| `:67` | `getTokenValueByLoginId(loginId)` | 拿到"这次登录刚生成的 token 值"，作为 Redis key 的后缀 |
| `:69-75` | 把 IP、浏览器、OS、时间、token、用户名装进 DTO | 这些就是监控页要展示的字段 |
| `:71-72` | 对 `userAgent` 判空 | 上面可能解析失败，不判空会 NPE |
| `:77` | `split(":")[0]` 取租户 | loginId 第一段就是租户 ID，这是 loginId 设计的回报（第 6 章 §1.4） |
| `:78` | 写 `online_tokens:<token>`，TTL 用 `timeout` | **注意用的是 `getTimeout()`（绝对有效期），不是 `activity-timeout`**，所以这条记录可能比"会话活动有效期"活得久，需要监控页懒清理（§2.5） |
| `:79` | 打 info 日志 | 排查"某人几点登录"时先搜这行 |
| `:90/:99/:108` | 注销/被踢/被顶时删同一个 key | **写删配对**，保证在线列表不残留 |

**关键理解：**

1. **`SaTokenListener` 是 Sa-Token 的"事件总线"**——框架在**登录、注销、被踢、被顶、封禁**等时刻**回调**你。本项目实现它，**只做一件事：维护 `online_tokens:` 这条 Redis 记录**。
2. **写、删是配对的**：`doLogin` 写（:78），`doLogout` / `doKickout` / `doReplaced` 三个都删（:90/:99/:108）。**保证"在线列表"和"真实登录态"一致**。
3. **租户从 loginId 里抠**（:77）：`loginId` 是 `tenantId:userType:userId`（第 2 章 §2.4），`split(":")[0]` 就是租户 ID——**这就是 loginId 设计成"带租户前缀"的用处之一**。
4. **`log.info("user doLogin, ...")`（:79）**：登录事件也打了日志，便于排查（不是 debug 级，默认 INFO 就能看到）。

## 三、需要哪些技术？

| 技术 / 机制 | 在本章里具体指什么 | 精确定位 | 详解在哪 |
|---|---|---|---|
| **`is-concurrent`** | 允不允许并发登录 | `application.yml:109` | §2.1 |

## 四、功能具体怎么实现（带着你读懂）

### 4.1 有效期：两种超时

`application.yml:105-107`：

```yaml
timeout: 186400          # 绝对有效期（秒）
activity-timeout: 28800  # 无操作超时（秒）= 8 小时
```

- **`timeout`（绝对有效期）**：token 从登录起**最多活多久**，到点必失效；
- **`activity-timeout`（活动有效期）**：**超过这么久没操作**就失效（每次请求会刷新）。

**两者是"AND"关系**——哪个先到就以哪个为准。**这就是"8 小时不操作自动退出，但最多也活不过 absolute timeout"的含义。**

> ⚠️ **坦白点（注释与数值不符）**：`application.yml:104` 的注释写「token 有效期 **设为一天**」，但值是 **`186400` 秒 ≈ 51.8 小时**（一天的 86400 秒，51.8 小时≈2.16 天）。**注释和实际值对不上**——这大概率是历史遗留/复制粘贴所致。**以数值为准（约 51.8 小时）**，别照着注释说"一天"。**这种"注释骗人"的地方，面试被问到就诚实说"以配置值为准"**，反而显得你真读过配置。

**`activity-timeout` 在哪体现？** 在 §2.5 的在线列表里（`SysUserOnlineController.java:62`）：

```java
StpUtil.stpLogic.getTokenActivityTimeoutByToken(token) < 0   // :62 活动超时为负 = 已失效
```

**能拿到"剩余活动时间"，判断负值即为"该会话已过期"**——在线列表靠这个**过滤掉"记录还在、其实已超时"的僵尸条目**。

### 4.2 完整登录过程（登录 → 写两个 key）

以张三在浏览器登录为例，把第 2 章和本章串起来：

```
POST /login （用户名密码）
  │
  ▼ SysLoginService.login()（第 2 章）
  │   校验通过 → buildLoginUser → 得到 LoginUser（loginId = "5:sys_user:101"）
  │
  ▼ LoginHelper.loginByDevice(loginUser, DeviceType.PC)          LoginHelper.java:78
  │   ① LOGIN_CACHE.set(loginUser)        塞 ThreadLocal（第 2 章多级缓存）
  │   ② StpUtil.login("5:sys_user:101", "pc")     ★ Sa-Token 真正登录
  │        └─ 生成 token（uuid 风格）→ 写 Redis: token:login:token:<token> → loginId
  │        │                                     （is-share=false → 每次都新建一个 token）
  │        └─ 触发 SaTokenListener.doLogin 回调 ★
  │              └─ UserActionListener.doLogin（UserActionListener.java:54）
  │                    ├─ 解析 User-Agent（浏览器/OS）
  │                    ├─ 取客户端 IP
  │                    └─ 写 Redis: online_tokens:<token> → UserOnlineDTO   :78
  │   ③ setLoginUser(loginUser)
  │        └─ StpUtil.getTokenSession().set("loginUser", loginUser)   第 2 章
  │
  ▼ 返回 token 给前端
```

**一眼看清"两个 key 的分工"：**

| 步骤 | 写哪个 key | 谁写 |
|---|---|---|
| ② `StpUtil.login` 内部 | `token:login:token:<token>` | Sa-Token / `PlusSaTokenDao` |
| ② 的副作用（监听回调） | `online_tokens:<token>` | `UserActionListener`（本项目） |
| ③ `setLoginUser` | **token-session**（`token:login:session:`） | `LoginHelper` |

**三条记录各司其职**：认证用第一条，监控用第二条，业务取当前用户用第三条。

### 4.3 "多点登录"的实际效果（本项目）

**场景：张三先用电脑登录（token A），再用手机 App 登录（token B）**——因为 `is-concurrent: true` + `is-share: false`：

```
电脑登录 → token A   （online_tokens:A 记一条）
手机登录 → token B   （online_tokens:B 记一条）
```

**结果：**

| 动作 | 效果 |
|---|---|
| 电脑 A 调接口 | token A 有效 → 正常 |
| 手机 B 调接口 | token B 有效 → 正常（**A 不受影响**） |
| 在电脑点"退出登录" | `StpUtil.logout()` → 只失效 token A（`doLogout` 删 `online_tokens:A`）→ **手机 B 仍在线** |
| 管理员在监控页踢 A | `kickoutByTokenValue(A)` → 只失效 A（`doKickout` 删 `online_tokens:A`）→ **手机 B 仍在线** |

**这就是"多点登录 + 每处独立"的完整效果。** 若把 `is-share` 改成 `true`，则会变成"大家共用一个 token，退出/踢出会影响所有设备"。

### 4.4 在线用户列表返回什么

看 `UserOnlineDTO.java:30-78` 的字段（以及 `SysUserOnline` 是它的展示实体）：

| 字段 | 含义 | 怎么来的 |
|---|---|---|
| `tokenId` | 会话编号（就是 token 值） | `StpUtil.getTokenValueByLoginId`（`UserActionListener:67`） |
| `userName` | 用户名 | `LoginUser.username` |
| `ipaddr` | 登录 IP | `ServletUtils.getClientIP()` |
| `browser` | 浏览器类型 | 解析 `User-Agent` |
| `os` | 操作系统 | 解析 `User-Agent` |
| `loginTime` | 登录时间（毫秒） | `System.currentTimeMillis()` |
| `tenantId` | 租户 ID | 从 loginId 抠（`split(":")[0]`） |
| `deptName` / `loginLocation` | 部门名 / 登录地 | **本项目里是注释掉的**（`UserActionListener:70/:76`），没填 |

> ⚠️ **坦白点**：`deptName`（部门名）和 `loginLocation`（IP 归属地）在本项目里**被注释掉了**（`UserActionListener.java:70` / `:76`）。所以在线用户页面**看不到"部门"和"登录地点"两列**——`AddressUtils.getRealAddressByIP` 那套 IP 归属地解析本项目**没启用**（需要额外的 IP 库/接口）。**别在答辩时说"能看到登录地点"**。

### 4.5 怎么"强制踢人"

前端在监控页选中某条在线记录 → 调 `DELETE /monitor/online/{tokenId}`（`SysUserOnlineController.java:97`）→ 后端 `StpUtil.kickoutByTokenValue(tokenId)`（:100）。

**"踢"到底做了什么？**

1. Sa-Token 把 `token:login:token:<token>` 删掉 → 这个 token 再也认不出 loginId → **认证失败**；
2. 触发 `SaTokenListener.doKickout` → `online_tokens:<token>` 被删（`UserActionListener:99`）→ **在线列表里消失**；
3. 被踢的用户**下次请求**会收到 **401**（`NotLoginException`，第 3 章 §4.5），前端**跳登录页**。

**注意"下次请求"**——**踢下线是"被动生效"的**：不会立刻给用户推消息，而是**等他下一次操作时才发现自己掉线了**。要做"实时踢人提示"得配 WebSocket 推送（第 14 章）。**这也是面试可能追问的点。**

### 4.6 `max-login-count` 超限会怎样？

本项目没配，走框架默认。**假设**某天配成 `max-login-count: 3`，张三在 4 台设备登录：

- 第 4 次登录时，**最早的（第 1 台）被顶下线**；
- 顶下线触发 `doReplaced` 回调（`UserActionListener.java:107`）→ 删掉第 1 台的 `online_tokens:`；
- 第 1 台下次请求 → 401。

**"顶下线"和"踢下线"的机制其实一样**（都是删 token + 触发回调），**区别只在"谁触发"**：顶下线是"新登录"触发的自动行为，踢下线是"管理员"主动行为。

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：★ 你们的多点登录是怎么配置的？**

三个开关（`application.yml:101-125`）：**`is-concurrent: true`**（允许同一账号并发登录）、**`is-share: false`**（每次登录新建独立 token，不共用）、`max-login-count` **未显式配置**（走框架默认）。效果是"**同一账号可在多处设备各自登录，每处独立、互不影响**"。**`is-concurrent` 决定"能不能多处登录"，`is-share` 决定"多处是不是共用一个 token"——两个正交开关。**

**Q2：`is-concurrent` 和 `is-share` 什么区别？**

`is-concurrent` 管**"允不允许同一账号同时在线多份"**（false = 新登录挤掉旧登录）；`is-share` 管**"多份登录共不共用一个 token"**（true = 共用，一处退出全体退出；false = 每处独立 token）。**本项目 `true` + `false` = 允许多处、且每处独立。**

**Q3：★ 一份 token 在 Redis 里存了几份数据？分别是什么？**

**两条**：① `token:login:token:<token>`（`Constants.java:91`）——token → loginId 的映射，**Sa-Token 框架认证用**，由 `PlusSaTokenDao` 写；② `online_tokens:<token>`（`:96`）——token → `UserOnlineDTO`（IP/浏览器/OS/登录时间），**本项目为"在线用户监控"自己加的**，由 `UserActionListener.doLogin`（`:78`）写。另外还有 **token-session**（`LoginHelper.setLoginUser`，`LoginHelper.java:87-89`）存 `LoginUser`。**前者是"命根子"，后者是"业务运营数据"，职责分离。**

**追问：`online_tokens:` 的 TTL 和 token 会话的有效期完全一样吗？** 不完全一样——它用的是 `tokenConfig.getTimeout()`（绝对有效期，`UserActionListener.java:78`），而会话还受 `activity-timeout` 影响；所以可能出现"token 已经因 8 小时无操作失效，但 `online_tokens:` 记录还活到 51.8 小时"的窗口，监控页靠 `:62` 的"活动超时<0 就跳过"做懒清理。

**Q4：在线用户监控怎么实现的？有什么隐患？**

扫全部 token（`StpUtil.searchTokenValue`，`SysUserOnlineController.java:57`）→ 从 `online_tokens:` 还原 DTO → 按租户/IP/用户名过滤（`SysUserOnlineController.java:67-84`，租户条件在 `:70/:74/:78/:82`）。**隐患**：`searchTokenValue` 底层是 Redis `keys` 扫描（`PlusSaTokenDao.searchData`），**在线量大时会阻塞 Redis**；而且 `online_tokens:` 的记录**在 TTL 到期前不会从列表自动消失**，靠"活动超时<0 就跳过"（`:62`）做懒清理。**生产上大在线量应改用 `scan` 或维护独立索引。**

**Q5：怎么强制踢人？被踢的人怎么知道？**

`StpUtil.kickoutByTokenValue(tokenId)`（`:100`）。它会**删 token + 触发 `doKickout` 清 `online_tokens:`**。**被踢人是"被动生效"**——**下次请求**才收到 401（`NotLoginException`），前端跳登录页。**要做"实时提示被踢"需要 WebSocket 推送**（本项目未实现，第 14 章）。**注意踢下线只影响那一个 token（因为 `is-share: false`）。**

**Q6：`UserActionListener` 是干什么的？**

实现 Sa-Token 的 **`SaTokenListener`（事件监听 SPI）**，在**登录/注销/被踢/被顶/封禁**等时刻被框架回调（`UserActionListener.java:46`）。本项目**只拿它维护 `online_tokens:` 这条在线记录**（`doLogin` 写、`doLogout`/`doKickout`/`doReplaced` 删，`:78/:90/:99/:108`）。**它是"框架事件"和"业务运营数据"之间的桥梁。**

**Q7：`DeviceType` 有什么用？你们支持多端吗？**

`DeviceType`（`DeviceType.java:27`）是**设备维度**，用来实现"**同端互斥**"（如"PC 端只能同时在线一个，但 PC 和手机可共存"）。登录时通过 `StpUtil.login(loginId, device)` 带上设备（`LoginHelper.java:80`）。**但坦白讲，本项目是纯 PC 系统，`SysLoginService` 里登录写死了 `DeviceType.PC`（`:154`/`:179`），APP/小程序等四个值定义了没用到**——是**为将来预留**的。**别说你们支持多端。**

**Q8：`timeout` 和 `activity-timeout` 有什么区别？**

`timeout`（:105）= **绝对有效期**，登录后到点必失效；`activity-timeout`（:107）= **无操作超时**（8 小时不操作就失效，每次请求刷新）。**两者取先到者**。**注意本项目 `timeout` 注释写"一天"但实际值 `186400` 秒 ≈ 51.8 小时**（注释与值不符，以值为准）。

**Q9：允许多点登录会不会有安全风险？**

会——**账号可能被共享**。本项目选择"体验优先"（办公场景多端是刚需），**风险靠登录日志事后审计**（第 8 章）而非"禁止并发"来堵。**如果安全要求高，应把 `is-concurrent` 设为 `false`（新登录顶掉旧登录）。**

### 本章答辩卡（追问级）

**① 问：`is-share: false` 之后，A 设备点退出，B 设备为什么不受影响？**

**10 秒答案**：因为每次登录是**不同的 token**，`LoginHelper.setLoginUser` 把 `LoginUser` 写进**各自 token 的 token-session**（`LoginHelper.java:87-89`），注销时只删 A 的 token 和 A 的 `online_tokens`（`UserActionListener.java:90`），B 的 token-session 完全没被碰。

**证据**：`E:\Develop\project\zhaoxin\zhaoxin-contract\ruoyi-admin\src\main\resources\application.yml:111`（`is-share: false`）；`E:\Develop\project\zhaoxin\zhaoxin-contract\ruoyi-base\ruoyi-common\src\main\java\com\ruoyi\common\helper\LoginHelper.java:87-89`（token-session）；`E:\Develop\project\zhaoxin\zhaoxin-contract\ruoyi-base\ruoyi-framework\src\main\java\com\ruoyi\framework\listener\UserActionListener.java:90`（注销只删当前 token）。

**② 问：在线用户列表里的记录，会不会比用户实际在线状态"活得久"？为什么？**

**10 秒答案**：会。`online_tokens:` 的 TTL 用的是**绝对有效期** `tokenConfig.getTimeout()`（`UserActionListener.java:78`，约 51.8 小时），而会话还受 `activity-timeout`（8 小时无操作）约束。用户 8 小时没操作后 token 实际已失效，但 `online_tokens:` 可能还在；监控页只能靠"活动超时<0 就跳过"（`SysUserOnlineController.java:62`）**懒清理**。

## 七、选型对比：登录态的几种方案

### 7.1 多点登录策略

| 策略 | 配置 | 适合场景 | 代价 |
|---|---|---|---|
| 单点互斥 | `is-concurrent=false` | 银行、支付（安全优先） | 多设备体验差 |
| **并发+共用 token** | `is-concurrent=true, is-share=true` | 少见 | 一处退出全体退出，无法单独踢 |
| **并发+独立 token（本项目）** | `is-concurrent=true, is-share=false` | 办公系统多端 | token 数量多，Redis 压力略大 |
| 限制并发数 | 加 `max-login-count: N` | 防账号共享 | 超过就顶掉最早的，用户可能困惑 |

**结论**：**办公系统选"并发+独立 token"**，兼顾体验与可管理性；**要防共享再加 `max-login-count`**。

### 7.2 会话存储

| 方案 | 位置 | 多点登录支持 | 分布式支持 |
|---|---|---|---|
| HTTP Session | 服务端内存 | 靠 `session` 机制，弱 | **差（需 session 共享）** |
| **token + Redis（本项目）** | Redis | **天然支持（每 token 一条）** | **好** |
| JWT 无状态 | 客户端 | 支持，但**难"踢人"**（无法作废已签发 JWT） | 好 |

**结论**：**要"多点登录 + 能踢人"，"token + Redis 有状态"是最优解**——JWT 虽无状态但**难以主动作废**（踢下线做不了，除非维护黑名单，那又回到 Redis）。本项目用 Sa-Token 的 **JWT 风格（第 2 章）+ Redis 存储**，兼得"JWT 的传输形态"和"Redis 的可管控"。

### 7.3 "踢下线"的实时性

| 方案 | 用户何时感知 | 实现成本 |
|---|---|---|
| **被动（本项目）** | **下次请求**收 401 | 零成本（Sa-Token 自带） |
| 主动推送 | 立刻收到提示 | 需 WebSocket（第 14 章） |

**结论**：**绝大多数后台系统用"被动"就够了**；对实时性要求高（如"账号在异地登录，立即弹窗"）才上 WebSocket。

## 本章小结 & 下一步

- **多点登录 = 三个开关的组合**：`is-concurrent`（能否并发）+ `is-share`（是否共用 token）+ `max-login-count`（上限）。本项目 = **并发 + 每次独立 token + 上限走默认**。
- **一份登录在 Redis 里两/三条记录**：`token:login:token:`（认证命根子）、`online_tokens:`（业务监控，本项目监听器写）、token-session（`LoginUser`）。
- **`UserActionListener`**（实现 `SaTokenListener`）= 登录事件监听，负责维护 `online_tokens:`（写/删配对）。
- **在线监控 + 踢人**：`/monitor/online/list` + `StpUtil.kickoutByTokenValue`；踢人是**被动生效**（下次请求 401）。
- **坦白点**：① `DeviceType` 定义了 5 种但**只用了 PC**；② `max-login-count` **未显式配置**；③ `timeout` 注释写"一天"实际≈51.8 小时；④ `deptName`/`loginLocation` **被注释掉了**，看不到部门与登录地；⑤ `searchTokenValue` 底层 `keys` 扫描，**在线量大是性能隐患**。

**下一章（第 6 章 · 多租户）**：前面五章（权限总览 → 认证 → 鉴权 → 数据权限 → 多点登录）讲的都是"**一个人在系统里怎么被识别、授权、隔离数据**"。下一章换一个维度——**"一整个租户和另一个租户之间怎么隔离"**。本项目是**多租户系统**（`sys_tenant` 表、`tenantId` 贯穿始终），第 6 章讲清 Sa-Token 的 loginId 为什么要带 `tenantId` 前缀、MyBatis 怎么自动给每条 SQL 加 `tenant_id` 条件。
