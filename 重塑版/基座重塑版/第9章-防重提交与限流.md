# 第 9 章 · 防重提交 · 限流 · 幂等

> **第 8 章讲"事后记录"，本章讲"事前拦截"。** 用户手抖**连点两次"提交"** → 会不会建两条合同？**有人拿脚本狂刷**你的导出接口 → 服务器扛不扛得住？
>
> **本章第一次讲透**：① **防重提交**（`@RepeatSubmit`）——怎么用 Redis 做"窗口期内同一请求只放行一次"，以及一个**非常聪明的"成功才拦、失败放行"**设计；② **限流**（`@RateLimiter` + Redisson 令牌桶）——三种限流维度；③ **幂等**是什么，和防重的区别，本项目怎么"用防重代替幂等"；④ 一个**必须坦白的事实**：**限流注解本项目其实一处都没用**。

---

## 一、这部分是做什么的？

### 1.0 零基础先补概念（第一次读先看这里）

| 概念 | 大白话 | 本章的真实例子 |
|---|---|---|
| **Redis key + TTL** | 在 Redis 里放一个"记号"，到点自动消失；窗口期内看到记号就拒绝 | 防重 key 写完 5 秒自动过期（`RepeatSubmitAspect.java:82`） |
| **AOP 前置/后置通知** | 在业务方法执行前"拦一下"，在返回后/抛异常时"补一刀" | `@Before` 放行时写 key，`@AfterReturning` 成功保留、失败删除（同文件 `:58`、`:98`、`:105`） |
| **令牌桶** | 桶里按固定速率生成令牌，请求拿走一个才放行；没令牌就排队/拒绝 | Redisson 的 `RRateLimiter`（`RedisUtils.java:50-54`） |
| **幂等** | 同一个请求执行 1 次和执行 N 次，最终结果一样 | 审批前先判断状态、数据库唯一约束（业务层） |

**先记住一句话**：**防重 = 时间窗口内的"去重"；限流 = 单位时间内的"限速"；幂等 = 执行 N 次结果不变**。三个词经常被混着说，但解决的不是同一件事。

### 1.1 三个容易混淆的概念

| 概念 | 要解决什么 | 关键词 | 本项目 |
|---|---|---|---|
| **防重提交** | 用户**短时间连点**，造成重复业务 | **时间窗口**去重 | `@RepeatSubmit`（**用了 40+ 处**） |
| **限流** | **接口被高频调用**（刷、爬、攻击） | **速率**控制 | `@RateLimiter` 基础设施（**但一处未用**） |
| **幂等** | **同一个请求执行 N 次，结果和执行 1 次一样** | **结果一致性** | 业务层自己保证（唯一约束/状态机） |

**关键区别**：

- **防重**是"**别让我连着点**"——**靠时间窗口**（比如 5 秒内同一个请求只处理一次）；
- **限流**是"**别让我点太快**"——**靠速率**（比如每 IP 每分钟最多 100 次）；
- **幂等**是"**就算点了 N 次，结果也对**"——**靠业务设计**（唯一索引、状态判断）。

**三者不是一回事，也不是"有 A 就不用 B"**。本项目**防重用得最多、限流有架子没用、幂等靠业务自己**。

### 1.2 为什么"前端防连点"不够？

前端确实可以做"点击后按钮置灰"。**但不可靠**，因为：

1. **网络延迟**：第一次请求还没回来，按钮"以为"没点成功，用户又点了；
2. **用户能绕开**：F12 改 DOM、Postman 直接发、复制请求重放；
3. **多标签页**：同一个页面开两个标签，各自都能点。

**所以"防重"必须做在后端**——和前端的按钮置灰**配合、但不能依赖**。（这和第 3 章"前端藏按钮不是安全措施"是同一个道理：**前端的约束不可信，后端必须自证。**）

### 1.3 防重的原理：Redis 里的"一次性锁"

一句话：**把"这一次提交"在 Redis 里标记一下，带个过期时间；窗口期内再来一次，看到标记就拒绝。**

```
第一次：Redis 里没这个 key → 写一个（TTL=5秒）→ 放行
第二次（5秒内）：Redis 里有 key → 拒绝"不允许重复提交，请稍候再试"
5秒后：key 自动过期 → 又能提交了
```

**逻辑上等价于"`SETNX`（set if not exists）+ TTL"**——一个经典的"分布式一次性锁"。**因为是 Redis，多台服务器也共享这个标记**（单体/集群都对）。

> ⚠️ **但要说得准确一点**：本项目 **不是**直接调 `SETNX`，而是先 `getCacheObject`（`:80`）再 `setCacheObject`（`:82`）。这两步**不是原子的**——极端并发下两个请求可能同时读到 `null`、同时写入，都放行。对"防手抖"够用，但不是严格的分布式锁。面试被追问"怎么保证原子"时，要敢承认这一点，并给出正解（Lua 脚本 / `SET key value NX PX` / Redisson 锁）。

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 防重的 key 是怎么算出来的？

看 `RepeatSubmitAspect.doBefore`（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/RepeatSubmitAspect.java:58-91`）：

```java
@Before("@annotation(repeatSubmit)")                            // :58 方法执行前
public void doBefore(JoinPoint point, RepeatSubmit repeatSubmit) throws Throwable {
    long interval = 0;
    if (repeatSubmit.interval() > 0) {                          // :62 用注解配的间隔
        interval = repeatSubmit.timeUnit().toMillis(repeatSubmit.interval());
    }
    if (interval < 1000) {                                      // :65 不允许小于 1 秒
        throw new ServiceException("重复提交间隔时间不能小于'1'秒");
    }
    HttpServletRequest request = ServletUtils.getRequest();
    String nowParams = argsArrayToString(point.getArgs());      // :69 ★ 把方法参数序列化
    String url = request.getRequestURI();                       // :72 ★ 请求地址
    // 唯一值：token（没有就用请求地址）
    String submitKey = StringUtils.trimToEmpty(request.getHeader(SaManager.getConfig().getTokenName()));  // :75
    submitKey = SecureUtil.md5(submitKey + ":" + nowParams);    // :77 ★ token + 参数 做 MD5
    // ★ 最终 key = 前缀 + url + md5
    String cacheRepeatKey = Constants.REPEAT_SUBMIT_KEY + url + submitKey;    // :79
    String key = RedisUtils.getCacheObject(cacheRepeatKey);     // :80 查 Redis
    if (key == null) {
        RedisUtils.setCacheObject(cacheRepeatKey, "", Duration.ofMillis(interval));  // :82 ★ 没记录 → 写一个（带TTL）
        KEY_CACHE.set(cacheRepeatKey);                          // :83 记进 ThreadLocal，后面要用
    } else {
        throw new ServiceException(message);                    // :89 ★ 有记录 → 拒绝
    }
}
```

**逐行读 `doBefore`（`RepeatSubmitAspect.java:58-91`）**：

| 行 | 代码在干什么 | 为什么这么写 |
|---|---|---|
| `58` | `@Before`：在目标方法执行**之前**运行 | 防重必须在业务落库前拦住，否则业务已经执行了 |
| `61-63` | 把注解上的 `interval` 换算成毫秒 | 支持 `interval + timeUnit` 自由组合（默认 5000ms） |
| `65-67` | 间隔小于 1000ms 直接抛异常 | 防呆：否则配置成 10ms 就等于没有防重 |
| `69` | 把方法参数序列化成字符串 | 参数进 key，才能区分"提交相同内容"和"提交不同内容" |
| `72` | 取当前请求 URI | 不同接口不能共用同一个防重标记 |
| `75` | 从请求头取 token（`SaManager.getConfig().getTokenName()`） | token 区分用户；取不到时 `trimToEmpty` 变成空串 |
| `77` | `md5(token + ":" + 参数)` | 把可能很长的参数压成固定 32 位，Redis key 不会过长 |
| `79` | 拼最终 key：`repeat_submit:` + URL + MD5 | 三段分别代表"哪个接口、谁、什么内容" |
| `80` | 查 Redis 里有没有这个 key | 有 = 窗口期内重复提交 |
| `82` | 没有 → 写入空值，TTL = 间隔时间 | 写入后 5 秒自动消失，不需要手动清理 |
| `83` | 把 key 存进 `ThreadLocal` | 后置通知要用同一个 key 决定"保留还是删除" |
| `85-89` | 已有 key → 解析提示语并抛 `ServiceException` | 业务方法根本不会被执行 |

**key 的组成是 `repeat_submit:` + `请求URL` + `md5(token:参数)`**（`:79`，前缀 `"repeat_submit:"` 定义在 `Constants.java:101`）。

**为什么要拼这三样？** 拆开看每一段的作用：

| 组成 | 作用 | 少它会怎样 |
|---|---|---|
| `url` | **区分接口** | 不同接口会互相干扰 |
| `token` | **区分用户/会话** | A 用户提交会影响 B 用户 |
| `参数` | **区分"内容"** | **同一接口提交不同内容也会被误判"重复"** |
| **三者都有** | **"同一个人的、对同一个接口、发同样的内容"才算重复** | — |

> 📌 **"拼参数"是最容易被忽略的一步**。如果不拼参数，用户在同一个表单页面**先提交 A 再提交 B**（两次内容不同）也会被拦——**那就不是"防重复"而是"防连续提交"了**。**本项目把参数纳入 key，做到了"内容相同的才算重复"。**

**为什么用 `md5`？** ——参数可能很长（一个表单 JSON 几百 KB），**直接拼进 Redis key 会很长**；`md5` 把它压成固定 32 字符。**这是"key 要短"的工程考虑。**

**为什么要 `ThreadLocal<String> KEY_CACHE`？**（`:56`）——`doBefore` 算出了 key，**后面 `doAfterReturning` / `doAfterThrowing` 要"删掉这个 key"**，所以得把 key 传过去。**`ThreadLocal` 是最方便的"同一次请求内、跨通知"传值方式**（同步执行，同线程，安全）。

### 2.2 ★ 最聪明的设计："成功才拦、失败放行"

看后置通知（`RepeatSubmitAspect.java:98-120`）：

```java
@AfterReturning(pointcut = "@annotation(repeatSubmit)", returning = "jsonResult")   // :98
public void doAfterReturning(JoinPoint joinPoint, RepeatSubmit repeatSubmit, Object jsonResult) {
    if (jsonResult instanceof R) {
        R<?> r = (R<?>) jsonResult;
        if (r.getCode() == R.SUCCESS) {
            return;                              // :103 ★ 成功 → 什么都不做（key 保留！）
        }
        RedisUtils.deleteObject(KEY_CACHE.get()); // :105 ★ 失败 → 删 key
        KEY_CACHE.remove();
    }
}

@AfterThrowing(value = "@annotation(repeatSubmit)", throwing = "e")   // :116
public void doAfterThrowing(JoinPoint joinPoint, RepeatSubmit repeatSubmit, Exception e) {
    RedisUtils.deleteObject(KEY_CACHE.get());    // :118 ★ 抛异常 → 删 key
    KEY_CACHE.remove();
}
```

**这套逻辑的含义是**：

| 本次提交结果 | 对 key 做什么 | 效果 |
|---|---|---|
| **成功** | **保留 key** | **窗口期内再点 → 被拦**（防重生效） |
| **业务失败（返回 `R` 且 code≠SUCCESS）** | **删 key** | **可以立刻重试**（不让失败卡住用户） |
| **抛异常** | **删 key** | **可以立刻重试** |

**为什么要区分成功和失败？** 想一个场景：**用户点"提交"，服务器返回"保存失败，请重试"**——

- **如果不管成败都保留 key**：用户**想重试却重试不了**（被自己的防重拦住了），**5 秒内干瞪眼**；
- **如果不管成败都删 key**：**防重就失效了**（失败后立刻能重复提交，而"重复提交"往往是"请求超时"导致的，跟成败无关）。

**本项目的选择**：**"成功"意味着"这次请求真的落地了"，所以要拦后续重复；"失败"意味着"这次没落地"，应该放行重试。** 这是一个**非常贴合业务直觉**的设计——**面试聊到这个点会让人眼前一亮。**

> ⚠️ **一个边界情况（坦白点）**：`:100` 的判断是 `if (jsonResult instanceof R)`。**如果方法返回值不是 `R`（比如返回 `void`、`AjaxResult`、自定义类型），整个 if 块不执行 → key 永远不删。** 也就是说**这类方法的防重 key 会一直保留到 TTL 到期**（"成功才拦"的语义对它不成立）。**本项目 Controller 统一返回 `R`，所以没问题**，但**要知道这个前提**。

### 2.3 为什么"间隔不能小于 1 秒"？

`RepeatSubmitAspect.java:65-67`：

```java
if (interval < 1000) {
    throw new ServiceException("重复提交间隔时间不能小于'1'秒");
}
```

**这是"防呆"**：如果允许配 `interval = 10ms`，**那不叫防重、叫"每秒 100 次提交"**——既没意义，又会**疯狂读写 Redis**。**设一个下限（1 秒），防止配置被玩坏。** 默认值是 **5000ms = 5 秒**（`RepeatSubmit.java:33`）。

### 2.4 限流：为什么用"令牌桶"？

**限流的核心问题是"单位时间内放行多少次"**。常见算法：

| 算法 | 特点 | 代价 / 风险 |
|---|---|---|
| 计数器 | 简单，固定窗口 | **临界时刻可能双倍放行**（窗口边界问题） |
| 漏桶 | 恒定速率 | 不能应对突发 |
| **令牌桶** | **匀速产令牌 + 允许突发** | **本项目用的（Redisson `RRateLimiter`）** |

本项目用 **Redisson 的 `RRateLimiter`**（分布式令牌桶）。看 `RedisUtils.rateLimiter`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/utils/redis/RedisUtils.java:50-58`）：

```java
public static long rateLimiter(String key, RateType rateType, int rate, int rateInterval) {
    RRateLimiter rateLimiter = CLIENT.getRateLimiter(key);                                 // :51 拿分布式限流器
    rateLimiter.trySetRate(rateType, rate, rateInterval, RateIntervalUnit.SECONDS);         // :52 设速率
    if (rateLimiter.tryAcquire()) {                                                        // :53 尝试取一个令牌
        return rateLimiter.availablePermits();                                             // :54 成功 → 返回剩余令牌数
    } else {
        return -1L;                                                                        // :56 失败 → -1
    }
}
```

**为什么用 Redisson 的 `RRateLimiter` 而不是自己在 Redis 里 `INCR` 计数？**

- **`INCR` 计数**只解决了"计数"，**没解决"匀速"**——可能"前 1 秒用完 100 次，后 59 秒全拒绝"；
- **`RRateLimiter` 是令牌桶**：**令牌匀速生成，请求取令牌，取不到就拒绝**——**更平滑、允许一定突发**；
- **而且是分布式的**（Redisson 保证多实例一致）。

**`trySetRate` 用的是 `try`（`:52`）**——因为**限流器可能已存在**（`RRateLimiter` 首次设置速率后，重复设置要小心），`trySetRate` 是"不存在时才设"的安全版。

### 2.5 限流的三种"维度"——`LimitType`

`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/LimitType.java:22-37`：

```java
public enum LimitType {
    DEFAULT,    // :26 全局限流（所有请求共用一个桶）
    IP,         // :31 按请求者 IP 限流（每个 IP 一个桶）
    CLUSTER,    // :36 按"客户端实例"限流（每个 Redisson 客户端一个桶）
}
```

**三种维度对应三种业务诉求**：

| 类型 | 桶的粒度 | 典型场景 |
|---|---|---|
| **DEFAULT** | **全接口共用一个桶** | "这个接口**全网**每分钟最多 100 次"（保护后端） |
| **IP** | 每个 IP 一个桶 | "**每个用户**每分钟最多 10 次短信"（防单用户刷） |
| **CLUSTER** | 每个客户端实例一个桶 | "**每台服务器**最多 100 QPS"（**按实例算总容量**） |

**key 怎么体现维度？** 看 `RateLimiterAspect.getCombineKey`（`RateLimiterAspect.java:63-77`）：

```java
public String getCombineKey(RateLimiter rateLimiter, JoinPoint point) {
    StringBuilder stringBuffer = new StringBuilder(rateLimiter.key());     // :64 前缀
    if (rateLimiter.limitType() == LimitType.IP) {
        stringBuffer.append(ServletUtils.getClientIP()).append("-");       // :67 ★ 拼 IP
    } else if (rateLimiter.limitType() == LimitType.CLUSTER) {
        stringBuffer.append(RedisUtils.getClient().getId()).append("-");   // :70 ★ 拼客户端实例 ID
    }
    MethodSignature signature = (MethodSignature) point.getSignature();
    Method method = signature.getMethod();
    Class<?> targetClass = method.getDeclaringClass();
    stringBuffer.append(targetClass.getName()).append("-").append(method.getName());  // :75 ★ 拼类名.方法名
    return stringBuffer.toString();
}
```

**关键点**：**"维度"是通过"往 key 里拼不同的东西"实现的**——拼 IP 就是按 IP 隔离、拼实例 ID 就是按实例隔离、什么都不拼（DEFAULT）就是全局共享。**同一套代码，靠 key 的构成切换维度。** 最后总拼上"类名 + 方法名"（`:75`）**保证不同接口的桶不互相污染**。

**`RateType` 也要跟着变**（`RateLimiterAspect.java:47-50`）：

```java
RateType rateType = RateType.OVERALL;                                    // :47 默认全局
if (rateLimiter.limitType() == LimitType.CLUSTER) {
    rateType = RateType.PER_CLIENT;                                      // :49 集群按客户端
}
```

### 2.6 幂等：本项目怎么做？

**"幂等"是比防重更根本的要求**：**一个请求，不管执行几次，系统的最终状态应该一致。**

**防重的局限**：防重靠"时间窗口"（5 秒），**5 秒后用户再点还是能重复**；而且**网络重试、多入口调用**都可能绕过。**真正的幂等不依赖时间窗口。**

**幂等的常见实现**：

| 手段 | 原理 | 本项目 |
|---|---|---|
| **唯一约束** | 数据库唯一索引，重复插入报错 | **业务层用了**（如某些表的唯一键） |
| **状态机判断** | "已审批"的不能再审批 | **业务层用了**（工作流流转） |
| **幂等 key（业务令牌）** | 客户端带唯一请求号，服务端记录已处理 | 未用 |
| **防重提交** | 时间窗口去重 | `@RepeatSubmit` |

**本项目的真实情况**：**`@RepeatSubmit` 是"轻量防重"（挡手抖），真正的幂等靠业务层的"唯一约束 + 状态判断"。** 比如"审批"这种操作，**业务上会先判断当前状态**（第 3 章提到的 `ContractAuditController` 每个审批动作都标了 `@RepeatSubmit`）。**纯粹靠 `@RepeatSubmit` 不算幂等**——这句话面试要敢说。

### 2.7 ★ 坦白点：`@RateLimiter` 本项目**一处都没用**

**这是本章最重要的坦白点。** 限流的基础设施（`@RateLimiter` 注解、`RateLimiterAspect` 切面、`RedisUtils.rateLimiter`、`LimitType` 枚举）**全都写好了**，**但在整个项目里 grep `@RateLimiter`，一处使用都没有。**

**也就是说**：

- 登录接口**没有** `@RateLimiter`（**登录限流是靠 `SysLoginService` 里手写的 Redis 错误次数计数**，第 2 章讲过）；
- 导出、查询等**高频接口也没有**限流注解。

**怎么解释？** 合理的说法是"**限流能力已就绪，但当前业务量下没启用**"——**这是一个"基础设施先于业务需求"的典型**（框架带的能力，业务没用到）。**答辩时如实说"限流组件已具备、尚未在接口上启用"，别说"我们所有接口都限流了"。**

> 📌 **顺便辨析**：**"登录错误次数锁定"不是限流，是"账户锁定"**。它是**针对特定账户**的、**锁定式的**（超限就锁一段时间），**不是"速率控制"**。**这两者容易被混为一谈**——面试若问"你们限流了吗"，**准确回答是"有账户级的登录失败锁定（自己实现的）；通用的接口限流组件具备但未启用"。**

### 4.3 防重的完整时序

```
  │   cacheRepeatKey = "repeat_submit:/conf/signingSubject" + submitKey      :79
  │   Redis 无此 key → set(key, "", ttl=5000ms)                             :82

  │
  ▼ Controller.add() 执行成功 → 返回 R.ok()
  │

  │
  ▼ 结果：key 在 Redis 里活 5 秒
  │
【5 秒内第二次提交（同样内容）】
```

### 4.4 限流的用法（虽然本项目没用，但要知道怎么用）

```java

    throw new ServiceException("访问过于频繁，请稍候再试");     // :53
}
```

**和防重一样抛 `ServiceException`**，由 `GlobalExceptionHandler` 统一转成前端提示——**复用了第 11 章的统一异常体系**。

### 4.5 `ServiceException` 最终怎么变成用户看到的提示

`ServiceException` 由 `GlobalExceptionHandler` 处理（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/web/exception/GlobalExceptionHandler.java:119`，第 11 章 §4.4 细讲），**返回一个"业务错误"的统一响应**（HTTP 200 + 错误 code + message），**前端弹提示**。

**为什么用 `ServiceException` 而不是直接返回 `R.fail`？** ——因为**切面/深层代码里"抛异常"比"构造返回值"更自然**，而且**异常能被统一处理器捕获、统一格式**。**"抛异常 + 全局处理"是本项目处理业务错误的统一风格**（第 11 章细讲）。

> ⚠️ **一个副作用（坦白点）**：`RateLimiterAspect.java:56-60` 先放行"超限"的 `ServiceException`（`:53`），但把**限流器自身执行失败**（比如 Redis 连接异常）包成了 `new RuntimeException("服务器限流异常，请稍候再试")`（`:59`）——这个 `RuntimeException` 会被 `GlobalExceptionHandler` 当成"未知运行时异常"兜底，**而不是"限流提示"**。**语义上不够精确**——**更好的做法是抛 `ServiceException`**。**这是另一处"本项目若启用限流要顺手修"的地方。**

## 五、一个操作的完整生命流程：一次"被防重拦住"的提交

```
张三在"新增签约主体"页面，5秒内点了两次"确定"
  │
  ▼ 【第一次】POST /conf/signingSubject   {name:"甲方A"}
  │   ├─ 第3章：登录✓ 权限✓
  │   ├─ RepeatSubmitAspect.doBefore：Redis 无 key → 写 key(ttl 5s) → 放行
  │   ├─ Controller → Service → Mapper → MySQL 落库
  │   ├─ 返回 R.ok()
  │   └─ doAfterReturning：成功 → key 保留
  │
  ▼ 【第二次（5秒内，内容相同）】
  │   ├─ RepeatSubmitAspect.doBefore：
  │   │     cacheRepeatKey 与第一次完全相同（同 url + 同 token + 同参数）
  │   │     Redis 有 key → throw ServiceException("不允许重复提交，请稍候再试")   :89
  │   ├─ ★ 方法体根本没执行（Controller 没被调用）
  │   └─ GlobalExceptionHandler：ServiceException → 统一错误响应
  │
  ▼ 前端收到提示 → 弹"不允许重复提交，请稍候再试"

  ▼ 【5 秒后再点】Redis key 已过期 → 正常放行
```

**注意**：**第二次提交时，业务方法 `add()` 完全没被调用**——`@Before` 在方法执行**之前**就抛了异常。**这就是"防重在业务代码执行前就拦住了"。**

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：你们怎么防止表单重复提交？**

`@RepeatSubmit` 注解 + AOP（`RepeatSubmitAspect.java:54`）。原理是**在 Redis 里放一个带 TTL 的一次性标记**：key = `repeat_submit:` + URL + `md5(token:参数)`（`:79`），`@Before` 时如果 key 已存在就抛异常拒绝（`:89`），否则写入并放行（`:82`）。**Redis 保证多实例共享，TTL 保证自动过期。**

**Q2：★ 防重的 key 为什么要拼"参数"和"token"？**

**为了精确识别"同一个人的同一次重复"**。拼 **token** 区分用户（A 的提交不影响 B），拼 **参数** 区分内容（**同一页面提交不同内容不算重复**）。**只拼 URL 会误伤"提交不同内容"的正常操作。** 用 `md5` 是为了把长参数压成固定长度的 key。

**追问：两个请求几乎同时到达，`get` 再 `set` 能保证只放行一个吗？**
**不能。** `:80` 读、`:82` 写是两条独立命令；并发时两个请求都可能读到 `null` 并各自写入，从而都放行。要严格原子，应改用 Lua 脚本或 Redis `SET key value NX PX`。这也是 §1.3 提醒的"逻辑上像 SETNX、实现上不是"。

**Q3：★ 防重时，为什么"成功才保留 key、失败要删 key"？**

因为**语义不同**：**这次提交"成功了"意味着请求真的落地了，所以要拦住后续重复**（避免重复落库）；**"失败了"意味着这次没落地，应该放行让用户重试**（否则用户被自己的防重卡住，5 秒内干瞪眼）。见 `RepeatSubmitAspect.java:103`（成功 return 保留）和 `:105`（失败删 key）。**这是"贴合业务直觉"的设计。**

**Q4：为什么防重间隔不能小于 1 秒？**

**防呆**（`RepeatSubmitAspect.java:65-67`）：间隔太小（如 10ms）**既不叫"防重"、又会让 Redis 高频读写**。默认 5 秒（`RepeatSubmit.java:33`）。

**Q5：你们怎么限流的？**

**分两层说**：① **登录**有"**账户级失败锁定**"（`SysLoginService` 里用 Redis 计错误次数，第 2 章），这是**针对账户的、锁定式的**；② **通用接口限流组件已具备**（`@RateLimiter` + `RateLimiterAspect` + Redisson `RRateLimiter` 令牌桶），支持 DEFAULT/IP/CLUSTER 三种维度，**但目前没有在接口上启用**（**坦白点**）。**准确说法是"防线有、限流框架在、通用限流未启用"，别夸大。**

**Q6：限流用的什么算法？为什么？**

**令牌桶**（Redisson `RRateLimiter`，`RedisUtils.java:50-58`）。因为它**令牌匀速生成 + 允许一定突发**，比**计数器**（固定窗口有"临界双倍放行"问题）更平滑，且 **Redisson 保证分布式一致**。用 `trySetRate`（`:52`）是"不存在时才设速率"的安全写法。

**Q7：`LimitType` 三种有什么区别？**

`DEFAULT`（全局限流，所有请求共用一个桶）、`IP`（每个 IP 一个桶）、`CLUSTER`（每个客户端实例一个桶），见 `LimitType.java:22-37`。**实现上靠"往 key 里拼不同的东西"**（`RateLimiterAspect.getCombineKey`，`:63-77`）：拼 IP 就按 IP 隔离、拼实例 ID 就按实例隔离、什么都不拼就全局共享。最后总拼"类名.方法名"（`:75`）避免接口间互相污染。

**Q8：防重提交等于幂等吗？**

**不等于。** **防重**是"**时间窗口**内去重"（5 秒后还能重复）；**幂等**是"**执行 N 次结果一致**"（不依赖时间窗口）。**防重只能挡"手抖连点"，挡不住"网络重试、定时补偿、多入口调用"**。**真正的幂等靠"唯一约束 + 状态机判断"**——本项目在**业务层**做（比如审批前判断状态、某些表加唯一索引）。**`@RepeatSubmit` 是"轻量防重"，不是幂等的完整方案。**

**Q9：防重和限流有什么区别？**

**防重看"内容"、限流看"速率"**。防重是"**同一个请求别重复**"（key 里带参数），限流是"**单位时间别太快**"（不关心内容）。**防重保护"业务正确性"（别建两条合同），限流保护"系统稳定性"（别被打垮）。**

### 本章答辩卡（追问级）

**追问组 1：Redis 宕机时，带 `@RepeatSubmit` 的接口还能正常用吗？**

- **10 秒答案**：**不能，会直接失败**。`doBefore` 里查 key、写 key 都没有 try/catch 降级，Redis 连不上时异常会冒泡到全局异常处理器。这相当于"fail-closed"：宁可拒绝请求，也不放一个可能重复的请求进去。
- **证据**：`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/RepeatSubmitAspect.java:80`（查 Redis）、`:82`（写 Redis）、`:58-59`（前置通知，无降级分支）。
- **一句话总结**：防重把 Redis 变成了强依赖，可用性和正确性之间选了正确性。

**追问组 2：请求头里没有 token 时，防重 key 会变成什么样？**

- **10 秒答案**：token 会被 `trimToEmpty` 变成空串，key 实际只由"URL + 参数"决定。不同用户在同一接口提交相同参数时，会算出同一个 key，互相把对方当成"重复提交"。
- **证据**：`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/RepeatSubmitAspect.java:75`（取不到 token 得到空串）、`:77`（`md5(token + ":" + 参数)`）、`:79`（拼进 key）。所以 `@RepeatSubmit` 适合放在**已登录**的接口上；匿名接口要么别用，要么自己把 IP/设备号拼进 key。
- **一句话总结**：token 是"人"的区分符，匿名接口没有它，维度就退化了。

**追问组 3：写 key 时先 `set` 再 `expire`，会不会有"永不过期"的漏洞？**

- **10 秒答案**：**理论上会**。`RedisUtils.setCacheObject` 的实现是先 `set` 再 `expire` 两条命令（`RedisUtils.java:139-140`），不是原子操作；如果进程在两条命令之间挂掉，key 会没有 TTL。正常运行时影响很小，但严格做分布式锁应当用一条 `SET ... NX PX`。
- **证据**：`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/utils/redis/RedisUtils.java:137-140`（`set` + `expire` 分开执行）、`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/RepeatSubmitAspect.java:82`（调用点）。
- **一句话总结**：业务防重可以接受这个小概率缺口；真锁必须原子。

## 七、选型对比

### 7.1 防重的实现位置

| 位置 | 做法 | 可靠性 | 本项目 |
|---|---|---|---|
| 前端按钮置灰 | 点击后禁用 | **低（可绕开）** | 有（但不依赖） |
| **后端注解 + Redis（本项目）** | `@RepeatSubmit` + Redis 标记 | **高（多实例共享）** | **✔** |
| 数据库唯一约束 | 唯一索引兜底 | **最高（最后防线）** | 业务层按需 |
| 前端 + 后端 + 唯一索引 | 层层设防 | **最高** | **接近（缺"幂等 key"）** |

**结论**：**后端防重是必需的，但最彻底的方案是"前端置灰 + 后端防重 + 数据库唯一约束"三层**。本项目**前两层有、第三层按业务表情况加**（不是所有表都有唯一约束——**坦白点：唯一约束依赖开发者自觉**）。

### 7.2 去重标记存哪

| 存储 | 多实例共享 | TTL 支持 | 本项目 |
|---|---|---|---|
| 本地内存（`Map`/`Caffeine`） | **✗（各实例各一份）** | 要自己实现 | ✗ |
| **Redis（本项目）** | **✔** | **原生** | **✔** |
| 数据库表 | ✔ | 要自己清理 | ✗ |

**结论**：**分布式系统里，去重标记必须放 Redis**（本地内存会导致"请求打到另一台机器就绕过了"）。**本项目用自己的 `RedisUtils` 封装。**

### 7.3 限流算法

| 算法 | 平滑度 | 突发容忍 | 复杂度 | 本项目 |
|---|---|---|---|---|
| 固定窗口计数 | 差（临界问题） | 无 | 低 | ✗ |
| 滑动窗口 | 好 | 无 | 中 | ✗ |
| 漏桶 | 好（恒速） | 无 | 中 | ✗ |
| **令牌桶（本项目基础设施）** | **好** | **有** | 中 | **✔（未启用）** |

**结论**：**令牌桶是"通用限流"的默认选择**（平滑 + 允许突发），Redisson 直接提供，**没必要自己实现**。

## 本章小结 & 下一步

- **防重提交**：`@RepeatSubmit`（默认 5 秒）+ `RepeatSubmitAspect`。**key = `repeat_submit:` + URL + `md5(token:参数)`**（`RepeatSubmitAspect.java:79`），**逻辑上**等价于 Redis `SETNX` + TTL 的分布式一次性锁；但实现是 `get`（`:80`）再 `set`（`:82`）两步，**不是原子操作**（§1.3 已坦白）。
- **★ 精妙设计**：**成功保留 key（拦住重复）、失败删 key（放行重试）**（`:103` vs `:105`/`:118`）。
- **限流**：`@RateLimiter` + Redisson **令牌桶**（`RedisUtils.rateLimiter`，`RedisUtils.java:50`）；`LimitType` 三维度靠 **key 拼不同内容**实现（`RateLimiterAspect.java:63-77`）。
- **幂等 ≠ 防重**：防重是"时间窗口去重"，幂等是"执行 N 次结果一致"；**本项目幂等靠业务层的"唯一约束 + 状态机"**。
- **坦白点**：① **`@RateLimiter` 全项目一处未用**（组件就绪、业务未启用）；② 限流异常抛的是 `RuntimeException`（`:59`）**会被当系统异常**，语义不精确；③ `RepeatSubmitProperties`（`@ConfigurationProperties("repeat-submit")`）**定义了但没任何地方注入**（遗留/未接线）；④ 防重的"成功/失败"判断**依赖返回值是 `R`**（`:100`），返回其他类型时语义失效；⑤ **唯一约束不是全表都有**（幂等的最后一道防线依赖开发者自觉）。
