# 第 1 章 · 权限体系总览

> **这一章是全卷的「地图」**。后面第 2~5 章会逐个拆开讲，但如果你先没这张地图，会看得云里雾里——因为「权限」这个词在后台系统里其实指**四件不同的事**。
>
> **本章第一次讲透**：① 权限体系回答的四个问题（认证 / 鉴权 / 数据权限 / 多点登录）；② RBAC 三层数据模型（用户 → 角色 → 权限）；③ 为什么「菜单」表同时管菜单、路由、权限（三合一）；④ 本项目对数据权限做的**双轨扩展**（`base` 标准轨 + 按业务模块自定义轨）。

## 一、这部分是做什么的？

### 零基础先补概念（30 秒）

> **① 角色（Role）**：岗位的抽象，比如「合同专员」「法务负责人」。权限不直接发给某个人，而是发给岗位。
>
> **② 多对多 / 中间表**：一个用户可以有多个角色，一个角色可以给多个用户。数据库里用一张只存「用户 id + 角色 id」的表表达这种关系，本项目叫 `sys_user_role`（建表语句 `script/sql/zxcm_init.sql:5021`）。`sys_role_menu`、`sys_role_dept` 同理。
>
> **③ 权限码**：一串普通文本，形如 `conf:signingSubject:add`，存在 `sys_menu.perms`（`SysMenu.java:120`）。接口上写「我需要这串文本」，用户登录时把「他拥有的所有文本」装进一个集合，鉴权就是判断「集合里有没有」。
>
> **④ 数据权限**：接口能进，不代表能看到所有数据行。同一句 SQL，不同角色会被自动加上不同的 `WHERE` 条件，这叫数据权限（第 4 章细讲）。本项目在 `sys_role` 上按业务模块平铺了 10 列来存这些范围（`SysRole.java:143-153`）。

### 1.1 「权限」其实是四个问题

新手最容易把「权限」当成一件事。其实在后台系统里，它拆成四件互相独立、一层层收窄的事：

| # | 问题 | 专业叫法 | 一句话 | 详解 |
|---|---|---|---|---|
| ① | **你是谁？** | 认证（Authentication） | 账号密码换成 token | 第 2 章 |
| ② | **你能不能调这个接口？** | 鉴权（Authorization） | token 里的权限码 vs 接口要求的权限码 | 第 3 章 |
| ③ | **你能看到哪些行数据？** | 数据权限（Data Scope） | 同一个接口，不同人查出不同数据 | 第 4 章 |
| ④ | **你能同时登录几个设备？** | 多点登录 | 同账号并发 / 互斥 / 顶下线 | 第 5 章 |

**四件事是递进的**：没通过 ①，②③④ 免谈；通过了 ① 但 ② 失败，接口直接拒绝（连 SQL 都不执行）；通过了 ②，③ 才在 SQL 层继续收窄你能看到的数据。④ 则是贯穿始终的「会话策略」。

### 1.3 RBAC：权限的三层数据模型

「谁有什么权限」这件事，本项目用 **RBAC（Role-Based Access Control，基于角色的访问控制）** 建模：**用户 → 角色 → 权限**。

```
sys_user ──sys_user_role──▶ sys_role ──sys_role_menu──▶ sys_menu
   (人)      (多对多)        (角色)      (多对多)        (菜单/按钮/权限码)
                                 │
                                 └──sys_role_dept──▶ sys_dept
                                     (数据权限范围：这个角色能看哪些部门)
```

**核心思想**：不直接给「人」配权限，而是给「角色」配权限，人再挂角色。

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么用 RBAC，而不直接给用户配权限？

因为**公司里同一岗位的人，权限是一样的**。

- 直接给用户配：一百个「合同专员」，得配一百遍；
- RBAC：给「合同专员」这个角色配一次，把一百个人挂上去，权限自动生效。

**RBAC 的核心价值不是「能不能管权限」，而是「权限的复用与维护成本」。** 新人入职 → 挂个角色；调岗 → 换角色；岗位权限变了 → 改角色的权限，所有在岗的人一起变。这一条在面试里几乎必答。

### 2.2 为什么「菜单表」同时管菜单、路由、权限？（三合一）

看 `SysMenu` 实体（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/entity/SysMenu.java:39`），一张 `sys_menu` 表里有这些字段：

| 字段 | 位置 | 作用 | 属于哪个视角 |
|---|---|---|---|
| `menuName` / `icon` / `orderNum` | `SysMenu.java:54/126/61` | 显示什么名字、图标、排第几 | **前端菜单** |
| `path` / `component` | `SysMenu.java:68/75` | 点击跳哪个路由、渲染哪个组件 | **前端路由** |
| `perms` | `SysMenu.java:120` | 权限码（如 `conf:signingSubject:add`） | **后端鉴权** |
| `menuType` | `SysMenu.java:101` | `M`目录 / `C`菜单 / `F`按钮 | 区分三者 |

**为什么三合一？** 因为这三件事**描述的本来就是同一个东西**：一个「功能入口」。你给「新增签约主体」配权限时，顺带就说清了「它在菜单里叫什么、点了跳哪、需要什么权限码」。拆成三张表，反而要维护三处关联。

**关键区分靠 `menuType`（`SysMenu.java:101`）**：

- `M`（目录）、`C`（菜单）→ 管**前端的路由与菜单显示**；
- `F`（按钮）→ 只管 `perms`，**不在前端显示**，纯给后端 `@SaCheckPermission` 用。

> **面试常问**：「按钮权限和菜单权限有什么区别？」——答：它们存在同一张 `sys_menu` 表里，靠 `menuType` 区分。菜单（`M`/`C`）会渲染成前端的菜单项；按钮（`F`）只提供 `perms` 权限码，供后端拦截器比对，前端则用 `v-hasPermi` 把没权限的按钮隐藏。

### 2.3 为什么权限码存数据库、不硬编码在代码里？

如果权限码写死在代码里（`@SaCheckPermission("sys:user:add")` 里的字符串是硬编码没错），但**「谁能用这个权限码」绝不能硬编码**——那要写死到数据库里：

- 管理员在「角色管理」页面给角色勾选权限 → 写 `sys_role_menu`；
- 给用户挂角色 → 写 `sys_user_role`；
- 登录时把该用户的权限码集合算出来，存进会话。

**这样运维人员不碰代码就能调权限。** 代码里只有「这个接口要求什么权限码」，**「谁能拥有这个权限码」完全由数据库决定**。这就是解耦。

### 2.4 为什么数据权限要做成「双轨」？（★本项目最重要的扩展）

这是本项目**对 RuoYi-Vue-Plus 的定制**，也是本卷最有价值的一个点。

**标准 RuoYi-Vue-Plus 只有一条轨**：`sys_role.data_scope` 一个字段决定这个角色的数据范围（`DataScopeType`，5 种：全部 / 自定义 / 本部门 / 本部门及以下 / 仅本人）。

**但合同系统的数据权限天然是「分模块」的**：同一份合同，用户 A 可能对**草拟中的合同**只能看本部门，对**审批完成的合同**却能看全部；对**台账**是只看本人，对**相对方**又是本部门。

一个 `data_scope` 字段根本表达不了。所以肇新原作者做了**双轨**：

| 轨 | 触发条件 | 用哪个枚举 | 数据来自角色哪个字段 |
|---|---|---|---|
| **标准轨** | `@DataPermission(resource = base)`（默认） | `DataScopeType`（5 种） | `sys_role.data_scope` |
| **自定义轨** | `@DataPermission(resource = xxx)` | `ContractPermission`（7 种） | `sys_role` 上**按模块分列**的字段 |

- **枚举 `DataPermissionResource`**（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/DataPermissionResource.java:22-32`）一共 11 个枚举值：`base`（默认轨）+ **10 个业务模块维度**——`draftPermission`（草拟中合同）、`contractPermission`（审批完成的合同）、`dashboardPermission`、`collabPermission`、`ledgerPermission`、`stampPermission`、`planPermission`、`comparePermission`、`partnerPermission`、`workPermission`。
- **`SysRole` 上就有对应的 10 个业务模块字段**（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/entity/SysRole.java:143-153`）——**每个模块一列**，`base` 轨不在实体上加列，而是复用已有的 `dataScope` 字段（`SysRole.java:87`）。
- **`ContractPermission`**（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/ContractPermission.java:36-66`）在标准 5 种之外，**多了 `MYDEPT`（6，我管理的部门）和 `MYDEPT_AND_CHILD`（7，我管理的部门及以下）**——因为合同系统里「部门负责人」是个高频角色。

**怎么读到「按模块的那一列」？** 靠**反射**：`PlusDataPermissionHandler.java:141` 用 `ReflectUtil.getFieldValue(role, dataPermission.resource().getIndex())`——按注解上的 `resource` 拼出字段名，从角色对象里取对应列的值。这就是 `DataPermissionResource` 注释里说的「**这里的 index 需要和 role 表的字段名一一对应**」（`DataPermissionResource.java:19-20`）。

#### 逐行读：一个真实的双轨注解

看 `zxcm-contract` 里合同草拟列表的 Mapper 方法（`zxcm-contract/src/main/java/com/ruoyi/contract/mapper/ContractDraftMapper.java:41-46`）：

```java
// 草拟阶段的列表查询,使用草拟人作为数据权限控制的逻辑
@DataPermission(value = {@DataColumn(key = "userId", value = "drafter_id")},
    resource = DataPermissionResource.draftPermission)
@Select("SELECT * FROM contract_draft ${ew.customSqlSegment}")
Page<ContractDraft> selectDraftPage(Page<ContractDraft> page,
    @Param(Constants.WRAPPER) Wrapper<ContractDraft> queryWrapper);
```

| 行号 | 代码 | 这一行在干什么、为什么这么写 |
|---|---|---|
| `:41` | 注释 | 说明这条查询属于「草拟阶段」，权限按「草拟人」判断。注释是给后来改代码的人看的，不参与运行。 |
| `:42` | `@DataPermission(value = {@DataColumn(key = "userId", value = "drafter_id")},` | `@DataPermission` 告诉 MyBatis-Plus 插件「这条 SQL 要加数据权限」。`@DataColumn` 有两件事：`key="userId"` 是 **SpEL** 模板里的变量名（SpEL 是 Spring 的表达式语言，写在模板里用 `#{...}` 取对象属性、调方法），`value="drafter_id"` 是数据库里代表「这条数据归谁」的列。 |
| `:43` | `resource = DataPermissionResource.draftPermission` | 选「自定义轨」：去 `sys_role` 的 `draft_permission` 列读这个角色对「草拟中合同」的范围，而不是读标准的 `data_scope`。 |
| `:44` | `@Select("SELECT * FROM contract_draft ${ew.customSqlSegment}")` | 正常写 SQL，但结尾用 `${ew.customSqlSegment}` 把 MyBatis-Plus 的条件构造器拼进来；数据权限插件会在执行前继续往这个 WHERE 里追加条件。注意 `${}` 是字符串替换，不是 `#{}` 预编译绑定。 |
| `:45-46` | 方法签名 | 返回 `Page` 表示分页查询；`@Param(Constants.WRAPPER)` 让条件构造器以 `${ew...}` 的形式可用。业务代码完全不用手写「部门/本人」过滤。 |

**一句话**：注解只声明「用哪个模块的权限、按哪一列认归属」，真正的 SQL 改写由插件统一做——这就是「对业务代码零侵入」。

**架构师的判断**：与其把「数据权限」做成一张通用的「权限规则表」（灵活但查询复杂、难缓存），不如**在角色表上按模块平铺成列**（不灵活但**读起来极快、结构一眼可见**，加一个模块就加一列）。**这是一种「用一点冗余换简单和性能」的取舍**——本项目模块数量可控，所以这个取舍划算。

## 四、怎么读怎么改

### 4.1 场景：给「签约主体」再加一个按钮权限

假设要在「签约主体」页加一个「导出」按钮，只有特定角色能用。要动的地方：

1. **数据库**：往 `sys_menu` 插一条 `menuType='F'` 的记录，`perms` 填如 `conf:signingSubject:export`，`parent_id` 指向「签约主体」那个菜单。
2. **后端**：在对应 Controller 方法上加 `@SaCheckPermission("conf:signingSubject:export")`。
3. **前端**：按钮上加 `v-hasPermi="['conf:signingSubject:export']"`。
4. **授权**：在「角色管理」页面给需要的角色勾上这个新权限（写 `sys_role_menu`）。

**注意第 4 步不是代码**——它是运维动作。**代码只声明「这个接口要什么权限码」，勾选权由数据库决定**（§2.3）。

### 4.2 场景：给数据权限加一个新模块维度

假设要给「发票」模块配独立的数据权限。按本项目的双轨设计：

1. **加枚举**：在 `DataPermissionResource.java:32`（最后一个枚举值 `workPermission`）后面加一个 `invoicePermission("invoicePermission", "发票数据权限")`；注意要把原来 `workPermission` 行尾的分号 `;` 改成逗号 `,`，新值末尾再用分号。
2. **加角色列**：给 `sys_role` 表加一列 `invoice_permission`（参考 `script/sql/zxcm_init.sql:4365-4374` 现有列的写法），并在 `SysRole.java:153`（最后一个 `workPermission` 字段）后加对应字段。
3. **使用**：在发票模块的 Mapper 方法上写 `@DataPermission(value = {...}, resource = DataPermissionResource.invoicePermission)`。

**这就是本项目「按模块平铺」设计的代价与便利**：加维度要动「枚举 + 表 + 实体」三处（不够灵活），但用起来只改一个注解参数（很方便读）。

### 4.3 动手验证：用 SQL 看见 RBAC 与「双轨」

> 连上项目库（本机学习环境通常是 `zxcm`，以 `application-dev.yml` 为准），逐条执行，对照预期。

1. **看见「用户 → 角色」这条边**：

   ```sql
   SELECT u.USER_NAME, r.ROLE_KEY, r.DATA_SCOPE,
   ```

## 五、一个操作的完整生命流程：登录后「我有哪些权限」怎么算出来

```
用户输账号密码 → POST /login                      SysLoginController → 第 2 章
  │
  ▼
校验通过 → 组装 LoginUser                          LoginUser.java
  │   ① 查 sys_user（这个人是谁）
  │   ② 查 sys_user_role → sys_role（他有哪些角色）
  │   ③ 查 sys_role_menu → sys_menu.perms（角色对应的权限码）
  │   ④ 查 sys_role_dept（角色的数据权限范围）
  ▼
LoginUser 里带上：
  ├─ menuPermission : Set<String>   权限码集合    LoginUser.java:95
  ├─ rolePermission : Set<String>   角色标识集合   LoginUser.java:100
  ├─ roles          : List<RoleDTO> 角色对象（数据权限要用）LoginUser.java:110
  ├─ roleId                         当前用于数据权限的角色  LoginUser.java:115
  └─ tenantId / userType            会话标识        LoginUser.java:120/60
  │
  ▼
StpUtil.login(...) → token 返回前端 → 存 Cookie（`zxcm-ui/src/utils/auth.js:3-7`，key `Admin-Token`）
  │
  ▼
后续每个请求带 token
  │
  ▼
SaInterfaceImpl 回调：
  getPermissionList() → loginUser.getMenuPermission()   ← 鉴权用（第 3 章）
  getRoleList()       → loginUser.getRolePermission()   ← 鉴权用
  │
  ▼
@SaCheckPermission("xxx") 比对权限集合 → 放行 / 拒绝
```

**关键点**：**权限码在「登录那一刻」就算好并缓存进会话了**，后续每次鉴权只是「内存里比对集合」，**不查数据库**。所以改角色权限后，通常要**让用户重新登录**（或触发会话刷新）才生效——这是所有 RBAC 系统的共性，不是缺陷。

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：你们系统的权限模型是什么？**

**RBAC（基于角色的访问控制）**，三层：用户 → 角色 → 权限。表上是 `sys_user` / `sys_role` / `sys_menu` 加两张关联表 `sys_user_role` / `sys_role_menu`。不直接给用户配权限，而是给角色配一次、用户挂角色——**核心价值是权限的复用与维护成本**。

**Q2：菜单权限、按钮权限、接口权限是什么关系？**

它们**存在同一张 `sys_menu` 表**里，靠 `menuType` 区分（`SysMenu.java:101`）：`M`目录 / `C`菜单会渲染成前端菜单并可配成路由；`F`按钮不进菜单，只提供 `perms` 权限码。后端接口上的 `@SaCheckPermission("xxx")` 就是拿这个 `perms` 去比对。前端再用 `v-hasPermi` 把没权限的按钮藏起来——但**前端藏按钮只是体验，真正的拦截在后端**。

> **追问：既然 M/C/F 都在一张表，后端查权限时怎么知道只取按钮的？** 它没有按 `menuType` 过滤——SQL 直接查该用户所有角色关联菜单的 `perms`（`ruoyi-base/ruoyi-system/src/main/resources/mapper/system/SysMenuMapper.xml:288-300`），然后在 Java 里丢掉空值、按逗号拆成集合（`ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysMenuServiceImpl.java:104-107`）。`M` 目录通常没配 `perms`，自然被丢掉。

**Q3：权限码是写死在代码里还是存数据库？**

**两头各一半**：「接口要求什么权限码」写在代码里（`@SaCheckPermission("conf:signingSubject:add")`）；**「谁能拥有这个权限码」完全存数据库**（`sys_role_menu`），由管理员在页面上勾选。这样调权限不用改代码、不用发版。

**Q4：用户在系统里的权限，是什么时候算出来的？**

**登录时**。登录成功组装 `LoginUser` 时，把该用户的权限码集合（`menuPermission`）、角色标识集合（`rolePermission`）、角色对象（`roles`，数据权限要用）一起算好放进会话（`LoginUser.java:95/100/110`）。之后每次鉴权只是**内存里比对集合，不查库**。副作用是：**改了角色权限要重新登录才生效**。

**Q5：你们的数据权限是怎么做的？**

分两轨。**标准轨**：`sys_role.data_scope` 一个字段 + `DataScopeType` 五种范围（全部/自定义/本部门/本部门及以下/仅本人）。**自定义轨**（本项目扩展）：因为合同系统要按模块区分数据权限（草拟中 / 审批完成 / 台账 / 相对方……各不相同），所以在 `sys_role` 上**按模块平铺成 10 列**（`SysRole.java:143-153`），配 `ContractPermission` 七种范围（比标准多了「我管理的部门」「我管理的部门及以下」）。**用哪个轨由 `@DataPermission` 注解的 `resource` 参数决定**。底层靠 JSqlParser **无痕改写 SQL 的 WHERE**，对业务代码零侵入。（详见第 4 章）

**Q6：为什么不把数据权限做成一张通用的「权限规则表」？**

通用规则表灵活，但**查询复杂、难缓存、难直观审计**。本项目选择**在角色表上按模块平铺成列**——加维度时要改「枚举+表+实体」三处（不灵活），但**读起来极快、结构一眼可见**，用起来只改一个注解参数。这是**「用一点冗余换简单和性能」**的取舍；本项目模块数量可控，所以划算。

**Q7：`sys_dept` 的树形结构怎么实现的？**

靠 `ancestors` 字段存「祖先链」（如 `0,100,101`）。查「某部门及以下」时用 `find_in_set` 判断某个祖先 id 是否在当前部门的 ancestors 里——见 `SysDataScopeServiceImpl.java:65` 的 `.or().apply("find_in_set({0},ancestors)", deptId)`。好处是**一次查询拿到整个子树，不用递归**；代价是移动部门时要批量更新祖先链。

### 本章答辩卡（追问级）

**卡 1：一个用户挂了两个角色，权限和数据范围分别怎么合并？**

**10 秒答案**：**权限码取并集**——菜单权限在 `SysPermissionService.java:64` 用 `addAll` 灌进同一个 `HashSet`，角色标识在 `:47` 同样 `addAll`。**数据范围也取并集**——查询类 SQL 会把每个角色的条件用 `OR` 拼起来，任一角色允许就能看到；但更新/删除类 SQL 用 `AND`，必须同时满足，防止越权改数据（`PlusDataPermissionHandler.java:125-126`）。

**证据**：`ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/service/SysPermissionService.java:41-49`、`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/handler/PlusDataPermissionHandler.java:125-126`、`:137`（遍历角色）。

**卡 2：`sys_role` 上 10 个数据权限列的默认值是什么？为什么？**

**10 秒答案**：初始化脚本里 `DRAFT_PERMISSION` 到 `PARTNER_PERMISSION` 这 9 列默认 `'5'`（仅本人），`WORK_PERMISSION` 默认 `NULL`（`zxcm_init.sql:4365-4374`）。默认最小权限，避免新建角色时误开全量数据；代码里反射取到空值会直接返回空条件（`PlusDataPermissionHandler.java:142-143`），等于不额外过滤，所以 `NULL` 的列要特别小心。

> 说明：`:143` 是 `return ""`，表示这条数据权限不追加条件；对 `workPermission` 这种默认 `NULL` 的列，效果就是「该模块不做数据过滤」。这是代码事实，不是推荐配置。

**证据**：`script/sql/zxcm_init.sql:4365-4374`、`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/handler/PlusDataPermissionHandler.java:141-143`。

**卡 3：给数据权限加一个新模块，为什么必须同时改「枚举 + 表 + 实体」？漏一处会怎样？**

**10 秒答案**：枚举的 `index` 字符串会被反射当作 `SysRole` 的字段名（`PlusDataPermissionHandler.java:141`），而 MyBatis-Plus 又把 `SysRole` 字段按驼峰转下划线映射到表列（`application.yml:221`）。漏枚举：注解里无法引用；漏实体字段：反射取不到、拼不出 SQL；漏表列：MyBatis 查询 `sys_role` 时报 `Unknown column`。三处是同一根链条。

**证据**：`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/DataPermissionResource.java:19-20`、`SysRole.java:143-153`、`ruoyi-admin/src/main/resources/application.yml:221`。

## 七、选型对比：权限方案的几条路

### 7.1 权限模型：RBAC vs 直接授权 vs ABAC

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 直接授权 | 用户 ↔ 权限 直接关联 | 最灵活、最细 | 维护成本爆炸 | 用户极少、权限极特殊 |
| **RBAC（本项目）** | 用户 → 角色 → 权限 | **复用强、维护成本低** | 角色爆炸（角色太多）时也会乱 | 绝大多数后台系统 |
| ABAC | 按属性动态判定（如「金额>10万且部门=财务」） | 极灵活 | 规则复杂、不可直观审计 | 策略多变的大型系统 |

**结论**：合同系统是「岗位驱动」的典型场景，RBAC 是正解。

### 7.2 权限码放代码 vs 放数据库

| 方案 | 优点 | 缺点 |
|---|---|---|
| 全放代码 | 改动可追溯、有版本 | 调权限要发版，运维碰不到 |
| **接口要求放代码 / 授权关系放数据库（本项目）** | 声明清晰 + 授权可运维 | 需要「重新登录」才刷新 |
| 全放数据库 | 最灵活 | 代码里出现魔法字符串、难静态分析 |

### 7.3 数据权限：插件改写 SQL vs AOP 手动拼条件

| 方案 | 优点 | 缺点 |
|---|---|---|
| AOP / 手动拼 where | 可控、直观 | 每个查询都要写、易漏、业务代码被污染 |
| **MyBatis-Plus 插件 + JSqlParser（本项目）** | **对业务代码零侵入**、一处注解全表生效 | 需理解插件与 SpEL、SQL 复杂时改写有风险 |

**结论**：本项目选插件方案，核心诉求是「**业务 SQL 保持纯净**」——业务开发只管写业务查询，数据范围由基座在底层无痕注入。
