# 附录 · 一个合同的完整生命周期与业务必修

> **这一篇解决什么问题**：三卷是按「知识块」写的，这一篇按「一条合同从生到死」把前后端、数据库、权限、状态串成一条线。
> 读完你应该能做到：**拿一张白纸，10 分钟画出合同系统的业务全景，并说清每一步对应哪个页面、哪个接口、哪张表、哪个状态字段。**
>
> **怎么用**：
> - 第一次读：先看 §一、§二，建立业务地图；再按 §三 逐阶段读，每个阶段回对应章节看代码。
> - 答辩前：只看 §四 状态矩阵、§七 业务问答、§九 一页速查。
> - 改代码前：在 §三 找到你要改的阶段，按「页面 → 接口 → 表 → 验证」的顺序定位。

## 一、先懂业务：合同系统到底在管什么

### 1.1 三个目标，决定所有设计

合同管理系统不是「把 Word 传到网上」这么简单。企业买它，通常为了解决三件事：

| 目标 | 具体表现 | 系统里的设计 |
|---|---|---|
| **风险控制** | 不该签的不能签、不该看的不能看、不该盖的章不能盖 | 审批流、权限码、数据权限、密级、双人复核 |
| **效率** | 少跑腿、少重复填、模板化、在线改 | 模板/条款/要素、在线编辑、编号自动生成、台账检索 |
| **留痕与审计** | 谁在什么时候改了什么、批了什么、盖了哪一版 | 版本表、节点日志、操作日志、历史不可变、归档 |

> **面试用法**：被问「为什么合同系统这么复杂」，先答这三个目标，再举一个本项目的设计（如「版本表就是为了留痕」）。

### 1.2 角色：谁在用这个系统

| 角色 | 典型动作 | 对应权限/页面 |
|---|---|---|
| **业务申请人 / 合同起草人** | 选主体、选合作方、起稿、传附件、发起审批 | 合同草拟、我的合同 |
| **部门负责人** | 审批本部门合同 | 待办、审批页 |
| **法务 / 合规** | 审条款、看风险、复核 | 审批页、复核、模板/条款 |
| **财务** | 看金额、发票、付款条件 | 合同详情、台账、报表 |
| **印章管理员** | 上传双章合同、用印 | 用印页 |
| **档案管理员** | 归档、借阅、台账 | 归档/台账（开源版部分只读） |
| **系统管理员** | 配菜单、角色、字典、流程、编号规则 | 系统管理、工作流设计器 |
| **老板 / 管理层** | 看统计、看进度 | 首页看板、报表 |

> 本项目用 **RBAC + 数据权限** 实现：角色决定「能进哪些菜单/按钮」，数据权限决定「进去后能看哪些行」。详见基座第 1/3/4 章。

### 1.3 十个业务术语（先混眼熟）

| 术语 | 一句话 | 本项目落点 |
|---|---|---|
| **签约主体** | 我方哪家公司签 | `conf_signing_subject`，后端第 1 章 |
| **合作方** | 对方公司/个人 | `conf_contract_counterpart`，后端第 2 章 |
| **合同类型** | 采购/销售/租赁/劳动合同等，树形分类 | `form` 表，后端第 4 章 |
| **编号规则** | 合同编号怎么生成（前缀+日期+流水） | `conf_bill_rule`，后端第 3 章 |
| **模板 / 条款 / 要素** | 合同正文模板、可复用条款、正文里可替换的字段 | `template_*`，后端第 7 章 |
| **草拟 / 草稿** | 合同还没进入审批的编辑态 | `contract_draft`，后端第 5 章 |
| **审批单** | 一次审批的档案快照，挂流程实例 id | `contract_audit_form`，后端第 6 章 |
| **用印 / 双章** | 双方盖章后的最终正本文件 | `FILE_TYPE_SEAL`、`uploadSealContract`，后端第 9 章 |
| **台账** | 已定稿合同的正式清单（可检索/导出） | `GET /contract/book/list`，后端第 9/10 章 |
| **归档** | 合同结束后封存，只读、可借阅 | `conf_archives`，后端第 9 章（开源版写接口缺失） |

### 1.4 先划边界：开源版做到了哪一步

**必须主动知道**，否则答辩时说错会减分：

| 能力 | 开源版状态 |
|---|---|
| 基础数据、草拟、审批、用印、台账、报表 | ✅ 有 Controller + 前端页面 |
| 模板、在线编辑（OnlyOffice） | ✅ 有，但 WPS 旧接口已不可用 |
| 归档 / 借阅 / 工作交接 | ⚠️ **只有 Service 层，没有 Controller 和前端页面** |
| 续期 | ⚠️ 后端接口有，**前端没有调用方** |
| 关闭合同 | ⚠️ 只有 Service 方法，**没有 Controller**，自动关闭任务也没接调度 |
| 变更 | ⚠️ 部分实现，细节见后端第 9 章坦白点 |

> 详见后端第 9 章 §2.7、附录 §五。**面试时主动说边界，比假装全做完可信。**

## 二、生命周期总图：一条合同的一生

```
① 基础数据准备
   签约主体（我方） + 合作方（对方） + 合同类型 + 编号规则
        │
        ▼
② 模板准备（可选，但企业版必用）
   模板 → 条款 → 要素；发布后才能被起草引用
        │
        ▼
③ 合同草拟
   选主体/合作方/类型 → 填基本信息 → 传附件 → 存草稿
   表：contract_draft + contract_draft_files
        │
        ▼
④ 发起审批
   选审批流程 → 生成审批单快照 → 启动 Activiti 流程实例
   表：contract_audit_form + act_ru_*；状态：审批中
        │
        ▼
⑤ 审批处理
   待办 → 同意/驳回/回退/转办/加签 → 流程结束
   表：act_ru_task / act_hi_*；状态：审批通过 / 不通过 / 撤销
        │
        ▼
⑥ 用印（签署）
   生成编号 → 上传双方盖章后的双章文件
   表：contract_draft_files（FILE_TYPE_SEAL）；状态：待签署 → 已签署/履行中
        │
        ▼
⑦ 履行 / 变更 / 续期
   到期提醒、变更单、续期（改 endTime）、续签（新合同 + 关联）
   表：contract_draft 的状态/时间字段 + contract_his
        │
        ▼
⑧ 作废 / 关闭
   未履行完可作废；履行完可关闭（开源版关闭无 Controller）
   状态：已作废 / 已结束
        │
        ▼
⑨ 归档
   封存正本与附件，只读、可借阅（开源版写接口缺失）
   表：conf_archives
        │
        ▼
⑩ 台账 / 报表 / 看板
   台账检索 + 导出；首页统计；待办角标
   接口：/contract/book/list、/contract/book/export、Dashboard
```

> **一条记忆口诀**：**主体对方定类型，编号模板起草案；审批用印再履行，变更续签到最后；作废关闭才归档，台账报表给老板。**

## 三、逐阶段拆解

> 每个阶段固定五栏：**业务问题 → 页面/接口 → 表/字段 → 设计取舍 → 验证/面试一句话**。
> 代码细节回对应章节，这里只给「串起来的地图」。

### 阶段 ① 基础数据：主体、合作方、类型、编号

**业务问题**：合同上必须写清「我方是谁、对方是谁、这是什么类型的合同、编号是什么」。这四样不先配好，合同没法起草。

| 项 | 页面 | 接口（示例） | 表 | 详见 |
|---|---|---|---|---|
| 签约主体 | `zxcm-ui/src/views/conf/signingSubject/index.vue` | `GET/POST /conf/signingSubject` | `conf_signing_subject` | 后端第 1 章 |
| 合作方 | `zxcm-ui/src/views/conf/contractCounterpart/index.vue` | `GET/POST /conf/contractCounterpart` | `conf_contract_counterpart` | 后端第 2 章 |
| 合同类型 | `zxcm-ui/src/views/system/form/index.vue` | `GET /system/form/list`、`GET /conf/treeSelect/contractTypeSelect` | `form`（自关联树） | 后端第 4 章 |
| 编号规则 | `zxcm-ui/src/views/conf/billRule/index.vue` | `GET/POST /conf/billRule` | `conf_bill_rule` + `conf_bill_rule_ext` | 后端第 3 章 |

**设计取舍（答辩点）**：

- **主体/合作方为什么把银行账号、联系人存 JSON 而不是子表？** 因为它们永远跟着主体一起读写，从不独立检索；建子表成本大于收益（后端第 1 章 §2.2）。
- **合同类型为什么是一张自关联树表，不是「大类表 + 小类表」？** 层级深度不固定，树表加节点不用改表结构（后端第 4 章 §2.1）。
- **编号为什么不用数据库自增？** 业务编号要带前缀/日期/分类，还要能预览、能补号；用 Redis + 规则表生成（后端第 3 章）。

**验证**：进「合同基础配置」四个菜单，各新增一条数据；查库确认 `del_flag=0`、`tenant_id` 有值。

**面试一句话**：基础数据是合同系统的「主数据」，设计重点是**引用完整性**（被引用的不能随便删）和**可配置**（类型/编号规则不写死在代码里）。

---

### 阶段 ② 模板、条款、要素（可选前置）

**业务问题**：企业不希望每次从空白 Word 起稿，而是用标准模板；模板里有些字段（甲方、金额、期限）要自动填。

| 概念 | 表 | 作用 | 详见 |
|---|---|---|---|
| 模板 | `template_contract` | 一份合同正文模板 | 后端第 7 章 |
| 条款 | `template_clause` / `template_clause_type` | 可复用条款片段 | 后端第 7 章 |
| 要素 | `template_element` | 正文里可替换的「占位」 | 后端第 7/8 章 |
| 发布态 | `template_contract` 状态字段 | 草稿/已发布/已停用；发布后不能直接改 | 后端第 7 章 §1.2 |

**设计取舍**：

- **发布后为什么不能直接改？** 已经有很多合同引用了它；直接改会让历史合同「静默变化」。要改就发新版本（后端第 7 章 §2.8）。
- **要素填充为什么用 Word contentControl，而不是后端替换 `{{占位符}}`？** Word 会把占位符拆成多个 run，POI 文本替换经常替换不到（后端第 8 章 §2.7）。

**验证**：模板列表看三态；发布一个模板；尝试编辑已发布模板，确认被拦。

**面试一句话**：模板体系的核心不是「存 Word」，而是**版本化 + 发布态 + 要素元数据**，保证「哪份合同用了哪一版模板」可追溯。

---

### 阶段 ③ 合同草拟：合同第一次进系统

**业务问题**：业务员选好主体/合作方/类型，填金额、期限、条款，传附件，存成草稿。

| 动作 | 接口 | 表 | 详见 |
|---|---|---|---|
| 上传附件 | `POST /conf/file/upload/{module}` | `conf_file` | 后端第 5 章 §5.1 |
| 新增合同 | `POST /contract/contractDraft` | `contract_draft` + `contract_draft_files` | 后端第 5 章 §5.2 |
| 合同详情 | `GET /contract/contractDraft/{id}` | 同上 | 后端第 5 章 §5.3 |
| 上传新版本 | `POST /contract/contractDraft/newVersion` | `contract_draft_files` 插新行 | 后端第 5 章 §5.6 |
| 版本历史 | `GET /contract/contractDraftFiles/fileVersions/{contractId}` | `contract_draft_files` | 后端第 5 章 §5.7 |

**关键设计：宽表 + 版本表**

- `contract_draft` 是**宽表**：把合同所有字段塞一张大表，因为字段稳定、总是一起读写。
- `contract_draft_files` 是**版本表**：每次上传新版本**插一行**，不覆盖旧行；因为合同是法律文件，历史必须留痕。
- 文件组 JSON（`fileGroupsJson`）：一个合同的多种文件（正文/附件/双章）塞进一个 JSON 字段，因为它们总是一起取，不单独检索。

**状态**：草稿阶段 `contractStatus = 拟定中`；审批中/已签署后不能直接改，只能发新版本。

**验证**：新增一份合同 → 查 `contract_draft` 一行、`contract_draft_files` 至少一行；再传新版本 → 版本表多一行、旧行还在。

**面试一句话**：草拟的关键取舍是「**宽表 vs 版本表**」——按变化频率拆：稳定的字段进宽表，会变的历史进版本表。

---

### 阶段 ④ 发起审批：从业务表跨到流程引擎

**业务问题**：起草人点「发起审批」，选一条流程（比如「部门负责人 → 法务 → 财务」），系统把任务派给第一个人。

| 动作 | 接口 | 表 | 详见 |
|---|---|---|---|
| 发起审批 | `POST /contract/contractAudit/beginAudit` | `contract_audit_form` + `act_ru_execution` / `act_ru_task` | 后端第 6 章 §5.1 |
| 我的待办 | `GET /activiti/process/taskList` | `act_ru_task` | 后端第 6 章 §5.2 |
| 审批历史 | `POST /activiti/process/listHistory` | `act_hi_*` | 后端第 6 章 §5.6 |
| 流程实例图 | `GET /activiti/process/designer/{instanceId}` | `act_ru_*` / `act_hi_*` | 后端第 6 章 §5.7 |

**两个桥接字段（必须记住）**：

- `contract_audit_form.instanceDefKey` → 用哪张流程图（`act_re_procdef`）；
- `contract_audit_form.instanceId` → 这次跑出来的流程实例（`act_ru_execution` / `act_hi_procinst`）。

**设计取舍**：

- **为什么审批单要存快照？** 审批的是「发起那一刻的合同内容」，后面合同改了也不能影响这次审批；快照保证可追溯。
- **为什么用 Activiti 而不是 if-else？** 审批规则经常变，画图改数据即可，不用改代码发版（后端第 6 章 §2.1）。
- **业务和引擎怎么解耦？** 业务侧发 Spring 事件，流程侧监听；两边不直接依赖（后端第 6 章 §4.3）。

**状态**：`contractStatus = 审批中`，`contractApproveStatus = 审批中`。

**验证**：发起审批后查 `contract_audit_form` 的 `instance_id` 不为空；查 `act_ru_task` 有一条当前待办。

**面试一句话**：发起审批的本质是「**业务快照 + 流程实例**」；业务表通过 `instanceId` 和引擎表桥接。

### 阶段 ⑤ 审批处理：同意、驳回、回退、转办、加签

**业务问题**：审批人打开待办，看合同和附件，决定同意/驳回；驳回退回起草人，同意流到下一个人，全部同意流程结束。

| 动作 | 接口 | 详见 |
|---|---|---|
| 同意 | `POST /activiti/process/complete` | 后端第 6 章 §5.3 |
| 驳回 | `POST /activiti/process/reject` | 后端第 6 章 §5.4 |
| 撤销申请 | `POST /activiti/process/cancelApply` | 后端第 6 章 §5.5 |
| 回退/转办/加签 | 流程服务内部方法 | 后端第 6 章 §4.7~4.11 |

**设计取舍**：

- **六个正交状态字段**：合同总状态/审批/用印/复核/变更/协同。为什么不是一个字段？因为一份合同可以同时「履行中 + 变更中」，一个字段表达不了（后端第 6 章 §1.2）。
- **状态约束散落在 Service 的 if 里**：这是「隐式状态机」，小系统够用，规模大了要引入显式状态机（后端第 6 章 §1.2 坦白点）。

**验证**：用两个账号走一遍「发起 → 同意 → 下一人 → 全部同意」；查 `contract_point_log` 是否有节点日志。

**面试一句话**：审批的动作是流程引擎的，业务状态是合同表的；两者通过事件和桥接字段同步，**不是一回事**。

---

### 阶段 ⑥ 审批通过 → 编号 → 用印

**业务问题**：所有人同意后，合同生成正式编号；业务员把双方盖章的「双章合同」扫描件传上来，合同进入履行。

| 动作 | 接口 | 表/字段 | 详见 |
|---|---|---|---|
| 审批通过自动生成编号 | 流程结束监听器 | `contract_draft.contract_code` | 后端第 3/6 章 |
| 上传双章合同 | `POST /contract/contractAudit/uploadSealContract` | `contract_draft_files`（`FILE_TYPE_SEAL`） | 后端第 9 章 §5.1 |
| 用印状态 | —— | `contract_stamped_status` | 后端第 6 章 §1.2 |
| 合同总状态 | —— | `contract_status`：待签署 → 已签署/履行中 | 后端第 6 章 §1.2 |

**设计取舍**：

- **为什么用印要单独传「双章文件」而不是在系统里 P 图？** 系统只存结果，盖章是线下/印章系统的事；双章文件是法律效力凭证。
- **为什么审批通过才生成编号？** 编号是正式合同的标识，草稿阶段不需要；避免废弃草稿占用号段（后端第 3 章）。

**验证**：审批通过后查 `contract_draft.contract_code` 是否从空变成正式编号；上传双章后查版本表是否多一条 `FILE_TYPE_SEAL`。

**面试一句话**：用印阶段的本质是「**把线下盖章结果回传系统**」，系统管的是文件版本和状态，不是盖章动作本身。

---

### 阶段 ⑦ 履行 / 变更 / 续期 / 续签

**业务问题**：合同生效后可能到期、要续、要改条款、要改金额。系统要能记录这些变化，并保留历史。

| 动作 | 实现 | 接口/表 | 详见 |
|---|---|---|---|
| 履行状态 | 按 `effectiveTime`/`endTime` 与当前时间算 | `getFulfilStatus` | 后端第 6 章 §1.2 |
| 变更 | 变更单 + 历史表 | `contract_his` / `contract_his_files` | 后端第 6/9 章 |
| 续期（改时间） | `endTime` 往后延 | `renew` / `renewInfo`（前端未接） | 后端第 9 章 §2.6、§4.8 |
| 续签（业务上是新合同） | 新起一份合同 + 关联老合同；**开源版只做了 `renewal`/`renewedStatus` 字段记录，没有自动新建合同** | `renewedStatus` 等字段 | 后端第 9 章 §2.6 |

**关键区分（高频追问）**：

- **续期 = 同一份合同改结束时间**，不产生新合同；
- **续签 = 新起一份合同**，通过关联字段指向老合同；
- **变更 = 改合同内容**，要留历史版本，不能覆盖。

**验证**：调续期预览接口看返回的新结束时间；确认前端没有调用方（这是坦白点）。

**面试一句话**：履行阶段的核心是「**时间驱动的状态 + 历史留痕**」；续期/续签/变更三个词不能混。

---

### 阶段 ⑧ 作废 / 关闭

**业务问题**：合同签错了、对方违约、或者履行完了，要结束它。

| 动作 | 接口 | 结果 | 详见 |
|---|---|---|---|
| 作废 | `POST /contract/contractAudit/cancelContract` | `contractStatus = 已作废`，保留数据 | 后端第 9 章 §5.2 |
| 回退草稿 | `POST /contract/contractAudit/backToDraft` | 作废的逆向操作 | 后端第 9 章 §5.4 |
| 关闭 | `closeContract`（**无 Controller**） | `contractStatus = 已结束` | 后端第 9 章 §4.7 |

**设计取舍**：

- **为什么作废不是删除？** 合同是法律文件，必须留痕；作废只是状态变化，数据还在。
- **为什么关闭没有 Controller？** 开源版裁剪/未接通；商业版可能由定时任务或后台触发（后端第 9 章坦白点）。

**验证**：作废一份合同，查 `contract_status` 变化、数据仍在；确认前端有作废按钮、没有关闭按钮。

**面试一句话**：作废/关闭都是「状态终结」，不是物理删除；区别是作废=无效，关闭=正常结束。

---

### 阶段 ⑨ 归档

**业务问题**：合同结束后封存，以后只能查/借阅，不能改。

| 项 | 说明 | 详见 |
|---|---|---|
| 归档表 | `conf_archives`（归档卷） | 后端第 9 章 §4.9 |
| 归档写操作 | Service 有 `batchArchiveStep1/2`，**无 Controller、前端只读** | 后端第 9 章 §2.7 坦白点③ |
| 借阅 | 开源版无完整实现 | 后端第 9 章 |

**设计取舍**：归档的本质是「**冻结 + 可检索**」；冻结靠状态/只读，检索靠台账和归档表。

**验证**：前端能看到归档名称，但找不到「执行归档」按钮——这是预期缺口。

**面试一句话**：归档不是「再存一份」，而是「**把合同置为只读并建立归档索引**」；开源版只完成了读侧。

### 阶段 ⑩ 台账 / 报表 / 看板

**业务问题**：老板要看「今年多少合同、多少金额、多少待办、多少到期」；业务员要按条件查合同、导出 Excel。

| 能力 | 接口 | 详见 |
|---|---|---|
| 台账列表 | `GET /contract/book/list` | 后端第 9/10 章 |
| 台账导出 | `POST /contract/book/export` | 后端第 10 章 §4.6 |
| 首页统计 | `GET /contract/dashboard/...`（多个 COUNT） | 后端第 10 章 §5.1 |
| 待办角标 | `GET /contract/dashboard/todoCount` | 后端第 10 章 §5.2 |
| 我的合同 | `GET /contract/dashboard/myContractList` | 后端第 10 章 §5.4 |

**设计取舍**：

- **台账不是一张表**：它是 `contract_draft` + 审批单 + 文件 + 主体/合作方的多表 JOIN 视图（后端第 10 章 §2.4）。
- **报表查询和业务查询不同**：报表要聚合、要跨模块、要导出，不能直接复用业务列表 SQL（后端第 10 章 §1.2 坦白点）。
- **首页 7 次 COUNT 可优化成一次 GROUP BY**：这是可以主动说的改进点（后端第 10 章 §2.8）。

**验证**：打开台账，按状态筛选、导出 Excel；看 Network 里的接口和返回字段。

**面试一句话**：台账是「**读视角**」，报表是「**聚合视角**」，看板是「**指标视角**」；三者都不改业务数据。

## 四、六个状态字段矩阵（答辩必背）

| 字段 | 管什么 | 典型值 | 谁会改 |
|---|---|---|---|
| `contract_status` | 合同总状态 | 拟定中 / 审批中 / 待签署 / 已签署 / 履行中 / 中止 / 已结束 / 已作废 | 审批、用印、作废、关闭 |
| `contract_approve_status` | 审批子状态 | 未审批 / 审批中 / 通过 / 不通过 / 撤销 | 流程监听器 |
| `contract_stamped_status` | 用印子状态 | 签署中 / 拒绝签署 / 签署完成 / 他人拒绝 | 用印接口 |
| `contract_review_status` | 复核子状态 | 复核中 / 复核失败 / 复核通过 | 复核接口 |
| `contract_change_status` | 变更子状态 | 未变更 / 变更中 / 已变更 / 变更失败 / 已撤回 | 变更流程 |
| `coordination_status` | 协同子状态 | 未协同 / 协同中 / 协同关闭 | 协同接口 |

> **为什么不是一个字段？** 因为状态是**正交**的：合同可以「履行中 + 变更中」，也可以「审批中 + 协同中」。一个字段只能表达一个维度。
> **前端显示的状态是算出来的**：`getContractStatusShow` 把六个字段 + 时间字段组合成一句给用户看的话，不是数据库里的一个字段。

## 七、业务必修问答（10 个必会）

**Q1：合同系统为什么需要版本表？直接覆盖不行吗？**

不行。合同是法律文件，必须知道「审批/盖章的是哪一版」。覆盖会让历史不可追溯；版本表每次插新行，旧版本永久保留。

**Q2：为什么合同有六个状态字段，而不是一个？**

因为状态是正交的：履行中可以有变更中，审批中可以有协同中。一个字段表达不了多个维度；前端显示的状态是组合计算出来的。

**Q3：审批流为什么用 Activiti，不用 if-else？**

审批规则经常变。画图改数据即可，不用改代码发版；引擎还提供待办、历史、流程图、转办/加签等能力。

**Q4：业务表和流程引擎表怎么关联？**

`contract_audit_form` 存 `instance_def_key`（哪张流程图）和 `instance_id`（这次流程实例）；业务侧通过这两个字段找到引擎里的任务和历史。

**Q5：为什么用印要单独传双章文件？**

系统不负责盖章，只负责保存盖章结果。双章文件是法律效力凭证，必须作为独立文件类型（`FILE_TYPE_SEAL`）留痕。

**Q6：续期、续签、变更有什么区别？**

续期=同一合同改结束时间；续签=新起一份合同并关联老合同；变更=改合同内容并留历史版本。

**Q7：台账和合同表是什么关系？**

台账不是一张独立的表，而是以 `contract_draft` 为主、JOIN 审批单/文件/主体/合作方的**读视图**；它面向检索和导出。

**Q8：归档做了什么？**

把合同置为只读并建立归档索引，保证以后只能查/借阅、不能改。开源版只完成了读侧，写接口缺失。

**Q9：为什么合同类型删除要发事件？**

因为合同类型被合同引用，删除前要跨模块校验引用完整性；发事件让「关心方」自己检查，避免合同模块反向依赖类型模块。

**Q10：这个项目最大的业务缺口是什么？**

归档/借阅/关闭的写链路没有接通（只有 Service），续期前端没接，变更细节不完整。这些是商业版裁剪留下的边界，答辩要主动说。

## 八、改造实验室：从「看懂」到「改得动」的 8 个练习

> 每个练习都给出**目标、改哪里、验收标准**。建议按顺序做，做完一个再下一个。

### 练习 1：给签约主体加一个「官网」字段

- **改哪里**：`conf_signing_subject` 加列 → `TSigningSubject.java` 加字段 → `TSigningSubjectBo/Vo` 加字段 → 前端表单加 `el-input` → 列表加一列。
- **验收**：新增/编辑能保存官网；列表能显示；查库字段有值。
- **考什么**：五件套 + 前后端字段对齐。

### 练习 2：给合同列表加一个「按金额区间筛选」

- **改哪里**：前端搜索区加两个输入框 → `queryParams` 加字段 → 后端 `buildQueryWrapper` 加 `ge/le` 条件。
- **验收**：输入 1000~5000，列表只剩区间内合同。
- **考什么**：`LambdaQueryWrapper` + 前后端参数传递。

### 练习 3：给合同类型树加一个「只显示启用」开关

- **改哪里**：后端树接口加 `status` 参数（已有）→ 前端加 `el-switch` → 传参。
- **验收**：开关切换，树只显示 `status=0` 的节点。
- **考什么**：树形查询 + 参数透传。

### 练习 4：给审批页加一个「抄送人」字段

- **改哪里**：审批单表加列 → Entity/BO/VO → 审批页表单 → 保存接口。
- **验收**：发起审批时能选抄送人，详情能看到。
- **考什么**：审批单快照 + 表单。

### 练习 5：把首页 7 次 COUNT 改成一次 GROUP BY

- **改哪里**：`DashboardController` 的统计方法 → 一条聚合 SQL → 返回 Map。
- **验收**：首页数字不变；SQL 日志从 7 条变 1 条。
- **考什么**：SQL 聚合 + 性能优化（答辩加分）。

### 练习 6：给台账导出加一列「合同状态」

- **改哪里**：导出 VO/ExcelBuilder 表头 + 数据组装。
- **验收**：导出的 Excel 多一列，值正确。
- **考什么**：EasyPOI/ExcelBuilder + 字典翻译。

### 练习 7：给合同列表加一个「批量作废」按钮

- **改哪里**：前端工具条加按钮 → 选中 ids → 调作废接口 → 后端支持批量。
- **验收**：勾选多条，批量作废成功；非法状态被拦。
- **考什么**：批量接口 + 状态校验 + 权限。

### 练习 8：把「续期」前端按钮接上

- **改哪里**：合同详情/台账加「续期」按钮 → 调 `renewInfo` 预览 → 调 `renew` 提交 → 刷新。
- **验收**：能预览新结束时间、提交后 `end_time` 变化。
- **考什么**：补全「后端有、前端没接」的链路（最能体现你读过源码）。
