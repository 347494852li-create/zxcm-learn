# 第 4 章 · 基础数据管理页面

> 上一章讲了「标准 CRUD 骨架」。这一章拿**四个真实页面**来验证它，并告诉你**同一套骨架是怎么长出四种不同形态的**。这四页是全站最简单的页面，也是你「读页面的练手区」——把这四页读透，后面第 5~10 章的复杂页面都是它们的叠加。

| 页面 | 文件 | 形态 | 骨架变体 |
|---|---|---|---|
| 签约主体 | `zxcm-ui/src/views/conf/signingSubject/index.vue` | 标准 CRUD | **正面教材**，最标准 |
| 合作方 | `zxcm-ui/src/views/conf/contractCounterpart/index.vue` + `edit.vue` | CRUD + 表单抽子组件 | **拆分变体** + 行级权限 |
| 编号规则 | `zxcm-ui/src/views/conf/billRule/index.vue` | 无表格、无分页 | **规则编辑器**（完全另一种） |
| 合同类型 | `zxcm-ui/src/views/system/form/index.vue` | 树表 | **树形变体**（用原生 el-table） |

> **零基础先补概念（前端视角）**
>
> - **`el-form` + `v-model`（表单与双向绑定）**：`el-form` 是 Element UI 的表单容器；里面的输入框用 `v-model` 把自己的值和 `data()` 里的字段绑在一起——输入框一改，字段就变；字段一变，输入框也变。本项目签约主体的搜索框就是 `v-model="queryParams.signingSubjectName"`（`zxcm-ui/src/views/conf/signingSubject/index.vue:36`）。语法见《Vue2 从 0 到精通》第 2 章 §5.1。
> - **`el-table` + `slot-scope`（表格与作用域插槽）**：`el-table` 把数组渲染成一行一行；`slot-scope="scope"` 让你在某一列里拿到「这一行的数据」`scope.row`，从而自定义这一列怎么显示。合作方的「纠纷状态」列就是用 `scope.row.disputeStatus` 决定显示「有纠纷 / 无纠纷」（`zxcm-ui/src/views/conf/contractCounterpart/index.vue:243-252`）。语法见《Vue2 从 0 到精通》第 2 章 §10、第 4 章 §8.3。
> - **父子组件通信：`ref` + `$emit`**：父组件给子组件写 `ref="edit"`，就能直接调用子组件的方法；子组件用 `this.$emit('getList')` 告诉父组件「我改完了，刷新一下」。合作方页的列表和表单就是这么配合的（`zxcm-ui/src/views/conf/contractCounterpart/index.vue:359`、`edit.vue:705/715`）。语法见《Vue2 从 0 到精通》第 4 章 §5.2、§9.1。
> - **动态表单（数组驱动界面）**：界面行数不写死，而是用 `v-for` 遍历一个数组；点「添加一行」就往数组 `push` 一项，点「删除」就 `splice` 一项，Vue 会自动重画。编号规则页的规则行就是这个套路（`zxcm-ui/src/views/conf/billRule/index.vue:48-94,282-289`）。语法见《Vue2 从 0 到精通》第 2 章 §7.1。

## 一、这部分是做什么的

这四页是**合同系统的「基础配置数据」**——在上层业务（草拟、审批）跑起来之前，得先把这些「字典一样的东西」配好：

- **签约主体**：我方公司/主体（合同上的「甲方」），带银行账户、联系人。
- **合作方**：对方公司（「乙方」），带争议状态、合作方类型。
- **编号规则**：合同编号怎么生成（如 `HT-2026-0001` 里 `HT` 是前缀、年份、流水号）。
- **合同类型**：合同分类的**树**（如「采购合同 → 框架采购 / 单项采购」），并绑定审批流程。

**一句话定位**：这四页是「合同生命周期的上游配置」。**它们本身不参与合同流转，但上层每个合同都要引用它们的数据。**

> 后端对应：签约主体见[后端重塑版 第 1 章](../后端重塑版/第1章-签约主体管理.md)、合作方见[第 2 章](../后端重塑版/第2章-合作方管理.md)、编号规则见[第 3 章](../后端重塑版/第3章-编号规则.md)、合同类型见[第 4 章](../后端重塑版/第4章-合同类型配置.md)。

## 二、站在架构师角度，为什么这么设计

### 2.1 为什么基础数据页都长得一样（这本身是设计）

四个页面，三个是「搜索 + 表格 + 弹窗」，长得几乎一样。**这不是偷懒，是刻意统一**：

- 用户学一次就会用所有页面（心智统一）。
- 开发复制粘贴改改就行（效率）。
- 脚手架工具（RuoYi 代码生成器）能批量生成。

**所以「基础数据页」的正确读法是**：**先认死一个骨架，再看每页「哪里不一样」**。下面每页我只讲**不一样的地方**。

### 2.2 为什么合作方要把表单抽到 `edit.vue`

看合作方页的目录：`index.vue`（655 行）+ `edit.vue`（825 行）。

**为什么拆**：合作方表单**特别长**（企业信息 + 法人 + 联系人 + 银行 + 争议状态……），如果塞进 `index.vue`，`index.vue` 会变成 1500 行的「巨无霸」，难维护。拆成 `<edit>` 子组件后：

- `index.vue` 只管**列表**（搜索/表格/分页）。
- `edit.vue` 只管**表单**（新增/修改/查看三种模式）。
- 两者靠 **`<edit ref="edit" @getList="getList" />`**（`zxcm-ui/src/views/conf/contractCounterpart/index.vue:359`）通信——子组件做完事，`$emit('getList')` 通知父组件刷新列表。

**这是「组件拆分」的经典案例**，答辩点：**「表单过长时抽成子组件，父组件用 `ref` 调方法把 `row` 传进去、子组件用 `$emit` 通知刷新」**。注意这里**没有用 props**——`edit.vue` 不声明任何 props，数据是通过方法参数传的（这是 `ref` 通信方式，和 props 的区别见《Vue2 从 0 到精通》第 4 章 §9.2）。而且 `edit.vue` 用 `showAddMode/showUpdateMode/showViewMode` 三种模式复用**同一个表单**——父组件在 `zxcm-ui/src/views/conf/contractCounterpart/index.vue:504/508/512` 分别调用它们，三个方法的定义在 `zxcm-ui/src/views/conf/contractCounterpart/edit.vue:583/590/615`。**新增/修改/查看共用一个模板，只切换是否可编辑**（查看模式由 `viewDisabled()` 把表单置灰并隐藏删除图标，`edit.vue:683-686`），避免写三份几乎一样的表单。提交成功后子组件在 `edit.vue:705` 和 `:715` 两次 `$emit('getList')`，分别对应「修改成功」和「新增成功」。

### 2.3 为什么合作方有「行级按钮权限」，别的页没有

看合作方页的操作列（`zxcm-ui/src/views/conf/contractCounterpart/index.vue:268-290`），实际代码是**两个「修改」按钮**：

```vue
<el-button
  v-hasPermi="['conf:contractCounterpart:query']"
  size="mini"
  type="text"
  icon="el-icon-search"
  @click="handleView(scope.row)"
>查看</el-button>
<el-button
  v-if="scope.row.contractCounterpartHead == userInfo.userId"
  v-hasPermi="['conf:contractCounterpart:edit']"
  v-notHasPermi="['conf:contractCounterpart:allEdit']"
  size="mini"
  type="text"
  icon="el-icon-edit"
  @click="handleUpdate(scope.row)"
>修改</el-button>
<el-button
  v-hasPermi="['conf:contractCounterpart:allEdit']"
  size="mini"
  type="text"
  icon="el-icon-edit"
  @click="handleUpdate(scope.row)"
>修改</el-button>
```

**读法**：第一个「修改」按钮同时满足三件事才显示——① `v-if` 判断「这一行的负责人就是当前登录人」（`contractCounterpartHead == userInfo.userId`）；② 有普通编辑权限 `edit`；③ **没有** `allEdit`（全量编辑）权限。第二个「修改」按钮只要有 `allEdit` 就显示。合起来就是：**没有 `allEdit` 权限的人，只能改自己负责的合作方；有 `allEdit` 权限的人，能改所有人的。** 这里用的是 `v-notHasPermi`（第 2 章讲的「反权限」指令）——本项目**唯一**用它的地方就是这里（全仓只有 `index.vue:225` 和 `:278` 两处）。

**逐行读这段按钮代码**：

1. `v-hasPermi="['conf:contractCounterpart:query']"`：没有查询权限就连「查看」都不显示。`v-hasPermi` 是自定义指令，权限码不在用户权限集合里时直接把元素移除（见《Vue2 从 0 到精通》第 2 章 §9.2）。
2. `@click="handleView(scope.row)"`：`scope.row` 是当前表格行数据；点击后把整行交给 `handleView`（定义在 `index.vue:511`），后者再调子组件 `showViewMode(row)`。
3. `v-if="scope.row.contractCounterpartHead == userInfo.userId"`：这是**行级**判断，不是权限码。`userInfo` 来自 Vuex（`index.vue:429` 的 `mapGetters(['userInfo'])`），`contractCounterpartHead` 是这行数据的负责人 ID。
4. `v-hasPermi="['conf:contractCounterpart:edit']"`：第二个条件——用户得有「编辑合作方」这个功能权限。
5. `v-notHasPermi="['conf:contractCounterpart:allEdit']"`：第三个条件——用户**不能**有「全量编辑」权限。三条合起来，才是「普通业务员改自己的」。
6. `@click="handleUpdate(scope.row)"`：两个按钮最后都走同一个方法（`index.vue:507`），真正决定能不能改的是**显示条件**和后端数据权限。
7. 第二个按钮只写 `v-hasPermi="['conf:contractCounterpart:allEdit']"`：有全量编辑权限的管理员，不要求是负责人本人。
8. 状态开关也用了同一套思路：有 `allEdit` 时显示可操作的 `el-switch`（`:218-224`），没有时只显示只读标签（`:225-234`）。

**为什么这么设计**：合作方是共享数据，普通业务员只能维护自己负责的；管理员要能维护全部。所以按钮的**显示**分两种情况。真正的数据隔离在后端（[后端重塑版 第 2 章](../后端重塑版/第2章-合作方管理.md)的数据权限 `@DataPermission`）。

> ⚠️ **坦白点**：`v-notHasPermi` 只控制**按钮显示**，前端**没有**在前端层面强制「只能改自己的」——`handleUpdate(row)` 点开就能改（`:282` 和 `:289` 指向同一个方法）。真正的隔离靠后端数据权限。**前端这份是「体验提示」，不是「安全边界」**。

### 2.4 为什么编号规则页**完全没有表格**

看 `zxcm-ui/src/views/conf/billRule/index.vue` 的结构：**没有搜索区、没有 JTable、没有分页、没有权限按钮**（`:3` 起直接是 `el-tabs`）。

**为什么**：编号规则不是「一堆数据」，而是「**一组配置项**」——每个业务类型（如「合同编号」「审批单号」）有**一条规则**，规则由「前缀 + 日期格式 + 流水号」这样**可动态增删的片段**组成。

所以它的形态是：
- `el-tabs`（`:3-14`）——每个 tab 是一种编号类型。
- 一个规则编辑器（`:16-157`）——动态增删「规则行」。
- 一个保存按钮（`:138-142`）。

**这是「数据形态决定界面形态」的例子**：规则是**结构化的配置**，用表格反而别扭，用「配置表单」才对。**答辩点**：别以为后台系统全是表格，**「配置型数据」用表单、「列表型数据」用表格**。

### 2.5 为什么合同类型用原生 `el-table` 而不是 `JTable`

看 `zxcm-ui/src/views/system/form/index.vue:72-121`——用的是 **`<el-table>` 原生**，还带了 `:tree-props="{children:'children'}"`（`:78`）。

**为什么不用 `JTable`**：
- 更准确地说：`JTable` **并不是不能做树表**——它本身就是对 `el-table` 的薄封装，并且把 `treeProps`、`rowKey` 暴露成了 props（`zxcm-ui/src/components/JTable/index.vue:2-12,55-63`）。所以「JTable 不支持树形」这个常见说法是**不准确的**。
- 合同类型页直接用原生 `el-table`，真实原因是：这页不需要 `JTable` 默认带的「序号列 / 统一高度 / 布局修复」，又需要 `row-key` + `tree-props` 直接控制树形展开；页面本身也不分页（`:72-121` 里没有 `pagination`）。用原生写法更直接。
- 合同类型数据是**树**（「采购合同」下面有子类型），所以必须配 `row-key` + `tree-props`（`system/form/index.vue:76-78`）。

**答辩点**：**「JTable 是通用列表封装，也能通过 treeProps/rowKey 渲染树；但树表、弹窗小表这类页面，直接用 el-table 少一层间接、更直观」**——封装是为了复用，不是为了「到处都用」。这也是第 3 章 §7.3 说的权衡。

### 2.6 合同类型为什么还牵扯「选流程」

看 `zxcm-ui/src/views/system/form/index.vue:195` 的 `<flowPane>` 和 `:467` 的 `choiceFlow`——**新增合同类型时要选一个审批流程**（Activiti 流程定义）。

**为什么**：合同类型决定「这类合同走哪套审批流」——采购合同走采购流程、销售合同走销售流程。所以合同类型页在保存前要**弹一个「选流程」面板**，让用户从工作流设计器里已发布的流程中选一个。

这就把**基础数据页**和**工作流**（第 10 章）连上了。**读这页时注意**：`getWorkflowName(code, 'audit')`（`:492`）就是去后端查「这个类型配的审批流程叫什么」。

## 六、面试高频问题

**Q1：基础数据管理页你是怎么做的？**
A：都套同一个 CRUD 骨架：搜索区 + 工具条 + `JTable` 表格 + `Pagination` 分页 + `el-dialog` 新增/编辑弹窗。如签约主体（`zxcm-ui/src/views/conf/signingSubject/index.vue`）、合作方（`zxcm-ui/src/views/conf/contractCounterpart/index.vue`）。

**Q2：表单太长怎么处理？**
A：像合作方那样**抽成子组件**。`index.vue` 管列表，`edit.vue` 管表单，父组件用 `ref` 调子组件的 `showAddMode/showUpdateMode/showViewMode`，子组件提交完 `$emit('getList')` 通知父组件刷新。而且三种模式**共用同一个表单模板**，避免写三份。
**追问：查看模式怎么做到只读？** 答：调 `showViewMode(row)` 时先执行 `viewDisabled()`（`edit.vue:683-686`），把 `formDisabled` 设为 `true`（所有输入框禁用）并把 `viewShow` 设为 `false`（隐藏添加/删除图标）；只读不是另写一份模板。

**Q3：为什么有的页面用 `JTable`，有的用 `el-table`？**
A：`JTable` 是对 `el-table` 的薄封装（默认序号列、统一高度、`doLayout` 等），并且也暴露了 `treeProps`/`rowKey`，所以它**能做树表**。合同类型页直接用原生 `el-table`，是因为这页要精确控制树形展开且不需要分页/默认序号，原生写法更直接。封装是为了复用，不是到处硬套。

**Q4：`v-notHasPermi` 是啥？什么时候用？**
A：和 `v-hasPermi` 相反——**没有**该权限才显示。本项目只在合作方页用（`contractCounterpart/index.vue:225,278`），实现「没有『全量编辑』权限的业务员只能操作自己的数据」这类行级展示差异。

**Q5：怎么控制「普通用户只能改自己的数据」？**
A：分两层。**前端**只在按钮显示上做提示（`v-notHasPermi`/`row.owner == currentUser`）；**真正隔离在后端**——后端合作方列表用了数据权限（`@DataPermission`），只返回当前用户有权限的数据。**前端不做安全，后端兜底**。（后端见[后端重塑版 第 2 章](../后端重塑版/第2章-合作方管理.md)）

**Q6：编号规则页为什么没有表格？**
A：因为编号规则不是「一堆记录」，而是「一组结构化配置」（前缀+日期+流水号片段）。数据形态是配置，就用「tabs + 表单编辑器」，用表格反而别扭。**数据形态决定界面形态。**

**Q7：动态增删规则行是怎么实现的？**
A：往数组里 push/splice。`addNewLine(data)` 往 `data.ruleArray` push 一行，`deleteLine(data,index)` splice 掉一行，Vue 响应式自动重渲染列表（`billRule/index.vue:282,287`）。

**Q8：合同类型为什么要选审批流程？**
A：合同类型决定「这类合同走哪套审批流」。所以新增合同类型时要绑定一个已发布的流程（Activiti 流程定义），弹 `<flowPane>` 让用户选（`system/form/index.vue:195,467`）。之后草拟合同时选了该类型就自动走这套流程。

**Q9：签约主体的「银行账户」是数组，怎么和后端交互的？**
A：后端字段存的是 JSON 字符串，前端**提交前** `JSON.stringify(array)`（`zxcm-ui/src/views/conf/signingSubject/index.vue:801-802`），**拉回来后** `JSON.parse(str)`（`:775-785`）。这是前后端数据结构的一个约定，容易踩坑。

**Q10：这四个页面哪几行代码最值得看？**
A：① 合作方的 `<edit ref="edit" @getList="getList" />`（`zxcm-ui/src/views/conf/contractCounterpart/index.vue:359`）——父子组件通信；② `edit.vue` 的三模式复用（定义在 `:583/590/615`）；③ 编号规则的 `addNewLine/deleteLine`（`zxcm-ui/src/views/conf/billRule/index.vue:282,287`）——动态表单；④ 合同类型的树表配置（`zxcm-ui/src/views/system/form/index.vue:78`）——`tree-props`。

### 本章答辩卡（追问级）

**卡 1：合作方页两个「修改」按钮，前端到底用什么条件区分「改自己的」和「改所有人的」？**
10 秒答案：两个按钮都调同一个 `handleUpdate`。普通按钮要求「负责人是当前用户 + 有 edit 权限 + 没有 allEdit 权限」三条同时成立；管理员按钮只要求有 allEdit 权限。前端只控制显示，真正的数据隔离在后端。
证据：`zxcm-ui/src/views/conf/contractCounterpart/index.vue:275-290`；`userInfo` 来自 `:429`；后端 `@DataPermission` 见《后端重塑版》第 2 章。

**卡 2：签约主体提交时，银行账户和联系人字段发出去是什么类型？为什么？**
10 秒答案：发出去是 JSON 字符串，不是数组。表单里为了动态增删用数组，提交前 `JSON.stringify` 两个数组；后端字段按字符串存，回显时再 `JSON.parse` 并兜底空数组。
证据：`zxcm-ui/src/views/conf/signingSubject/index.vue:801-802`（提交）、`:775-785`（回显）。

**卡 3：合同类型页为什么不能用 `JTable`？树表的数据从哪来？**
10 秒答案：`JTable` 面向平面列表和分页，树形数据要靠原生 `el-table` 的 `row-key` + `tree-props` 才能展开子节点。后端返回的是平铺数组，前端用 `handleTree` 按 `id/parentId` 组装成树。
证据：`zxcm-ui/src/views/system/form/index.vue:72-78`（`row-key`/`tree-props`）、`:298`（`handleTree(response.data, 'id', 'parentId')`）。

## 七、选型对比

### 7.1 单文件页面 vs 拆分组件

| | 全塞一个 `.vue` | 拆 `index` + `edit`（合作方做法） |
|---|---|---|
| 文件大小 | 大（1500+ 行） | 适中（各 600-800） |
| 可维护 | 差 | 好 |
| 通信成本 | 无 | 要 props/$emit |

**结论**：**表单短就一个文件，表单长就拆**。合作方表单字段太多，拆了；签约主体相对简单，就没拆。判断标准是「文件会不会长到难读」。

### 7.2 配置型数据：表格 vs 表单编辑器

| | 表格 | 表单编辑器（编号规则做法） |
|---|---|---|
| 适合 | 多条同构记录 | 一组结构化配置 |
| 增删行 | 表格行增删 | 表单行增删 |
| 编号规则 | 不自然（只有几条） | ✅ 自然 |

**结论**：看数据是「多条记录」还是「一组配置」。编号规则是后者，所以用表单编辑器。

### 7.3 树表：`JTable` vs 原生 `el-table`

| | `JTable` | 原生 `el-table` + `tree-props` |
|---|---|---|
| 平面列表 | ✅ 首选 | 也行，但少序号列等便利 |
| 树形数据 | ✅ 可以通过 `treeProps`/`rowKey` 支持 | ✅ 直接写，少一层封装 |
| 分页 | 页码组件仍要单独放 `pagination` | 树表一般不分页 |

**结论**：树表两种都能做。本项目合同类型页选原生 `el-table`，主要是这页不分页、又需要直接控制树形展开，原生写法更直观；这不是能力限制，而是取舍。

## 本章小结

- 四个基础数据页 = 同一套 CRUD 骨架的**四种变体**。读法是「先认骨架，再看差异」。
- **签约主体**：最标准的 CRUD 正面教材；注意 JSON 字符串字段、`handleExport` 是死代码。
- **合作方**：表单抽 `edit.vue`（三模式复用），行级权限用 `v-notHasPermi`；**前端只管显示，隔离靠后端**。
- **编号规则**：无表格，是「tabs + 动态表单」（`addNewLine`/`deleteLine`）。配置型数据用表单。
- **合同类型**：原生 `el-table` 树表 + 绑审批流程（连第 10 章）。
- 通用规律：**数据形态决定界面形态**；表单长了就拆组件。
