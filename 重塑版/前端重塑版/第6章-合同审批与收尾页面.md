# 第 6 章 · 合同审批与收尾页面

> 这是全站**业务最复杂**的前端页面族。核心难点只有一个：**同一个合同列表，根据合同当前状态，显示完全不同的按钮**——审批中的能「撤销审批」，审批失败的能「重新编辑」，已盖章的能「作废」，等等。理解了这个「**按钮状态机**」，这一章就通了。

---

## 一、这部分是做什么的

合同草拟完成后进入**后半段**：审批 → 用印 → 收尾（作废/跟踪/归档）。对应目录 `src/views/contract/contractAudit/`：

| 文件 | 行数 | 干什么 |
|---|---|---|
| `index.vue` | 37 | 审批页的外壳（套一个 `<left>` + 内容） |
| `left.vue` | 61 | 左侧分类（按状态筛选） |
| `auditList.vue` | **1046** | **审批/合同列表 + 全部操作按钮**（核心） |
| `uploadSealFile.vue` | 246 | **上传双章合同**弹窗 |
| `trace.vue` | 258 | **合同跟踪**（备注时间轴） |
| `contractCancel.vue` | 85 | **作废**填理由弹窗 |

另有：
| 文件 | 干什么 |
|---|---|
| `contractAuditForm/index.vue`（739） | 审批表单**模板**管理（标准 CRUD） |
| `book/index.vue`（411） | **合同台账**（收尾后的只读视图，第 9 章后端） |

> **零基础先补概念（前端视角）**
>
> - **`v-if` / `v-show`（条件渲染）**：`v-if` 是「条件不成立就把这个节点从 DOM 里删掉」，`v-show` 是「只改 `display:none`，节点还在」。审批列表的按钮用的是 `v-if`——没有权限/状态不对时，按钮根本不会渲染出来（`zxcm-ui/src/views/contract/contractAudit/auditList.vue:334-354`）。区别见《Vue2 从 0 到精通》第 2 章 §6.2。
> - **权限指令 `v-hasPermi`**：它不是一个普通属性，而是项目注册的自定义指令。指令拿到你的权限码数组，和当前用户的权限集合比对；不匹配就把元素移除。所以「按钮能不能看见」是前端算出来的（`auditList.vue:363,391,443`）。原理见《Vue2 从 0 到精通》第 2 章 §9.2。
> - **父子组件 `ref` 调用**：父页面在模板里写 `<trace ref="trace" />`，就能在方法里执行 `this.$refs.trace.showRemarks(...)` 直接调子组件方法。合同跟踪、上传双章、作废三个弹窗都是这么打开的（`auditList.vue:576-579`、`:937-939`、`:963-965`、`:1017-1019`）。原理见《Vue2 从 0 到精通》第 4 章 §9.1。
> - **「状态字段驱动界面」**：同一行合同数据里有 `contractStatus`、`contractApproveStatus`、`contractStampedStatus` 等状态字段；模板用这些字段组合出 `v-if` 条件，决定这一行显示哪组按钮。可以把它想成前端的**按钮状态机**：状态是输入，按钮是输出（状态组合见 §4.1 表）。

> 后端对应：[后端重塑版 第 6 章（审批流）](../后端重塑版/第6章-审批流与事件状态机.md) + [第 9 章（用印·作废·续签·归档）](../后端重塑版/第9章-用印·作废·续签·归档.md)。

## 二、站在架构师角度，为什么这么设计

### 2.1 核心设计：一个列表页里的「按钮状态机」

打开 `zxcm-ui/src/views/contract/contractAudit/auditList.vue` 的操作列（`:328-504`），你会看到**同一个位置塞了十几个按钮**，每个按钮外面都套着 `v-if`——**根据 `scope.row` 的状态和权限，决定显示哪几个**。

这是一个**有限状态机**的界面表达：

```
状态组合（字段真实取值）                                   →  能看到的按钮（除“查看合同/合同跟踪”外）
──────────────────────────────────────────────────────────────────────────
contractStatus=3 且 contractApproveStatus=1（审批中）     →  撤销审批 / 前往修订（二选一）
contractStatus=3 且 contractApproveStatus=3（审批失败）   →  重新编辑 / 作废（删记录）
contractStatus=3 且 contractApproveStatus=2（审批通过）   →  下载文档 / 上传双章合同
contractStatus=4 且 contractStampedStatus=1（盖章中）     →  下载文档 / 上传双章合同
contractStatus=4 且 contractStampedStatus=2（已盖章）     →  上传双章合同 / 作废（填理由）
contractStatus=4 且 contractStampedStatus=3（拒绝盖章）   →  重新编辑
contractStatus=5 且 contractReviewStatus=5（复核失败）    →  上传双章合同
```

「撤销审批」和「前往修订」二选一，由 `isEditNode(row)` 判断当前审批任务是不是「起草人节点」（`auditList.vue:747-752`）：是起草人节点就显示「前往修订」，否则显示「撤销审批」。

**为什么这么设计**：合同每个阶段能做的动作不同，**用一个列表页 + 状态驱动按钮**，比「每个状态一个页面」省得多，用户也只需要熟悉一个列表。

**这是本章最大的答辩点**：**「审批列表用『状态 + 权限』双条件驱动按钮的显示，本质是前端的状态机」**。

### 2.2 为什么按钮的显示要「状态 + 权限」双条件

看这些按钮的写法（`zxcm-ui/src/views/contract/contractAudit/auditList.vue`）：

| 行号 | 按钮 | 条件 |
|---|---|---|
| `:363-367` | 重新编辑 | `v-if`（审批失败状态）+ `v-hasPermi(['...:backToDraft'])` |
| `:391-395` | 上传双章合同 | `v-if`（审批成功）+ `v-hasPermi(['...:uploadStampedContract'])` |
| `:443-447` | 作废（已盖章） | `v-if`（已盖章）+ `v-hasPermi(['...:stampCancel'])` |
| `:458-462` | 重新编辑（另一分支） | `v-if` + 同一权限 |
| `:498-502` | 合同跟踪 | `v-if` + `v-hasPermi(['...:trace'])` |

**为什么要双条件**：
- **状态条件（`v-if`）**：这个动作在当前状态下**合不合理**（审批中的合同没法「作废」）。
- **权限条件（`v-hasPermi`）**：这个人**有没有资格**做这个动作（合同管理员才能作废）。

**答辩点**：**「状态决定『能不能做』，权限决定『谁允许做』，两者都要满足按钮才出现」**。这是 RBAC + 状态机在实际业务里的结合。

### 2.3 为什么「上传双章合同」是最重要的操作

看 `uploadSealContract`（`zxcm-ui/src/views/contract/contractAudit/auditList.vue:963-965`）——它打开 `zxcm-ui/src/views/contract/contractAudit/uploadSealFile.vue` 弹窗，用户上传**已盖好双方章的合同文件**。

**为什么重要**：本系统的用印**不是系统内盖章**，而是**线下盖章后上传盖章件**（[后端重塑版 第 9 章 §2.1](../后端重塑版/第9章-用印·作废·续签·归档.md)）。上传这个动作会**原子性地**更新 5 个字段（文件、盖章文件 ID、盖章状态、审批状态、合同状态）。

**前端体现**：这个按钮权限码单独叫 `contract:contractDraft:uploadStampedContract`（`:391`），和普通编辑不同——**说明「上传盖章件」是单独授权的高风险操作**。

### 2.4 为什么「作废」有两个不同的按钮

`zxcm-ui/src/views/contract/contractAudit/auditList.vue` 里：
- `:369-374` 的**作废**（**没有单独权限码**，只受父级「审批失败」状态 `v-if` 控制）→ `handleDelete`（`:854-870`）——针对**审批失败**的合同（还没用印，删除）。
- `:442-448` 的**作废**（`contract:contractDraft:stampCancel` 权限）→ `cancelContract`（`:1017-1019`）——针对**已盖章**的合同（不能用印了，走作废流程 + 填理由）。

**为什么分开**：**未盖章的作废 = 删记录；已盖章的作废 = 保留记录 + 作废标记 + 填理由**。因为「历史不可变」原则——已盖章的合同**不能删**，只能标记作废（[后端重塑版 第 9 章 §2.3](../后端重塑版/第9章-用印·作废·续签·归档.md)）。

**答辩点**：**前端两个「作废」按钮对应后端两种完全不同的处理**——这是「前端界面的差异，反映的是后端业务规则的差异」。

### 2.5 `trace.vue` 为什么是「时间轴 + 可增删的备注」

`trace.vue` 是**合同跟踪**弹窗——通过顶部三个 tab 分别展示「流程跟踪 / 流程信息 / 跟踪信息」（`zxcm-ui/src/views/contract/contractAudit/trace.vue:11-17`）。「流程跟踪」用 `simpleFlow` + `recordList` 画当前流程和历史任务（`:18-19`）；「跟踪信息」是一个 `el-table`，列出这个合同的所有人工备注（谁、什么时候、说了什么，`:47-71`），上方带一个「添加跟踪信息」表单（`:27-46`），支持**添加备注**（`addRemark`，`:204-219`）和**删除备注**（`:232-250`）。**这里没有用 `el-timeline`**——时间轴/流程图由工作流组件 `simpleFlow` 负责，人工备注是普通表格。

**为什么**：合同流转周期长，需要一个「过程记录」让相关人员了解进展。**这是业务操作留痕**，对应后端的 `contract_remarks` 表（[后端重塑版 第 10 章](../后端重塑版/第10章-报表与看板.md) 的 `ContractRemarksController`）。

### 2.6 `book/index.vue` 台账为什么是只读的

合同台账（`book/index.vue`）只有「查看合同」和「导出」（`:266,377`），**没有增删改**。

**为什么**：台账是**「已生效合同的只读视图」**——是给人「查」的，不是给人「改」的。它的数据来自后端 `GET /contract/book/list`，后端用 `defaultLedgerStatus()` 过滤出「非草稿」的合同（[后端重塑版 第 9 章 §2.5](../后端重塑版/第9章-用印·作废·续签·归档.md)）。

**答辩点**：**「台账不是一张新表，是一个过滤视图；前端也只读」**。

**读法**：把这张表抄下来，你就知道「合同在什么状态下，界面上会出现什么按钮」。**这是答辩时讲「审批流程」最有力的一张图**。

**逐行读「审批失败」这一支（`auditList.vue:355-375`）**：

```vue
<template
  v-if="
    scope.row.contractStatus == '3' &&
      scope.row.contractApproveStatus == '3'
  "
>
  <!--审批失败-->
  <el-button
    v-hasPermi="['contract:contractDraft:backToDraft']"
    size="mini"
    type="text"
    icon="el-icon-edit"
    @click="backToDraft(scope.row)"
  >重新编辑</el-button>
  <el-button
    size="mini"
    type="text"
    icon="el-icon-delete"
    @click="handleDelete(scope.row)"
  >作废</el-button>
</template>
```

1. `<template v-if="...">`：`template` 本身不渲染成 DOM，只用来**把一组按钮包在同一个条件里**；条件不成立，里面所有按钮都不渲染。
2. `scope.row.contractStatus == '3'`：`scope.row` 是当前表格行；`contractStatus=3` 表示合同处于「审批阶段」。
3. `scope.row.contractApproveStatus == '3'`：审批子状态为 3 表示「审批失败」。两个状态**同时满足**才进入这个分支。注意：它**不是** `review=5`；`reviewStatus=5` 是后面的「复核失败」（`:481-494`）。
4. `<!--审批失败-->`：模板注释，只给人看，不参与渲染。
5. `v-hasPermi="['contract:contractDraft:backToDraft']"`：再叠一层权限条件——有「退回草稿」权限的人才看得到「重新编辑」。
6. `size/type/icon`：Element 按钮的尺寸、文字按钮样式、图标，不影响逻辑。
7. `@click="backToDraft(scope.row)"`：点击后把整行交给 `backToDraft`（`:805-818`），它先弹确认框，再 `POST /contract/contractAudit/backToDraft`，成功后跳回合同草拟页。
8. 第二个按钮只写了 `@click="handleDelete(scope.row)"`，**没有 `v-hasPermi`**：也就是说只要合同处于审批失败状态，任何能看到这一行的人都能点「作废」。父级并没有再包一层权限。这是一个**授权粒度上的坦白点**：真正的删除权限还取决于后端接口有没有校验，前端这里只做了状态限制。
9. `handleDelete`（`:854-870`）调用的是 `delContractDraft`，所以这个「作废」实际是**物理删除草稿记录**，和已盖章分支的「保留记录 + 填理由」完全不同（见 §2.4）。

### 4.7 动手验证（在浏览器里确认「按钮状态机」）

1. **看列表数据**：进入「合同审批」页面，按 `F12` 打开 DevTools → **Network**，刷新后找到 `contractAudit/list` 请求。在 Response 的 `rows[0]` 里找四个字段：`contractStatus`、`contractApproveStatus`、`contractStampedStatus`、`contractReviewStatus`，以及 `auditForm.instanceId`。这几列就是按钮 `v-if` 的输入。
2. **对照按钮**：用 Response 里的状态值对照 §4.1 表。例如 `contractStatus=3`、`contractApproveStatus=1` 的行，操作列应该看到「撤销审批」或「前往修订」；`contractApproveStatus=3` 的行应该看到「重新编辑 / 作废」。
3. **看权限指令效果**：在 **Elements** 面板搜索「上传双章合同」。如果你当前的账号没有 `contract:contractDraft:uploadStampedContract` 权限，这个按钮在 DOM 里根本不存在（不是 `display:none`），说明 `v-hasPermi` 是**移除节点**。
4. **打开合同跟踪**：任意行点「合同跟踪」，弹窗顶部应有「流程跟踪 / 流程信息 / 跟踪信息」三个 tab；切到「跟踪信息」能看到备注表格。Network 里同时会出现 `GET /activiti/process/designer/{instanceId}`、`POST /activiti/process/listHistory` 和 `GET /contract/contractAudit/getRemarks/{id}` 三类请求——这证明跟踪弹窗不是一个 `el-timeline`，而是三块数据拼起来的。
5. **试上传双章合同**：点「上传双章合同」，选一个非 PDF 文件（比如 `.docx`），上传控件应拒绝；`uploadSealFile.vue:125` 把 `fileType` 固定为 `['pdf']`。再用 PDF 上传，Network 里能看到 `POST /contract/contractAudit/uploadSealContract`，Payload 的 `fileGroupsId` 是 JSON 字符串。

**预期**：按钮出现情况与状态表一致；无权限按钮不出现在 DOM；上传只接受 PDF；成功后列表行状态变化、按钮组切换。若状态和按钮对不上，先检查后端返回的字段名是否与模板里的 `contractStatus / contractApproveStatus / contractStampedStatus` 一致。

## 五、一个操作的完整生命流程

> 本节流程里的 `auditList.vue` / `uploadSealFile.vue` / `trace.vue` / `contractCancel.vue` 均指 `zxcm-ui/src/views/contract/contractAudit/` 下的同名文件。

### 5.1 【审批通过 → 上传双章合同】（主线）

```
① 审批人在审批列表点「查看合同」→ 走审批表单（auditList.vue:754）
   └─ 审批通过/失败由工作流引擎驱动（第 10 章）

② 审批成功后，合同状态变为「审批成功」(review=6)
   └─ 列表刷新，该行出现「上传双章合同」按钮（auditList.vue:391）

③ 点「上传双章合同」→ uploadSealContract(row)                   (:963)
   └─ 打开 uploadSealDialog 子组件（:576,607）

④ 在 uploadSealFile.vue 上传已盖双方章的合同文件               (:59)
   └─ 点确定 → submitForm()                                     (:221)
      → uploadSealContract(sealContractForm)                    (:230)
      → POST /contract/contractAudit/uploadSealContract

⑤ 后端原子更新：文件入库 + 盖章文件 ID + 盖章状态(pass) + 审批状态(success) + 合同状态(履行中 6)
   （后端见《后端重塑版》第 9 章 §2.1）

⑥ 弹窗关闭、emit 通知父组件刷新 → 列表显示合同已进入「履行中」

⑦ 该行按钮变成「作废(stampCancel)」+「合同跟踪(trace)」
   —— 状态机切换了
```

### 5.2 【已盖章合同作废】

```
① 已盖章合同行点「作废」→ cancelContract(row)                   (auditList.vue:1017)

② 在 contractCancel.vue 填作废理由                              (:26)
   └─ addCancelRemark({...}) → POST /contract/contractAudit/cancelContract  (:61,64)

```

## 六、面试高频问题

**Q1：合同审批列表的按钮是怎么控制的？**
A：**「状态 + 权限」双条件**。每个按钮外套 `v-if`（判断合同当前状态，如审批失败才显示「重新编辑」）和 `v-hasPermi`（判断当前用户权限）。本质是一个**按钮状态机**——合同处于什么状态、用户有什么权限，组合决定显示哪些按钮。

**Q2：为什么同一个位置有好几个「上传双章合同」按钮？**
A：因为合同在不同分支状态下（审批通过 / 盖章中 / 已盖章 / 复核失败）都可能需要重新上传盖章件，每个分支的 `v-if` 条件不同。它们在代码里是分开的 `v-if` 块（`auditList.vue:390-396 / 412-418 / 427-433 / 488-494`），但都调同一个 `uploadSealContract`。
**追问：多个按钮调同一个方法，怎么知道是哪条合同？** 答：每个按钮都写 `@click="uploadSealContract(scope.row)"`，把当前行数据传进去；方法再 `this.$refs.uploadSealDialog.init(row)`，弹窗里的 `openId` 来自这一行的 `id`（`auditList.vue:963-965`、`uploadSealFile.vue:152-161`）。

**Q3：为什么「作废」有两个按钮？**
A：**未盖章的作废是「删除」，已盖章的作废是「标记作废 + 填理由」**。因为「历史不可变」原则，已盖章合同不能删。两个按钮权限不同（`edit` vs `stampCancel`），走后端不同接口。

**Q4：上传双章合同是什么？**
A：本系统**不在系统内盖章**，而是线下盖好双方章后，把盖章件上传。上传调用 `POST /contract/contractAudit/uploadSealContract`（`api:127`），后端会原子更新 5 个字段（文件、盖章文件 ID、盖章状态、审批状态、合同状态），合同直接进入「履行中」。这是高风险操作，单独授权 `uploadStampedContract`。

**Q5：「撤销审批」和「重新编辑」有什么区别？**
A：「撤销审批」是**审批中**时撤回（`POST /activiti/process/cancelApply`，`auditList.vue:838`），走的是工作流引擎。「重新编辑」是**审批失败后**退回草稿态重新做（`POST /contract/contractAudit/backToDraft`，`:808`）。触发状态和接口都不同。

**Q6：合同跟踪怎么实现的？**
A：`trace.vue` 是一个三 tab 弹窗：流程跟踪用 `simpleFlow` + `recordList`，流程信息用 `preview`，跟踪信息用 `el-table` 列人工备注（`trace.vue:11-19,47-71`）。父组件通过 `ref` 调 `showRemarks(contractId, instanceId)`（`trace.vue:189-203`）打开；`getRemarks` 拉备注（`:195`），支持 `addRemark`/`deleteRemark`（`POST/DELETE /contract/remarks`，`:204-219,232-250`）。对应后端 `contract_remarks` 表。**注意：项目里没有用 `el-timeline`**。

**Q7：台账页和审批列表有什么区别？**
A：台账（`book/index.vue`）是**只读**的——只有「查看」和「导出」，数据来自 `GET /contract/book/list`，后端按 `defaultLedgerStatus()` 过滤出非草稿合同。审批列表（`auditList.vue`）是可操作的、按钮随状态变化。**台账是「查」的视角，审批列表是「办」的视角。**

**Q8：`auditSuccess`/`auditFail` 这两个方法用了吗？**
A：**坦白说没有**。它们在 `zxcm-ui/src/api/contract/contractAudit.js:58,67` 有定义，`zxcm-ui/src/views/contract/contractAudit/auditList.vue:793,799` 也有同名方法，但**实际没被调用**——审批通过/失败是由 Activiti 工作流引擎驱动的，前端不直接调这两个接口。这是遗留代码。

**Q9：导出台账是怎么做的？**
A：点导出 → `handleExport()` → `download('contract/book/export', queryParams, 文件名)`（`book/index.vue:377-379`）。走第 1 章的通用 `download` 函数（POST + blob + 进度遮罩）。

**Q10：审批表单模板页是干啥的？**
A：管理「审批表单的字段模板」，是一个标准 CRUD 页（`zxcm-ui/src/views/contract/contractAuditForm/index.vue`），权限 `contract:contractAuditForm:*`。没有特殊逻辑。

### 本章答辩卡（追问级）

**卡 1：「审批失败」的按钮分支到底用哪个字段判断？`reviewStatus=5` 是什么？**
10 秒答案：审批失败看 `contractStatus=='3' && contractApproveStatus=='3'`；`contractReviewStatus=='5'` 是另一个阶段的「复核失败」，对应 `contractStatus=='5'`。两套状态不能混用。
证据：`zxcm-ui/src/views/contract/contractAudit/auditList.vue:355-359`（审批失败）、`:481-485`（复核失败）。

**卡 2：合同跟踪弹窗是时间轴组件吗？它一次打了几个接口？**
10 秒答案：不是 `el-timeline`。它用三个 tab 组合三类数据：流程图/历史任务、流程预览、人工备注表格。打开时至少会请求流程设计数据、流程历史、备注列表三个接口。
证据：`zxcm-ui/src/views/contract/contractAudit/trace.vue:11-19,47-71`、`:138-188`（流程信息）、`:195`（备注）、`:199-202`（流程图）。

**卡 3：未盖章「作废」和已盖章「作废」在代码上差在哪？**
10 秒答案：未盖章的作废调 `handleDelete → delContractDraft`，是删草稿记录，按钮只受「审批失败」状态控制、没有单独权限码；已盖章的作废调 `cancelContract` 打开填理由弹窗，走 `cancelContract` 接口，按钮要求 `stampCancel` 权限。
证据：`auditList.vue:369-374`、`:854-870`；`:442-448`、`:1017-1019`；`contractCancel.vue:61-77`。

## 七、选型对比

### 7.1 状态驱动按钮 vs 每个状态一个页面

| | 一个列表页 + `v-if`（本项目） | 每个状态一个页面 |
|---|---|---|
| 用户心智 | 只学一个列表 | 要记多个入口 |
| 代码 | 一个页面 + 条件 | 多个页面大量重复 |
| 维护 | 加状态改条件 | 加状态加页面 |

**结论**：合同状态多（草稿/审批中/成功/失败/盖章/作废），如果用多页面会爆炸。**一个列表 + 状态驱动按钮**是正解。

### 7.2 用印：系统内盖章 vs 线下盖章后上传

| | 线下盖章后上传（本项目） | 系统内电子盖章 |
|---|---|---|
| 实现 | 上传文件 + 改状态 | 需 CA 证书、电子签章服务 |
| 合规 | 依赖线下流程 | 需要电子签章资质 |
| 成本 | 低 | 高 |

**结论**：本项目选「线下盖章 + 上传」，实现简单、合规靠线下。代价是「盖章」这个动作的自动化程度低。**这是一个业务选型的坦白**——不是技术上做不到，而是电子签章涉及资质和成本。

### 7.3 合同跟踪：三 tab 组合 vs 单一时间轴

| | 三 tab + 备注表格（本项目） | 单一 `el-timeline` |
|---|---|---|
| 流程轨迹 | ✅ 用工作流组件画流程图/任务记录 | ❌ 表达不了流程分支 |
| 人工备注 | ✅ 表格列「操作人/时间/内容」，可增删 | 可以，但长备注会挤 |
| 实现成本 | 高（要组合三类数据） | 低 |

**结论**：合同跟踪不只是「一条时间线」——它既要把工作流的流程轨迹画出来，又要管理人工备注，所以本项目用「流程跟踪 / 流程信息 / 跟踪信息」三个 tab 组合（`zxcm-ui/src/views/contract/contractAudit/trace.vue:11-19`）。如果只是纯备注列表，表格或时间轴都可以。

## 本章小结

- 本章核心：**审批列表的「按钮状态机」**——按钮的显示 = 状态条件（`v-if`）+ 权限条件（`v-hasPermi`）。
- `auditList.vue` 一张表列清所有按钮的触发条件（§4.1），这是答辩讲审批流程的核心图。
- 「作废」有两个：未盖章删记录、已盖章标记作废 + 填理由（历史不可变）。
- 「上传双章合同」是用印的关键操作，单独授权，后端原子改 5 个字段。
- `trace.vue` 合同跟踪 = 三个 tab（流程跟踪 / 流程信息 / 跟踪信息）+ 备注表格增删，父组件用 ref 调 `showRemarks`；**没有用 `el-timeline`**。
- `book/index.vue` 台账是**只读**视图；`contractAuditForm` 是标准 CRUD。
- **坦白点**：`auditSuccess`/`auditFail` 是死代码（审批实际由工作流引擎驱动）。
