# 第 8 章 · 在线文档编辑页面

> 这是前端**技术含量最高**的一章。前七章的页面都是「前端自己渲染界面」，这一章不一样——**真正的编辑器不是我们写的，是第三方服务（OnlyOffice / WPS）**，我们只负责把它「嵌」进页面，并跟它**双向通信**。通信手段是浏览器原生的 `postMessage`，这既是本章的核心，也是本章的难点。

> **零基础先补概念（前端视角）**
>
> - **iframe（页面里的页面）**：`iframe` 是 HTML 里的一块「子窗口」，它可以在当前页面里再加载另一个网页。第三方编辑器不是一段普通的 `<div>`，而是一整套网页应用，所以 OnlyOffice 被加载后会自己在容器里创建 iframe，编辑器界面都跑在 iframe 里面。本章看到 `window.frames[1].frames[0]`，意思就是「当前窗口里第 1 个 frame 里再套的第 0 个 frame」（`zxcm-ui/src/views/components/wps/onlyoffice.vue:54`）。
> - **`postMessage`（跨窗口发消息）**：浏览器为了安全，不允许 A 页面直接读 B 域 iframe 里的 DOM；但允许两边「寄信」——`postMessage` 是发信，`window.addEventListener('message', ...)` 是收信。本项目前端给编辑器发 `{action:'forceSave'}` 就是寄信（`onlyoffice.vue:68-73`），编辑器加载完回寄一个字符串 `'loaded'`（`onlyoffice.vue:38-47`）。
> - **SDK（别人提供的现成代码包）**：SDK 可以理解成「第三方服务提供的一箱工具」。OnlyOffice 的 SDK 是一个远程 JS 文件 `api.js`，动态插进 `<head>` 后提供全局对象 `window.DocsAPI`；WPS 的 SDK 是本地文件 `web-office-sdk-solution-v2.0.5.es.js`（`wps.vue:5`）。
> - **内容控件（Content Control）**：Word 里可以插入一种「有名字、可以程序定位的填空框」。OnlyOffice 在文档里给控件打一个 `Tag`，前端发指令时按 `Tag` 找到它并填值。本项目约定的 `Tag` 是 `templateElement + 文档 id`（`onlyoffice.vue:74-104`）。

## 一、这部分是做什么的

用户在系统里要能**在线打开、编辑、预览合同文档（Word）**，还得能**在文档里填内容**（如「甲方名称」「金额」）。做的事情是：

1. 后端返回一个「文档配置」（文档地址、服务器地址、编辑模式），前端用它**初始化第三方编辑器**。
2. 编辑器嵌在一个**全屏页面**里（`/contractFileEdit`）。
3. 编辑器加载完 → 通知前端（`pluginLoaded`）。
4. 前端需要操作文档（保存、填内容、加水印）→ 通过 `postMessage` **给编辑器发指令**。

对应目录 `src/views/components/wps/`：

| 文件 | 行数 | 干什么 |
|---|---|---|
| `onlyoffice.vue` | 151 | **OnlyOffice 编辑器封装**（核心，含 postMessage 协议） |
| `wps.vue` | 28 | WPS 编辑器封装（`WebOfficeSDK`） |
| `contractFileEdit.vue` | 309 | **合同文档编辑页**（独立路由 `/contractFileEdit`） |
| `contractFileView.vue` | 310 | 合同文档查看页（`/contractFileView`） |
| `contractFileRevise.vue` | 336 | 合同文档修订页（`/contractFileRevise`） |
| `fileView.vue` | 239 | 通用文件预览（`/fileView`） |
| `templateMerge.vue` | 266 | **模板合并/预览**（供合同详情内嵌） |
| `versionList.vue` | 89 | 版本列表 |

路由：这四个页面**都注册在静态路由**里（`zxcm-ui/src/router/index.js:74-97`，第 2 章讲过），因为它们要**独立窗口打开、不进菜单**。

## 二、站在架构师角度，为什么这么设计

### 2.1 为什么要「嵌入第三方编辑器」而不是自己写

在线编辑 Word 文档是**极其困难**的——要处理富文本、格式、分页、批注、多人协同、版本……**自己写一个等于重造 Word**。

**本项目的选择**：不自研，**集成第三方**（OnlyOffice / WPS）。前端的工作量从「写一个 Word」变成「**把一个现成的编辑器嵌进来 + 跟它对话**」。

**代价**：要依赖第三方服务部署（OnlyOffice 服务端 / WPS 云），要和它定通信协议。

**答辩点**：**「不自研编辑器，用 OnlyOffice/WPS 集成，前端做集成适配层」**——这是工程上非常理性的取舍。

### 2.2 编辑器怎么「嵌」进来的（两条路）

看 `onlyoffice.vue` 的做法，是**「动态加载 + 挂载」**：

1. **动态加载 SDK**（`addonlyofficeHead`，`:120-135`）：往 `<head>` 里插一个 `<script src="{onlyofficeDomain}/web-apps/apps/api/documents/api.js">`，这个脚本提供全局对象 `window.DocsAPI`。
2. **挂载编辑器**（`loadonlyoffice`，`:136-148`）：在页面里放一个 `<div id="viewFile">`，然后 `new window.DocsAPI.DocEditor('viewFile', fileModel)`——**编辑器会在这个 div 里创建 iframe**。

**关键认知**：编辑器本体跑在**多层嵌套的 iframe** 里（OnlyOffice 内部结构）。这就是为什么后面看到 `window.frames[1].frames[0]` 这种「第 1 层 iframe 的第 0 个子 iframe」的路径——**因为要和 iframe 里的编辑器通信**。

**为什么用 `setTimeout(..., 500)`**（`:144`）：编辑器初始化需要时间，等 500ms 让 SDK 准备好。**这是个「不稳定」的做法**（坦白点，见 §2.7）。

### 2.3 核心机制：`postMessage`（跨 iframe 通信）

浏览器出于安全，**不允许一个页面直接读另一个域 iframe 的内容**。但可以用 `postMessage` **发消息**过去。这就是前端和编辑器对话的方式。

**两个方向**：

**① 前端 → 编辑器**（前端给编辑器下指令）：用 `postMessage`

```js
// onlyoffice.vue:54
window.frames[1].frames[0].postMessage(JSON.stringify(data), '*')
```

`data` 是一个指令对象，如：

| action | 干什么 | 定义在 |
|---|---|---|
| `addWatermark` | 加水印 | `onlyoffice.vue:49-55` |
| `mergeContent` | 合并模板内容（填要素） | `:56-67` |
| `forceSave` | 强制保存 | `:68-73` |
| `createContentControl` | 创建内容控件（表单域） | `:74-82` |
| `getContentControl` | 选中内容控件 | `:83-89` |
| `deleteContentControl` | 删除内容控件 | `:90-96` |
| `updateContentControl` | 更新内容控件 | `:97-104` |

**② 编辑器 → 前端**（编辑器通知前端）：用 `addEventListener('message', ...)`

```js
// onlyoffice.vue:20-22（mounted）
window.addEventListener('message', this.receiveMessage)
// onlyoffice.vue:38-48
receiveMessage(event) {
  if (event.data === 'loaded') {        // 编辑器发了 'loaded'
    this.pluginLoaded = true
    this.$emit('pluginLoaded')          // 通知父组件：编辑器就绪了
  }
}
```

**答辩点（本章最关键）**：**「前端和第三方编辑器通过 `postMessage` 双向通信：往下发指令（保存/填内容/水印），往上收事件（loaded）」**。因为没有后端参与，纯前端跨 iframe 通信，所以只能用 `postMessage`。

### 2.4 为什么「保存」要 `forceSave` + 延迟提示

看 `saveDoc`（`contractFileEdit.vue:105-113`）：

```js
saveDoc() {
  this.$refs.onlyoffice.forceSave()          // 给编辑器发「强制保存」指令
  setTimeout(async() => {
    this.$message.success('保存成功！')       // 1.5 秒后才提示
  }, 1500)
}
```

**为什么**：`forceSave` 只是「**请求**编辑器保存」，编辑器保存要时间（发给后端存对象存储）。所以**延迟 1.5 秒**再提示「保存成功」——**这是个「假同步」**：前端并不知道编辑器到底存没存完，只是「估计差不多好了」。

**坦白点**：**这个提示不可靠**。如果网络慢，1.5 秒可能还没存完就提示成功了。**正确的做法应该是等编辑器回调保存完成事件**（编辑器其实支持），但本项目用了「猜时间」的土办法。

### 2.5 为什么有「查看 / 编辑 / 修订」三个页面

`contractFileEdit.vue`（编辑）、`contractFileView.vue`（查看）、`contractFileRevise.vue`（修订）三个文件结构几乎一样，只是**初始化的参数不同**（编辑 vs 只读）。

**为什么不多用一个页面加参数**：虽然大部分代码像，但**权限、按钮（有没有「保存」）、水印策略**不同。分开写虽然有点重复，但清晰。**这是一个「重复 vs 清晰」的权衡**——坦白说这里有优化空间（可以合并成一个页面 + mode 参数）。

而且入口也不同：`contractFileEdit.vue:94-102` 从 `$route.query` 读 `id`/`file`/`revise` 三个参数决定怎么加载（`revise` 有值就进修订模式）。

### 2.6 编辑器怎么选（OnlyOffice 还是 WPS）

`contractFileEdit.vue:206-213`：后端返回的 `editorType` 决定用哪个——

```js
} else if (res.data.editorType == 'onlyoffice') {
  this.viewFile = 'office'
  this.editorType = 'onlyoffice'
  this.$refs.onlyoffice.loadDoc(...)         // 用 OnlyOffice
}
```

模板里两个编辑器都放好了，用 `v-show` 切换（`:51-57`）：

```vue
<OnlyOffice v-show="editorType === 'onlyoffice'" ... />
<Wps v-show="editorType === 'wps'" ... />
```

**为什么做两套**：给客户**选择权**——有的客户有 OnlyOffice 私有部署，有的用 WPS 云。**「可插拔的编辑器适配层」**。

### 2.7 ⚠️ 坦白点：这一章有几个明显的「没做完」的地方

这是本书**「缺口主动写出来」**原则的集中体现。在线编辑这块**演示能跑，但工程上没做扎实**：

1. **「要素填充」链路没接通**：`mergeData`（`:56`）、`addContentControl`（`:74`）、`selectContentControl`（`:83`）、`updateContentControl`（`:97`）、`deleteContentControl`（`:90`）这五个方法**定义了但全项目没人调用**（`grep` 可验证）。也就是说「在合同里填甲方名称/金额」这个功能，**前端只写了「发指令的方法」，没写「谁来调这些方法」**。
2. **WPS 基本不可用**：`contractFileEdit.vue:181-186` 的 WPS 分支只是打开 `wps.vue`；而 `wps.vue:11-22` 里 `appId: 'SX20230920RTMYNA'` **写死**，且**直接把登录 token 当 WPS token 传**（`:18`）——这在安全上是**不可接受**的（WPS token 应由后端单独签发）。加上 WPS 那段注释掉的老代码（`:187-205`），说明 **WPS 集成是「试过但没跑通」**。
3. **`disableMore()` 是死代码**：`contractFileEdit.vue:216-230` 和 `onlyoffice.vue:105-119` 的 `disableMore` 依赖 `this.jssdk`，但 `contractFileEdit.vue` 里 **`jssdk` 从未被赋值**，所以它一调用就会报错。它是 WPS 老 API 的遗留。
4. **`window.frames[1].frames[0]` 写死 iframe 路径**（`onlyoffice.vue:54` 等）：这是**脆弱写法**——如果 OnlyOffice 内部 iframe 结构变了（升级版本），路径就失效。稳妥做法是遍历 `window.frames` 找目标帧。
5. **`setTimeout 500ms` 等编辑器初始化**（`:144`）：用「猜时间」代替「等就绪事件」，慢机器上会偶发失败。
6. **`templateMerge` 的 `uploadid` 事件没有下文**：组件在加载完文件后 `$emit('uploadid', {contractidarr, attachmentidarr})`（`zxcm-ui/src/views/components/wps/templateMerge.vue:144`），唯一监听方是审批编辑容器 `Edit.vue` 的 `@uploadid="uploadid"`（`zxcm-ui/src/views/workflow/form/Edit.vue:30`），而接收方法只把两组 id 合并存进 `idarr`（`Edit.vue:214-216`）；全项目再没有任何地方读 `idarr`。也就是说「模板合并」的**前端接力棒传出去后没人接**，真正的合并链路并未在前端闭环。
7. **「提交审批前强制保存」的守卫写错了 ref**：`info/index.vue` 的 `onCheckAudit()` 里判断的是 `this.$refs.onlyoffice`（`zxcm-ui/src/views/contract/contractDraft/info/index.vue:52-54`），但这个页面给子组件起的 ref 名是 `officeEdit`（同文件 `:21-25`），所以这个 `if` 永远不成立，`forceSave()` 从来不会在提交审批前被调用。

**答辩时主动说这些**——「在线编辑我做了集成和调通主流程（加载、保存、切换文档），但要素填充的内容控件链路和 WPS 集成是半成品，因为……」。**承认缺口比假装完美更可信**。

## 四、怎么读怎么改

### 4.1 `onlyoffice.vue` —— 编辑器封装（151 行，核心）

| 行号 | 内容 |
|---|---|
| `:2-5` | 承载编辑器的 `<div id="viewFileContainer">` |
| `:8-9` | import `getUrl`（获取文档配置）、`request` |
| `:20-22` | `mounted` 注册 `message` 监听（**接收编辑器事件**） |
| `:25-37` | `loadDoc(fileId,type,contractId,isEdit,isReview)` —— **主入口**：拉配置 → 注入 SDK → 挂载编辑器 |
| `:38-48` | `receiveMessage(event)` —— **收到 `'loaded'` → emit `pluginLoaded`** |
| `:49-55` | `addWatermark()` 发 `addWatermark` 指令 |
| `:56-67` | `mergeData(dataList)` 发 `mergeContent` 指令（填要素，**未被调用**） |
| `:68-73` | `forceSave()` 发 `forceSave` 指令（**被调用**） |
| `:74-104` | 内容控件增删改查（**未被调用**） |
| `:105-119` | `disableMore()`（死代码） |
| `:120-135` | `addonlyofficeHead(data)` —— **动态注入 SDK script** |
| `:136-148` | `loadonlyoffice(fileModel)` —— **挂载编辑器** |

**逐行读主入口 `loadDoc()`（`zxcm-ui/src/views/components/wps/onlyoffice.vue:25-37`）和 `loadonlyoffice()`（同文件 `:136-148`）**：

```js
loadDoc(fileId, type, contractId, isEdit, isReview = false) {
  this.isEdit = isEdit
  getUrl(fileId, type, contractId, isEdit, isReview).then((res) => {
    var index = res.data.fileName.lastIndexOf('.')
    var ext = res.data.fileName.substring(index + 1)
    if (!this.onlyofficeLoaded) {
      this.addonlyofficeHead(res.data)
    }
    this.loadonlyoffice(res.data.onlyofficeModel)
  })
}
```

```js
loadonlyoffice(fileModel) {
  this.viewFile = true
  this.$nextTick(() => {
    var html = ' <div id="viewFile" style="height: calc(100vh - 65px); width: calc(100vw - 0px)"></div>'
    document.getElementById('viewFileContainer').innerHTML = html
    setTimeout(function() {
      const docEditor = new window.DocsAPI.DocEditor('viewFile', fileModel)
    }, 500)
  })
}
```

1. `loadDoc(fileId, type, contractId, isEdit, isReview)`：它是编辑器封装的**总入口**。页面传「文件 id、业务类型、合同 id、是否编辑、是否复核」，它负责把后端配置变成屏幕上的编辑器。
2. `this.isEdit = isEdit`：把编辑/只读模式记在组件里。当前只在 `receiveMessage` 的注释代码里被用到（`:43-46`），属于**预留字段**。
3. `getUrl(...).then(...)`：先请求 `GET /wps/weboffice/geturl` 拿配置（接口定义在 `zxcm-ui/src/api/tool/wps.js:13-18`）。注意这是**异步**的：`.then` 里的代码要等网络回来才执行。
4. `res.data.fileName.lastIndexOf('.')` 和 `substring(index + 1)`：从文件名里截后缀（如 `合同.docx` → `docx`）。代码里算出的 `ext` 在 `onlyoffice.vue` 里**没有被使用**——后缀分流实际写在父页面 `zxcm-ui/src/views/components/wps/contractFileEdit.vue:159-162`，这里是复制粘贴留下的冗余。
5. `if (!this.onlyofficeLoaded)`：本意是「SDK 只注入一次」。但全项目**没有任何地方把 `onlyofficeLoaded` 置为 `true`**（只在 `:15` 初始化为 `false`），所以这个判断永远成立——每次切文档都会再插一个 `api.js` 标签，是**失效的缓存标记**。
6. `this.addonlyofficeHead(res.data)`：动态创建 `<script src="{onlyofficeDomain}/web-apps/apps/api/documents/api.js">` 并塞进 `<head>`（`:120-135`）。这一步执行完，浏览器才开始下载 SDK，**并不保证马上下载完**。
7. `this.loadonlyoffice(res.data.onlyofficeModel)`：把后端返回的 `onlyofficeModel`（编辑器配置对象，包含文档地址、回调地址、权限等）交给挂载方法。
8. `this.viewFile = true`：组件 data 里并没有 `viewFile` 字段（`data()` 只有 `baseURL/onlyofficeLoaded/pluginLoaded/isEdit`，`:12-19`），这行是**无效赋值**；真正控制显示的是父页面的 `viewFile`。
9. `this.$nextTick(() => {...})`：Vue 的数据变化到 DOM 更新是异步的，`$nextTick` 等本轮 DOM 更新结束后再执行回调（原理见《Vue2 从 0 到精通》第 3 章 §8.2）。这里是为了确保容器 `#viewFileContainer` 已经在页面上。
10. `document.getElementById('viewFileContainer').innerHTML = html`：先往容器里塞一个 `<div id="viewFile">`，作为编辑器的挂载点。
11. `setTimeout(function() {...}, 500)`：等 500 毫秒，赌 SDK 已经下载完成。**这是本章最脆的地方**：慢网络下 500ms 不够，`window.DocsAPI` 还不存在就会报错。
12. `new window.DocsAPI.DocEditor('viewFile', fileModel)`：SDK 提供的构造函数。第一个参数是挂载 div 的 id，第二个是后端给的配置；调用后 OnlyOffice 在该 div 里创建 iframe 并渲染文档。
13. 整条链路可以记成：**页面传 id → 后端给配置 → 注入 SDK → 挂载 DocEditor → iframe 里的编辑器就绪后回发 `'loaded'`**。前半段在本文件，最后一步在 `receiveMessage`（`:38-48`）。

**读法**：认准两件事——**往下发指令用 `postMessage`**（`:54` 等），**往上收事件用 message 监听**（`:21,38`）。搞懂这两条，这个文件就通了。

## 六、面试高频问题

**Q1：你们的在线文档编辑是怎么实现的？**
A：不自研编辑器，集成第三方（OnlyOffice / WPS）。前端从后端拿文档配置（`GET /wps/weboffice/geturl`），动态往页面注入编辑器的 SDK script，然后 `new DocsAPI.DocEditor(divId, model)` 把编辑器挂到页面的 div 里。编辑器本体跑在嵌套 iframe 中。

**Q2：前端怎么跟编辑器通信？**
A：浏览器跨 iframe 只能用 `postMessage`。前端→编辑器用 `window.frames[1].frames[0].postMessage(JSON.stringify({action, ...}), '*')` 发指令（如 `forceSave`、`mergeContent`）；编辑器→前端用 `window.addEventListener('message', cb)`，收到编辑器的 `'loaded'` 事件就知道它就绪了（`onlyoffice.vue:21,38,54`）。

**Q3：`postMessage` 为什么第二个参数是 `'*'`？**
A：`'*'` 是 targetOrigin，表示「不限制目标源」。安全上应该写死编辑器的域（如 `https://onlyoffice.xxx.com`），用 `'*'` 任何域都能收到，有被恶意页面监听的风险。**这里是简化处理**（生产应限制 origin）。

**Q4：「保存」是怎么让文档存到后端的？**
A：前端调 `this.$refs.onlyoffice.forceSave()`，它发 `postMessage({action:'forceSave'})` 给编辑器；编辑器收到后自己把文档回传给后端保存。前端只是「请求保存 + 延迟 1.5 秒提示」（`contractFileEdit.vue:105-113`）。**坦白**：这个「延迟提示」不可靠，正确做法是等编辑器的保存完成回调。

**Q5：怎么决定用 OnlyOffice 还是 WPS？**
A：后端在 `getUrl` 返回里给 `editorType`，前端据此 `v-show` 显示对应的编辑器组件（`contractFileEdit.vue:51-57,206-213`）。两套都封装好了，做成「可插拔的适配层」，客户可以用自己的部署。

**Q6：文档里的「要素填充」（填甲方名称、金额）怎么做的？**
A：**坦白说这块是半成品**。`onlyoffice.vue` 里定义了 `mergeData`（合并内容）、`addContentControl`（创建内容控件）、`updateContentControl` 等方法（`:56-104`），用的是 OnlyOffice 的「内容控件（Content Control）」机制，按 `Tag='templateElement'+id` 定位。但这些方法**全项目没有被调用**——只写了「发指令的能力」，没接上「谁来触发」。功能链路是断的。

**Q7：为什么编辑器页面要走独立路由、独立窗口？**
A：编辑器是全屏、重资源、带富交互的独立应用，塞进弹窗又挤又慢。所以放在静态路由（`zxcm-ui/src/router/index.js:74-97`），用 `window.open` 开新标签页（第 5 章 `editDoc`）。静态路由意味着它不进菜单，符合「工具页」定位。

**Q8：WPS 集成好用吗？**
A：**坦白讲没跑通/不完整**。`wps.vue` 里 `appId` 写死（`:14`），且直接把登录 token 当 WPS token 传（`:18`）——这有安全问题，WPS token 应该由后端单独签发。`contractFileEdit.vue` 里还有大段注释掉的 WPS 老代码。**它更像「试过但没完成」**。

**Q9：`setTimeout` 500ms 是干啥的？能去掉吗？**
A：在 `loadonlyoffice`（`onlyoffice.vue:144`）里，用 500ms 等 OnlyOffice SDK 加载完再 `new DocEditor`。这是「猜时间」的不可靠做法——慢机器可能还没就绪。更稳的是监听 SDK 的 ready 事件。**这是个技术债。**

**Q10：`window.frames[1].frames[0]` 这么写有什么问题？**
A：它写死了「第 1 层 iframe 的第 0 个子 iframe」这个路径，依赖 OnlyOffice 的内部结构。如果 OnlyOffice 升级改了 iframe 层级，就失效。稳妥做法是遍历 `window.frames` 按特征找目标帧，或让编辑器暴露明确的通信入口。

### 本章答辩卡（追问级）

**卡 1：OnlyOffice 里打开的文档内容，是前端传给它的吗？**
10 秒答案：不是。前端只把「文件 id、业务类型、合同 id」发给后端换配置；后端返回 `onlyofficeModel`，里面是文档服务能访问的文档地址/回调地址/权限，编辑器 iframe 自己去文档服务取文件。前端全程没有读过文档二进制。
证据：`zxcm-ui/src/views/components/wps/contractFileEdit.vue:154-157`（取配置）、`zxcm-ui/src/api/tool/wps.js:13-18`（参数）、`zxcm-ui/src/views/components/wps/onlyoffice.vue:25-36,136-148`（把 model 交给 DocEditor）。

**卡 2：`templateMerge` 把文件 id 发出去之后，谁在做合并？**
10 秒答案：严格按源码，前端没有下一步。`uploadid` 事件只有 `Edit.vue` 接住，合并后的 `idarr` 再没被读过；所以「前端合并链路」是断的，真正的合并如果存在，只能在后端流程里发生，不能答辩成「我前端调了合并接口」。
证据：`zxcm-ui/src/views/components/wps/templateMerge.vue:144`（emit）、`zxcm-ui/src/views/workflow/form/Edit.vue:30`（监听）、`Edit.vue:210,214-216`（只存不用）。

**卡 3：代码里有 `addWatermark()`，为什么编辑器上没看到水印？**
10 秒答案：因为这个方法只有定义、没有调用。原来「只读模式加载完加水印」的调用被注释掉了；而且它依赖 `window.frames[1].frames[0]` 和固定的 `action:'addWatermark'`，属于未验证的半成品。
证据：`zxcm-ui/src/views/components/wps/onlyoffice.vue:49-55`（方法定义）、同文件 `:43-46`（被注释的调用）、`:38-41`（`'loaded'` 分支里只剩 emit）。

## 七、选型对比

### 7.1 自研编辑器 vs 集成第三方

| | 集成第三方（本项目） | 自研 |
|---|---|---|
| 工作量 | 中（集成 + 适配） | 极大（等于做 Word） |
| 功能完整度 | 高（现成的） | 很难做全 |
| 依赖 | 要部署 OnlyOffice/WPS 服务 | 无 |

**结论**：在线编辑 Word 必须用第三方，自研不现实。**这是全项目的合理取舍。**

### 7.2 OnlyOffice vs WPS

| | OnlyOffice（主用） | WPS |
|---|---|---|
| 开源/私有部署 | ✅ 可私有部署 | 云服务为主 |
| 本项目状态 | 主流程能跑 | **半成品**（写死 appId、token 安全问题） |
| 通信 | `postMessage` + `DocsAPI` | `WebOfficeSDK` |

**结论**：本项目**实际以 OnlyOffice 为主**，WPS 是「备选接入但没做完」。做「双编辑器适配层」的想法是对的，但 WPS 那条路没走通。

### 7.3 `postMessage` vs 后端中转

| | `postMessage`（本项目） | 后端中转 |
|---|---|---|
| 前端↔编辑器 | 直接通信，快 | 要绕后端 |
| 复杂度 | 低 | 高 |
| 安全 | 要注意 origin | 后端可鉴权 |

**结论**：前端和编辑器在**同一个浏览器页面**里，直接 `postMessage` 最自然。后端中转没有意义（编辑器和前端本来就在一起）。**但要限制 targetOrigin 才安全**（本项目用了 `'*'`，是简化）。

## 本章小结

- 在线编辑 = **集成第三方编辑器（OnlyOffice/WPS）+ 前端做适配层**，不自研。
- 集成方式：动态注入 SDK `<script>` → `new DocsAPI.DocEditor(div, model)` 挂载 → 编辑器跑在嵌套 iframe。
- **核心通信机制 `postMessage`**：前端→编辑器发指令（`forceSave`/`mergeContent`…），编辑器→前端发事件（`'loaded'`）。
- 路由 `/contractFileEdit` / `/contractFileView` / `/contractFileRevise` / `/fileView` 都在**静态路由**、独立窗口打开。
- 后端给 `editorType` 决定用哪个编辑器，做成可插拔适配层。
- **坦白点（本章重点）**：① 要素填充的 `mergeData`/`addContentControl` 等**定义了但没人调用**，链路断开；② WPS 集成是半成品（写死 appId、token 安全妥协）；③ `disableMore` 是死代码；④ `window.frames[1].frames[0]` 写死路径脆弱；⑤ `setTimeout 500ms` 是猜时间；⑥ `templateMerge` 的 `uploadid` 传出去后没人消费，合并链路未闭环；⑦ 「提交审批前强制保存」的 ref 判断写错，`forceSave` 实际不会执行；⑧ `onlyofficeLoaded` 从未置 `true`，SDK 会被重复注入。
