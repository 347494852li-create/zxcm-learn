# 第 10 章 · 工作流前端页面

> 前面第 6 章讲合同审批按钮时，反复出现「工作流引擎」「撤销审批」「待办」——那些背后的东西，这一章收口。工作流前端是全站**最「企业级」**的一块：有**流程设计器**（画流程图）、**流程模型管理**、**待办/已办**、**各种审批动作表单**（同意/驳回/转办）。这一章把这块地图铺开。

> **零基础先补概念（前端视角）**
>
> - **工作流 / 流程实例 / 任务**：工作流就是「一件事按画好的步骤流转」。画好的步骤叫**流程定义**；每发起一次合同审批，就按定义复制出一份**流程实例**（这次实际在跑的那条流程）；实例走到某个审批节点时，会给审批人生成一条**任务**，这就是「待办」（接口 `GET /activiti/process/taskList`，见 `zxcm-ui/src/views/workflow/todoItem/todo/index.vue:316-322`）。本书的「待办」不是前端数组，而是后端工作流引擎里的任务。
> - **BPMN**：业务流程建模符号标准，简单说就是「流程图的一套通用画法和 XML 格式」。本项目前端有一个**自研的卡片式设计器**（`zxcm-ui/src/views/workflow/engine/index.vue`），把节点画成 `FlowCard`；后端再用 `DesignerAdapterUtil.JSONToBPMN` 把前端 JSON 转成 BPMN XML 部署到 Activiti（`zxcm-workflow/src/main/java/com/ruoyi/workflow/engine/controller/WorkflowDesignerController.java:59-61`）。
> - **动态组件 `<component :is>`**：模板里写 `<component :is="currentView" />`，Vue 会按 `currentView` 的值决定渲染哪个组件。审批页靠它实现「同一条流程壳，不同业务流程换不同业务表单」（`zxcm-ui/src/views/workflow/form/Audit.vue:27-34,106-113`）。这不是新语法，只是 `:is` 绑定了一个组件对象。
> - **审批动作与表单**：同意、拒绝、驳回、转办、撤销是不同动作，要填的信息不同，所以每个动作有自己的弹窗组件；提交时也调不同的后端接口（见 §4.6）。**动作 → 表单 → 接口**是一一对应的。

## 二、站在架构师角度，为什么这么设计

### 2.1 为什么要「流程设计器」（画流程图）

合同审批不是「一条直线」——可能是「业务员提交 → 部门经理 → 法务 → 总经理」，也可能「部门经理批完就够」。**每个公司、每种合同类型的审批链不同**。

**本项目的做法**：做一个**流程设计器**（`engine/index.vue`），让管理员**可视化地编辑审批流程**（加审批节点/条件节点、改节点属性），存下来、部署到 Activiti 引擎。之后合同走流程时，就按这张图走。

**答辩点**：**「审批流程不写死在代码里，用小规模流程设计器可视化配置」**——和「菜单/字典不写死」（第 2、3 章）是同一个思想：**能配的别写死**。

### 2.2 流程设计器到底长什么样（先纠正一个常见误解）

看 `zxcm-ui/src/views/workflow/designer/index.vue:63` 和 `:71`：

```vue
<Designer v-if="formVisible" ref="designer" @refresh="refresh" />
...
import Designer from '../engine/index.vue'
```

`engine/index.vue`（322 行）就是设计器本体，但它**不是 `bpmn-js`**，也**没有 iframe 嵌入**。它是项目/框架自带的**自研卡片式设计器**：

- 顶部两个步骤：`basicSetting`（基础设置）和 `processDesign`（流程设计），定义在 `engine/index.vue:81-85`；模板按 `activeStep` 用 `v-show` 切换（`:20-38`）。
- 流程画布是 `@/components/workflow/Process`（`engine/index.vue:45,57-61`），它内部用 `FlowCard` 画节点卡片、用 `PropPanel` 编辑节点属性（`zxcm-ui/src/components/workflow/Process/index.vue:2-4,128-140`）。
- 所以你在页面上看到的是 **HTML 卡片和箭头，不是 BPMN 画布**。这正是可以用 Elements 直接看到 `.flow-path-card` 的原因。

**那 BPMN 在哪？** 在后端。前端「提交」时把 `{basicSetting, processData}` 以 JSON 发到 `POST/PUT /workflow/designer`（`engine/index.vue:115-159`）；后端 `DesignerAdapterUtil.JSONToBPMN(...)` 把 JSON 转成 BPMN XML，再部署到 Activiti（`WorkflowDesignerController.java:59-61,126-128,163-164`）。**前端画 JSON，后端转 BPMN**——这条边界答辩时要讲清楚。

另外，`activiti/modeler/index.vue` 是另一条路：它是 Activiti 官方老版模型编辑器，点「在线设计」会 `window.open` 到 `{VUE_APP_BASE_API}/modeler/modeler.html?modelId=...`（`zxcm-ui/src/views/workflow/activiti/modeler/index.vue:237-243`）；仓库里对应的 `zxcm-ui/public/modeler.html:1-81` 加载的是 AngularJS 的 `editor-app` 资源，也不是 bpmn-js。**两套设计器不要混为一谈。**

**读法**：`designer/index.vue` 是**列表 + 打开设计器**（`:116-121` 的 `addOrUpdateHandle` 打开），`engine/index.vue` 是**设计器本体**。**「列表页 + 编辑器」的经典拆分**（和第 7 章模板「列表 + 弹窗」一个思路）。

### 2.3 三个文件夹的分工：「定义 / 运行 / 任务」

工作流前端分成三组，对应工作流引擎的三个概念：

| 组 | 目录 | 管什么 |
|---|---|---|
| **定义期** | `designer` / `engine` / `activiti/definition` / `activiti/modeler` | 画流程、部署流程（**流程长什么样**） |
| **运行期-我的** | `myApply` | 我发起的申请 |
| **运行期-待办** | `todoItem/todo` / `todoItem/done` | 我要处理 / 我已处理的任务 |

**为什么这么分**：**「定义」和「运行」是工作流的两个阶段**——先画出流程（定义），才有人跑流程、产生任务（运行）。这是 BPM 系统的通用架构。

**答辩点**：**「工作流分定义期和运行期：`designer/engine` 是定义期，`myApply/todoItem` 是运行期」**。

### 2.4 `business/audit.vue` 为什么是「业务审批页」

`business/audit.vue`（505 行）——它是**合同审批的业务表单**，但它**不是「conf 驱动的动态表单」**。`props` 里虽然有 `conf`（`zxcm-ui/src/views/workflow/business/audit.vue:331`），但 `conf` 只被用来传两个 id：`init()` 里读 `this.conf.instanceId` 和 `this.conf.contractId`，调 `GET /contract/contractDetail/audit`（`:400-406`）。页面的字段、标题、金额、日期等**都是模板里写死的合同字段**（模板从 `:1` 开始，没有按 `conf` 做 `v-for` 渲染）。`recordList` 则传给底部审批记录组件（`:317`）。

**为什么叫「business」**：它展示的是**业务数据**（合同内容），而不是流程节点。工作流引擎只负责「**谁审、审到哪**」，业务表单负责「**审的是什么内容**」。**这是「流程」和「业务」的分离**——工作流引擎不知道合同是什么，它只知道有个任务要处理；业务页面按 `instanceId/contractId` 去业务表拿合同内容渲染给审批人看。

**真正做「换业务」的是外层容器**：`Audit.vue` 用 `require([\`@/views/workflow/business/${data.flowType}\`], resolve)` 动态加载业务组件（`zxcm-ui/src/views/workflow/form/Audit.vue:106-113`），再通过 `<component :is="currentView" :conf="setting">` 渲染（`:27-34`）。所以解耦点是「**流程壳 + 按 flowType 换业务组件**」，不是「conf 描述字段」。

**答辩点（重要）**：**「工作流引擎和业务解耦：引擎管流程流转，业务表单管展示内容，两者通过业务 ID 关联」**。这是工作流集成的核心设计原则；但不要把它美化成一个通用的动态表单引擎——本项目只有合同这一种业务表单。

### 2.5 为什么审批动作有这么多表单

`workflow/form/` 下有 7 个表单文件：`Audit`（审批）/ `Agree`（同意）/ `Back`（驳回）/ `BatchAgree`（批量同意）/ `TransUser`（转办）/ `Edit`（编辑）/ `EditAgree`（编辑同意）。

**为什么**：每个审批动作要填的东西不同：
- **同意**：填审批意见，调 `POST /activiti/process/complete`（`form/Agree.vue:103-116`）。
- **拒绝**：终止整个流程，必须填原因，调 `POST /activiti/process/reject`（`form/Audit.vue:189-230`）。**「拒绝」和「驳回」不是一回事**。
- **驳回**：必须填理由 + 选择退回节点，调 `POST /activiti/process/jumpTo`（`form/Back.vue:169-202`，请求在 `:200-202`）。
- **转办**：选转给谁，调 `POST /activiti/process/delegate`（`form/TransUser.vue:83-90`）。
- **批量同意**：一次同意多条，调 `POST /activiti/process/batchComplete`（`form/BatchAgree.vue:73-86`）。
- **撤销**：终止自己发起的流程，调 `POST /activiti/process/cancelApply`（`form/Audit.vue:231-263`）。

每个动作一个表单组件，**按动作弹出对应表单**。**这是「动作 → 表单 → 接口」的一一映射**。

**答辩点**：**「不同审批动作弹不同表单，动作和表单一一对应；而且提交接口也不同，不是所有动作都调 complete」**。

### 2.6 ⚠️ 坦白点：工作流这块「框架自带多、业务定制少」

工作流这块**框架自带的多、项目定制的少**，但「设计器」要单独说清楚：

1. **`activiti/definition/index.vue` 和 `activiti/modeler/index.vue`**（各 300 行左右）是**标准 Activiti 管理页**（流程定义列表、模型列表、暂停/激活、转模型），是框架给的；模型「在线设计」跳到 Activiti 官方老版编辑器页面（`modeler/index.vue:237-243`）。
2. **`designer` + `engine` + `components/workflow/*` 是框架内的自研可视化设计器**（卡片式，不是 bpmn-js）：`engine/index.vue` 负责两步表单和保存，`Process/FlowCard/PropPanel` 负责画布。它把 JSON 存到业务表，后端转 BPMN 后部署（`WorkflowDesignerController.java:59-61`）。
3. **`form/` 下 7 个表单**是框架的通用审批表单，字段是「审批意见/驳回到哪/转给谁」这类**通用**字段，**不针对合同业务定制**。
4. **合同真正走的审批**，是从 `auditList.vue`（第 6 章）跳来，用 `Audit.vue` 这个流程壳 + `business/audit.vue` 展示合同 + 这些通用表单做动作。
5. **`designer/simpleFlow.vue`（68 行）**不是设计器，而是审批页上的**只读简易进度条**：它调 `GET /activiti/process/simpleWorkflow` 拿节点列表，用 `el-steps` 展示当前走到哪（`zxcm-ui/src/views/workflow/designer/simpleFlow.vue:3-14,44-64`）。

**答辩时这样说**：「工作流用的是 Activiti 6；可视化设计器是框架自带的卡片式设计器（前端存 JSON、后端转 BPMN 部署），Activiti 定义/模型管理页和通用审批表单也是框架的。我重点对接的是合同业务：`Audit.vue` 流程壳按 `flowType` 动态加载 `business/audit.vue` 展示合同，以及合同状态机联动。」——**把「框架给的」和「项目做的」分清楚，是答辩的关键。**

### 4.2 `engine/index.vue` —— 流程设计器（322 行）

**这是画流程图的地方**。`designer/index.vue:116-121` 通过 `$refs.designer.init(id)` 打开它。

| 行号 | 内容 |
|---|---|
| `:20-38` | 模板：`BasicSetting` 和 `Process` 两个步骤组件，`v-show` 按 `activeStep` 切换 |
| `:45-47` | import `Process`、`BasicSetting`、`request` |
| `:81-85` | 步骤定义：基础设置 / 流程设计 |
| `:95-111` | `init(id)`：新建给空配置；编辑按 id 拉 `GET /workflow/designer/{id}` 并 `JSON.parse` |
| `:115-134` | `publish()`：收集两个子组件的 `getData()`，`Promise.all` 后得到 `{basicSetting, processData}` |
| `:135-159` | `sendToServer(param)`：有 id → `PUT /workflow/designer/{id}`；无 id → `POST /workflow/designer` |
| `:192-205` | 基础设置与流程节点的发起人双向同步 |

**逐行读「打开设计器 → 加载配置」这段（`zxcm-ui/src/views/workflow/designer/index.vue:116-121` + `zxcm-ui/src/views/workflow/engine/index.vue:95-111`）**：

```js
// designer/index.vue
addOrUpdateHandle(id, isDetail) {
  this.formVisible = true
  this.$nextTick(() => {
    this.$refs.designer.init(id)
  })
}

// engine/index.vue
init(id) {
  this.id = id
  if (id == null) {
    this.mockData = { basicSetting: {}, processData: {}, formData: {} }
  } else {
    request({
      url: `/workflow/designer/${id}`,
      method: 'get'
    }).then(res => {
      this.mockData = JSON.parse(res.data.json)
    })
  }
}
```

1. `addOrUpdateHandle(id, isDetail)`：列表页「新增」和「编辑」共用的入口（`designer/index.vue:22,56`）。
2. `this.formVisible = true`：把列表隐藏、把 `<Designer v-if="formVisible">` 显示出来（模板在 `designer/index.vue:3,63`）。这里不是路由跳转，所以 URL 不变。
3. `this.$nextTick(() => {...})`：`formVisible` 刚改成 `true` 时，`Designer` 还没被创建，`this.$refs.designer` 是 `undefined`。等本轮 DOM 更新完再取 ref（`$nextTick` 原理见《Vue2 从 0 到精通》第 3 章 §8.2）。
4. `this.$refs.designer.init(id)`：父组件拿到子组件实例，直接调它的 `init` 方法——`ref` 通信方式（《Vue2 从 0 到精通》第 4 章 §9.1）。
5. `init(id)` 第一行 `this.id = id`：记住当前设计的是哪条流程，提交时决定 `POST` 还是 `PUT`（`engine/index.vue:136-148`）。
6. `if (id == null)`：`null`/`undefined` 代表「新增」。给三个空对象，让两个子组件有初始结构可渲染。
7. `else`：编辑已有流程，发 `GET /workflow/designer/{id}`。这个接口返回的 `res.data.json` 是**字符串**（后端把整份设计存在一个 JSON 字段里，`WorkflowDesignerController.java:87-93`）。
8. `JSON.parse(res.data.json)`：把字符串还原成对象，赋给 `mockData`；模板再把 `mockData.basicSetting` / `mockData.processData` 传给两个子组件（`engine/index.vue:21-37`）。
9. 之后用户拖动/编辑节点时，改动都发生在 `Process` 组件内部的数据结构里；点「提交」才由 `publish()` 通过 `getData()` 收回来（`:115-128`）。
10. 保存成功后列表通过 `$emit('refresh', true)` 刷新（`:147-159,162-171`）——**子组件通知父组件**的另一种用法。

**读法**：`init(id)` 负责「把后端 JSON 装进设计器」，`publish()`/`sendToServer()` 负责「把设计器 JSON 存回后端」；画图细节在 `components/workflow/Process/index.vue`。**改流程画法看 `Process`，改存取链路看 `engine`。**

### 4.8 我要「改审批流程」怎么办

**不用改代码**——去「流程设计器」（`designer` → `engine`）编辑流程图，然后**提交**。后端在新建/更新时会直接转 BPMN 并部署一次；列表里的「部署」按钮用于再次部署。改完合同走的就是新流程。**这就是「流程可配置」的意义。**

## 六、面试高频问题

**Q1：你们的审批流程是怎么做的？**
A：基于 Activiti 6 工作流引擎。管理员用**流程设计器**（`workflow/engine/index.vue`）可视化配置审批流程、部署到引擎；合同发起审批时启动流程实例，按流程流转，产生的任务出现在审批人的「待办」里（`GET /activiti/process/taskList`）。

**Q2：审批流程是写死在代码里吗？**
A：**不是**。用可视化的流程设计器配置，存成一条流程设计记录（JSON：`basicSetting` + `processData`），后端再转 BPMN 并部署成流程定义。改审批链不用改代码，重新画图提交/部署即可。这和「菜单/字典不写死」是同一个思路。

**Q3：工作流前端分几块？**
A：三块——**定义期**（`designer`/`engine` 画流程、`activiti/definition`/`modeler` 管理定义和模型）、**运行期-我的**（`myApply` 我的申请）、**运行期-待办**（`todoItem/todo` 待办、`todoItem/done` 已办）。

**Q4：工作流引擎怎么和合同业务对接的？**
A：**解耦设计**。引擎只负责「谁审、审到哪」，不知道合同是什么；流程壳 `Audit.vue` 用 `:is="currentView"` 按 `flowType` 动态加载业务组件（`Audit.vue:106-113`），合同业务组件 `business/audit.vue` 再用 `conf.instanceId/contractId` 调 `GET /contract/contractDetail/audit` 拿合同内容渲染（`:400-406`）。两者通过业务 ID 关联。**注意 `conf` 不是「字段配置」，只是两个 id 的载体。**

**Q5：审批动作有哪些？怎么实现？**
A：同意、拒绝、驳回、转办、批量同意、撤销等，每个动作对应一个表单/入口（`workflow/form/` 下的 `Agree`/`Back`/`TransUser`/`BatchAgree`，拒绝和撤销是 `Audit.vue` 里的 `$prompt`）。**接口不同**：同意/编辑同意调 `/activiti/process/complete`，驳回调 `/jumpTo`，转办调 `/delegate`，批量同意调 `/batchComplete`，拒绝调 `/reject`，撤销调 `/cancelApply`（§4.6 有完整表）。

**Q6：「待办」和首页的待办是同一个吗？**
A：**同一个数据源**——都是 `GET /activiti/process/taskList`。首页 `zxcm-ui/src/views/dashboard/todo.vue:184-188` 是简版，`zxcm-ui/src/views/workflow/todoItem/todo/index.vue:316-322` 是详版（有批量同意、跳转审批等操作）。

**Q7：「流程模型」和「流程定义」有什么区别？**
A：**模型是设计态，定义是部署态**。这里有两套路线：① 主设计器把流程图存成流程设计记录（JSON），提交时后端直接转 BPMN 并部署；② Activiti 模型页走 `/activiti/modeler/*`，模型编辑/部署后变成「流程定义」（`/activiti/definition/*`），定义才是能实际运行的。`convert2Model` 还能把已部署的定义转回模型再编辑。

**Q8：流程设计器是你们自己写的吗？**
A：**主设计器不是从零写的，但也不是 bpmn-js**。`engine/index.vue` 是框架内自带的**卡片式可视化设计器**（`Process`/`FlowCard`/`PropPanel`，见 `zxcm-ui/src/components/workflow/Process/index.vue:2-4,114-143`），前端存 JSON、后端 `DesignerAdapterUtil.JSONToBPMN` 转 BPMN 部署（`WorkflowDesignerController.java:59-61`）。Activiti 定义/模型管理页是框架标准页。项目做的是**和合同业务的对接**：`Audit.vue` 按 `flowType` 动态加载 `business/audit.vue`、`auditList.vue` 的状态机联动、以及把流程绑定到合同类型。

**Q9：驳回和同意在技术上有什么区别？**
A：**不只是传变量不同，接口也不同**。同意调 `POST /activiti/process/complete`（`Agree.vue:114-116`）；驳回调 `POST /activiti/process/jumpTo`，body 里带 `toTaskId/toTaskName/comment/rejectConfig`（`Back.vue:200-202`，参数在 `:176-198`）。转办是 `POST /delegate`、批量同意是 `POST /batchComplete`、拒绝是 `POST /reject`、撤销是 `POST /cancelApply`。前端对应不同组件/弹窗。

**Q10：`activiti/definition` 页面能干什么？**
A：管理已部署的流程定义——列出定义、暂停/激活（`suspendOrActiveDefinition`）、删除部署（`delDefinition`）、把定义转回模型（`convert2Model`）。是框架标准的 Activiti 管理功能。

**卡 3：你们有两套「流程设计」入口，分别是什么？**
10 秒答案：主入口是自研卡片式设计器（`designer` + `engine` + `components/workflow/Process`），存 JSON、后端转 BPMN；另一个是 Activiti 官方老版模型编辑器，点模型页「在线设计」会新开 `{VUE_APP_BASE_API}/modeler/modeler.html?modelId=...`，加载的是 AngularJS `editor-app`，不是 bpmn-js。两套不要混答。

## 七、选型对比

### 7.1 工作流引擎：Activiti vs Flowable vs 自研

| | Activiti 6（本项目） | Flowable | 自研状态机 |
|---|---|---|---|
| 成熟度 | 高（老牌） | 高（Activiti 分支） | 低 |
| 可视化设计器 | ✅ 有 | ✅ 有 | ❌ 要自己写 |
| 版本 | **6.0.0.RC1**（`zxcm-workflow/pom.xml:33`） | — | — |
| 本项目选它 | RuoYi 工作流插件默认就是 Activiti | — | — |

**结论**：本项目用 Activiti 6，是**跟着 RuoYi 工作流插件走**。Flowable 是 Activiti 的后续分支（更活跃），但换引擎要重做集成，收益不明显。**答辩时说清「版本是 6.0.0.RC1，不是 7」**——这是个容易说错的点。

### 7.2 流程设计器：可视化 vs 写 XML

| | 可视化设计器（本项目） | 手写 BPMN XML |
|---|---|---|
| 使用门槛 | 低（拖拽） | 高（要懂 BPMN） |
| 出错率 | 低 | 高 |
| 改动成本 | 低 | 高 |

**结论**：给业务管理员用，必须可视化。手写 XML 只有开发者能维护，不现实。

### 7.3 流程与业务：紧耦合 vs 解耦

| | 解耦（本项目 `business/audit.vue`） | 紧耦合 |
|---|---|---|
| 引擎通用性 | ✅ 引擎不关心业务 | ❌ 引擎要知道合同 |
| 复用 | 一个引擎服务所有业务 | 每业务一套 |
| 复杂度 | 要设计「业务表单」接口 | 简单 |

**结论**：企业里工作流要服务多种业务（合同、请假、报销），必须解耦。**本项目的真实实现是「流程壳 + 按 `flowType` 动态加载业务组件 + 业务 ID 关联」**（`Audit.vue:106-113`）；`business/audit.vue` 自身仍是合同专用页面，不是通用动态表单。

## 本章小结

- 工作流前端两大块：**定义期**（`designer`/`engine` 画流程、`activiti/definition`/`modeler` 管定义）和**运行期**（`myApply` 我的申请、`todoItem` 待办/已办）。
- **流程可视化配置**（设计器），不写死在代码里；改流程重新画图部署即可。
- **流程与业务解耦**：引擎管流转；流程壳 `Audit.vue` 按 `flowType` 动态加载业务组件（`<component :is>`），`business/audit.vue` 负责展示合同内容，通过业务 ID 关联。
- 审批动作（同意/拒绝/驳回/转办/批量同意/撤销）各有对应入口，**且提交接口不同**（complete/jumpTo/delegate/batchComplete/reject/cancelApply）。
- 待办数据源 `GET /activiti/process/taskList`（首页简版 + 待办页详版共用）。
- **坦白点**：主流程设计器是框架带的**卡片式自研设计器**（不是 bpmn-js），Activiti 定义/模型管理页和通用审批表单也是框架自带；`business/audit.vue` 的 `conf` 只传两个 id，不是动态表单配置。本项目做的是「工作流 ↔ 合同业务」的对接。引擎版本是 **Activiti 6.0.0.RC1**（`zxcm-workflow/pom.xml:33`）。
