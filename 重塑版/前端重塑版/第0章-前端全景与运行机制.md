# 第 0 章 · 前端全景与运行机制

> 本章是全书的「地基章」。你打开浏览器输入网址，到屏幕上出现一个能点的页面，中间经历了**浏览器解析 → 加载 JS → 启动 Vue → 全局装配 → 权限校验 → 拉菜单 → 渲染页面**这一整条链路。这一章把这条链路讲透，后面每一章都是往这条链路的某个环节里塞细节。
>
> **本章第一次讲透的概念**：SPA（单页应用）、`main.js` 全局装配、目录即分层、前端一次「冷启动」的完整顺序。这些概念后面不再重复讲，只给一句回顾 + 指路。
>
> ⚠️ **行号说明（2026-10-19）**：本章行号默认以**答案册** `zhaoxin-contract/zxcm-ui` 为准；`zxcm-learn/zxcm-ui` 的 12 个文件已加 `★` 注释，行号整体后移。读注释版请看[附录 C · 注释版行号说明](附录-注释版行号说明.md)。

> **零基础先补概念（第一次看前端，先读这 4 条）**
>
> 1. **SPA（单页应用，Single Page Application）**：浏览器第一次只拿到一个 HTML 文件，之后所有页面都靠已经下载到浏览器里的 JS「换一块组件」画出来。所以点菜单时地址栏变了，但页面不会整页刷新。本项目只有 `zxcm-ui/public/index.html:148` 这一个 `<div id="app">` 容器，页面切换由 `<router-view>` 完成。Vue 侧完整解释见《Vue2 从 0 到精通》第 0 章 §2.3。
> 2. **入口文件**：打包后浏览器最先执行的那个 JS。它负责 import 依赖、把全局能力挂到 Vue 上、最后创建根实例。本项目入口是 `zxcm-ui/src/main.js`，最后一行动作是 `new Vue(...)`（`zxcm-ui/src/main.js:134-139`）。见《Vue2 从 0 到精通》第 1 章 §6.1。
> 3. **全局注册**：Vue 的 `Vue.component('名字', 组件)` 注册一次后，任何页面都能直接写这个标签，不用再 import。本项目的 `JTable`、`Pagination` 等就是这样注册的（`zxcm-ui/src/main.js:93-106`）。见《Vue2 从 0 到精通》第 4 章 §3.2。
> 4. **路由懒加载**：`() => import('...')` 不会在启动时执行，而是等用户真正进入该路由时才下载对应页面的 JS。本项目登录页就是懒加载的（`zxcm-ui/src/router/index.js:46`）。见《Vue2 从 0 到精通》第 5 章 §八。

## 一、这部分是做什么的

前端就干三件事：

1. **把界面画出来** —— 一个合同列表长什么样、按钮放哪儿、弹窗里有几个输入框。
2. **跟后端说话** —— 点「保存」，把表单数据发到后端接口；打开列表，从后端把数据拉回来。
3. **决定「我能不能点」** —— 没权限的按钮**直接消失**，不是点了报错。

这三件事分别对应本项目前端的三个底座：

| 干的事 | 靠什么 | 落点 | 全书哪章讲透 |
|---|---|---|---|
| 画界面 | Vue 2 组件 + Element-UI 组件库 | `src/views/`（每个页面一个文件夹） | 第 4~10 章 |
| 跟后端说话 | axios 封装 + 拦截器 | `src/utils/request.js` | **第 1 章** |
| 能不能点 | 动态路由 + `v-hasPermi` 指令 | `src/permission.js` + `src/directive/` | **第 2 章** |

**一句话定位**：第 0 章讲「前端这本机器怎么转起来」，第 1~3 章讲机器的三个核心零件（请求层、权限层、组件层），第 4~10 章讲「装在上面的一个个具体页面」。

## 二、站在架构师角度，为什么这么设计

这一节不写代码，只讲**为什么前端会是现在这个样子**。你答辩时被问「你们前端为什么用 Vue 不用 jQuery」，答案就在这里。

### 2.1 为什么是「单页应用（SPA）」而不是一堆独立的 HTML 页面

**老做法（MPA，多页应用）**：每个功能一个 `.html`，点链接就整页刷新，服务器返回一个新页面。

问题很明显：
- 每次跳转整页白屏闪一下，体验差。
- 后端要负责拼 HTML（模板引擎），前后端耦合。
- 页面间传数据只能靠 URL 参数或后端 session。

**本项目的做法（SPA）**：整个项目只有**一个 `index.html`**（在 `zxcm-ui/public/index.html`），所有页面都是 JS 在浏览器里**动态画出来**的。你点菜单跳页面，URL 变了，但页面**不刷新**——Vue Router 只是把「这个 div 里现在该显示哪个组件」换一下。

**为什么好**：
- 跳转快，没有白屏。
- 后端只返回**纯 JSON 数据**，不再管界面长什么样 → 前后端彻底分离，前端可以独立开发。
- 登录状态、用户信息等存在前端内存里，页面切换时不丢。

**代价（也是面试考点）**：
- 首次加载要下载一大坨 JS，首屏慢 → 本项目的解法是**路由懒加载**（下面 §2.3 讲）。
- SEO 不友好（搜索引擎抓不到动态渲染的内容）→ 本项目是**后台管理系统**，不需要被搜索引擎收录，所以这个代价可以接受。

### 2.2 为什么要有「全局装配」这一步

一个后台系统有几十个页面，每个页面都用到「分页组件」「表格组件」「字典标签」这些东西。如果每个页面都 `import` 一遍，会**在几十个文件里重复写同样的 import**。

本项目的解法：在 `main.js` 里**一次性全局注册**（`zxcm-ui/src/main.js:92-115`），之后任何页面**直接用标签名**就能使：

```js
// main.js:105
Vue.component("JTable", JTable);
```

注册之后，任何 `.vue` 文件里写 `<JTable ... />` 就能用，**不用 import**。这就是「约定优于配置」——你只要知道有哪些全局组件，就能读懂所有页面。

### 2.3 为什么路由要「懒加载」

`zxcm-ui/src/router/index.js` 里你能看到这种写法（如 `:46`、`:71`）：

```js
component: () => import('@/views/contract/contractDraft/index')
```

`() => import(...)` 是**懒加载**：这段代码不会在启动时执行，只有**用户真的点进这个路由**时，浏览器才去下载这个页面的 JS。

**为什么**：一个后台系统有上百个页面，如果启动时全下载，首屏白屏十几秒。懒加载之后，首屏只下载登录页 + 框架壳，其它页面用到才下。这是 SPA 首屏性能的标准解法。

### 2.4 为什么「目录结构」本身就是一种架构

打开 `zxcm-ui/src/`，你会看到：

```
src/
├── api/          所有「调后端接口」的函数，一个模块一个文件
├── assets/       静态资源（图片、样式）
├── components/   可复用的通用组件（JTable、文件上传……）
├── directive/    自定义指令（v-hasPermi 权限指令）
├── layout/       整体布局壳（左侧菜单 + 顶部导航 + 内容区）
├── router/       路由表
├── store/        Vuex 全局状态（token、用户信息、菜单）
├── utils/        工具函数（request.js 是核心）
├── views/        所有页面（一个业务模块一个文件夹）
├── App.vue       根组件
├── main.js       入口，全局装配
└── permission.js 路由守卫（进页面前的权限校验）
```

这个结构**不是随便分的**，它对应一条清晰的数据流：

```
用户点一个页面(views)
   → 页面调用 api/ 里的函数
       → api/ 用 utils/request.js 发请求
           → request.js 注入 token（token 从 store/ 拿）
               → 后端返回 JSON
           ← 页面把数据渲染出来
```

**答辩时这样讲**：前端目录是「按职责分层的」，`views` 是「界面层」、`api` 是「接口层」、`utils/request.js` 是「传输层」、`store` 是「共享状态层」。一个页面要干活，必须**自顶向下**经过这几层，不能跳——就像后端 Controller → Service → Mapper 不能跳过 Service 一样。**这是前后端架构上少见的「同构」**（结构相似），是很好的答辩素材。

> ⚠️ 注意：别拿后端当心智模型硬套。前端这么分是**为了「一个功能改哪些文件一目了然」**，而不是为了「层与层职责隔离」。比如前端没有「Service 层」，业务逻辑直接写在页面的 methods 里是很正常的。详见第 3 章 §2.1。

## 四、怎么读这套前端代码

因为前端整包沿用答案册、你不从零敲，这一节教你**怎么读**。

### 4.1 读懂一个 `.vue` 文件的三段结构

任何页面 `.vue` 文件都是三段：

```vue
<template>  <!-- 一段 HTML：界面长什么样 -->
  <div class="app-container">
    <el-button @click="handleAdd">新增</el-button>
  </div>
</template>

<script>    <!-- 一段 JS：数据 + 方法 -->
export default {
  data() { return { list: [] } },      // 这个页面的「数据」
  created() { this.getList() },        // 页面加载时干啥
  methods: {
    handleAdd() { ... },               // 点了「新增」干啥
    getList()   { ... },               // 从后端拉列表
  }
}
</script>

<style>     <!-- 一段 CSS：长什么样（可选） -->
</style>
```

**读页面的顺序**（很重要，后面每章都按这个顺序讲）：
1. 先看 `<template>` 里的**按钮**，看每个按钮 `@click` 绑的哪个方法 —— 这告诉你「这个页面能干什么」。
2. 再看 `<script>` 的 `methods`，顺着方法名找到它调用了 `api/` 里的哪个函数 —— 这告诉你「这个动作打了哪个后端接口」。
3. 最后看 `data()` —— 这告诉你「这个页面的状态有哪些」。

### 4.4 找到「一个按钮打了哪个后端接口」的标准动作

这是前端答辩最高频的追问：**「你点这个按钮，后端发生了什么？」**

三步走，以「合同列表页的『创建合同』为例」：

1. 在页面里搜按钮文字「创建合同」→ 找到 `zxcm-ui/src/views/contract/contractDraft/index.vue:76-83` 的 `<el-button>`；权限指令在 `:77`，`@click="handleAdd"` 在 `:82`。
2. 顺着 `handleAdd` 找到 `methods` 里的定义 → `zxcm-ui/src/views/contract/contractDraft/index.vue:385-387`。注意它这里没有直接调后端，而是打开子组件：`this.$refs.createContract.add()`（`:386`）。

## 五、一次「冷启动」的完整生命流程

这一节把 §2 讲的机制串成一条线：**你在浏览器地址栏输入 `http://localhost` 回车，到看见登录页，中间发生了什么。**

```
① 浏览器请求站点
   └─ dev 服务器（vue.config.js 里配的，见 §6 Q10）返回 zxcm-ui/public/index.html
      · 源码里只有一个 <div id="app"></div> 容器和「系统加载中」的占位动画（zxcm-ui/public/index.html:148-159）
      · 入口 <script> 是 Vue CLI 构建时自动注入的，源码 index.html 里看不到它

② 浏览器下载并执行 app.js（就是 src/main.js 打包后的产物）

③ main.js 自上而下执行「全局装配」
   ├─ import Vue / Element / store / router / directive / plugins ...  (main.js:1-69)
   ├─ 注册全局原型方法：this.download / this.parseTime ...           (main.js:72-90)
   ├─ 注册全局组件：JTable / Pagination / DictTag ...                 (main.js:93-106)
   ├─ 装插件：Vue.use(directive) / Vue.use(plugins) ...               (main.js:108-114)
   ├─ 装字典系统：DictData.install()                                  (main.js:115)
   └─ import "./permission"  ← 注意：这一行会「注册路由守卫」（第 1 步就生效） (main.js:24)

④ new Vue({ el:'#app', router, store, render: h => h(App) })          (main.js:134-139)
   └─ 把 App.vue 渲染进 <div id="app">，Vue 应用正式启动

⑤ 启动时，Vue Router 发现「用户要去某个路由」（默认是 /）
   └─ 触发全局前置守卫 router.beforeEach（定义在 src/permission.js）
      ├─ 开进度条 NProgress.start()                                    (permission.js:15)
      ├─ 判断有没有 token（getToken() 从 Cookie 读）                    (permission.js:36)
      │   ├─ 没有 token：
      │   │   └─ 如果目标页在白名单（/login 等）→ 放行
      │   │       否则 → 跳转 /login?redirect=原地址                     (permission.js:91)
      │   └─ 有 token → 进入下一段
      ├─ 有 token 但 store 里还没用户信息（roles 为空）：
      │   ├─ 调 GetInfo（GET /getInfo）拿用户/角色/权限
      │   ├─ 调 GenerateRoutes（GET /getRouters）拿菜单 → 转成路由 → router.addRoutes
      │   └─ 加水印（watermark）
      └─ NProgress.done()，放行 next()
```

**关键结论（答辩时能说出这几条，层次就上去了）**：

- **「权限是从后端拉菜单得来的」**：前端路由不是写死的，而是启动时 `GET /getRouters` 从后端拿「当前用户能看哪些菜单」，再动态 `addRoutes`。所以给一个用户多配个角色，前端菜单**自动多出来**——不用改前端代码。
- **「`import './permission'` 这一行没有导出任何东西」**：它 import 的副作用是**注册了全局守卫**。这是 Vue 项目里很常见的「副作用导入」，第一次看会懵。
- **「登录页本身不请求用户信息」**：因为 `permission.js` 先判断 token，没 token 直接跳登录、根本不进 GetInfo，省掉一次无效请求。

> 这条链路对应后端：`GET /getRouters` 和 `GET /getInfo` 是 RuoYi 框架的登录鉴权接口，具体实现见《后端重塑版》第 1 章的鉴权部分。

### 5.1 逐行读：`main.js` 最后 8 行到底在干什么

这是全站最核心的 8 行——前面所有 import、注册、插件，都是为它们做准备的：

```js
// zxcm-ui/src/main.js:132-139
Vue.config.productionTip = false;
new Vue({
  el: "#app",
  router,
  store,
  render: (h) => h(App),
});
```

| 行号 | 代码 | 这一行在干什么 | 为什么这么写 |
|---|---|---|---|
| `:132` | `Vue.config.productionTip = false` | 关掉开发模式的启动提示 | 控制台干净，不影响功能 |
| `:134` | `new Vue({` | 创建整个应用的**根实例** | 前面的 import、全局注册、插件安装都是「准备材料」，到这里才真正点火 |
| `:135` | `el: "#app"` | 把根实例挂到 `index.html` 的 `#app` 容器上 | 容器在 `zxcm-ui/public/index.html:148`；挂载后里面的占位内容由 Vue 接管 |
| `:136` | `router` | 把路由实例交给根实例 | 这样模板里的 `<router-view>` 才知道当前该渲染哪个页面 |
| `:137` | `store` | 把 Vuex 仓库交给根实例 | 所有组件才能通过 `this.$store` 取 token、角色、菜单 |
| `:138` | `render: (h) => h(App)` | 指定根组件是 `App.vue` | `h` 是 Vue 传入的 `createElement`；`App.vue:3` 里只有一个 `<router-view />`。用 render 函数而不是在根实例写 template，是 Vue CLI 运行时构建的常见写法 |
| `:139` | `});` | 结束配置，开始挂载 | 守卫在 `zxcm-ui/src/main.js:24` 已经注册好，首次路由导航会经过它 |

> 根实例、`render` 函数、`el` 挂载点的原理见《Vue2 从 0 到精通》第 1 章 §6.1、§6.2。

### 5.2 动手验证：亲眼看到「不刷新」和「懒加载」

前提：后端在 `8080` 启动；在 `zxcm-ui` 目录执行 `npm run dev`（端口由 `zxcm-ui/vue.config.js:12` 决定，默认 80），浏览器打开 `http://localhost/`。

1. **看入口 HTML**：登录前按 `F12` → Network → 勾选 `Preserve log` → 刷新页面。第一条 `localhost` 请求的 Type 是 `document`；点它的 Response，能看到 `<div id="app">` 和「系统加载中」占位（`zxcm-ui/public/index.html:148-159`）。
2. **看 SPA 不整页刷新**：登录后清空 Network，点左侧任意菜单。预期：地址栏变成对应路径，但 Network 里**没有新的 document 请求**，页面内容直接切换——这是「只换组件、不换页面」。
3. **看路由懒加载**：第一次进入一个此前没打开过的页面时，Network 的 `JS` 过滤器里会多出该页面的 chunk；第二次再进同一页面时，通常直接读浏览器缓存，不再下载。对应写法 `component: () => import('@/views/...')`（如 `zxcm-ui/src/router/index.js:46`）。
4. **对比「源代码」和「Elements」**：DevTools → Elements 展开 `<div id="app">`，能看到布局、菜单、表格；而在新标签页打开 `view-source:http://localhost/`，看到的仍只是占位 HTML。这个对比能直观证明「页面是 JS 在浏览器里画出来的」。

## 六、面试高频问题

**Q1：你们前端是什么架构？**
A：前后端分离的 Vue 2 SPA。整个应用只有一个 `index.html`（`zxcm-ui/public/index.html:148` 只有一个 `#app` 容器），所有页面由 Vue Router 动态渲染；后端只提供 JSON 接口。目录按职责分层：`views`（页面）/ `api`（接口）/ `utils/request.js`（传输）/ `store`（共享状态）。

**Q2：为什么用 Vue 2 不用 Vue 3 / React？**
A：项目底层是 RuoYi-Vue-Plus 4.0.1s（根目录 `pom.xml:9`），它当时的技术选型就是 Vue 2 + Element-UI（`zxcm-ui/package.json:64` Vue `2.6.12`、`:47` Element-UI `2.15.6`）。选 Vue 2 的现实原因是：Element-UI 只支持 Vue 2（Vue 3 要用 Element-Plus），而 Element-UI 的中文后台组件生态最成熟、表格/表单开箱即用。详见 §七选型对比。

**Q3：SPA 首屏为什么慢？你们怎么优化？**
A：SPA 首屏要把框架和入口 JS 全下载完才能渲染。本项目用**路由懒加载**（`component: () => import(...)`）把页面拆成小块，首屏只加载登录页和框架壳；另外 `vue.config.js` 配了 `compression-webpack-plugin` 做 gzip 压缩（`zxcm-ui/vue.config.js:61-69`）。

**追问：懒加载之后，第一次进某个页面还是会顿一下，怎么解释？**
A：那一次顿是在下载这个页面自己的 JS chunk；下载完浏览器会缓存，之后再进就快了。在 Network 的 `JS` 过滤器里能看到「首次多出来、第二次消失」的请求。

**Q4：前端怎么知道「当前用户是谁、有什么权限」？**
A：启动时 `permission.js` 拦截路由，调 `GET /getInfo` 拿用户信息和权限码，存进 Vuex（`zxcm-ui/src/store/modules/user.js:67-95`）；调 `GET /getRouters` 拿菜单生成动态路由。**菜单和权限都来自后端**，前端不写死。

**Q5：`main.js` 里 `import './permission'` 这行没接收任何导出，为什么还要写？**
A：因为 `permission.js` 的**副作用**是执行 `router.beforeEach(...)` 注册全局路由守卫。import 一个模块，模块顶层的代码就会执行，所以这行的作用不是「拿东西」而是「跑一遍守卫注册」。这是经典的副作用导入。

**Q6：一个页面 `.vue` 文件的分工是什么？**
A：三段——`<template>` 管界面（HTML）、`<script>` 管数据和逻辑（`data` 存状态、`methods` 存动作、`created/mounted` 是生命周期钩子）、`<style>` 管样式。读页面时先看 template 里的按钮 @click，再顺着方法找到调用的 api 函数，就能定位后端接口。

**Q7：为什么很多组件不用 import 就能用？**
A：它们在 `main.js:93-106` 全局注册了（`Vue.component('JTable', JTable)`），全局注册的组件在任何页面直接用标签名。方法类的（`this.download`）是用 `Vue.prototype.x = ...` 挂的（`main.js:72-84`）。

**Q8：前端目录为什么这么分？**
A：按职责分层，和「一次请求的数据流」对应：`views`（界面）→ `api`（接口定义）→ `utils/request.js`（传输）→ `store`（共享状态）。改一个功能时能一眼知道动哪几个文件。

**Q9：`App.vue` 和 `layout/` 是什么关系？**
A：`App.vue` 是**根组件**，也是路由的入口容器（模板里就一个 `<router-view />`，`zxcm-ui/src/App.vue:3`）。`layout/` 是**后台的整体框架壳**——左侧菜单、顶部导航、标签页、内容区，登录进去后的所有页面都渲染在 layout 的内容区里。登录页不走 layout（`zxcm-ui/src/router/index.js:44-48` 里 login 是顶级路由，没有 Layout 包裹）。

**Q10：dev 环境前端请求 `/dev-api/xxx`，后端在 8080，怎么连上的？**
A：靠 webpack dev-server 的**代理**。`zxcm-ui/.env.development:8` 里 `VUE_APP_BASE_API = '/dev-api'`，`zxcm-ui/vue.config.js:35-44` 配了把 `/dev-api` 开头的请求代理到 `http://localhost:8080`（`:38`），并 `pathRewrite`（`:40-42`）把 `/dev-api` 前缀去掉。所以业务代码里永远只写接口路径，前缀由环境变量统一提供。补充一个容易被忽略的点：本项目的后端其实也配了宽松的全局 CORS（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/ResourcesConfig.java:50-67`），所以代理的主要价值不只是「绕开跨域」，还有统一前缀、环境切换和生产同构。**逐行拆解见[附录 B](附录B-零基础精读：一次请求的完整流程.md)**。

### 6.1 本章答辩卡（3 组追问级问答）

**追问 1：你怎么证明你们是 SPA，不是后端拼好的多个页面？**
10 秒答案：入口 HTML 只有一个 `<div id="app">` 占位，真正的页面由 `main.js` 创建根实例后交给路由组件渲染；点菜单时地址变了，但浏览器不再请求新的 document。
证据：`zxcm-ui/public/index.html:148-159`、`zxcm-ui/src/main.js:134-139`、`zxcm-ui/src/App.vue:3`。

**追问 2：`main.js` 里哪些事必须赶在 `new Vue` 之前做？**
10 秒答案：全局组件和原型方法注册、插件安装、路由守卫注册都要先做。根实例一挂载就开始渲染并触发首次导航，之后再注册就赶不上首屏了。
证据：`zxcm-ui/src/main.js:72-115`（注册都在 `:134` 之前）、`zxcm-ui/src/permission.js:14`（守卫注册）。

**追问 3：给你一个没看过的页面，怎么最快找到它调的接口？**
10 秒答案：先看模板按钮的 `@click`，再进 `methods` 找同名方法，最后看它调用的 `api/` 函数；`api` 函数里的 `method + url` 就是后端接口。如果方法只是打开子组件，还要再进子组件找真正的接口调用。
证据：按钮 `zxcm-ui/src/views/contract/contractDraft/index.vue:76-83` → `handleAdd` `:385-387` → 子组件 `zxcm-ui/src/views/contract/contractDraft/createContract.vue:547` → API `zxcm-ui/src/api/contract/contractDraft.js:48-54`。

## 七、选型对比：为什么是这套技术栈

### 7.1 Vue 2 vs Vue 3 vs React

| 维度 | Vue 2（本项目） | Vue 3 | React |
|---|---|---|---|
| 配套 UI 库 | Element-UI（成熟、中文后台组件最全） | Element-Plus | Ant Design |
| 学习曲线 | 平缓，模板语法贴近 HTML | 稍陡（组合式 API） | 陡（JSX + 大量生态选择） |
| 底层框架兼容 | ✅ RuoYi 4.0.1s 就是 Vue 2 | 需 RuoYi-Vue-Plus 5.x | 与 RuoYi 不匹配 |
| 本项目选它的原因 | **跟着 RuoYi 底座走**；Element-UI 表格/表单开箱即用，后台开发效率高 | — | — |

**答辩一句话**：选 Vue 2 不是因为它比 Vue 3 好，而是因为**底座 RuoYi-Vue-Plus 4.0.1s 就是 Vue 2**，且后台管理系统重「表单+表格」，Element-UI 这套组件的成熟度最高。换 Vue 3 意味着换底座，收益（性能）对后台系统不明显，成本却很大。

### 7.2 Element-UI vs 自研组件

本项目的标准表格用 Element-UI 的 `<el-table>`，但**业务列表页用的是自研的 `<JTable>`**（`main.js:105`）。

| | Element-UI `<el-table>` | 肇新自研 `<JTable>` |
|---|---|---|
| 来源 | 开源组件库 | 本项目封装（`src/components/JTable`） |
| 适用 | 通用表格、树表、简单列表 | 业务列表（带搜索栏/工具条/分页的一整套） |
| 本项目用在哪 | 合同类型的树表（`views/system/form/index.vue`）、弹窗内小表 | 90% 的列表页（合同列表、合作方列表……） |

**为什么自己封装**：后台系统 90% 的列表页结构一模一样（搜索条件 + 工具按钮 + 表格 + 分页），如果每个页面都堆一遍 Element 原生代码，会有大量重复。`JTable` 把这套「标准列表页骨架」封成一个组件，页面只要传列定义和数据源。**这是「约定优于配置」的典型应用**，也是本项目前端最大的自研亮点。详见第 3 章。

### 7.3 axios vs fetch vs Vue-Resource

| | axios（本项目） | 原生 fetch | vue-resource（已废弃） |
|---|---|---|---|
| 拦截器 | ✅ 内置请求/响应拦截器 | ❌ 要自己包装 | ✅ |
| 自动 JSON | ✅ 自动解析 | ❌ 要 `.json()` | ✅ |
| 取消请求 / 超时 | ✅ | 需 AbortController | ✅ |
| 生态 | 最主流 | 浏览器原生 | 早已停维护 |

**为什么用 axios**：本项目需要在**每个请求自动注入 token**（`request.js` 请求拦截器）、**统一处理 401/500**（响应拦截器）、**统一防重复提交**。这些正好是 axios 拦截器的强项，用 fetch 得自己从头包一层。详见第 1 章。

## 本章小结

- 前端 = 画界面（Vue + Element）+ 跟后端说话（axios）+ 决定能不能点（动态路由 + 指令）。
- SPA 的核心：只有一个 html，页面靠 JS 动态渲染，跳转不刷新。
- `main.js` 是全站「公共字典」——所有全局组件和方法都在这儿注册，读代码卡住先回头看 `main.js` + `plugins/`。
- 一次冷启动链路：`index.html → main.js 装配 → permission.js 守卫 → getInfo/getRouters → 渲染页面`。
- `src/views/` 是「找页面」的地图，一个业务模块一个文件夹。

**下一章**：第 1 章讲全站最核心的一个文件 —— `src/utils/request.js`。所有跟后端的通信都经过它，token 注入、401 处理、防重复提交都在这一层完成。
