# 第 1 章 · 请求层与登录鉴权

> 全站所有跟后端的通信都经过**一个文件**：`zxcm-ui/src/utils/request.js`。它干三件事：给每个请求**带上 token**、统一**处理 401/500 等错误**、**拦住连点重复提交**。此外还导出下载文件的 `download` 函数。这一章把它逐行讲透。
>
> ⚠️ **行号说明（2026-10-19）**：本章行号默认以**答案册** `zhaoxin-contract/zxcm-ui` 为准；`zxcm-learn/zxcm-ui` 的 12 个文件已加 `★` 注释，行号整体后移。读注释版请看[附录 C · 注释版行号说明](附录-注释版行号说明.md)。

> **零基础先补概念（第一次看请求层，先读这 4 条）**
>
> 1. **HTTP 请求/响应**：浏览器发一份「请求」（方法 + URL + 请求头 + 请求体），服务器回一份「响应」（状态码 + 响应头 + 响应体）。本项目后端业务数据用 JSON 返回，如 `{ code, msg, rows, total }`。
> 2. **axios 实例**：axios 是浏览器里发请求的库；`axios.create({...})` 是先建一个「配好默认值的客户端」，之后所有接口都复用它，`baseURL`、超时只写一次（`zxcm-ui/src/utils/request.js:19-24`）。
> 3. **拦截器（interceptor）**：在请求真正发出前、响应刚回来后自动执行的一段统一代码。本项目在请求拦截器里加 token，在响应拦截器里判错误码（`zxcm-ui/src/utils/request.js:27`、`:71`）。Vue 侧通用原理见《Vue2 从 0 到精通》第 7 章 §7.3、§7.4。
> 4. **Promise**：一个「将来才有结果」的占位对象；用 `.then()` 拿成功值、`.catch()` 接失败值。`request(...)` 返回的就是 Promise，页面里 `listXxx(...).then(res => ...)` 就是在等这个结果。见《Vue2 从 0 到精通》第 0 章 §5.11。

## 一、这部分是做什么的

前端有**几十个页面、上百个接口调用**，如果每个调用都自己写「加 token、判断错误码、弹提示」，会重复几百遍。所以本项目把所有「每次请求都要做一遍的事」**抽到一个公共文件里**：

```
页面  →  api/xxx.js（定义"我要调哪个接口"）  →  utils/request.js（统一处理）
                                                    ├─ 请求拦截器：加 token、防重复
                                                    └─ 响应拦截器：判错误码、弹提示、处理 401
```

| 谁 | 文件 | 职责 |
|---|---|---|
| **传输层** | `src/utils/request.js` | axios 实例 + 两个拦截器 + `download` |
| **接口层** | `src/api/**/*.js` | 一个业务模块一个文件，每个函数 = 一个后端接口 |
| **凭据层** | `src/utils/auth.js` | 读写 token（存 Cookie） |
| **会话状态** | `src/store/modules/user.js` | 存用户信息、角色、权限；登录/登出动作 |
| **入口页** | `src/views/login.vue` | 登录表单、验证码、记住密码 |

**一句话定位**：`request.js` 是全站唯一的「出口」和「入口」——所有请求从这里出去，所有响应从这里回来。**读懂它 = 读懂了前端跟后端的所有约定**。

## 二、站在架构师角度，为什么这么设计

### 2.1 为什么要有「拦截器」这层

axios 提供了**拦截器（interceptor）**：请求发出**前**先过一遍「请求拦截器」，响应回来**后**先过一遍「响应拦截器」。这正好把「每次都要做的事」集中了：

**请求拦截器要做的事**（`request.js:27-68`）：
1. **加 token**：登录后后端给的 token 存在 Cookie 里，每次请求从 Cookie 读出来塞进请求头。
2. **GET 参数转换**：GET 请求的参数（对象）转成 `?a=1&b=2` 拼到 URL 上。
3. **防重复提交**：POST/PUT 请求在 1 秒内如果「同 URL + 同数据」再来一次，直接拒掉。

**响应拦截器要做的事**（`request.js:71-132`）：
1. **统一判错误码**：后端约定成功码是 `200`，其它码代表不同错误。
2. **401 单独处理**：token 过期 → 弹「重新登录」框 → 登出 → 跳登录页。
3. **只把 `res.data` 返回给业务**：页面拿到的直接是后端返回的 JSON，不用再 `.data.data`。

**为什么这么设计**：这叫**关注点分离**。业务页面只关心「我调的结果是什么」，不关心「token 是怎么加的」「错了该怎么弹窗」。换成没这层，每个页面都得写一遍 `if (code === 401) ...`，改一次要改一百个地方。

### 2.2 为什么 token 要放 Cookie，还要加 `Bearer ` 前缀

- **放 Cookie 而不是 localStorage**：Cookie 读写方便（`js-cookie`），同源请求会自动带上，后端也能读到。本项目 token 存在 Cookie，key 是 `Admin-Token`（`zxcm-ui/src/utils/auth.js:3`）；`setToken` 没有传 `expires`（`:9-11`），所以它是**会话 Cookie**——关浏览器通常清除，刷新页面不受影响。
- **加 `Bearer ` 前缀**：这是 **OAuth 2.0 / JWT 的行业惯例**，请求头格式 `token: Bearer xxxxx`。后端 RuoYi 的鉴权过滤器就是按这个格式解析的。**你答辩被问「token 怎么用的」就答：存 Cookie，每次请求由拦截器取出拼成 `Bearer xxx` 放进请求头 `token` 字段。**

> ⚠️ **注意一个易错点**：登录接口本身**不能**带 token（因为还没登录，没 token），所以 `api/login.js:15-17` 给登录请求加了 `headers: { isToken: false }`。拦截器读到这个标记就跳过加 token（`request.js:29,32`）。`/captchaImage`（验证码）、`/register`（注册）、`/getTenants`（租户列表）同理。

### 2.3 为什么「防重复提交」要放在前端

后端的防重复提交**费数据库查询**（每次请求都要查一遍），前端拦一道能挡掉**绝大部分手抖连点**，省下大量无效请求。所以这是「前端为主、后端兜底」的双保险。

本项目的实现（`request.js:42-64`）：把「上一次 POST/PUT 的 URL + 数据 + 时间」存进 `sessionStorage`（`cache.session`），新请求来了跟它比——**如果「同 URL」且「同数据」且「距上次不到 1000ms」，就判定重复，直接 reject**。

**一个坦白点**：这个判断有个明显缺陷——**它比的是「和上一次请求」而不是「和所有进行中的请求」**。如果用户快速点了 A、B 两个不同按钮，再点 A，`sessionObj` 已被 B 覆盖，A 就能再发一次。所以要真正稳，还得靠后端兜底。**这一点面试时主动说出来，比藏着强**。

### 2.4 为什么 401 要用 `isRelogin.show` 这个开关

token 过期时，页面上可能**同时有好几个请求**在飞（首页一进来就发好几个），如果每个 401 都弹一个「重新登录」框，会**弹出一堆框**。所以用一个模块级变量 `isRelogin.show` 当锁（`request.js:13`）：第一个 401 弹框并置 `true`，后面的 401 看到是 `true` 就**不重复弹**。这是个很典型的**「并发去重」小技巧**，答辩点是「怎么避免弹窗风暴」。

### 4.2 `api/` 层的写法约定（**必须会认**）

每个 `api/xxx.js` 文件都是这个套路，以 `src/api/conf/signingSubject.js` 为例：

```js
// zxcm-ui/src/api/conf/signingSubject.js:1-52（节选）
import request from '@/utils/request'

// 查询列表（:4-10）
export function listSigningSubject(query) {
  return request({ url: '/conf/signingSubject/list', method: 'get', params: query })
}
// 新增
export function addSigningSubject(data) {
  return request({ url: '/conf/signingSubject', method: 'post', data })
}
// 修改
export function updateSigningSubject(data) {
  return request({ url: '/conf/signingSubject', method: 'put', data })
}
// 删除
export function delSigningSubject(id) {
  return request({ url: '/conf/signingSubject/' + id, method: 'delete' })
}
```

**规律**：
- `url` 就是后端接口路径（不含 `/dev-api`，前缀由 `baseURL` 自动加）。
- **RESTful 风格**：查 `GET /list`、增 `POST`（无后缀）、改 `PUT`、删 `DELETE /{id}`。这套风格和[后端重塑版 第 1 章](../后端重塑版/第1章-签约主体管理.md)的 Controller 一一对应。
- 函数名几乎永远是 `listXxx / getXxx / addXxx / updateXxx / delXxx`。

> **读懂任意接口调用的捷径**：看到页面里 `import { listXxx } from '@/api/xxx'`，直接去 `src/api/xxx.js` 找 `listXxx`，看 `method` + `url`，就知道后端接口是什么。

### 4.4 我想改「请求超时时间」/「加一个公共请求头」怎么办

- **改超时**：`request.js:23` 的 `timeout: 10000`（毫秒）。
- **加公共请求头**：在 `zxcm-ui/src/utils/request.js:34` 之后（`if` 块结束、`return config` 之前）写 `config.headers['xxx'] = 'yyy'`。
- **改成功码判断**：`:73` 决定「什么算成功码」（`res.data.code || 200`），`:104-110` 决定「非 200 怎么处理」；如果后端成功码不是 200，这两处要一起改。
- **下载接口超时**：注意下载用的是**单独的超时**（`request.js:141`，`3 * 60 * 1000` = 3 分钟），因为导出大数据慢。

### 4.5 逐行读：请求拦截器（`zxcm-ui/src/utils/request.js:27-41`）

```js
service.interceptors.request.use(config => {
  // 是否需要设置 token
  const isToken = (config.headers || {}).isToken === false
  // 是否需要防止数据重复提交
  const isRepeatSubmit = (config.headers || {}).repeatSubmit === false
  if (getToken() && !isToken) {
    config.headers['token'] = 'Bearer ' + getToken() // 让每个请求携带自定义token
  }
  // get请求映射params参数
  if (config.method === 'get' && config.params) {
    let url = config.url + '?' + tansParams(config.params);
    url = url.slice(0, -1);
    config.params = {};
    config.url = url;
  }
  // ……防重复提交在 :42-64，最后 :65 return config
})
```

| 行号 | 这一行在干什么 | 为什么这么写 |
|---|---|---|
| `:27` | 向 axios 注册「请求发送前」的钩子 | 每个接口都要加 token，集中在这里只写一次 |
| `:29` | 读请求配置里的自定义头 `isToken === false` | 登录/验证码等「还没有 token」的接口用它主动跳过（`zxcm-ui/src/api/login.js:15-17`） |
| `:31` | 读 `repeatSubmit === false` | 个别接口如果不想被防重复逻辑拦截，可以单独关闭（本项目的登录接口仍会走防重复） |
| `:32` | 只有「Cookie 里有 token」且「没主动跳过」才进入 | 避免给登录接口塞一个 `Bearer undefined` |
| `:33` | 把 `Bearer ` + token 放进请求头 `token` 字段 | 后端鉴权过滤器按这个格式解析；key 名和 `Bearer ` 前缀是前后端约定 |
| `:36` | 只处理 GET 且有 `params` 的请求 | POST 的数据在请求体里，不需要拼 URL |
| `:37` | 用 `tansParams` 把对象转成 `a=1&b=2&` | `tansParams` 的实现在 `zxcm-ui/src/utils/ruoyi.js:238-258`，每个键值后面都会加 `&` |
| `:38` | `slice(0, -1)` 去掉最后一个多余的 `&` | 否则 URL 会以 `&` 结尾 |
| `:39-40` | 清空 `params`，把拼好的 URL 写回 `config.url` | 否则 axios 会再把 `params` 追加一次，参数重复 |
| `:65` | `return config` | 拦截器必须把配置交回去，axios 才会真正发请求 |

**紧接着的 `:42-64` 是防重复提交**：只拦 POST/PUT；把 `url + data + 时间` 存进 `sessionStorage`；下一次请求若「同 URL、同数据、间隔小于 1000ms」就 `Promise.reject`（`:56-59`）；否则覆盖旧记录（`:61`）。它只和「上一次请求」比较，这是 §2.3 说的缺陷。

### 4.6 动手验证：在 DevTools 里把请求层看穿

前提：前端打开 `http://localhost/`，后端在 `8080`；DevTools → Network 勾选 `Preserve log`。

1. **登录请求不带 token**：在登录页输入账号密码、点登录，找到 `login` 请求。预期：Request Headers 里**没有** `token`；Payload 里有 `username/password/code/uuid/tenantId`（`zxcm-ui/src/api/login.js:6-12`、`:15-17`）。
2. **后续请求带 token**：找紧随其后的 `getInfo`、`getRouters` 请求，Request Headers 里应有 `token: Bearer ...`（`zxcm-ui/src/utils/request.js:32-34`）。
3. **token 存在 Cookie**：Application → Cookies → `http://localhost`，能看到 `Admin-Token`（`zxcm-ui/src/utils/auth.js:3`）。
4. **防重复提交**：打开任意新增/编辑弹窗，清空 Network，在 1 秒内连点两次「确定」。预期：只发出一个 POST/PUT；Console 出现 `[请求地址]: 数据正在处理，请勿重复提交`（`zxcm-ui/src/utils/request.js:56-59`）。
5. **401 弹窗**：在 Application 里把 `Admin-Token` 的值改成任意字符串，再点一个会发请求的菜单。预期：弹出「登录状态已过期…」确认框（`zxcm-ui/src/utils/request.js:80-97`）。点「取消」留在本页，点「重新登录」清 token 并回登录页。
6. **下载走单独通道**：合同台账页点「导出」，Network 里 `contract/book/export` 的响应是二进制文件流，浏览器弹出保存框，文件名形如 `合同台账_时间戳.xlsx`（`zxcm-ui/src/views/contract/book/index.vue:377-383`）。

## 五、一个操作的完整生命流程

### 5.1 【登录】从点「登录」按钮到进入首页

```
① 用户在 views/login.vue 填账号密码验证码，点「登录」
   └─ 触发 handleLogin()                                        (login.vue:227)

② handleLogin 里 el-form 表单校验通过后
   ├─ 若勾了「记住密码」：把用户名/加密后的密码写 Cookie     (login.vue:231-239)
   └─ 若租户为空：先调 getTenantList(用户名) 自动选租户        (login.vue:251)
   └─ 再 this.$store.dispatch('Login', this.loginForm)         (login.vue:274)

③ store 的 Login action 执行                                   (store/modules/user.js:49)
   └─ 调 api/login.js 的 login() → POST /login（`zxcm-ui/src/api/login.js:5-21`；请求头 isToken:false，不带 token）
      · 请求经过 request.js 请求拦截器：因为没有 token 且 isToken=false，跳过加 token
      · 但防重复提交仍生效（POST 会被拦）

④ 后端校验通过，返回 { code:200, data:{ token:'xxxx' } }

⑤ Login action 拿到 token
   ├─ setToken(token)  → 写 Cookie 'Admin-Token'                (user.js:57)
   └─ commit('SET_TOKEN', token) → 存进 Vuex                    (user.js:58)
   └─ resolve() 通知 handleLogin 成功

⑥ login.vue 里跳转（通常是跳 redirect 参数或 '/'）              (login.vue:276)

⑦ 跳转触发路由守卫 router.beforeEach（见 permission.js:14）
   └─ 这次「有 token」了 → 走 store.getters.roles.length === 0 分支 (permission.js:43)
      ├─ 调 GetInfo → GET /getInfo，拿用户信息 + roles + permissions (user.js:67)
      ├─ 调 GenerateRoutes → GET /getRouters，拿菜单生成动态路由   (见第 2 章)
      ├─ 加页面水印（用户名 + 工号 + 日期）                       (permission.js:65)
      └─ next({...to, replace:true}) 正式进入目标页
```

**关键点**：**「登录」和「拿用户信息」是两次请求**。`POST /login` 只换 token；token 有了之后，路由守卫才通过 `GET /getInfo` 换「我是谁、我能干啥」。这样设计的好处是：刷新页面时只要 Cookie 里有 token，就能**重新拉一次用户信息**，不会丢登录态。

### 5.2 【普通业务请求】以「查询签约主体列表」为例

```
① 进签约主体页面，created 钩子（:707-709）调 this.getList()，方法定义在 :712
   (views/conf/signingSubject/index.vue:707-712)
   └─ getList 调 api 里的 listSigningSubject(this.queryParams)（api 定义在 :4-10）

② api 函数：request({ url:'/conf/signingSubject/list', method:'get', params: query })
   （zxcm-ui/src/api/conf/signingSubject.js:4-10）

③ 请求拦截器（zxcm-ui/src/utils/request.js:27-41）
   ├─ 有 token → config.headers['token'] = 'Bearer ' + getToken()（:32-34）
   └─ GET 有 params → 转成 /conf/signingSubject/list?pageNum=1&pageSize=10 拼到 URL（:36-40）

④ axios 发出：GET /dev-api/conf/signingSubject/list?...
   └─ dev 服务器代理：/dev-api 前缀去掉，转发到 http://localhost:8080/conf/signingSubject/list
      （zxcm-ui/vue.config.js:35-44，target 在 :38）

⑤ 后端 Controller 处理完返回 { code:200, msg:'查询成功', rows:[...], total:100 }
   （TableDataInfo 的四个字段：total `:43`、rows `:49`、code `:55`、msg `:61`，
    路径 ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/page/TableDataInfo.java）

⑥ 响应拦截器（request.js:71-73、:109-110）
   └─ 读 res.data.code（没返回时默认按 200）；不是 401/500/其它错误码 → return res.data
      ← 返回的是后端 JSON 本身

⑦ 页面拿到 { code, msg, rows, total }，读 response.rows / response.total 赋给表格

⑧ Vue 响应式：数据一变，界面上表格自动刷新

❌ 若 token 过期 → 后端返回 code:401
   └─ 响应拦截器：弹「登录状态已过期」框 → 点确定 → LogOut → 跳登录页
```

> **答辩高频**：「你前端一个列表页怎么拿数据的？」→ 页面 `created` 调 `getList` → `getList` 调 `api` 函数 → `request.js` 加 token 发出去 → 响应拦截器判完 `code` 后返回后端 JSON → 页面把 `rows` 赋给表格。**后端那一半**见[后端重塑版 第 1 章](../后端重塑版/第1章-签约主体管理.md) §五。
>
> **零基础逐行版**：每一步涉及的 URL、同源、axios、`process.env`、`[expr]:`、Promise、拦截器、Vue 响应式等概念，都在[附录 B](附录B-零基础精读：一次请求的完整流程.md)里单独补课。

### 5.3 【下载文件】以「导出台账」为例

```
① 页面点「导出」→ this.handleExport()                          (zxcm-ui/src/views/contract/book/index.vue:377)
   └─ this.download('contract/book/export', {...查询条件}, `合同台账_${new Date().getTime()}.xlsx`) (book/index.vue:378-382)

② download() 函数（request.js:135）
   ├─ 开全屏 Loading 遮罩「正在下载数据，请稍候」
   ├─ 用 POST + responseType:'blob' 发请求（超时放宽到 3 分钟）
   ├─ 响应回来后 blobValidate(data)：判断回来的是文件还是错误 JSON
   │   ├─ 是文件 → new Blob + saveAs(blob, filename) 触发浏览器保存
   │   └─ 是错误 JSON（如没权限）→ 解析出 msg 弹错误
   └─ 关 Loading 遮罩
```

**为什么不用普通 axios**：文件下载响应是**二进制流**，不是 JSON。普通拦截器会把 blob 当 JSON 解析报错，所以 `download` 单独走一条路，并且把 `Content-Type` 设成 `x-www-form-urlencoded`。

## 六、面试高频问题

**Q1：你们的请求是怎么统一处理的？**
A：封装在 `src/utils/request.js`。用 `axios.create` 建实例（`baseURL` 取环境的 `/dev-api`，超时 10 秒），加两个拦截器：请求拦截器负责注入 token、GET 参数拼接、防重复提交；响应拦截器负责统一判错误码、401 弹重登、只把 `res.data` 返回给业务。

**Q2：token 存在哪？每次请求怎么带上的？**
A：存在 Cookie，key 是 `Admin-Token`（`utils/auth.js:3`）。每次请求由请求拦截器读取，拼成 `token: Bearer xxx` 放进请求头（`request.js:32-34`）。登录接口本身用 `isToken:false` 标记跳过（`api/login.js:15-17`）。

**追问：如果后端要求请求头叫 `Authorization` 而不是 `token`，改哪里？**
A：只改 `zxcm-ui/src/utils/request.js:33` 这一行的键名即可；响应侧不用动，因为 401 判断的是响应体里的 `code`，不是请求头。

**Q3：token 过期了前端怎么处理？**
A：后端返回 `code:401`，响应拦截器弹出「登录状态已过期，请重新登录」，用户确认后调 `LogOut` 清 token 并跳登录页（`request.js:80-97`）。用 `isRelogin.show` 做开关，防止并发多个 401 弹多个框。

**Q4：怎么防止表单重复提交？**
A：双层。前端在请求拦截器里，把上一次 POST/PUT 的 URL+数据+时间存 `sessionStorage`，新请求若「同 URL 同数据且间隔 <1 秒」就拒绝（`request.js:42-64`）；后端另有兜底。**坦白**：前端这个判断只跟「上一次请求」比，快速切不同按钮时会漏，所以后端兜底是必要的。

**Q5：登录之后为什么还要请求 `/getInfo`？直接返回不行吗？**
A：`POST /login` 只发 token，职责单一。`GET /getInfo` 单独返回用户信息、角色、权限码——因为**刷新页面时 token 还在 Cookie 里，但内存里的用户信息没了**，需要重新拉一次。分开这两个接口，刷新时才能无感恢复登录态。

**Q6：`request.js` 响应拦截器为什么 `return res.data` 而不是 `res`？**
A：因为后端返回格式统一是 `{ code, msg, data }`（对应[后端重塑版 第 0 章](../后端重塑版/第0章-总纲-业务全景与分层架构.md)的 `R` 统一返回）。业务只关心 `data`，所以拦截器直接把外层剥掉，页面里写 `res.rows`、`res.data` 就够，不用写 `res.data.data`。

**Q7：GET 请求的参数为什么要单独转？**
A：axios 的 GET 用 `params` 传对象，但有些场景（如数组、特殊字符）默认序列化格式后端不认。本项目用 `tansParams` 手动转成 `key=value&key2=value2` 拼到 URL（`request.js:36-41`），保证格式可控。

**Q8：文件下载为什么单独写 `download` 函数？**
A：写文件返回的是**二进制 blob**，不是 JSON；而且导出可能很慢（放宽到 3 分钟超时）；下载后要么触发浏览器保存、要么是错误 JSON。这些都跟普通请求不同，所以单独封装（`request.js:135-159`），内部用 `blobValidate` 判断回来的是文件还是错误。

**Q9：前端怎么存登录状态，刷新页面会掉吗？**
A：token 存 Cookie 所以刷新不丢；用户信息存 Vuex（内存）刷新会丢，但路由守卫发现 `roles` 为空会**自动重新调 `/getInfo`** 补回来，用户无感。

**Q10：`NProgress` 和 `watermark` 是什么？**
A：NProgress 是页面顶部那条细进度条，`permission.js` 在路由切换开始 `start()`、结束 `done()`，给用户「正在跳转」的反馈。watermark 是水印库，登录后给整页铺上「用户名+工号+日期」的浅色水印（`permission.js:65-69`），用于**防截图泄露**——这是合同系统常见的合规要求。

### 6.1 本章答辩卡（3 组追问级问答）

**追问 1：后端 HTTP 状态码是 200，但业务码 `code:401`，axios 会不会把它当成功？**
10 秒答案：axios 默认只看 HTTP 状态码，所以它先走成功回调；是响应拦截器读到 `res.data.code` 后手动进入 401 分支。也就是说，业务错误是前端拦截器自己判出来的。
证据：`zxcm-ui/src/utils/request.js:71-73`（先取 `res.data.code`）、`:80-97`（401 分支）。

**追问 2：防重复提交的「上一次请求」为什么放 `sessionStorage`，不放 Vuex？**
10 秒答案：`sessionStorage` 只属于当前标签页、刷新还在、关标签页就清，正好符合「短时间内防连点」的语义；放 Vuex 会被业务状态和路由切换干扰，也活不过刷新。
证据：`zxcm-ui/src/utils/request.js:48-63`、`zxcm-ui/src/plugins/cache.js:1-33`（sessionCache 的读写实现）。

**追问 3：响应拦截器 reject 出来的值类型统一吗？页面 `.catch` 能拿到什么？**
10 秒答案：不统一。401 reject 的是字符串，500 和其它业务码 reject 的是 `Error` 或字符串 `'error'`，网络错误 reject 的是原 error 对象。所以页面做提示应依赖拦截器统一弹窗，不要假设 `.catch` 里一定是 `Error`。
证据：`zxcm-ui/src/utils/request.js:97`、`:103`、`:108`、`:130`。

## 七、选型对比

### 7.1 axios vs 原生 fetch

| | axios（本项目） | fetch |
|---|---|---|
| 拦截器 | ✅ 内置 | ❌ 要自己包 |
| 自动 JSON 解析 | ✅ | ❌ 要 `.json()` |
| 超时设置 | ✅ 一个配置 | ❌ 要 AbortController |
| 下载/上传进度 | ✅ | 需手动 |
| 错误码（4xx/5xx） | 默认 reject | 默认 resolve（需手动判 `ok`） |

**结论**：要「统一加 token、统一处理错误、统一防重复」这些横切逻辑，axios 的拦截器是刚需。fetch 原生不给拦截器，得自己从头包一个，没必要重造。

### 7.2 token 存 Cookie vs localStorage vs sessionStorage

| | Cookie（本项目） | localStorage | sessionStorage |
|---|---|---|---|
| 刷新后还在 | ✅ | ✅ | ✅ |
| 关浏览器后 | 本项目未设 `expires`，属会话 Cookie，通常清除（浏览器「恢复会话」时可能保留） | 还在 | **清空** |
| 后端可直接读 | ✅ | ❌ | ❌ |
| 防 XSS | 可设 HttpOnly（更安全） | 易被 JS 读 | 易被 JS 读 |

**为什么用 Cookie**：`js-cookie` 读写方便，同源请求会自动携带；需要过期时间时给 `setToken` 加个 `expires` 即可（本项目当前没加，所以是会话 Cookie）。`sessionStorage` 只用来存「上一次请求」做防重复（关浏览器即清，正好合适）。

### 7.3 前端防重复提交 vs 后端防重复提交

| | 前端（请求拦截器） | 后端（`@RepeatSubmit` 注解） |
|---|---|---|
| 成本 | 零网络开销 | 每次查一次（Redis/内存） |
| 覆盖 | 挡手抖连点 | 挡所有来源（含脚本刷） |
| 可靠性 | 弱（只比上一次） | 强 |

**结论**：本项目**两者都做**——前端省流量、后端保底。这是「不能只靠前端做安全校验」原则的体现：**前端的任何校验都只是体验优化，真正的兜底必须在后端**。

## 本章小结

- 全站请求出口只有一个文件：`src/utils/request.js`。
- 请求拦截器：加 token（`Bearer xxx`）、GET 转参、防重复提交。
- 响应拦截器：判 `code`，401 弹重登（`isRelogin` 防弹窗风暴）、500 弹错、200 只返回 `res.data`。
- token 存 Cookie（`Admin-Token`），登录接口用 `isToken:false` 跳过。
- 登录是「两次请求」：`/login` 换 token → 路由守卫 `/getInfo` 换身份。
- `api/` 层是纯接口定义，RESTful 风格，和[后端重塑版](../后端重塑版/README.md)的 Controller 一一对应。
