# 第 9 章 · 首页看板与消息页面

> 登录进来的**第一屏**就是首页看板——四个统计数字 + 任务中心的两个标签页 + 右侧常用功能。这一章讲首页怎么「用数据驱动界面」，以及旁边那套**消息通知**（消息模板、消息日志、我的消息）是怎么做的。

> **零基础先补概念（前端视角）**
>
> - **看板 / 统计卡片**：看板就是「把关键数字集中放在一屏」。本项目的首页**不是图表**，而是 4 张数字卡片（`v-for` 渲染的 `div`）；整个首页没有引入 ECharts，ECharts 只出现在监控页的缓存图表里（`zxcm-ui/src/views/monitor/cache/index.vue:71,96`）。卡片数据来自 `GET /contract/dashboard/contractCount`（`zxcm-ui/src/views/index.vue:250-260`）。
> - **数据驱动 / 响应式**：不写死 HTML，而是把数据放进 `data()`，模板用 `{{ }}`、`v-for` 描述「数据长什么样」。数据一变，Vue 自动重画界面。首页的 `statList` 一变，4 张卡片就跟着变（`index.vue:76-88,261-290`）。语法见《Vue2 从 0 到精通》第 1 章 §5.2、第 2 章 §7.1。
> - **标签页 + 条件挂载**：`el-tabs` 只负责「显示哪一页」；真正的切换条件是 `v-if="activeName == 'audit'"`。`v-if` 为假时组件被销毁，为真时才创建并执行 `created`，所以能省请求（`index.vue:105,111`）。`v-if` 与 `v-show` 的区别见《Vue2 从 0 到精通》第 2 章 §6.2。
> - **Vuex 全局状态**：有些数字不归首页管，而是放在全局仓库里，侧边栏拿到后写进 Vuex，首页再从 Vuex 读。待办角标就是这么来的（`zxcm-ui/src/layout/components/Sidebar/index.vue:98-114` → `zxcm-ui/src/store/modules/user.js:42-44` → `index.vue:155-157,223-226`）。Vuex 的 `state/getters/mutations` 见《Vue2 从 0 到精通》第 6 章 §3；`watch` 监听 Vuex 见《Vue2 从 0 到精通》第 3 章 §5.5。

## 一、这部分是做什么的

登录后系统展示两部分：

**① 首页看板**（`zxcm-ui/src/views/index.vue` + `zxcm-ui/src/views/dashboard/`）：
- 顶部问候卡：头像、问候语、部门/角色、日期（`index.vue:6-28`）。

## 二、站在架构师角度，为什么这么设计

### 2.1 为什么首页是「数据驱动」而不是「写死」

看 `zxcm-ui/src/views/index.vue:250` 的 `getList()`——它只调 `GET /contract/dashboard/contractCount` 拿一个对象，然后 `buildStatList(data)`（`:261-290`）**用后端数据拼出 4 个卡片**。

**后端的返回比前端用到的多**：`DashboardController.dashboard()` 对 7 种合同状态各做一次 `selectCount`（草稿/审批中/签署中/已签署/履行中/暂停/完结），再算一次「即将到期」，一共 8 个数字（`zxcm-contract/src/main/java/com/ruoyi/contract/controller/DashboardController.java:86-133,147-154`）。前端只挑了 4 个：`draftCount`、`auditCount`、`fulfilCount`、`doneCount`（`index.vue:261-290`）。所以答辩时说「首页 4 卡来自一次接口、接口内部做了多次 COUNT」，不要说「后端只查了 4 次」。

**为什么**：统计数字是**实时变化的**（今天 5 个草稿，明天 8 个）。如果写死在前端，永远不变。所以**卡片不是写死的 HTML，而是「根据数据生成」**——`v-for` 遍历 `statList` 渲染卡片（`:76-88`）。

**答辩点**：**「首页卡片是数据驱动的：后端给数字，前端 `v-for` 渲染，数字一变界面就变」**。这是 Vue 响应式的典型应用（见《Vue2 从 0 到精通》第 1 章 §5.3）。

### 2.2 为什么待办/我的合同/常用功能是三个独立子组件

看 `index.vue` 的 import（`:124-128`）：`myContract`、`todo`、`functionList` 三个子组件。

**为什么拆**：三个功能块是**独立的**，各有自己的数据、接口、逻辑。塞进 `index.vue` 会让首页变成 1000+ 行。拆开后：
- `index.vue` 只管「**外框**」：统计卡 + 标签页切换。
- 每个 tab 内容是独立组件。

**而且用 `v-if` 懒挂载**（`zxcm-ui/src/views/index.vue:105,111`）：只有切到某个 tab 才挂载那个组件——**切到「待办」才加载待办的数据**，省资源。**这是「按需加载」在 tab 上的应用**（和第 3 章字典的按需加载一个思路）。

**待审批 tab 还套了一层权限**：整个 `el-tab-pane` 用 `v-if="checkPermi(['contract:workflow:query'])"` 控制（`index.vue:98`）；`created` 里还会检查一次，没有这个权限的人默认落在「我的合同」（`index.vue:205-208`）。所以「看不到待审批」不一定是没数据，也可能是没权限。

### 2.3 为什么「待办」和「我的合同」是两个不同的数据源

- **待办**（`todo.vue:185`）：`GET /activiti/process/taskList`——**来自工作流引擎**。它查的是「**当前用户待处理的流程任务**」。
- **我的合同**（`myContract.vue:54`）：`GET /contract/dashboard/myContractList`——**来自业务表**。它查的是「**我创建的合同**」。

**为什么分开**：「待办」是「**我该做什么**」（工作流视角），「我的合同」是「**我的东西**」（业务视角）。一个合同可能我创建了但现在不在我这儿审批（在别人那），也可能别人创建了但轮到我审批。**两个视角，两份数据**。

**答辩点**：**「待办来自工作流引擎（Activiti 的 task），我的合同来自业务表」**——这是「业务流程」和「业务数据」两个维度的清晰划分。

### 2.4 为什么待办列表要传 `searchFlow`

看 `todo.vue:149`：

```js
searchFlow: ['audit', 'change', 'stamp', 'stampChange']
```

**这是什么**：查询待办时，告诉后端「只查这四类流程的任务」——**审批(audit) / 变更(change) / 用印(stamp) / 用印变更(stampChange)**。

**为什么**：系统里可能有各种流程，待办列表只关心**这四类和合同相关**的。这是**过滤条件**，也说明本项目的工作流主要服务这四类业务动作。

### 2.5 为什么「常用功能」是可配置的

看 `zxcm-ui/src/views/dashboard/function.vue:175-194` 的 `setFunctionList()`——它**从用户的 `config` 里读出「常用功能列表」**；`:215-227` 的 `submitChange()` 允许用户**自己配置**哪些功能放这儿，并调用 `changeUserConfig` 存回后端（`zxcm-ui/src/api/system/user.js:84-89` → `PUT /system/user/changeConfig`）。

**注意生命周期**：调用 `setFunctionList()` 的是 `mounted`（`function.vue:167-169`），不是 `created`。因为要读的 `config` 来自 `mapGetters(['config'])`（`:99-101`），对应 Vuex 的 `user.config`（`zxcm-ui/src/store/getters.js:11`），而 `user.config` 是 `GetInfo` 时解析后存进来的（`zxcm-ui/src/store/modules/user.js:85-88`）。

**为什么**：不同角色常用的功能不同（业务员常用「新建合同」，管理员常用「模板管理」）。让**用户自己配**「我常用的」，比前端写死一个列表灵活；每个入口外面还有 `v-hasPermi="[item.permission]"`（`function.vue:31`），没权限的入口不会显示。

**答辩点**：**「常用功能存用户配置里，用户自定义快捷入口」**——这是「个性化」的设计，也复用了 Vuex 里存的 `user.config`（第 1 章 GetInfo 时存的）。

### 2.6 消息模板为什么用富文本编辑器

看 `zxcm-ui/src/views/notify/template/index.vue`——它管理「消息模板」，模板内容可以是富文本：编辑弹窗里用的是全局注册的 `<editor>` 组件（`index.vue:243-245`；全局注册见 `zxcm-ui/src/main.js:96-98`，组件本身在第 3 章 §4.1 讲过）。

**为什么**：消息内容可能要带格式、链接、变量占位符（如「${合同名}已审批通过」）。富文本比纯文本强。**这是 `<Editor>` 组件的一个实际使用场景**。

**但要看清现状**：模板页的「新增/修改/删除/导出」工具条整体被 HTML 注释包住了（`index.vue:72-123`），表格里的「修改/删除」操作列也被注释（`:161-188`）。所以**这个页面当前实际是只读列表**，富文本弹窗在代码里存在、但页面上没有正常入口能打开。这一点答辩时要说清，别把「代码里有」说成「功能可用」。

### 2.7 消息机制的三种角色

| 页面 | 角色 | 谁的活儿 |
|---|---|---|
| 消息模板（`notify/template`） | 定义「消息长什么样」 | 管理员配 |
| 消息日志（`notify/log`） | 记录「发了哪些消息」 | 系统写 |
| 我的消息（`system/user/ann`） | 「我收到的消息」 | 用户看 |

**为什么分三个**：**「模板定义」和「实际发送」和「用户收取」是三件事**。模板是配置，日志是审计，收件箱是消费。**典型的消息系统三段式**。

### 2.8 ⚠️ 坦白点：首页和消息页有几处「看着有、实际没接通」

1. **待办角标不是 `todo.vue` 的 `$emit` 更新的**。`todo.vue` 确实在拿到 `total` 后 `$emit('updateCount','auditCount',total)`（`zxcm-ui/src/views/dashboard/todo.vue:191`），但首页的接收方法 `updateCount(type, count) {}` 是**空函数**（`zxcm-ui/src/views/index.vue:291`）。角标的真实来源是侧边栏在 `mounted`、`updateTipCount` 事件和 WebSocket 消息时拉 `GET /contract/dashboard/todoCount`（`zxcm-ui/src/layout/components/Sidebar/index.vue:82-91,98-114,194-201`），写进 Vuex 的 `showNum`，首页再 `watch` 它（`index.vue:147-153,222-226`）。**「子传父」这段代码存在，但结果是丢掉的。**
2. **4 张统计卡只有 2 张能点**。`buildStatList` 只给「草拟中」「审批中」配了 `to`，履行中/已完结没有（`index.vue:262-289`）；点击处理 `toPage(item)` 遇到没有 `to` 就直接 `return`（`index.vue:246-249`）。所以后两张卡只是展示，不是入口。
3. **消息模板页的 CRUD 入口被注释**（`notify/template/index.vue:72-123,161-188`），页面实际是只读列表；新增/修改弹窗（`:201-255`）和富文本编辑器（`:243-245`）都还在代码里，只是没有正常按钮能打开。
4. **消息日志页没有新增/修改按钮**：工具条区域是空的（`zxcm-ui/src/views/notify/log/index.vue:57-59`），只有查询表单 + 表格 + 分页。
5. **「我的消息」的单条「标为已读」按钮被隐藏**：整个操作列写着 `v-if="false"`（`zxcm-ui/src/views/system/user/ann/index.vue:105-110`）。实际能用的已读入口是「点未读消息正文」跳转时顺手标记（`:71-78,223-233`）和顶部「全部标为已读」（`:40-49,246-262`）。

| `:291` | `updateCount(type,count) {}` —— **空实现**，`todo.vue` 的 emit 到这里就丢了 |

**接口**：`GET /contract/dashboard/contractCount`（`:253`）；角标的另一个接口是 `GET /contract/dashboard/todoCount`（`zxcm-ui/src/layout/components/Sidebar/index.vue:100-103`）。

**读法**：首页只干两件事——① 拉统计数字渲染卡片；② 挂载子组件。**业务逻辑在子组件里；但待办角标不要盯 `todo.vue` 的 emit，它没被首页消费，真正的链路在侧边栏 → Vuex → watch**。

**逐行读「数据怎么变成 4 张卡」`getList()` + `buildStatList()`（`zxcm-ui/src/views/index.vue:250-290`）**：

```js
getList() {
  this.loading = true;
  request({
    url: "/contract/dashboard/contractCount",
    method: "get",
  }).then((res) => {
    this.loading = false;
    this.contractCount = res.data;
    this.buildStatList(res.data);
  });
},
buildStatList(data) {
  this.statList = [
    { fullName: "草拟中",   num: data.draftCount,   icon: "el-icon-edit-outline",  theme: "draft",  to: "/contract/contractDraft" },
    { fullName: "审批中",   num: data.auditCount,   icon: "el-icon-s-claim",       theme: "audit",  to: "/contract/contractAudit" },
    { fullName: "履行中",   num: data.fulfilCount,  icon: "el-icon-s-cooperation", theme: "fulfil" },
    { fullName: "已完结",   num: data.doneCount,    icon: "el-icon-s-finance",     theme: "done" },
  ];
},
```

1. `getList()`：首页拉数据的唯一入口，`created` 里调用（`:203`）。
2. `this.loading = true`：打开 loading 遮罩。模板的统计区绑了 `v-loading="loading"`（`:74`）。
3. `request({...})`：项目封装的 axios 请求（第 1 章），会自动加 token、处理 401。
4. `url: "/contract/dashboard/contractCount"`：统计接口；注意它是 `GET`，没有参数，数据权限在后端按当前登录人算（后端 `DashboardController.java:80-84`）。
5. `.then((res) => {...})`：请求成功后进入回调。项目的响应拦截器已经把 `response.data` 剥出来了，所以这里直接 `res.data`（第 1 章 §2.4）。
6. `this.loading = false`：无论有没有数据都关遮罩（失败时由拦截器统一弹错，这里没写 `.catch`）。
7. `this.contractCount = res.data`：把原始对象也存一份，顶部快捷卡要用它的 `draftCount`（`:198-200`）。
8. `this.buildStatList(res.data)`：把「后端字段名」翻译成「界面卡片需要的结构」——这是前端适配层的关键一步。
9. `this.statList = [...]`：整体替换数组。数组是响应式的，替换后模板 `v-for` 自动重画（响应式原理见《Vue2 从 0 到精通》第 10 章 §二）。
10. `fullName`：卡片标题，模板里 `{{ item.fullName }}`（`:85`）。
11. `num`：卡片数字，模板里 `{{ item.num || 0 }}`（`:84`）——后端某个字段为空时兜底显示 0。
12. `icon` / `theme`：分别控制图标和配色 class（`:79,82`），只影响外观。
13. `to`：点击卡片要跳的路由，模板 `@click="toPage(item)"`（`:80`）；`toPage` 里 `if (!item.to) return`（`:246-248`）。**履行中、已完结没有 `to`，所以这两张卡点不动**——答辩时主动说明，别说「四张卡都能点」。
14. 整段就是「**接口 → 数据 → 数组 → 模板**」的单向流：没有手动操作 DOM，数据变了界面自己变。这就是「数据驱动」。

## 六、面试高频问题

**Q1：首页看板是怎么做的？**
A：数据驱动。`index.vue` 的 `getList()` 调 `GET /contract/dashboard/contractCount` 拿统计数字，`buildStatList` 拼成数组，模板 `v-for` 渲染统计卡（`index.vue:250,261,76`）。数字一变界面自动变。

**Q2：首页下面的标签页怎么实现的？**
A：任务中心是两个独立子组件（`todo`/`myContract`），用 `v-if="activeName==='xxx'"` **懒挂载**——切到哪个才挂载哪个、才发请求（`index.vue:105,111`）；右侧「常用功能」是第三个子组件，但它不在 tab 里，而是一直挂载（`index.vue:117`）。这样既省请求，又不影响常用功能。

**Q3：「待办」和「我的合同」有什么区别？**
A：**待办来自工作流引擎**（`GET /activiti/process/taskList`），是「当前该我处理的流程任务」；**我的合同来自业务表**（`GET /contract/dashboard/myContractList`），是「我创建的合同」。一个是「要做什么」，一个是「我有什么」。

**Q4：`searchFlow: ['audit','change','stamp','stampChange']` 是啥？**
A：查待办时的过滤条件——只查这四类流程的任务：审批 / 变更 / 用印 / 用印变更（`todo.vue:149`）。说明本系统工作流主要服务这四类合同动作。

**Q5：待办数量怎么显示在首页角标上？**
A：**不是靠 `todo.vue` 的 `$emit`**。虽然 `todo.vue:191` 确实 `$emit('updateCount',...)`，但首页的接收方法 `updateCount(type,count) {}` 是空的（`zxcm-ui/src/views/index.vue:291`），这个事件被丢掉了。真实链路是：侧边栏 `getTipCount()` 调 `GET /contract/dashboard/todoCount`（`Sidebar/index.vue:98-114`）→ `commit('SET_SHOWNUM', data)`（`:110`）→ Vuex `user.showNum`（`store/modules/user.js:14,42-44`）→ 首页 `watch showNum`（`index.vue:147-157`）→ `updateShowNum()` 更新角标文本（`:222-233`）。**答辩时主动说这个「emit 空接」的缺口，比背父子通信模板更可信。**

**Q6：「常用功能」是怎么自定义的？**
A：从用户的 `config`（随 `GetInfo` 拉取、存 Vuex 的 `user.config`）读出 `functionList`（`function.vue:175`），用户改完 `submitChange` 存回去（`:215`）。**用户级个性化配置，存后端用户表。**

**Q7：消息系统有哪几个页面？**
A：三个——**消息模板**（`notify/template`，定义「消息长什么样」，富文本代码在；但当前 CRUD 入口被注释，页面只读）、**消息日志**（`notify/log`，记录发了哪些）、**我的消息**（`system/user/ann`，用户收件箱）。模板是「定义」、日志是「审计」、收件箱是「消费」。

**Q8：消息模板为什么用富文本编辑器？**
A：消息可能要带格式、链接、变量占位符（如「${合同名}已通过」），富文本比纯文本灵活。页面确实用了全局注册的 `<editor>`（`notify/template/index.vue:243-245`，全局注册在 `main.js:96-98`）。**但要补充：模板页的新增/修改工具条和表格操作列被注释了（`:72-123,161-188`），当前实际是只读列表，富文本弹窗没有正常入口——这是项目的缺口，不要说成「模板可以正常维护」。**

**Q9：首页的统计卡为什么不用 `v-show` 切 tab？**
A：因为 `v-show` 只是隐藏、组件一直挂载着（数据和请求都在），多个 tab 都这样会白白发请求。`v-if` 是「切到才挂载」，更省。**tab 内容一般是 `v-if`。**

**Q10：`myContractList` 的数据权限怎么加的？**
A：**这个是手动加的**，不是注解。后端 `DashboardController.myContractList` 里手动给查询加 `drafter_id = 当前用户` 过滤（`zxcm-contract/src/main/java/com/ruoyi/contract/controller/DashboardController.java:213`；[后端重塑版 第 10 章](../后端重塑版/第10章-报表与看板.md) §2.3）。因为 `myContractList` 走的是 `BaseMapper` 方法，注解式数据权限拦不到，所以要手动写。

### 本章答辩卡（追问级）

**卡 1：首页顶部两条快捷统计和下面四张统计卡，数据来源一样吗？**
10 秒答案：不完全一样。下面四张卡的 4 个数字都来自 `contractCount`；顶部「草拟中」也来自它的 `draftCount`，但顶部「待审批」来自另一个接口 `todoCount`，经侧边栏写进 Vuex 后由首页 `watch` 读取。一个页面里有两条数据链路。
证据：`zxcm-ui/src/views/index.vue:32-51,195-200`（顶部卡）、`:250-290`（四张卡）；`zxcm-ui/src/layout/components/Sidebar/index.vue:98-114`；后端 `DashboardController.java:77-155`（contractCount）与 `:163-190`（todoCount）。

**卡 2：常用功能列表到底存在哪？为什么换个用户会不一样？**
10 秒答案：存在用户表的 `config` JSON 里，键是 `functionList`。登录后 `GetInfo` 把 `user.config` 解析进 Vuex，首页常用功能组件用 `mapGetters(['config'])` 读出来；用户修改后 `submitChange` 调 `PUT /system/user/changeConfig` 把整个 config 存回后端。所以是「用户级配置」，不是前端写死。
证据：`zxcm-ui/src/views/dashboard/function.vue:99-101,175-194,215-227`；`zxcm-ui/src/store/modules/user.js:85-88`；`zxcm-ui/src/api/system/user.js:84-89`。

**卡 3：「我的消息」的已读状态是怎么改的？为什么页面上看不到「标为已读」按钮？**
10 秒答案：单条已读有两个方法，但行内「标为已读」所在的操作列被 `v-if="false"` 隐藏了；实际可用的是「点未读消息正文」——先 `PUT /notify/myAnnounce/editByAnntIdAndUserId` 标已读，再跳到 `openPage`；批量已读走顶部按钮的 `PUT /notify/myAnnounce/readAll`。
证据：`zxcm-ui/src/views/system/user/ann/index.vue:105-110`（隐藏操作列）、`:223-233`（点正文）、`:246-262`（全部已读）；`zxcm-ui/src/api/notify/myAnnounce.js:13-28`。

## 七、选型对比

### 7.1 首页统计：后端聚合 vs 前端算

| | 后端 `contractCount`（本项目） | 前端自己算 |
|---|---|---|
| 数据量 | 后端一次 COUNT 搞定 | 要拉全量数据到前端算 |
| 性能 | 好 | 差（大数据量崩） |
| 实时性 | 每次刷新拉一次 | 要前端缓存 |

**结论**：统计必须**后端算**（`COUNT` 是数据库的强项），前端只渲染。**和[后端重塑版 第 10 章](../后端重塑版/第10章-报表与看板.md)「报表 vs 业务查询」是一个道理**。

### 7.2 tab 内容：`v-if` vs `v-show`

| | `v-if`（本项目） | `v-show` |
|---|---|---|
| 挂载时机 | 切到才挂载 | 一开始就挂载 |
| 请求 | 切到才发 | 全发 |
| 切换速度 | 首次慢（要加载） | 快（已挂载） |

**结论**：tab 内容差异大、请求重时用 `v-if`（省资源）；切换极频繁且轻量时用 `v-show`。首页 tab 请求重，用 `v-if` 对。

### 7.3 消息：模板 + 日志 + 收件箱 vs 直接发

| | 三段式（本项目） | 直接发 |
|---|---|---|
| 可维护 | ✅ 模板改文案不用改代码 | ❌ 硬编码文案 |
| 可审计 | ✅ 有日志 | ❌ 无记录 |
| 复杂度 | 高（三个页面） | 低 |

**结论**：企业系统要「模板化 + 可审计」，所以三段式。**能改文案、能追责**是刚需。

## 本章小结

- 首页 = **数据驱动的统计卡**（`GET /contract/dashboard/contractCount`）+ **两个懒挂载的 tab 子组件**（待审批/我的合同）+ **右侧常用功能卡片**（不在 tab 里）。
- **待办来自工作流引擎**（`/activiti/process/taskList`），**我的合同来自业务表**（`/contract/dashboard/myContractList`）——两个视角。
- 待办角标的真实链路：侧边栏 `GET /contract/dashboard/todoCount` → Vuex `showNum` → 首页 `watch`；`todo.vue` 的 `$emit('updateCount')` 被空方法接住，**没有实际作用**。
- 常用功能从 `user.config` 读，用户可自定义，保存走 `PUT /system/user/changeConfig`。
- 消息系统三段式：**模板**（`notify/template`，富文本入口被注释）/ **日志**（`notify/log`，只读列表）/ **收件箱**（`system/user/ann`，点正文或全部已读）。
- tab 用 `v-if` 懒挂载；统计走后端聚合（呼应后端「报表 vs 业务查询」）。
- **坦白点**：① `todo.vue` 的计数 emit 没被首页消费；② 4 张统计卡只有 2 张配了跳转；③ 消息模板页 CRUD 入口被注释；④ 消息日志页只读；⑤ 我的消息单条「标为已读」按钮被 `v-if="false"` 隐藏。
