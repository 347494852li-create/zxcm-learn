# 第 10 章 · 报表与看板

> 前九章都是「**管一条合同**」——草拟、审批、用印、归档。本章换视角：**从"管单条"切到"看全局"**。首页要显示「草拟中 12 项 / 审批中 3 项 / 履行中 48 项」，台账要**一次拉出上万条合同**并按各种条件筛选导出——这些都是**聚合查询**，它对数据库的用法和业务查询**完全不同**。
>
> 本章第一次讲透的新概念：**报表查询 vs 业务查询的本质区别**、**数据权限的两种施加方式（注解 vs 手工拼 SQL）**、**聚合查询的性能陷阱**。

> **零基础先补概念（本章 4 个关键词）**
>
> 1. **聚合查询**：不是「按 id 查一条」，而是「**数一数、分分组**」——`COUNT(*)`、`GROUP BY contract_status` 都是聚合。例：首页要显示「草拟中几项 / 审批中几项」，就是对 `contract_draft` 按 `CONTRACT_STATUS` 分组计数。
> 2. **看板统计口径**：「履行中」这三个字，在不同页面可能不是同一个 SQL。首页的「履行中」不是简单的 `status=6`，还要求「已经生效、且还没到期」（`zxcm-contract/src/main/java/com/ruoyi/contract/controller/DashboardController.java:106-112`）。**口径**就是「这个数字到底按什么条件算出来的」。
> 3. **数据权限（数据范围）**：同一个 `/contract/book/list` 接口，部门经理只能看到本部门合同、普通员工只能看到自己的、管理员看全部。本项目的做法是把「当前用户能看哪些行」翻译成一段 SQL 条件，拼到查询后面（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/helper/DataPermissionHelper.java:96-138`）。
> 4. **N+1 查询**：先查 1000 条合同，再对每条合同单独查一次审批单，总共 1001 次数据库往返。报表里用 `LEFT JOIN` 一次拿全，就是专门为了避免 N+1（`zxcm-contract/src/main/java/com/ruoyi/contract/mapper/ContractDraftMapper.java:162-170`）。

### 1.2 「报表」和「业务」的本质区别（本章的核心认知）

这是本章**最该记住**的一张对比表：

| 维度 | 业务查询（第 1~9 章） | 报表查询（本章） |
|---|---|---|
| **典型 SQL** | 按 ID 查一条、插入、更新状态 | `COUNT`、`GROUP BY`、多表 `JOIN` 聚合 |
| **数据量** | 单条 / 少量 | 全表扫描级别（上万条） |
| **返回给谁看** | 程序逻辑用 | **人看的**（数字/表格） |
| **能不能慢** | 不能（用户点一下要立刻响应） | 可以慢一点，但**不能拖垮业务** |
| **并发特征** | 高频、每次少量 | 低频、每次大量 |
| **索引策略** | 走主键/唯一索引 | 往往要**专门为报表加索引**甚至**预聚合** |

**Why（架构师视角）**：报表查询如果和业务查询**共用一个数据库连接池、一套索引、一张表**，一个"导出全年合同"的慢查询就可能**把连接池占满，导致业务接口全部超时**。所以企业级系统会把报表拆出去（读库、OLAP、预聚合表），**本章这套开源代码没有拆**——这正是 §2 要讲的第一个坦白点。

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么「首页统计」要单独一个 Controller？

`DashboardController` 完全可以塞进 `ContractDraftController`，但系统把它**单独拆出来**。

**Why**：
- **职责不同**：`ContractDraftController` 管「一条合同的增删改查」，`DashboardController` 管「全局聚合」。混在一起，`ContractDraftController` 会又长又杂。
- **权限不同**：看板有独立的权限资源 `dashboardPermission`（`DataPermissionResource`），和草稿/审批/台账的权限**分开配置**。同一个用户可能「能看台账但不能看首页统计」。
- **变化频率不同**：看板的需求天天变（今天加个到期预警，明天加个环比），和稳定的 CRUD 逻辑分开，改动互不干扰。

**How to apply**：划分 Controller 的原则是「**按变化的原因分，不按实体分**」。看板和合同虽然是同一张表，但**变化的原因不同**（一个因"老板想看什么"变，一个因"合同字段变"变），所以拆开。

| 判断维度 | 塞进 `ContractDraftController` | 单独拆（选用） |
|---|---|---|
| 职责 | CRUD + 全局聚合混杂 | 各自单一 |
| 权限 | 共用一套 | `dashboardPermission` 独立 |
| 变化频率 | 互相干扰 | 互不影响 |

### 2.2 为什么看板数据要「受数据权限控制」？

首页的「履行中 48 项」，是**全公司的 48 项**，还是**你（或你部门）的 48 项**？

**业务答案**：取决于角色。部门经理看自己部门，普通员工看自己，管理员看全部。这就是**数据权限**（第 2 章合作方管理讲过的概念）。

**关键代码**：`DashboardController.java:80-84`

```java
String s = DataPermissionHelper.getContractDataPermissionSql(
    LoginHelper.getLoginUser(),
    "contract_charge_id",                        // 按"合同负责人"这个字段做权限过滤
    DataPermissionResource.dashboardPermission); // 用"仪表盘权限"这套规则
if (StringUtils.isNotEmpty(s)) {
    s = " AND " + s;                             // 拼成 SQL 片段，追加到查询后面
}
```

拿到 `s` 之后，7 个计数查询**每一个都 `draft.last(s)`**（`:88`、`:93`、`:98`、`:103`、`:111`、`:116`、`:121`）——把权限 SQL 片段接到自己的 WHERE 后面。

**Why 用 `last()` 拼 SQL 而不是用注解？** 见 §2.3（这是本章最值得讲的一个技术点）。

### 2.3 【本章重点】数据权限的两种施加方式

这个项目里，给查询加数据权限有**两套机制**，本章恰好两种都用到了：

**方式 A：注解 `@DataPermission`（自动织入）**

```java
// ContractDraftMapper.java:148-151
@DataPermission(value = {@DataColumn(key = "userId", value = "contract_charge_id")},
    resource = DataPermissionResource.contractPermission)
@Select("SELECT count(1) from contract_draft ${ew.customSqlSegment}")
public long countNum(@Param("ew") Wrapper wrapper);
```

- 由 **MyBatis-Plus 拦截器**在运行时把权限条件**自动塞进 SQL**；
- 优点：业务代码干净，看不到权限 SQL；
- **限制**：只能作用于**被 `@DataPermission` 标注的方法**。

**方式 B：手工拼 SQL（`DataPermissionHelper.getContractDataPermissionSql`）**

- 由业务代码**自己**算出权限 SQL 片段，自己拼进去；
- 优点：能作用于**任何查询**（包括 MyBatis-Plus 自带的 `selectCount`）；
- 缺点：业务代码里能看到一堆 SQL 拼接，容易漏加。

**为什么 `contractCount` 必须用方式 B？**

因为 `DashboardController.java:89` 用的 `contractDraftMapper.selectCount(draft)` 是 **MyBatis-Plus `BaseMapper` 的自带方法**，它**没有 `@DataPermission` 注解**，拦截器**管不到它**。所以必须手工加权限。

**How to apply（面试加分点）**：
> 「同一个项目里，数据权限有两套机制并存——注解式用于自定义 Mapper 方法，手工式用于 BaseMapper 自带方法。这不是设计混乱，而是**覆盖范围不同导致的必然结果**。企业级项目会统一成一套，比如用一个 AOP 切面拦截所有 Mapper 方法，避免开发者忘记手工加权限导致**数据越权泄漏**。」

**⚠️ 这个风险要主动说**：手工方式的最大隐患是**开发者忘记加 `last(s)`**。`DashboardController` 里 7 个 `selectCount` 都加了 `draft.last(s)`，没有遗漏——但这**靠的是人工纪律，不是机制保障**。一旦漏一个，那个数字就会**越过权限暴露全公司数据**。

### 2.4 为什么台账查询要 `JOIN` 三张表？

`ContractDraftMapper.bookPage`（`:171`）的 SQL：

```sql
SELECT a.*,
       b.partner_names    as "auditForm.partnerNames",
       b.subject_names    as "auditForm.subjectNames",
       b.currency         as "auditForm.currency",
       b.inouttype        as "auditForm.inouttype",
       b.contract_name    as "auditForm.contractName",
       b.amount           as "auditForm.amount",
       b.EFFECTIVE_TIME   as "auditForm.effectiveTime",
       b.END_TIME         as "auditForm.endTime",
       b.create_time      as "auditForm.createTime",
       b.apply_user_name  as "auditForm.applyUserName",
       COALESCE(a.project_name, b.project_name) as "projectName",
       a.CONTRACT_APPROVE_PASS_TIME as "contractApprovePassTime",
       ar.archives_name AS "archivesName"                       -- ← 第三张表
FROM CONTRACT_DRAFT a
LEFT JOIN CONTRACT_AUDIT_FORM b ON a.audit_id = b.id            -- ← 第二张表
LEFT JOIN CONF_ARCHIVES ar ON a.contract_archives_id = ar.id    -- ← 第三张表
${ew.customSqlSegment}
```

> 上面是 `bookPage` 的字段（`ContractDraftMapper.java:162-170`）。导出用的 `bookList`（`:182-190`）多查了 `b.apply_dept_name`，因为 Excel 里有「申请人部门」这一列，列表页不需要。

**为什么要 JOIN？** 因为台账要展示的字段**不在一张表里**：
- 合同基础信息在 `contract_draft`（a）；
- 合作方名、金额、申请人、申请部门在**审批表单** `contract_audit_form`（b）；
- 归档卷名在 `conf_archives`（ar）。

**Why 不分开查？** 如果先查 `contract_draft` 再对每条循环查 `contract_audit_form`，就是典型的 **N+1 查询**（1000 条合同 = 1001 次数据库往返）。`JOIN` 一次搞定，**这是报表查询的基本功**。

**`COALESCE(a.project_name, b.project_name)` 是什么？** 项目名在合同表（a）和审批表单（b）**都可能有**——优先用合同表自己的，没有就用审批表单的。`COALESCE` 取第一个非 NULL 值。这是**同一字段分散在两张表**时的常见处理。

### 2.5 为什么导出要单独走一个 `bookList` 而不是复用 `bookPage`？

`list`（`:95`）用 `bookPage`（分页），`export`（`:107`）用 `bookList`（不分页）。

**Why**：
- **列表**是给人**翻页看**的 → 分页查，一次只取 10 条；
- **导出**是给人**下载整份**的 → 要全部数据，不能分页。

| 场景 | 查询方式 | 上限 | 风险 |
|---|---|---|---|
| 列表 | `bookPage` 分页 | 10 条/页 | 无 |
| 导出 | `bookList` 全量 | 无 | 50 万条一次性读进内存 → OOM |

**⚠️ 风险（要主动指出）**：`bookList` **没有分页、没有上限**。如果台账有 50 万条合同，导出会**一次性把 50 万条读进内存**（`List<ContractBookVo> list = ...`），**极易 OOM**。企业级的做法是**流式导出**（`SXSSFWorkbook` 边读边写）或**异步导出**（生成任务→后台跑→给下载链接）。

### 2.6 为什么台账导出用 EasyPOI 的 `ExcelBuilder` 而不是 `ExcelUtil`？

大部分 Controller（如 `ContractRemarksController.java:85-88`）导出用的是 RuoYi 封装：

```java
ExcelUtil.exportExcel(list, "合同备注", ContractRemarksVo.class, response);   // ContractRemarksController.java:87
```

但台账导出（`ContractBookController.java:107-124`）用的是 **EasyPOI 的链式 `ExcelBuilder`（底层还是 POI）**，不是「裸写 POI」：

```java
Workbook workbook = createExcel(list).getWorkbook();   // :111；createExcel 在 :295
response.setContentType("application/vnd.openxmlformats-officedocument.spreadsheetml.sheet;charset=utf-8"); // :112
workbook.write(response.getOutputStream());            // :114
```

`createExcel`（`:295-356`）返回的类型是 `cn.afterturn.easypoi.excel.ExcelBuilder`（`zxcm-third/zxcm-excel/src/main/java/cn/afterturn/easypoi/excel/ExcelBuilder.java:52`）；`ExcelBuilder.create()` 默认创建 `XSSFWorkbook`（`ExcelBuilder.java:63-64`、`:77-84`）。

**Why 不用 `ExcelUtil`**：因为台账导出需要的不是「把一个 List 按注解映射成表格」，而是**动态拼表头 + 分段写列**：
- 表头分 `header1`（合同编号/申请人/合同类型…）+ `header2`（合同摘要/状态/金额…）两段（`ContractBookController.java:306-310`）；
- 「合作方」「签约主体」有几列**不固定**，要先扫一遍数据算出最大值，再用 `numberedHeaders` 生成「合作方1、合作方2…」（`:296-303`、`:313-314`、`:416-422`）；
- 还有纠纷列、归档列，列的总数要到运行时才确定（`:323-335`）；
- 写入的是 `packageData` 翻译过字典的数据（`:204-231`）。

> **注意源码里没有「设置列宽」**：`createExcel` 设置了行高（`:305`）和表头样式（`:325`），但没有 `setColumnWidth`。所以不要照抄二手资料里的「自定义列宽」说法。

**How to apply**：「**通用工具够用就用通用的（省事、统一），不够用就换更灵活的构造方式**」。`ExcelUtil` 适合「实体字段固定、注解能描述」的导出；像台账这种**列数动态、多段表头**的场景，就适合 `ExcelBuilder` 这种链式 API。代价是**要自己管资源**：`workbook.close()` 放在 `finally` 里（`ContractBookController.java:117-123`），这也是这段代码有 try/finally 的原因。

### 2.7 「读写分离的报表 Mapper」——理想 vs 本仓库现实（坦白点）

关于「**读写分离的报表 Mapper**」这个常见说法，这里必须**讲清理想、同时坦白现实**。

**理想的做法**：把报表查询**单独放一个 Mapper**，比如 `ContractReportMapper`，和业务 Mapper（`ContractDraftMapper`）分开。好处：
1. 报表 SQL 再多也不污染业务 Mapper；
2. 报表 Mapper 可以**指向只读从库**（`@DS("slave")`），不占主库资源；
3. 一眼能看出哪些是报表、哪些是业务。

**⚠️ 坦白点 ①：本仓库没有做这个分离。**

所有报表查询都**塞在 `ContractDraftMapper` 里**，和业务查询混在一起：

| 方法 | 行号 | 类型 |
|---|---|---|
| `selectDraftPage` | `:45` | 业务（草稿分页） |
| `selectContractPage` | `:60` | 业务（合同分页） |
| `pageContractWidthForm` | `:99` | **报表**（JOIN 审批表单） |
| `pageContractWidthTask` | `:131` | **报表**（JOIN 履行任务 + 子查询） |
| `pageContractWithoutPermission` | `:146` | **看板**（我的合同） |
| `countNum` | `:151` | **报表**（计数） |
| `bookPage` | `:171` | **报表**（台账分页） |
| `bookList` | `:190` | **报表**（台账导出） |
| `contractRemarkList` | `:209` | **报表**（备注追溯） |

**怎么交代**：「这个项目把报表 SQL 和业务 SQL 放在同一个 Mapper 里，没有做读写分离。**理想做法是拆成独立的报表 Mapper 并指向只读库**。这是企业级优化的方向，开源版没做。」

**为什么这个点重要**：面试官问「你们报表怎么做的」，你如果说「我们有独立的报表 Mapper、指向只读库」——一查代码就露馅。**如实说「报表 SQL 和业务混在一起，没有读写分离，这是我们的优化方向」**，反而显得你**真读过代码、真懂架构**。

### 2.8 坦白点（必读）——本章的其他缺口

**坦白点 ②：首页统计是 7 次独立 COUNT，不是 1 次 GROUP BY。**

`DashboardController.contractCount`（`:77-155`）对**同一张 `contract_draft`** 跑了 **7 次 `selectCount`**（draft/audit/signing/signed/fulfil/suspend/done，`:89`~`:122`）。

**更好的写法**是**一次 `GROUP BY contract_status`**：

```sql
SELECT CONTRACT_STATUS, COUNT(1) FROM contract_draft
WHERE DEL_FLAG = '0'
GROUP BY CONTRACT_STATUS
```

一次查询拿到所有状态的数量，而不是 7 次 COUNT。即使 `CONTRACT_STATUS` 有索引（`script/sql/zxcm_init.sql:1165`），7 次 COUNT 也意味着**对同一张表做 7 遍聚合**。

**怎么交代**：「首页统计跑了 7 次 COUNT，可以优化成一次 GROUP BY。这是明显的性能优化点。」

**坦白点 ③：`todoCount` 的 `@ApiOperation` 是从 `contractCount` 复制粘贴的。**

`DashboardController.java:162` 的 `@ApiOperation("查询我的首页数据")` 和 `contractCount`（`:76`）**完全一样**——但方法实际是「查询待办数量」。这是**复制粘贴没改注释**，Swagger 文档会显示错。小 bug，但能看出你逐行读过。

**坦白点 ④：`getMyTodoCount` 为了拿"总数"，实际查了 10 条数据。**

`WorkflowServiceImpl.getMyTodoCount`（`zxcm-workflow/src/main/java/com/ruoyi/workflow/engine/service/impl/WorkflowServiceImpl.java:32-45`）在 `:36` 设置了 `task.setPageSize(10)`，然后 `:44` `return info.getTotal()`——**只用了总数，却让 Activiti 查了 10 条明细**。属于「为了拿 count 干了 page 的活」，浪费。

**坦白点 ⑤：`borrowAuditCount` 是写死的 0。**

`DashboardController.java:189`：`map.put("borrowAuditCount", 0);`——「借阅审批数」**永远是 0**，是个占位符。前端拿到也不会显示什么有用的。

**坦白点 ⑥：没有真正的"图表"。**

名为「看板」，但 `zxcm-ui/src/views/index.vue` 里**全是数字卡片**（`buildStatList`:261 组装的是 `{fullName, num, icon, theme}`），**没有一处 echarts / 折线图 / 饼图**（`grep -rln "echarts" zxcm-ui/src/views/contract` 零命中）。所谓"看板"是**数字概览 + 列表**。

**怎么交代**：「我们的看板是数字卡片 + 待办列表，没有做可视化图表。如果要加趋势图（比如每月签约量），需要引入 echarts 并新增按时间的聚合接口。」

**坦白点 ⑦：权限 key 叫 `report`，控制器却叫 `book`。**

台账接口的权限是 `@SaCheckPermission("contract:report:list")`（`ContractBookController.java:93`/`:104`），控制器路径却是 `/contract/book`。**权限命名和控制器命名不一致**（权限里叫 report，因为语义上它就是"报表"；控制器叫 book，因为业务上叫"台账"）。没有对应 `contract/report` 路径的控制器。命名漂移，但不影响运行。

**拿到需求先做四件事**

① **给需求定性，再推架构**

| 判断维度 | 本模块的答案 | 推出的设计 |
|---|---|---|
| 数据性质 | 纯查询，不写业务数据 | 不建表，只做读模型 |
| 数据源 | 多表 join + 聚合 | 手写 SQL / 独立 Mapper |
| 权限 | 看板、台账两档 | 两种施加方式（注解 / 手工拼） |
| 性能 | 与业务同库 | 慢查询会拖垮业务，要有边界意识 |

→ 架构：统计接口 + 台账查询 + 导出，共用现有表，不新增表。

② **定数据源**：合同主表 + 审批单 + 引擎待办表 + 备注表，全是读。

③ **定接口**：统计卡、待办数、台账列表、导出、备注，见 §四。

④ **定实现边界：哪些不用写、哪些必须写、哪些是缺口**

- **框架给**：分页、数据权限、Excel 导出；
- **必须自己写**：聚合 SQL、台账 join、导出后处理；
- **已知缺口**：报表与业务同库、无读写分离；无预聚合；导出全量内存组装。

**数据设计：不建表，难点在「查得对、查得快」**

| 数据 | 来源 | 备注 |
|---|---|---|
| 各状态合同数 | `contract_draft` 按 `CONTRACT_STATUS` 分组 | 一条 `GROUP BY` |
| 待办数 | `act_ru_task`（引擎运行时表） | 只算当前登录人 |
| 台账列表 | `contract_draft` + 审批单 `LEFT JOIN` | 手写 SQL |
| 备注 | `contract_remarks` | 人工填写 |
| 数据权限 | `dashboardPermission` / `ledgerPermission` | 两档分开配 |

**报表和业务的本质区别**（本章核心认知）：

| 维度 | 业务查询 | 报表查询 |
|---|---|---|
| SQL | 按 id 查、增删改 | `COUNT` / `GROUP BY` / 多表 join |
| 数据量 | 单条 / 少量 | 全表级别 |
| 能不能慢 | 不能 | 可以慢，但**不能拖垮业务** |
| 索引 | 主键 / 唯一索引 | 往往要专门加报表索引 |

**为什么这条区别重要**：报表和业务共用连接池时，一个「导出全年合同」的慢查询可能把连接池占满，业务接口全部超时。正规做法是拆读库 / 预聚合；**本章这套开源代码没有拆**，这是要能说出口的坦白点。

**四个关键取舍**

| 决策 | 选择 | 代价 | 什么情况下反过来 |
|---|---|---|---|
| 实时查 vs 预聚合 | 实时查 | 数据量大时慢 | 上百万行、要求秒开时建汇总表 |
| 同库 vs 读库 | 同库 | 慢查询影响业务 | 报表和业务分离部署 |
| 台账导出 | EasyPOI `ExcelBuilder` | 代码多 | 简单表头可用 `ExcelUtil` |
| 看板权限 | 单独一档 `dashboardPermission` | 配置项多 | 和台账共用一档 |

**已知缺陷 / 边界**

- **报表和业务同库同连接池**，没有读写分离（§2.7）；
- **台账查询 join 多表**，没看到专门的报表索引；
- **导出是全量内存组装**，数据量再大要分批；
- **看板数字是实时算的**，不是缓存，刷新一次跑一次聚合。

**施工计划**

### 4.1 首页看板后端：`contractCount`

**本步目标**：一条聚合 SQL 出各状态合同数，并受看板数据权限限制。
**做完的标志**：页面数字和直接跑 SQL 一致；换角色数字变小。

**位置**：`zxcm-contract/src/main/java/com/ruoyi/contract/controller/DashboardController.java:77`

**完整逻辑**：

```java
@GetMapping("/contractCount")
public R<Map> dashboard() {

    // ① 算出当前用户的数据权限 SQL 片段（手工式，§2.3）
    String s = DataPermissionHelper.getContractDataPermissionSql(
        LoginHelper.getLoginUser(),
        "contract_charge_id",
        DataPermissionResource.dashboardPermission);
    if (StringUtils.isNotEmpty(s)) {
        s = " AND " + s;   // 拼成 " AND (...)"
    }

    // ② 依次统计 7 个状态的数量（每次都用 last(s) 加权限）
    LambdaQueryWrapper<ContractDraft> draft = new LambdaQueryWrapper();
    draft.eq(ContractDraft::getContractStatus, ContractStatusEnums.draft.getIndex()); // "0"
    draft.last(s);                                  // ← 手工追加权限条件
    Long draftCount = contractDraftMapper.selectCount(draft);

    // ... audit(3) / signing(4) / signed(5) / suspend(7) / done(8) 同理 ...

    // ③ "履行中"要额外判断"当前是否在有效期内"
    LambdaQueryWrapper<ContractDraft> fulfil = new LambdaQueryWrapper();
    Date yyddmm = DateUtil.parse(DateUtil.today());
    fulfil.eq(ContractDraft::getContractStatus, ContractStatusEnums.fulfil.getIndex()); // "6"
    fulfil.le(ContractDraft::getEffectiveTime, yyddmm);   // 生效时间 <= 今天
    fulfil.and(i -> i.ge(ContractDraft::getEndTime, yyddmm).or().isNull(ContractDraft::getEndTime));
    // ↑ (到期时间 >= 今天) 或 (到期时间为空=无固定期限)
    fulfil.last(s);
    Long fulfilCount = contractDraftMapper.selectCount(fulfil);
    // ...
}
```

**「履行中」的计数条件值得单独说**——它不是简单的 `status = 6`，而是：

```
status = 6  AND  生效时间 <= 今天  AND  (到期时间 >= 今天 OR 到期时间为空)
```

也就是「**已经生效、还没到期的履行中合同**」。`isNull(EndTime)` 是为了兼容**无固定期限合同**（它们没有到期日，永远算履行中）。**这是业务语义 → SQL 条件的翻译，写报表最容易在这里出错。**

**怎么"复制"**：你的 `zxcm-learn` 里，先写最简版——7 个状态各一次 `selectCount`，条件只写 `status = X`。跑通后，再补「履行中」的生效/到期判断。

### 4.2 首页「即将到期」查询

**本步目标**：按结束时间筛出快到期合同。
**做完的标志**：列表条数和 SQL 一致。

**位置**：`DashboardController.java:124-133`

```java
LambdaQueryWrapper<ContractDraft> lqw = new LambdaQueryWrapper<ContractDraft>();
List<String> status = new ArrayList<String>();
status.add(ContractStatusEnums.fulfil.getIndex());   // "6"
status.add(ContractStatusEnums.suspend.getIndex());  // "7"
lqw.in(ContractDraft::getContractStatus, status);
Date remindTime = DateUtils.getStepBeforeDay(new Date(), -45);  // 今天 -（-45）天 = 45 天后
lqw.le(ContractDraft::getEndTime, remindTime);                  // 到期时间 <= 45天后

```

**关键点**：`DateUtils.getStepBeforeDay(new Date(), -45)` **负数是往后推**——所以 `remindTime` = **45 天后**。条件是「履行中/中止状态 且 到期时间在 45 天内」。

**为什么是 45 天？** 这是个**业务上拍的经验值**（给续签留出 1.5 个月的处理时间）。**注意**：`-45` 是**硬编码的魔数**，理想做法是配置化（`sys.todo.remindDays`）。这是一个可以主动提的改进点。

**两个查「即将到期」的地方重复**：`contractCount`（`:131`）和 `todoCount`（`:175`）各写了一遍。区别是 `todoCount` 多了 `isNull(RenewedStatus)`（还没设置续约状态的才算待办）。

private QueryWrapper<ContractDraft> buildQueryWrapper(ContractBookBo bo) {

```java
// packageData（:204-231）：把原始行加工成"人看的"
private List<ContractBookVo> packageData(List<ContractBookVo> vos) {
    List<FormVo> forms = formService.queryList(new FormBo());                 // :205 拉全部表单
    Map<Long, FormVo> typeMap = forms.stream()
        .collect(Collectors.toMap(FormVo::getId, form -> form, (a, b) -> a)); // :209-210 表单id -> 表单
    // 预加载 5 套字典：收支类型/币种/合同状态/纠纷状态/发票类型（:212-216）
    for (ContractBookVo vo : vos) {
        fillFromAuditForm(vo);                                                // :218 从 JOIN 出来的 auditForm 补字段
        vo.setInouttype(dictLabel(inoutData, vo.getInouttype()));             // :219 0/1/2 -> 文字
        vo.setCurrency(dictLabel(currencyData, vo.getCurrency()));            // :220
        fillContractTypeName(vo, typeMap);                                    // :221 合同类型id -> 表单名
        vo.setContractStatusName(dictLabel(statusData, vo.getContractStatus())); // :222
        // 纠纷状态、发票类型同理（:223-228）
    }
    return vos;
}
```

**这段到底在干什么？** 分三件事：
1. `fillFromAuditForm`（`:249-275`）：SQL 已经把审批单字段映射成 `vo.auditForm`，这里只在「合同表自己的字段为空」时用审批单的值兜底；
2. `dictLabel`（`:242-247`）：把数据库里的 `0/1/2` 翻译成「收入类/支出类」这种给人看的文字；
3. `fillContractTypeName`（`:277-293`）：`contract_type` 存的是 JSON 形式的类型 id 链，取最后一个 id 去 `typeMap` 里找表单名。

**为什么不在 SQL 里做完？** 字典翻译要查 `sys_dict_data`，在 SQL 里写一堆 `CASE WHEN` 或多次 JOIN 字典表会很啰嗦；放到 Java 里用「先加载字典 Map、再逐条替换」更清晰。**代价是 `formService.queryList(new FormBo())` 会把全部表单拉进内存**（`:205`）——数据量大时也是 OOM 隐患。

    String[] archiveKey = {"归档档案库"};                                      // :310

    List<String> subject = numberedHeaders("签约主体", maxSubject);            // :314

    int totalRow = header1.length + subject.size() + partner.size() + header2.length
        + disputeHeader.length + archiveKey.length + change.size();            // :323-324
    eb.addOneRow("合同台账报表", totalRow, 50, getHeaderStyle(eb.getWorkbook())); // :325
    eb.addNoneRow();                                                           // :326
    eb.addCells(header1, 1, 0);                                                // :327
    eb.addCells(subject, 1, header1.length);                                   // :328
    // ...合作方、header2、纠纷列、变更列、归档列依次写到第 1 行（:329-335）

    int row = 2;                                                               // :337
    int index = 1;                                                             // :338
    for (ContractBookVo vo : vos) {                                            // :339
        eb.addNoneRow();                                                       // :340
        addBaseColumns(eb, vo, row, index);                                    // :341

        eb.addCells(splitCsv(vo.getPartnerNames()), row, header1.length + subject.size()); // :343

**逐行读（按"为什么要这么绕"来理解）**：

| # | 行号 | 这一行在干什么 | 为什么这么写 |
|---|---|---|---|
| 1 | `:295` | 方法返回 `ExcelBuilder`，不是 `Workbook` | 调用方 `export` 在 `:111` 通过 `.getWorkbook()` 取底层工作簿，再写给响应流；Builder 负责「按行拼」，Workbook 负责「输出」 |
| 2 | `:296-303` | **第一遍扫描数据**，统计「合作方」「签约主体」最多各几个 | 这两组列的**数量不固定**；不先扫一遍，就无法决定表头有多少列、后面的列从第几列开始 |
| 3 | `:305` | `ExcelBuilder.create()` 创建构建器，`setRowHeight(20)` 设行高 | `create()` 默认用 `XSSFWorkbook`（`ExcelBuilder.java:63-64`、`:77-84`），所以输出 `.xlsx`；行高设置对整个 sheet 生效 |
| 4 | `:306-310` | 定义三段固定表头：`header1`、`header2`、`archiveKey` | 把「合同基础信息」和「业务信息」拆成两段，便于按列偏移量拼接；归档列单独一段 |
| 5 | `:313-314` | `numberedHeaders("合作方", maxPartner)` 生成「合作方1、合作方2…」 | 动态列靠这个方法生成，数量来自第 2 步的扫描结果；`numberedHeaders` 本体在 `:416-422` |
| 6 | `:323-325` | 算出总列数 `totalRow`，写标题行并**横向合并 0 ~ totalRow-1 共 totalRow 列** | `addOneRow(content, cellSize, rowHeight, style)` 内部会调 `PoiMergeCellUtil.addMergedRegion`（`ExcelBuilder.java:153-160`），所以标题能跨整张表 |
| 7 | `:327-335` | 按「列偏移量」把各段表头写到第 1 行 | 因为列是动态的，不能像普通导出那样一个字段一列；必须从 `header1.length` 开始算下一段的起点 |
| 8 | `:339-354` | 第二遍遍历数据，每行先加空行，再按同样的偏移量写各段值 | 第一遍算列数、第二遍写数据，是「动态表头」的典型两遍扫描 |
| 9 | `:111-114` | 取 `Workbook`，设 `.xlsx` 响应头，写 `response.getOutputStream()` | 这是文件下载的标准三件套：Content-Type + 输出流 + close |
| 10 | `:117-123` | `finally` 里 `workbook.close()` | XSSFWorkbook 是全内存对象，不 close 会占内存/文件句柄 |

**关于内存**：`ExcelBuilder.create()` 默认创建 `XSSFWorkbook`（全内存，.xlsx 2007+）；对应还有 `HSSFWorkbook`（老的 .xls）。几万行就会占不少内存。大数据量应该换 `SXSSFWorkbook`（流式，边写边刷盘）或直接用 EasyExcel。

**响应头**（`ContractBookController.java:112`）固定套路，背下来：

```java
response.setContentType("application/vnd.openxmlformats-officedocument.spreadsheetml.sheet;charset=utf-8");
```

这个长 MIME 类型就是 **.xlsx 的标准 Content-Type**。

**怎么"复制"**：先照抄 `ExcelUtil.exportExcel(...)` 一行搞定（`ContractRemarksController.java:87` 那种）。等你需要「动态列 / 多段表头」时，再照着 `createExcel` 用 `ExcelBuilder` 的链式 API。

## 六、本章面试官高频问题 + 答案（企业级开发者角度）

**Q1：报表查询和普通业务查询有什么区别？**
> 三个核心区别：①**数据量**——报表查全表级别，业务查单条；②**SQL 形态**——报表用 COUNT/GROUP BY/JOIN 聚合，业务用主键/条件查；③**资源隔离**——报表慢查询不能拖垮业务，企业级会把报表放只读从库或预聚合表。

**Q2：你们的报表有没有做读写分离？**
> （**诚实回答**）没有。这个项目的报表 SQL 和业务 SQL 都放在 `ContractDraftMapper` 里，没有独立的报表 Mapper、也没有指向只读库。这是我们明确的优化方向——理想做法是拆出 `ContractReportMapper` 并用 `@DS("slave")` 指向从库。

**Q3：数据权限是怎么加到查询里的？**
> 有两套机制。**注解式** `@DataPermission` 由 MyBatis-Plus 拦截器自动把权限条件织入 SQL，作用于自定义 Mapper 方法；**手工式** `DataPermissionHelper.getContractDataPermissionSql` 自己算 SQL 片段拼进去，用于 BaseMapper 自带方法（如 `selectCount`，拦截器管不到）。两套并存是因为**覆盖范围不同**。

**Q4：手工式数据权限有什么风险？**
> 最大风险是**开发者忘记加**。它不像注解那样有机制保障，全靠人工纪律。一旦漏加，查询就**越过权限暴露全公司数据**。企业级应该统一成 AOP 切面拦截所有 Mapper 方法。

**Q5：首页统计你这个是怎么实现的？**
> 每个合同状态一次 `selectCount`，加上数据权限条件。「履行中」还要额外判断「已生效且未到期」。**坦白说这里跑了 7 次 COUNT，可以优化成一次 `GROUP BY contract_status`**——这是我知道的性能优化点。
>
> **追问：改成 `GROUP BY` 后，数据权限怎么加？**
> 照样加。权限片段是拼在 `WHERE` 后面的，`GROUP BY contract_status` 只是把「7 次单状态查询」换成「1 次分组查询」，权限条件仍然放在 `WHERE`（现在的手工片段见 `DashboardController.java:80-84`，模板解析见 `DataPermissionHelper.java:96-138`）。

**Q6：台账查询为什么要 JOIN 三张表？**
> 因为展示字段分散在三张表：合同基础信息在 `contract_draft`，合作方/金额/申请人在 `contract_audit_form`，归档卷名在 `conf_archives`。JOIN 一次拿全，避免 N+1 查询。

**Q7：台账导出有什么风险？**
> 导出用的 `bookList` **没有分页、没有上限**，会把全部数据读进内存，**大表会 OOM**；而且 `ExcelBuilder.create()` 默认用 `XSSFWorkbook`（全内存），几万行就占不少内存。企业级应该用**流式导出**（`SXSSFWorkbook`）或**异步导出**（后台生成 + 下载链接）。

**Q8：为什么台账导出用 EasyPOI 的 `ExcelBuilder`，不用封装的 `ExcelUtil`？**
> 因为台账导出是「**动态列 + 两段表头**」：合作方、签约主体有几列要先扫数据才知道，`ExcelUtil` 那种「实体字段固定、注解映射」的模式表达不了。`ExcelBuilder` 可以按行、按列偏移量手工拼，还写入了字典翻译后的值。**通用工具够用就用，不够用就换更灵活的**；代价是要自己管资源（`workbook.close()` 放 finally）。
>
> **追问：那它和 EasyExcel 比呢？**
> `ExcelBuilder` 最终建的是 `XSSFWorkbook`，全内存；数据量大时应该换 EasyExcel（SAX 流式）或 `SXSSFWorkbook`。当前台账量级下够用，属于「先能跑、再优化」的取舍。

**Q9：`COALESCE(a.project_name, b.project_name)` 是干什么的？**
> 项目名在合同表和审批表单里都可能存在，`COALESCE` 取第一个非 NULL 的——优先用合同表自己的，没有就用审批表单的。这是**同一字段分散在多表**的常见处理。

**Q10：默认排序为什么要三重？**
> `ORDER BY 审批通过时间 DESC, 创建时间 DESC, id ASC`。如果只按一个可能重复的字段排序，**同一时间的记录顺序不确定，翻页会出现重复或遗漏**。加上唯一列（id）保证排序**稳定**。

**Q11：首页的统计数字是"全部"还是"我的"？**
> 受数据权限控制。用 `dashboardPermission` 这套规则 + 按 `contract_charge_id`（合同负责人）过滤。部门经理看本部门、员工看自己、管理员看全部。

**Q12：待办数的数据从哪来？**
> 从流程引擎来。合同模块的 `DashboardController` 调 workflow 模块的 `WorkflowService.getMyTodoCount`，后者用 Activiti 查「待我处理的 `audit/change/stamp/stampChange` 流程任务」。这是**模块间依赖**。

**Q13：看板多久刷新一次？**
> 前端进入首页时查一次；待办数另有 **WebSocket 推送**——后端有新待办主动推给前端，前端对比数量变化后弹提示并重查。不是纯轮询。

**Q14：你这个"看板"有图表吗？**
> （诚实）没有。目前是数字卡片 + 待办列表，没有引入 echarts。要做趋势图（如每月签约量）需要新增按时间聚合的接口 + 前端图表库。

**Q15：如果台账有 50 万条合同，你怎么办？**
> ①**列表**：分页不变（本来就有分页插件）；②**导出**：改成异步任务——用户点导出后后台跑，生成文件存 OSS/文件服务，完成后发通知给下载链接；③**查询**：为高频筛选字段加索引，甚至做**预聚合表**（把台账常用统计预先算好）；④**隔离**：报表查询指向只读从库，不占主库连接。

## 七、为什么不选其他技术栈（选型对比）

### 7.1 为什么用「MyBatis-Plus 动态条件拼接」而不是「写死的多条 SQL」

| 方案 | 优点 | 缺点 | 本项目选择 |
|---|---|---|---|
| **`QueryWrapper` 动态拼（当前）** | 一个方法应对 20+ 种筛选组合 | SQL 不直观、复杂查询难维护 | ✅ |
| 每个筛选组合写一条 SQL | 每条 SQL 清晰 | **组合爆炸**（20 个条件 = 上百万种组合，不可能穷举） | ❌ |
| XML 里 `<if>` 动态 SQL | SQL 直观 + 动态 | 需要写 XML、和 Java 分离 | ❌（本项目用注解 SQL） |

**结论**：筛选条件多且可任意组合时，**动态拼接是唯一可行方案**。`QueryWrapper` 的 `.like(条件成立, "列", 值)` 语法正是为此设计。

### 7.2 为什么用「注解 `@Select` 写 SQL」而不是「XML Mapper」

| 方案 | 优点 | 缺点 | 本项目选择 |
|---|---|---|---|
| **注解 `@Select`（当前）** | SQL 和接口在一起、好找 | 长 SQL 塞注解里难读 | ✅ |
| XML Mapper | SQL 独立、支持复杂动态标签 | 两个文件来回跳 | 部分用 |
| MyBatis-Plus 纯 Wrapper（不写 SQL） | 零 SQL | **多表 JOIN 写不了** | ❌ |

**结论**：**单表/简单查询用 Wrapper，多表 JOIN 用注解 SQL**。本项目报表查询（`bookPage` 等三表 JOIN）都用注解 SQL，因为它能塞进一个注解。**超过一定复杂度（比如带 `<if>` 分支）才值得迁到 XML**。

### 7.3 为什么「手工式数据权限」不能完全取代「注解式」

| 方案 | 覆盖范围 | 是否容易漏 | 本项目 |
|---|---|---|---|
| 注解 `@DataPermission` | 只能注解自定义方法 | 不容易（机制保障） | 用于 Mapper 自定义方法 |
| 手工 `DataPermissionHelper` | 任何查询 | **容易漏** | 用于 BaseMapper 方法 |
| AOP 切面（理想） | 所有 Mapper 方法 | 不容易 | ❌ 本项目没做 |

**结论**：手工式的存在**是技术债**——理想方案是 **AOP 切面统一拦截所有 Mapper 方法**。本项目因为 Annotation 覆盖不到 `BaseMapper.selectCount`，不得不手工，形成两套并存的局面。

### 7.4 为什么用「EasyPOI `ExcelBuilder`（底层 `XSSFWorkbook`）」而不是「第三方报表工具（JasperReport / EasyExcel）」

| 方案 | 优点 | 缺点 | 本项目选择 |
|---|---|---|---|
| **EasyPOI `ExcelBuilder`（当前，底层 `XSSFWorkbook`）** | 链式 API、动态列/多段表头能表达、项目已有依赖 | 全内存、代码量大 | ✅ |
| **EasyExcel（阿里）** | 内存友好（SAX 流式）、API 简洁 | 多一个依赖、自定义样式略绕 | ❌（本项目用 EasyPOI） |
| JasperReport | 模板化、专业报表 | 重、学习成本高、需要设计器 | ❌ |

**结论**：本项目**通用导出用 `ExcelUtil`（底层也是 POI），台账这种动态列导出用 EasyPOI 的 `ExcelBuilder`**。**如果让我重构，大数据量导出我会换 EasyExcel**——它用 SAX 流式解析，50 万行也不会 OOM。这是一个很好的"如果重来我会怎么选"的答点。

### 7.5 为什么「预聚合」是小项目不该过早上的东西

| 方案 | 优点 | 缺点 | 何时该用 |
|---|---|---|---|
| **实时聚合查询（当前）** | 数据实时、零维护 | 大表慢 | 数据量 < 百万 |
| 预聚合表 / 定时任务算好 | 查询极快 | **要维护同步**、数据有延迟 | 数据量大 + 性能要求高 |
| 物化视图 | 自动刷新 | 依赖数据库特性 | 特定数据库 |

**结论**：对本项目这种合同量级（`selectCount` 7 次），**几十万条以内通常还跑得动**（具体取决于机器、索引和数据分布），**不必过早预聚合**。**过早做预聚合 = 引入数据同步复杂度却没有收益**。这是 YAGNI（你不会需要它）原则的典型应用——等真慢了再说。
