# 第 3 章 · 编号规则

> 前面两章录的是「主数据」（我方主体、对方公司）。本章开始碰「**合同的编号**」——比如 `HT-2024-0001`、`BX-202406-0007`。
>
> 编号看着简单，实则是后端最容易出 bug 的地方之一：**怎么保证不重号？** 单机能靠锁，集群呢？预览时编号能变吗？本章就把这些问题讲透。
>
> **本章第一次讲透**：① **Redis 缓存**（编号预览为什么要缓存、怎么缓存）；② **`synchronized` 在单机能用、集群会重号**这个经典坑；③ **`REQUIRES_NEW` 独立事务**——「宁跳号、不重号」的取舍。
>
> **本章你会碰到的表**：`conf_bill_rule`（规则定义）+ `conf_bill_rule_ext`（扩展计数器）+ Redis（本章第一次用）。
>
> **两种读法**：想先理解「为什么缓存、为什么能重号」→ 读 §四；想直接动手、边复制边调试 → 读 **§五「施工版」**，它按 6 个业务动作给完整代码，并带你验证「预览两次只加一次号」。

> **零基础先补概念（编号问题的四个关键词）**
>
> - **Redis 缓存**：一个把数据放在内存里的 key-value 存储，读写极快，可以给 key 设置过期时间（TTL）。本章用它存「预览编号」：`BILLRULE_用户ID_规则编码_日期` → 编号，24 小时过期（`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/ConfBillRuleServiceImpl.java:371-375`）。
> - **`synchronized`（对象锁）**：Java 关键字，保证同一个 JVM 里同一时刻只有一个线程进入某段代码。注意它锁的是「当前对象」，**管不到另一台服务器上的 JVM**。
> - **事务传播 `REQUIRES_NEW`**：Spring 事务的一种传播行为，意思是「先挂起外层事务，自己开一个新事务，干完立刻提交」。本章用它实现「编号生成不随业务回滚」。
> - **原子操作**：一个不会被其他线程打断的操作。Redis 的 `INCR` 是原子的，所以多台服务器同时自增也不会算错；这正是本项目 `synchronized` 在集群下的替代方案（§2.4）。

## 一、这部分是做什么的？

### 1.1 业务含义

公司里的合同要有**编号**，而且编号常常有含义——比如「**合同类型 + 年份 + 当月第几份**」。不同公司、不同合同类型，编号规则还不一样。

所以系统做了一个「**编号规则配置**」功能：管理员**用拼积木的方式**定义编号长什么样，系统按规则自动生成。

![编号规则页结构示意](images/bill-rule-page-schematic.svg)

> **图注**：按 `billRule/index.vue` 的结构画的**示意图，不是真实截图**（官方未提供该页面截图）。上半部分是规则列表（规则存成 JSON 数组），下半部分演示「固定串 + 日期 + 流水号」怎么拼出一个编号。

### 1.2 编号是怎么「拼」出来的

规则存在 `conf_bill_rule.rule` 字段里，是一个 **JSON 数组**，数组里每个元素是编号的一个「**片段**」。片段有类型（`type`）：

| `type` | 含义 | 例子 |
|---|---|---|
| `1` | 固定字符串 | `"HT"`（合同） |
| `2` | 年月日（固定格式） | `20240617` |
| `3` | 按**年**重置的流水号 | 0001、0002…（跨年归零） |
| `4` | 按**月**重置的流水号 | 0001、0002…（跨月归零） |
| `5` | 按**日**重置的流水号 | 0001、0002…（跨日归零） |
| `6` | 合同类型编号 | 略 |
| `8` | 起草部门编号 | 略 |
| `9` | 流程编号 | 略 |
| `subject` | 第一个签约主体编号 | 略 |
| `time-yyMM` / `time-yyyy` | 年月 / 年（另一种格式） | 略 |
| `relateCode` | 关联合同编号 | 续签时用（第 9 章） |
| `number` | 流水号（**不重置**） | 0001、0002…（永远累加） |

**一串规则拼起来就是一个编号**。比如规则是 `[{"type":"1","string":"HT"},{"type":"2"},{"type":"4"}]`，生成的就是 `HT` + `20240617` + `0001` = `HT202406170001`。

> 常量定义在 `ConfBillRuleServiceImpl.java:65-77`。
> ⚠️ **小观察**：类型编号里**没有 `7`**（1,2,3,4,5,6,8,9）——中间有个空洞，应该是历史遗留（`7` 被废弃了）。这种「代码里的空洞」在真实项目里很常见，面试被问到可以诚实说。

### 1.3 三个容易被忽略但很关键的需求

1. **「预览」时编号不能变**：用户打开草拟页面，系统自动填一个编号给他看。如果他刷新一下页面编号就变了（0001→0002），那 0002 就被白白浪费了。所以**预览的编号要缓存住**，反复刷新看到的还是同一个。
2. **「真正用了」才消耗编号（设计目标）**：理想情况下，只有保存/提交时编号才算被占用。**但当前实现不是这样**——第一次预览调用 `getNumber` 时计数器就已经 `+1` 了（§2.3），`useBillNumber` 只是删预览缓存、并不会「占用」编号。这一点在 §2.3 和 §6.2 会讲清楚，属于「设计目标与实现不一致」的坦白点。
3. **不能重号**：两个人同时保存，绝不能生成两个 `0001`。

| 接口 | 干什么 |
|---|---|
| `GET /conf/billRule/list` | 规则列表 |
| `GET /conf/billRule/{id}` | 规则详情 |

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么编号规则要用「JSON 数组配置」，而不是给每种规则写死代码？

想象一下写死代码：`if (类型 == 合同) 编号 = "HT" + 年份 + 流水号; else if (类型 == 报销) ...`。一旦客户要求「我们合同编号要加部门」，就得改代码重新发版。

**JSON 数组配置**把「编号长什么样」变成了**数据**：管理员在页面上拖几个片段、配好顺序，编号就变了，**代码一行不用改**。这是「**把变化点数据化**」的经典设计——凡是业务上会变的规则，都别写死在代码里。

代价是代码要「解释」这串 JSON（就是 §4.4 那一大段 `if-else` 遍历）。**用一段稍复杂的解释器代码，换来了业务的灵活性**，很值。

### 2.2 最核心的设计：为什么「预览编号」要缓存到 Redis？

这是本章最重要的设计。看 `ConfBillRuleServiceImpl.java:364-383` 的 `getBillNumber`：

```java
public String getBillNumber(String enCode, Map<String, String> params, boolean isCache) {
    String strNumber;
    if (isCache == true) {
        String thisDate = DateUtils.format(new Date(), "yyyyMMdd");
        String cacheKey = "BILLRULE_" + LoginHelper.getUserId() + enCode + thisDate;   // ← 缓存 key

        if (!RedisUtils.hasKey(cacheKey)) {
            strNumber = this.getNumber(enCode, params);              // 缓存没有 → 真正生成一个
            RedisUtils.setCacheObject(cacheKey, strNumber, Duration.ofHours(24));   // 存 24 小时
        } else {
            strNumber = RedisUtils.getCacheObject(cacheKey).toString();   // 缓存有 → 直接返回
        }
    } else {
        strNumber = this.getNumber(enCode, params);      // 不走缓存，每次都新生成
    }
    return strNumber;
}
```

**逐行读：这段「预览缓存」的 8 行**

| 行 | 代码 | 在干什么 | 为什么这么写 |
|---|---|---|---|
| 1 | `public String getBillNumber(...)` | 对外的「取编号」入口 | Controller 和内部业务都调它 |
| 2 | `if (isCache == true)` | 判断是「预览」还是「真实占用」 | 同一个方法用布尔参数区分两种语义 |
| 3 | `DateUtils.format(new Date(), "yyyyMMdd")` | 取当天日期字符串 | 让缓存按天自然隔离 |
| 4 | `"BILLRULE_" + 用户ID + enCode + thisDate` | 拼缓存 key | 用户 + 规则 + 日期三个维度，张三的预览不会覆盖李四的 |
| 5 | `if (!RedisUtils.hasKey(cacheKey))` | 缓存里有没有 | 有就直接复用，避免重复消耗编号 |
| 6 | `strNumber = this.getNumber(enCode, params)` | 缓存没有 → 真正生成 | 注意：这一步会读写数据库计数器 |
| 7 | `RedisUtils.setCacheObject(..., Duration.ofHours(24))` | 把新编号缓存 24 小时 | key 已带日期，24 小时是双保险 |
| 8 | `else { strNumber = RedisUtils.getCacheObject(cacheKey).toString(); }` | 命中缓存 → 直接返回 | 刷新页面看到的还是同一个编号 |

**为什么必须缓存？** 回到 §1.3 的需求 1：用户打开页面 → 系统调 `getBillNumber` 生成 `0001` → 用户刷新 → 又调一次 → 如果没有缓存，就会生成 `0002`。**用户什么都没做，编号就被消耗掉了**（因为「生成编号」这个动作本身会把计数器 +1，见 §2.3）。

缓存后：同一个用户 + 同一个规则 + 同一天，**反复调都返回同一个编号**，只有缓存过期或主动清掉才会重新生成。

**缓存 key 的设计也有讲究**：`BILLRULE_ + 用户ID + 规则编码 + 日期`（`:371`）——按「用户」隔离（张三的预览编号和李四的互不影响）、按「日期」隔离（跨天自动失效）。

### 2.3 为什么「生成编号」就等于「消耗一个号」？（所以才有那个清缓存接口）

看 `getNumber` 的核心逻辑（`:219-233`，以按年重置的流水号为例）：

```java
if (numberType.equals("0")) {
    Date d = entity.getThisNumberDate();
    Date currentDate = new Date();
    String thisYearDate = DateUtils.format(currentDate, "yyyy");
    String oldYearDate = DateUtils.format(d, "yyyy");
    // 处理每年编号重置的功能
    if (!thisYearDate.equals(oldYearDate)) {
        entity.setThisNumber(entity.getStartNumber());      // 跨年了 → 用起始号
    } else {
        entity.setThisNumber(entity.getThisNumber() + 1);   // 同一年 → 计数器 +1
    }
    entity.setThisNumberDate(currentDate);
    strNumber.append(PadUtil.padRight(String.valueOf(entity.getThisNumber()),
        entity.getNumberLength().intValue(), '0'));         // 左侧补 0 到指定长度
}
// ... 循环结束后：
this.baseMapper.updateById(entity);    // :355  ★ 把计数器写回数据库
```

**关键**：只要规则里含流水号片段，每次调 `getNumber` 都会 **`+1` 并写库**（`:355`）——所以「生成编号」!=「看看编号」，它是**真的把号用掉了**。纯固定文本的规则不会改变计数器，但同样会把 `entity` 更新回库。

这就解释了两个设计：
1. **为什么要有 Redis 预览缓存**（§2.2）——避免预览动作白白消耗编号。
2. **为什么要有 `useBillNumber` 清缓存接口**（`ConfBillRuleServiceImpl.java:386-390`）：
   ```java
   public void useBillNumber(String enCode) {
       String cacheKeyPrefix = "BILLRULE_" + LoginHelper.getUserId() + enCode + thisDate;
       RedisUtils.deleteObject(cacheKeyPrefix);      // 删掉缓存
   }
   ```
   它的语义是「**这个编号我真的用了，把它从缓存里抹掉**」。抹掉之后，下次预览会生成**新的**编号。**注意这里有个坑**：清缓存的接口只是「删缓存」，它**不会去占用编号**——因为编号在第一次 `getNumber` 时就已经 `+1` 占掉了。所以「预览→使用」的模型是：**首次预览即占用**，清缓存只是为了「用了之后别再显示旧的」。

### 2.4 为什么用 `synchronized` 保证不重号？它够用吗？（本章最该记住的坑）

看 `getNumber` 的方法签名（`ConfBillRuleServiceImpl.java:191-193`）：

```java
@Override
@Transactional(propagation = Propagation.REQUIRES_NEW)   // 独立事务
public synchronized String getNumber(String enCode, Map<String, String> param) {   // 加锁
```

- **`synchronized`**：给方法加**对象锁**，保证**同一个 JVM 内**同时只有一个线程能进来读计数器、+1、写回。
- **`REQUIRES_NEW`**：开一个**独立的新事务**（不复用外层事务）。

**这里有个致命问题：`synchronized` 只在单机有效。**

如果系统部署了**两个实例**（生产环境为了高可用常见），两个实例各有自己的 JVM、各有自己的锁：

```
实例 A：读计数器=5 → +1 → 写回 6
实例 B：读计数器=5 → +1 → 写回 6     ← 同时发生，两个都生成 0006！重号！
```

**`synchronized` 拦不住跨 JVM 的并发。** 这是分布式系统里最经典的坑之一。

**正确做法应该是什么？** 三种常见方案：

| 方案 | 做法 | 评价 |
|---|---|---|
| 数据库行锁 | `select ... for update` 锁住计数器那一行 | 能扛集群，但有锁等待、性能差 |
| **Redis 原子自增** | `RedisUtils.incr(key)`——Redis 是原子操作，天然跨实例 | 主流做法，性能好 |
| 号段模式 | 一次从数据库取 1000 个号到内存，用完再取 | 性能最好，但实例重启会跳号 |

> **面试这是必考题**：「你们的编号怎么保证不重号？」
> **标准答法**：单机用 `synchronized` + `REQUIRES_NEW` 能保证；但**集群下 `synchronized` 无效**（锁只在单个 JVM 内），会重号。生产上应该改成 **Redis 原子自增**（`incr`）或**数据库行锁 `for update`**。**能主动说出「这个实现集群下有风险」，比假装完美更让面试官信服**——说明你真懂并发。

### 2.5 为什么 `REQUIRES_NEW`（独立事务）？——「宁跳号、不重号」

`REQUIRES_NEW` 的意思是：**从当前事务里脱离出来，开一个全新的事务**。

为什么要这样？假设生成编号和外层业务（比如「保存合同」）在**同一个事务**里。如果外层业务后来**回滚了**，那么编号的 `+1` 也会跟着回滚——**编号被「还回去」了**，下一个请求会拿到同一个号。听起来挺好？但如果**并发的另一个请求已经拿到了下一个号**，回滚后的号就重复了。

所以编号的取舍是：**宁肯跳号（浪费几个号），也绝不重号**。用独立事务，意味着编号一旦生成就**立即提交、独立于业务成败**——业务回滚了，号也不退回（跳号），但绝不会和别人撞号。**这是「编号」这类场景的通用原则。**

### 2.6 为什么要拆出 `conf_bill_rule_ext` 这张表？（「拆表 = 拆锁」）

默认情况下，一个编号规则的计数器存在 `conf_bill_rule.this_number` 这一列里。但你看 §2.4 的 `synchronized`——**整个 `getNumber` 方法共用一把锁**。如果所有编号都挤在**同一行**计数器上：

- 按合同类型编号时，类型 A 和类型 B 的编号会**互相等锁**（明明是两件不相干的事）。

所以本项目拆出了 `conf_bill_rule_ext` 表，用 `(code, type, typeKey)`（`ConfBillRuleExtServiceImpl.java:94-97`）来**按维度分开计数器**：每个「合同类型」或每个「签约主体」有**自己独立的计数器行**。这样 A 和 B 的编号各算各的，**锁竞争小了**。

> **这叫「拆表拆锁」**——把一个热点行拆成多个行，减少数据库层面的行冲突。面试如果聊到高并发编号，「热点行拆分成多行」是个能加分的点。
>
> **但要诚实补一句**：当前 `getNumber` 整个方法仍被 `synchronized` 锁住（`ConfBillRuleServiceImpl.java:193`），所以 ext 表并没有真正消除「方法级串行」——它解决的是「不同维度共用一个计数器」的语义问题和数据库行更新冲突。要把方法锁竞争也降下来，得缩小锁粒度（按 `code/type/typeKey` 分段加锁）或换成 Redis 原子自增。

### 4.2 Entity

```java
@Data
@EqualsAndHashCode(callSuper = true)
@TableName("conf_bill_rule")
public class ConfBillRule extends BaseEntity {
    @TableId(value = "id")
    private Long id;                 // ← 注意是 Long
```

### 4.3 Service 的 `getNumber`：编号的「解释执行器」

这是本章代码量最大的一段（`ConfBillRuleServiceImpl.java:193-360`），但逻辑很直白：**读规则 JSON → 逐个片段拼字符串 → 最后把计数器写回库**。骨架：

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public synchronized String getNumber(String enCode, Map<String, String> param) {
    // 1. 取参数
    String deptCode = param.get("deptCode");
    String flowCode = param.get("flowCode");
    String subjectCode = param.get("subjectCode");
    // 2. 按规则编码查出规则
    ConfBillRule entity = baseMapper.selectOne(
        new QueryWrapper<ConfBillRule>().lambda().eq(ConfBillRule::getCode, enCode));
    if (entity != null) {
        StringBuilder strNumber = new StringBuilder();
        JSONArray array = JSONUtil.parseArray(entity.getRule());     // 规则 JSON
        for (int i = 0; i < array.size(); i++) {                     // 逐片段拼
            JSONObject o = array.getJSONObject(i);
            if (o.getStr("type").equals(TYPE_STRING)) {               // "1" 固定字符串
                strNumber.append(o.getStr("string"));
            } else if (o.getStr("type").equals(TYPE_DATE_yyyyMMdd)) {  // "2" 年月日
                strNumber.append(thisDate);
            } else if (o.getStr("type").equals(TYPE_NUMBER_yyyy)) {    // "3" 按年重置
                // ... 判断跨年 → 重置或 +1 → 补 0 → append
            }
            // ... type 4/5/6/8/9/"subject"/"relateCode"/"number" 各有分支
        }
        this.baseMapper.updateById(entity);      // ★ 计数器写回库
    } else {
        strNumber.append("单据规则不存在");        // ⚠️ 返回一个字符串当编号（见下）
    }
    return strNumber.toString();
}
```

> ⚠️ **一个「坏味道」**：规则不存在时，方法返回**字符串 `"单据规则不存在"` 当编号**（`:357`）。这意味着系统会**拿一句中文当合同编号存进数据库**——应该 `throw new ServiceException(...)` 才对。面试如果被问「异常处理」，这个例子可以说明「本项目有些地方把错误当返回值，不够规范」。

### 4.4 重置逻辑（三种周期的写法几乎一样）

`type 3/4/5` 分别对应「按年/按月/按日重置」，代码结构完全相同，只是格式串不同：

```java
// type=3 按年重置（:219-233）
String thisYearDate = DateUtils.format(currentDate, "yyyy");
String oldYearDate = DateUtils.format(d, "yyyy");
if (!thisYearDate.equals(oldYearDate)) {
    entity.setThisNumber(entity.getStartNumber());      // 跨年 → 回到起始号
} else {
    entity.setThisNumber(entity.getThisNumber() + 1);   // 同年 → 累加
}
entity.setThisNumberDate(currentDate);
strNumber.append(PadUtil.padRight(String.valueOf(entity.getThisNumber()),
    entity.getNumberLength().intValue(), '0'));          // 补 0 到 numberLength 位

// type=4 按月：格式 "yyyyMM"（:247-261）
// type=5 按日：格式 "yyyyMMdd"（:275-289）
```

**判断重置的机制很朴素**：把「上次生成日期」和「当前日期」按同样格式（年/年月/年月日）格式化，**字符串不相等就说明跨周期了**。比如按年重置，`"2024" != "2025"` → 重置。

**`PadUtil.padRight(String.valueOf(数字), 长度, '0')`** 把 `5` 补成 `0005`（`PadUtil.java:47`）。注意方法名叫 `padRight`，但实际是**在左边补 0、字符串右对齐**——名字有点误导，看代码为准。

### 4.5 本章重点：Redis 缓存的用法（第一次讲透）

**本项目的 Redis 工具类是 `RedisUtils`**（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/utils/redis/RedisUtils.java:37`），它把 Redis 操作包装成了几个好用的静态方法。本章用到三个：

```java
RedisUtils.hasKey(cacheKey)                          // 判断 key 存不存在
RedisUtils.getCacheObject(cacheKey)                  // 取对象（返回 Object，用 .toString() 转字符串）
RedisUtils.setCacheObject(cacheKey, value, Duration.ofHours(24))   // 存对象 + 设置过期时间
RedisUtils.deleteObject(cacheKey)                    // 删 key
```

**存的是「对象」不是「字符串」**——`RedisUtils.setCacheObject` 内部会做序列化，所以你存一个 `String`、取出来 `.toString()` 就能用。

**缓存 key 的命名规范**（`:371`）：`BILLRULE_` + 用户ID + 规则编码 + 日期。这是一个**很好的 key 设计范例**——前缀（业务域） + 维度（用户） + 标识（规则） + 版本（日期）。面试被问「Redis key 怎么设计」，就讲这个：**要有业务前缀、要包含会变的维度这样能自然失效、要设过期时间**。

> **为什么设 24 小时过期（`Duration.ofHours(24)`）？** 因为 key 里已经带了日期（`yyyyMMdd`），跨天 key 自然不同、旧的会自动过期。设 24 小时是双保险，防止野 key 堆积。

### 5.1 先看完整业务流

### 5.9 编号解释执行器：`getNumber`

这是整章最核心的方法。它读 `rule` 数组，**一段一段拼**：

```java
@Override
@Transactional(propagation = Propagation.REQUIRES_NEW)
public synchronized String getNumber(String enCode, Map<String, String> param) {
    String thisDate = DateUtils.format(new Date(), "yyyyMMdd");
    String deptCode = param.get("deptCode");
    String flowCode = param.get("flowCode");
    String subjectCode = param.get("subjectCode");
    String contractTypeCode = param.get("contractTypeCode");
    String relatedCode = param.get("relatedCode");

    StringBuilder strNumber = new StringBuilder();

    QueryWrapper<ConfBillRule> queryWrapper = new QueryWrapper<>();
    queryWrapper.lambda().eq(ConfBillRule::getCode, enCode);
    ConfBillRule entity = baseMapper.selectOne(queryWrapper);

    if (entity == null) {
        return "单据规则不存在";
    }

    JSONArray array = JSONUtil.parseArray(entity.getRule());
    String numberType = entity.getNumberType();

    for (int i = 0; i < array.size(); i++) {
        JSONObject o = array.getJSONObject(i);
        String type = o.getStr("type");

        if (TYPE_STRING.equals(type)) {
            strNumber.append(o.getStr("string"));
        } else if (TYPE_DATE_yyyyMMdd.equals(type)) {
            strNumber.append(thisDate);
        } else if (TYPE_CONTRACT_TYPE.equals(type)) {
            if (StringUtils.isEmpty(contractTypeCode)) {
                throw new ServiceException("合同类型编码不能为空");
            }
            strNumber.append(contractTypeCode);
        } else if (TYPE_DEPT.equals(type)) {
            if (StringUtils.isEmpty(deptCode)) {
                throw new ServiceException("部门编码不能为空");
            }
            strNumber.append(deptCode);
        } else if (TYPE_FLOW_CODE.equals(type)) {
            if (StringUtils.isEmpty(flowCode)) {
                throw new ServiceException("流程编码不能为空");
            }
            strNumber.append(flowCode);
        } else if (TYPE_SUBJECT.equals(type)) {
            if (StringUtils.isEmpty(subjectCode)) {
                throw new ServiceException("签约主体编号不能为空");
            }
            strNumber.append(subjectCode);
        } else if (TYPE_PARENT_CODE.equals(type)) {
            if (StringUtils.isEmpty(relatedCode)) {
                throw new ServiceException("关联合同编号不能为空");
            }
            strNumber.append(relatedCode);
        } else if (TYPE_NUMBER_yyyy.equals(type)) {
            strNumber.append(getNumberWithReset(entity, numberType, param,
                "yyyy", relatedCode, subjectCode, contractTypeCode));
        } else if (TYPE_NUMBER_yyyyMM.equals(type)) {
            strNumber.append(getNumberWithReset(entity, numberType, param,
                "yyyyMM", relatedCode, subjectCode, contractTypeCode));
        } else if (TYPE_NUMBER_yyyyMMdd.equals(type)) {
            strNumber.append(getNumberWithReset(entity, numberType, param,
                "yyyyMMdd", relatedCode, subjectCode, contractTypeCode));
        } else if (TYPE_NUMBER.equals(type)) {
            if ("0".equals(numberType)) {
                entity.setThisNumber(entity.getThisNumber() + 1);
                entity.setThisNumberDate(new Date());
            } else {
                strNumber.append(getExtNumber(entity, numberType,
                    relatedCode, subjectCode, contractTypeCode, param));
            }
        }
    }

    baseMapper.updateById(entity);   // 计数器落库
    return strNumber.toString();
}

/** 按年 / 月 / 日重置的流水号 */
private String getNumberWithReset(ConfBillRule entity, String numberType,
    Map<String, String> param, String pattern,
    String relatedCode, String subjectCode, String contractTypeCode) {

    if ("0".equals(numberType)) {
        Date old = entity.getThisNumberDate();
        Date now = new Date();
        String oldKey = DateUtils.format(old, pattern);
        String nowKey = DateUtils.format(now, pattern);

        if (!nowKey.equals(oldKey)) {
            entity.setThisNumber(entity.getStartNumber());   // 跨周期，回到起始号
        } else {
            entity.setThisNumber(entity.getThisNumber() + 1);
        }
        entity.setThisNumberDate(now);
        return PadUtil.padRight(String.valueOf(entity.getThisNumber()),
            entity.getNumberLength().intValue(), '0');
    }
    return getExtNumber(entity, numberType, relatedCode, subjectCode, contractTypeCode, param, pattern);
}

/** 独立计数器（扩展表） */
private String getExtNumber(ConfBillRule entity, String numberType,
    String relatedCode, String subjectCode, String contractTypeCode,
    Map<String, String> param) {
    return getExtNumber(entity, numberType, relatedCode, subjectCode, contractTypeCode, param, null);
}

private String getExtNumber(ConfBillRule entity, String numberType,
    String relatedCode, String subjectCode, String contractTypeCode,
    Map<String, String> param, String pattern) {

    String typeKey;
    if ("relatedCode".equals(numberType)) {
        typeKey = relatedCode;
    } else if ("subjectCode".equals(numberType)) {
        typeKey = subjectCode;
    } else {
        typeKey = contractTypeCode;
    }

    if (pattern == null) {
        return confBillRuleExtService.getBillNumber(numberType, typeKey, param, entity);
    }
    return confBillRuleExtService.getBillNumberWithResetByPattern(
        numberType, typeKey, param, entity, pattern);
}
```

**讲解**：

| 设计 | 为什么 |
|---|---|
| `synchronized` | 单机 JVM 内串行，防止两个请求同时读到同一个 `thisNumber` |
| `REQUIRES_NEW` | 编号生成独立事务：外层保存合同失败回滚，已消耗的号也不退回（宁跳号、不重号） |
| `StringBuilder` 逐段拼 | 规则是数据，不是代码；加新段类型只改解释器，不改业务 |
| 每段都校验参数 | 缺「合同类型编码」时直接报错，而不是拼出一个残缺编号 |

> **集群下的坑**：`synchronized` 只在**单个 JVM** 内有效。部署两个节点时，两个节点会同时读到 `thisNumber=5`，各自加 1 再写回，**产生重号**。生产上要换 Redis 自增 / 数据库行锁 / 号段，见 §2.4 和 §八 的选型对比。

### 5.10 扩展计数器：`conf_bill_rule_ext`

当 `numberType != 0`（按主体/合同类型/父合同独立编号）时，计数器不在主表，而在扩展表。核心逻辑：

```java
@Override
public String getBillNumberWithResetByPattern(String type, String typeKey,
    Map<String, String> param, ConfBillRule entity, String updatePattern) {

    if (StringUtils.isEmpty(typeKey)) {
        throw new ServiceException("生成扩展编号的参数不全，请检查编号规则的设置");
    }

    LambdaQueryWrapper<ConfBillRuleExt> wrapper = new LambdaQueryWrapper<>();
    wrapper.eq(ConfBillRuleExt::getType, type);
    wrapper.eq(ConfBillRuleExt::getTypeKey, typeKey);
    wrapper.eq(ConfBillRuleExt::getCode, entity.getCode());
    List<ConfBillRuleExt> exts = baseMapper.selectList(wrapper);

    if (exts.size() == 0) {
        // 第一次：建计数器，从 1 开始
        ConfBillRuleExt ext = new ConfBillRuleExt();
        ext.setType(type);
        ext.setTypeKey(typeKey);
        ext.setThisNumber(1L);
        ext.setStartNumber(1L);
        ext.setThisNumberDate(new Date());
        ext.setNumberLength(entity.getNumberLength());
        ext.setCode(entity.getCode());
        baseMapper.insert(ext);
        return PadUtil.padRight("1", entity.getNumberLength().intValue(), '0');
    }

    if (exts.size() == 1) {
        ConfBillRuleExt ext = exts.get(0);
        String oldKey = DateUtils.format(ext.getThisNumberDate(), updatePattern);
        String nowKey = DateUtils.format(new Date(), updatePattern);

        if (!nowKey.equals(oldKey)) {
            ext.setThisNumber(ext.getStartNumber());   // 跨周期重置
        } else {
            ext.setThisNumber(ext.getThisNumber() + 1);
        }
        ext.setThisNumberDate(new Date());
        baseMapper.updateById(ext);
        return PadUtil.padRight(ext.getThisNumber().toString(),
            entity.getNumberLength().intValue(), '0');
    }

    throw new ServiceException("查询到多个匹配规则，生成编号失败");
}
```

**讲解**：

- 查询条件是「规则编码 + 类型 + 类型值」，三者确定一个独立计数器；
- 第一次用某个 `typeKey` 时自动建行，从 1 开始；
- 查到多条直接报错，避免「不知道该加哪个」。

## 七、面试官高频问题 + 答案（企业级视角）

**Q1：你们的编号是怎么生成的？**

编号规则**存在数据库里**（`conf_bill_rule.rule` 是 JSON 数组），程序运行时解释这串 JSON，逐个片段拼接：固定文本直接拼、日期取当前时间、流水号则读写计数器。规则可变是因为**把「编号长什么样」数据化了**，改规则不用改代码。（指 `ConfBillRuleServiceImpl.java:193-360`）

**Q2：编号怎么保证不重号？**

**单机**：`getNumber` 方法加了 `synchronized`，保证同一 JVM 内串行执行「读计数器→+1→写回」。**但集群部署下 `synchronized` 无效**（锁只在单个 JVM 内），会重号。生产环境应改用 **Redis 原子自增（`incr`）** 或**数据库行锁（`select ... for update`）**。
**能主动指出这个风险**是加分项。（指 `ConfBillRuleServiceImpl.java:193`）
**追问：那换成 Redis `incr` 之后还需要 `synchronized` 吗？** 不需要本地锁了，但「读当前值 → 加一 → 写回」必须收敛成 Redis 的一条原子命令；如果仍然先 `get` 再 `set`，多实例下一样会重号。

**Q3：为什么 `getNumber` 要用 `REQUIRES_NEW` 开独立事务？**

为了「**宁跳号、不重号**」。如果编号生成和外层业务共用事务，业务回滚会把编号的 `+1` 一起回滚，重试时可能拿到已被人占用的号。独立事务让编号一旦生成就立即提交、不随业务回滚，代价是业务失败时会「跳号」（浪费几个号），但绝不会重号。

**Q4：为什么要在 Redis 里缓存「预览编号」？**

因为「生成编号」会**真的把计数器 +1**（`:355`）。用户打开模板草拟页面时系统会预填一个编号（真实调用见 `zxcm-ui/src/views/template/templateDrafts/TemplateDraftsEditDialog.vue:263-271`），如果不缓存，用户刷新几次页面就会白白消耗掉好几个号。缓存后，同一用户+同一规则+同一天反复请求返回同一个编号。（指 `ConfBillRuleServiceImpl.java:364-383`）
**追问：缓存过期了会怎样？** 过期后下一次预览会重新走 `getNumber`，计数器再 +1，用户会看到一个新号；如果旧号已经用在了业务上，就形成「旧号作废、正式号后移」的跳号。

**Q5：Redis 的 key 怎么设计的？**

`BILLRULE_ + 用户ID + 规则编码 + 日期`（`:371`）。前缀标识业务域，用户维度保证互不干扰，日期维度让 key 跨天自然失效；再配 24 小时过期做双保险。**设计 key 的通用原则：业务前缀 + 会变的维度 + 过期时间。**

**Q6：`useBillNumber` 清除缓存接口是干嘛的？**

语义是「这个编号我用了」。它删掉 Redis 里的预览缓存，这样下次预览会生成新编号。注意它**只删缓存、不占用编号**——编号在首次生成时就已 `+1`。

**Q7：为什么拆出 `conf_bill_rule_ext` 表？**

为了**减少数据库行冲突、让不同维度各自计数**（拆表拆锁）。默认所有编号共用 `conf_bill_rule.this_number` 一行计数器；拆出 ext 表按 `(code,type,typeKey)` 分计数器后，各维度独立自增。**注意**：`getNumber` 方法本身仍是 `synchronized`，所以方法级仍然是串行的；ext 表并没有消除这一点（§2.6 的补充说明）。

**Q8：如果编号规则不存在会怎样？**

当前实现会**返回字符串 `"单据规则不存在"` 当编号**（`ConfBillRuleServiceImpl.java:357`），这是不规范的——应该抛 `ServiceException`。属于可以指出的改进点。

**Q9：`thisNumber` 用数据库自增序列不行吗？**

不行。因为这里的流水号是**按周期重置**的（跨年/月/日回到起始值），数据库自增只增不减。而且项目用了 `REQUIRES_NEW` 独立事务，自增序列的消费和事务回滚关系复杂。用「一个字段存当前值 + 代码控制重置」更可控。

**Q10：编号规则里流水号类型（`numberType`）和片段类型（`type`）是什么关系？**

`type` 决定「这一片段是什么」（固定文本/日期/流水号…）；`numberType` 决定「流水号按什么维度算」（`0`=默认按 thisNumber 重置，或 `relatedCode`/`subjectCode`/`contractTypeCode`=按关联合同/主体/类型分别计数，走 ext 表）。两者配合才决定最终用哪套计数器。

### 本章答辩卡（3 组追问级问答）

**卡片 1：`synchronized` 加在 Spring 的 Service 方法上，锁的到底是哪个对象？Service 变成多例会怎样？**

> **10 秒答案**：锁的是当前 Service 实例（`this`）。Spring 默认单例，所以能挡住同一个应用的并发；如果把这个 Bean 配成多例（prototype），每个请求拿一个实例，各有各的锁，就完全失效了。
> **证据**：`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/ConfBillRuleServiceImpl.java:58-60`（`@Service`，默认单例）、`:193`（`public synchronized String getNumber(...)`）。

**卡片 2：`getBillNumber` 和 `getNumber` 都标了 `@Transactional(REQUIRES_NEW)`，内层调用会再开一个事务吗？**

> **10 秒答案**：不会。`getBillNumber` 里用 `this.getNumber(...)` 调用，属于「自调用」，不经过 Spring 代理，内层方法上的 `@Transactional` 不生效。真正生效的是外层 `getBillNumber` 上的 `REQUIRES_NEW`，它已经把编号生成包在独立事务里了。
> **证据**：`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/ConfBillRuleServiceImpl.java:362-364`（外层注解）、`:374`（`this.getNumber(...)` 自调用）、`:191-193`（内层注解）。

**卡片 3：为什么 ext 表查计数器要用 `(code, type, typeKey)` 三个条件，主表却只用 `code`？**

> **10 秒答案**：主表一条规则只有一个计数器，`code` 就能唯一定位；ext 表是按维度拆开的，同一规则下「不同合同类型 / 不同主体 / 不同父合同」各有一行，所以必须三个条件一起用。查出多于一行会直接抛异常，防止数据污染后乱发号。
> **证据**：`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/ConfBillRuleServiceImpl.java:203-205`（主表按 `code` 查）、`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/ConfBillRuleExtServiceImpl.java:94-97`（三元组查询）、`:72-74`（多行则抛异常）。

## 八、选型对比：为什么不选其他技术栈

### 8.1 发号方案：`synchronized` vs Redis 自增 vs 数据库序列 vs 号段

| 方案 | 能扛集群？ | 性能 | 备注 |
|---|---|---|---|
| `synchronized`（本项目当前） | ❌ **不能** | 单机好 | 集群会重号，**仅适合单机部署** |
| 数据库 `AUTO_INCREMENT` / 序列 | ✅ | 中（每次查库） | 简单可靠，但没法按周期重置 |
| **Redis `incr`（推荐）** | ✅ | **高**（内存操作、原子） | 主流方案，天然跨实例原子 |
| 号段模式（一次取 1000 个） | ✅ | 最高 | 实例重启会跳号 |

**结论**：本项目选 `synchronized` 是因为**当前是单机部署、且要支持按周期重置**（Redis/序列都不直接支持「跨年归零」）。这是一种**在特定约束下的选择**，但**集群化时是必须改的**。面试的核心是把「当前选择 + 它的边界 + 升级路径」讲清楚。

### 8.2 规则存储：JSON 数组 vs 关系表 vs 硬编码

| 方案 | 评价 |
|---|---|
| 硬编码 `if-else` | 改规则要改代码发版，❌ |
| 关系表（片段拆成多行） | 规范，但要 join 拼装、读写复杂；片段是**强顺序**的，关系表表达能力弱 |
| **JSON 数组（选用）** | 保存/读取都简单，天然表达**有序片段列表**；代价是数据库不能按片段查询（也不需要） |

**为什么 JSON 更合适**：编号规则的本质是「**一串有序片段**」，JSON 数组天然就是这个结构。片段数量少、只整体读写、不单独查询——完全命中「JSON 字符串」的适用场景（第 1 章 §2.2）。

### 8.3 为什么用 Redis 缓存预览编号，不在前端缓存？

前端缓存（比如存 localStorage）**拦不住「换浏览器/清缓存后重进」**，而且多个页面/多个 tab 之间不同步。缓存放服务端（Redis）才能做到**对所有客户端一致**，且服务端能控制过期策略。**凡是「状态需要跨客户端一致」的缓存，都应放服务端。**

### 8.4 为什么 `REQUIRES_NEW` 而不是普通事务传播？

普通传播（`REQUIRED`）下，编号生成会**加入外层事务**——外层回滚，编号的 `+1` 也没了。`REQUIRES_NEW` 挂起外层、独立提交，实现「编号不受业务成败影响」。**代价**是数据库连接占用时间变长（两个事务并行），但编号场景值得。
