# 第 10 章 · 进阶原理与性能优化

> **这一章解决什么问题**：前九章你一直在「用」Vue：改数据，页面自动变；写 `$nextTick`，就能拿到更新后的 DOM；套 `keep-alive`，页面就能缓存。这一章回答**为什么**，并把这些知识变成面试能讲、性能能优化的能力。
>
> **学完标准**：能画出「数据变化 → 视图更新」的完整链路；能说清 Vue 2 响应式的边界（哪些改动监听不到、为什么）；能解释虚拟 DOM、diff、key、`nextTick`、`keep-alive`、mixin、自定义指令、插件；能说出本项目具体做了哪些性能优化。
>
> 🎯 **选读说明**：如果你的目标是「会用、会改」，本章可以**先跳过**；它主要服务面试追问和性能优化。只有遇到 `Vue.set`、`$nextTick`、`keep-alive` 具体问题时，回来看对应小节即可。

> **版本提醒**：本章全部基于 **Vue 2.6.12**。Vue 3 用 `Proxy` 重写了响应式，数组下标、对象新增属性都能监听，`nextTick`、diff 细节也不同。面试时先问清对方问的是哪个版本，再答。

## 一、先看全景：一次数据变化，Vue 到底做了什么

```
你在代码里写：this.list = res.rows
        │
        ▼
① 赋值触发属性的 setter（Object.defineProperty 定义的）
        │
        ▼
② setter 里的 dep.notify() 通知所有订阅者
        │
        ▼
③ 每个 Watcher 被放进异步更新队列（去重）
        │
        ▼
④ 本轮同步代码执行完，nextTick 回调里统一 flush 队列
        │
        ▼
⑤ 渲染 Watcher 执行 update → 重新执行 render → 得到新 vnode
        │
        ▼
⑥ patch(oldVnode, newVnode) 对比差异，只更新变化的真实 DOM
        │
        ▼
⑦ 页面变了；$nextTick 的回调在 ④~⑥ 之后执行
```

这一章就是把 ①~⑦ 每一步拆开讲。

## 二、响应式原理：`Object.defineProperty` + Watcher

### 2.1 最核心的三行代码

Vue 2 把 `data` 里的每个属性都改造成「带 getter/setter 的属性」，本质就是：

```js
function defineReactive(obj, key, val) {
  const dep = new Dep()              // 依赖收集器

  Object.defineProperty(obj, key, {
    get() {
      dep.depend()                   // 谁读了我，就把谁记下来
      return val
    },
    set(newVal) {
      if (newVal === val) return
      val = newVal
      dep.notify()                   // 我变了，通知所有记录过的 Watcher
    }
  })
}
```

对应的三个角色：

| 角色 | 职责 | 一句话理解 |
|---|---|---|
| **Observer** | 递归遍历 data，把每个属性变成 getter/setter | 「给数据装上传感器」 |
| **Dep** | 依赖收集器，存一组 Watcher | 「记录谁用过这份数据」 |
| **Watcher** | 订阅者，数据变化时执行回调 | 「数据变了我要做什么」 |

### 2.2 谁在「读」数据？——渲染 Watcher

模板里写了：

```html
<span>{{ message }}</span>
```

编译后相当于渲染函数里读了 `this.message`。Vue 在执行渲染函数前，会把当前「渲染 Watcher」设为 `Dep.target`；读取 `message` 时触发 getter → `dep.depend()` → 把这个 Watcher 收进 `message` 的依赖列表。

之后 `this.message = '新值'` 触发 setter → `dep.notify()` → 渲染 Watcher 重新执行 → 视图更新。

**这就是「数据驱动」的底层**：你从没写过 `document.querySelector(...).innerText = ...`，Vue 在替你做。

### 2.3 三种 Watcher

| 类型 | 谁创建 | 特点 |
|---|---|---|
| 渲染 Watcher | 每个组件一个 | 数据变 → 重新 render |
| 用户 Watcher | `watch` 选项 | 数据变 → 执行你写的回调 |
| 计算 Watcher | `computed` 选项 | **懒执行**，依赖不变就不重算（第 3 章 §4） |

`computed` 的缓存就靠计算 Watcher 的 `dirty` 标记：依赖变化时把 `dirty` 置 true，下次读取才重新求值；依赖没变，直接返回上次结果。

### 2.4 三个「监听不到」的边界（面试必问）

Vue 2 的 `Object.defineProperty` 只能拦截**已经存在的属性**的读写，所以：

```js
// ① 给对象新增属性：监听不到
this.obj.newKey = 'x'

// ② 删除对象属性：监听不到
delete this.obj.key

// ③ 直接改数组下标 / 长度：监听不到
this.arr[0] = 'x'
this.arr.length = 0
```

为什么数组更特殊？因为 `Object.defineProperty` 可以定义数组下标，但 Vue 2 出于性能考虑**没有对每个下标做拦截**，而是改写了数组的原型方法。被改写的方法有 7 个：

```
push / pop / shift / unshift / splice / sort / reverse
```

调用这 7 个方法会触发更新；直接赋值下标不会。

**项目里的真实例子**：

| 场景 | 代码 | 为什么能更新 |
|---|---|---|
| 编号规则加一行 | `billRule/index.vue:282-286`：`data.push({ type: '1' })` | `push` 被改写 |
| 编号规则删一行 | `:287-289`：`data.splice(index, 1)` | `splice` 被改写 |
| 字典选项填充 | `utils/dict/Dict.js:76`：`dict.type[type].splice(0, MAX, ...dicts)` | `splice` 被改写 |
| 字典新增类型键 | `utils/dict/Dict.js:35-36`：`Vue.set(this.label, type, {})` | 新增属性，必须用 `Vue.set` |
| 字典 label 映射 | `Dict.js:78`：`Vue.set(dict.label[type], d.value, d.label)` | 给已有对象新增 key，必须用 `Vue.set` |

`Vue.set(obj, key, value)` / `this.$set(obj, key, value)` 做两件事：先给对象加属性，再手动触发这个对象 `__ob__.dep.notify()`。数组下标也能用：`this.$set(arr, index, val)` 内部会转成 `splice`。

**项目里用 `$set` 的典型场景**：动态表单设计器给 `element` 临时加 `defaultValue` 字段（`src/views/tool/build/DraggableItem.vue:33`）、给表格行对象补字段（`src/components/workflow/FormControls/InputTable/index.vue:104`）。这些对象都是运行时才构造的，初始没有该字段，所以必须用 `$set`。

### 2.5 让一个对象「不可响应」

```js
data() {
  return {
    bigStaticList: Object.freeze(hugeArray)
  }
}
```

`Object.freeze` 后属性不可配置，Vue 无法 `defineProperty`，会直接跳过。适用于**只读的大数据**（比如一份全省行政区划），可以省掉递归遍历的开销。项目里没有这种用法，属于通用优化手段。

> **Vue 3 对比（面试加分）**：Vue 3 用 `Proxy` 代理整个对象，新增/删除属性、数组下标都能拦截，不需要 `Vue.set`；但 `Proxy` 不兼容 IE，且需要支持 `Map/Set` 等集合类型。答题时先说「Vue 2 的限制是什么」，再说「Vue 3 怎么解决」。

## 三、虚拟 DOM 与 diff

### 3.1 从模板到真实 DOM

```
template 字符串
   │  vue-template-compiler 编译
   ▼
render 函数：render(h) { return h('div', ...) }
   │  执行
   ▼
VNode（虚拟节点，一个描述 DOM 的普通 JS 对象）
   │  patch
   ▼
真实 DOM
```

VNode 大致长这样：

```js
{
  tag: 'div',
  data: { class: 'app-container' },
  children: [ { tag: 'span', text: '你好' } ],
  key: undefined
}
```

虚拟 DOM 的价值**不是「比真实 DOM 快」**，而是：

1. 用 JS 对象描述界面，方便跨平台（web / 小程序 / native）；
2. 每次更新先在内存里对比，**只改真正变化的 DOM**；
3. 批量更新、合并操作，减少浏览器重排重绘。

### 3.2 patch 与 diff 的基本策略

新旧两棵 VNode 树对比时，Vue 不会做「树的最小编辑距离」那种高复杂度算法（O(n³)），而是用启发式策略，把复杂度降到 O(n)：

1. **同层比较**：只比较同一层级的节点，不跨层移动；
2. **类型不同直接替换**：`div` 变 `span`，整棵子树重建；
3. **类型相同则复用真实 DOM**，只更新属性/文本；
4. **子节点列表**用「双端比较 + key 映射」找出可复用的节点。

`sameVnode` 的核心判断是：`key` 相同、`tag` 相同、是否为注释、data 是否都有定义等。**key 是判断「是不是同一个节点」的第一依据。**

### 3.3 `key` 到底解决什么问题

```html
<!-- 反例：用 index 当 key -->
<li v-for="(item, index) in list" :key="index">{{ item.name }}</li>
```

假设列表从 `[A, B, C]` 变成 `[X, A, B, C]`（头部插入）：

- 用 `index` 当 key：第 0 个节点 key 从 0 变 0，Vue 认为「还是同一个节点」，于是把 A 的文本改成 X、B 的文本改成 A……**所有节点都更新一遍**，如果节点内部有输入框/组件状态，就会串位；
- 用唯一 id 当 key：Vue 发现新增了 key=X 的节点，其余 A/B/C 的 key 都没变，直接复用并移动位置。

**结论**：`key` 应该是**稳定且唯一**的业务标识（数据库 id），不要用 index。

项目里的正确与错误例子：

| 位置 | 写法 | 评价 |
|---|---|---|
| `position/index.vue:45` | `:key="dict.value"` | 字典 value 唯一，正确 |
| `billRule/index.vue:10` | `:key="item.id"` | 规则 id，正确 |
| `billRule/index.vue:50` | `:key="item.value"`，但数组项没有 `value` | 所有 key 都是 `undefined`，错误 |
| `billRule/index.vue:64` | `:key="dict.value"` | 正确 |

### 3.4 渲染函数与函数式组件：项目里的真实写法

绝大多数页面用模板。但模板最终也会编译成 render 函数，所以你可以直接用 JS 写渲染逻辑。项目里就有：

`src/layout/components/Sidebar/Item.vue:1-53`：

```js
export default {
  name: 'MenuItem',
  functional: true,       // 函数式组件：没有实例、没有 data、没有生命周期
  props: { icon: String, title: String, ... },
  render(h, context) {
    const { icon, title, showNum } = context.props
    const vnodes = []
    if (icon) vnodes.push(<svg-icon icon-class={icon} />)
    if (title) vnodes.push(<span slot="title">{title}</span>)
    return vnodes
  }
}
```

要点：

- `functional: true`：组件没有 `this`，只有 `context`（`props`/`children`/`data`/`listeners`），渲染开销更小；
- `h` 是创建 VNode 的函数：`h('div', { class: 'x' }, '文本')`；
- 这里用了 **JSX**（`<svg-icon />`），需要 Babel 插件支持；本项目已配置，所以能在 `.vue` 的 `<script>` 里写 JSX。

函数式组件适合**纯展示、无状态**的小组件。业务页面不要滥用，模板可读性更好。

### 3.5 异步组件与路由懒加载

```js
component: () => import('@/views/system/user')
```

这是**异步组件**写法：webpack 把每个 `import()` 拆成独立 chunk，用户访问到该路由时才下载对应 JS，首屏只加载必需代码。

项目路由表里几乎每一条都是这种写法（`src/router/index.js:40,46,51,56,61,66,71,76,...`）。配合 `vue.config.js:104-128` 的 `splitChunks`：

- `chunk-libs`：`node_modules` 里的第三方库；
- `chunk-elementUI`：把 Element UI 单独拆出来；
- `chunk-commons`：`src/components` 下被 3 个以上模块引用的公共组件；
- `runtimeChunk('single')`：把 webpack 运行时代码单独拆出，避免它变化导致业务 chunk 的 hash 全变。

这是本项目最实在的构建层优化。

## 四、异步更新队列与 `$nextTick`

### 4.1 为什么数据改了，DOM 不是立刻变

```js
this.message = 'A'
this.message = 'B'
this.message = 'C'
```

如果每次赋值都立刻更新 DOM，就要渲染三次。Vue 的做法是：把 Watcher 放进队列、**去重**，等本轮同步代码执行完，再统一更新一次。所以最终只渲染一次（`C`）。

这个「统一更新」的时机由 `nextTick` 调度，Vue 2.6 优先用 `Promise.then`（微任务），降级到 `MutationObserver`、`setImmediate`、`setTimeout`。

### 4.2 `$nextTick` 的语义

```js
this.visible = true
console.log(this.$refs.form)      // undefined！DOM 还没更新

this.$nextTick(() => {
  console.log(this.$refs.form)    // 表单组件，已渲染
})
```

**一句话**：`$nextTick(cb)` 把回调推迟到「本轮 DOM 更新完成之后」执行。不传回调时返回 Promise：

```js
await this.$nextTick()
this.$refs.form.clearValidate()
```

### 4.3 项目里的固定套路

打开/关闭弹窗、切换 Tab、动态渲染表格后要操作 DOM，几乎都要 `$nextTick`：

| 位置 | 代码 | 目的 |
|---|---|---|
| `position/index.vue:235-240` | `formVisible = true` 后 `$nextTick` 调 `Form.init` | 等子组件创建完，`$refs.Form` 才有值 |
| `position/Form.vue:148-149` | `$nextTick` 后 `resetFields()` | 等表单项渲染完，才能重置 |
| `position/Selector.vue:56-57` | `$nextTick` 后访问 `$refs.transfer` | 同上 |
| `tool/gen/index.vue:237-244` | `activated()` 中根据 `$route.query.t` 重新查询 | 配合 keep-alive 刷新缓存页 |

第 9 章已经拆过前三个，这里只需要把它们归到「异步更新队列」这个原理下。

### 4.4 常见误区

```js
// 误区：以为 nextTick 是「延时」
this.$nextTick(() => { ... })   // 不是 setTimeout(fn, 0) 的替代品
```

- `nextTick` 保证的是「DOM 更新后」，不是「任意异步操作完成后」；
- 如果回调里又改了数据，会触发新一轮更新；`nextTick` 的回调里再调 `$nextTick`，可以等到再下一轮；
- 多个 `$nextTick` 回调在同一轮会按注册顺序执行。

## 五、`keep-alive`：页面缓存与 `activated`

### 5.1 基本用法

```html
<keep-alive :include="cachedViews">
  <router-view :key="key" />
</keep-alive>
```

`keep-alive` 是 Vue 内置的**抽象组件**：它不渲染自己的 DOM，而是把内部组件的实例缓存起来。切走再切回时：

- 不重新 `created`/`mounted`；
- 触发 `activated`；
- 切走时触发 `deactivated`。

### 5.2 本项目的缓存链路

`src/layout/components/AppMain.vue:1-22`：

```html
<keep-alive :include="cachedViews">
  <router-view :key="key" />
</keep-alive>
```

```js
computed: {
  cachedViews() { return this.$store.state.tagsView.cachedViews },
  key() { return this.$route.path }
}
```

- `include` 接收**组件 name 数组**，只有名字匹配的组件才会被缓存；
- `key` 绑定路由 path，保证不同路由对应不同组件实例。

`cachedViews` 从哪来？用户打开一个页签时，TagsView 会 dispatch `addView`，最终执行 `src/store/modules/tagsView.js:15-20`：

```js
ADD_CACHED_VIEW: (state, view) => {
  if (state.cachedViews.includes(view.name)) return
  if (view.meta && !view.meta.noCache) {
    state.cachedViews.push(view.name)
  }
}
```

两个条件：

1. **组件必须有 `name`**（否则 `undefined` 被 push 进去，`include` 匹配不到任何组件）；
2. 路由 `meta.noCache` 不为 true。

### 5.3 项目里的真实对照

| 页面 | 是否有 `name` | 结果 |
|---|---|---|
| `conf/billRule/index.vue:180` | `name: 'BillRule'` | 可以被 keep-alive 缓存 |
| `tool/gen/index.vue` | 有 name，并使用 `activated`（`:237-244`） | 缓存生效，可用 `activated` 做「回来时刷新」 |
| `system/position/index.vue:158-160` | **没有 `name`** | `include` 匹配不到，缓存不生效；每次进入都重新 `created` |

> **坦白点**：这是项目里一个真实的「隐性 bug」。岗位页没有写 `name`，所以即使页签在，组件也不会被缓存。它不会报错，只是「看起来能用」。面试如果聊到 keep-alive，可以主动讲这个发现：**include 匹配的是组件 name，不是路由 name，也不是文件路径**。
>
> 另外，`router/index.js:18` 的注释也明确写了：「name 一定要填写，不然使用 `<keep-alive>` 时会出现各种问题」。

### 5.4 `activated` 的典型用途

页面被缓存后，第二次进入不会执行 `created`。如果需要在「回来时」刷新数据，就写在 `activated`：

```js
created() { this.getList() },        // 第一次进入
activated() {                        // 每次（包括第一次）激活
  const time = this.$route.query.t
  if (time != null && time !== this.uniqueId) {
    this.uniqueId = time
    this.getList()
  }
}
```

`tool/gen/index.vue:237-244` 用时间戳判断「是否需要刷新」，避免第一次进入重复请求。配合 `/redirect` 刷新套路（第 5 章 §7.3）：先 `delCachedView`，再跳 `/redirect`，回来时组件重新创建。

### 5.5 keep-alive 的代价

- 被缓存的组件**不会销毁**，`beforeDestroy` 不执行，定时器/事件监听要放在 `deactivated` 清理；
- 占内存；列表页缓存大量数据可能越来越卡；
- 需要「每次进来都最新」的页面，不适合缓存，或必须在 `activated` 里刷新。

## 六、mixins：逻辑复用

### 6.1 项目实例：`ResizeHandler`

`src/layout/index.vue:35`：

```js
import ResizeMixin from './mixin/ResizeHandler'
export default {
  name: 'Layout',
  mixins: [ResizeMixin]
}
```

`src/layout/mixin/ResizeHandler.js`：

```js
export default {
  watch: {
    $route(route) {
      if (this.device === 'mobile' && this.sidebar.opened) {
        store.dispatch('app/closeSideBar', { withoutAnimation: false })
      }
    }
  },
  beforeMount() {
    window.addEventListener('resize', this.$_resizeHandler)
  },
  beforeDestroy() {
    window.removeEventListener('resize', this.$_resizeHandler)
  },
  mounted() {
    if (this.$_isMobile()) { ... }
  },
  methods: {
    $_isMobile() { ... },
    $_resizeHandler() { ... }
  }
}
```

`Layout` 组件自己没写 `mounted`、`beforeDestroy`、`watch`，但通过 mixin 全部拿到了——这就是「把一段通用的组件选项抽出来复用」。

### 6.2 合并规则（面试常问）

组件与 mixin 有同名项时：

| 选项 | 合并策略 |
|---|---|
| `data` | 递归合并，**组件优先** |
| `methods` / `computed` | 同名时**组件覆盖 mixin** |
| 生命周期钩子 | **都执行**，mixin 的先执行 |
| `watch` | 合并成数组，都执行 |
| `props` | 合并，冲突时组件优先 |

### 6.3 mixin 的三个坑

1. **隐式依赖**：`Layout` 的模板用了 `this.device`、`this.sidebar`，它们来自 `mapState`，不是 mixin；但 mixin 里的 `watch` 又依赖它们。读代码时必须在两个文件间来回跳。
2. **命名冲突**：多个 mixin 都定义 `getList`，谁覆盖谁很难一眼看出。所以项目约定 mixin 私有方法用 `$_` 前缀（`ResizeHandler.js:28-29` 注释引用了 Vue 风格指南）。
3. **来源不明**：组件里突然多出一个 `activated`，你不知道是哪来的。大型项目更推荐 **Vue 3 的 Composition API** 或 **renderless 组件** 做逻辑复用；Vue 2 里也可以用 `scoped slot` 封装。

> 本项目除 `Layout`（`ResizeHandler`）和 `SidebarItem`（`FixiOSBug`）外，没有大规模使用 mixin。读项目时看到 `mixins: [...]`，去对应文件看它注入了什么即可。

### 7.2 `v-hasPermi` 逐行看

`src/directive/permission/hasPermi.js:43-100`：

```js
export default {
  inserted(el, binding, vnode) {
    const { value } = binding
    const all_permission = '*:*:*'
    const permissions = store.getters && store.getters.permissions

    if (value && value instanceof Array && value.length > 0) {
      const hasPermissions = permissions.some(permission => {
        return all_permission === permission || value.includes(permission)
      })
      if (!hasPermissions) {
        el.parentNode && el.parentNode.removeChild(el)
      }
    } else {
      throw new Error('请设置操作权限标签值')
    }
  }
}
```

要点：

- **钩子函数**：`bind`（绑定）、`inserted`（插入父节点）、`update`、`componentUpdated`、`unbind`。这里用 `inserted`，因为要操作父节点移除自己；
- **`binding.value`**：指令表达式的值，即 `['system:config:add']`；
- **`all_permission`**：超级管理员权限码 `*:*:*`，直接放行；
- **移除 DOM**：`el.parentNode.removeChild(el)`。注意这是**物理删除**，不是 `display:none`；如果权限数据在组件渲染后才异步到达，指令不会重新执行（`inserted` 只跑一次），所以权限通常要在登录后、进入页面前就准备好。

真实用法：`src/views/system/config/index.vue:75` 等页面：

```html
<el-button v-hasPermi="['system:config:add']" ...>新增</el-button>
```

### 7.3 插件：`Vue.use()` 做了什么

`src/main.js` 里：

```js
Vue.use(Element, { size: ... })
Vue.use(directive)        // 执行 directive/index.js 的 install
Vue.use(plugins)          // 执行 plugins/index.js 的 install
DictData.install()
```

`src/plugins/index.js:7-20`：

```js
export default {
  install(Vue) {
    Vue.prototype.$tab = tab
    Vue.prototype.$auth = auth
    Vue.prototype.$cache = cache
    Vue.prototype.$modal = modal
    Vue.prototype.$download = download
  }
}
```

插件就是一个**带 `install(Vue, options)` 方法的对象**（或函数）。`Vue.use` 会调用它，并把 Vue 传进去。常见用途：

- 挂原型方法：`this.$modal.msgSuccess(...)`；
- 注册全局组件；
- 注册指令；
- 注册 mixin（`DictData.install()` 就是这么做的，见 §9）。

**区分三个概念**：

| 机制 | 解决的问题 | 本项目例子 |
|---|---|---|
| 组件 | UI 复用 | `Pagination`、`JTable` |
| 指令 | 对 DOM 做底层操作 | `v-hasPermi`、`v-dialogDrag` |
| 插件 | 一次性给整个 Vue 装能力 | `$modal`、`$tab`、字典 mixin |

### 7.4 `$modal` 的实现

`src/plugins/modal.js` 只是对 Element 的 `Message`/`MessageBox`/`Notification`/`Loading` 做了一层封装：

```js
msgSuccess(content) { Message.success(content) },
confirm(content) { return MessageBox.confirm(content, '系统提示', {...}) },
loading(content) { loadingInstance = Loading.service({...}) },
closeLoading() { loadingInstance.close() }
```

好处是：业务代码不直接依赖 Element UI 的 API，未来换 UI 库只改这一个文件；同时可以统一处理错误文案（`normalizeUserMessage`）。

## 八、性能优化：本项目做了什么、还能做什么

### 8.1 项目已经做的

| 优化 | 位置 | 效果 |
|---|---|---|
| 路由懒加载 | `router/index.js` 大量 `() => import(...)` | 首屏不加载全部页面 |
| 第三方库拆包 | `vue.config.js:104-127` | 业务代码更新时，`chunk-libs`/`chunk-elementUI` 可继续用浏览器缓存 |
| runtime chunk 单独拆 | `vue.config.js:128` | 避免 runtime 变化影响业务 chunk hash |
| gzip 预压缩 | `vue.config.js:61-69` `CompressionPlugin` | Nginx 开启 `gzip_static` 后直接发 `.gz`，减少传输体积 |
| keep-alive 页签缓存 | `AppMain.vue:4` + `tagsView` | 切页签不重新渲染 |
| 后端分页 | 所有列表接口 `pageNum/pageSize` | 不一次性拉全量数据 |
| 表格 `doLayout` | `JTable/index.vue:65-88` | 修正隐藏容器里列宽错位（体验优化，不是性能） |
| 防重复提交 | `request.js:118-167` | 减少无效请求 |
| SVG 雪碧图 | `vue.config.js:76-91` | 图标合并成一个 sprite，减少请求数 |

### 8.2 常见可优化点（结合项目现状）

| 优化点 | 项目现状 | 建议 |
|---|---|---|
| `v-if` vs `v-show` | 弹窗类多用 `v-if`/`v-loading`；频繁切换的块可用 `v-show` | `v-if` 销毁重建，`v-show` 只切 `display` |
| `v-for` 与 `v-if` 同用 | 个别模板存在 | 先过滤数据再渲染，避免每次渲染都判断 |
| `key` 正确性 | `billRule:50` 用 `item.value`（不存在） | 用稳定唯一 id 或 index（纯展示且不重排时） |
| 大对象深度监听 | 项目里 `watch` 多为普通监听 | `deep: true` 会递归遍历，大对象慎用 |
| 长列表 | 合同/待办列表用分页 | 上千行可考虑虚拟滚动（项目未使用） |
| 首屏体积 | Element UI 全量引入（`main.js:195`） | 可按需引入，但改造量大；项目选择全量 |
| 图片/附件 | 走 OSS 或后端接口 | 加懒加载、缩略图 |
| 重复请求 | 搜索防抖未做 | 输入框可加 `debounce`；回车搜索已够用 |

### 8.3 一条重要的认知

> **不要为了优化而优化。** 先量：Chrome Network 看加载体积和时间，Performance 看渲染耗时，Vue Devtools 看组件重渲染。没有数据支撑的「优化」经常只是把代码写复杂。

项目里最影响体验的通常不是 Vue 本身，而是：超大页面组件（比如合同编辑页上千行）、一次性渲染几千条数据、频繁全量刷新。这些问题优先用「拆分组件 + 分页 + 按需加载」解决。

## 九、把机制串起来：`dicts` 是怎么工作的

第 9 章你见过：

```js
export default {
  dicts: ['PO_TYPE']
}
```

然后模板里就能用 `dict.type.PO_TYPE`。这不是 Vue 自带的能力，而是**插件 + 全局 mixin + `Vue.set` + 异步**的组合：

```js
// src/utils/dict/index.js:4-33
export default function(Vue, options) {
  mergeOptions(options)
  Vue.mixin({
    data() {
      if (this.$options.dicts == null) return {}
      const dict = new Dict()
      dict.owner = this
      return { dict }
    },
    created() {
      if (!(this.dict instanceof Dict)) return
      this.dict.init(this.$options.dicts).then(() => {
        this.$nextTick(() => {
          this.$emit('dictReady', this.dict)
          ...
        })
      })
    }
  })
}
```

逐层拆：

1. **插件**：`DictData.install()` → `Vue.use(DataDict, {...})`；
2. **全局 mixin**：每个组件 `data()` 都会执行这段逻辑；写了 `dicts` 的组件才注入 `this.dict`；
3. **异步加载**：`dict.init()` 请求 `/system/dict/data/type/{type}`；
4. **`Vue.set`**：往 `dict.type`/`dict.label` 里加新键（`Dict.js:35-36,78`）。因为 `dict.type` 初始是 `{}`，直接 `dict.type[type] = []` 监听不到，模板里的下拉不会更新；
5. **`splice`**：请求回来后往已有数组里填选项（`Dict.js:76`），保证数组本身是响应式的。

**这条链路几乎把本章所有知识点用了一遍**：响应式、`$set`、异步更新、`nextTick`、mixin、插件。能独立讲清它，说明你对 Vue 2 的理解已经到位。
