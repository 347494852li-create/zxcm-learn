# 第 7 章 · 工程化与请求层

> **这一章解决什么问题**：`.vue` 文件浏览器不认识，`import '@/api/...'` 里的 `@` 也不是浏览器语法。这些代码是怎么被加工成浏览器能跑的文件的？页面里的请求又是怎么发出去、怎么统一处理错误的？
>
> **学完标准**：能看懂 `package.json`、`vue.config.js`、`.env.*`、`src/main.js`、`src/utils/request.js`；能说清「`npm run dev` 之后发生了什么」；能自己新增一个 API 文件并在页面里调用；能解释 `@` 别名、`/dev-api` 代理、token 请求头、响应拦截器分别在哪一行生效。

---

## 一、为什么需要「工程化」

浏览器原生只认三样东西：HTML、CSS、JavaScript。但项目源码里有：

| 源码里的东西 | 浏览器能直接跑吗 | 需要谁处理 |
|---|---|---|
| `.vue` 单文件组件 | 不能 | `vue-loader` |
| `import x from '@/xxx'` | 不能（`@` 是别名） | webpack 的 `resolve.alias` |
| `import Vue from 'vue'`（不带路径） | 不能 | webpack 去 `node_modules` 找 |
| SCSS 嵌套语法 | 不能 | `sass-loader` |
| 可选链、模板字符串等新语法 | 老浏览器不能 | Babel |
| 几十个页面一次性加载 | 能，但慢 | 代码分割 / 懒加载 |

**工程化 = 用一套工具，把源码加工成浏览器能高效运行的静态文件。**

本项目用的工具链：

```
npm          管理依赖（node_modules）
Vue CLI 4    项目脚手架 + 开发服务器
webpack      打包：把模块拼成 bundle
Babel        把新语法转成兼容语法
vue-loader   把 .vue 拆成 JS/CSS
sass-loader  编译 SCSS
```

## 二、一个前端项目的三个阶段

> 这一章看起来东西很多（`package.json`、`vue.config.js`、`.env`、axios、代理、Nginx），其实只围绕三个阶段。先建立这张地图，后面每一节都知道自己在哪。

| 阶段 | 命令 | 谁在工作 | 产物 / 入口 | 对应章节 |
|---|---|---|---|---|
| **开发** | `npm run dev` | webpack-dev-server | `http://localhost:80` | §三~§九 |
| **构建** | `npm run build:prod` | webpack | `dist/` 静态文件 | §十 |
| **部署** | 运维 | Nginx | `https://你的域名` | §十 |

开发阶段的完整链路：

```
源码（.vue / .js / .scss）
  → webpack + loader 编译
  → devServer 提供页面 + 热更新
  → 浏览器打开 localhost
  → 页面里的 axios 发请求
  → devServer 代理到后端 8080
```

**建议阅读顺序**：

1. 先读 **§三~§七**：项目怎么启动、`main.js` 装配了什么、请求层怎么发请求；
2. 再读 **§八~§九**：`baseURL` 从哪来、`/dev-api` 被谁接住；
3. 最后读 **§十**：同一套代码怎么打包、怎么由 Nginx 接住；
4. **§十一** 把一条请求从头到尾串一遍；**§十二** 是排错手册。

> 如果现在只想知道「页面上的请求怎么走到后端」，可以直接跳到 §七 和 §九，再回头看 §八。

**`NODE_OPTIONS=--openssl-legacy-provider` 是什么？**

Vue CLI 4 / webpack 4 依赖旧版 OpenSSL 的加密算法。Node 17+ 默认改用 OpenSSL 3，会报 `ERR_OSSL_EVP_UNSUPPORTED`。这个参数让新 Node 兼容旧算法。

所以本项目在较新的 Node 上跑，必须带这个环境变量——脚本里已经写好了，直接 `npm run dev` 即可。

> 本机如果出现 `node` 找不到、安装回滚，多半是 PATH 里 Node 版本不对，属于环境问题，不是项目代码问题。

## 四、`npm run dev` 之后发生了什么

简化版流程：

```
npm run dev
  → node_modules/.bin/vue-cli-service serve
  → 读取 vue.config.js
  → webpack 从 src/main.js 开始分析依赖
      → 遇到 import './App.vue'，用 vue-loader 编译
      → 遇到 import '@/api/...'，用别名解析到 src/api/...
      → 遇到 import 'vue'，去 node_modules 找
      → 遇到 .scss，用 sass-loader 编译
  → 把结果放在内存里（开发环境不写 dist）
  → 启动 devServer，监听端口（默认 80）
  → 打开浏览器 http://localhost
```

### 4.1 热更新（HMR）

你改一个 `.vue` 文件保存，浏览器不刷新整页，只替换改动的模块——这叫**热更新（Hot Module Replacement）**。

学习时最有用的一点：**改模板、改样式、改方法，保存就能看到效果**，不用重启。

### 4.2 入口是 `src/main.js`

webpack 需要一个入口文件，Vue CLI 默认就是 `src/main.js`。从它开始，顺着 `import` 一层层把所有用到的文件拉进来，形成依赖图。

`src/main.js:46-48`：

```js
import App from "./App";
import store from "./store";
import router from "./router";
```

所以 `main.js` 是「总装配线」，`App.vue` 是根组件，`store`、`router` 是两大基础设施。

### 4.3 产物在 `dist/`

`npm run build:prod` 之后：

```
dist/
├── index.html
└── static/
    ├── js/
    │   ├── app.[hash].js
    │   ├── chunk-libs.[hash].js
    │   ├── chunk-elementUI.[hash].js
    │   └── 各个懒加载页面的 chunk
    ├── css/
    └── img/
```

`vue.config.js:23-25` 指定了 `outputDir: 'dist'`、`assetsDir: 'static'`。

`vue.config.js:104-127` 还把第三方库拆成 `chunk-libs`、`chunk-elementUI`、`chunk-commons`，避免一个文件过大。

### 5.3 别名 `@`

`vue.config.js:56-60`：

```js

  alias: {
    '@': resolve('src')
  }
}
```

`resolve` 在文件顶部定义（`vue.config.js:4-6`）：

```js
function resolve(dir) {
  return path.join(__dirname, dir)
}
```

所以 `@` = 项目根目录下的 `src`：

```js

```

没有这个别名，你得写 `../../utils/request`，文件一移动就全错。

## 七、请求层：从页面到后端

### 7.1 API 层：一个接口一个函数

`src/api/conf/billRule.js:13-19`：

```js
// 查询编号规则列表
export function listBillRule(query) {
  return request({
    url: "/conf/billRule/list",
    method: "get",
    params: query,
  });
}
```

同一文件里每个接口一个函数：

| 函数 | 方法 | URL | 参数位置 |
|---|---|---|---|
| `getBillCode` | GET | `/conf/billRule/getBillNumber/{code}` | `params` |
| `listBillRule` | GET | `/conf/billRule/list` | `params` |
| `getBillRule` | GET | `/conf/billRule/{id}` | 拼在 URL |
| `addBillRule` | POST | `/conf/billRule` | `data`（请求体） |
| `updateBillRule` | PUT | `/conf/billRule` | `data` |
| `delBillRule` | DELETE | `/conf/billRule/{id}` | 拼在 URL |

**为什么要单独一层 API 文件？**

1. 页面只关心「调哪个函数」，不关心 URL 和请求方法；
2. 接口地址变了，只改一处；
3. 函数名有语义（`listBillRule`），比在页面里写 `request({url: ...})` 好读。

### 7.2 axios 实例

### 7.3 请求拦截器

`src/utils/request.js:74-174`：

```js
service.interceptors.request.use(config => {
  const isToken = (config.headers || {}).isToken === false
  const isRepeatSubmit = (config.headers || {}).repeatSubmit === false

  if (getToken() && !isToken) {
    config.headers['token'] = 'Bearer ' + getToken()
  }

  if (config.method === 'get' && config.params) {
    let url = config.url + '?' + tansParams(config.params);
    url = url.slice(0, -1);
    config.params = {};
    config.url = url;
  }

  // 防重复提交 ...
  return config
})
```

> **`config` 是什么**：axios 为这一次请求生成的配置对象，包含 `url`、`method`、`baseURL`、`params`、`data`、`headers`、`timeout` 等。`config.headers` 是其中的请求头键值表——`config.headers['token'] = ...` 就是在发请求前加一个 `token` 头。拦截器最后必须 `return config`，否则请求不会发出。想看真实对象，在拦截器第一行加 `console.log(config)`。

三件事：

**① 自动带 token**

```js
config.headers['token'] = 'Bearer ' + getToken()
```

除了登录、注册等显式设置 `isToken: false` 的接口（`src/api/login.js:61-68`），所有请求都会带上：

```
token: Bearer xxxxx
```

这和后端配置的 `token-name: token` 对应（`application.yml:103`）。

token 本身存在 Cookie 里，键名 `Admin-Token`（`src/utils/auth.js:3-7`）。

**② GET 参数序列化**

`tansParams`（`src/utils/ruoyi.js:238-258`）把对象拼成查询字符串：

```js
{ pageNum: 1, pageSize: 10 }
  → "pageNum=1&pageSize=10&"
```

注意它**跳过 `null` 和 `undefined`**（`:243`）：

```js
if (value !== null && typeof value !== "undefined") {
```

这就是第 3 章说的「查询条件写 `undefined`，后端就收不到这个字段」。

**③ 防重复提交**

`src/utils/request.js:118-167`：对于 POST/PUT，把「URL + 请求体 + 时间」存进 sessionStorage。1 秒内出现完全相同的请求，直接拒绝：

```js
const message = '数据正在处理，请勿重复提交';
return Promise.reject(new Error(message))
```

### 7.4 响应拦截器

`src/utils/request.js:183-249`：

```js
service.interceptors.response.use(res => {
  const code = res.data.code || 200;
  const msg = normalizeUserMessage(errorCode[code] || res.data.msg || errorCode['default'])

  if (res.request.responseType === 'blob' || res.request.responseType === 'arraybuffer') {
    return res.data
  }

  if (code === 401) {
    // 弹窗提示重新登录 → LogOut → 整页跳转
  } else if (code === 500) {
    Message({ message: msg, type: 'error' })
    return Promise.reject(new Error(msg))
  } else if (code !== 200) {
    Notification.error({ title: msg })
    return Promise.reject('error')
  } else {
    return res.data
  }
})
```

关键点：

1. **业务状态码在 `res.data.code`**，不是 HTTP 状态码；
2. `code === 200` 时 `return res.data`，所以页面拿到的是**后端返回的 JSON 本身**：

```js
{
  code: 200,
  msg: '查询成功',
  rows: [...],
  total: 100
}
```

因此页面里写的是：

```js
this.billRuleList = response.rows
this.total = response.total
```

而不是 `response.data.rows`。这一点在第 1 章和附录 B 都强调过，因为非常容易错。

3. `401` 的处理（`:80-97`）：

```js
MessageBox.confirm('登录状态已过期...', '系统提示', { ... })
  .then(() => {
    store.dispatch('LogOut').then(() => {
      location.href = process.env.VUE_APP_CONTEXT_PATH + "index";
    })
  })
```

token 过期 → 弹窗 → 清登录状态 → 整页跳回首页（再由守卫踢到登录页）。

4. `blob`/`arraybuffer` 直接返回，用于文件下载。

### 7.5 错误处理

`src/utils/request.js:251-276`：

```js
error => {
  let { message } = error;
  if (message == "Network Error") {
    message = "后端接口连接异常";
  } else if (message.includes("timeout")) {
    message = "系统接口请求超时";
  } else if (message.includes("Request failed with status code")) {
    message = "系统接口" + message.substr(message.length - 3) + "异常";
  }
  Message({ message, type: 'error', duration: 5 * 1000 })
  return Promise.reject(error)
}
```

把 axios 的英文错误翻译成中文提示。所以页面 `.catch` 里通常不用再弹错误，只处理自己的状态（比如 `loading = false`）。

### 7.6 下载

`src/utils/request.js:283-325`：

```js
export function download(url, params, filename) {
  // 用 POST + blob 拿文件流
  return service.post(url, params, {
    transformRequest: [(params) => tansParams(params)],
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    responseType: 'blob',
    timeout: 3 * 60 * 1000,
  }).then(async (data) => {
    const isLogin = await blobValidate(data)
    if (isLogin) {
      saveAs(new Blob([data]), filename)
    } else {
      // 返回的其实是 JSON 错误信息
    }
  })
}
```

`responseType: 'blob'` 告诉 axios 按二进制处理。但如果后端返回的是错误 JSON，`blobValidate` 会识别出来并弹错误提示（`src/utils/ruoyi.js:261` 起）。

### 7.7 需要带 token 取图片

`src/utils/request.js:333-343`：


### 7.9 怎么读第三方库（以 axios 为例）

> 这一节不是讲 axios，而是讲「遇到一个不熟的库，怎么确认它到底怎么工作」。方法可以套到 Vue Router、Element UI、任何 npm 包上。

#### 7.9.1 第一步：先定版本

同一份 API，不同大版本行为可能完全不同。先确认三件事：

1. `package.json` 里写的版本（本项目 `axios: 0.24.0`，`package.json:41`）；
2. `node_modules/axios/package.json` 里实际安装的版本；
3. 官方文档对应的版本（不要拿 axios 1.x 的文档读 0.24 的代码）。

> 一个真实差异：axios 0.24 的 `config.headers` 是普通对象；1.x 改成了 `AxiosHeaders` 类，取值/设值方式变了。版本不对，结论就会错。

#### 7.9.2 第二步：看类型定义 / 函数签名

有 TypeScript 类型时，这是最快、最权威的入口：

```ts
// node_modules/axios/index.d.ts:62-72
export interface AxiosRequestConfig<D = any> {
  url?: string;
  method?: Method;
  baseURL?: string;
  headers?: AxiosRequestHeaders;
  params?: any;
  data?: D;
  timeout?: number;
}

// :164-175
export interface AxiosInterceptorManager<V> {
  use<T = V>(onFulfilled?: (value: V) => T | Promise<T>, ...): number;
}
interceptors: {
  request: AxiosInterceptorManager<AxiosRequestConfig>;
  response: AxiosInterceptorManager<AxiosResponse>;
};
```

读法：`request` 管的是 `AxiosRequestConfig`，`use` 的回调参数也是它 → 所以拦截器里的 `config` 类型就是 `AxiosRequestConfig`。

没有类型定义的库怎么办？看 JSDoc、README 的 API 段、函数参数默认值，或者直接在源码里搜这个函数名。

#### 7.9.3 第三步：顺调用链读源码

不要从第一行读到最后一行，只追「这个值从哪来、到哪去」：

```
axios(...) / service.request(...)
  → Axios.prototype.request
      config = mergeConfig(this.defaults, config)     Axios.js:39
      config.method = config.method.toLowerCase()     :41-48
      组装 requestInterceptorChain                      :78-84
      dispatchRequest(newConfig)                        :108
  → dispatchRequest(config)                             dispatchRequest.js:28
      config.headers = config.headers || {}             :32
      拍平 common / get / post 分组头                    :43-47
      adapter(config)  ← 真正发请求                     :56
  → adapter（xhr / http）
```

三个实用技巧：

- **搜符号**：在 `node_modules` 里搜 `dispatchRequest`、`interceptors.request` 这类名字，比从头读快；
- **从报错栈入手**：报错信息里会带文件行号，顺着栈往回看；
- **读测试**：`test/specs/` 里的用例通常把「预期行为」写得比文档还清楚。

#### 7.9.4 第四步：回项目看用法 + 运行时验证

源码告诉你「库怎么实现」，项目代码告诉你「我们怎么用」：

```js
// src/utils/request.js
config.headers['token'] = ...
config.method === 'get'
config.url + '?' + tansParams(config.params)
return config
```

最后一定要跑一次：

```js
console.log('请求配置：', config)
```

或者 F12 → Network 看实际发出的请求头/参数。**打印结果和类型定义对得上，结论才算成立。**

#### 7.9.5 三个判断原则

| 原则 | 意思 |
|---|---|
| **以实际安装的代码为准** | 博客、记忆、旧文档都可能过时；`node_modules` 里那份才是运行时真正执行的 |
| **看「谁创建、谁消费」** | 不要只看变量名；找到它被谁赋值、被谁读取，语义才确定 |
| **结论必须能验证** | 能打印、能打断点、能看 Network，才算「确认」，否则只是「猜测」 |

#### 7.9.6 一张 checklist

- [ ] 版本对上了（`package.json` + `node_modules` + 文档）
- [ ] 找到类型定义或函数签名
- [ ] 找到这个值的「创建点」
- [ ] 找到它的「消费点」（谁用它发请求/渲染）

## 八、环境变量 `.env`：`/dev-api` 从哪来

### 8.1 两个文件

`.env.development:8`：

```
VUE_APP_BASE_API = '/dev-api'
```

`.env.production:17`：

```
VUE_APP_BASE_API = '/prod-api'
```

`npm run dev` 默认加载 `.env.development`；`npm run build:prod` 默认加载 `.env.production`；`build:stage` 加载 `.env.staging`（脚本 `package.json:10`）。

### 8.2 只有 `VUE_APP_` 开头的变量会进前端代码

Vue CLI 的规则：只有以 `VUE_APP_` 开头的变量，才会被注入到客户端代码里。

- `VUE_APP_BASE_API` ✅
- `ENV` ❌（没有前缀，只在 Node 配置里可用，不会出现在浏览器代码里）

这是为了防止把服务器密钥之类的变量误打进前端包。

### 8.3 编译时替换

浏览器代码里写：

```js
baseURL: process.env.VUE_APP_BASE_API
```

webpack 在**打包时**就把 `process.env.VUE_APP_BASE_API` 替换成字符串 `'/dev-api'`。浏览器里最终执行的是：

```js
baseURL: '/dev-api'
```

生产构建同理，只是换成 `/prod-api`——三种产物的对照见 §8.6。

所以：

1. 它**不是运行时读取**，改 `.env` 后必须**重启 devServer** 才生效；
2. 不能写 `process.env['VUE_APP_' + name]` 这种动态拼接，webpack 静态替换不了。

### 8.4 `vue.config.js` 里读到的是另一回事

`vue.config.js:37`：

```js
[process.env.VUE_APP_BASE_API]: { ... }
```

这行运行在 **Node 进程**里（构建配置阶段），读取的是真实的系统环境变量 + `.env` 文件加载后的值。所以这里的 `process.env` 和浏览器里的不是同一个东西，但值一致。

### 8.5 其它常用变量

| 变量 | 位置 | 用途 |
|---|---|---|
| `VUE_APP_TITLE` | `.env.development:2` | 网页标题（`vue.config.js:10`） |
| `VUE_APP_CONTEXT_PATH` | `.env.development:11` | 应用访问路径（`publicPath`、退出登录跳转） |
| `VUE_APP_MONITRO_ADMIN` | `.env.development:14` | 监控后台地址 |
| `VUE_APP_XXL_JOB_ADMIN` | `.env.development:17` | 定时任务控制台地址 |

### 8.6 一个源码，三种产物

`process.env.VUE_APP_BASE_API` 在打包时被替换成对应 `.env` 文件里的值，所以：

```js
// 源码（只有这一份）
const service = axios.create({
  baseURL: process.env.VUE_APP_BASE_API
})
```

```js
// npm run dev 打包出来的代码
baseURL: '/dev-api'
```

```js
// npm run build:prod 打包出来的代码
baseURL: '/prod-api'
```

源码没变，**变的是打包产物**。

**哪个命令读哪个文件**：

| 命令 | mode | 读的文件 | `VUE_APP_BASE_API` |
|---|---|---|---|
| `npm run dev` | development | `.env.development` | `/dev-api` |
| `npm run build:prod` | production | `.env.production` | `/prod-api` |
| `npm run build:stage` | staging | `.env.staging` | `/stage-api` |

`.env` 文件里只有 `VUE_APP_` 开头的变量会被打进前端代码；其他变量只在 Node 侧可见。

**两边的「约定」必须对上**：

- 开发：`baseURL` 打包成 `/dev-api` → devServer 的 proxy 键也是 `/dev-api`；
- 生产：`baseURL` 打包成 `/prod-api` → Nginx 的 `location /prod-api/` 接住。

前端只负责「发一个相对路径」，**谁来接、转到哪，由环境决定**。

**怎么验证**：

1. 开发环境：F12 Network 看请求是 `/dev-api/...`；
2. 生产构建后：在 `dist/js/*.js` 里搜 `/prod-api`，能搜到；搜 `/dev-api` 应该搜不到。

## 九、开发环境：请求怎么到达后端（devServer 代理）

前端跑在 `http://localhost`（80），后端跑在 `http://localhost:8080`。浏览器直接请求 8080 会跨域——这一节讲**开发环境**怎么用 devServer 代理绕过去；生产环境由 Nginx 做同样的事，见 §十。

### 9.1 先理解「源」和跨域

浏览器判断两个地址是不是同一个源，看三样：**协议 + 域名 + 端口**，三者完全一样才算同源。

| 地址 | 协议 | 域名 | 端口 |
|---|---|---|---|
| 前端 `http://localhost` | http | localhost | **80**（默认） |
| 后端 `http://localhost:8080` | http | localhost | **8080** |

端口不同 → **不同源**。浏览器对跨源请求的规则是：请求可以发出去，但响应默认**不让 JS 读**，除非后端返回 `Access-Control-Allow-Origin` 之类的 CORS 头。

**「不让 JS 读」到底是什么意思？**

不是「请求没发出去」，而是：

- 请求可能已经到达后端，后端也可能已经处理并返回了；
- 但浏览器在把响应交给页面 JS 之前，会检查响应头里有没有允许当前源的 CORS 头；
- 没有 → 浏览器把响应「扣下」，`fetch`/`axios` 直接进 `catch`，你拿不到 `status`、拿不到 `response.data`；
- F12 Network 里**能看到**这条请求和响应（浏览器自己能看到），但页面 JS 读不到。

控制台大概长这样：

```
Access to XMLHttpRequest at 'http://localhost:8080/conf/...'
from origin 'http://localhost' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

**两种跨源请求的区别**：

| 类型 | 例子 | 浏览器行为 |
|---|---|---|
| 简单请求 | GET/POST + 普通 Content-Type | 请求先发出去，响应回来再检查；不通过就扣下响应 |
| 非简单请求 | `Content-Type: application/json`、PUT/DELETE、自定义头 | 先发一个 `OPTIONS` 预检；预检不通过，**真正的请求根本不会发** |

> 这也是为什么「跨域」不等于「请求没到后端」：简单请求可能已经改了数据，只是 JS 读不到结果。安全上要注意 CSRF，不能只靠前端拦。

**CORS 头由后端返回**，常见几个：

```
Access-Control-Allow-Origin: http://localhost
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, token
Access-Control-Allow-Credentials: true
```

**代理为什么能绕过**：浏览器只访问 `localhost`（同源），根本不触发 CORS 检查；转发是 devServer 这个 Node 进程做的，Node 不受同源策略约束。

所以前端代码如果直接写 `http://localhost:8080/conf/...`，就会遇到跨域问题。

### 9.2 代理做了什么

`npm run dev` 启动的 devServer 是一个 **Node 进程**：它既负责把前端页面编译好给你访问，也能顺便做转发。

```
浏览器（页面在 http://localhost:80）
   │  GET /dev-api/conf/signingSubject/list
   ▼
devServer（Node 进程，就在 localhost:80）
   │  路径以 /dev-api 开头 → 命中代理规则
   │  去掉 /dev-api，转发到 http://localhost:8080
   ▼
后端（localhost:8080）
   │  收到 GET /conf/signingSubject/list
   ▼
返回 JSON → devServer 原样返回 → 浏览器
```

关键点：**浏览器从头到尾只访问了 `localhost`**，同源，没有跨域问题；真正访问 8080 的是 devServer 这个 Node 进程，**服务端之间的请求不受浏览器同源策略限制**。

### 9.3 配置逐行读

`vue.config.js:31-46`：

```js
devServer: {
  host: '0.0.0.0',
  port: port,               // port = 80（vue.config.js:12）
  proxy: {
    [process.env.VUE_APP_BASE_API]: {   // 键：'/dev-api'
      target: `http://localhost:8080`,  // 转发到哪
      changeOrigin: true,
      pathRewrite: {
        ['^' + process.env.VUE_APP_BASE_API]: ''   // 去掉开头的 /dev-api
      }
    }
  }
}
```

**① 键为什么是 `[process.env.VUE_APP_BASE_API]`**

`process.env.VUE_APP_BASE_API` 在 `.env.development:8` 里是 `/dev-api`；外面加 `[]` 是**计算属性名**（第 0 章 §5.6 的对象语法）：先把表达式求值，拿结果当键。所以这一项实际是 `'/dev-api': { ... }`，含义是「所有以 `/dev-api` 开头的请求都走这条代理」。

axios 那边也是同一个值（`src/utils/request.js:61` 的 `baseURL`），所以页面写 `/conf/...`，浏览器实际发的是 `http://localhost/dev-api/conf/...`。

**② `target`**

转发目标：本机后端 `http://localhost:8080`。

**③ `changeOrigin: true`**

把请求头里的 `Host` 改成目标地址的 Host，很多后端/虚拟主机需要这个。

**④ `pathRewrite`**

```js
pathRewrite: {
  ['^' + process.env.VUE_APP_BASE_API]: ''
}
```

把路径开头的 `/dev-api` 删掉：

```
/dev-api/conf/billRule/list  →  /conf/billRule/list
```

正则拆开：`^` 只匹配开头；`/dev-api` 是要删的字符串；替换成 `''` 就是删掉。**必须删**，因为后端 `@RequestMapping` 里没有 `/dev-api` 这个前缀；不删就会 404。

> 完整的一次请求（URL 怎么拼、代理怎么匹配、后端怎么收到）在
> [附录 B · 零基础精读：一次请求的完整流程](../重塑版/前端重塑版/附录B-零基础精读：一次请求的完整流程.md)
> 里逐行拆过，这里不重复。

### 9.4 一个容易误解的点

项目后端本身配置了宽松的全局 CORS（`ResourcesConfig.java:50-67`，允许所有来源）。所以**直接请求 8080 也可能成功**——代理不是「唯一能解决跨域的办法」。它的主要价值是：

1. 统一 `/dev-api` 前缀，前端代码不用写死后端地址；
2. 开发/生产用不同前缀，切换环境不改代码；
3. 生产环境由 Nginx 做同样的转发，前后端部署方式一致；
4. 浏览器地址栏里看不到后端真实端口；
5. 同源请求对 Cookie、凭证更友好。

### 9.5 怎么验证

F12 → Network（浏览器视角）：

```
Request URL: http://localhost/dev-api/conf/signingSubject/list?pageNum=1&pageSize=10
```

后端控制台/日志（服务器视角）：

```
GET /conf/signingSubject/list
```

同一个请求，两个视角的路径不一样——差的正是被 devServer 剥掉的 `/dev-api`。

再做两个实验：

1. **停掉后端**，再点查询：Network 里会出现代理转发失败（504 / ECONNREFUSED），说明请求确实经过了 devServer；
2. **把 `pathRewrite` 注释掉**，重启 `npm run dev`，再点查询：会 404，因为后端收到了 `/dev-api/conf/...`。

> 改 `vue.config.js` 必须**重启 dev server**，热更新不会让代理配置生效。

### 9.6 常见坑

| 现象 | 原因 |
|---|---|
| 404，后端日志里路径带 `/dev-api` | `pathRewrite` 没写或写错 |
| 404，后端完全没日志 | `baseURL` 和代理的键对不上（比如一个 `/dev-api` 一个 `/api`） |
| 504 / ECONNREFUSED | 后端没启动，或 `target` 地址/端口错 |
| 改了配置不生效 | 没重启 `npm run dev` |
| 生产环境 404 | Nginx 没配 `/prod-api` 转发（代理只在开发环境有效） |

### 9.7 为什么不直接访问 8080？

**可以直连**——本项目后端本身开了全局 CORS，前端把 `baseURL` 写成 `http://localhost:8080` 也能跑。但直连有几个代价：

| 直连 8080 的问题           | 具体表现                                                                |
| --------------------- | ------------------------------------------------------------------- |
| **地址写死在前端**           | 换环境（开发/测试/生产、换机器、换端口）就要改代码或加环境变量                                    |
| **每个环境都要配 CORS**      | 后端要允许前端来源、方法、自定义头；带 Cookie 时 `Allow-Origin` 还不能写 `*`                |
| **生产要暴露后端端口**         | 如果生产直连，就得把后端的 8080 对外开放；正常部署只开放 Nginx 的 443，后端留在内网             |
| **HTTPS 页面调 HTTP 后端** | 浏览器会按「混合内容」拦掉，生产必须走 HTTPS，代理可以统一                                    |
| **前端路由和后端路径可能撞车**     | 页面路由 `/contract/draft` 和接口 `/contract/...` 容易混；加个 `/dev-api` 前缀就分开了 |

**别误解：devServer 自己也监听 80**

浏览器访问 `http://localhost` 时，连的就是 devServer（Node 进程）；它当然有端口，而且是对外的入口。所谓「不暴露后端端口」，指的是**浏览器/公网不能直接连到 8080**，不是后端没有端口。

开发环境：

```
浏览器 → devServer:80（入口，对外）
             ↓ 转发
         后端:8080（在 devServer 后面，浏览器不需要能访问）
```

生产环境：

```
浏览器 → Nginx:443（入口，对外）
             ↓ 转发
         后端:8080（内网/容器网络，不对外）
```

| 环境 | 浏览器能访问的 | 谁去访问后端 8080 |
|---|---|---|
| 开发 | devServer:80 | devServer（Node 进程） |
| 生产 | Nginx:443 | Nginx |

**为什么不让浏览器直接连 8080**：

1. **攻击面**：后端所有接口都会暴露，包括 actuator、druid、内部管理接口；
2. **TLS / 限流 / WAF**：这些通常由 Nginx 统一做，后端只处理业务；
3. **网络拓扑**：后端在内网/容器里，本来就不该有公网入口；
4. **同源**：浏览器只对一个入口说话，不用配 CORS。

Docker 部署很直观：

```bash
# 只发布 Nginx 的端口
docker run -p 80:80 -p 443:443 nginx

# 后端容器不写 -p，只能通过内部网络被 Nginx 访问
docker run backend
```

一句话：**devServer 和 Nginx 是同一个角色**——对外入口 + 反向代理。开发时由 Node 担任，生产时由 Nginx 担任；后端 8080 始终躲在它们后面。

**代理/前缀方案把「地址」变成了「约定」**：

- 前端只写 `/dev-api`，不关心后端在哪；
- 开发环境由 devServer 转发；
- 生产环境由 Nginx 转发；
- 前端代码一行不改，只换环境变量。

**「加了又减」不是白做**：

- **加前缀**：前端在说「这个请求走 API 通道」；
- **减前缀**：代理在说「我知道真正的后端路径是什么」。

这是反向代理的标准做法。生产环境的 Nginx 也在做同样的事（`/prod-api` 加进去、`proxy_pass` 时去掉），只是换了一个执行者。

**什么时候可以直接访问**：本地小 demo、没有 Cookie/凭证、CORS 已配好、只有一套环境——直连完全没问题。团队项目、多环境部署、生产要收口，代理更稳。

## 十、生产环境：打包、dist 与 Nginx

### 10.1 打包

```bash
npm run build:prod
```

产物在 `dist/`。部署时把 `dist/` 放到 Nginx 的静态目录。

### 10.2 生产环境需要哪些配置

| 需求 | Nginx 配置思路 |
|---|---|
| 前端路由 history 模式 | `try_files $uri $uri/ /index.html;`（第 5 章 §6.2） |
| 接口转发 | `location /prod-api/ { proxy_pass http://后端地址/; }` |
| gzip 静态文件 | 开启 `gzip_static on;`，配合 `vue.config.js:61-69` 生成的 `.gz` |

前端代码里的 `/prod-api`（`.env.production:17`）和生产 Nginx 的转发前缀必须一致。

> 本项目仓库里没有 Nginx 配置文件（部署配置不在 `zxcm-ui` 内），以上是通用部署知识，不要当成项目里已有的文件。

### 10.3 为什么开发和生产都用「前缀 + 转发」

开发：`/dev-api` → devServer 代理 → 8080
生产：`/prod-api` → Nginx 转发 → 后端

好处：

- 前端代码永远只写相对路径，不写后端 IP；
- 换环境只改 `.env` 和部署配置；
- 浏览器始终同源，不依赖后端 CORS。

### 10.4 `/dev-api` 到底是什么

它**不是后端地址**，只是一个「暗号前缀」：前端代码只认 `/dev-api`；开发环境由 devServer 认出并转发；生产环境换成 `/prod-api`，由 Nginx 认出并转发。

`.env.production`：

```
VUE_APP_BASE_API = '/prod-api'
```

Nginx 大致这么配：

```nginx
location /prod-api/ {
    proxy_pass http://后端地址/;
}
```

`proxy_pass` 末尾的 `/` 作用类似 `pathRewrite`：把 `/prod-api/` 去掉再转发。所以前端代码一行都不用改，只是打包时环境变量被替换了。

### 10.5 生产环境：Nginx 是怎么「接住」的？

不是 Nginx 自动识别，而是**配置里写了匹配规则**。生产环境的 Nginx 通常长这样：

```nginx
server {
    listen 443 ssl;
    server_name contract.example.com;

    root /usr/share/nginx/html;      # 前端 dist 放这里
    index index.html;

    # ① API 请求：/prod-api/ 开头 → 转发给后端，并去掉前缀
    location /prod-api/ {
        proxy_pass http://127.0.0.1:8080/;   # 末尾的 / 很关键
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # ② 其它路径：交给前端（history 路由的兜底）
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

**它为什么能接住**：

1. 浏览器访问的是 `https://contract.example.com/prod-api/conf/...`；
2. Nginx 监听 443，拿到路径 `/prod-api/conf/...`；
3. Nginx 按 `location` 做**前缀匹配**，`/prod-api/` 命中第 ① 条；
4. `proxy_pass http://127.0.0.1:8080/;` 把请求转给后端；
5. 末尾的 `/` 会把 `/prod-api/` 替换成 `/`，所以后端收到的是 `/conf/...`。

**末尾 `/` 的差别**（最容易踩）：

```nginx
# 有斜杠：/prod-api/conf/x → http://127.0.0.1:8080/conf/x
proxy_pass http://127.0.0.1:8080/;

# 没斜杠：/prod-api/conf/x → http://127.0.0.1:8080/prod-api/conf/x（通常 404）
proxy_pass http://127.0.0.1:8080;
```

**如果没有 `location /prod-api/` 会怎样**：

请求会落到 `location /`，被 `try_files` 兜成 `index.html`。前端拿到一段 HTML，却按 JSON 去解析——报错通常长这样：

```
Unexpected token '<', "<!DOCTYPE "... is not valid JSON
```

或者直接 404。**看到这个报错，先检查 Nginx 的前缀有没有配对。**

**为什么「改环境变量」和「改 Nginx」必须一起做**：

- `.env.production` 决定前端请求哪个前缀（`/prod-api`）；
- Nginx 的 `location` 决定谁来接这个前缀；
- 两边是同一个约定，改了一边不改另一边，就对不上。

### 10.6 浏览器是怎么找到 Nginx 的？

「浏览器 → Nginx:443」不是一句话，中间有四步：

```
① DNS：contract.example.com → 服务器公网 IP
② TCP：浏览器连 IP 的 443 端口（HTTPS 默认端口）
③ TLS：握手、校验证书（SNI 用来选对应的 server 块）
④ HTTP：在 TLS 连接里发请求，Nginx 按 location 转发
```

**① DNS 解析**

浏览器先问 DNS：`contract.example.com` 对应哪个 IP？域名服务商那里配一条 A 记录（或 CNAME）指向服务器公网 IP。可以用命令验证：

```bash
nslookup contract.example.com
```

**② 连 443**

HTTPS 的默认端口是 443（HTTP 是 80）。所以地址栏写 `https://contract.example.com`，浏览器实际连的是 `IP:443`。如果 Nginx 监听的是 8443，地址就必须写成 `https://contract.example.com:8443`。

**③ TLS 握手 + 证书**

浏览器和 Nginx 建立加密连接，并校验证书：

- 证书域名要和访问的域名匹配；
- 证书链要可信（CA 签发）；
- 否则浏览器会弹「不安全」警告。

Nginx 这边对应这段配置：

```nginx
server {
    listen 443 ssl;
    server_name contract.example.com;

    ssl_certificate     /etc/nginx/certs/contract.crt;
    ssl_certificate_key /etc/nginx/certs/contract.key;

    location /prod-api/ {
        proxy_pass http://127.0.0.1:8080/;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

- `listen 443 ssl`：在这个端口上监听并启用 TLS；
- `server_name`：匹配哪个域名（多个域名时靠它区分）；
- `ssl_certificate` / `ssl_certificate_key`：证书和私钥。

**④ 请求进来之后**

TLS 连接建立好，浏览器在连接里发：

```
GET /prod-api/conf/signingSubject/list HTTP/1.1
Host: contract.example.com
```

Nginx 拿到路径 `/prod-api/...`，按 `location` 匹配，转发给后端。

**谁负责哪一段**：

| 环节 | 谁负责 | 怎么配 |
|---|---|---|
| 域名 → IP | 域名服务商 | A 记录 / CNAME |
| 端口放行 | 防火墙 / 云安全组 | 放行 443（80 通常也放行，用于跳转） |
| 证书 | 运维 / CA | Nginx 的 `ssl_certificate` |
| 监听 443 | Nginx | `listen 443 ssl` |
| 按路径转发 | Nginx | `location` + `proxy_pass` |

**和开发环境对照**：

| | 开发 | 生产 |
|---|---|---|
| 域名/IP | `localhost` → `127.0.0.1`（不用 DNS） | 域名 → 公网 IP（DNS） |
| 端口 | devServer 监听 80 | Nginx 监听 443 |
| 加密 | 一般没有（http） | TLS 证书 |
| 入口 | devServer | Nginx |

> 如果前面还有 CDN / 云负载均衡，DNS 会先指向 CDN，再由 CDN 回源到 Nginx；对浏览器来说，仍然是「连一个 443 端口」。

**怎么验证**：

```bash
nslookup contract.example.com          # 域名解析到哪个 IP
curl -v https://contract.example.com/prod-api/conf/signingSubject/list
ss -lntp | grep 443                    # 服务器上谁在监听 443
nginx -T                               # 打印当前生效的 Nginx 配置
```

## 十二、常见工程问题

### 12.1 改了 `.env` 没生效

环境变量是**编译时替换**的，必须重启 devServer。

### 12.2 `@` 别名在编辑器里报红

编辑器不认识 webpack 别名。项目能正常编译，只是 IDE 提示问题。可以在项目根加 `jsconfig.json` 配置 `paths`，但本项目没有加，不影响运行。

### 12.3 Node 版本导致启动失败

- 报 `ERR_OSSL_EVP_UNSUPPORTED`：脚本里的 `--openssl-legacy-provider` 就是解决它的；
- 报找不到 `node` / 安装回滚：检查 PATH 里的 Node 路径和版本（本机环境问题）。

### 12.4 端口 80 被占用

`vue.config.js:12` 默认端口是 80。被占用时改这一行，或者通过 `process.env.port` 覆盖（这一行会优先读它）。

### 12.5 请求 404

按顺序排查：

1. Network 里请求的 URL 对不对（有没有 `/dev-api`）；
2. `vue.config.js` 的代理前缀和后端地址对不对；
3. 后端 Controller 的 `@RequestMapping` 路径对不对（`ConfBillRuleController.java:66` 是 `/conf/billRule`）；
4. 后端服务是否启动在 8080。

### 12.6 请求 401

- token 没带上：看请求头有没有 `token: Bearer ...`；
- token 过期：响应拦截器会弹重新登录；
- 登录接口本身不该带 token：检查 `isToken: false`。

### 12.7 生产环境刷新 404

history 模式的 Nginx fallback 没配（§10.2）。

### 12.8 打包后白屏

常见原因：

1. `publicPath` 和实际部署路径不一致；
2. 静态资源 404（Network 里看 `static/js/...`）；
3. 路由 base 配置不对。
