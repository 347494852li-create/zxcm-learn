## 一、先分清「谁设计的」，再看「怎么进库的」

打开 Navicat 会看到 77 张表。新手第一反应是「这么多表怎么记得住」——**先别背**。先站在**学习者**的位置问三个问题：**这张表谁设计的？为什么需要它？我什么时候会真正用到它？** 按这个标准，77 张表只有 **三个来源**：

| 来源 | 表数 | 谁设计 / 谁建 | 为什么需要它（它解决什么） | 你第一次真正用到 |
|---|---|---|---|---|
| **① 框架系统表** | **26** | **RuoYi 框架原作者**设计；**你**跑 `01` 脚本导进库 | 「登录 → 认出你是谁 → 发菜单 → 记日志」。**凡是 RuoYi 后台都有这几十张，跟合同业务无关** | **M0 登录那一刻**（没 `sys_user` 谁都进不去） |
| **② 业务表** | **27** | **肇新合同系统原作者**设计；**你**跑 `03`/`04` 脚本导进库 | 合同「草拟 → 审批 → 用印 → 归档」全生命周期的数据 | **M1 开始时**（T2 第一张业务表） |
| **③ Activiti 引擎表** | **24** | **引擎启动时自己建**（一行代码不用写） | 审批流程要跑，引擎得有自己的运行时 / 历史表 | **M2 提交审批时**（M0 启动后端它就自动建好了） |

**26 + 2 + 25 + 24 = 77 张。**

> 💡 **三种来源，对你的要求完全不同——这才是你该记住的**：
> - ① **框架系统表** → 你**会用**就行（不用背，用到时回来查本文 §三）。
> - ② **业务表** → 你**要讲得出「为什么这么设计」**（答辩主要考这个，本文 §四 逐张讲）。
> - ③ **引擎表** → 你**知道它干嘛**就行（本文 §四·组⑧ 只给规律，细节归 [M2](M2-审批流与事件状态机（总览）.md)）。
>
> ⚠️ **还有第四种——「你自己设计的表」**：答案册里**根本没有** M4 的 `contract_borrow`（合同借阅），这张得你自己加。**作品集里你能说「这是我设计的表」的，就是这一类**（也是唯一一类）。

**再补一层「工程视角」**（知道即可，不影响你把业务学明白）：这 77 张不是一次建出来的，而是分**四批**、用不同方式进你库里的——

| 批次 | 表数 | 谁让它进库的 | 什么时候 | 有哪些表 |
|---|---|---|---|---|
| ① **框架底座表** | **26** | 你跑 `01-zxcm-learn-base.sql` | **M0 · T4-T5** 建库导入时 | `sys_*`（24 张）+ `gen_*`（2 张） |
| ② **非业务但必需** | **2** | 你跑 `03-missing-base-tables.sql` | **M0 之后、M1-T5 / M2 之前** | `form`（合同类型）、`act_designer`（流程设计器） |
| ③ **业务表** | **25** | 你跑 `04-biz-tables.sql` | **M1 开始前一次性建好** | `conf_*`(6) `contract_*`(11) `template_*`(7) `work_handover`(1) |
| ④ **Activiti 引擎表** | **24** | **引擎启动时自动建**（一行代码不用写） | **M0 · T7 第一次启动后端** | `ACT_*` |

> ⚠️ **别把上面两张表搞混**：「来源」表里 ② 业务表是 **27** 张，「批次」表里 ②+③ 才是 27 张——因为 `form`/`act_designer` 虽然名字不带业务前缀，**本质是业务表**（见下方「两件最容易搞混的事」）。

**⚠️ 新手最容易搞混的两件事**（照下面两句记，就不会错）：

1. **业务表不是你设计的，是原作者设计、脚本帮你导进库的。** 你要做的是**理解每张表为什么这么设计**，而不是从零写建表语句。（答案册早期确实是一张张手写 DDL，后来把 25 张一次性提取成 `04-biz-tables.sql`。见 [M1 · T2](M1-基础数据与合同CRUD（总览）.md)。）
2. **`form` 和 `act_designer` 躺在名叫「missing-base-tables」的脚本里，但它们其实是业务表。** 名字骗人——`01` 脚本的筛选条件是「只保留 `sys_` / `gen_` 开头的表」，这两张表名字对不上就被误排除了，只好单独补一个脚本。详见 §四。

**怎么验证 ④ 批是「引擎自建」而不是脚本建的**（一句话自查）：

```sql
SELECT TABLE_NAME, CREATE_TIME FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'zxcm' AND TABLE_NAME LIKE 'ACT%' ORDER BY CREATE_TIME LIMIT 1;
```

实测 `ACT_GE_PROPERTY` 的建表时间比 `sys_menu` 晚 **36 秒**——那 36 秒就是 Spring 启动、Activiti 初始化引擎的时间。所以 ④ 批不是脚本建的，是**应用启动的副作用**。

**怎么自查表建全了没有**：

```sql
SELECT COUNT(*) FROM information_schema.TABLES WHERE TABLE_SCHEMA='zxcm';
```

M0 跑完 `01` + 启动后端后应是 **50** 张（26 系统表 + 24 引擎表）；再跑完 `03` / `04` 后应是 **77** 张。

**三种来源分别在哪一节详解**：

| 来源 | 表数 | 详解位置 |
|---|---|---|
| ① 框架系统表 | 26 | **§三**（底座主体，逐张讲） |
| ② 业务表（含 `form` / `act_designer`） | 27 | **§四 · 组①~组⑦**（逐张讲） |
| ③ Activiti 引擎表 | 24 | **§四 · 组⑧**（只给分组规律，细节归 [M2](M2-审批流与事件状态机（总览）.md)） |

## 二、关系总图

先看**权限链**（这是整个底座的主干，答辩必问）：

```
   sys_user ──sys_user_role───► sys_role ──sys_role_menu───► sys_menu
      │                            │
      │                            └──sys_role_dept──────► sys_dept     ← 框架数据权限(自定)
      │
      ├──sys_user_dept──────────► sys_dept                            ← 业务数据权限(本部门/本部门及以下)
      ├──sys_user_post──────────► sys_position                        ← 岗位（本学习版空表）
      └──sys_user_manage ─(自关联)─► sys_user                          ← 谁管谁（一对一交接）
```

再看**组织和租户**：

```
   sys_dept (PARENT_ID 自关联，ANCESTORS 存祖级链 "0,100")
      └── sys_user.DEPT_ID 指向「默认部门」，多部门走 sys_user_dept

   sys_tenant (一个租户)
      ├── sys_tenant_module ──► sys_business_module      ← 租户能买哪些模块
      └── sys_business_module_menu ──► sys_menu          ← 模块包含哪些菜单
```

**一句话记忆**：`sys_user` 是中心，向左连「组织」（dept / position / user_manage），向右连「权限」（role → menu）。字典、参数、日志、存储这四组是**挂在主干旁边的工具表**，不属于权限链。

### 业务表关系总图（合同那条线）

底座表管「谁能用系统」，业务表管「合同怎么流转」。合同这股数据的中心是 `contract_draft`：

```
   conf_signing_subject(签约主体)      conf_contract_counterpart(合作方/相对方)
              ▲  SUBJECTS(JSON)                     ▲  PARTNERS(JSON)
              └──────────────┬───────────────────────┘
                             │
                    ┌────────┴─────────┐
                    │  contract_draft  │  ← 合同本体（系统的心脏，85 列宽表）
                    └──┬────┬────┬─────┘
                       │    │    └──────── contract_point_log（事件流水：到底发生了什么，只增不改）
                       │    └───────────── contract_draft_files（合同文件，带版本 V1.0/V1.1）
                       └────────────────── contract_draft_partnerids（相对方关联表）
                                                │ 审批走完 → 抄一份快照
                                                ▼
                       contract_his / contract_his_files（合同历史快照，只读不写）

  合同类型 form ──INSTANCE_DEF_KEY──► act_designer（业务侧流程定义）
                                            │  EN_CODE = 引擎侧 ACT_RE_PROCDEF.KEY_
                                            ▼
                              contract_audit_form（审批单）── contract_remarks（审签意见）

  模板线：template_contract（壳）──template_link_relation──► template_clause / template_element
  用印线：contract_seal ──► contract_seal_notes（用印流水，法律凭证，只增不改）
  文件线：conf_file ← 统一文件表，靠 MODULE 列区分来源（M1 合同附件 / M3 模板文件 / M4 双章合同都存它）
```

**一句话记忆**：**签约主体 + 合作方 → 合同本体 `contract_draft` → 审批（`form`→`act_designer`→`contract_audit_form`）→ 快照（`contract_his`）→ 用印（`contract_seal*`）**。模板线、文件线是围绕它转的配套设施。

## 三、底座表逐张详解（26 张 · 框架系统表）

> **字段表怎么读**：`允许空` = 建表时的 NULL / NOT NULL；`默认`：`NULL` = 可空且未写 DEFAULT（MySQL 隐式 NULL）；`无` = NOT NULL 且无默认，插入必须传值；其它为显式默认值；`键` = PK 主键（唯一/普通索引见字段表下方的「索引」行）；`说明` 来自数据库列注释。


**这 26 张是 RuoYi 框架自带的系统表，不是你为合同系统设计的。** 它们跟业务无关——用户、角色、菜单、部门、字典、日志，任何 RuoYi 后台都有。**你的角色是「会用」**：知道哪张表干嘛、用到了回来查字段就行。

字段表**逐列列出**：字段名、类型、允许空、默认值、键、说明。审计四件套（`CREATE_BY / CREATE_TIME / UPDATE_BY / UPDATE_TIME`）、`DEL_FLAG`、`TENANT_ID` 也都在表里，不再省略。

> 📖 **本节讲的是 ① 框架系统表（26 张）**。② 业务表（27 张）在 **§四**。

### 组 ① 权限与组织（11 张）——底座的主干

**例子**：`DEPT_ID=100, PARENT_ID=0, ANCESTORS=0, DEPT_NAME=总公司, LEADER=1`
→ 根部门；`ANCESTORS=0` 表示它没有上级。

**⚠️ 坑**：`LEADER` 存的是用户 id，不是名字；用户被删后这里会悬空。

#### 6. sys_user_role 用户和角色关联表（行 3164）

**一句话**：多对多中间表——一个用户可以有多个角色，一个角色可以给多个用户。

**一行代表什么**：一次「授权」。`USER_ID=1, ROLE_ID=5` 表示 1 号用户拥有 5 号角色。

**字段逐个说**（共 3 列）

| # | 字段 | 类型 | 允许空 | 默认 | 键 | 说明 |
|---|---|---|---|---|---|---|
| 1 | `USER_ID` | decimal(20,0) | 是 | NULL |  | 用户ID |
| 2 | `ROLE_ID` | decimal(20,0) | 是 | NULL |  | 角色ID |
| 3 | `TENANT_ID` | varchar(64) | 是 | NULL |  | 租户ID |

**索引**：⚠️ 无主键

**为什么没有主键、没有索引**：RuoYi 原生设计如此——关联表只用「两个外键」表达关系，靠业务代码保证不重复。代价是：**同一对 `(USER_ID, ROLE_ID)` 可以插两次**，多角色遍历时会重复；表大了 join 会全表扫。生产环境建议加 `PRIMARY KEY(USER_ID, ROLE_ID)`。

**写入链路（先删后插）**：`SysUserServiceImpl.insertUserAuth(userId, roleIds)`：
```java
userRoleMapper.delete(new LambdaQueryWrapper<SysUserRole>().eq(SysUserRole::getUserId, userId));
insertUserRole(userId, roleIds);   // 循环 new 对象 → insertBatch
```
**不是 diff**，是「全删再全插」——简单、不会漏，代价是每次改角色都重写这个用户的全部行。

**读取链路**：`SysMenuMapper.xml` 的 `selectMenuTreeByUserId` 三表 join：
```sql
sys_menu m
  left join sys_role_menu rm on m.menu_id = rm.menu_id
  left join sys_user_role urd on rm.role_id = urd.role_id
where urd.user_id = #{userId}
```
数据权限那边则按 `user.getRoles()` **逐个角色 OR 拼接**（`PlusDataPermissionHandler:137`）。

**例子**：`USER_ID=1, ROLE_ID=1587990785801162753`
→ 1 号用户（zxcmAdmin）绑定了「系统管理员」角色。

**⚠️ 坑 / 面试点**：
- 没有唯一约束，重复授权会产生重复行；
- 「业务上只取第一个角色」是误读——数据权限是**多角色 OR**，菜单也是多角色并集；
- 删用户时 `SysUserServiceImpl` 会先删这张表，再删 `sys_user`。

**一句话**：角色能看哪些菜单、能点哪些按钮。**侧边栏和按钮权限的最终开关**。

**一行代表什么**：一次「角色 → 菜单」授权。`ROLE_ID=2, MENU_ID=1` 表示 2 号角色能看到 1 号菜单。

**字段逐个说**（共 3 列）

| # | 字段 | 类型 | 允许空 | 默认 | 键 | 说明 |
|---|---|---|---|---|---|---|
| 1 | `ROLE_ID` | decimal(20,0) | 是 | NULL |  | 角色ID |
| 2 | `MENU_ID` | decimal(20,0) | 是 | NULL |  | 菜单ID |
| 3 | `TENANT_ID` | varchar(64) | 是 | NULL |  | 租户ID |

**索引**：⚠️ 无主键

**为什么按钮（F 类型）也要在这里授权**：`sys_menu` 里 F 行是权限点，只有把 F 行也插进 `sys_role_menu`，`getMenuPermission` 才会把 `conf:signingSubject:add` 放进用户的权限集合——前端按钮才显示、后端 `@SaCheckPermission` 才通过。**只授页面行、不授按钮行，页面能进但按钮全 403。**

```java

roleMenuMapper.delete(new LambdaQueryWrapper<SysRoleMenu>().eq(SysRoleMenu::getRoleId, role.getRoleId()));
return insertRoleMenu(role);   // 循环 menuIds → insertBatch
```
改一次角色权限，整张角色的菜单关联会被重写。

**读取链路**：
- 菜单树：`selectMenuTreeByUserId` join 它；
- 按钮权限码：`SysPermissionService.getMenuPermission` 查 `PERMS` 集合；
- 角色管理页回显：`selectRoleMenuIds`（勾选状态）。

**例子**：`ROLE_ID=2, MENU_ID=1`
→ 「普通角色」能看到「开发管理」目录。

**⚠️ 坑 / 面试点**：
- 无主键、无索引，同一 `(ROLE_ID, MENU_ID)` 可重复；
- 133 行是底座里最大的关联表——每次登录 `getRouters` 都要 join 它，所以**菜单越多越慢**；
- 改角色是 delete + insert，不是增量更新；并发改同一角色会互相覆盖（最后提交的赢）。

## 五、三个「一表三用」的深坑（面试核心区）

### 5.1 数据权限有**三套引擎**，不是一套

| 引擎 | 靠什么实现 | 配在哪 | 过滤维度 | 谁在用 |
|---|---|---|---|---|
| ① 框架原生 | `@DataScope` + SpEL 模板 | `sys_role.DATA_SCOPE`（5 档） | 按**部门** | 框架自带列表（用户/角色等） |
| ② MyBatis-Plus 插件 | `@DataPermission` + JSqlParser 改写 SQL | `sys_role` 横向 10 个 `*_PERMISSION` 列（7 档） | 按**负责人 / 部门 / 本人** | 合作方、合同、台账 |
| ③ 手工拼 SQL | `DataPermissionHelper.getContractDataPermissionSql` | 代码里拼条件 | 看业务需要 | 报表 / 看板（第 10 章） |

**为什么三套并存**：

- 框架原生那套只有 5 档、按部门，管不了「草稿只能看自己的、已审批的看本部门」；
- 所以第 2 章在 `sys_role` 上横向加了 10 列，每个业务域一档（`DRAFT_PERMISSION` / `CONTRACT_PERMISSION` / `PARTNER_PERMISSION`…）；
- 报表 SQL 太复杂（多表 join、聚合），插件改写容易出错，就改成在代码里手工拼一段 SQL 塞进 `where`。

**怎么判断一个查询走哪套**：看 Mapper 方法上有没有 `@DataPermission`——有就走插件；没有但 SQL 里出现 `getContractDataPermissionSql` 就是手工拼；两者都没有就是不过滤。

**面试问法**：「你们的数据权限怎么做的？」
**答**：「分两层：功能权限管能不能调接口（`@SaCheckPermission`），数据权限管能看到哪些行。数据权限有三套实现——框架原生的部门数据范围、MyBatis-Plus 插件按角色扩展列改写 SQL、以及报表里手工拼。选哪套看查询复杂度，不是越多越好。」

---


### 5.2 三张日志表 = 三种写入机制

| 表 | 写入方式 | 实现位置 | 触发条件 |
|---|---|---|---|
| `sys_oper_log` | **注解式 AOP** | `LogAspect` 切 `@Log` | Controller 上写了 `@Log` |
| `sys_logininfor` | **业务代码手写** | `SysLoginService` / `SysRegisterService` 调 `recordLogininfor()` | 登录/登出/注册 |
| `sys_err_log` | **logback Appender** | `DbErrorLogAppender` 挂 ROOT logger | 任何 `log.error()` |

**三者都带 `@Async` 或异步**（`recordOper`、`recordLogininfor` 都有 `@Async`；Appender 本身在日志线程上），**不阻塞主请求**。

**面试问法**：「为什么登录日志不用 AOP？」
**答**：「因为登录接口执行时**还没有登录用户**，AOP 拿不到 `oper_name`；而且登录失败要分 IP 限次，得精确记录每种失败原因（验证码过期 / 密码错误 / 超过重试次数），这些语义 AOP 的通用模型表达不了，所以用手工埋点。」

**面试问法**：「为什么要有两张错误表（`sys_oper_log.ERROR_MSG` 和 `sys_err_log`）？」
**答**：「不是一回事。`sys_oper_log` 记的是**业务请求失败**（一个接口抛异常了），有用户名、URL、请求参数，是**审计视角**；`sys_err_log` 记的是**任何 `log.error()`**，包括定时任务、异步线程里的异常，没有 HTTP 上下文，是**排障视角**。前者给管理员看『谁干了什么失败了』，后者给开发看『哪儿崩了』。」

### 5.3 逻辑删除 `DEL_FLAG` ≠ 枚举

**⚠️ 这个坑我在读表时踩到了**：`DEL_FLAG` 的注释写的是「**0 未删除 2 已删除**」。

- **不是 `0/1`**，是 `0/2`！
- 原因是 `1` 被别的状态占了。`sys_menu` 里 `VISIBLE` 是「0显示 1隐藏」，`STATUS` 是「0正常 1停用」，`IS_FRAME` 是「0是外链 1否」……**这个项目的所有 `char(1)` 状态位编码完全不统一**。

**答辩风险**：写 SQL 时想当然写 `WHERE DEL_FLAG = 1` 会**查出全部数据**。另外 MyBatis-Plus 的逻辑删除是全局配置的（`@TableLogic`），手写 XML 时**不会自动加这个条件**——`SysPostMapper.xml` 那种手写 SQL 里如果漏了 `DEL_FLAG`，就会查出已删除数据。

**建议**：统一用 Java 实体走 MyBatis-Plus（自动带逻辑删除），少手写 SQL；非要手写，先确认那三五个 `char(1)` 状态位的编码。

> 💡 **一句话说人话**：这个项目的 `char(1)` 状态位**各表各写各的**（同是「0/1」，有的 1 表示「是」、有的 1 表示「停用」）。写 SQL 前**先 `SHOW CREATE TABLE 表名` 看列注释**，别凭直觉写 `WHERE DEL_FLAG = 1`——那会查出**全部**数据（含已删除的）。

## 六、面试问法与参考答法

**Q1：为什么主键用 `decimal(20,0)` 而不是 `bigint` 或者自增？**
A：用的是**雪花算法**生成的分布式 ID，19 位数字，所以 `decimal(20,0)` 兜得住。好处是分库分表时不用改、ID 不泄露业务量；代价是**占空间比 bigint 大、索引效率略低**。另外注意：Java 侧接收 19 位 long 到前端**必须序列化成字符串**，否则 JS 的 Number 精度只有 53 位会丢精度——所以你会看到 `@JsonSerialize(using = ToStringSerializer.class)`。

**Q2：部门树的「查某部门及以下」怎么实现的？**
A：`sys_dept.ANCESTORS` 存祖级链（根是 `0`，子部门是 `0,100`）。查「100 及以下」直接 `find_in_set(100, ancestors)`，一次查询搞定，不需要递归。**代价是移动部门时要批量重写子树的 `ANCESTORS`**——这是空间换时间。

**Q3：用户和部门是一对多还是多对多？**
A：**两套并存**。`sys_user.DEPT_ID` 是**默认部门**（一对多，一个部门多个用户），`sys_user_dept` 是**兼职部门**（多对多，一人多部门）。业务数据权限按后者算。加 `sys_user_dept` 是因为合同管理里法务专员常兼管多个部门，单 `DEPT_ID` 表达不了。

**Q4：一个角色对「草稿」和「已审批合同」能设不同可见范围吗？**
A：能。这是本项目在 RuoYi 原生 `DATA_SCOPE` 之上**横向扩展了 10 列**（`DRAFT_PERMISSION` 到 `WORK_PERMISSION`），每列独立走 `ContractPermission` 枚举的 7 档。触发方式是 `@DataPermission(resource = DataPermissionResource.xxxPermission)`，Handler 用**反射**按枚举 `index` 去读 `sys_role` 对应列。

**Q5：菜单权限和数据权限有什么区别？**
A：**菜单权限管「能不能进这个页面/能不能点这个按钮」**，靠 `sys_role_menu` → `sys_menu.PERMS` → 前端 `v-hasPermi` + 后端 `@SaCheckPermission`；**数据权限管「进去以后能看到哪些行」**，靠 `sys_role.*_PERMISSION` → `@DataPermission` → 往 SQL 里拼 `WHERE`。前者是粗粒度、静态的；后者是细粒度、动态的。

**Q6：`/getRouters` 为什么返回菜单树，不返回菜单列表？**
A：前端要直接塞给 vue-router，`children` 嵌套结构省得前端再组树；更重要的是**`COMPONENT` 字段是后端配的组件路径**，前端 `import(@/views/${component})` 动态加载，所以加菜单**不用改前端代码**。这是「权限驱动路由」的核心。

**Q7：操作日志怎么保证不影响接口性能？**
A：AOP 里最后一句 `recordOper()` 上加了 `@Async`，丢到线程池落库，主请求不等待。**代价是可能丢日志**（线程池满了 / 应用被 kill），所以真正的审计场景要同步写。

**Q8：字典改了为什么不生效？**
A：字典走 Redis 缓存。`SysDictDataServiceImpl` 增删改时会清 `CacheConstants.SYS_DICT_KEY`。**直接改库不会清缓存**，必须走后台接口改，或者手工删 key。

**Q9：`sys_config` 和 `sys_dict_data` 都存配置，区别是什么？**
A：**`sys_dict_data` 是「枚举值的候选集」**（下拉框里有哪些选项，多行、有序、带 label/value）；**`sys_config` 是「系统的单个开关或参数」**（一个 key 一个值，值可以是 JSON）。选人用字典，选行为用参数。

**Q10：这套系统是多租户吗？**
A：**是 SaaS 架构但当前跑单租户**。所有表都有 `TENANT_ID`，有 `sys_tenant` / `sys_tenant_module` / `sys_business_module_menu` 一整套「租户 → 模块 → 菜单」授权链，MyBatis-Plus 也有租户插件拦截。但底座数据只有 `00000000` 一个租户，所以实际是单租户运行。**答题技巧**：主动说「架构预留了多租户，当前部署是单租户」，比含糊说「有多租户」稳。

## 九、🎤 一分钟讲法（对着面试官讲）

被问「你这套系统的权限底座是怎么设计的」，照下面这段讲，**一分钟内讲完**：

> 「整套权限的底座就一条链：**用户 `sys_user` → 角色 `sys_role` → 菜单 `sys_menu`**，中间靠 `sys_user_role`、`sys_role_menu` 两张多对多关联表接起来。`sys_menu` 是**一张表三用**——`MENU_TYPE` 区分目录 M / 菜单 C / 按钮 F，权限码就存在它的 `PERMS` 列里，这是**功能权限**。
>
> 数据权限我们做了**三套引擎**：第一套是 RuoYi 原生的 `sys_role.DATA_SCOPE`（5 档，按数据属于**哪个部门**过滤）；第二套是我们在它旁边**横向加了 10 列 `*_PERMISSION`**（7 档，按数据属于**哪个人**过滤）——因为合同是「人」的资产不是「部门」的资产，而且同一个角色对「草稿中的合同」和「已审批的合同」要能配不同范围；第三套是 `sys_user_manage` 表，按人做休假交接。
>
> 三套用的是同一个机制：Mapper 方法上标 `@DataPermission`，MyBatis-Plus 拦截器往 SQL 的 `WHERE` 里拼条件——**同一个接口、同一份代码，不同的人看到不同的行**。」

如果面试官只给你 30 秒，就讲这一句：

> 💡 **一句话说人话**：**`sys_user` 是中心，向左连组织、向右连权限；功能权限管「能不能进这个页面」，数据权限管「进去以后能看哪些行」，我们的数据权限有三套引擎。**

**⚠️ 讲这段时最容易踩的两个坑**：

1. **别说「权限码在角色表上」**。权限码在 `sys_menu.PERMS`；角色表上放的是**数据范围**（`DATA_SCOPE` 和那 10 个 `*_PERMISSION`）。这两样经常被混着说，面试官一听就知道你没分清。
2. **别顺嘴提「文件走 OSS」**。`sys_oss` / `sys_oss_config` 两张表在本项目是**空壳、零 Java 代码**，文件走的是 `ruoyi.profile` 本地磁盘（见 §三·组④）。主动说「遗留未启用」比被问住强。

> ⭐ **进阶版收尾**（面试官明显懂行时再讲）：
> 「这套设计里我觉得最值得讲的是**第二套引擎**。原生 RuoYi 一个 `DATA_SCOPE` 管所有业务，但我们发现**一个角色对不同业务对象要不同的可见范围**——法务专员草拟中的合同只能看自己的，但审批完成的合同整个部门都能看。一个 `DATA_SCOPE` 列表达不了两个维度，所以我们横向扩展成 10 列，每列独立走 `ContractPermission` 枚举的 7 档，用 `@DataPermission(resource = xxxPermission)` 指定读哪一列。**这是本项目在 RuoYi 上最有价值的一处扩展。**」
