## 0. 全景：这个系统的数据"住"在 5 个地方

### 0.1 五个位置，各管一摊

| # | 位置 | 存什么 | 特征 | 谁负责 | 本文小节 |
|---|---|---|---|---|---|
| 1 | **本地磁盘** | 文件**字节**（合同、模板、图片、附件） | 大、不变、要备份 | `conf_file` 表记路径 | §1 |
| 2 | **MySQL** | 业务**事实**（合同、状态、留痕、文件元数据） | 要事务、要查询 | MyBatis-Plus | §1.4 / §3 |
| 3 | **Redis** | **易失的、高频读的**（登录态、权限、字典、验证码、防重） | 可丢、要快 | Redisson | §2 |

| 5 | **对方服务器** | 在线编辑中的文档（OnlyOffice 那边） | 不在你手里 | OnlyOffice | §4.2 |

### 0.2 一次「上传合同附件」，字节到底去了哪

```
用户在前端拖一个「采购合同.pdf」进来，点上传
        │
        ▼
  POST /conf/file/upload/contract          ← 前端组件直接打这个地址（带 token）
        │
        ├──① 字节 ──→ 本地磁盘
        │            <profile>/upload/contract/2026/07/09/<uuid>.pdf
        │            （路径根 = application-dev.yml:4 的 ruoyi.profile）
        │            ★ 文件名被换成 uuid，原名只留在数据库里
        │
        └──② 元数据 ──→ MySQL 表 conf_file
                     { ID, FILE_NAME(uuid), ORIGINAL_NAME(采购合同.pdf),
                       FILE_SUFFIX(.pdf), URL(http://.../profile/upload/...),
                       MODULE(contract) }
                     │
                     └── 业务表再"引用"这个 ID：
                          contract_draft_files.MAIN_FILE_ID → conf_file.ID
                          contract_draft.SEAL_FILES_ID      → contract_draft_files.ID
```

**一句话记住**：**数据库里存的是"发票"（元数据 + 路径），真正的东西在"仓库"（磁盘）里。**

### 0.3 贯穿全文的两条判断原则

| 原则 | 含义 | 反例（这套系统的短板） |
|---|---|---|
| **① 大对象不进数据库** | 文件、图片的**字节**永远不放 DB，DB 只放 key/路径 | ✅ 做到了（用 `conf_file`） |
| **② 能重算的不缓存，缓存的要能失效** | 缓存只放"查库慢 / 每次都查"的东西，且必须有清理时机 | ⚠️ 有一处缓存**没有失效逻辑**（见 §2.5） |

## 1. 文件存储：合同/模板/图片的真身在哪

### 1.1 有哪些功能

| 功能 | 谁用 | 为什么需要 |
|---|---|---|
| **上传（按模块）** | 合同附件、模板、签约主体资质 | 业务必然要传文件 |
| **下载（带鉴权）** | 合同正文、双章件 | 合同是法律凭证，**下载要留痕** |
| **打包下载** | 一份合同的全部文件 | 一个合同可能有正文 + N 个附件 |
| **图片预览** | 头像、资质图 | 要被 `<img>` 直接引用 |
| **在线编辑** | 模板、合同草稿 | 不下载 Word，直接网页改（OnlyOffice） |
| **版本管理** | 合同文件 | 改内容**不覆盖**旧版（"历史不可变"） |

### 1.2 为什么不能把文件塞进数据库

这是面试**必问**的一题。三个理由，按重要性排：

1. **备份/主从复制会被拖垮**：一个 50MB 的合同 BLOB 塞进 `contract_draft`，binlog 立刻暴涨，主从同步延迟；而磁盘文件**可以单独增量备份**。
2. **数据库连接是稀缺资源**：读一个大 BLOB 会长时间占用连接，把"查列表"这种快查询**一起堵死**。
3. **没法用 CDN / 静态服务 / 断点续传**：文件放磁盘或对象存储，可以挂 Nginx、上 CDN、支持分片下载；放 DB 里只能走应用层吐字节。

> **企业级标准答案**：**文件进对象存储（MinIO / 阿里云 OSS / S3），数据库只存 object key。**
> 本项目**表结构是按这个设计的**（表名注释就叫「OSS对象存储表」），但**落地时换成了本地磁盘**——这是它和企业级的最大差距，见 §1.9。

### 1.3 设计思路：三层引用，各管一件事

```
     ┌─────────────────────────────────────────────────┐
     │  业务表 contract_draft                          │
     │    SEAL_FILES_ID ────────┐                      │  ← 合同"当前用的是哪个文件组"
     └─────────────────────────┬┘                      │
                               ▼                        │
     ┌─────────────────────────────────────────────────┐
     │  文件组表 contract_draft_files                  │
     │    MAIN_FILE_ID ─────────┐   FILE_GROUPS_VERSION │  ← 一份合同的"文件清单 + 版本"
     └─────────────────────────┬┘                       │
                               ▼                         │
     ┌─────────────────────────────────────────────────┐
     │  物理文件表 conf_file                            │
     │    ID / URL / MODULE / ONLYOFFICE_KEY            │  ← 磁盘上一个真实文件的"身份证"
     └─────────────────────────────────────────────────┘
```

**为什么拆三层，而不是在业务表里直接存一个 URL 字符串？**
- **`conf_file` 独立**：所有模块（合同/模板/资质）的文件**共用一套上传下载代码**，靠 `MODULE` 列区分来源。改上传逻辑只改一个地方。
- **`contract_draft_files` 做"文件组"**：一份合同有正文 + 附件，需要**一起管理、一起下载、一起版本化**，所以单独一张表装这个"包"。
- **业务表只存 ID**：合同表不关心文件名、路径——**换存储引擎（磁盘→OSS）时业务表一行都不用改**。这就是"依赖倒置"在存储上的体现。

### 1.7 图片 vs 文档：**同一条上传，两条读取通道**（重点）

这是本系统设计上**最值得讲**的一点：**存储是同一套，但"读"分了两条路，因为敏感度不同**。

| | 🖼 图片（jpg/png/gif/bmp） | 📄 Office 文档（doc/docx/xls/pdf…） |
|---|---|---|
| 上传 | 同一条 `/conf/file/upload/{module}` | 同一条 |
| **怎么读** | `GET /profile/upload/...jpg` → `<img src>` 直接显示 | ❌ **这条路返回空**，必须走 `/conf/file/download/{fileId}` |
| **鉴权** | **免鉴权**（`application.yml:167` `- /profile/**` 在 `security.excludes`，注释「开放文件预览」） | **必须带 token** |
| **留痕** | 无 | 下载/打包下载**写事件日志** |
| 额外限制 | 仅限图片后缀 | `module=contract` 的 Office 文件**直接拒绝**，要求走打包下载 |

**关键代码 ①：`/profile/**` 只放行图片**（`CommonController.java:132-137`）

```java
String ext = FileNameUtil.extName(imgPath);
if (!Arrays.asList(MimeTypeUtils.IMAGE_EXTENSION).contains(ext)) {
    return;                 // ← 不是图片后缀，直接不给你看
}
```

图片后缀白名单（`MimeTypeUtils.java:33`）：`{ "bmp", "gif", "jpg", "jpeg", "png" }`

**关键代码 ②：合同的 Office 文件不给单下**（`ConfFileController.java:128-132`）

```java
if (StringUtils.isNotEmpty(confFile.getModule()) && confFile.getModule().equals("contract")) {
    if (isOfficeFile(confFile.getFileSuffix())) {
        throw new ServiceException("没有权限访问该文件");   // 提示改走 downloadZip
    }
}
```

> 🎤 **为什么这么设计（面试可以直接讲）**：
> 「图片是**低敏感**内容，要被 `<img>` 免登录引用、可以挂 CDN；而**合同正文是高敏感法律凭证**，
> 每次下载都要**过鉴权 + 留痕**。所以同一个存储层，用**两条读取通道区分敏感度**——
> 这是一个"**安全和体验的权衡**"，不是随手写的。」

### 1.8 坑

| 坑 | 现象 | 原因 |
|---|---|---|
| **URL 存的是绝对地址** | 换域名/上 https 后历史图片全挂 | 存的是 `http://localhost:8080/...`，写死了 host（`application-dev.yml:4` 决定盘符，`serverConfig.getUrl()` 决定域名） |
| **图片后缀可伪造** | `evil.jsp` 改名 `evil.jpg` 能过 | `/profile/**` 只按**后缀**判图片，不验真实 MIME |
| **改了盘符找不到旧文件** | 换 `ruoyi.profile` 后老数据 404 | 磁盘根变了，但 DB 里的 URL 还是旧的 |
| **前端组件指向已废弃接口** | 框架自带的 `ImageUpload` 默认打 `/system/oss/upload` | 该 Controller **已被移除**（只剩混淆日志 `script/bin/log.xml` 有痕迹）；实际用的是 `/conf/file/upload/{module}` |
| **80MB 上限、无分片** | 超大扫描件传不上 | `application.yml:72` `max-file-size: 80MB`，且无分片/断点续传 |

### 1.9 企业级差距（面试"如果让你重做"可以讲）

| 现状 | 企业级应该是 |
|---|---|
| 本地磁盘 | **MinIO / 阿里云 OSS / S3**（多实例部署才不会 A 机传、B 机读不到） |
| URL 存绝对地址 | **DB 存相对 object key**，出参时再拼域名 |
| `/profile/**` 全放开、按后缀判类型 | **校验真实 MIME + 签名 URL（短时效预签名 token）** |
| 正本可被回调**原地覆盖** | 正本**只增不改**（新版本另存）+ **存 SHA-256 哈希**防篡改 |
| 无分片 | 分片上传 + 断点续传 + 秒传（按 hash 去重） |

## 2. Redis 缓存全景

### 2.1 为什么用 Redis（而不是 Spring Cache / 本地 Map）

三个理由：

1. **要跨实例共享**：多台后端共用一个 Redis，**登录态、权限**才能一致。（本地 `Map` 做不到）
2. **要能设过期**：验证码 2 分钟、防重 5 秒、临时占号 24 小时——**TTL 是缓存的核心能力**。
3. **要快且可丢**：字典、参数**几乎不变但每次请求都要**，放 Redis 省一次 DB 往返；Redis 挂了也只影响性能、不影响数据正确性。

> ⚠️ **一个反直觉的事实**：本项目 **`@EnableCaching` 是开着的、`RedissonSpringCacheManager` 也配了，但全项目没有一个生效的 `@Cacheable`**
> （仅 `SysUserServiceImpl.java:406,421,448,461,473,605,624` 有 7 行**被注释掉的** `@CacheEvict`）。
> **所以：本项目的缓存全部是"手写"的**——自己拼 key、自己 `RedisUtils.setCacheObject`、自己管失效。
> 这既解释了"为什么升级权限要重登"，也是面试里一个很好的对比点（手写 vs 注解式）。

### 2.2 基础设施：怎么连、怎么序列化

| 项 | 值 | 证据 |
|---|---|---|
| 客户端 | **Redisson**（不是 Jedis/Lettuce 直连） | `RedisConfig.java:61` `RedissonClient redisson()` |
| 连接（dev） | host=localhost, port=6379, **database=5**, 无密码 | `application-dev.yml:184-196` |
| 序列化 | **`JsonJacksonCodec`**（JSON 编码，不是 JDK 序列化） | `RedisConfig.java:69` |
| 业务读写入口 | **`RedisUtils`**（封装 Redisson，全项目统一走它） | `RedisUtils.java` |

> 💡 **为什么用 JSON 编码而不是 JDK 序列化**：JDK 序列化出来的值是**二进制乱码**，
> 用 `redis-cli` 根本没法人眼看；JSON 编码**在 redis 里直接能读懂**，排查问题方便得多。
> 这是"可运维性"的考量。

### 2.3 key 命名空间总表（这是本文的干货核心）

**框架级 + 系统级**（常量集中在 `ruoyi-common/.../constant/Constants.java`）：

### 2.4 逐个讲（按业务重要性排序）

#### ① 登录态：`token:login:session:*`（最核心）

**存什么**：一整个 `LoginUser` 对象——**用户信息 + 权限码集合 + 角色集合**，全在里面。

```java
// LoginHelper.java:87-99  —— 登录写入 / 读取
public static void setLoginUser(LoginUser loginUser) {
    StpUtil.getTokenSession().set(LOGIN_USER_KEY, loginUser);   // 写进 Redis 会话
}
public static LoginUser getLoginUser() {
    LoginUser loginUser = LOGIN_CACHE.get();                    // ① 先查 ThreadLocal（本次请求内）
    if (loginUser != null) return loginUser;
    return (LoginUser) StpUtil.getTokenSession().get(LOGIN_USER_KEY);  // ② 再查 Redis
}
```

> 🎯 **两级缓存**：`LOGIN_CACHE` 是 **`ThreadLocal`**（`LoginHelper.java:46`），**一次请求内**复用；
> 跨请求就靠 Redis 会话。**ThreadLocal 用完必须清**（否则线程池复用会串号），这是框架在 `FilterConfig` 里统一处理的。

**key 为什么是 `token:` 开头而不是 `satoken:`？**
因为 `application.yml:103` 配了 `token-name: token`，sa-token 拿这个名字去拼 key。
而 `PlusSaTokenDao` **把框架传进来的 key 原样当 Redis key 用、不做二次加工**（`PlusSaTokenDao.java:38-40`）。

**有效期**（`application.yml:103-123`）：

| 配置 | 值 | 含义 |
|---|---|---|
| `timeout` | 186400 秒（≈51.8 小时） | token **绝对**过期 |
| `activity-timeout` | 28800 秒（8 小时） | **无操作**过期 |
| `is-concurrent` | true | 同账号可多端同时在线 |
| `token-style` | uuid | token 是 uuid |

#### ② 权限与菜单：**没有独立缓存，全在会话里**

这是理解"**改了权限为什么不生效**"的关键：

```
登录时：SysLoginService 查 sys_menu → 得到权限码集合 → 塞进 LoginUser
        → LoginUser 整体存进 Redis 的 token:login:session:*
以后：  /getRouters 和 @SaCheckPermission 都读 Redis 会话，【不再查库】
```

**完整链路**（`SysLoginService.java:243-244` + `LoginHelper.java:88`）：

```java
loginUser.setMenuPermission(permissionService.getMenuPermission(user));  // 登录时查一次
loginUser.setRolePermission(permissionService.getRolePermission(user));
// → 随 setLoginUser 一起进 Redis 会话
```

> ⚠️ **结论**：**改了角色/菜单权限后必须重新登录**，因为会话里的 `LoginUser` 还是旧的。
> 系统**没有**做主动失效（`SysUserServiceImpl` 里那 7 个 `@CacheEvict` 全被注释了）。
> **这是设计取舍，不是 bug**——详见 §2.6。

#### ③ 字典缓存：`sys_dict:<dictType>`（典型的 Cache-Aside）

```java
// SysDictTypeServiceImpl.java:100-111  —— 标准的"旁路缓存"模式
public List<SysDictData> selectDictDataByType(String dictType) {

    dictDatas = dictDataMapper.selectDictDataByType(dictType);                      // ② 未命中查库
    if (CollUtil.isNotEmpty(dictDatas)) {

```

**失效时机**：改字典类型/数据时**主动删**（`SysDictTypeServiceImpl.java:148`），
或提供 `clearDictCache()` 用 `keys("sys_dict:*")` **批量清**（`:174-177`）。

> 🎯 **这就是 **Cache-Aside（旁路缓存）**范式：读时"先缓存后库、回填"；写时"删缓存"。
> 面试问"缓存怎么和数据库保持一致"，答这个模式 + "**删缓存优于改缓存**"（因为改缓存会遇到并发写覆盖）。

#### ④ 参数缓存：`sys_config:<configKey>`

和字典**一模一样**的 Cache-Aside（`SysConfigServiceImpl.java:84,91,198`）。存的是像 `sys.watermark.doc`（水印文字）这样的**全局参数值**。

> 水印那段就用到了它：`ChangeFileToPDFService.java:100` `sysConfigService.selectConfigByKey("sys.watermark.doc")`。

#### ⑤ 验证码：`captcha_codes:<uuid>`（**过期即失效**的典型）


> **`uuid` 作为 key 让验证码和会话解耦**，前端自己带着 uuid 回来，不需要服务端记住"这个浏览器"。

#### ⑥ 防重复提交：`repeat_submit:<url><md5>`（AOP + Redis）

**为什么需要**：用户手抖双击、网络慢重复点，会**重复下单/重复提交审批**。

**实现**（`RepeatSubmitAspect.java:58-91`）：

```java
@Before("@annotation(repeatSubmit)")
public void doBefore(JoinPoint point, RepeatSubmit repeatSubmit) {
    long interval = repeatSubmit.timeUnit().toMillis(repeatSubmit.interval());   // 默认 5000ms
    String nowParams = argsArrayToString(point.getArgs());                       // 入参序列化
    String url = request.getRequestURI();
    String submitKey = SecureUtil.md5(token + ":" + nowParams);                  // 用 token+参数做指纹
    String cacheRepeatKey = Constants.REPEAT_SUBMIT_KEY + url + submitKey;       // repeat_submit:<url><md5>
    if (RedisUtils.getCacheObject(cacheRepeatKey) == null) {
        RedisUtils.setCacheObject(cacheRepeatKey, "", Duration.ofMillis(interval)); // ★ 第一次：占坑，TTL=interval
        KEY_CACHE.set(cacheRepeatKey);
    } else {
        throw new ServiceException(repeatSubmit.message());                      // ★ 间隔内第二次：拒绝
    }
}
```

**用法**：在 Controller 方法上加 `@RepeatSubmit()` 即可（全项目 40+ 处，如 `ContractAuditController.java:174-326`）。

> 🎯 **面试点**：**key 里为什么带 `token`？**——不加的话，两个用户同时提交相同参数会被误判成重复。
> **为什么失败要删 key**（`:105,118`）？——不然用户"提交失败后立刻重试"会被拦 5 秒，体验差。

#### ⑦ 编号规则占号：`BILLRULE_<userId><enCode><date>`

**业务背景**：合同编号（如 `SWHT-20260709-001`）要**唯一且连续**。

**关键认知**：**真正的计数器不在 Redis，在数据库**（`conf_bill_rule.this_number` 自增），
**Redis 只缓存"我已经预占的号"**，避免同一用户 24 小时内反复取号、把计数器白白推进。

```java
// ConfBillRuleServiceImpl.java:363-390
public String getBillNumber(String enCode, Map<String,String> params, boolean isCache) {
    if (isCache) {
        String cacheKey = "BILLRULE_" + LoginHelper.getUserId() + enCode + thisDate;   // 按"人+规则+日期"
        if (!RedisUtils.hasKey(cacheKey)) {
            strNumber = this.getNumber(enCode, params);                                // 取新号（推进计数器）
            RedisUtils.setCacheObject(cacheKey, strNumber, Duration.ofHours(24));      // 占号 24h
        } else {
            strNumber = RedisUtils.getCacheObject(cacheKey).toString();                // 复用已占的号
        }
    }
    ...
}
```

**两个接口的区别**（面试高频）：

| 接口 | 行为 | 用在哪 |
|---|---|---|
| `getBillNumber(isCache=true)` | **预览**下一个号，**不推进**计数器（复用缓存） | 页面打开时先显示"预计编号" |
| `useBillNumber(enCode)` | **真正占用**，`deleteObject` 清掉占号缓存 | 点保存、真要用这个号时 |

> ⚠️ **并发安全的真相**（老实说，别硬编）：
> 计数器自增那个方法是 `public synchronized String getNumber(...)`（`ConfBillRuleServiceImpl.java:192-193`）
> ——**这是 JVM 级的 `synchronized`，只在单实例有效**。多实例部署下它**挡不住并发**。
> 而且**没有用 Redis 锁、没有数据库行锁（没有 `select ... for update`）、没有原子自增**。
> **正确做法**应是：`UPDATE conf_bill_rule SET this_number = this_number + 1 WHERE code = ?`（DB 原子）
> 或 Redis `INCR`，再或 `@Lock4j` 分布式锁。**这块是本项目一个真实的技术债。**

#### ⑩ 合同明细短缓存：`CONTRACT_DETAIL_<id>`（30 秒）

`ContractDetailController.java:128-129` 读缓存，`:211` 写缓存，**TTL 只有 30 秒**。

> 💡 **为什么只有 30 秒**：合同详情页**打开时会被前端连续请求好几次**（头部、正文、附件、日志各一次），

> **"短 TTL 缓存"是并发读优化的常用手段**——面试可以拿它举"缓存时长怎么定"的例子。

### 2.5 这套缓存实现的短板（企业级视角）

| # | 问题 | 后果 | 企业级做法 |
|---|---|---|---|
| 1 | **全手写缓存、命名不统一**：`sys_dict:` 在常量类，`BILLRULE_`/`CONTRACT_DETAIL_`/`positionlist_` 是硬编码字符串 | 容易拼错 key、难排查 | key 常量集中管理 / 用 `@Cacheable` 注解式 |
| 2 | **`positionlist_` 缓存没有失效点** | 岗位改了，页面可能一直显示旧的 | 增删改时清缓存 |
| 3 | **`login_error:` 未达阈值时无 TTL** | 计数永远不清理，积累垃圾 key | 每次都带 TTL |
| 4 | **权限变更无主动失效** | 改了权限必须重登（体验差），且**超管测不出权限配错** | 改权限时**按 loginId 清会话**，或会话里只存 userId、权限实时查 |
| 5 | **计数器并发保护靠 `synchronized`** | **多实例部署会重号** | DB 原子自增 / Redis `INCR` / `@Lock4j` 分布式锁 |
| 6 | **`lock4j` 依赖和配置都在，但全项目 0 处使用** | 白白引依赖 | 要么用起来，要么删掉 |

> 🎤 **第 6 点很值得主动说**：「我注意到项目 `pom.xml` 引了 `lock4j-redisson`、`application.yml` 也配了超时，
> 但全项目**没有任何一处 `@Lock4j`**。这说明**它准备了分布式锁的能力，但在业务里没用上**——
> 编号规则那里如果用了它，重号问题就解决了。」**能指出这个，说明你是在读代码而不是背八股。**

### 2.6 为什么"改了权限要重新登录"（本节最重要的一问）

**标准答案（三层）**：

1. **数据在哪**：权限码在**登录时**查一次，随 `LoginUser` 存进 **Redis 会话**（`token:login:session:*`）。
2. **为什么不主动失效**：主动失效要**遍历所有会话**找到该用户的 session 再改——成本高、易漏；
   而且**无法解决"代码里已经缓存的 ThreadLocal 副本"**（一次请求内 `LOGIN_CACHE` 已经拿了旧值）。
3. **所以的取舍**：**用"重登"换"实现简单 + 逻辑可靠"**。这是一个**明确的、可接受的 trade-off**。

> ⚠️ **面试踩坑提醒**：**超管**走短路分支（`permissions` 直接返回 `["*:*:*"]`，根本不查 `sys_menu`）。
> 两个后果：① 超管改菜单立刻生效；② **超管永远测不出权限配置对不对**（它什么都通过）。
> **想真验证权限，必须建一个普通用户。**

### 4.1 本地临时目录（`getTempPath()`）

### 4.2 OnlyOffice 服务器上的文档缓存（**不在你手里**）

在线编辑时，**用户改的其实是 OnlyOffice 服务器上的一份转换后副本**，不是你的原始 Word：

```
你的磁盘上的 采购合同.docx
      ↓ OnlyOffice 下载并转换
OnlyOffice 服务器上的 Editor.bin（浏览器实际编辑的是这个）
      ↓ 用户关闭/定时 → OnlyOffice 回调你的 callbackUrl
你的后端下载新文件 → 【覆盖】回磁盘上那个采购合同.docx（SaveCallback.java:87-98）
```

**`conf_file.ONLYOFFICE_KEY` 的作用**：它是**文档内容版本的唯一标识**（不是文件 ID）。
- 协同编辑要求所有用户用**同一个 key**，才会进入同一个编辑会话；
- 文件内容变了要**换 key**，否则 OnlyOffice 会认为"文件没变"、命中旧缓存（`ConfFileServiceImpl.changeKey()` 就是干这个的）。
- **踩坑**：`callbackUrl` 必须是 **OnlyOffice 服务器能访问到的地址**（写 `localhost` 必失败）；JWT 密钥两边要一致；回调接口**必须免鉴权**（它是 OnlyOffice 在调，没有你的用户 token）。

> 详见 [M3-模板体系与文档生成](M3-模板体系与文档生成（总览）.md) 的 OnlyOffice 章节。

|---|---|---|
| **token** | `localStorage`（`utils/auth.js` 的 `getToken/setToken`） | 刷新页面不丢登录态；`request.js:32-34` 每次请求头带 `token: Bearer xxx` |
| **用户/权限信息** | Vuex store | 页面内共享；刷新后重新拉 |
| **动态路由** | Vuex + `router.addRoute` | 登录后按 `/getRouters` 返回的菜单树生成 |

> ⚠️ **安全提醒**：token 放 `localStorage` 有 **XSS 窃取风险**（脚本能读）。
> 更稳的是 `HttpOnly` Cookie，但那样就要处理 CSRF。**这是"XSS vs CSRF"的经典权衡**，面试常问。

## 5. 面试讲解（详细 + 通俗）

### 5.1 三句话总纲（先背这个）

> 「这个系统的数据分五处放：**文件字节在磁盘、业务事实在 MySQL、易失的登录态和字典在 Redis、
> 转换中间文件在临时目录、在线编辑中的文档在 OnlyOffice 那边**。
> 数据库里存的是**元数据 + 路径**，不存字节——因为 **BLOB 会拖垮备份和连接**。
> 缓存全部手写（没用 `@Cacheable`），**最关键的取舍是"权限放会话里、改了要重登"**。」

### 5.2 高频问题 Q&A

**Q1：文件是怎么存的？**
> 「分三层：**`conf_file` 存物理文件的身份证**（ID、路径、模块），**`contract_draft_files` 存合同的"文件组"**（正文+附件+版本），**业务表只存一个 ID**。
> 字节落在本地磁盘，按 `模块/年月日/uuid` 分目录，**原名只留在 DB 里**。
> 好处是**换存储引擎时业务表一行不改**——这就是依赖倒置。」

**Q2：为什么不用 BLOB 存数据库？**
> 「三个原因，按严重程度：**一，备份和主从复制会被拖垮**——binlog 里塞大字段，从库延迟；
> **二，读大 BLOB 长时间占连接**，把快查询一起堵死；**三，没法上 CDN、没法断点续传**。
> 所以标准做法是**文件进对象存储、DB 只存 key**。」

**Q3：图片和文档的存储有什么不一样？**
> 「**上传是同一条管道，读取是两条通道**。图片走 `/profile/**`，**免鉴权**、能被 `<img>` 直接引用；
> 文档必须走**带鉴权的下载接口**，而且合同的 Office 文件**禁止单下、只能打包下载并留痕**。
> 因为**图片低敏感、文档是高敏感法律凭证**——这是安全和体验的权衡。」

**Q4：缓存都缓存了什么？**
> 「八类：**登录会话、验证码、防重复提交、在线用户、登录失败次数、字典、参数、编号占号**。
> 其中最核心的是**登录会话**——它不只存用户，还存了**整个权限码集合**，这就是**改了权限要重登**的原因。」

**Q5：缓存和数据库怎么保持一致？**
> 「字典和参数用的是 **Cache-Aside（旁路缓存）**：**读的时候先查缓存、未命中查库再回填；
> 写的时候删缓存**。**删而不是改**，是因为并发写会互相覆盖。
> 权限那块比较特殊——**不做主动失效，靠重登**，这是用实现简单换逻辑可靠的取舍。」

**Q6：缓存时间怎么定？**
> 「看数据的**变化频率和一致性要求**。**字典、参数几乎不变**→永久缓存 + 改时删；
> **验证码 2 分钟**（一次性）、**防重复提交 5 秒**（刚好挡住双击）、
> **合同详情 30 秒**（合并页面打开时那一波并发读，又不能太长否则看不到自己的修改）。
> **短 TTL 缓存是并发读优化的常用手段。**」

**Q7：编号怎么保证不重号？**
> 「编号规则拆成段存在 `conf_bill_rule_ext`，**计数器单独一张表**减少行锁冲突。
> Redis 只用来**占号**——同一用户 24 小时内复用同一个号，避免反复推进计数器。
> **不过我要老实说**：计数器自增用的是 `synchronized`，**这是 JVM 级的，多实例部署挡不住并发**。
> 正确做法是 **DB 原子自增 `SET n = n + 1`** 或 Redis `INCR` 或分布式锁。」

**Q8：为什么用 Redis 不用 Spring Cache？**
> 「其实项目**引了 Spring Cache、也配了管理器，但一个 `@Cacheable` 都没用**——
> 缓存全是手写的。手写的好处是**控制精细**（key 怎么拼、什么时候删、TTL 多少都能定），
> 代价是**重复代码多、key 命名不统一**（有的是常量、有的硬编码）。
> 而且项目还引了 `lock4j` 却没用——**准备了能力但没用上**。」

**Q9：分布式锁用了吗？**
> 「**没用**。`pom.xml` 引了 `lock4j-redisson`、配置也写了超时，但**全项目 0 处 `@Lock4j`**。
> 唯一接近的是**钉钉同步用 Redis key 做了个 15 分钟的互斥标志**，那是个土办法。」

### 5.3 一个完整的"讲一遍"示范

> 「我拿**上传一个合同附件**把存储链路串一遍。
>
> 前端 `el-upload` 打 `POST /conf/file/upload/contract`，带 token。后端 `ConfFileServiceImpl.upload()` 做四件事：
> 拼目录、**写盘**（按 `模块/年月日/uuid` 分目录）、拼 URL、**把元数据插进 `conf_file`**。
> 响应回三个字段：`url`、`fileName`、**`fileId`**——**`fileId` 是核心**，前端把它塞进文件组 JSON 一起提交给合同接口。
>
> 所以**数据库里存的是"发票"，真正的东西在"仓库"里**。业务表只认 ID，不认路径——
> **将来把磁盘换成 OSS，业务表一行都不用改**。
>
> 再说缓存。系统缓存了八类东西，最核心是**登录会话**：登录时把**权限码集合**塞进 `LoginUser`，
> 整个存进 Redis 的 `token:login:session:*`。所以**改了权限必须重登**——会话里还是旧值。
>
> 字典和参数用的是标准的 **Cache-Aside**：读时先缓存后库、写时删缓存。
> 编号规则用 Redis 只做**占号**，真正的计数器在数据库——**不过那里并发保护只有 `synchronized`，
> 多实例会有问题，这是个真实的技术债。**」

### 5.4 容易翻车的地方（面试官会追问）

| 你可能会说 | 但实际上 | 被追问会露馅 |
|---|---|---|
| 「缓存用 `@Cacheable` 做的」 | 全项目**没有一个生效的** `@Cacheable` | ❌ 去看代码就穿帮 |
| 「用了分布式锁保证编号唯一」 | **没有分布式锁**，只有 `synchronized` | ❌ 直接说"这块是技术债"更安全 |
| 「文件存在 OSS 上」 | 表叫 OSS，**实际是本地磁盘** | ❌ 说"表结构是按 OSS 设计的，落地落在本地磁盘" |
| 「URL 存在数据库里，直接访问」 | 对，**但那是绝对地址，换环境会失效** | ✅ 主动说这个缺点反而加分 |
| 「权限改了刷新页面就行」 | **必须重新登录** | ❌ 会话里的 `LoginUser` 不会自动更新 |
