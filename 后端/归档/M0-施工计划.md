### API 链路实测结果（2026-09-18 晚）

> 虚拟机开机后，用 `curl` **通过前端 devServer 的 80 端口**把整条链路跑了一遍。
> 走 80 端口而不是直连 8080 是故意的——这样才能同时验证 `vue.config.js` 里的 **devServer 代理**在真实请求下生效（而不只是配置写对了）。

| # | 验证项 | 命令要点 | 结果 |
|---|---|---|---|
| 0 | 代理生效 | `curl http://localhost/dev-api/captchaImage` | ✅ 返回后端响应，`/dev-api` 前缀被去掉并转发到 8080 |
| 1 | 中间件 + Web | `curl http://localhost:8080/captchaImage` | ✅ `{"code":200,...}`；`/actuator/health` → `{"status":"UP"}` |
| 2 | 验证码入 Redis | 从 Redis db5 读 `captcha_codes:<uuid>` | ✅ 拿到答案（本次是 `6`），证明 Redis 真的在工作 |
| 3 | 登录换 token | `POST http://localhost/dev-api/login` | ✅ `{"code":200,...,"data":{"token":"eyJ..."}}` |
| 4 | token 解出来是啥 | 解码 JWT 的 payload | ✅ `{"loginId":"00000000:sys_user:1","rn":"..."}` |
| 5 | 拉用户信息 | `GET /dev-api/getInfo`，头带 `token: Bearer <jwt>` | ✅ `permissions:["*:*:*"]`、`roles:["admin"]`、`userName:"zxcmAdmin"` |
| 6 | 拉菜单树 | `GET /dev-api/getRouters` | ✅ **25 个节点**，`name` 序列与 Task 5 记录完全一致 |
| 7 | 用户列表 | `GET /dev-api/system/user/listWithP` | ✅ `total:1` |
| 8 | 前端静态资源 | `curl http://localhost/` | ✅ HTML 标题「合同管理系统」，`app.js` / `chunk-vendors.js` 均 HTTP 200 |

**几个值得记住的观察：**

- **`loginId` 是 `00000000:sys_user:1`**，不是裸 `1`。前 8 位是租户号（`00000000` 代表系统租户），后面才是 `表名:用户id`。这是多租户设计在 token 里的体现。
- **`permissions` 返回 `["*:*:*"]`** 而不是一长串权限码——因为超管走的是**短路分支**，`SysPermissionService.getMenuPermission()` 直接返回通配符，**不查 `sys_menu`**。
  > ⚠️ **2026-09-19 更正**：我第一次讲这条时说"因为 `zxcmAdmin` 是超管"，但没讲清**怎么判定超管**。实测后确认：判定靠 `sys_user.SYSTEM_ADMIN=1` 这个**字段**（`SysUser.isAdmin()`，第 237 行），**跟 `sys_role` 表毫无关系**。`zxcmAdmin` 挂的角色是「系统管理员」「档案管理员」，它并**没有**挂名叫「超级管理员」的角色。
  > 所以「改角色权限动不了超管」——它的权限不走角色表。完整讲解见 `learning/D2-前后端调用链路.md` 第零部分 0.3。
- **`getInfo` 印证了多租户**：JWT 解出来的 `loginId` 是 `00000000:sys_user:1`，前 8 位是租户号（`00000000` = 系统内置租户），与 `sys_user.TENANT_ID` 对得上。
- ⚠️ **想验证「权限码真的来自 `sys_menu`」目前做不到**——`sys_user` 表里只有 `zxcmAdmin` 一个用户，而它必然走短路分支。要验证得先在「系统管理 → 用户管理」里新建一个普通用户并分配角色。这条同时也是验证 `v-hasPermi` 删按钮的最佳素材。
- **`listWithP` 和 `list` 都返回 `total:1`**。数字相同是因为库里只有一个用户且在数据权限范围内；二者的差别在于 `listWithP` 背后的 SQL 被 `@DataPermission` 改写过（多拼了用户可见范围的过滤条件）。
- **端口是 80，不是 81**。之前出现过 `App running at http://localhost:81/` 的漂移，那是残留 dev-server 占着 80 导致的。这次启动前先 `netstat` 确认过 80/81 均空闲，所以是干净的 80。

**仍然只能靠浏览器完成的（curl 替代不了）：**

| 待验证 | 为什么 curl 做不了 |
|---|---|
| 登录页表单交互、租户下拉框、验证码图片渲染 | 需要 JS 执行 + DOM |
| 左侧菜单真的渲染出来（而不只是接口返回了数据） | 需要 Vue 把 JSON 变成 DOM |
| Cookie 里写入 `Admin-Token` | 需要浏览器执行 `js-cookie` |
| `v-hasPermi` 指令隐藏按钮 | 需要浏览器执行指令钩子 |

```sql
-- =============================================================================
-- 清理业务菜单：以两棵框架树为「保留根」向下展开成保留集，
-- 再剔除三棵业务子树，最后删除所有不在保留集里的菜单。
-- =============================================================================

DROP PROCEDURE IF EXISTS clean_biz_menu;
DELIMITER $$
CREATE PROCEDURE clean_biz_menu()
BEGIN
    DECLARE added INT DEFAULT 1;

    -- ⚠️ 这里必须用「普通表」而不是 TEMPORARY TABLE。
    -- 实测：用临时表会在第三步闭包处直接报
    --   ERROR 1137 (HY000) at line 3275: Can't reopen table: 'tmp_biz_menu'
    -- 原因是 MySQL 不允许在同一个查询里引用同一张临时表两次，而闭包循环恰好是
    -- `INSERT INTO t SELECT ... JOIN t` 这种「目标是它、来源也是它」的形态。
    -- 普通表没有这个限制。代价是会在库里留下三张中间表，所以过程开头与结尾都
    -- DROP，保证脚本可重复执行。
    DROP TABLE IF EXISTS _zxcm_tmp_keep_menu;
    DROP TABLE IF EXISTS _zxcm_tmp_biz_menu;
    DROP TABLE IF EXISTS _zxcm_tmp_del_menu;

    CREATE TABLE _zxcm_tmp_keep_menu (MENU_ID DECIMAL(20,0) NOT NULL PRIMARY KEY);
    CREATE TABLE _zxcm_tmp_biz_menu  (MENU_ID DECIMAL(20,0) NOT NULL PRIMARY KEY);
    CREATE TABLE _zxcm_tmp_del_menu  (MENU_ID DECIMAL(20,0) NOT NULL PRIMARY KEY);

    -- ① 业务子树的根：工作交接、消息通知、消息通知记录
    INSERT INTO _zxcm_tmp_biz_menu (MENU_ID) VALUES
        (1570406241592532994),
        (1550367557167640576),
        (1550368279875579904);

    -- ② 框架子树的根：开发管理、人员组织管理
    INSERT INTO _zxcm_tmp_keep_menu (MENU_ID) VALUES
        (1),
        (1578230801211191297);

    -- ③ 业务子树向下闭包
    SET added = 1;
    WHILE added > 0 DO
        INSERT IGNORE INTO _zxcm_tmp_biz_menu (MENU_ID)
        SELECT m.MENU_ID FROM sys_menu m
          JOIN _zxcm_tmp_biz_menu b ON m.PARENT_ID = b.MENU_ID;
        SET added = ROW_COUNT();
    END WHILE;

    -- ④ 框架子树向下闭包
    SET added = 1;
    WHILE added > 0 DO
        INSERT IGNORE INTO _zxcm_tmp_keep_menu (MENU_ID)
        SELECT m.MENU_ID FROM sys_menu m
          JOIN _zxcm_tmp_keep_menu k ON m.PARENT_ID = k.MENU_ID;
        SET added = ROW_COUNT();
    END WHILE;

    -- ⑤ 保留集里剔掉业务子树
    DELETE FROM _zxcm_tmp_keep_menu WHERE MENU_ID IN (SELECT MENU_ID FROM _zxcm_tmp_biz_menu);

    -- ⑥ 待删除集合 = 全部菜单 − 保留集
    INSERT INTO _zxcm_tmp_del_menu (MENU_ID)
    SELECT m.MENU_ID FROM sys_menu m
     WHERE m.MENU_ID NOT IN (SELECT MENU_ID FROM _zxcm_tmp_keep_menu);

    -- ⑦ 先解除角色绑定，再删菜单
    DELETE FROM sys_role_menu WHERE MENU_ID IN (SELECT MENU_ID FROM _zxcm_tmp_del_menu);
    DELETE FROM sys_menu      WHERE MENU_ID IN (SELECT MENU_ID FROM _zxcm_tmp_del_menu);

    -- ⑧ 清理「菜单-业务模块」关联表里指向不存在菜单的行（该表 MENU_ID 是 varchar）
    --    条件是「不在保留集」，不是「在被删集」。实测该表除了指向本次被删菜单的行，
    --    还有 86 行指向早已不存在的菜单（2022 年遗留，例如 MENU_ID=4），只用后者
    --    会留下悬空数据。
    DELETE FROM sys_business_module_menu
     WHERE MENU_ID IS NOT NULL
       AND MENU_ID REGEXP '^[0-9]+$'
       AND CAST(MENU_ID AS DECIMAL(20,0)) NOT IN (SELECT MENU_ID FROM _zxcm_tmp_keep_menu);

    DROP TABLE IF EXISTS _zxcm_tmp_keep_menu;
    DROP TABLE IF EXISTS _zxcm_tmp_biz_menu;
    DROP TABLE IF EXISTS _zxcm_tmp_del_menu;
END$$
DELIMITER ;

CALL clean_biz_menu();
DROP PROCEDURE IF EXISTS clean_biz_menu;
```

> **为什么用 WHILE 循环而不是 `WITH RECURSIVE`**：循环版本只依赖最基本 SQL，且 MySQL 对「递归 CTE 嵌套在 `INSERT ... SELECT` 里」的支持在各小版本间并不完全一致，用循环可以避开这类坑。逐层扩散的语义也更容易在库里单步验证。
>
> **MySQL 版本：这个脚本不依赖 MySQL 8，在 5.7 和 8.0 上都能导。**
> 早期我担心建表语句带 `utf8mb4_0900_ai_ci`（MySQL 8 专有）会卡住 5.7，实测后发现：本脚本里 `utf8mb4_0900_ai_ci` 出现 **0 次**——答案册的 `修复SQL-5.7兼容.ps1` 早就把 46 处换成了 `utf8mb4_general_ci`，而我们 Task 5 是从转换后的文件里提取的。另外脚本里还有 257 处 `utf8mb3`，该写法在 5.7 和 8.0 上都被接受（8.0 里 `utf8mb3` 是 `utf8` 的旧名，会打 deprecation warning 但不影响建表）。
>
> **实测记录**：本脚本先在原虚拟机 MySQL 5.7.43 上零报错导入过（26 张表），后按用户决定把虚拟机升级到 **Docker 版 MySQL 8.0.46**，重建库后再次零报错导入，26 张表、75 个菜单、7 项核对全部通过。

### 精读时值得停下来想的三处

**① `store/modules/user.js` 的 `GetInfo` —— 前端权限的源头**

它拉回当前用户的 `roles` 和 `permissions` 数组，后续 `v-hasPermi` 指令和路由守卫都依赖它。
**这就是后端 `sys_menu.perms` 流到前端的路径**：数据库 → `/getInfo` 响应 → Vuex state → 指令比对 DOM。

**② `store/modules/permission.js` 的 `loadView()` —— 字符串怎么变成组件**

```js
export const loadView = (view) => {
  if (process.env.NODE_ENV === 'development') {
    return (resolve) => require([`@/views/${view}`], resolve)   // ← 注意这个写法
  } else {
    return () => import(`@/views/${view}`)
  }
}
```

后端返回的菜单里 `component` 是**字符串**（如 `"system/user/index"`），靠这两行才能变成真的 Vue 组件。
⚠️ 开发模式下的那句 `require([...])`（把路径写成**数组 + 模板字符串**）会让 webpack 为**整个 `@/views/` 目录**建立上下文——**目录下每个文件都会被打进包**。这意味着：只要 `views/` 里残留任何文件，它就会被编译；反过来，想「精简前端」就不能靠删 `views/` 里的文件，得连引用一起清。这也是当初决定「整包复制答案册」而不是「手工裁剪」的技术原因之一。

**③ `permission.js` 的 `next({ ...to, replace: true })` —— 动态路由最经典的坑**

```js
router.addRoutes(accessRoutes)   // 动态注入路由
next({ ...to, replace: true })   // ← 必须重新进入一次
```

若这里直接 `next()`，刚注入的路由尚未生效，会命中 404。细节见 D2 文档链路③。

在 `SaInterfaceImpl.getPermissionList()` 第一行打断点，以 Debug 模式启动后端，浏览器登录。断点命中后：

```bash
# 另开终端，看 Redis 里的 token（虚拟机 Redis 设了密码 root）
redis-cli -h 192.168.56.10 -a root -n 5 KEYS "token*"
```

> 这一步把"Sa-Token 用 Redis 存会话"从文档上的话变成你亲眼看到的事实。Redis 用的是 `database: 5`，所以必须加 `-n 5`。
>
> ⚠️ **订正（2026-09-26 实测）**：前缀是 **`token:`** 不是 `satoken:`。Sa-Token 默认值确实是 `satoken`（网上文章大多这么写），但本项目 `application.yml:103` 把 `sa-token.token-name` 设成了 `token`，而 Redis key 前缀用的就是这个值。**照抄 `satoken*` 会一条都查不到。**
>
> 实测一次 `zxcmAdmin` 登录会落下 **5 个 key**：`token:login:token:<JWT>`（token→loginId）、`token:login:token-session:<JWT>`（含 `loginUser` 和 `menuPermission`）、`token:login:last-activity:<JWT>`、`token:login:session:00000000:sys_user:1`（账号级，含 `tokenSignList`）、`online_tokens:<JWT>`。每个 key 的含义见 `learning/D1-SaToken鉴权链路.md` 的 1.5 节。
