## M3 做完是什么样

| 页面 | 能做什么 |
|---|---|
| 模板管理 → **草稿箱** | 新建模板：上传 Word、定义**条款**库、插入**元素**（占位符）、挂附件 |
| 模板管理 → **已发布列表** | 把草稿发布成正式模板；创建新版本；停用 |
| 模板管理 → **已停用列表** | 重新发布 |
| 合同草拟 → 新建合同 | 选一个已发布模板 → **生成合同文件** → 浏览器里直接改 → 保存 |

**主链位置**：

```
      【M3 就是这一段】
  模板草稿 → 发布 → 已发布模板
                        ↓
    合同草拟时选模板 → 生成 Word 文件（contract_draft_files）
                        ↓
        OnlyOffice 在线编辑 → 回调保存 → 原地覆盖源文件（不新增版本）
                        ↓
                    提交审批（M2）
```

## ★ 先看懂这一节 ★

### 模板不是一个"文档"，是一套结构

新手会以为「模板 = 一个 Word 文件」。**这个项目的模板是 7 张表拼出来的**：

| 表 | 存什么 | 类比 |
|---|---|---|
| `template_contract` | 模板本体（名称、类型、版本、状态） | 模板的"壳" |
| `template_element` | **元素**：`{{甲方名称}}` 这种占位符 | Word 里的"域" |
| `template_clause` | **条款**：可复用的段落（保密条款、违约责任…） | 段落零件库 |
| `template_clause_type` | 条款分类 | 零件的分类目录 |
| `template_link_relation` | 模板 ↔ 元素/条款 的关联 | 拼装关系 |
| `template_scope` | 模板适用范围（哪些部门/角色能用） | **权限** |
| `template_attachment` | 附件（模板附带的参考文件） | 附件 |

**为什么这么拆？** 因为要支持「**同一套条款，换个模板复用**」。如果模板就是一个 Word 文件，改一处要在每个文件里改一遍。拆成表之后：

```
模板A ─┐
       ├─→ 引用「保密条款」这一条记录
模板B ─┘
```

改「保密条款」的记录，A 和 B 同时变。**这是"模板引擎"的价值，也是它比"存个 Word 文件"复杂得多的原因。**

> 💡 **一句话说人话**：**模板不是一个 Word 文件，是一份"配方"**——正文是 Word 文档，其中"哪些字要按合同数据替换（元素）、哪些整段可以复用（条款）、谁能用（范围）"分别存在不同的表里，靠 `template_link_relation` 拼起来。所以「改一处、引用它的所有模板跟着变」才成立。

> 面试点：「你的模板功能怎么做的？」→ 说「拆成模板/元素/条款/关联/范围五类表，条款可跨模板复用」比说「我存了一个 Word 文件」高一个层级。

### 文档生成 = 模板 + 数据 → Word

```
template_contract（模板文件，带 {{占位符}}）
        +
contract_draft（合同数据：金额、甲乙方、日期…）
        ↓  替换占位符
生成的 Word 文件
        ↓  存进 contract_draft_files（一份合同可以有多个版本）
        ↓  打开 OnlyOffice 编辑
```

`contract_draft_files` 这张表就是**文件版本表**——一份合同可以有 V1.0 / V1.1 / V1.2 多个文件版本。

## 📊 M3 用到的技术 & 表

### 技术清单

| 技术 | 在 M3 里干什么 | 关键点 |
|---|---|---|
| **OnlyOffice Document Server** | 浏览器里编辑 Word（真正的编辑器是**另一个服务器**） | 不是库，是**独立部署的服务**（Docker） |
| **JWT** | OnlyOffice 回调本系统时的**身份验证** | 回调接口没有用户 token，只能靠共享密钥验签 |
| **HTTP 回调（Webhook）** | 编辑完通知本系统保存 | 保存动作由**第三方服务器**发起，不是用户浏览器 |
| **POI / 文档处理** | 把 `{{占位符}}` 替换成合同数据 | 生成合同文件 |
| **文件版本管理** | 合同文件的开新版本（`contract_draft_files.FILE_GROUPS_VERSION`）| ⚠️ **不是** OnlyOffice 保存回调干的 —— 回调是**原地覆盖**（见第五节）|
| **WPS WebOffice** | **旧实现**（代码还在，已不可用） | 靠 `onlineEditor` 开关切换，属技术债 |

### M3 的表：7 张 template_* + 2 张文件表

| 表 | 列数 | 干什么 | **为什么这么建** |
|---|---|---|---|
| `template_contract` | 27 | 模板本体 | 名称 + 类型 + **版本号** + **状态**（草稿/已发布/已停用）。版本和状态是分开的两列——**改内容开新版本，不要了是停用，都不删** |
| `template_element` | 16 | **元素** | `{{甲方名称}}` 这类占位符的定义（名称、key、类型）。**位置信息不在数据库里**——元素在 Word 里的位置由文档本身决定，数据库只登记"有这些元素" |
| `template_clause` | 16 | **条款** | 可复用的段落（保密条款、违约责任……）。**这是能跨模板复用的关键** |
| `template_clause_type` | 11 | 条款分类 | 条款的目录树（和 `form`、`sys_menu` 一样是自关联树） |
| `template_link_relation` | 10 | **关联表** | 模板 ↔ 元素/条款 的多对多。**这张表就是"模板引擎"的核心**（见下） |
| `template_scope` | 12 | 适用范围 | 哪些部门/角色能用这个模板。`getLoginerCanUseTemplate` 按它过滤 |
| `template_attachment` | 13 | 模板附件 | 模板附带的参考文件 |
| `contract_draft_files` | 17 | **生成的文件** | `FILE_GROUPS_VERSION`（`V1.0`）+ `FILE_GROUPS_JSON`。**一份合同多个文件版本**（M1 已建，M3 开始用） |
| `conf_file` | 12 | 文件元数据 | 统一文件表，`MODULE` 列区分来源；**`ONLYOFFICE_KEY` 是回调时找到文件的凭据** |

### ★ 为什么模板要拆成 7 张表（本里程碑的核心设计）

**新手以为「模板 = 一个 Word 文件」，这个项目把它拆成了 7 张表：**

```
template_contract（壳：名称/版本/状态）
        │
        ├── template_link_relation ──┬── template_clause ──── template_clause_type
        │        （多对多关联）        │      （段落零件）          （零件分类）
        │                             │
        │                             └── template_element
        │                                    （占位符定义）
        ├── template_scope    （谁能用）
        └── template_attachment（附件）
```

**收益：条款跨模板复用。**

```
模板A ─┐
       ├─→ 都引用「保密条款」这**一条记录**
模板B ─┘
```

改「保密条款」这条记录，A 和 B 同时变。**如果模板就是一个 Word 文件，改一处要在每个文件里改一遍。**

> 🎯 **面试点（高频题：「你的模板功能怎么做的？」）**：
> - ❌ 弱答：「上传一个 Word，填占位符。」
> - ✅ 强答：「拆成**模板 / 元素 / 条款 / 关联 / 范围**五类表，条款是独立实体、可跨模板复用，用 `template_link_relation` 做多对多关联。」
> - 🏆 加分：「这样拆的代价是**结构复杂**（7 张表、一次保存要写多表），只适合**条款复用**是真实需求的场景。如果模板只是内部几个固定文档，存 Word + 占位符就够了，**别过度设计**。」
>
> **能说出「什么时候不该这么拆」比背结构更能体现判断力。**

### 另外两条 M3 的表设计规律

1. **"被引用过的东西"一律版本化或软删除**——`template_contract` 的 `VERSION` + `VERSION_SHOW` + `STATUS`、`contract_draft_files` 的 `FILE_GROUPS_VERSION`、M2 的 `contract_his`（快照的设计意图）。**这条规律从 M1 一路串到 M4**（[M1 已点过](M1-基础数据与合同CRUD（总览）.md#另外三个跨表规律记住能串起-m1-m4)）。
   **为什么？** 因为模板被合同引用。直接改模板内容，**已经用旧模板生成的合同就对不上了**。
2. **`conf_file` 是全项目统一的文件表**，M3 的模板文件、M1 的合同附件、M4 的双章合同**都存它**，靠 `MODULE` 列区分来自哪个业务。
   > 好处：文件上传/下载/预览**只有一套代码**；代价：这张表会成为热点，且业务侧要自己保证 `MODULE` 值不写错。

✅ **验证**：进「模板管理 → 草稿箱」，能新建一个模板、上传 Word、列表出数。

```sql
SELECT ID, TEMPLATE_NAME, STATUS, VERSION FROM template_contract;
-- ⚠️ 列名是 STATUS / VERSION，不是 TEMPLATE_STATUS / TEMPLATE_VERSION（写错会报 Unknown column）
```

🧠 **原理 · `editjson` 是什么**

`POST /template/templateDrafts/editjson` 收一个 `TemplateJsonBo` —— 里面是 **JSON 数组**，描述「这份模板由哪些条款、哪些元素、按什么顺序组成」。

**为什么用 JSON 而不是多次调用接口逐条存？** 因为前端编辑器里用户是**一次性编辑完整个结构再保存**的。逐条存要么中途失败留下半成品，要么需要一整套增量同步协议。**用一个 JSON 一次性覆盖**：要么全成功，要么全失败（配合 `@Transactional`）。

> 面试点：这是「**聚合根**」思想的朴素用法——把「模板+条款+元素」当成一个整体来保存，而不是三个独立的 CRUD。

| 方法 | URL | 权限码 | 用途 |
|---|---|---|---|
| GET | `/template/templateDrafts/publish/{id}` | `template:templateDrafts:publish` | 草稿 → 已发布 |
| GET | `/template/templatePublish/list` | `template:templatePublish:list` | 已发布列表 |
| GET | `/template/templatePublish/stop/{id}` | `template:templatePublish:stop` | 停用 |

| GET | `/template/templatePublish/changeVersion` | `template:templatePublish:versionList` | 切换版本 |
| GET | `/template/templateStop/rePublish/{id}` | `template:templateStop:rePublish` | 重新发布 |

📋 **复制清单**：`controller/TemplatePublishController.java` + `TemplateStopController.java` + `TemplateAuditController.java`（已在 T1 的 54 个文件里）+ 前端 `api/template/{templatePublish.js, templateStop.js, templateAudit.js}` + `views/template/templatePublish/**` + `views/template/templateStop/**`

**数据库**：无需新增（复用 T1 的表）

✅ **验证**
```sql
SELECT TEMPLATE_NAME, STATUS, VERSION, VERSION_SHOW FROM template_contract ORDER BY UPDATE_TIME DESC;
-- 发布后 STATUS 变 '1'；新建版本后 VERSION 递增；生效版本那行 VERSION_SHOW='1'
-- ⚠️ 列名是 STATUS / VERSION，不是 TEMPLATE_STATUS / TEMPLATE_VERSION
```

> 📌 **「哪个版本生效」不是"版本号最大的那个"**，而是 `VERSION_SHOW='1'` 的那一行。同一个 `TEMPLATE_CODE` 下可以有多行（多版本），**但只有一行 `VERSION_SHOW=1`**；`POST /template/templatePublish/changeVersion` 做的就是「把同编码的所有行置 `VERSION_SHOW=0`、把选中的那行置 `1`」。
> 📌 `STATUS`：`0` 未发布 / `1` 已发布 / `2` 已停用。另有一个 `PUBLISHED`（`0`/`1`）列跟 `STATUS` **语义重叠**——停用方法 `realStop` 会把 `PUBLISHED` 也置 `1`，容易不一致，是个已知的小技术债。
> 📌 **模板编号 `TEMPLATE_CODE`（形如 `TEM-年-流水`）是"发布时"才生成的**，走编号规则 `TEMPLATE_RULE`（`getBillNumber("TEMPLATE_RULE", ...)`）——所以**刚新建的草稿还没有编号**，这是正常的。

🧠 **原理 · 为什么模板要"版本 + 停用"而不是直接改**

因为**模板被合同引用**。如果直接改模板内容，已经用旧模板生成的合同就对不上了。

```
模板 V1.0 ──引用──→ 合同A（2026-03 生成）
                      ↑ 改模板V1.0会污染这个
模板 V1.1 ──引用──→ 合同B（2026-09 生成）
```

所以正确做法是：**改内容 → 建成新版本 V1.1**，老合同继续指向 V1.0。同理「停用」而不是「删除」——停用后新合同选不到，但老合同还能打开。

> **这套「版本 + 停用」的模式在 M1 就见过一次**：`contract_draft_files` 的文件版本、M2 的 `contract_his`（合同快照——表建了、开源版主流程没往里写，见 [M2 T3](M2-审批流与事件状态机（总览）.md)），都是同一个思路。
> **面试点**：如果你能说出「这个系统里所有'被引用过的东西'都用版本或软删除，从不就地修改」，面试官会觉得你读懂了系统而不是只做完了功能。M1 的签约主体、合作方、这里的模板、合同文件，**一条规律串到底**。

```yaml
  domain: http://192.168.0.100     # ← OnlyOffice Document Server 地址
  port: 8081
  callbackUrl: http://192.168.0.10:8080/onlyofficeCallback   # ← 必须让 OnlyOffice 服务器能访问到本系统
  secret: zxcm                     # ← 必须和 OnlyOffice 服务端 local.json 里的 secret 一致
```

▶️ **操作步骤**

这一步**必须先有一个 OnlyOffice Document Server**。三种选择：

| 方案 | 说明 | 适合 |
|---|---|---|
| **A. 不装，跳过 T3** | M1/M2/M4 不受影响，只是不能在线编辑 | ✅ **推荐先这样** |
| B. 虚拟机里 Docker 起一个 | `docker run -i -t -d -p 8081:80 onlyoffice/documentserver` | 想把 M3 做完整 |
| C. 用公共服务 | 有网络限制和安全风险 | 不推荐 |

选 B 的话，改 `application-dev.yml` 的 `domain` 为虚拟机 IP、`prometheus` 不用管、`secret` 两边保持一致。

✅ **验证（选 B 时）**
```bash
curl -s -o /dev/null -w "%{http_code}\n" http://192.168.56.10:8081/   # 预期 200
```
然后合同草拟里点在线编辑，浏览器里能出 Word 编辑器，改完保存后：

```sql
SELECT * FROM contract_draft_files WHERE CONTRACT_ID='<合同ID>' ORDER BY CREATE_TIME DESC;
-- 预期多一个文件版本
```

🧠 **原理 · OnlyOffice 的「回调」是全部难点**

**关键在于：编辑发生在 OnlyOffice 服务器上，不在你的服务器上。**

```
① 前端向你的后端要配置：GET /wps/weboffice/getConfig
   你的后端返回：{ 文档地址, 回调地址, JWT 签名, ... }
        ↓
② 前端把这段配置交给 OnlyOffice 的 JS SDK，它去 OnlyOffice 服务器
   打开一个 iframe 显示文档
        ↓
③ 用户在 iframe 里改文档。改的内容存在 OnlyOffice 服务器上
        ↓
④ 用户关闭 / 定时触发 → OnlyOffice 服务器 POST 你的 callbackUrl
   → 你的 /onlyofficeCallback/save 收到通知
        ↓
⑤ 你的后端**回调去 OnlyOffice 下载改好的文件**，**原地覆盖**本地源文件 +
   刷新 `conf_file.ONLYOFFICE_KEY`（★ 不新增 `contract_draft_files` 版本行）
```

**三个必然踩的坑**：

1. **`callbackUrl` 必须是 OnlyOffice 服务器能访问到的地址**。写 `localhost:8080` 一定失败——那是 OnlyOffice 自己的 localhost。
2. **JWT 签名两边必须一致**。`secret: zxcm` 要和 OnlyOffice 服务端 `local.json` 里的 `secret` 完全相同，否则所有回调被拒（表现是「改了但保存不了」）。`DefaultJwtManager` 就是干这个的。
3. **回调接口必须免鉴权**。`/onlyofficeCallback/**` 要加到 `application.yml` 的 `security.excludes` 里——它是 OnlyOffice 服务器在调，**没有你的 token**。
   > 这是个典型的「安全 vs 可用」权衡：回调接口不能带用户 token，所以只能靠 **JWT 签名验证来源**（而不是靠用户身份）。这也是为什么 `secret` 不能泄露。

> 💡 **`wps` 包为什么还在但"已不可用"**：看配置注释——WPS 是早期接口，后来换成了 OnlyOffice。**但作者没有删掉 wps 包**，而是留了一个 `onlineEditor` 开关做切换。
> 面试点：这种「保留旧实现 + 开关切换」是**保守的工程习惯**（回滚成本低），代价是代码库里有两套做同一件事的代码。你可以讲这个 trade-off，但不建议在学习项目里学它——**在主分支留死代码是负债**。

## M3 踩坑预警

| 症状 | 大概率原因 |
|---|---|
| 合同草拟的模板下拉框是空的 | `getLoginerCanUseTemplate` 会**按 `template_scope` 过滤**——当前用户不在模板适用范围内。要么给模板配范围，要么用超管测 |
| 模板发布后合同里选不到 | 模板状态不是「已发布」，或版本不是最新 |
| 在线编辑打开是空白 | OnlyOffice 服务器地址写错 / 没起来。先 `curl` 那个地址 |
| 编辑能改但保存不了 | JWT `secret` 两边不一致（看后端日志有没有 401/403 回调） |
| 回调根本没进来 | `callbackUrl` 写成了 `localhost` —— OnlyOffice 服务器访问不到你的 `localhost` |
| 回调报 401 | 忘了把 `/onlyofficeCallback/**` 加进 `security.excludes`（本项目 `application.yml` 里默认已加） |
| 模板文件里 `{{占位符}}` 没被替换 | 元素名和占位符文本不一致（大小写、空格） |
| 回调日志报 `{"error":1,"message":"JWT validation failed"}` | `DefaultJwtManager` 验签失败——`onlyoffice.secret` 与 OnlyOffice 端 `local.json` 的 secret 不一致 |
| 编辑/保存提示「该文档不允许修改」 | `SaveCallback` 会校验合同状态**必须是 `draft(0)` 或 `audit(3)`**，其他状态（已履行/已作废等）不允许在线改 |
| 运行期报 `Invalid bound statement (not found)` | **没拷 `resources/mapper/template/*.xml`**（`selectLinkTemplateName` / `selectScopeList` 只有 XML 实现，编译能过、跑起来才炸） |
| 发布/版本列表报 500 `Table 'zxcm.TEMPLATE_CONTRACT' doesn't exist` | XML / Service 里用了**大写表名**，`lower_case_table_names=0` 的库必炸 → 改小写 |
| 拿不到文档模型 / 编辑器初始化缺数据 | `getConfig` 只回 `fileName/editorType/fileType`；**带 `onlyofficeModel` 的是 `geturl`**，别调错接口 |
| 每次打开编辑器都像"新会话" | 正常。`geturl` 里 `onlyofficeKey` 为空会**重新生成**，所以每次打开 key 都变 |

## 🎤 怎么对面试官讲

> 被问到 M3 时，围绕「模板是版本化的结构」和「OnlyOffice 的回调难点」两句展开：
>
> 「M3 做的是**模板体系 + 文档生成**。我先把一个容易被误解的点讲清楚：**模板不是一个 Word 文件，是一套版本化的结构**——我用 7 张表把它拆开：主表管版本、元素表管占位符、条款表管可复用片段、范围表管谁能用，用 `template_link_relation` 做多对多关联。
> 发布时**生成模板编号、把生效版本标记成 `VERSION_SHOW=1`**；改内容一律**开新版本**而不是覆盖——这样**已经基于它生成的合同引用的旧版本就不受影响**，这就是『不可变 + 版本指针』，和代码打 tag 是一个道理。
> 技术上最难的其实是 **OnlyOffice 在线编辑**：难点不在 Java，在**回调协议**。编辑器是**另一个独立部署的服务**（Docker），改完由**它反向回调**我的后端，所以 `callbackUrl` 必须双向可达（不能写 `localhost`）；回调又**不带用户登录态**，项目用『把打开者的 sa-token 编进回调 URL + `secret` 做 JWT 验签』来兜。
> 我读代码时还注意到一个分工：**保存回调只把文件原地覆盖并刷新 key，不新增版本行**——版本递增是合同模块的事，不在这条回调链里，能说清这个前后端分工，比说『我集成了 OnlyOffice』更实在。」
