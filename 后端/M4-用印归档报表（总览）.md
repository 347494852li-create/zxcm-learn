**M1-M3 是「照答案册复制」，M4 不是——答案册里有一部分代码根本不存在。**

我核对过答案册的 `zxcm-contract/src` 和 `zxcm-ui/src`，M4 的功能分成三类：

| 类别 | 功能 | 后端 | 前端页面 | 你能做什么 |
|---|---|---|---|---|
| **A. 完整** | 用印申请、上传双章合同、合同作废、合同报表 | ✅ Controller 有 | ✅ 页面有 | **直接复制，和 M1-M3 一样** |
| **B. 半成品** | 合同续签 | ✅ 接口有 | ⚠️ 融在审签跟踪页里，无独立页面 | 复制接口，前端入口在已有页面里 |
| **C. 只有服务层** | **归档、借阅、工作交接** | ⚠️ **只有 Service，没有 Controller** | ❌ **完全没有** | **需要你自己补 Controller + 页面** |

## M4 做完是什么样

```
审批通过（CONTRACT_STATUS 仍是 '3'，另置 CONTRACT_APPROVE_STATUS='2'；'4'/'5' 是死状态，别当真）

   ↓       ↓           ↓              ↓

（'6'）  （'2'）   （只改 END_TIME）
   ↓
合同报表（按各种条件统计）
```

## 📊 M4 用到的技术 & 表

### 技术清单

| 技术 | 在 M4 里干什么 | 关键点 |
|---|---|---|
| **印章/用印流水** | 记录「谁在何时给哪份合同用了哪个章」 | 用印是**不可撤销的法律行为**，所以流水表只增不改 |
| **Excel 导出（EasyExcel）** | 合同报表导出 | 大数据量要分批写，别一次 load 进内存 |
| **统计专用 Mapper** | 报表聚合查询（`COUNT`/`SUM`/`GROUP BY`） | 和业务 Mapper 分开（见下） |
| **合同自关联** | 续签：新合同指向原合同 | `RELATED_CONTRACT_ID` 指自己这张表 |
| **电子签章** | ⚠️ **本项目没有**，盖章是**线下**做的 | 系统管的是「流程 + 留痕」，不是「真盖上去」。要做电子签就替换这一步 |

### ★ M4 四条「表设计」的规律（面试前必背）

**1. 用印为什么单独一套表，而不是在合同表加个字段**

因为**一家公司有多个印章**（公章、合同专用章、法人章、财务章），每个章有**保管人**和**使用记录**：

- `contract_seal` —— 印章/申请本体
- `contract_seal_notes` —— **用印流水**（谁、何时、给哪份合同、用了哪个章）

**「notes」这张流水表是关键**：用印是不可撤销的法律行为，出事要追溯责任。**它和 M2 的 `contract_point_log` 是同一类东西——不可篡改的流水。**

> 💡 **一句话说人话**：**"用印"= 给合同盖公章这件事本身要留痕**。所以要像记账一样，每盖一次记一笔（`contract_seal_notes`），而不是只在合同表上打个"已盖章"的勾——**因为出了纠纷要能回答"这个章是谁拿去盖的"**。

**2. 作废为什么用多个列（宽表冗余）**

`contract_draft` 上和作废有关、**真正被 `cancelContract` 写**的是**两个**（外加一个前端标记列）：

| 列 | 用途 | `cancelContract` 是否写 |
|---|---|---|
| `CONTRACT_STATUS='2'` | **列表过滤**（"显示所有已作废的合同"） | ✅ 写 |
| `CONTRACT_CANCEL_REMARK` | 存原因，用于追责 | ✅ 写 |
| `CONTRACT_CANCEL='1'` | **布尔标记**，前端控制「作废」按钮的显示/禁用 | ❌ **不写**（遗留） |

**为什么不合成一个？** 因为查询快、前端判断简单（比判断状态字符串直白）。**代价是冗余——理论上有不一致的风险。**

> 🎯 面试问「为什么不用一个状态字段」→ 答：「**查询性能 + 前端判断简单，代价是冗余和不一致风险**，所以配套了事件日志（`contract_point_log`）作为对账依据。」
> **注意这个答法的结构：先说好处，再说代价，最后说怎么兜底。** 只讲好处会被追问到死。
> ⚠️ 提"宽表"时说**两个真正被写的列**即可 —— `CONTRACT_CANCEL` 在开源流程里没回填。

**3. 续签为什么不在原合同上改**

```
续签的完整语义 = 新建一份 contract_draft + 用 RELATED_CONTRACT_ID 指向原合同
```

**因为原合同已经签署、已经履行过、可能已经归档**——它是有法律效力的**既成事实，不能动**。

`contract_draft` 上为此准备了一组列：
`RELATED_CONTRACT_ID` / `_NAME` / `_CODE`（关联到哪份合同）、`RELATED_TYPE`（关联类型）、`RENEWAL` / `RENEWAL_TEXT`（是否续签）、`renewed_status`（续约状态）。

> ⚠️ **但开源版只实现了"延期"那一半**：后端 `renew` 接口**只改原合同的 `END_TIME`**，
> **不建新合同、不写 `RELATED_CONTRACT_ID`**；"新建合同 + 关联"的语义在前端一个**没接线**的方法里（`createContract.vue:renew`）。
> 讲设计意图时可以说"续签应当不改原合同"，但别声称"这个项目的续签新建了合同"。

> 🏆 **「历史不可变」这条规律在 M4 里出现第 3 次了**：**作废不删、模板不就地改、续签不原地改**。
> 面试时把这一条作为**整个系统的设计哲学**讲出来，比讲十个 CRUD 都有说服力。

**4. 报表为什么单独一个 Mapper（设计意图）**

`ContractDraftStatMapper` 的**设计意图**是统计查询**单独一个 Mapper**，不塞进 `ContractDraftMapper`：

| | 业务 SQL（`ContractDraftMapper`） | 统计 SQL（`ContractDraftStatMapper`） |
|---|---|---|
| 查什么 | 具体合同记录（列多） | 聚合结果（`COUNT`/`SUM`/`GROUP BY`） |
| 有没有索引 | 有（`CONTRACT_STATUS` 等） | 全表扫是常态 |
| 用在哪 | 页面列表 | 报表页 |
| 怎么优化 | 加索引 | 加缓存 / 预计算 / 物化视图 |

> ⚠️ **实测纠正**：合同报表页（`ContractBookController`）**走的是 `ContractDraftMapper.bookPage` / `bookList`**，
> **不是 `ContractDraftStatMapper`**。后者里大多是注释掉的 SQL + 争议/案件统计，这个页面**没调用它**。
> 讲"按变化原因分离"这条原则没问题，但**别说"这个报表用的是 StatMapper"**。

**分开写，将来优化统计查询只动一个文件，不影响业务流程。** 这是「**按变化原因分离**」——同一个表，两类用途，两个 Mapper。

> 📌 这条规律在 M2 也出现过一次（Activiti 的 `ACT_RU_*` 和 `ACT_HI_*` 按生命周期分表）。**「按变化原因分离」是贯穿整个系统的第二条主线**（第一条是「历史不可变」）。

🖥 **前端入口**：**合同管理 → 审签跟踪** → 某条合同 → 「上传双章合同」（★ 没有「申请用印」按钮了，旧流程已废弃）

📋 **复制清单**（M2 时 `ContractAuditController.java` 已经复制过了，如果 M2 做过就直接能用）

| 补充文件 | 说明 |
|---|---|

> ⚠️ **注意权限码不是 `:edit` 而是 `:uploadStampedContract`**。这说明**上传双章合同是一个独立授权点**——有的角色能改合同草稿，但不能上传盖章件（因为盖章件是法律效力凭证）。**权限设计到这里已经是「按业务动作」而不是「按增删改查」了**。

✅ **验证**

```sql
SELECT ID, CONTRACT_CODE, CONTRACT_STATUS, CONTRACT_STAMPED_STATUS,
       CONTRACT_REVIEW_STATUS, SEAL_FILES_ID, CONTRACT_STAMPED_TIME
  FROM contract_draft WHERE ID='<合同ID>';
-- 上传双章后：CONTRACT_STATUS='6'(履行中)，STAMPED_STATUS='2'，REVIEW_STATUS='6'，STAMPED_TIME 有值
SELECT * FROM contract_seal WHERE CONTRACT_ID='<合同ID>';
-- ⚠️ 预期为空 —— 主流程不写这张表
```

🧠 **原理 · 为什么"用印"要单独一套表**

因为**一家公司可能有多个印章**（公章、合同专用章、法人章、财务章），每个印章有**保管人**和**使用记录**。

- `contract_seal` —— 印章本体（章名、图样、保管人、状态）
- `contract_seal_notes` —— **用印记录**（谁、什么时候、给哪份合同、用了哪个章）

**"notes" 这张流水表是关键**：用印是不可撤销的法律行为，出事要能查到「这个章是谁盖的」。所以**用印记录和 M2 的 `contract_point_log` 一样，是不可篡改的流水**。

> 🔴 **但开源版的"用印"是精简过的**：主流程 `uploadSealContract` **只接收线下盖好的双章文件 +
> 把合同状态推到"履行中"**，**不写 `contract_seal` / `contract_seal_notes` / `contract_review` 三张表**（用印 + 复核被合并成一步自动完成）。
> 这三张表是**旧流程 / 商业版的遗留**。旧流程 `applyStamp`（已 `@Deprecated`）才涉及"用印申请单 + 流水"，但**它现在是死代码**：

```
applyStamp（旧流程，已废弃）：
① 校验合同状态（必须审批通过）
② 生成一份「用印申请单」
③ 把合同文件导出成待盖章版，放到特定目录
④ 通知印章保管人
⑤ 写一条 contract_seal_notes 流水
```

**主流程 `uploadSealContract` 的真实动作**（对照 `ContractAuditServiceImpl` 实测）：

```
① 校验 fileGroupsId 非空 → 否则「合同的文件不能为空」
② 查合同；状态必须是三者之一（approved / signing / reviewFailed），否则「当前合同未审批通过，不能上传双章合同」
③ 生效时间必传（「合同生效时间不能为空」）；END_TIME_TYPE='fixed' 必须有截止时间（「合同截止时间不能为空」）；
   截止时间早于生效时间会报「合同截止时间不能小于生效时间」；'open'（无固定期限）忽略截止时间
④ 双章文件里必须有一个正文（type='0'），否则「必须选择一个合同作为双章正文」
⑤ 把双章文件存成 contract_draft_files 里 FILE_TYPE_SEAL('2') 的一组，并回填 contract_draft.SEAL_FILES_ID
⑥ 回填负责人 / 生效时间 / 截止时间
⑦ 一次性推进四个状态（★ 核心）：CONTRACT_STAMPED_STATUS='2'（签署完成）、CONTRACT_STAMPED_TIME=now、
   CONTRACT_REVIEW_STATUS='6'（复核通过）、CONTRACT_STATUS='6'（履行中 / fulfil）← ★ 不是 '5'
⑧ 更新审批单当前节点为「履行中 / 合同负责人」
⑨ 发通知「用印完成」给拟稿人
⑩ 发三个事件：uploadSeal / sealPass / reviewPass（★ 事件日志由此记录）
```

> 💡 **一句话说人话**：**开源版把"用印 + 复核"合并成一步"自动完成"**。上传双章文件时，代码顺手把"用印状态=签署完成""复核状态=通过""合同状态=履行中"三个字段一起写好——**所以 `contract_seal` / `contract_seal_notes` / `contract_review` 这三张表在主流程里根本没被写过**。

**盖章是线下做的**，系统管的是「流程 + 留痕」，不是「真的盖上去」。如果你以后要做**电子签章**（第三方电子签名服务），替换的就是这一步。

## T2 · 合同作废（A 类）

🎯 **目标**：已签署的合同能作废，且**必须填作废原因**。

🖥 **前端入口**：审签跟踪 → 「合同作废」，页面 `views/contract/contractAudit/contractCancel.vue`

🔌 **接口入口**：`POST /contract/contractAudit/cancelContract`

📋 **复制清单**：`domain/bo/ContractDraftBo.java` 里的作废字段 + 前端 `contractCancel.vue`

✅ **验证**：作废后 `CONTRACT_STATUS='2'`，且 `CONTRACT_CANCEL_REMARK` 有原因。

```sql
SELECT CONTRACT_STATUS, CONTRACT_CANCEL, CONTRACT_CANCEL_REMARK
  FROM contract_draft WHERE ID='<合同ID>';
-- CONTRACT_STATUS='2'，CONTRACT_CANCEL_REMARK 有原因；CONTRACT_CANCEL 不变（★ 不写）
```

🧠 **原理 · 作废为什么不用「删除」**

看 `contract_draft` 上和作废有关、**真正被 `cancelContract` 写**的是**两个**：`CONTRACT_STATUS='2'`、`CONTRACT_CANCEL_REMARK`（还有一个前端标记列 `CONTRACT_CANCEL`，开源流程**没回填**）。

**为什么不全塞进一个状态列？** 因为：
- `CONTRACT_STATUS` —— 用于**列表过滤**（"显示所有已作废的合同"）
- `CONTRACT_CANCEL` —— 一个**布尔标记**，前端控制"作废"按钮的显示/禁用（比判断状态字符串快、语义直白）（⚠️ 本项目**未写**）
- `CONTRACT_CANCEL_REMARK` —— 存原因，用于追责

**一张表里同一个概念用多种方式表达，是宽表设计的典型特征。** 好处是查询快、代码直白；坏处是**冗余**——理论上这几列可以不同步。
> 面试点：如果被问「为什么不用一个状态字段」，答：「查询性能 + 前端判断简单，代价是冗余和不一致风险，所以配套了事件日志（`contract_point_log`）作为对账依据。」

## T3 · 合同续签（B 类）

🎯 **目标**：快要到期的合同，延长截止时间（完整语义是"基于原合同生成一份新合同"，但开源版只做了"延期"）。

🖥 **前端入口**：审签跟踪页内（`views/contract/contractAudit/auditList.vue` 里有续签入口），**没有独立的续签页面**；⚠️ 而且 `api/contract/contractAudit.js` 里**没有 `renew`/`renewInfo` 函数** → 这两个接口**没有前端调用者**

🔌 **接口入口**

| 方法 | URL | 用途 |
|---|---|---|
| GET | `/contract/contractAudit/renewInfo/{contractId}` | 取原合同信息（`END_TIME` +1 年，预填用）|
| POST | `/contract/contractAudit/renew/{contractId}` | 发起续签（**只改 `END_TIME`**）|

✅ **验证**：续签后**只有原合同的 `END_TIME` 变了** —— ⚠️ **不生成新合同**。

```sql
-- 原合同：END_TIME 被改成新值；CONTRACT_STATUS 不变
SELECT CONTRACT_CODE, CONTRACT_STATUS, END_TIME FROM contract_draft WHERE ID='<原合同ID>';
-- ⚠️ 预期查不到"新合同"（开源版 renew 不建新合同）
SELECT ID, CONTRACT_CODE, RELATED_CONTRACT_ID FROM contract_draft
 WHERE RELATED_CONTRACT_ID='<原合同ID>';
```

🧠 **原理 · "关联合同"是怎么表达的（★ 但开源版没实现）**

`contract_draft` 上为"关联合同"准备了一组列：

| 列 | 含义 |
|---|---|
| `RELATED_CONTRACT_ID` / `_NAME` / `_CODE` | 关联到哪份合同 |
| `RELATED_TYPE` | 关联类型（默认 `main`） |
| `RELATED_TIME` | 关联时间 |
| `RENEWAL` / `RENEWAL_TEXT` | 是否续签 / 续签条款 |
| `renewed_status` | 续约状态 |

**续签的完整语义 = 新建一份合同 + 用 `RELATED_CONTRACT_ID` 指向原合同**。不是"在原合同上改"。

**为什么不原地改？** 因为原合同**已经签署、已经履行过、可能已经归档**——它是有法律效力的既成事实，不能动。续签的语义是「产生一份新的、在条款上和原合同有关联的合同」。

> ⚠️ **但开源版只实现了"延期"这一半**：
> 后端 `renew` 接口**只 `setEndTime` 后 `updateById`** —— 不建新合同、不改状态、不写 `RELATED_CONTRACT_ID`。
> 而体现"新建 + 关联"语义的前端方法 `createContract.vue:renew(row)`（它设了 `relatedContractId` 并走新建流程）**没有任何调用者**。
> **面试时可以讲"续签应当不改原合同"这个设计原则**，但要诚实说明本项目里它只有"延期"落地。

> 💡 这条规律在 M4 里出现第 3 次了：**作废不删、模板不就地改、续签不原地改**。整个系统的设计哲学是「**历史不可变**」。面试时把这一条讲出来，比讲十个 CRUD 都有说服力。

## T4 · 合同报表（A 类）

🎯 **目标**：按条件统计查询合同，能导出 Excel。

🖥 **前端入口**：**统计报表 → 合同报表**，路由 `/report/book`，页面 `views/contract/book/index.vue`，API `api/contract/book.js`

🔌 **接口入口**（`ContractBookController`，**注意它映射了两个路径**）

```java
@RequestMapping({"/contract/book", "/contract/contractBook"})   // ← 两个前缀都认
```

| 方法 | URL | 权限码 | 用途 |
|---|---|---|---|
| GET | `/contract/book/list` | `contract:report:list` | 报表数据 |
| POST | `/contract/book/export` | `contract:report:list` | 导出 Excel |

📋 **复制清单**

| 文件 | 说明 |
|---|---|
| `controller/ContractBookController.java` | Controller |
| `domain/bo/ContractBookBo.java` · `domain/vo/ContractBookVo.java` | 入参/出参 |
| `mapper/ContractDraftMapper.java` | ★ **报表 SQL 在这里**（`bookPage` / `bookList`），不是 StatMapper |
| 前端 `api/contract/book.js` · `views/contract/book/index.vue` | 前端 |
| **easypoi** | 导出用（依赖在 `zxcm-third/zxcm-excel`）|

**数据库**：无需新增（查的是 `contract_draft`）

🧠 **原理 · 报表为什么（概念上）单独一个 Mapper**

`ContractDraftStatMapper` 的**设计意图**是统计查询单独一个 Mapper，而不是塞进 `ContractDraftMapper`。**为什么？** 因为统计 SQL 和业务 SQL 的需求完全不同：

| | 业务 SQL（`ContractDraftMapper`） | 统计 SQL（`ContractDraftStatMapper`） |
|---|---|---|
| 查什么 | 具体的合同记录（列多） | 聚合结果（`COUNT`/`SUM`/`GROUP BY`） |
| 有没有索引 | 有（`CONTRACT_STATUS` 等） | 全表扫描是常态 |
| 用在哪 | 页面列表 | 报表页 |
| 优化手段 | 加索引 | 加缓存/预计算/物化视图 |

**分开写，将来要优化统计查询时只动一个文件，不会影响业务流程。** 这是「按变化原因分离」——同一个表，两类用途，两个 Mapper。

> ⚠️ **实测纠正**：合同报表页（`ContractBookController`）**实际走的是 `ContractDraftMapper.bookPage` / `bookList`**，
> **不是 `ContractDraftStatMapper`** —— 后者在这个页面**没被调用**。讲原则没问题，别把"这个报表用了 StatMapper"说成事实。

> ⚠️ `@RequestMapping({"/contract/book", "/contract/contractBook"})` 这种「一个 Controller 挂两个路径」是**历史兼容**——改名后老的调用方还没迁完。项目里看到这种写法，一律理解为"**这里有过一次改名**"。

## T5 · C 类：自己补一个归档功能（可跳过的加分项）

⚠️ **答案册里没有这块的 Controller 和前端页面**。如果你时间紧，**直接跳过 T5，M4 照样算完成**（A+B 类已经覆盖了 M4 的主要业务闭环）。

如果你想做，这是**整个项目里最有价值的一段**——因为它是唯一一个「不是复制、要你自己设计」的部分。下面给你设计要点。

### 已经给你准备好的零件

| 零件 | 位置 | 状态 |
|---|---|---|
| `ConfArchives.java` + Mapper + Service | `conf/domain|mapper|service/` | ✅ 有 |
| `ContractArchivesFile.java` + Mapper + Service | `contract/domain|mapper|service/` | ✅ 有 |
| `ContractArchivesFileBo.java` + `ContractBatchArchiveBo.java` | `contract/domain/bo/` | ✅ 有（**连入参都定义好了**） |
| `ContractBorrow.java` + BO/VO/Service | `contract/domain|service/` | ⚠️ **Java 有，但下面的表不存在** |
| `BorrowEnum.java` | `contract/enums/` | ✅ 有 |
| **建表语句** | `conf_archives` **有**（`04-biz-tables.sql` 已建） / `contract_borrow` **没有** | ⚠️ **借阅表要你自己设计** |
| **Controller** | — | ❌ **要你写** |
| **前端页面** | — | ❌ **要你写（这个成本很高，可以只做后端 + curl 验证）** |

> ⚠️ **`contract_borrow` 是个陷阱**：Java 侧 `IContractBorrowService` / `ContractBorrow.java` / `BorrowEnum.java` **一整套都在**，但**答案册的 `zxcm_init.sql` 里没有这张表**（我逐表核对过全部 91 张表）。
> 这是**从商业版裁剪**留下的痕迹：源码没裁干净，SQL 文件被清理过。
> **所以做借阅时要先自己设计表**——别去答案册里找建表语句，找不到的。
> 反过来，这也说明 `borrow` 的 `BorrowEnum` 是**现成的状态机设计参考**（借出/归还的状态流转），可以当设计文档用。

### 建议的做法

**① 先只做后端，用 `doc.html` 验证。** 前端页面从零写成本极高（参照 `views/conf/billRule/index.vue` 也有几百行），**先用 curl 证明逻辑通**，前端可以后面再补。

**② 照着 M1 的模板抄结构**（这是最有价值的部分）：

```
domain/ContractArchives.java            ← 照 conf/domain/ConfArchives.java（已有，直接用）
domain/bo/ContractArchivesFileBo.java   ← 已有
mapper/ContractArchivesMapper.java      ← 照 conf/mapper/ConfArchivesMapper.java（已有）
service/IContractArchivesService.java   ← 自己定，参考 IConfBillRuleService 的方法签名风格
service/impl/...ServiceImpl.java
controller/ContractArchivesController.java   ← ★ 这是你要写的
```

**③ Controller 的骨架**（照着 `ConfBillRuleController` 抄，权限码用 `conf:archives:*`）：

```java
@Validated
@Api(value = "合同归档", tags = "合同归档")
@RequiredArgsConstructor
@RestController
@RequestMapping("/contract/archives")
public class ContractArchivesController extends BaseController {
    private final IContractArchivesService archivesService;

    @SaCheckPermission("conf:archives:list")
    @GetMapping("/list")
    public TableDataInfo<ContractArchivesVo> list(ContractArchivesBo bo, PageQuery pageQuery) {
        return archivesService.queryPageList(bo, pageQuery);
    }
    // add / edit / remove / export 同理，抄 ConfBillRuleController
}
```

**④ 别忘了两件事**：
- **菜单**：在「系统管理 → 菜单管理」里加一条菜单 + 按钮权限，或者在 `sys_menu` 里插 SQL（权限码要和 Controller 上的一致）
- **归档动作要改合同状态**：归档完成后写 `CONTRACT_ARCHIVES_ID` / `CONTRACT_ARCHIVES_TIME` / `CONTRACT_ARCHIVES_USER_ID`（M1 看列名时见过这三列），并写一条 `contract_point_log`

### 借阅（borrow）比归档更复杂

`contract_borrow` 表有借出/归还的概念，`BorrowEnum` 定义了状态。它本质上是一个**简化的审批流**（申请借阅 → 批准 → 借出 → 归还），**可以复用 M2 的 Activiti 流程**，也可以自己写个状态机。

**建议：借阅留到做完归档之后再决定做不做。** 它是整个项目里复杂度第三的功能（前两个是合同草拟和审批流）。

## M4 踩坑预警

| 症状 | 大概率原因 |
|---|---|
| 到处找不到「借阅管理」「归档管理」的页面/接口 | **它本来就不存在**（见文首 C 类说明），不是你没找到 |
| 上传双章合同报「当前合同未审批通过」 | 合同必须是审批通过（`'3'`+`APPROVE_STATUS='2'`）、待签署（`'4'`）、或复核失败重传（`'5'`+复核失败）状态。先走完 M2 |
| 上传双章合同 403 | 权限码是 `contract:contractDraft:uploadStampedContract`，**不是 `:edit`** |
| `getSeal` 返回空列表 | `contract_seal` 表里没有印章数据——**要先在「用印管理」里配印章**，而那个页面也是 C 类（不存在）。可以先手动往 `contract_seal` 插一条 |
| 报表查询很慢 | 统计 SQL 没有索引。加 `CONTRACT_STATUS` / `CREATE_TIME` 索引，或加缓存 |
| 续签后没生成新合同 | **正常**。开源版 `renew` 只把原合同 `END_TIME` 往后延，不建新合同、不改状态（"新建+关联"的语义在前端一个没接线的方法里）|
| 报表页 500 `Table 'zxcm.CONTRACT_DRAFT' doesn't exist` | 报表 SQL（`ContractDraftMapper.bookPage` / `bookList`）用的是**大写表名**，`lower_case_table_names=0` 的库必炸 → 改成小写 |
| 上传双章报「必须选择一个合同作为双章正文」 | 双章文件里必须有一个 `type='0'` 的正文文件 |
| 上传双章报「合同截止时间不能为空」 | 合同是固定期限（`END_TIME_TYPE='fixed'`）就必须填截止时间；无固定期限用 `'open'` 时会**忽略**你传的截止时间 |
| 调 `/renew` 直接 500（不是业务提示）| `renew` 里用 `draft.getEffectiveTime().getTime()` 比时间——**原合同 `EFFECTIVE_TIME` 为空时会空指针**，走不到那句「合同截止时间不能小于合同开始时间」 |
| 合同关闭 / 状态 `8`、中止 `7` 找不到入口 | `closeContract`（关闭合同，置 `'8'`）和 `applySign`（续约设置）**只有 Service、没有 Controller 接口和页面**；`'7'` 中止全项目没人写 |

## 🎤 怎么对面试官讲

> 被问到 M4 时，围绕「用印是法律行为」「宽表妥协」「历史不可变」三句展开：
>
> 「M4 是审批通过**之后**的事：盖章、上传双章、作废、续签、报表。
> 用印我单独设计了一套表（`contract_seal` + `contract_seal_notes`），因为**用印是不可撤销的法律行为**——出事要能查到『这个章是谁、何时、盖在哪份合同上』，所以那张流水表**只增不改**，它和审批事件日志 `contract_point_log` 是同一类东西：**不可篡改的流水**。
> 作废我没做删除，而是在合同表上同时用**状态位**（`CONTRACT_STATUS='2'`，方便列表过滤）和**原因列**（`CONTRACT_CANCEL_REMARK`，方便追责）——这是**用空间换查询性能的宽表取舍**，代价是冗余、可能不一致，所以我配了事件日志做对账。
> 还有一条贯穿全系统的原则叫『**历史不可变**』：**作废不删、模板改内容开新版本、续签应当新建合同而不是改原合同**——已经产生法律效力的记录只能追加、不能覆盖。
> 另外我读源码时发现开源版裁剪得不太干净：`contract_seal` 等表**有表但没有主流程写它**、`contract_borrow` **有 Java 代码但建表语句不存在**——**能分清『这是我配错了』还是『项目本来就没做』**，靠的是交叉验证（表 ↔ 实体 ↔ Mapper ↔ Controller）。」
