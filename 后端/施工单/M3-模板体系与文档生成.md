### 3.1 `template_contract` 的「版本三列」（M3 的表设计核心）

| 列 | 作用 |
|---|---|
| `STATUS` | `0 未发布 / 1 已发布 / 2 已停用` |
| `VERSION` | 版本号（默认 `'1.0'`）|
| **`VERSION_SHOW`** | **`1` = 当前生效版本**（同一 `templateCode` 只有一行是 1）|

> 🔑 **「哪个版本生效」由 `VERSION_SHOW` 决定，不是「版本号最大的」** —— 这是版本化设计的关键。
> `changeVersion` 就是把同 `templateCode` 的 `VERSION_SHOW` 全置 0、把选中的置 1。

### 3.2 为什么模板要拆 7 张表（M3 的核心设计）

| 拆法 | 为什么 |
|---|---|
| **主表 + 版本** | 改内容**开新版本**，旧版本保留 → 已发的合同引用的是**冻结的旧版本** |
| **`template_link_relation`** | 条款/关联模板**可跨模板复用**（`PARENT_ID` / `CHILD_ID`）|
| **`template_scope`** | 模板**按部门/人员**限定谁能用（`getLoginerCanUseTemplate` 靠它过滤）|
| **`template_element`** | 模板正文里的 `{{占位符}}` 单独成表 → 和 `DOC_ID`（Word contentControl id）对应 |

> **面试答法**：「模板不是一个『文档』，是**一套结构**：文档 + 占位符 + 条款 + 适用范围的组合。
> 所以拆成多张表 —— **主表管版本、关联表管复用、范围表管权限、元素表管动态填充**。」

### 3.4 架构视角：这套表真正的代价

拆法本身在 §3.2 已经讲清（主表管版本、关联表管复用、范围表管权限、元素表管填充）。这里只补**代价和缺口**，面试时用来平衡「只讲好处」：

- **主表会膨胀**：一个模板 10 个版本 = `template_contract` 里 10 行；
- **「单选生效」靠代码**：先把同 code 全置 0、再把目标置 1，**没有数据库唯一约束、没有加锁**；并发发布可能出现两行 `VERSION_SHOW=1`；
- **状态字段冗余**：`PUBLISHED` 是历史遗留，和 `STATUS` 语义重叠，判断能不能用只看 `STATUS`；
- **残留表**：`template_attachment` 已被 `FILE_GROUP` JSON 取代，新代码别再依赖；
- **模板审批是半成品**：`INSTANCE_DEF_KEY` / `INSTANCE_ID` 有字段，链路没接通。

## 四、T1~T3 逐个怎么做

### T1 · 模板草稿箱 ★★

**做什么**：建模板 → 传主文件（Word）→ 配适用范围 → 存草稿。

**关键点**：
- 页面 `views/template/templateDrafts/index.vue` → `GET /template/templateDrafts/list`（`?status=0`）
- 上传主文件走 **`POST /conf/file/upload/template`**（`fileUploadMain.vue:48`）→ 「文件」是 `conf` 包管的
- 新建/编辑弹窗 `TemplateDraftsEditDialog.vue`：类型下拉用 **T5 的 `getContractTypeEnable`**
- ⚠️ **「关联模板」页签在前端被注释掉了**（`TemplateDraftsEditDialog.vue:109-116`），UI 未启用

**完成标志**：草稿箱列表出现你新建的模板。

### T2 · 发布 / 停用 / 重新发布 ★★

**做什么**：草稿 → 发布（生成编号、置版本生效）→ 停用 → 重新发布。

**发布逻辑**（`TemplateContractServiceImpl.publish`，`L164-206`）：
1. 无 `templateCode` → 调 **`confBillRuleService.getBillNumber("TEMPLATE_RULE", …)`** 生成编号（**T4 的编号规则**）
2. 同 `templateCode` 的其他行 `VERSION_SHOW=0`
3. 当前行 `VERSION_SHOW=1`、`STATUS='1'`、`PUBLISH_TIME=now`
4. **非关联模板**要检查它引用的关联模板**都已发布**，否则抛「当前模板依赖的关联模板未发布」

| 操作 | 关键行为 |
|---|---|
| **停用** `stop` | 若该模板是「关联模板」，把它被引用的非关联模板**一起停用** |
| **重新发布** `rePublish` | 非关联模板要校验其关联模板都已发布 |
| **新版本** `addNewVersion` | 版本号必须**严格大于所有历史且不重复**；复制主文件（新 `ConfFile`）+ 复制全部 `template_element` |
| **切换版本** `changeVersion` | 同 `templateCode` 全部 `VERSION_SHOW=0`，选中行 `=1` |

> ⚠️ **`realStop` 把 `PUBLISHED` 也置 `'1'`** —— `PUBLISHED` 和 `STATUS` 语义重叠、容易不一致（技术债）。

**完成标志**：发布后模板编号有值；`VERSION_SHOW=1`；停用后状态变 `2`。

### T3 · OnlyOffice 在线编辑 ★★★★（M3 的技术难点）

**做什么**：在浏览器里**在线编辑 Word 模板**并保存。

> 🔴 **T3 不是「写 Java」，是「部署一台服务 + 配 3 个地址」**。先看清楚整条链路。

#### T3-1 部署 OnlyOffice 文档服务器（独立服务）

```bash
docker run -i -t -d -p 8081:80 onlyoffice/documentserver
```
**它必须是「OnlyOffice 服务器能访问到你的后端」的网络关系**（回调要回到你的 8080）。

#### T3-2 改 3 项配置（`application-dev.yml`）

```yaml
onlyoffice:
  domain: http://<OnlyOffice 服务器 IP>       # ① 前端从这加载 api.js
  port: 8081
  callbackUrl: http://<后端能被访问到的 IP>:8080/onlyofficeCallback   # ② ③ OnlyOffice 回调用它
  secret: zxcm                                 # ③ 必须与 OnlyOffice 端 local.json 的 secret 一致
```

> ⚠️ **`callbackUrl` 不能是 `localhost`** —— 因为发起回调的是**另一个容器**，它认不了你的 localhost。

#### T3-3 完整回调链路（★ 背下来）

```
【打开】
1. 合同草拟点「在线编辑」→ 新窗口打开路由 /contractFileEdit
2. contractFileEdit.vue:loadDoc() → getUrl(fileId,'CONTRACT',...)  →  GET /wps/weboffice/geturl
3. 后端 WpsController.geturl（L126-240）：
     · 读 ConfFile，取/生成 onlyofficeKey（key 空则重新生成 → 每次打开都是新会话）
     · 组装 OnlyofficeFileModel：
          callbackUrl = callbackUrl + "/save?fileId=..&contractId=..&loginToken=" + StpUtil.getTokenValue()
          document.url = callbackUrl + "/download/{fileId}?...&loginToken=.."
          token = JWT(onlyoffice.secret)   ← DefaultFileConfigurer 里签名
4. onlyoffice.vue 动态注入 <script src="{domain}/web-apps/.../api.js"> → new DocsAPI.DocEditor(...)
   （页面里怎么临时加载这个脚本 → [E2 §6.4 动态加载第三方脚本](../../前端/E2-前端代码导读.md)）

【保存】
5. 编辑完 → OnlyOffice 服务器 POST 到 callbackUrl  →  /onlyofficeCallback/save
6. OnlyofficeCallbackController.save（L81-109）：
     · LoginHelper.getLoginUserByToken(loginToken) + login(user)  ← 用打开者的 sa-token 重新登录
     · jwtManager.parseBody(body)  ← 用 onlyoffice.secret 验签，失败抛 JWT validation failed
     · 按 Track.status 分发：SAVE(2)→SaveCallback、MUST_FORCE_SAVE(6)→ForcesaveCallback、EDITING(1)→EditCallback(空壳)
7. SaveCallback.handle（L64-116）：
     · 校验合同状态必须是 draft/audit，否则抛「该文档不允许修改」
     · 把 body.url 的流下载，覆盖写回本地文件
     · confFileService.changeKey(...)  ← 刷新 onlyofficeKey
     · ⚠️ 不生成 PDF、不新增 contract_draft_files 版本行
```

> 💡 **一句话说人话**：这条链里**最反直觉的是"谁在调谁"**——文档不是在你的服务器上编辑的，是在**另一台 OnlyOffice 服务器**上编辑的；它改完**反过来回调你的后端**。
> 所以"保存"这一下：**发起者是 OnlyOffice 服务器，不是用户浏览器**。用户浏览器早就关了也没关系，回调照样来。
> 这也是为什么回调地址必须让**那台服务器**访问得到、为什么回调里没有用户登录态（只能靠 `loginToken` + `secret` 验签补回来）。

**完成标志**：浏览器能打开编辑器、编辑后保存、文件内容真的变了。

### 技术清单

| 技术 | 在 M3 里干什么 | 关键点 |

### ★ Q1：模板功能怎么做的？

**模板 = 一套结构**（正文文件 + 占位符元素 + 条款 + 适用范围），不是单个文档。
生命周期：**草稿 → 发布（生成编号、版本生效）→ 停用 → 重新发布**。

> **答法**：「模板是**版本化的、可复用的文档骨架**。我用 7 张表把它拆开：
> 主表管版本、元素表管占位符、条款表管复用片段、范围表管谁能用。
> 发布时**生成编号 + 标记生效版本**，改内容**开新版本**而不是覆盖 —— 这样**已发的合同引用的旧版本不受影响**。」

### ★ Q2：为什么模板要版本化，不能直接改？

**因为合同是从模板实例化出来的，改了模板会「污染历史」。**

> **答法**：「如果直接改模板，**已经基于它生成的合同会对不上**（模板变了，合同里的内容却不是当初那份）。
> 所以模板**只增不改**：改内容 = 开新版本（`VERSION`），**哪个版本生效由 `VERSION_SHOW` 决定**。
> 旧的合同永远引用它生成时的那个版本。**这是『不可变 + 版本指针』的思路**，和代码的 tag、文档的修订版是一个道理。」

### ★ Q3：OnlyOffice 集成的难点在哪？（M3 招牌题）

**难点不在 Java，在「回调协议 + 网络可达性 + 鉴权」这三件事**：

1. **回调方向是反的**：是你**把 callbackUrl 交给 OnlyOffice 服务器**，编辑完**它回调你** ——
   所以 `callbackUrl` 必须是**它能访问到的地址**（不能是 localhost）
2. **回调这个「新请求」怎么鉴权**：回调不带你的登录态 →
   项目的解法是把**打开编辑器那个用户的 sa-token 写进 callbackUrl 的 query**（`loginToken=...`），回调时用它重新登录；**再叠加 `onlyoffice.secret` 的 JWT 验签**
3. **保存是「覆盖」不是「加版本」**：`SaveCallback` 把文件流**原地覆盖** + 刷新 key，**不新增版本行**

> **面试答法**：「OnlyOffice 集成的坑主要是**分布式下的地址与鉴权**：
> ①回调地址要双向可达；②第三方回调无法走正常登录，我用『把用户 token 编进回调 URL』这个折中方案 ——
> **但它有风险：把 sa-token 明文写进了交给第三方的 URL（会进 OnlyOffice 日志）**。
> 更干净的做法是**用一次性、短时效的签名 token 专门给回调**，不直接复用用户的登录 token。」

### Q4：文件是怎么管理的？

- **文件元数据**在 `conf_file`（含 `ONLYOFFICE_KEY`），**文件实体**在 `ruoyi.profile` 目录（`URL` 存相对路径）
- 上传统一走 `POST /conf/file/upload/{module}`（`module` = `template` / `contract` …）
- ⚠️ **文件上传依赖 `conf` 包的 Controller** —— 「文件」是**跨模块公共能力**

## 十、★ 你没考虑周全的地方

### A. M3 暴露的「文件与文档」跨模块问题

**事实**：文件能力（`conf_file` + 上传接口）在 **conf 包**，模板在 **template 包**，编辑器在 **onlyoffice/wps 包** ——
**一个「在线编辑」功能横跨三个包 + 一台外部服务**。

**Why 重要**：说明**「文件/文档」在本项目里是「跨模块公共能力」**，不是某个模块的私产。
`conf_file` 被模板、合同、附件共用。

**How to apply（面试怎么讲）**：
- **识别**：「文件是**横切能力**，`conf_file` 一张表服务模板/合同/附件。」
- **讲边界**：「所以文件上传接口放在 `conf` 而不是 `template` —— **能力放对了地方，复用才自然**。」
- **讲代价**：「代价是**任何要传文件的模块都依赖 `conf`**，`conf` 成了隐性「基础能力层」。」

### B. 项目级的两个提醒

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | **「有 Service 无 Controller/页面」是常态** | 归档/借阅（M4）、条款库（M3）都是这样。**别以为漏拷了，是答案册本身没做前端** |
| 2 | **编译能过 ≠ 运行能过** | Mapper XML 缺失是**运行期**才炸 —— **「零必改」的检查必须包含「XML 是否齐全」**，不能只看 Java |

### C. M3 特有的

**C-1. ★ T3 的验收要留出「环境时间」**

OnlyOffice 是**独立服务**，部署 + 网络 + secret 对齐，**可能要花掉 M3 一半的时间**。
别把它当成「顺手配一下」—— **先把 `docker run` 和服务连通性单独验通，再谈 Java 集成**。

**C-2. 把「保存为什么是覆盖不是加版本」讲清楚**

答案册的 `SaveCallback` **只覆盖文件 + 换 key**。**这是有意的**：
`conf_file.ONLYOFFICE_KEY` 每次打开都重新生成 → **「每次打开都是一次新会话」**。
版本递增是**合同模块**的事（`contract_draft_files.FILE_GROUPS_VERSION`），**不在这条回调链里**。
面试里讲清这个分工，比说「我集成了 OnlyOffice」专业得多。

> ✅ **面试标准答**：**6 张模板体系表（主表 + 配套，原作者设计）+ 文件表**；技术难点是 **OnlyOffice 独立部署 + 回调协议 + 鉴权**；**保存回调只覆盖不新增版本**（版本属于合同模块）。
