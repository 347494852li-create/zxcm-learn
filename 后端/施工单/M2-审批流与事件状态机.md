| 方案 | 做法 | 代价 |

### 3.4 ★ M2 最重要的表设计：一条「四跳的桥接链」

**这是 M2 的核心概念** —— 业务（合同）和引擎（Activiti）怎么挂上钩。逐跳：

| 跳 | 从（表.列）| 到（表.列）| 含义 |
|---|---|---|---|
| **①** | `contract_draft.CONTRACT_TYPE` | `form.ID` | 合同**类型** |
| **②** | `form.INSTANCE_DEF_KEY` | `act_designer.EN_CODE` | 类型 → **流程编码** |
| **③** | `act_designer.EN_CODE` | `ACT_RE_PROCDEF.KEY_` | 流程编码 → **引擎里的流程定义** |
| **④** | `contract_audit_form.INSTANCE_ID` | `ACT_RU_TASK.PROC_INST_ID_` | 审批单 → **运行中的流程实例** |

**串起来读**：
```
合同草稿(contract_draft)  --①-->  合同类型(form)  --②-->  流程编码(act_designer.EN_CODE)
      --③-->  引擎流程定义(ACT_RE_PROCDEF.KEY_)  --④-->  运行实例(ACT_RU_TASK.PROC_INST_ID_)
```

> 💡 **一句话说人话**：这条链回答的是「**我拿着一份合同，怎么找到它对应的待办任务**」。
> 合同自己不知道走哪条流程（它只记得"我是什么类型"），于是**一路问下去**：合同 → 类型配了哪条流程 → 那条流程在业务侧叫什么 → 在引擎里对应哪个流程定义 → 引擎给谁开了待办。**四个"翻译"，一棒接一棒。**

> 🔑 **第 ③ 跳的实现**（`TaskMapper.java`）：引擎表和自建表靠 **`LEFT JOIN`** 相连：
> `LEFT JOIN act_designer d ON p.KEY_ = d.EN_CODE`（`p` = `ACT_RE_PROCDEF`）。
> **这一跳是整个「业务↔引擎」桥接的物理实现** —— 引擎只知道 `KEY_`，业务需要 `EN_CODE` 对应的中文名/配置，靠这个 JOIN 补上。
>
> ⚠️ **桥接链的自检**：第 ③ 跳要求 `act_designer.EN_CODE` 与 `form.INSTANCE_DEF_KEY` **对得上**（都是 `swhtsp`）。
> 对不上 → 待办列表 JOIN 出空。`03` 脚本末尾自带校验 SQL。

### 3.6 架构视角：三套表、三个主人

M2 的表不是「一套」，是**三层拼起来的**，每层的规范都不一样：

| 层 | 表 | 谁建的 | 你的职责 |
|---|---|---|---|
| 引擎层 | 24 张 `ACT_*` | Activiti 启动时自建 | 只读、只 join，不手改 |
| 桥接层 | `act_designer` | `03` 脚本 | 维护流程编码（`EN_CODE`） |
| 业务层 | `contract_audit_form`、`contract_point_log` 等 | `04` 脚本 | 自己的 CRUD 和状态 |

**代价（面试可以主动说）**：

- **三套命名规范**：引擎全大写 `ACT_*`、桥接表小写 `act_designer`、业务表大写下划线 `CONTRACT_*`；
- **三套主键风格**：引擎 `varchar`、审批单 `decimal(20)`、合同 `varchar(64)`；
- **状态校验分散**：没有显式状态机，非法跃迁靠各 Service 的 if 拦（第 6 章 §1.2 坦白点）。

**已知缺口**：`contract_remarks` 没有主键；`contract_point_log` 只增不删、会持续膨胀。

> 完整版（四跳桥接链、六个状态字段、事件解耦）见《重塑版 · 第 6 章》§4.1。

### T2 · 画一条审核流程 ★★

**做什么**：让 `act_designer` 里有一条可用的流程定义，并**部署到引擎**。

**关键点**：
- 设计器页面 `views/workflow/designer/index.vue` → 调 `/workflow/designer`（列表）、`/workflow/designer/deploy/{id}`（部署）

### T3 · 提交审批 ★★★（M2 的第一个硬骨头）

**做什么**：合同草稿 → 点「提交审批」→ 引擎里**起一个流程实例**。

**核心链路**（这是 M2 最该背下来的一条）：

```
ContractAuditServiceImpl.beginAudit(L496)
   ① 校验：contractStatus==draft(0) && coordination!=progress && approveStatus==none(0)
   ② 置状态：approveStatus=progress(1)、contractStatus=audit(3)、applyTime=now
   ③ 发 AuditFlowEvent(TYPE_START)   ← 解耦！业务不直接调引擎
        ↓
FlowAuditService.start(L93, @EventListener)   ← 桥接层接住事件
   ④ 组装流程变量（合同名/金额/收支/签约主体/合作方/deptLeader/companyLeader…）
   ⑤ processService.submitApply(...) → runtimeService.startProcessInstanceByKeyAndTenantId(key, businessId, vars, tenantId)
   ⑥ 回写：form.setInstanceId(instance.getId()) → contractAuditFormMapper.updateById
   ⑦ asyncUpdateService.updateAuditTaskInfo(tasks)   ← 把引擎的当前任务回填到业务表
```

**关键点**：
- **③ 是解耦点**：业务侧只发一个事件，**不知道引擎的存在**（依赖倒置，见 Q3）
- `contract_stock=="0"` 时正常走审批；否则（**存量合同**）直接置 `fulfil(6)` 跳过审批
- 写表：`contract_audit_form`（instance_id / audit_status）+ `contract_draft`（状态列）+ `contract_point_log`（节点日志）

**完成标志**：`ACT_RU_TASK` 里出现一条待办任务；合同 `CONTRACT_STATUS='3'`（审批中）。

### T4 · 我的待办 / 审批动作 ★★★

**做什么**：待办列表 → 点「同意」→ 流程往下走。

**核心链路**：
```

   → ProcessServiceImpl.complete(L583)：taskService.claim → taskService.complete
        （处理 NEXT_TASK_ID 跳转、delegate/resolveTask）
```

## 六、技术栈 + 面试高频题

### 技术清单

| 技术 | 在 M2 里干什么 | 关键点 |
|---|---|---|
| **Activiti 7** | 流程引擎 | 外挂式（引擎自建 24 表、`databaseSchemaUpdate: true`）|
| **Spring 事件（`@EventListener`）** | 业务↔引擎解耦 | `AuditFlowEvent` / `ContractEvent` |
| **BPMN 委托表达式** | 引擎回调业务 | `${flowEndListener}` / `${userTaskListener}` |
| **MyBatis-Plus + 手写 SQL** | 桥接查询 | `TaskMapper` 手写引擎 SQL（`LEFT JOIN act_designer`）|
| **Sa-Token** | 权限 | ⚠️ 极稀疏（只有 `printAudit`）|

### ★ Q1：状态机怎么设计的？（M2 招牌题）

**不是规则表，是散在 Service 方法里的「状态迁移」**（`ContractEnums.ContractStatusEnums`）：

| 值 | 含义 | 谁来置 |
|---|---|---|
| 0 | 拟稿 | 新建 |
| **1** | **（故意空缺）** | —— |
| 2 | 作废 | 删除 / 作废 |
| 3 | **审批中** | `beginAudit`；⚠️ **审批通过后仍是 `3`**（不改这列，只置 `CONTRACT_APPROVE_STATUS='2'`）|
| 4 | （本版本死状态）| 只有已废弃的 `applyStamp` 会置，主流程不用 |
| 5 | （本版本死状态）| 全代码库无人写入 |
| 6 | 履行中 | `uploadSealContract`（M4 上传双章合同）直接跳到 `6` |
| 7 | 中止 | |
| 8 | 已结束 | |

> **面试答法**：「状态值定义在枚举里，**但迁移规则没有集中表** —— 散在 `beginAudit`/`complete`/`reject` 等方法里。
> 优点是**读一处就懂一个迁移**；缺点是**没有全局视图，改状态容易漏**。
> 严谨的做法是抽一个**状态机引擎**（如 Spring StateMachine）把迁移规则显式化。**当前项目没做到，这是改进方向。**」

### ★ Q2：业务系统怎么和流程引擎解耦？（M2 招牌题）

**核心：业务侧不直接调引擎，而是发「事件」；桥接层接住事件再调引擎。**

- 业务发 `AuditFlowEvent(TYPE_START)` → `FlowAuditService`（`@EventListener`）接住 → 调引擎
- **好处**：合同模块**不知道 Activiti 的存在**（只认事件）；换引擎不改业务代码

> **面试答法**：「用**事件（观察者模式）**做解耦 —— 这叫道**依赖倒置**：
> 业务依赖『事件』这个抽象，引擎实现挂在监听器里。**代价是「静默」**：
> 事件发出去没人接不报错（就像 M1 的 `DataDeleteEvent`），排查很隐蔽。**这是事件驱动最大的坑。**」

### ★ Q3：点「同意」之后发生了什么？（链路题，背下来）

1. 前端 → `POST /activiti/process/complete`
2. `ProcessServiceImpl.complete` → `taskService.claim` + `taskService.complete`
3. 流程流转；到终点触发 BPMN 的 `${flowEndListener}`
4. `FlowEndListener` 判 `pass=="true"` → `flowAuditService.auditSuccess`
5. 写回 `contract_draft`（状态 → 待签/履行）+ `contract_audit_form`
6. `contract_point_log` 落一条节点日志

> 能**从头到尾串下来**，比背单个 API 强得多。

### Q4：Activiti 的 RU 表和 HI 表为什么分开？

- `ACT_RU_*`（Runtime）：**运行中**的实例/任务，**数据量小、读写频繁**
- `ACT_HI_*`（History）：**已结束**的归档，**数据量大、写得少**

> 「**读写模式不同 → 分表**。运行表要快（频繁增删改），历史表要全（只追加）。
> 这跟『热数据/冷数据分离』是一个道理。**代价是查询历史要跨表、状态要对齐**。」

### Q5：为什么会有「多个状态列」，这算好设计吗？

`contract_draft` 同时有 `CONTRACT_STATUS`（主状态）、`CONTRACT_APPROVE_STATUS`（审批）、`CONTRACT_STAMPED_STATUS`（用印）……

> 「**主状态 + 若干子状态**是宽表的常见做法 —— 主状态给『一眼看全貌』，子状态给『看具体环节』。
> 好处是**查询不用 join**；坏处是**子状态之间可能矛盾、没有唯一真值**。
> M2 的补救是 `contract_point_log`（事件日志）**作为真值来源** —— **状态列是快照，事件日志是流水**。」

### Q6：你读源码时发现什么问题？（★ 分类讲）

| 现象 | 定性 |

| `MyAuditContractMapper` / `ContractAuditFormMapper` 用**大写表名** | **真 bug**（本机必挂）|
| `ApprovedCounterSignCompleteListener` 是 `@Component` 但 BPMN 里**零引用** | **死 bean**（恒不触发）|

## 十、★ 你没考虑周全的地方

### A. M2 暴露的「横切关注点」问题

**事实**：审批流是**横切**所有业务的 —— 它不属于合同，但合同、模板（M3）都要用。

**为什么重要**：横切模块的**依赖方向是「业务 → 引擎」**（合同依赖引擎），
但**引擎的桥接层又反过来依赖业务对象**（`FlowAuditService` import `ContractDraft`）→ **双向耦合**。

**How to apply（面试怎么讲）**：
- **承认**：「审批引擎和业务对象**双向依赖** —— 业务发事件，引擎的桥接层又要读业务对象。」
- **讲取舍**：「这是**单体项目里做工作流的常见代价**。真要彻底解耦，桥接层应该**只依赖业务对象的『接口』而不知道具体类**，
  但那样代码量和抽象层次都要上一个台阶。**当前项目的取舍是「可读性优先」。**」
- **给结论**：「所以我判断：**能识别出这条双向依赖、并说清为什么暂时不拆**，比硬拆一个漏抽象层要值。」

### B. 项目级的两个提醒

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | **事件驱动的「静默失效」** | M1 的 `DataDeleteEvent` 无人监听 → M2 才补上监听器。**事件发出去没人接不报错**，上线前必须检查「事件有没有人接」|
| 2 | **权限注解极稀疏** | 审批动作（complete/reject/delegate）**全靠前端挡**。**前端隐藏 ≠ 后端拦截**，这是真实的安全隐患 |

### C. M2 特有的

**C-1. ★ 把「四跳桥接链」画出来并讲清楚**

M2 最值钱的产出不是「跑通了审批」，而是**能画出并讲清那条四跳链**：
`contract_draft → form → act_designer → ACT_RE_PROCDEF → ACT_RU_TASK`。
**面试里画这条链，胜过背一堆 API。**

**C-2. 验收姿势：先主干，后分支**

M2 的主干是「提交 → 待办 → 同意」。**先把主干跑通并验收**，
把「转办/批量/撤销/跳节点」这些**分支**标注为「支线功能，按需验证」。
别为了「全绿」在 M2 就把所有审批动作全测一遍。

## 🎤 怎么对面试官讲

> 如果面试官只给你 1 分钟讲 M2，按这个顺序说（先结论、再机制、最后亮点）：
>
> 「M2 是合同审批流。**状态机不是规则表**，状态值在 `ContractEnums`、迁移规则散在 `beginAudit`/`complete`/`reject` 里，所以**没有全局视图**——这是我想引入显式状态机的改进点。
> **解耦**上，合同侧发起审批**不直接调 Activiti**，只发 `AuditFlowEvent`，`FlowAuditService` 用 `@EventListener` 接住再启动流程实例；这样**业务模块不认识引擎**，换引擎不用改业务代码。
> 两边靠**四跳桥接链**对齐：`contract_draft → form → act_designer → ACT_RE_PROCDEF → ACT_RU_TASK`，引擎表和业务表用 `LEFT JOIN act_designer d ON p.KEY_ = d.EN_CODE` 缝在一起。
> 一致性上，我除了用状态字段，还加了 `contract_point_log` 事件日志；**状态列是快照、事件日志是流水**。
> 我也发现几个真问题：`ContractEvent` 的 `businessJson` 没赋值、`complete`/`reject` 这些敏感动作**没有权限注解**、`getInnerJoinSql` 字符串拼接有注入面——**能分档说清『真 bug / 死 bean / 半成品 / 安全隐患』，比只说『我跑通了』更有说服力。**」

## 🔎 本模块「账本」：被问「这功能用到哪些表 / 谁做的 / 为什么」就背这里

> **一句话口径**：M2 的表分**三层**——**24 张引擎表（引擎自建，不用管）+ 1 张桥接表 `act_designer`（脚本建）+ 6 张业务/桥接表（脚本建）**。逐跳的表设计见 **本文「§三 用哪些表 + 建表脚本」**，这里只给「面试口径」。
> 字段级详解在 [D0 · 数据库表地图](../D0-底座表地图.md)（**同一主题只深讲一处**）。

**① 数据：用到了哪些表**

| 表 | 在本模块里的角色 | 谁设计的 / 谁建的 | 为什么这么设计（一句话）|
|---|---|---|---|
| **24 张 `ACT_*`** | 引擎表（`ACT_RE_/RU_/HI_`）| **Activiti 引擎启动自建**（`databaseSchemaUpdate: true`）| **审批流不该手写状态机**，交给成熟引擎；**你不用管它怎么建表** |
| **`act_designer`**（19 列，2 行）| **桥接关键**（流程编码）| **肇新原作者**（`03-missing-base-tables.sql`）| `EN_CODE` 有唯一索引 → **业务类型 ↔ 引擎流程定义** 的翻译表 |
| **`contract_audit_form`**（62 列）| **桥接枢纽** | 肇新原作者（`04`）| 审批单持有 `INSTANCE_ID` → **合同 ↔ 运行中流程实例** 的锚点 |
| **`contract_point_log`**（13 列）| **事件流水** | 肇新原作者（`04`）| 宽表状态列会互相矛盾 → 用它当「**到底发生了什么**」的权威来源 |
| `contract_draft` / `contract_remarks` | 合同主表 / 备注 | 肇新原作者 | T6 已建；`contract_remarks` **无主键**（⚠️ 可讲的坏味道）|
| `form` | 类型 → 流程编码 | 肇新原作者（`03`）| 桥接链的第 ① 跳 |

**② 组件：用到了哪些中间件 / 框架**

| 组件 | 谁做的 | 你这一站真正用到哪一步 | 为什么用它（面试答法）|
|---|---|---|---|
| **★ Activiti 7 引擎** | 开源工作流引擎（RuoYi 集成）；**无独立服务** | 起后端时**自动建 24 张表**；提交合同 → 生成流程实例 / 待办任务 | **引擎嵌在应用里**；「点同意之后发生了什么」= 引擎推进 + 回写业务表 |
| **Spring Event / 监听器** | Spring 框架 | 事件触发 → **写 `contract_point_log`** | 解耦「业务动作」和「事件流水」 |
| **（无 Redis / MQ 新增）** | — | 本站**没有引入新的中间件** | ✅ 诚实说「没新增中间件，用的是引擎」是加分项 |

> ✅ **面试标准答**：**24 张引擎表（不是我的）+ 1 张桥接表 + 6 张业务表**；核心讲 **★ 四跳桥接链**（类型→流程编码→流程定义→运行实例）；**审批流靠 Activiti 引擎，不是手写状态机**。
