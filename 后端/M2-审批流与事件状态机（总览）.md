## M2 做完是什么样

一份合同能完整走完这条链：

```
合同草拟（CONTRACT_STATUS = '0' 拟定中）
      ↓  点「提交审批」
   审批中（'3'）→ 审批人的「审批管理」待办列表里出现这条
      ↓  审批人点「同意」
   审批通过（状态仍 '3'，另置 CONTRACT_APPROVE_STATUS='2'）→ 审签跟踪里能看到流程节点走完了
      ↓  审批人点「驳回」
   回到拟定中（'0'）→ 草拟人能在「审签跟踪 → 流程」里看到驳回原因
```

| 页面 | 能做什么 |
|---|---|
| 合同基础配置 → **审核流程管理** | 拖拽画流程图（开始 → 审批节点 → 条件分支 → 结束），保存并发布 |
| 合同管理 → **合同草拟** → 提交审批 | 选流程、发起审批 |
| 合同审签 → **审批管理** | 我的待办 / 我已办 / 我发起 |
| 合同管理 → **审签跟踪** | 按合同查当前审批状态、流程轨迹、审签意见 |
| 合同管理 → **事件日志** | 一份合同从头到尾发生过什么 |

## ★ 先看懂这一节 ★

### 合同状态机（这是 M2 的骨架）

`ContractEnums.ContractStatusEnums` 定义了 8 个状态。**记住这几个数字，M2/M4 的所有代码都在它们之间切换**：

| 值 | 名称 | 谁把它改成这个 |
|---|---|---|
| `0` | **拟定中** | 新建合同默认值 / 驳回 / 退回 |
| `2` | **已作废** | M4 的 `cancelContract` |
| `3` | **审批中** | M2 的 `beginAudit`；⚠️ `auditSuccess`（审批通过）**不改这一列**，只把 `CONTRACT_APPROVE_STATUS` 置 `2`，所以通过后 `CONTRACT_STATUS` 仍是 `3` |
| `4` | 待签署 | ⚠️ **本版本里是死状态**：只有已废弃的 `applyStamp` 会置 `4`，主流程（`auditSuccess`）根本不走它 |
| `5` | 已签署 | ⚠️ **本版本里是死状态**：全代码库**没有任何地方**把它设成 `5` |
| `6` | 履行中 | M4 的 `uploadSealContract`（上传双章合同） |
| `7` | 中止 | M4 |
| `8` | 已结束 | M4 |

> ⚠️ **注意 `1` 是空的**。这不是笔误——大概率是历史上「已提交待审」被合并进了 `3 审批中`。**别自己补一个 `1`**，否则和答案册不一致。
>
> ⚠️ **`4`/`5` 也别当真**。这个版本的状态机是这样走的：审批通过后 `CONTRACT_STATUS` 停在 `3`，靠 `CONTRACT_APPROVE_STATUS='2'`（前端据此放行"上传双章合同"按钮，见 `auditList.vue:376`）来标记"审批已完成"；真正推进 `CONTRACT_STATUS` 的是 M4 的 `uploadSealContract`，它直接跳到 `6 履行中`。所以 `4 待签署`/`5 已签署`只是枚举里留着、主流程不用的历史残留。
>
> ⚠️ **`7 中止` / `8 已结束` 在界面上也基本走不到**：全代码库**没有任何地方**把状态置成 `7`；`8` 只有 `closeContract`（关闭合同）和 `applySign`（续约设置）两个 **Service 方法**会写，而这两个方法**都没有对应的 Controller 接口、也没有前端入口**（全项目搜不到调用者）。所以在开源版里，你在页面上能真正走出来的链路其实只有这一条：
>
> ```
> 拟定中(0) ──提交审批──▶ 审批中(3) ──审批通过(APPROVE_STATUS=2)──▶ 上传双章 ──▶ 履行中(6) ──作废──▶ 已作废(2)
> ```
>
> 💡 **一句话说人话**：**枚举里定义了 8 个状态，主流程只用到 4 个**。看到"列了一堆状态"先别慌，去代码里搜"谁把它改成这个值"——搜不到的就是历史残留。

**除了 `CONTRACT_STATUS`，`contract_draft` 还有 4 个并行状态列**（`CONTRACT_APPROVE_STATUS` / `CONTRACT_STAMPED_STATUS` / `CONTRACT_REVIEW_STATUS` / `CONTRACT_CHANGE_STATUS`）。

🧠 **为什么会有"多个状态列"这种设计，以及它的毛病**

好处：每种状态各管一摊（审批走了不改用印、用印走了不改审批），写代码时不用 join 流程表。

毛病：**没人知道哪个才是权威的**。审批通过了但 `CONTRACT_STATUS` 没改？用印完了但 `CONTRACT_STAMPED_STATUS` 是 1？这类「状态不一致」是这类设计的天生缺陷。

**所以答案册引入了 `contract_point_log`（事件日志）**——不去猜当前状态对不对，而是看「**到底发生过哪些事件**」。这是 M2 里最值得学的一个设计决策。
> 面试点：「状态字段和事件日志你都用吗？」→「状态字段用于**查询过滤**（快），事件日志用于**追溯和对账**（准）。两者职责不同，不是二选一。」

### Activiti：流程引擎是「外挂」进来的

M0 时有个细节值得回想：**你的库里现在有 50 张表，其中 24 张是 `ACT_*` 开头的**。而 `01-zxcm-learn-base.sql` 里 **`ACT_` 表是 0 张**（筛选条件只留 `sys_`/`gen_` 开头的表，把引擎表排除了）。
> ⚠️ 但**答案册的 `zxcm_init.sql` 里有 25 张 `ACT_` 表**（24 张引擎表 + 自建的 `act_designer`）—— 别以为答案册也没有。

**这 24 张表是 Activiti 引擎在应用启动时自动建的**（`ACT_HI_*` 存历史、`ACT_RU_*` 存运行时、`ACT_RE_*` 存流程定义）。

```
zxcm-contract 模块里没有这些表 —— 它们在 zxcm-workflow 模块的依赖里
zxcm-workflow/pom.xml:
    org.activiti:activiti-spring-boot-starter-rest-api
    org.activiti:activiti-bpmn-layout
    org.activiti:activiti-json-converter
```

✅ **对你的影响**：M2 复制 `zxcm-workflow` 的代码后启动，Activiti 发现表已存在就直接用；如果你哪天重建库，它会**自动重新建好**，不用你管。

### 这一章有 81 个 Java 文件，但你要理解的只有 4 个概念

`zxcm-workflow` 有 **81 个** Java 文件，规模不小。但拆开看只有 4 个概念：

| 概念 | 在哪 | 干什么 |
|---|---|---|
| **流程定义（BPMN）** | `engine/designer/` + `engine/modeler/` | 前端拖出来的流程图，存成 BPMN XML |
| **任务（Task）** | `engine/controller/ActivitiProcessController` | 待办/已办/发起，`complete`（同意）`reject`（驳回） |
| **监听器（Listener）** | `engine/listener/` | 流程走到某节点时触发的回调（**会签、抄送、流程结束**都在这里） |
| **业务桥接** | `business/service/FlowAuditService` | **业务单子和流程实例的对应关系**——合同 ID ↔ 流程实例 ID |

**「业务桥接」是最关键的一个**：Activiti 只认流程实例 ID（`instanceId`），它不知道什么是「合同」。这层桥接负责：

```
提交审批：contractId + 流程key  →  启动流程实例  →  把 instanceId 写回合同/审批单
审批通过：taskId  →  complete(taskId)  →  监听器回调  →  改合同状态
```

> 💡 **一句话说人话**：Activiti 只认识「流程实例 ID（`instanceId`）」，你把「合同 ID」递给它，它不认识。所谓"桥接"，就是**在合同和流程实例之间记一条对应关系**——启动流程时把 `instanceId` 写回 `contract_audit_form.INSTANCE_ID`，之后拿到 `instanceId` 就能反查出是哪份合同。**这条对应关系就是「两个世界」之间唯一的那根线。**

### M2 的表：引擎表 24 张 + 业务表 6 张

**① 引擎表（Activiti 自建，你只管用）—— 按「生命周期」分成四组**

| 前缀 | 全称 | 存什么 | 生命周期 |
|---|---|---|---|
| `ACT_RE_*` | **Re**pository 仓库 | 流程**定义**（BPMN 部署记录、版本） | 发布后长期存在，**版本递增** |
| `ACT_RU_*` | **Ru**ntime 运行时 | **正在跑**的实例、任务、变量 | **流程一结束就删** |
| `ACT_HI_*` | **Hi**story 历史 | **跑完**的实例、任务、变量、活动 | 永久保留 |
| `ACT_GE_*` | **Ge**neral 通用 | 二进制资源（BPMN 文件、流程图图片） | 长期 |

> 🎯 **面试点：为什么引擎要分 RU 和 HI 两套表？**（这题很能看出你懂不懂存储设计）
> 因为「**正在跑的**」和「**已经跑完的**」查询特征完全相反：
> - `ACT_RU_*`：表小、**每秒被查很多次**、**要加行锁**（审批人并发点同意）→ 必须精简、必须快
> - `ACT_HI_*`：只写不读、**无限增长**、从不加锁 → 可以慢慢查、可以归档到别的库
>
> 混在一张表里的后果：**历史数据把热数据挤爆，锁竞争还互相影响**。这和 M1 里「业务 Mapper 和统计 Mapper 分开」是**同一类思想：按变化的原因分离**。

**② 业务表（`04-biz-tables.sql` 已建好）**

| 表 | 列数 | 干什么 | **为什么这么建** |
|---|---|---|---|
| `act_designer` | 19 | 流程设计器模板 | **业务侧的流程表**。`EN_CODE` 是桥接键，`JSON` 列存整张流程图的节点树（前端拖拽用的数据结构，不是 BPMN） |
| `contract_audit_form` | 62 | **审批单** | 把合同的关键字段（`SUBJECTS`/`PARTNERS`/`AMOUNT`/`STAMP_ORDER`…）**抄一份**存进来。`INSTANCE_DEF_KEY` 指向流程，`EXT_DATA` 存扩展数据 |
| `contract_point_log` | 13 | **事件流水** | `CONTRACT_ID` + `POINT`（事件类型）+ `BUSINESS_JSON` + `CREATE_BY_ID`；`CONTRACT_ID` 和 `POINT` 上都建了索引（因为按这两个查） |

### ★ M2 最重要的表设计：一条四跳的「桥接链」

**这是整个 M2 的骨架**，理解了它就理解了「业务系统怎么用流程引擎」：

```
contract_draft.CONTRACT_TYPE          （M1：合同是哪个类型）
        ↓  查 form 表
form.INSTANCE_DEF_KEY = 'swhtsp'      （M1-T5：这个类型走哪条审批流）
        ↓  按 EN_CODE 找
act_designer.EN_CODE = 'swhtsp'       （M2：业务侧的流程定义）
        ↓  SQL: LEFT JOIN act_designer d ON p.KEY_ = d.EN_CODE
ACT_RE_PROCDEF.KEY_ = 'swhtsp'        （引擎侧：Activiti 认的流程定义 key）
        ↓  引擎启动实例后产生
ACT_RU_TASK                           （待办任务，审批人在这里看到）
```

**三个关键观察**：

1. **`EN_CODE` = `KEY_`，一个字符串两个世界的名字**。业务侧叫「流程编码」，引擎侧叫「流程定义 key」，**靠字符串对齐**——这就是「桥接」的字面含义。
   证据在 `TaskMapper.java`，每一条待办查询都写了这句：
   ```sql
   LEFT JOIN act_designer d ON p.KEY_ = d.EN_CODE
   ```
   **为什么要 join 而不是只查引擎表？** 因为 `ACT_RU_TASK` 里只有流程 key，**没有业务信息**（流程分类、流程名、图标）。要按「审批/变更」分类过滤待办，就必须 join 回业务表。**这是"引擎表只存流程、业务信息存业务表"的必然代价**。

2. **引擎表被「当业务表查」**。`TaskMapper` 里的 SQL 是 `ACT_RU_TASK` / `ACT_HI_TASKINST` **直接 JOIN 业务表**。这说明这个项目**没有把引擎表完全隔离**——查询时是直连的。好处是灵活，代价是**深度绑定 Activiti 的表结构**，换引擎要重写这些 SQL。

3. **`act_designer` 的表结构风格和别处不一样**：它用 `decimal(11,0)` 当布尔标志（`DELETE_MARK`/`ENABLED_MARK`）、用 `CREATOR_TIME`/`LAST_MODIFY_TIME` 而不是 `CREATE_TIME`/`UPDATE_TIME`、**连主键都没定义**。这是**另一套代码生成器留下的痕迹**——正是「外挂模块」的证据。
   > 我在 `03-missing-base-tables.sql` 里给它补了主键和 `EN_CODE` 索引（原表两个都没有）。**能注意到"这张表风格不对"本身就是读懂系统的表现。**

▶️ **操作步骤**
1. 进「审核流程管理」，新建一个流程（比如 key = `contract_audit`）

🧠 **原理**

🧠 **原理 · `beginAudit` 内部干了什么**

```java
beginAudit(contractId)
  ├─ 1. 查合同 + 审批单
  ├─ 2. 四道校验：状态必须 '0' 拟定中 / 不能处于协同中 / 审批状态必须是 '0' 未审批 / 必须选了流程（instanceDefKey 非空）
  ├─ 3. 置合同状态：CONTRACT_APPROVE_STATUS='1'、CONTRACT_STATUS='3'、CONTRACT_APPROVE_APPLY_TIME=now
  ├─ 4. 生成【审批单号】AUDIT_CODE（编号规则 BILL_CODE = 'APPROVE_ORDER_RULE'），审批单 AUDIT_STATUS='1'
  ├─ 5. 分支：非存量合同（CONTRACT_STOCK='0'）→ 发通知 + 发 AuditFlowEvent(TYPE_START)
  │         存量合同（CONTRACT_STOCK!='0'）→ 直接置 CONTRACT_STATUS='6' 履行中，跳过整个审批
  └─ 6. FlowAuditService 接住事件：组装流程变量 → 启动流程实例 → 回写审批单 INSTANCE_ID → 由 AsyncUpdateService 把当前任务写进审批单
```

> ⚠️ **两处和"想当然"不一样（实测纠正，对着源码 `ContractAuditServiceImpl.beginAudit` 核过）**：
> - **合同编号不在这一步生成**：`beginAudit` 生成的是**审批单号**（`AUDIT_CODE`）；合同编号的生成代码是**注释掉的**（源码注释写着"客户要求审批通过之后再生成合同编号，先禁用"），真正生成合同编号是在 **`complete`（审批通过）** 里。
> - **`contract_his` 快照在开源版没有落地**：`ContractHis` 实体和 `ContractHisMapper` 都在，但**全项目没有任何地方往里写数据**（连 Service 都没有）。所以"提交时把合同冻结成副本"是这张表的**设计意图**，不是当前实现。
> - 另外，`CURRENT_REVIEWER` 这个列**没有任何代码写它**（全项目搜不到 `setCurrentReviewer`）；"当前该谁审"是写在审批单 `contract_audit_form` 的 `CURRENT_TASK` / `CURRENT_ASSIGNEE` 上，由 `AsyncUpdateService` 回填的。

**「快照」这个思路仍然值得记住**（这是审批类系统的通用答案）：审批过程中如果又去改合同，审批人看到的内容会变，正确做法是提交时冻结合同副本，**审批看的永远是提交那一刻的样子**。
> 面试点：「审批过程中数据被改了怎么办？」→ 快照。这也是「为什么需要 `contract_his` 这张表」的答案——**表建了、思路对，但开源版主流程没写这条数据**，你要能说清这个区别。

**「流程变量」是 Activiti 的核心机制**：流程图里的条件分支（比如「金额 > 100 万要总监审批」）靠的就是流程变量。变量在启动时传进去，引擎在网关节点上求值。

> 📋 **实际传进去的流程变量**（`FlowAuditService.start` 里逐个 `variables.put(...)`，条件分支能用的就是这些名字）：`CONTRACT_ID`、`合同名`、`签约主体`、`合作方`、`收支类型`、`合同金额`、`币种`、`生效时间`、`截止时间`、`印章类型`、`盖章顺序`、`合同类型`、`apply`、`applyName`、`applyDept`、`applyDeptName`、`remarks`、`applyTime`、`isTemplate`、`deptLeader`、`companyLeader`，以及按岗位动态注入的 `P_{岗位flowCode}`（或签）与 `P_{岗位flowCode}_LIST`（会签）。
> ⚠️ **条件分支里写的变量名必须和上面完全一致（中文名也要一样）**，对不上时引擎在网关处抛 `Unknown property`。

⚠️ **关于「提交审批时插一条 `contract_point_log`」**：确实会写一条，但不是在 `beginAudit` 里直接写，而是 `beginAudit` 发一个 `ContractEvent(audit)` 事件，由 `ContractPointLogServiceImpl`（`@EventListener`）接住后落库——又是一次"事件解耦"（同一套模式在本模块里用了两回）。

🧠 **原理 · 「同意」这个动作跨越了两个世界**

```
用户点「同意」
   ↓  POST /activiti/process/complete  { taskId, comment }
【流程世界】Activiti：
   complete(taskId) → 引擎推进到下一个节点
   → 触发监听器（FlowEndListener / UserTaskListener / ApprovedCounterSignCompleteListener）
   ↓
【业务世界】FlowAuditService（桥接层）：
   监听器回调进来 → 用 instanceId 反查业务单
   → 调 ContractAuditService.auditSuccess()
   → 改 contract_draft 状态 + 写 contract_point_log
```

**为什么要绕这一圈？** 因为**流程引擎不该知道业务状态**。Activiti 只知道「流程走到哪了」，不知道「合同是待签署还是已作废」。把两者解耦的好处是：**换流程引擎不用改业务代码，改业务流程不用改业务代码**。
> 面试点：这是「**依赖倒置**」的实例——业务定义接口（监听器），引擎在恰当时机回调。同一套模式在 Spring 的事件机制、MQ 消费里都是这个样子。

**`contract_point_log`（事件日志）就是在这条链的末端被写进去的**。它记录 `合同ID + 事件类型 + 操作人 + 时间 + 备注`，是整条合同生命周期的流水账。

## M2 踩坑预警

| 症状 | 大概率原因 |
|---|---|
| 启动报 Activiti 建表错误 | 库里 `ACT_*` 表是**旧版本** Activiti 建的，跟当前依赖版本不匹配。看 `ACT_GE_PROPERTY` 里的 `schema.version`；对不上就 `DROP` 掉全部 `ACT_*` 表让引擎重建 |
| `/activiti/**` 全部 404 | `zxcm-workflow` 没被 Maven 识别 → IDEA Reload Maven Project |
| 提交审批报「没有可用的流程定义」 | 流程**只保存没发布**（PUT 存了设计，没调 `deploy`） |
| 提交后待办列表空 | 流程节点指定的是**角色**而不是**具体人**，但你登录的账号没有那个角色 |
| 同意后合同状态没变 | 流程**走完了但监听器没触发**（`FlowEndListener` 没注册上），或走完了但没到终点（还有下一个节点） |
| 重复提交审批 | 忘了校验合同状态——`beginAudit` 必须先判断 `CONTRACT_STATUS='0'` |
| 流程图画了条件分支但不走分支 | 流程变量没传，或变量名和条件表达式里的名字不一致（见 T3 的变量清单） |
| 提交审批报「找不到下一位审批人，审批暂时无法继续。请联系管理员检查流程审批节点、岗位成员或部门负责人配置。」| 流程节点绑的是**岗位 / 部门负责人**，但该岗位没人、或部门没配负责人——引擎抛的 `Unknown property` 被 `FlowAuditService` 翻译成了这句中文（**别去猜是代码坏了，先查组织架构**）|
| 提交审批报「合同还在协同中，请先结束协同再发起审批」 | 合同 `COORDINATION_STATUS='1'`（协同中），得先结束协同 |
| 提交审批报「当前合同不能发起审批」 | `CONTRACT_APPROVE_STATUS` 不是 `0`（撤销 / 驳回过的合同要先回到未审批） |
| 待办列表报 SQL 语法错 | `ProcessServiceImpl.getInnerJoinSql` 把用户输入**字符串拼接**进 SQL（注入面），关键词带引号/特殊字符就炸 |
| 审批通过后报空指针 / 状态没变 | `FlowEndListener` 直接 `execution.getVariable("pass").toString()`——**流程图里没设 `pass` 变量就会空指针**；而且它**只在 `pass=="true"` 时**才回调 `auditSuccess`。驳回是另一条路（`reject` → `runtimeService.deleteProcessInstance`），**根本不会**触发这个监听器 |
| `contract_point_log.BUSINESS_JSON` 永远是 null | `ContractEvent` 的 4 参构造器**声明了 `businessJson` 形参却没赋值**（源码 bug）——事件日志的"业务数据"列填不上，不是你库配错了 |

## 🎤 怎么对面试官讲

> 被问到 M2 时，用 3~5 句把「状态机 + 引擎解耦 + 桥接」串起来，别背 API：
>
> 「M2 做的是合同的审批流。**状态机我没有做成规则表**——状态值定义在 `ContractEnums`，迁移规则散在 `beginAudit` / `complete` / `reject` 这些方法里；好处是读一处就懂一个迁移，缺点是**没有全局视图、改状态容易漏**，这也是我想改进成显式状态机（比如 Spring StateMachine）的地方。
> 流程引擎我引的是 Activiti 7，它是**外挂**的：自己一套 24 张 `ACT_*` 表，不碰业务表。
> 关键在**解耦**：合同侧发起审批时**不直接调引擎**，只发一个 `AuditFlowEvent`；由 `FlowAuditService`（`@EventListener` 桥接层）接住再启动流程实例——这样合同模块**不知道 Activiti 的存在**，换引擎不用改业务代码。
> 业务和引擎之间靠**一条四跳桥接链**对齐：`contract_draft.CONTRACT_TYPE → form.INSTANCE_DEF_KEY → act_designer.EN_CODE → ACT_RE_PROCDEF.KEY_`，最后落到 `ACT_RU_TASK` 的待办任务。
> 状态一致性上，除了几列状态字段，我还用 `contract_point_log` 事件日志作为**真值来源**——**状态列是快照、事件日志是流水**，两者职责不同、不是二选一。」
