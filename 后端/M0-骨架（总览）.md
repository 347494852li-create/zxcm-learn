## 📊 M0 用到的技术 & 表（整个项目的技术栈全景，只在这里讲一次）

M0 不写业务，但它把**后面 M1-M4 要用的全部技术**都装好了。所以技术栈全景放在这一节讲，后面各篇只讲「某个技术在这个功能里怎么用」。

### 技术栈

| 层 | 技术 | 版本 | 在项目里的角色 |
|---|---|---|---|
| **JDK** | Java | **11** | ⚠️ 本机命令行默认 JDK 15，必须切到 11，否则 Lombok 编译失败 |
| **容器** | Spring Boot | **2.6.4** | 单体应用，打包成一个 `zxcm-admin.jar` |
| **构建** | Maven | 多模块 | 父 pom + 7 个模块（`ruoyi-admin` / `ruoyi-base` / 5 个 `zxcm-*`） |
| **ORM** | MyBatis-Plus | **3.5.2** | `BaseMapperPlus` 零 SQL CRUD；**几乎不用 XML** |
| **鉴权** | Sa-Token | **1.29.0** | 登录、token、`@SaCheckPermission` 权限注解 |
| **工作流** | Activiti | 7.x | M2 用；**24 张 `ACT_*` 表在 M0 就自动建好了** |
| **缓存** | Redis + Redisson | Redis 7.2.1 | token-session、菜单权限缓存、验证码；Redisson 做分布式锁 |
| **数据库** | MySQL | 8.0.46 | 跑在虚拟机 Docker 里 |
| **连接池** | HikariCP | — | Spring Boot 默认 |
| **接口文档** | Knife4j | — | `http://localhost:8080/doc.html`（M1 起天天用） |
| **Excel** | EasyExcel | — | M1 的导入导出 |
| **前端** | Vue 2 + Element UI | 2.6.12 / 2.15.6 | **不由你编写**，整包复制 |
| **前端构建** | Vue CLI | 4.4.6 | 跑在 80 端口 |

> 🎯 **面试点**：「你项目的技术栈是什么？」——**不要只背名词**。挑 2-3 个说自己**为什么用它**：
> - **MyBatis-Plus 而不是 JPA**：这个项目 SQL 密集（报表、统计），MyBatis 的可控性更重要；同时 MP 的 `BaseMapperPlus` 又省掉了 90% 的 CRUD 样板代码。
> - **Sa-Token 而不是 Spring Security**：Sa-Token 更轻、API 更直白（一行 `StpUtil.login()`），权限注解 `@SaCheckPermission` 一眼看懂。代价是生态不如 Spring Security、复杂场景（OAuth2、SSO）支持弱。
> - **Activiti 而不是自研状态机**：审批流是合同系统的核心域，流程会变（加签、驳回、并行审批），自研状态机很快就撑不住。代价是引擎表 24 张、模型和业务表要桥接（M2 的重点难点）。

### 数据库全景：77 张表，先分清「谁设计的」再看「怎么进库的」

**打开 Navicat 会看到 77 张表，别急着背。** 先站在**学习者**的位置问三个问题：**这张表谁设计的？为什么需要它？我什么时候会真正用到它？** 按这个标准，77 张表只有 **三个来源**：

| 来源 | 表 | 谁设计 / 谁建 | 为什么需要它 | 你第一次真正用到 |
|---|---|---|---|---|
| ① **框架系统表**（26 张）| `sys_*`(24) + `gen_*`(2) | **RuoYi 框架原作者**设计；你跑脚本导入 | 「登录、认人、发菜单、记日志」——**任何 RuoYi 后台都有这几十张，不是合同系统特有的** | **M0 登录那一刻**（没 `sys_user` 谁都进不去）|
| ② **业务表**（27 张）| `conf_*` `contract_*` `template_*` `form` `act_designer` `work_handover` | **肇新合同系统原作者**设计；你跑脚本导入 | 合同「草拟 → 审批 → 用印 → 归档」的全生命周期数据 | **M1 开始时**（T2 第一张业务表）|
| ③ **引擎表**（24 张）| `ACT_*` | **Activiti 引擎启动时自己建**，不用你管 | 审批流程要跑，引擎得有自己的运行时 / 历史表 | **M2 提交审批时**（M0 启动后端它就自动建好了）|

> 💡 **三种来源，对你的要求不同——这才是要记住的**：① 你「**会用**」就行；② 你「**要讲得出为什么这么设计**」（答辩主要考这个）；③ 你「**知道它干嘛**」就行。
> ⚠️ **还有第四种：你自己设计的表**——M4 的 `contract_borrow`（合同借阅）答案册里没有，得你自己加。**作品集里能说「我设计的表」的，只有这一类。**

**再补一个「工程视角」**（知道就行，不影响你学业务）：这 77 张是分四批进你库里的——

| 批次 | 表 | 张数 | 谁让它进库的 | 什么时候 |
|---|---|---|---|---|
| ① 框架底座表 | `sys_*` + `gen_*` | 26 | 你跑 `01-zxcm-learn-base.sql` | M0 · T4-T5 |
| ② 非业务必需表 | `form` + `act_designer` | 2 | 你跑 `03-missing-base-tables.sql` | M1-T5 / M2 之前 |
| ③ 业务表 | `conf_*` `contract_*` `template_*` `work_handover` | 25 | 你跑 `04-biz-tables.sql` | M1 开始时 |
| ④ Activiti 引擎表 | `ACT_*` | 24 | **引擎启动自建** | M0 · T7 第一次启动后端 |

**26 + 2 + 25 + 24 = 77。** M0 结束时库里是 **50** 张（① + ④，即 26 系统表 + 24 引擎表）；剩下 27 张（②③）在 M1 开始前补。

> ⚠️ **别把上面两张表搞混**：「来源」表里 ② 业务表是 **27** 张，「批次」表里 ②+③ 才是 27 张——因为 `form`/`act_designer` 名字不带业务前缀，**本质却是业务表**（见下）。

> 📖 **每张表「为什么这么设计、重要字段、谁在读写」的唯一归口 → [D0 · 数据库表地图](D0-底座表地图.md)**。本节只讲「这些表跟你的关系」，细节一律去 D0 查。

> ⚠️ **为什么 `form` / `act_designer` 要单独一个脚本（批次 ②）**：`01` 的筛选条件是「只留 `sys_` / `gen_` 开头的表」，这两个表名既不带 `sys_` 也不带 `gen_`，**被一并排除了**。但它们**是业务表**——`form` 是合同类型（含 56 条初始数据）、`act_designer` 是流程设计器（M2 必需）。**这是「按名字前缀过滤」的典型漏洞**：白名单规则是人写的，总会有按业务语义分组的表意外落网。详见 [M1 · T5](M1-基础数据与合同CRUD（总览）.md#t5--合同类型配置在-zxcm-form-模块里) 和 [M2](M2-审批流与事件状态机（总览）.md)。

### 三个中间件（都在虚拟机里）—— 用「谁做的 / 为什么 / 我用到哪一步」的账本视角看

> **这里把「数据库表」那套账本视角，同样用到「中间件」上**：它们**都不是你写的**，但**是你部署、你要负责讲清楚为什么需要它们**。

| 中间件 | 谁做的 · 谁部署的 | 为什么需要它（它解决什么）| 你在项目里用到哪一步 | 地址 |
|---|---|---|---|---|
| **MySQL 8.0.46** | Docker 官方镜像；**你在虚拟机里 `docker run` 部署** | 关系型落库的事实标准 | 建 `zxcm` 库、跑 `01` 脚本建 26 张框架表；**M1 起每站都写它** | `192.168.56.10:3306`，库 `zxcm`，`root/root` |
| **Redis 7.2.1** | Docker 官方镜像；**你部署** | 需要一个**跨实例共享**的快速存储 | **验证码 / token-session / 菜单权限缓存**（M0 就用上）；**后面 `@RepeatSubmit` 防重、编号预览缓存**也全靠它 | `192.168.56.10:6379`，**`database: 5`**，密码 `root` |
| **Activiti 7** | **开源工作流引擎**（RuoYi 已集成）；**无独立服务** | 审批流不该手写状态机，交给引擎 | **引擎嵌入在应用里**，启动时**自建 24 张 `ACT_*` 表**（存在同一个 MySQL 库）| 无独立地址 |

**虚拟机默认是关机的**。每次开工第一步是 `ping 192.168.56.10`——不通就是没开机（`ERROR 2003 (10060)`）。

> ✅ **面试口径**：这**三个中间件都不是我写的**，是我在虚拟机里用 Docker / 框架集成**部署**的；**MySQL 管落库、Redis 管共享缓存（token + 防重 + 编号预览）、Activiti 管审批流**。**能说清「为什么需要它」比「它怎么装」更重要。**

## 附录 · M0 接口链路实测记录

2026-09-18 实测。**故意走前端 devServer 的 80 端口**而不是直连 8080——这样才能同时验证 `vue.config.js` 里的代理真的生效。

| # | 验证项 | 结果 |
|---|---|---|
| 0 | 代理生效（`curl http://localhost/dev-api/captchaImage`） | ✅ `/dev-api` 前缀被去掉并转发到 8080 |
| 1 | 中间件 + Web（`/captchaImage`） | ✅ `{"code":200,...}` |
| 2 | 验证码入 Redis（读 db5 的 `captcha_codes:<uuid>`） | ✅ 拿到答案，证明 Redis 真在工作 |
| 3 | 登录换 token（`POST /dev-api/login`） | ✅ `data.token` 是 `eyJ...` 开头的 JWT |
| 4 | 解 JWT payload | ✅ `{"loginId":"00000000:sys_user:1"}` |
| 5 | 拉用户信息（`GET /dev-api/getInfo`） | ✅ `permissions:["*:*:*"]`、`roles:["admin"]` |
| 6 | 拉菜单树（`GET /dev-api/getRouters`） | ✅ **25 个节点**，与底座脚本记录一致 |
| 7 | 用户列表（`GET /dev-api/system/user/listWithP`） | ✅ `total:1` |
| 8 | 前端静态资源（`curl http://localhost/`） | ✅ 标题「合同管理系统」，`app.js` 等 200 |

**四条值得记住的观察**

1. **`loginId` 是 `00000000:sys_user:1`，不是裸 `1`**。格式是 `租户号:表名:用户id`，前 8 位 `00000000` 是系统内置租户。这是多租户设计在 token 里的体现。
2. **`permissions` 返回 `["*:*:*"]` 而不是一长串权限码**——超管走**短路分支**，`SysPermissionService.getMenuPermission()` 直接返回通配符，**不查 `sys_menu`**。
   > ⚠️ **判定超管靠 `sys_user.SYSTEM_ADMIN=1` 这个字段**（`SysUser.isAdmin()`），**跟 `sys_role` 表毫无关系**。`zxcmAdmin` 挂的角色是「系统管理员」「档案管理员」，**并没有**挂名叫「超级管理员」的角色。所以「改角色权限动不了超管」。详见 [D2 第零部分 0.3](D2-前后端调用链路.md)。
3. **想验证「权限码真的来自 `sys_menu`」目前做不到**——库里只有 `zxcmAdmin` 一个用户，它必然走短路分支。要验证得先在「用户管理」里新建一个普通用户并分配角色。**这件事留到 M1 做角色/菜单相关时才顺手做**。
4. **`listWithP` 和 `list` 都返回 `total:1`**，差别在于前者 SQL 被 `@DataPermission` 改写过。
