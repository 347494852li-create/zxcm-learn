## 0.2 功能权限 vs 数据权限（先把这张表记住）

| 维度 | 功能权限（D1/D2 讲的） | 数据权限（本篇） |
|---|---|---|
| 管什么 | 能不能调用这个接口 / 看到这个按钮 | 调用成功之后，能看到**哪些行** |
| 落在哪 | `sys_menu.perms`（`conf:contractCounterpart:list`） | `sys_role.partner_permission`（`1`~`7`） |
| 谁校验 | `@SaCheckPermission` → Sa-Token | `@DataPermission` → MyBatis-Plus 拦截器 |
| 校验时机 | 进 Controller **之前** | **SQL 发出之前**（改 SQL） |
| 失败表现 | 403 / 前端按钮不显示 | 接口 200，但列表少了几行（**静默**） |
| 本项目枚举 | —— | `ContractPermission`（外挂）+ `DataScopeType`（RuoYi 原生） |

> **面试里最值钱的一句话**：功能权限是"门禁"，数据权限是"从门里进去之后你能进哪几个房间"。两个都做完了，才叫"权限体系完整"。很多候选人只答得出第一层。

# 第一部分 · 从一个真实接口切入

拿 M1-T3 刚落地的「合作方列表」当标本，这是它 Mapper 上的注解原文（`conf/mapper/TContractCounterpartMapper.java:46-64`）：

```java
@DataPermission(value = {@DataColumn(key = "userId", value = "a.contract_counterpart_head")},
    resource = DataPermissionResource.partnerPermission)
@Select("select a.*,b.NICK_NAME as headName "
    + "from  conf_contract_counterpart a left join sys_user b on a.CONTRACT_COUNTERPART_HEAD = b.USER_ID "
    + "${ew.customSqlSegment}")
List<TContractCounterpartVo> getListJoinSysUserWithPermission(@Param(Constants.WRAPPER) QueryWrapper<TContractCounterpart> lqw);

// 另外两个：selectPartnerByPermission / selectPagePartnerByPermission（都不带 join，用于分页和写前校验）
```

三个字段各有分工，**缺一不可**：

| 元素 | 值 | 作用 |
|---|---|---|
| `@DataColumn.key` | `userId` | 决定了 SpEL 模板里 `#userId` 这个名字绑定到什么 |
| `@DataColumn.value` | `a.contract_counterpart_head` | 绑定成**列名**（带表别名）。这一列就是"数据归属人" |
| `resource` | `partnerPermission` | 反射去 `RoleDTO` 上读哪一列（即 `PARTNER_PERMISSION`） |

> **为什么 key 必须叫 `userId`？** 因为 `ContractPermission` 的模板里写死了 `#{#userId}`。你换个别名，模板就找不到变量 → SpEL 报错。这是硬耦合，改不了（除非改枚举）。

## 1.1 哪些方法过滤、哪些不过滤 —— 这张表要能背出来

同一个 Mapper 里有 4 个查询方法，**只有 3 个带注解**：

| Mapper 方法 | 有 `@DataPermission`？ | Service 调用者 | Controller 入口 |
|---|---|---|---|
| `selectVoPage`（MP 自带） | ❌ 无 | `queryPageList` | 无（未暴露） |
| `selectPagePartnerByPermission` | ✅ | `queryPermissionPageList` | **`GET /list`** ← 前端在用的 |
| `getListJoinSysUserWithPermission` | ✅ | `queryListWithPermission` | 无 |
| `getListJoinSysUser` | ❌ 无 | `queryList` | 无 |

**结论**：`/list` 走的是带权限那条；`queryPageList` 那条路虽然写好了但**没有任何 Controller 暴露它** —— 注释掉一半的代码，属于历史残留。

## 1.2 实测：一条 SQL 是怎么被改写的

假设当前用户在 `sys_role` 上的 `PARTNER_PERMISSION = '5'`（仅本人），且 `userId = 100`。

**发出去之前**（Mapper 里写的）：
```sql
SELECT * FROM conf_contract_counterpart WHERE (DEL_FLAG = '0' AND COMPANY_TYPE = '0')
```

**拦截器改写之后**（真正发给 MySQL 的）：
```sql
SELECT * FROM conf_contract_counterpart
WHERE (DEL_FLAG = '0' AND COMPANY_TYPE = '0')
  AND ( contract_counterpart_head = 100 )
```

如果角色是 `'3'`（部门），就变成：
```sql
  AND ( contract_counterpart_head IN ('100','101','102') )
```

如果角色是 `'1'`（全部），**什么都不加**：
```sql
SELECT * FROM conf_contract_counterpart WHERE (DEL_FLAG = '0' AND COMPANY_TYPE = '0')
```

> ⭐ 注意 `AND ( ... )` 外面那层括号。`getSqlSegment` 里特意包了一层 `Parenthesis`（`Handler:109`），注释写着"数据权限使用单独的括号 防止与其他条件冲突"。这是防 `a OR b` 被拼成 `x AND a OR b` 的经典括号陷阱。

# 第二部分 · 注解层

## 2.1 `@DataPermission`（`common/annotation/DataPermission.java`）

```java
@Target({ElementType.METHOD, ElementType.TYPE})   // ★ 方法级 + 类级都能挂
@Retention(RetentionPolicy.RUNTIME)
public @interface DataPermission {
    DataColumn[] value();                                    // 数组，可以配多列
    DataPermissionResource resource() default DataPermissionResource.base;
}
```

两个设计点：

1. **`value()` 是数组**。为什么要多列？因为一条 SQL 可能 join 了多张表、要同时按两个字段过滤。此时 `joinStr`（`" OR "` / `" AND "`）会把两个条件拼起来 —— 读操作是 OR（任一角色命中即可），写操作是 AND（必须全部满足，更严格）。
2. **`resource` 默认 `base`**。`base` 走的是 RuoYi 原生那套（`sys_role.data_scope` + `DataScopeType`），本项目合同模块**全部覆盖成了自己的资源**。所以判断"这段逻辑走哪条分支"看的就是 `resource` 是不是 `base`（`Handler:139`）。

## 2.2 `@DataColumn`（`common/annotation/DataColumn.java`）

```java
@Target(ElementType.METHOD)
public @interface DataColumn {
    String key() default "deptName";
    String value() default "dept_id";
}
```

- `key` → SpEL 变量名（本项目合同模块统一用 `userId`）
- `value` → 拼进 SQL 的**列名**（可带表别名 `a.xxx`）

> ⚠️ `value` 是**字符串拼接进 SQL** 的，不是参数占位符。所以这个注解只能由开发者写在代码里，**绝对不能**让用户输入参与。见 8.4。

## 2.3 `DataPermissionResource`（`common/enums/permissionType/DataPermissionResource.java`）

```java
base("base", "默认"),
draftPermission("draftPermission", "草拟中的合同权限"),
contractPermission("contractPermission", "审批完成的合同权限"),
dashboardPermission("dashboardPermission", "仪表盘权限"),
collabPermission("collabPermission", "协同权限"),
ledgerPermission("ledgerPermission", "台账权限"),
stampPermission("stampPermission", "用印权限"),
planPermission("planPermission", "计划权限"),
comparePermission("comparePermission", "合同比对数据权限"),
partnerPermission("partnerPermission", "相对方数据权限"),
workPermission("workPermission", "工作交接数据权限");
```

**这个枚举的 `index` 必须和 `sys_role` 的列名一一对应**（源码注释原话）。`Handler:141` 是这么用的：

```java
String resourceP = (String) ReflectUtil.getFieldValue(role, dataPermission.resource().getIndex());
```

`ReflectUtil.getFieldValue` 接收的字符串是**字段名**。它拿 `"partnerPermission"` 去找 `RoleDTO` 上的字段。**所以 `RoleDTO` 上必须有一个叫 `partnerPermission` 的字段，`sys_role` 上也必须有 `partner_permission` 列** —— 名字对不上就永远是 `null`，然后走 `return ""` = 看全部（这也是 8.3 那个安全点的根因）。

> **实测**：`sys_role` 上这 11 个 `*_PERMISSION` 列**都存在**（`PARTNER_PERMISSION` 也在，两个建表脚本都有）。`RoleDTO` 上对应的字段也都在。所以配置链路是通的。

# 第三部分 · 拦截器层

## 3.1 它是怎么被挂进 MyBatis-Plus 的

`ruoyi-framework/config/MybatisPlusConfig.java`：

```java
:51   addInnerInterceptor(dataPermissionInterceptor());
:62   private InnerInterceptor dataPermissionInterceptor() { return new PlusDataPermissionInterceptor(); }
```

`InnerInterceptor` 是 MyBatis-Plus 的**插件 SPI**（分页、乐观锁、防全表更新都靠它）。`PlusDataPermissionInterceptor` 继承了两个东西：

```java
public class PlusDataPermissionInterceptor extends JsqlParserSupport implements InnerInterceptor
```

- `InnerInterceptor` → 提供 `beforeQuery` / `beforePrepare` 钩子
- `JsqlParserSupport` → 提供 `parserSingle` / `parserMulti` + `processSelect/Update/Delete` 模板方法（省掉手写 jsqlparser 的样板）

> **这正是功能权限和数据权限的技术分水岭**：功能权限（Sa-Token）是 **AOP 环绕**，在方法调用外面拦；数据权限是 **SQL 拦截器**，在方法进入之后、SQL 落地之前改 SQL。两者的插入点根本不在同一层。

## 3.2 两个钩子，分工明确

| 钩子 | 触发时机 | 处理什么 | 调用 |
|---|---|---|---|
| `beforeQuery` (`:51`) | 查询前 | SELECT | `parserSingle(sql, ms.getId())` → `processSelect` |
| `beforePrepare` (`:66`) | 预编译前 | **仅** UPDATE / DELETE | `parserMulti(sql, ms.getId())` → `processUpdate` / `processDelete` |

**为什么 UPDATE/DELETE 走 `beforePrepare` 而 SELECT 走 `beforeQuery`？**
因为 MyBatis-Plus 的插件链里，`beforeQuery` 只对 `SELECT` 可靠地触发；写操作要拦在 `StatementHandler` 预编译那一步（`beforePrepare` 里手动判 `sct == UPDATE || sct == DELETE`）。

## 3.3 三道"快速跳过"闸门

不要以为每次查询都会做一遍反射+SpEL+SQL 解析，那样性能早就崩了。它有三级短路（`Interceptor:53-58`）：

```java
if (InterceptorIgnoreHelper.willIgnoreDataPermission(ms.getId())) return;   // ① 方法上有 @InterceptorIgnore
if (dataPermissionHandler.isInvalid(ms.getId())) return;                    // ② 缓存里确认"这方法没注解"
```

- **① `@InterceptorIgnore`**：MyBatis-Plus 原生注解。写 `@InterceptorIgnore(dataPermission = "true")` 可以强制跳过。定时任务、系统内部查询常用这招。
- **② `inavlidCacheSet`**：`getSqlSegment` 第一次发现某个 `mappedStatementId` 没有注解时，就把它丢进这个 Set（`Handler:90`）。以后每次查询直接命中 Set 返回，**连反射都省了**。注意源码把这个字段拼错了 —— `inavlid`（少个 `i`），不影响功能，但看到别以为是自己眼花。

还有第三级在 `findAnnotation` 里：`dataPermissionCacheMap`（`ConcurrentHashMap`）缓存"方法/类 → 注解实例"。注解是运行期不变的，缓存一次终身有效。

## 3.4 `mappedStatementId` 长什么样

它是形如这样的全限定名（MyBatis 内部约定 = `Mapper接口全名.方法名`）：

```
com.ruoyi.conf.mapper.TContractCounterpartMapper.selectPagePartnerByPermission
```

`findAnnotation` 就把它从最后一个 `.` 切开（`Handler:200-203`），拿到 `类名` + `方法名`，然后：

1. `ClassUtil.loadClass(clazzName)` 加载接口
2. 遍历同名方法，找 `@DataPermission` → 找到就缓存返回
3. 方法上没有 → 再看**类上**有没有（`@Target` 里带 `TYPE` 就是为这个）
4. 都没有 → 返回 `null` → 上层标记为 invalid

> **一个坑**：`loadClass` 是按**字符串**反射加载。如果你的 Mapper 方法名被重载（同名不同参），它只按名字过滤会拿到多个 `Method`，然后**取第一个有注解的**。本项目没踩过，但值得知道。

# 第四部分 · Handler 层：`buildDataFilter` 逐行拆

这是最核心的方法（`Handler:123-197`），我按执行顺序拆。

## 4.1 拼 SQL 的"分隔符"随读写变化

```java
String joinStr = isSelect ? " OR " : " AND ";
```

- **读（SELECT）用 `OR`**：用户有多个角色，只要**任一角色**覆盖到这条数据，就该能看见 → 取并集。
- **写（UPDATE/DELETE）用 `AND`**：必须**所有角色**都允许，才准改 → 取交集，更严格。

这个"读并集、写交集"的设计是安全上的好实践，面试可以主动讲。

## 4.2 上下文准备

```java
LoginUser user = DataPermissionHelper.getVariable("user");     // 当前用户
StandardEvaluationContext context = new StandardEvaluationContext();
context.setBeanResolver(beanResolver);                          // 让 @sdss 能用
DataPermissionHelper.getContext().forEach(context::setVariable); // 把 request 里的变量灌进去
```

`DataPermissionHelper` 的存储介质有点特别（`DataPermissionHelper:53,74-85`）：

```java
private static final String DATA_PERMISSION_KEY = "data:permission";
// getContext(): 从 HttpServletRequest 的 attribute 里取 Map
```

**存在 `HttpServletRequest` 的 attribute 里** —— 这是**请求级**作用域，不是 ThreadLocal。意义是：一次 HTTP 请求内多次查询共享同一份变量；请求结束自动销毁，不用担心线程池复用污染。（对比：`LoginHelper` 用的是 `ThreadLocal` + Redis 双级。）

## 4.3 绑列名

```java
for (DataColumn dataColumn : dataPermission.value()) {
    context.setVariable(dataColumn.key(), dataColumn.value());
}
//  → #userId = "a.contract_counterpart_head"
```

**这一步是全篇最容易看错的地方**：`#userId` 拿到的不是"当前用户 id 的数字"，是**一个列名字符串**。模板 `#{#userId} = #{#user.userId}` 展开后是：

```
a.contract_counterpart_head = 100
    ↑ 来自 DataColumn.value()      ↑ 来自 LoginUser.userId
```

左边是"数据归属列"，右边才是"当前用户"。**别以为两边都是 userId。**

## 4.4 遍历角色，两条分支

```java
for (RoleDTO role : user.getRoles()) {
    user.setRoleId(role.getRoleId());          // ← 副作用：把 roleId 塞回 user，供 @sdss.getRoleCustom 用
    if (!dataPermission.resource().equals(DataPermissionResource.base)) {
        // 分支 A：本项目合同模块走这条
        String resourceP = (String) ReflectUtil.getFieldValue(role, resource.getIndex());
        ...
    } else {
        // 分支 B：RuoYi 原生，按 sys_role.data_scope
        DataScopeType type = DataScopeType.findCode(role.getDataScope());
        ...
    }
}
```

**分支 A（外挂合同权限）** 的完整判断树：

```
resourceP = 角色上那一列的值（String "1"~"7"）
  │
  ├─ StringUtils.isEmpty(resourceP)
  │      → return ""            ← ① 没配 = 不过滤 = 全部可见（安全问题，见 8.3）
  │
  ├─ ContractPermission.findCode(resourceP) 找不到
  │      → throw ServiceException("角色数据范围异常 => " + resourceP)
  │
  ├─ type == ALL
  │      → return ""            ← ② 显式"全部" = 不过滤
  │
  └─ 其它
         sql = SpEL 解析 type.getSqlTemplate()
         sqlString.append(joinStr).append(sql)
         isSuccess = true
         if (!isSuccess) sqlString.append(joinStr).append(type.getElseSql());  ← ③ 永远进不来（见 8.2）
```

关键点：
- `return ""` 是**立刻返回**，不是 `continue`。所以只要**遍历到第一个角色**就命中"空"或"ALL"，后面的角色直接被忽略。→ 多角色场景下**结果依赖角色顺序**（`user.getRoles()` 的返回顺序）。这是个隐藏的坑。
- ①②两处 `return ""` 都会让 `getSqlSegment` 里 `StringUtils.isBlank(dataFilterSql)` 成立（`Handler:103`），直接返回原 where —— 等于**这条 SQL 完全没被改**。

## 4.5 收尾

```java
if (StringUtils.isNotBlank(sqlString.toString())) {
    return sqlString.substring(joinStr.length());   // 把开头的 " OR " / " AND " 剪掉
}
return "";
```

`StringBuilder` 是 `" OR " + 条件1 + " OR 条件2"` 拼出来的，所以要把第一个分隔符剪掉。剪的长度正好是 `joinStr.length()`（`" OR "` = 4，`" AND "` = 5）。

## 4.6 回到 `getSqlSegment` 收口

```java
Expression expression = CCJSqlParserUtil.parseExpression(dataFilterSql);
Parenthesis parenthesis = new Parenthesis(expression);       // 单独包一层括号
if (ObjectUtil.isNotNull(where)) {
    return new AndExpression(where, parenthesis);            // 原 where AND (新条件)
} else {
    return parenthesis;                                      // 原 SQL 没 where，直接挂上
}
```

然后 `Interceptor:114-116` 把返回的 Expression `setWhere` 回去，`parserSingle` 会把整棵 AST 重新序列化成 SQL 字符串。**这就是 SQL 被改写的完整闭环。**

# 第七部分 · 面试问答

## Q1. 功能权限和数据权限的区别？

**一句话**：功能权限管"能不能调这个接口"，数据权限管"调通了能看到哪些行"。

展开：
- 功能权限 → `sys_menu.perms` + `@SaCheckPermission` + Sa-Token，**进 Controller 之前**拦，失败 403。
- 数据权限 → `sys_role.*_permission` + `@DataPermission` + MyBatis-Plus `InnerInterceptor`，**SQL 发出之前**改 WHERE，失败是"静默少几行"。
- 两者串行：先过功能权限（门禁），再过数据权限（房间）。只做前者，等于"所有人都能看全部数据"。

## Q2. 为什么要用 MyBatis-Plus 拦截器改 SQL，而不是在 Service 里手写 where？

- **手写的问题**：N 个 Mapper 方法就要写 N 遍，漏一个就漏一个权限洞；而且改条件的位置分散，评审时看不出来。
- **拦截器的好处**：只要在 Mapper 方法上**标一个注解**，所有走这条 SQL 的路径自动生效，**零侵入**。新增查询方法时，配注解即可。
- **代价**：SQL 被动态改写，出问题不好排查（所以要有 SQL 日志）；而且**反射 + SpEL + jsqlparser 三次解析**有性能成本 → 所以才有 3.3 那三级缓存短路。

## Q3. `buildDataFilter` 里的 `joinStr` 为什么读用 OR、写用 AND？

多角色场景：一个用户可能挂多个角色，每个角色配了不同数据范围。
- **读**：任一角色覆盖到，就该能看见 → **并集（OR）**。用户视角"我权限的合集"。
- **写**：必须所有角色都允许，才准改 → **交集（AND）**。防止"一个角色给的全权"被用来改另一个角色本该只看的数据。

这是"最小权限 + 读友好"的折中。

## Q4. `@DataPermission` 是 AOP 吗？

**不是。** 这是很多人会答错的点（和 D1 里 `@SaCheckPermission` 不是 AOP 是同一个陷阱）。

- `@DataPermission` 是给 **MyBatis-Plus 的 `InnerInterceptor` 插件链**用的，注解在**Mapper 方法**上，靠 `mappedStatementId` 反射找到。
- 它作用的对象是**被执行的 SQL**，不是被调用的 Java 方法。
- 对比：`@SaCheckPermission` 也不是 AOP，是 Sa-Token 自己的注解拦截器。

**本项目里真正的 AOP 用在别处**（如日志 `@Log`）。

## Q5. 数据权限和租户隔离是一回事吗？

**不是，是两个正交维度。**
- **租户隔离**（多租户）：`tenant_id` 维度，租户 A 完全看不到租户 B 的数据。本项目用 MyBatis-Plus 的 `TenantLineInnerInterceptor`（另一个 `InnerInterceptor`）实现，而且是 `getSqlSegment:99` 里 `LoginHelper.isTenantAdmin()` **租户管理员跳过数据权限**——两套机制在同一个 handler 里交汇。
- **数据权限**：同一租户/公司**内部**，按角色划分"能看哪些行"。

面试里能讲清"这是两个维度、分别由不同 `InnerInterceptor` 处理"，层次就上去了。

## Q6. 如果角色配了数据权限但查不到数据，你的排查路径？

1. **看角色配了什么**：`SELECT partner_permission FROM sys_role WHERE role_id = ?` → 是 `null`（→ 反而全看，不是这问题）、还是具体 code。
2. **看登录快照**：Redis 里 token-session 的 `LoginUser.roles[].partnerPermission` 是否和库里一致 → 不一致说明**改完没重新登录**。
3. **看有没有命中注解**：断点 `Handler:87`，`findAnnotation` 返回 null 吗？null 说明注解没写到实际调用的方法上（比如 Service 调的是 `selectVoPage` 而不是 `selectPagePartnerByPermission`）。
4. **看数据本身**：`contract_counterpart_head` 这一列**是不是空的**。如果业务数据没维护"负责人"，而权限是"仅本人"，自然一条都匹配不上。→ 这是最常见的"不是 bug 的 bug"。
5. **看归属列对不对**：注解里 `@DataColumn.value` 写的列名，是否真的存在、是否有值。

> 第 4 条特别重要：**数据权限依赖"归属字段"有值**。落 T3 时如果导入的合作方没有 `contract_counterpart_head`，所有非"全部"权限的用户都会看到空列表。这是 M1 落地时最容易踩的坑。

## Q7. 自定义一套 `ContractPermission` 而不复用 `DataScopeType`，有什么风险？

- **好处**：粒度自由（人维度 vs 部门维度）、不用污染原生模块、可以为不同业务资源配不同范围（合同/相对方/用印各一套列）。
- **风险 1 · 一致性**：10 个 `*_PERMISSION` 列要靠开发者手工保证和 `RoleDTO` 字段、枚举 `index` 三处名字对齐，任一错位 → 读出来是 `null` → **静默变成"看全部"**（8.3）。
- **风险 2 · 可维护性**：`DataPermissionResource` 加一个资源，就要同时改 `sys_role` 表、`RoleDTO`、枚举、前端角色配置页四处。没有编译期校验，全靠人。
- **改进方向**：把 `index` 和 `RoleDTO` 字段名的对应做成启动期自检（`@PostConstruct` 反射校验所有 resource 在 RoleDTO 上都有同名字段，缺一个就启动失败）。这在面试里可以作为"我会怎么加固"的加分回答。

# 第八部分 · 坑与设计决策

## 8.1 ⭐ 角色权限是"登录快照"，改完必须重新登录

`SysLoginService.java:248`：

```java
List<RoleDTO> roles = BeanUtil.copyToList(user.getRoles(), RoleDTO.class);
```

角色（含 10 个 `*_PERMISSION`）在**登录那一刻**被拷进 `LoginUser`，然后存进 Redis 的 token-session。之后每次请求，`DataPermissionHelper.getVariable("user")` 拿的是 **Redis 里的快照**，不是实时查库。

**后果**：管理后台改了角色的数据权限，**当前在线的用户不会立即生效**，必须退出重登（或等 token 过期）。

**这算设计缺陷吗？** 一半一半。好处是每次请求不用查库（性能），坏处是权限变更有延迟。企业级做法通常是：改角色权限时**主动踢掉**受影响的在线会话（Sa-Token 支持按 loginId 强制注销），或者把权限读缓存加短 TTL。本项目没做这层。

> **落地提醒**：T3 演示时改 `PARTNER_PERMISSION`，**一定要重新登录**再试，否则会以为"没生效"。

## 8.2 `elseSql` 兜底是死代码

`buildDataFilter:153-163`：

```java
boolean isSuccess = false;
String sql = parser.parseExpression(type.getSqlTemplate(), parserContext).getValue(context, String.class);
sqlString.append(joinStr).append(sql);
isSuccess = true;                          // ← 无条件置 true
if (!isSuccess) {                          // ← 永远为 false，进不来
    sqlString.append(joinStr).append(type.getElseSql());
}
```

`isSuccess` 在赋值 `true` 之前**没有任何条件判断**，所以 `if (!isSuccess)` 分支永远不执行 → `elseSql`（`SELF` 的 `" 1 = 0 "`、`MYDEPT` 的 `" 1 = 0 "`）**永远不会被拼接**。

**后果**：这个"兜底失败就查不到数据"的安全设计**实际上没生效**。如果 SpEL 解析抛异常，是直接向上抛 `ServiceException`（没有 try/catch），而不是走兜底。这是照抄 RuoYi 原生代码时留下的结构（原生 `DataScopeType` 分支里也一样）。

> 不影响正常功能，但**不要以为 elseSql 在保护你**。如果哪天真依赖"解析失败就 1=0"，得自己补 try/catch。

## 8.3 ⚠️ 没配权限 = 看全部（默认放行，不是默认拒绝）

`Handler:142-143`：

```java
if (StringUtils.isEmpty(resourceP)) {
    return "";        // ← 不拼任何条件
}
```

角色的 `partner_permission` 是**空**（`null` 或空串）时，**直接放行全部数据**。

**安全含义**：这是个 **default-allow（默认允许）** 设计，不是 **default-deny（默认拒绝）**。新建的角色如果没有专门去配"相对方数据权限"，那么这个角色能看**所有**合作方数据。

**怎么理解这个选择？** 对新建角色"开箱即用"友好（不用配就能用），但对安全不友好。企业级更稳妥的是 default-deny（没配 = 看不到），或者至少管理员角色的 `ALL` 要显式配。

**排查时的意义**：如果某用户看到的数据**比预期多**，第一反应就查 `partner_permission` 是不是空的。

## 8.4 ⚠️ `@DataColumn.value` 是拼 SQL 的，不是参数

```java
@Select("... ${ew.customSqlSegment}")     // ← ${} 字符串拼接，不是 #{} 预编译
@DataPermission(value = {@DataColumn(key = "userId", value = "a.contract_counterpart_head")})
```

数据权限拼出来的 SQL 也是走**字符串拼接**进最终 SQL 的（`CCJSqlParserUtil.parseExpression` 后序列化）。

**当前安全**：`DataColumn.value` 是**代码里写死的注解属性**，`#user.userId` 来自服务端登录态，`@sdss` 返回的是数据库里查出来的 id 拼的（且都是数字）。**用户输入不能直接进这些位置** —— 用户输入的 `contractCounterpartName` 等走的是 `QueryWrapper.like(...)`，MyBatis-Plus 会用 `#{}` 参数化。

**红线**：永远不要写 `@DataColumn(value = <用户可控的字符串>)`，也不要在 `ContractPermission` 模板里引入用户输入。这里是 SpEL + 字符串拼接双重危险区，一旦有入口就是 SQL 注入。

## 8.5 写操作的数据权限靠"手动查一次"来兜

`TContractCounterpartServiceImpl.updateByBo`（`ServiceImpl:184-192`）：

```java
TContractCounterpart contractCounterpart = baseMapper.selectById(bo.getId());
LambdaQueryWrapper<TContractCounterpart> wrapper = new LambdaQueryWrapper<>();
wrapper.eq(TContractCounterpart::getId, bo.getId());
List<TContractCounterpart> pData = this.baseMapper.selectPartnerByPermission(wrapper);   // ← 带注解的查询
if (pData.size() == 0) {
    throw new ServiceException("您没有权限操作该数据");
}
```

**为什么这么做？** 因为 `updateById` / `selectById` 是 MyBatis-Plus 自带方法，**没有注解**，拦截器不会过滤（也没有 where 可挂）。所以要在写之前，先借一个"带 `@DataPermission` 的查询"确认这行对当前用户可见 —— 查得到才准改。

**这是"数据权限只拦查询"这个设计缺陷的变通补丁**，值得在面试里主动讲：
- 拦截器的拦截点是 SQL 的 WHERE，而按主键 `UPDATE ... WHERE id=?` 的 WHERE 是主键，拦它没意义（用户本来就看不到 id）。
- 所以写路径的权限必须在**业务层**显式补一次"可见性校验"。

**⚠️ 但 `deleteWithValidByIds` 没做这个校验**（`ServiceImpl:266-275`）。它直接 `deleteBatchIds`，只拦了"批量删除"（>1 条报错），**没有校验这条数据是否属于当前用户**。这是 T3 落地后残留的一个权限缺口 —— 只要知道 id，任何人都能删（逻辑删除）。

> 如果要补：在 `deleteWithValidByIds` 里加一段和 `updateByBo` 一样的 `selectPartnerByPermission` 校验。

## 8.6 `user.setRoleId(...)` 污染 `LoginUser`

```java
for (RoleDTO role : user.getRoles()) {
    user.setRoleId(role.getRoleId());     // ← 把循环里的 role 写回 user
```

这个副作用是为了让 `#{@sdss.getRoleCustom( #user.roleId )}`（原生 `CUSTOM` 分支）能取到当前角色 id。但 `user` 是**请求级共享对象**（从 `DataPermissionHelper` 的 request attribute 拿的），循环结束后 `user.roleId` 停在**最后一个角色**上。

**后果**：多角色用户 + 原生 `CUSTOM`(code 2) 权限时，只有最后一个角色生效。本项目合同模块走外挂分支（不读 `roleId`），所以没受影响。

## 8.7 权限列名三处对齐（最容易犯的配置错误）

一个"相对方数据权限"要能工作，需要**三个地方名字对上**：

| 位置 | 值 | 错了会怎样 |
|---|---|---|
| `sys_role` 表列 | `PARTNER_PERMISSION` | 列不存在 → 配置页保存报错 |
| `RoleDTO` 字段 | `partnerPermission` | 字段不存在 → `ReflectUtil.getFieldValue` 抛异常 |
| `DataPermissionResource` 的 `index` | `"partnerPermission"` | 对不上 → 读成 `null` → **静默看全部** |

第三个是**最危险的**，因为它不报错，只是权限失效。这是"字符串弱类型"设计的典型代价。

# 第九部分 · 🎤 一分钟讲法（对着面试官讲）

被问「同一个接口为什么不同人看到的数据不一样」，照这段讲，**一分钟内讲完**：

> 「这套系统里权限分两层。**功能权限是门禁**，管你能不能调这个接口，实现是 Sa-Token 的注解拦截器，在**进 Controller 之前**拦。**数据权限是进屋之后你能开哪几个文件柜**，管你能看到**哪些行**，实现是 MyBatis-Plus 的 `InnerInterceptor`，在 **SQL 发出去之前改 `WHERE`**。两层插入点根本不在同一层。
>
> 数据权限具体怎么改 SQL：Mapper 方法上标一句 `@DataPermission(value = {@DataColumn(key = "userId", value = "a.contract_counterpart_head")}, resource = partnerPermission)`。拦截器先用 jsqlparser 解析这条 `SELECT`，反射找到方法上的注解，再**反射读角色实体上 `partnerPermission` 这一列的值**（取值 1~7），把 `ContractPermission` 枚举里对应的 SpEL 模板求值，最后拼成一段 `AND ( contract_counterpart_head = 100 )` 挂到原来的 `WHERE` 上，套一层括号防条件串味。
>
> **同一个接口、同一份代码——张三看到 3 条、李四看到 30 条，就是这么来的。**」

如果只给 30 秒，就讲这一句：

> 💡 **一句话说人话**：**`@DataPermission` 不拦方法、只改 SQL——它让 MyBatis-Plus 在查询发出去之前，按当前角色的数据范围往 `WHERE` 里加一句「你只能看这些行」。**

**⚠️ 这段里三个必答的坑**：

1. **角色权限是「登录快照」**——`RoleDTO`（含那 10 个 `*_PERMISSION`）在登录那一刻拷进 `LoginUser` 存进 Redis，之后不查库。所以改完角色权限**必须重新登录**才生效（§8.1）。
2. **没配权限 = 看全部**——`partner_permission` 为空时直接 `return ""`，不拼任何条件。这是 **default-allow（默认放行）**，不是默认拒绝（§8.3）。用户看到的数据比预期**多**，第一反应就是查这一列是不是空的。
3. **数据权限依赖「归属字段」有值**——权限模板是按 `contract_counterpart_head` 这种「负责人」列过滤的，如果业务数据这一列是空的，那么所有非「全部」权限的用户都会看到**空列表**。这通常不是 bug，是数据没维护（§7 Q6 第 4 条）。

> ⭐ **进阶收尾**（面试官追问「为什么自己写一套枚举」时）：
> 「原生 RuoYi 的 `DataScopeType` 是**按部门**过滤（模板里写死 `#deptName`），而合同/相对方有明确的负责人字段，权限要落到**人**头上。而且原生的模板被所有走 `base` 分支的模块共用，硬改会污染它们，所以我们外挂了一套独立的 `ContractPermission` 枚举，按 `user_id` 过滤。**代价是三个地方的名字要手工对齐**——`sys_role` 列名、`RoleDTO` 字段名、枚举 `index`，任一错位就读成 `null`、静默变成「看全部」（§8.7）。」
