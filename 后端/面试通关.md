## Part 1 · 面试速通（按 M0→M4）

### 0. 开场：介绍这个项目

#### ★ 3 分钟版（背下来，练到能自然说出来）

> 「我做的是一个**企业合同管理系统**，覆盖合同从草拟到归档的全生命周期。
>
> **业务流程是这样的**：业务员新建合同（选模板、填信息、生成 Word）→ 提交审批，走审批流（支持多级审批、驳回、退回）→ 审批通过后申请用印 → 线下盖章后上传双章合同 → 进入履行 → 到期可续签、异常可作废 → 全程留痕，最后进报表统计。
>
> **技术栈**：Spring Boot 2.6.4 + Java 11，数据访问用 MyBatis-Plus，鉴权用 Sa-Token，审批流用 Activiti 7，前端是 Vue 2 + Element UI，数据库 MySQL 8 + Redis。
>
> **后端分了 7 个 Maven 模块**：`ruoyi-admin` 是启动模块，`ruoyi-base` 是公共能力，业务拆成合同、表单、工作流、通知、第三方接入几个模块——**划分依据是依赖方向，不是业务归属**。比如表单引擎被合同依赖，所以独立成模块。
>
> **我自己做的主要是两件事**：一是把整套系统**从零搭起来**（数据库、中间件、模块裁剪、前后端联调），二是把**合同的核心业务链路**跑通——合同 CRUD、审批流、模板生成、用印归档。
>
> **我觉得这个系统最值得讲的是它的表设计**，有两条一以贯之的原则：**历史不可变**和**按变化原因分离**。整个库 77 张表，业务表零物理外键，状态和留痕分离……」

**几个可以展开的钩子**（面试官往往会顺着其中一个问下去）：
- 「77 张表」→ 展开讲表设计
- 「两条原则」→ 展开讲历史不可变 / 按变化原因分离
- 「依赖方向不是业务归属」→ 展开讲模块划分
- 「Activiti」→ 展开讲流程引擎桥接

#### 被问「前端是你写的吗」

**诚实答**：「前端页面我用的是成熟的 Vue 2 + Element UI 方案，**主要精力放在后端**——我把接口链路、权限、数据流转都跑通了，也能看懂前端的调用链（axios 封装、权限指令、路由动态生成），但页面不是我从零写的。」

> ⚠️ **不要吹**。被追问「那你说说 `v-hasPermi` 怎么实现的」时答不上来很难看。**主动说清自己的边界，比被戳穿强得多**；而且「重后端」对后端岗位是正常的。

#### 🎤 怎么对面试官讲

**面试官说「简单介绍一下你的项目」时，别一上来背那 3 分钟版。** 先给 20 秒的"电梯版"，看他眼神有反应了再展开：

> 「我做一个企业**合同管理**系统，覆盖合同从草拟、审批、用印到归档的全生命周期。技术栈是 Spring Boot + MyBatis-Plus + Sa-Token + Activiti 7，前端 Vue 2。**我主要负责后端**——把整套骨架从零搭起来，再把合同的核心业务链路跑通。」

他要是"嗯"一声示意你继续，再按这个顺序展开（**每一段都留一个钩子，等他问**）：

| 讲什么 | 开场句 | 留的钩子 |
|---|---|---|
| 业务流程 | 「业务流程是这样的：业务员新建合同，选模板、填信息、生成 Word → 提交审批 → 审批通过后申请用印 → 线下盖章后传回双章合同 → 进入履行 → 到期可续签、异常可作废」 | 「多级审批、驳回、退回」→ 引到 Activiti |
| 技术栈 | 「后端 Spring Boot 2.6.4 + Java 11，数据访问 MyBatis-Plus，鉴权 Sa-Token，审批流 Activiti 7」 | 「为什么不用 JPA / Spring Security」→ 引到选型题 |
| 架构 | 「后端分了几个 Maven 模块，**划分依据是依赖方向，不是业务归属**」 | 「依赖方向」→ 引到 M0 模块划分 |
| 我做了什么 | 「一是搭骨架，二是跑通合同核心链路」 | 「搭骨架踩了什么坑」→ 引到项目裁剪 |
| 亮点 | 「最值得讲的是表设计，两条原则：历史不可变、按变化原因分离」 | 这条是**压轴钩子**，等他问再展开 |

**⚠️ 介绍项目时的三个「千万不要」**：

1. **不要从技术栈开始背**。先讲「这是什么系统、解决什么问题」，再讲用了什么技术——面试官先关心你做的东西有没有价值。
2. **不要用「实现了增删改查」这种词**。要说**业务动作**：「提交审批」「上传双章合同」「用印留痕」。同样的代码，说法不同，听感差一个档次。
3. **不要一口气讲满 3 分钟不停**。讲到「多级审批」停一下、讲到「依赖方向」停一下——**留白是给面试官提问的机会**，他顺着问，你才讲得出深度。

**被问「前端是你写的吗」，可以这样开口**：

> 「前端页面我用的是成熟的 Vue 2 + Element UI 方案，**主要精力在后端**。不过前端这条链我是通的——登录后怎么用 axios 带 token、`v-hasPermi` 怎么隐藏按钮、后端返回的菜单树怎么变成前端路由，这些我都能讲清楚。但**页面本身不是我从零写的**，我不想夸大这部分。」

这段话的关键是**主动划边界**：先把「我会到哪一步」说清，再补一句「我不会什么」。这比"都做过"更可信，因为面试官一追问就露馅，而**诚实 + 说清相邻知识**永远更安全。

### 2. M0 · 骨架 / 技术栈 / 权限

#### ★ Q：你的技术选型理由是什么

**不要背名词，挑三个说「为什么」**：

| 选型 | 理由 | **代价**（一定要说） |
|---|---|---|
| **MyBatis-Plus**（不用 JPA） | 合同系统 SQL 密集（报表、统计、复杂条件查询），MyBatis 对 SQL 的可控性更重要；同时 MP 的 `BaseMapperPlus` 省掉 90% CRUD 样板 | 关联查询要手写 SQL，不像 JPA 那样自动级联 |
| **Sa-Token**（不用 Spring Security） | 更轻、API 直白（`StpUtil.login()` 一行），`@SaCheckPermission` 一眼看懂 | 生态弱于 Spring Security，复杂场景（OAuth2 / SSO）支持不够 |
| **Activiti 7**（不自研状态机） | 审批流是核心域，流程会变（加签、驳回、并行审批），自研状态机很快撑不住 | 引擎表 24 张，**模型和业务表要桥接**（这是主要复杂度来源） |

#### ★ Q：多模块怎么划分的

**「按依赖方向，不是按业务归属」**——这是最能体现判断力的答法。

```
ruoyi-admin（启动 + Web 层）
    ↓ 依赖
ruoyi-base（公共能力：工具、异常、安全、Excel）
    ↓ 依赖
zxcm-form（表单引擎）  ← 谁都不依赖它，它只被依赖
    ↑ 被依赖
zxcm-contract（合同业务）  ← import zxcm-form 的 FormBo
```

**证据**：`zxcm-contract` 的 `TreeSelectorController` 能 `import zxcm-form` 的 `FormBo`，而 `zxcm-form` 里**没有任何** import 合同的代码。**依赖是单向的。**

> 🎯 为什么这点重要：如果按「业务归属」分，很容易分出两个**互相依赖**的模块（合同要查表单、表单要查合同），编译都过不了。**先问"谁依赖谁"，再决定模块边界。**

#### ★ Q：权限怎么设计的

**RBAC 五张表**：

```
sys_user ──(sys_user_role)── sys_role ──(sys_role_menu)── sys_menu
```

- `sys_menu` 是**三合一**的表：目录(M) / 菜单(C) / 按钮(F) 都存它，用 `MENU_TYPE` 区分，`PARENT_ID` 自关联成树
- 菜单的 `PERMS` 列存权限码（如 `conf:signingSubject:add`），就是后端 `@SaCheckPermission` 校验的那个字符串

**三层权限**（详见 [D2](D2-前后端调用链路.md)）：

| 层 | 手段 | 作用 |
|---|---|---|
| 菜单可见 | `/getRouters` 只返回有权限的菜单 | 看不到入口 |
| 按钮可见 | 前端 `v-hasPermi` 指令 | 按钮消失 |
| **接口授权** | 后端 `@SaCheckPermission` | ⭐ **真正的防线** |

> 🎯 **面试点**：前端隐藏只是**体验**，**后端拦截才是安全**。验证时要把按钮的 `v-hasPermi` 删掉（或直接 curl 打接口），**没权限的用户仍然应该被后端拒绝**——这才是权限真的生效。

#### ★ Q：权限改了为什么不生效 / 怎么排查

**因为权限码和菜单树在登录时查一次、之后一直用缓存**：

```
登录 → SysPermissionService.getMenuPermission() 查 sys_menu → 权限码集合塞进 LoginUser
     → LoginUser 存 Redis 的 token-session
     → 之后 /getRouters 和 @SaCheckPermission 都读 Redis，不读数据库
```

**修改菜单或角色权限后必须重新登录。**

> ⚠️ **超管例外**：超管走**短路分支**，`permissions` 直接返回 `["*:*:*"]`，**根本不查 `sys_menu`**。
> 两个后果：① 超管改菜单立刻生效；② **超管永远测不出权限配置对不对**（它什么都通过）。
> **想真验证权限，必须建一个普通用户。**

#### ★ Q：你怎么做项目裁剪的（搭骨架那段）

**做法**：保留 Maven reactor 结构，**按模块清 `src` 只留 `pom.xml`**，而不是删模块目录。

**为什么**：父 pom 的 `<modules>` 里列着模块，**少一个整个工程就构建不了**。

**踩到的坑（讲这个最加分）**：清空后 `ruoyi-admin` 有 3 处**悬空引用**（import 了被清空模块的类），编译期就炸。**这类错误的特征是不会拖到运行期**——所以 Maven 编译本身就是最好的检查工具。

#### Q：菜单清理你遇到什么问题

**两类反直觉的脏数据**：

1. **框架菜单挂在业务目录下**：`人员组织管理` 目录下挂着 4 个**框架**菜单（用户/角色/部门/岗位管理）。按业务目录递归删，会把用户管理一起删掉——**而那 4 个 Controller 明明还在跑**。
2. **树本身是脏的**：有**孤儿菜单**（父节点在表里不存在，从任何顶级目录递归都碰不到）、有**错位菜单**（`合同基础配置` 目录下挂着动态表单的菜单）。

**结论**：「删掉不想要的」永远比「保留想要的」容易漏。**白名单（保留集）比黑名单（删除集）安全**——这也是权限系统的通用原则。

#### 🎤 怎么对面试官讲

**技术选型题**——不要背名词，挑三个说「为什么 + 代价」，节奏是「先给结论，再补代价」：

> 「选型上我有三个判断。**MyBatis-Plus**：合同系统 SQL 密集，报表、统计、复杂条件查询多，我需要 SQL 可控，所以不用 JPA 的自动级联；代价是关联查询得手写。**Sa-Token**：比 Spring Security 轻得多，`@SaCheckPermission` 一行就能看懂；代价是生态弱，要做 OAuth2、SSO 还得换。**Activiti 7**：审批流是核心域，流程会变——加签、驳回、并行审批，自研状态机很快撑不住；代价是引擎表 24 张，**模型和业务表要桥接**，这是主要复杂度来源。」

**模块划分题**——一句话定调，再举证据：

> 「我的划分依据是**依赖方向，不是业务归属**。`ruoyi-admin` 依赖 `ruoyi-base`，`ruoyi-base` 依赖 `zxcm-form`，`zxcm-contract` 反过来 import 表单引擎——**依赖是单向的**。证据就是合同模块能 import 表单的 `FormBo`，但表单模块里没有任何一行 import 合同的代码。如果按业务归属分，很容易分出两个**互相依赖**的模块，编译都过不了。**先问『谁依赖谁』，再决定模块边界。**」

**权限设计题**——先给一张图，再点出真正的防线：

> 「权限用 **RBAC 五张表**：用户、角色、菜单三张主表，加两张多对多关联表。`sys_menu` 是**三合一**的——目录、菜单、按钮都存它，靠 `MENU_TYPE` 区分，权限码存在 `PERMS` 列里。三层：菜单可见（`/getRouters` 只返回有权限的菜单）、按钮可见（前端 `v-hasPermi`）、**接口授权（后端 `@SaCheckPermission`）**。**前两层是体验，第三层才是安全**——验证的时候我把按钮的 `v-hasPermi` 删掉，或者直接 curl 打接口，没权限的用户照样被后端拒绝，这才叫权限生效。」

**项目裁剪题**（这段最能讲故事，别平铺直叙）：

> 「我搭骨架的做法是：**保留 Maven reactor 结构，按模块清 `src` 只留 `pom.xml`**，而不是删模块目录——因为父 pom 的 `<modules>` 里列着模块，少一个整个工程就构建不了。清空之后 `ruoyi-admin` 有 3 处**悬空引用**，编译期就炸了。**好在这类错误不会拖到运行期**——所以 Maven 编译本身就是最好的检查工具。」

### 3. M1 · 基础数据与合同 CRUD

#### ★ Q：一个 CRUD 模块的代码结构

**固定的 7 个必需文件 + 前端 2 个**：

```
Entity（@TableName）→ BO（入参）→ VO（出参）
→ Mapper（extends BaseMapperPlus，零 SQL CRUD）
→ IService / ServiceImpl（业务逻辑）
→ Controller（@RequestMapping + @SaCheckPermission）
```

**链路**：`index.vue → axios → GET /conf/signingSubject/list → Controller → Service → Mapper → MySQL`

> 🎯 **加分点**：BO 和 VO 分开的价值——**入参和出参的字段集经常不同**（比如入参没有 id 和创建时间，出参有。或者出参要脱敏）。用同一个 Entity 既当入参又当出参，迟早出问题。

#### ★ Q：一对多怎么设计（本项目的招牌题）

**先反问需求，再给答案**：

| 判断 | 选型 |
|---|---|
| 子数据只跟着主表一起读写、不单独查、不被外部引用 | **JSON 列** |
| 子数据要被单独查询 / 关联 / 统计，或自己有状态和权限 | **关联表** |

**我们系统里两种都有，这就是最好的证据**：

| | 合作方 ↔ 联系人 | 合同 ↔ 相对方 |
|---|---|---|
| 存法 | `conf_contract_counterpart.CONTACTS`（**JSON 列** `varchar(4000)`） | `contract_draft_partnerids`（**关联表**：`CONTRACT_DRAFT_ID` + `PARTNER_ID`） |
| 能单独查吗 | ❌ 查不了「联系人叫张三的合作方」 | ✅ 能反查「这个合作方参与哪些合同」 |
| 谁负责 JSON 转换 | **前端**（`JSON.parse` / `JSON.stringify`），后端实体就是 `String` 原样透传 | 后端正常增删行 |
| 上限 | `varchar(4000)`，超了报错 | 无上限 |
| 更新方式 | 整字段覆盖 | 增/删其中一行 |

**JSON 列的三个代价**（一定要说）：① 不能对内部字段建索引；② 有长度上限；③ 数据库看不出结构约束，靠应用层自觉。

> 🏆 **能说出"同一个系统里两种做法并存，选型跟着需求走"，比背"一对多要建子表"高一个层级。**

#### ★ Q：为什么用逻辑删除

**因为数据被引用**。历史合同引用了某个合作方，如果物理删除，合同详情的「相对方」就悬空了。

**实现**：MyBatis-Plus 全局配置 `logicDeleteValue: 2` / `logicNotDeleteValue: 0`，配表上的 `DEL_FLAG char(1)`。
**所以调 `DELETE` 接口实际执行的是 `UPDATE ... SET DEL_FLAG = 2`**——看控制台打的 SQL 就能看到。

> 🎯 **代价**：所有查询都要带 `DEL_FLAG=0`（MP 自动加，但手写 SQL 时要记得）；表会越来越大。

#### ★ Q：这张表 85 列，为什么设计得这么宽

`contract_draft` **85 列**，承担**整条合同生命周期**的状态，字段按里程碑分布：

| 字段组 | 属哪个里程碑 |
|---|---|
| 基本信息（名称、类型、金额、币种） | M1 |
| 主体/相对方 | M1 |
| **审批状态**（`CONTRACT_APPROVE_STATUS` / `CURRENT_REVIEWER`） | M2 |
| 用印状态（`CONTRACT_STAMPED_STATUS` / `SEAL_FILES_ID`） | M4 |
| 归档、纠纷、作废、续签 | M4 |
| 文件版本（`FILE_GROUPS_ID` / `VERSION`） | M3 |

**好处**：查询快（不用 join 一堆流程表）、代码直白。
**代价**：⭐ **字段一多就没人知道哪个状态是权威的**——`CONTRACT_STATUS` / `CONTRACT_APPROVE_STATUS` / `CONTRACT_STAMPED_STATUS` 三个都可能不同步。

> 🏆 **这就是整个项目最值得讲的"设计缺陷 + 补救"**：
> 「我们引入了 `contract_point_log` 事件日志作为**权威来源**——不去猜当前状态对不对，而是看**到底发生过哪些事件**。」
> **能主动指出自己系统的缺陷并说出补救方式，比把系统吹成完美强得多。**

#### Q：编号规则怎么保证不重号

规则被拆成**若干段**存在 `conf_bill_rule_ext`（固定前缀 / 日期段 / 流水号段），发号时按顺序拼接，流水号段取当前计数 +1 后补零。

**关键设计**：把「会频繁被 `UPDATE` 的计数字段」**单独拆到 ext 表**——减少和「很少变的规则定义」的行锁冲突。

**两个接口的区别**：`useBillNumber`（**占用**一个号，推进计数）vs `getBillNumber`（**预览**下一个号，不推进）。

> ⚠️ **如果要深挖并发**：严格来说这里需要**乐观锁或数据库行锁**保证并发安全（`UPDATE ... SET THIS_NUMBER = THIS_NUMBER + 1` 这种原子操作，或加版本号）。**没看过这部分实现就老实说"这块我还没深究"**，别硬编。

#### Q：为什么大部分 SQL 用注解不用 XML

全项目 `zxcm-contract` 模块**只有 1 个 Mapper XML**（`ContractRemarksMapper.xml`）。

**判据**：简单 CRUD → `@Select` 注解；需要 `@if` / `@foreach` 拼动态 SQL → XML。

> 💡 **别一上来就建 XML**。注解的 SQL 和 Java 方法在一起，跳转方便；XML 的优势是动态标签和复用 `<sql>` 片段。

#### Q：为什么业务表不加物理外键

全库 36 个 `FOREIGN KEY` **全是 Activiti 的 `ACT_FK_*`**（引擎表内部约束），**业务表零外键**。

**取舍**：
- 无物理外键的好处：方便分库分表、方便数据迁移和批量导入、不会被级联删除坑到
- 代价：**数据库不管一致性，全靠应用层和测试兜**

> 🎯 这是「**约束放数据库还是放应用**」的经典权衡。金融/强一致场景往往加外键；互联网高并发场景通常不加。

#### 🎤 怎么对面试官讲

**「一对多怎么设计」是本项目的招牌题**，一定要用「先反问需求、再给两条路线、再举本系统两个例子」的三段式讲：

> 「我不会一上来就说『建子表』。**先问需求**：这份子数据是只跟着主表一起读写，还是要被单独查询、被外部引用？
>
> 如果**只跟主表一起读写**，我用 **JSON 列**——比如合作方的联系人存在 `conf_contract_counterpart.CONTACTS` 里，就是一个 `varchar(4000)` 的 JSON 字符串，前端 `JSON.parse` / `JSON.stringify`，后端实体原样透传就行。
>
> 如果**要被单独查、有关联、有自己的状态**，就用**关联表**——比如合同和相对方，走 `contract_draft_partnerids` 这张关联表，能反查『这个合作方参与了哪些合同』。
>
> **同一个系统里两种做法并存，是因为选型跟着需求走。** JSON 列的代价是三条：不能对内部字段建索引、有长度上限、数据库看不出结构约束。」

**逻辑删除题**——先给因，再给实现，最后给代价：

> 「因为**数据被引用**。历史合同引用了某个合作方，如果物理删除，合同详情里的『相对方』就悬空了。实现上 MyBatis-Plus 全局配了 `logicDeleteValue: 2`、`logicNotDeleteValue: 0`，配表的 `DEL_FLAG` 列——所以调 `DELETE` 接口实际执行的是 `UPDATE ... SET DEL_FLAG = 2`，**看控制台打的 SQL 就能看到**。代价是：所有查询都要带 `DEL_FLAG=0`（MP 自动加，但**手写 SQL 时要自己记得**），而且表会越来越大。」

**宽表题**（主动指缺陷，这是加分点）：

> 「`contract_draft` 85 列，一张表承担整条合同生命周期，好处是查询快、代码直白。**但代价我要主动说**：字段一多，就没人知道哪个状态是权威的——`CONTRACT_STATUS`、`CONTRACT_APPROVE_STATUS`、`CONTRACT_STAMPED_STATUS` 三个都可能不同步。所以我们引了一张 `contract_point_log` 事件日志作为**权威来源**——不去猜当前状态对不对，而是看**到底发生过哪些事件**。」

### 4. M2 · 审批流与事件状态机

#### ★ Q：状态机怎么设计的

`ContractEnums.ContractStatusEnums` 定义 8 个状态：

| 值 | 名称 | 谁改的 |
|---|---|---|
| `0` | 拟定中 | 新建 / 驳回（`auditFail`）/ 退回 |
| `2` | 已作废 | M4 `cancelContract` |
| `3` | 审批中 | M2 提交审批（`beginAudit`）|
| `4` | 待签署 | ⚠️ 只有**已废弃**的 `applyStamp` 会置；当前流程**不产生** |
| `5` | 已签署 | ⚠️ **没有任何代码会置**（枚举里存在，但流程跳过）|
| `6` | 履行中 | M4 `uploadSealContract`（+ 存量合同发起审批即置）|
| `7` / `8` | 中止 / 已结束 | 关闭 / 续期超期 → M4 |

> ⚠️ **`1` 是空的**——大概率历史上「已提交待审」被合并进了 `3`。**别自己补一个 `1`**。
> ⚠️ **`4` / `5` 在本版是"死状态"**：`grep` 全仓 `.setContractStatus(` 只有 7 处，**没有一处置 `'4'` 或 `'5'`**。
> 审批通过后 `CONTRACT_STATUS` **仍停在 `'3'`**，改由 **`CONTRACT_APPROVE_STATUS='2'`** 表示"已通过" ——
> 前端「上传双章合同」按钮就是 `contractStatus=='3' && contractApproveStatus=='2'` 触发的（`auditList.vue:376`）。
> **面试时别说"审批通过变 '4'"**，会被读过代码的人戳穿；讲"审批通过用一个并行的审批状态列表达"反而更准。

#### ★ Q：为什么会有「多个状态列」，这算好设计吗

**除了 `CONTRACT_STATUS`，还有 4 个并行状态列**（审批 / 用印 / 复核 / 变更）。

**好处**：每种状态各管一摊，写代码不用 join 流程表。
**毛病**：**没人知道哪个权威**——审批通过了但 `CONTRACT_STATUS` 没改？

**结论千万别只说"这样设计不好"**，要说：
> 「这是典型的**宽表 + 多状态列**设计，好处是查询快、逻辑直白；代价是冗余和不一致风险。**项目用事件日志 `contract_point_log` 来兜底**——状态字段管查询（快），事件日志管追溯（准）。」

#### ★ Q：业务系统怎么和流程引擎解耦

**桥接链（这是 M2 的骨架，务必能画出来）**：

```
contract_draft.CONTRACT_TYPE            合同是哪个类型
        ↓ 查 form 表
form.INSTANCE_DEF_KEY = 'swhtsp'        这个类型走哪条审批流
        ↓ 按 EN_CODE 找
act_designer.EN_CODE = 'swhtsp'         业务侧的流程定义
        ↓ SQL: LEFT JOIN act_designer d ON p.KEY_ = d.EN_CODE
ACT_RE_PROCDEF.KEY_ = 'swhtsp'          引擎的流程定义 key
        ↓ 引擎启动实例
ACT_RU_TASK                             待办任务
```

**三个观察**：
1. **`EN_CODE` = `KEY_`，一个字符串两个世界的名字**——这就是「桥接」的字面含义
2. **引擎表被当业务表 join 查**（`TaskMapper` 里直接 `JOIN act_designer`）——因为 `ACT_RU_TASK` 里只有流程 key，没有业务信息（分类、名称）
3. **换引擎要重写这些 SQL**——灵活性和绑定深度是矛盾的

#### ★ Q：点「同意」之后发生了什么

```
用户点「同意」→ POST /activiti/process/complete {taskId, comment}
【流程世界】Activiti：
   complete(taskId) → 引擎推进到下一个节点 → 触发监听器
        ↓
【业务世界】FlowAuditService（桥接层）：
   监听器回调 → 用 instanceId 反查业务单 → 调 auditSuccess()
   → 改 contract_draft 状态 + 写 contract_point_log
```

**为什么要绕这一圈**：**流程引擎不该知道业务状态**。Activiti 只知道「流程走到哪」，不知道「合同是待签署还是已作废」。

**好处**：换流程引擎不用改业务代码，改流程不用改业务代码。
> 🎯 **这是「依赖倒置」的实例**——业务定义接口（监听器），引擎在恰当时机回调。同一套模式在 Spring 事件机制、MQ 消费里都是这个样子。

#### ★ Q：审批过程中数据被改了怎么办

**快照**。提交审批时把合同**冻结**成一份 `contract_his`，**审批人看的永远是提交那一刻的样子**。

**为什么必须这样**：如果审批人看的是活数据，草拟人在审批期间改一个金额，审批人签的字就对不上了——**审批意见和审批对象必须绑定**。

> 🎯 这是审批类系统的**通用答案**，也是「为什么需要 `contract_his` 这张表」的答案。

#### ★ Q：Activiti 的 RU 表和 HI 表为什么分开

| 前缀 | 存什么 | 特征 |
|---|---|---|
| `ACT_RU_*` | 正在跑的实例/任务 | 表小、**高频查**、**要加行锁** |
| `ACT_HI_*` | 跑完的历史 | 只写不读、**无限增长**、不加锁 |

**混在一张表的后果**：历史数据把热数据挤爆，锁竞争互相影响。

> 🏆 **这是「按变化原因分离」**——和「业务 Mapper 和统计 Mapper 分开」是同一类思想。**能把两处串起来讲，说明你是在读系统而不是背知识点。**

#### Q：流程变量怎么用

流程图里的**条件分支**（「金额 > 100 万走总监审批」）靠流程变量。变量在**启动流程实例时传进去**，引擎在**网关节点上求值**。

**排查经验**：分支不走，先查两件事——变量有没有传进去、变量名和条件表达式里写的是不是一致。

#### 🎤 怎么对面试官讲

**「业务怎么和流程引擎解耦」是 M2 的骨架题**，答的时候一定要**边画边说**（拿张纸画这条链，面试官会跟着你的笔走）：

> 「核心是**桥接 + 监听器回调**。这条链是这样的：合同的 `CONTRACT_TYPE` 决定它走哪条审批流，查到 `form.INSTANCE_DEF_KEY`；再按 `EN_CODE` 找到业务侧的 `act_designer`；SQL 里 `LEFT JOIN act_designer d ON p.KEY_ = d.EN_CODE`，对上引擎的 `ACT_RE_PROCDEF.KEY_`；引擎启动实例，生成 `ACT_RU_TASK` 待办。
>
> **`EN_CODE` 等于 `KEY_`——一个字符串两块世界的名字，这就是『桥接』的字面含义。**
>
> 用户点『同意』之后：请求打到引擎，引擎 `complete(taskId)` 推进流程、触发监听器；监听器回调到业务层的 `FlowAuditService`，用 `instanceId` 反查业务单，再改 `contract_draft` 的状态、写 `contract_point_log`。**流程引擎不该知道业务状态**——Activiti 只知道流程走到哪，不知道合同是待签署还是已作废。好处是换引擎、改流程都不用动业务代码。**这就是依赖倒置**：业务定义接口（监听器），引擎在恰当时机回调。」

**快照题**（一句话就能答完，别啰嗦）：

> 「**审批期间数据被改**，我们的答案是**快照**——提交审批时把合同冻结成一份 `contract_his`，审批人看的永远是提交那一刻的样子。如果审批人看的是活数据，草拟人改一个金额，审批人签的字就对不上了——**审批意见和审批对象必须绑定**。」

**RU/HI 分表题**（顺带把它和后面 M4 的报表分 Mapper 串起来）：

> 「`ACT_RU_*` 存正在跑的实例，表小、高频查、要加行锁；`ACT_HI_*` 存跑完的历史，只写不读、无限增长、不加锁。**混在一张表的后果**是历史数据把热数据挤爆、锁竞争互相影响。**这是『按变化原因分离』**——和 M4 里『业务 Mapper 和统计 Mapper 分开』是同一类思想。」

### 5. M3 · 模板体系与文档生成

#### ★ Q：模板功能怎么做的

**核心：模板不是一个 Word 文件，是 7 张表拼出来的结构**。

| 表 | 存什么 |
|---|---|
| `template_contract` | 模板本体（名称/类型/**版本**/**状态**） |
| `template_element` | **元素**：`{{甲方名称}}` 这类占位符定义 |
| `template_clause` | **条款**：可复用段落（保密条款、违约责任…） |
| `template_clause_type` | 条款分类（自关联树） |
| `template_link_relation` | **模板 ↔ 元素/条款 的多对多** |
| `template_scope` | 适用范围（哪些部门/角色能用） |
| `template_attachment` | 附件 |

**为什么这么拆**：为了**条款跨模板复用**——模板 A 和 B 都引用「保密条款」这**一条记录**，改一处两边同时变。**如果模板就是一个 Word 文件，改一处要在每个文件里改一遍。**

> 🏆 **加分收尾**：「但这样拆的代价是**结构复杂**（7 张表、一次保存要写多表），只适合**条款复用是真实需求**的场景。如果模板只是内部几个固定文档，存 Word + 占位符就够了，**别过度设计**。」
> **能说出"什么时候不该这么拆"，比背结构更能体现判断力。**

#### ★ Q：为什么模板要版本化，不能直接改

**因为模板被合同引用**。直接改模板内容，**已经用旧模板生成的合同就对不上了**。

```
模板 V1.0 ──引用──→ 合同A（2026-03 生成）   ← 改 V1.0 会污染这个
模板 V1.1 ──引用──→ 合同B（2026-09 生成）
```

**正确做法**：改内容 → **建成新版本**，老合同继续指向老版本。
同理「**停用**」而不是「删除」——停用后新合同选不到，但老合同还能打开。

#### ★ Q：OnlyOffice 集成的难点在哪

**难点全在「回调」**，因为**编辑发生在 OnlyOffice 服务器上，不在你的服务器上**：

```
① 前端向你的后端要配置（文档地址、回调地址、JWT 签名）
② 前端把配置交给 OnlyOffice 的 JS SDK，它去 OnlyOffice 服务器打开 iframe
③ 用户在 iframe 里改文档 → 改的内容存在 OnlyOffice 服务器上
④ 用户关闭/定时触发 → OnlyOffice 服务器 POST 你的 callbackUrl
⑤ 你的后端回调去 OnlyOffice 下载改好的文件，存进 contract_draft_files
```

**三个必然踩的坑**：
1. **`callbackUrl` 必须是 OnlyOffice 服务器能访问到的地址**。写 `localhost:8080` 一定失败——那是 OnlyOffice 自己的 localhost
2. **JWT 密钥两边必须一致**，否则所有回调被拒（表现是「改了但保存不了」）
3. **回调接口必须免鉴权**（加进 `security.excludes`）——它是 OnlyOffice 服务器在调，**没有你的用户 token**

> 🎯 **第 3 点是个很好的「安全 vs 可用」权衡题**：
> 「回调接口不能带用户 token，所以只能靠 **JWT 签名验证来源**（而不是验证用户身份）。这也是为什么 `secret` 不能泄露。」
> **能主动说出这个权衡，说明你不只是把功能接通了。**

#### Q：文件是怎么管理的

- **统一文件表 `conf_file`**：所有模块的文件（模板、合同附件、双章合同）都存它，靠 `MODULE` 列区分来源 → **上传/下载/预览只有一套代码**。`ONLYOFFICE_KEY` 是回调时找到文件的凭据
- **文件版本表 `contract_draft_files`**：一份合同可以有 V1.0 / V1.1 / V1.2 多个版本

#### 🎤 怎么对面试官讲

**模板体系题**——先用一句反常识的话开场，再展开：

> 「**模板在我们系统里不是一个 Word 文件，是 7 张表拼出来的结构**：`template_contract` 模板本体、`template_element` 元素占位符、`template_clause` 条款、`template_clause_type` 条款分类、`template_link_relation` 模板和元素/条款的多对多、`template_scope` 适用范围、`template_attachment` 附件。
>
> **为什么这么拆**——为了**条款跨模板复用**。模板 A 和模板 B 都引用『保密条款』这**一条记录**，改一处两边同时变；如果模板就是一个 Word 文件，改一处得在每个文件里改一遍。
>
> **但我会主动说代价**：这样拆结构复杂，一次保存要写多张表，**只适合『条款复用是真实需求』的场景**。如果模板只是内部几个固定文档，存 Word 加占位符就够了，**别过度设计**。」

**版本化题**——先给规则，再给理由：

> 「模板**不能直接改内容**，因为模板被合同引用——直接改，已经用旧模板生成的合同就对不上了。正确做法是**改内容就建成新版本**，老合同继续指向老版本。同理我们**停用**而不是**删除**模板——停用后新合同选不到，但老合同还能打开。」

**OnlyOffice 回调题**（先说清「为什么难」，再说五个步骤和三个坑）：

> 「难点全在**回调**——因为编辑发生在 **OnlyOffice 的服务器上，不在我的服务器上**。流程是：前端向我的后端要配置（文档地址、回调地址、JWT 签名），交给 OnlyOffice 的 JS SDK 打开 iframe；用户在 iframe 里改，内容存在 OnlyOffice 那边；用户关闭或定时触发时，OnlyOffice 服务器 **POST 我的 callbackUrl**；我的后端回调再去 OnlyOffice 下载改好的文件，存进 `contract_draft_files`。
>
> 三个必然踩的坑：**一**、`callbackUrl` 必须是 OnlyOffice 服务器能访问到的地址，写 `localhost:8080` 一定失败——那是它自己的 localhost；**二**、JWT 密钥两边必须一致，否则所有回调被拒，表现是『改了但保存不了』；**三**、回调接口**必须免鉴权**（加进 `security.excludes`），因为它是 OnlyOffice 服务器在调，**没有我的用户 token**。
>
> **第三点其实是个『安全 vs 可用』的权衡**：回调接口不能带用户 token，所以只能靠 **JWT 签名验证来源**，而不是验证用户身份——这也是为什么 `secret` 不能泄露。」

### 6. M4 · 用印、作废续签与报表

#### ★ Q：用印为什么单独一套表

**因为一家公司有多个印章**（公章、合同专用章、法人章、财务章），每个章有**保管人**和使用记录：

- `contract_seal` —— 用印申请单（申请类型、签署状态、用了哪些章）
- `contract_seal_notes` —— **用印流水**（谁、何时、给哪份合同、用了哪个章）

**「notes」这张流水表是关键**：用印是**不可撤销的法律行为**，出事要能追责。**它和 M2 的 `contract_point_log` 是同一类东西——不可篡改的流水。**

> 🎯 **还有个细节能加分**：系统实际做的是「**流程 + 留痕**」，**盖章是线下做的**（生成待盖章文件 → 通知保管人 → 线下盖章 → 传回来）。**如果以后要接电子签章，替换的就是这一步。**

#### ★ Q：权限码为什么是 `uploadStampedContract` 而不是 `edit`

**说明权限设计已经从「按增删改查」进化到「按业务动作」了。**

上传双章合同是一个**独立授权点**——有的角色能改合同草稿，但**不能上传盖章件**（因为盖章件是法律效力凭证）。

> 🎯 **面试点**：CRUD 权限（`add`/`edit`/`remove`）是**技术动作**；`uploadStampedContract` 是**业务动作**。**成熟的系统按业务动作授权**——因为业务上「能改草稿」和「能上传盖章件」是两个完全不同的责任。

#### ★ Q：合同作废为什么用三个列

| 列 | 用途 |
|---|---|
| `CONTRACT_STATUS='2'` | **列表过滤**（"显示所有已作废的"） |
| `CONTRACT_CANCEL='1'` | **布尔标记**，前端控制按钮显示/禁用 |
| `CONTRACT_CANCEL_REMARK` | 存原因，用于追责 |

**为什么不合成一个**：查询快 + 前端判断简单（比判断状态字符串直白）。**代价是冗余，理论上有不一致风险。**

> 🎯 追问「为什么不用一个状态字段」→ 「**查询性能 + 前端判断简单，代价是冗余和不一致风险**，所以配套了事件日志作为对账依据。」
> **注意这个答法的结构：好处 → 代价 → 怎么兜底。**

#### ★ Q：续签为什么不在原合同上改

**续签 = 新建一份合同 + 用 `RELATED_CONTRACT_ID` 指向原合同**。

**因为原合同已经签署、已经履行过、可能已经归档**——它是有法律效力的**既成事实，不能动**。

> 🏆 **这条规律在 M4 出现第 3 次**：**作废不删、模板不就地改、续签不原地改**。
> **面试时把「历史不可变」作为整个系统的设计哲学讲出来，比讲十个 CRUD 都有说服力。**
> **还有第 4 个**：合同文件开新版本而不覆盖。

#### ★ Q：报表为什么单独一个 Mapper

`ContractDraftStatMapper` —— 统计查询**单独一个 Mapper**，不塞进 `ContractDraftMapper`：

| | 业务 Mapper | 统计 Mapper |
|---|---|---|
| 查什么 | 具体记录（列多） | 聚合（`COUNT`/`SUM`/`GROUP BY`） |
| 索引 | 有 | 全表扫是常态 |
| 优化手段 | 加索引 | 加缓存 / 预计算 / 物化视图 |

**分开写，将来优化统计只动一个文件，不影响业务流程。**

> 🏆 **这是「按变化原因分离」**——和 Activiti 的 RU/HI 分表是同一类思想。

#### Q：`@RequestMapping({"/contract/book", "/contract/contractBook"})` 为什么两个路径

**历史兼容**——改名后老调用方还没迁完。**项目里看到这种写法，一律理解为「这里有过一次改名」。**

> 🎯 能识别出这个模式，说明你读代码时在**看模式**而不是**看行**。

### 7. 跨模块问题（最能拉开差距）

#### ★ Q：这个系统你最欣赏的设计是什么

**答「历史不可变」+「按变化原因分离」这两条主线，并各举 3 个例子**：

**主线 1 · 历史不可变**（被引用过的东西从不就地改）：
| 场景 | 做法 |

#### Q：如果让你重做，你会改什么

**说三个真实存在的问题**（能指出问题是成熟的表现）：

1. **宽表的状态列冗余**：`contract_draft` 85 列、多个状态列可能不同步。可以抽一个「合同状态」聚合，或者干脆让事件日志成为唯一权威

> 🎯 **第 2 条特别加分**：「保留旧实现 + 开关切换」是**稳妥但保守**的做法，**代价是代码库里有两套做同一件事的代码**。可以讲这个 trade-off，但**不建议学它**。

#### Q：你遇到最大的困难是什么

**推荐讲 M2 的监听器回调**（这是全项目最绕的地方）：

> 我是靠**在监听器上打断点**、以及**在 `contract_point_log` 里查流水**来定位的。后来我理解了这是**依赖倒置**——业务定义接口，引擎回调，好处是两边解耦。
>
> 让我复述一遍的话：**`contract_draft.CONTRACT_TYPE` → `form.INSTANCE_DEF_KEY` → `act_designer.EN_CODE` → `ACT_RE_PROCDEF.KEY_` → `ACT_RU_TASK`**,这条链就是业务和引擎的桥。」

> 🏆 **能从头到尾复述一条最绕的链路，比多做一个功能有用得多。**

#### Q：你怎么保证数据一致性

**分层说**：
1. **事务**：改状态 + 写事件日志在同一个 `@Transactional` 里

**老实说边界**：「跨服务的分布式事务**没有涉及**——这是单体应用，所有操作在同一个库同一个事务里。」

> ⚠️ **别硬编分布式事务**。单体应用说「没有分布式事务问题」是完全正常的答案。

### 8. 数据库与 SQL 优化（近期重点 · 必背）

> 这一章和前面不一样：前面讲「**我的系统怎么设计的**」，这一章是**面试官最爱问、也最容易把人问穿**的硬技能。
> 唯一的写法要求：**每条结论都落到本项目的真实表上**。空背索引原理，一定被追问「那你项目里怎么优化的」。

#### 8.0 先给流程，再给知识点（这是最重要的开场）

被问「你怎么做 SQL 优化」，**最忌讳上来就背「加索引」**。正确的开场是**一套流程**：

```
① 哪条慢？      → 慢查询日志 / Druid 监控 / Arthas trace
② 慢在哪？      → EXPLAIN 看 type / key / rows / Extra
③ 为什么不走索引 → 索引缺失？索引失效？优化器选错？
④ 怎么改？      → 加索引 / 改 SQL / 改表结构 / 加缓存（四选一，不是只会加索引）
⑤ 改完验证      → 重新 EXPLAIN + 压测对比 + 确认不影响业务写入
```

**本项目怎么开慢查询日志**（MySQL 8.0.46 在虚拟机上，`root/root`）：

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;          -- 超过 1 秒就记录
SELECT * FROM mysql.slow_log ORDER BY start_time DESC LIMIT 20;
```

> 🎯 **一句话定调**：「我的顺序是**先定位、再分析、最后才改**——不问清楚是哪条 SQL 慢、慢在**扫描**还是**排序**，直接加索引是瞎猜。」
> **只背『加索引』的人，会在『如果加了索引还是慢呢』这一个追问上翻车。**

#### 8.1 我的系统里，哪几条 SQL 最可能慢（先列清单，这是"真实情况"）

| 场景 | 涉及表 | 症状 | 为什么 |
|---|---|---|---|
| **合同列表分页** | `contract_draft` | 越翻越慢 | `SELECT *` 拉 **85 列**；条件列大多无索引；`ORDER BY UPDATE_TIME` 无索引 → **filesort** |
| **合同名称搜索** | `contract_draft` | 搜一次全表 | `LIKE '%关键词%'` 前导 `%` → **索引失效**（且该列本就没索引） |
| **合同详情 → 相对方** | `contract_draft_partnerids` | 关联慢 | 这张表**只有主键**，`CONTRACT_DRAFT_ID` / `PARTNER_ID` 都没索引 → **全表扫** |
| **合同 → 文件版本列表** | `contract_draft_files` | 关联慢 | 同样**只有主键**，`CONTRACT_DRAFT_ID` 没索引 |
| **首页 / 报表统计** | `contract_draft`、`contract_fulfil_task` | 统计卡顿 | **派生表 + GROUP BY + 列上套函数**（`DATE_FORMAT(...)`），派生表物化后**没有索引** |
| **审批待办列表** | `contract_draft` ⟕ `contract_audit_form` | join 慢 | 子表有 `CONTRACT_ID` 索引，但主表 `a.AUDIT_ID` 是 `decimal(20,0)`、子表 `b.ID` 也是 `decimal(20,0)`——**类型对得上**，这条其实不慢，**别乱讲** |

> ⚠️ **最后一行是故意的**：面试时**不要把所有 join 都说慢**。上面这条 join 的两端类型一致、子表还有索引，是**健康**的。
> **能说清『哪条慢、哪条不慢、为什么』，比笼统说『我系统 SQL 优化过』可信得多。**

#### 8.2 ★ 索引到底是怎么加速的（用 `contract_draft` 讲透）

**InnoDB 用 B+ 树**：树矮（3~4 层就能存千万行）、叶子节点用链表串起来（范围查询快）。

`contract_draft` 上真实的索引有 **5 个**：

| 索引名 | 列 | 类型 |
|---|---|---|
| `PRIMARY` | `ID` | 主键（**聚簇索引**）|
| `draft_index_code` | `(CONTRACT_CODE, TENANT_ID)` | 唯一索引 |
| `draft_index_status` | `(CONTRACT_STATUS)` | 普通索引 |
| `draft_index_charge` | `(CONTRACT_CHARGE_ID)` | 普通索引 |
| `draft_index_drafter` | `(DRAFTER_ID)` | 普通索引 |

**聚簇索引 vs 二级索引**（这是必答）：

- **聚簇索引**（主键）：B+ 树叶子节点**存的是整行数据**。所以主键查询一跳到叶子就拿到全行。
- **二级索引**（上面后 4 个）：叶子节点**存的是「索引列 + 主键值」**，不是整行。

**回表**：走二级索引 → 拿到主键 → **再回聚簇索引取整行**，这第二次查找就是「回表」。

**覆盖索引**：如果**要查的列都在索引里**，就不用回表。对比同一条 SQL：

```sql
-- ① 覆盖索引：只要 ID 和 CONTRACT_CODE，都在 draft_index_code(CONTRACT_CODE, TENANT_ID) 里
SELECT ID, CONTRACT_CODE FROM contract_draft WHERE CONTRACT_CODE = 'HT-2026-001';
-- Extra: Using index  ← 不回表

-- ② 必须回表：SELECT * 要 85 列，索引里只有 2 列
SELECT * FROM contract_draft WHERE CONTRACT_CODE = 'HT-2026-001';
-- Extra: 无 Using index ← 每行都要回表取 85 列
```

> 🏆 **这就回答了「`SELECT *` 为什么不好」**——不是审美问题：**它让所有索引都变成「非覆盖索引」，必然回表；而且 85 列全走网络，列表页其实只需要十几列。**
> 本项目的 `ContractDraftMapper` 里就写着 `SELECT * FROM contract_draft ${ew.customSqlSegment}`（`ContractDraftMapper.java:44`）——**这就是我第一个会改的地方**。

#### 8.3 ★ EXPLAIN 怎么读（面试必问，逐列讲）

`EXPLAIN` 加在 SQL 前面就行。下面拿**真实的合同列表 SQL** 举例（数据量按「20 万条合同」设想，**数字是示意，结论才是重点**）：

```sql
EXPLAIN SELECT * FROM contract_draft
WHERE DEL_FLAG = '0' AND CONTRACT_NAME LIKE '%采购%' AND TENANT_ID = '00000000'
ORDER BY UPDATE_TIME DESC, ID ASC
LIMIT 0, 10;
```

| 列 | 示意值 | 怎么读 |
|---|---|---|
| `type` | **`ALL`** | ⚠️ **全表扫描**（最差级别）|
| `possible_keys` | `NULL` | 没有任何索引可用——`DEL_FLAG`、`UPDATE_TIME` 都没索引，`LIKE '%..%'` 也用不上 |
| `key` | `NULL` | 实际没走索引 |
| `rows` | `200000` | 预估要扫 20 万行 |
| `Extra` | **`Using where; Using filesort`** | 过滤靠扫描 + **额外排序**（`filesort`）|

**`type` 从好到坏**：`system > const > eq_ref > ref > range > index > ALL`。**看到 `ALL` 就要警惕**（小表例外）。

**`Extra` 里两个红灯**：
- **`Using filesort`** → 排序没走索引，要把结果拉到内存/磁盘排。**本项目列表 `ORDER BY UPDATE_TIME DESC, ID ASC` 而 `UPDATE_TIME` 无索引，必然 filesort。**
- **`Using temporary`** → 用了临时表，常见于 `GROUP BY` 无索引（报表 SQL 就是）。
- 绿灯是 **`Using index`** → 覆盖索引，最快。

> 🎯 **面试落点**：「我会重点看两列——`type` 和 `Extra`。`type=ALL` 说明在扫全表；`Extra` 里出现 `Using filesort` 或 `Using temporary`，说明排序或分组没走索引。**这两样是本项目合同列表和报表统计的典型问题。**」

#### 8.4 ★ 索引失效的 7 种场景（每条挂本项目）

| # | 场景 | 本项目实例 |
|---|---|---|
| 1 | **不满足最左前缀** | 索引是 `(CONTRACT_CODE, TENANT_ID)`，只查 `TENANT_ID` → 用不上 |
| 2 | **列上做函数/运算** | 报表里 `GROUP BY DATE_FORMAT(d.EFFECTIVE_TIME,'%Y%m')`——**列被函数包住，索引直接废** |
| 3 | **隐式类型转换** | `varchar` 列传数字（如 `CONTRACT_CODE = 123`）→ 相当于给列套了函数 |
| 4 | **`LIKE '%x%'`（前置 %）** | 合同名称模糊搜索 `LIKE '%采购%'` |
| 5 | **`OR` 两侧有一个无索引** | 数据权限拼出来的 `(drafter_id=? OR contract_charge_id=?)`——两个字段**各自都有索引**，但 `OR` 会让优化器**倾向全表扫**（见 8.9）|
| 6 | **`!=` / `<>` / `NOT IN` / `IS NOT NULL`** | 选择性差时优化器干脆放弃索引 |
| 7 | **优化器觉得全表扫更快** | `DEL_FLAG` 只有 `'0'/'2'` 两个值，**99% 是 '0'**，给它建索引也没用（低选择性）|

> ⚠️ **第 7 条是新人的坑**：「多加点索引总没错」是错的。**选择性低的列（性别、状态、删除标志）单独建索引，优化器根本不走，还拖慢写入。**
> 正确做法是把它放进**联合索引的后缀**（如 `(CONTRACT_STATUS, DEL_FLAG)`），或者干脆不建。

#### 8.5 ★ 联合索引与最左前缀

`draft_index_code(CONTRACT_CODE, TENANT_ID)` 是联合索引，能命中的查询：

```sql
WHERE CONTRACT_CODE = ? AND TENANT_ID = ?   -- ✅ 全用上
WHERE CONTRACT_CODE = ?                     -- ✅ 用上前缀（最左前缀）
WHERE TENANT_ID = ?                         -- ❌ 用不上（缺最左列）
```

> 🎯 **一句话**：「联合索引**先按第一列排序，第一列相同再按第二列排**——所以必须先有第一列，才能用到后面的列。这就是最左前缀。」
>
> 💡 **本项目的实际用法**：查合同编号 `CONTRACT_CODE` 是**等值**，能命中这个索引的前缀——**所以"按编号精确查合同"是列表页里唯一走得通索引的条件**。而名称、时间、状态这几种过滤都靠不上。

#### 8.6 ★ 深分页：`LIMIT 20000, 10` 为什么慢

MyBatis-Plus 的 `Page` 最终会生成 `LIMIT offset, size`。**MySQL 会先把前 `offset + size` 行都读出来再丢掉前 `offset` 行**——翻到第 2000 页时，前 20000 行白读。

**三种改法（按推荐度）**：

```sql
-- ① 延迟关联（改造成覆盖索引，先把 ID 捞出来，再拿 ID 回表取详情）
SELECT d.* FROM contract_draft d
INNER JOIN (
  SELECT ID FROM contract_draft
  WHERE DEL_FLAG='0' ORDER BY UPDATE_TIME DESC, ID ASC LIMIT 20000, 10
) t ON t.ID = d.ID;

-- ② 游标 / keyset（不让用户跳页，只允许「下一页」，用上一页最后一条做条件）
SELECT * FROM contract_draft
WHERE (UPDATE_TIME, ID) < (?, ?)          -- 上一页最后一行
ORDER BY UPDATE_TIME DESC, ID ASC LIMIT 10;

-- ③ 业务上限制：只允许翻到前 N 页（很多后台系统真这么干）
```

> 🎯 **面试落点**：「深分页慢的**根因是 `offset` 越大，被丢弃的行越多**。我优先用**延迟关联**——把排序和分页压在**覆盖索引**上先取出主键，再回表拿整行；如果产品允许，**游标分页**是最优解，因为它**不用丢弃任何行**。」

#### 8.7 ★ 关联查询与派生表（本项目真实的两处）

**问题一：子表没索引 → join 全表扫**

```sql
-- 「这个相对方参与了哪些合同」
SELECT * FROM contract_draft_partnerids WHERE PARTNER_ID = ?;
-- 这张表结构：只有 PRIMARY KEY(ID)
-- PARTNER_ID varchar(20)、CONTRACT_DRAFT_ID varchar(20) —— 都没索引 → 全表扫
```

**改法**（补两个索引，注意**双向都要**，因为要按合同查相对方、也要按相对方反查合同）：

```sql
ALTER TABLE contract_draft_partnerids ADD INDEX idx_partner (PARTNER_ID);
ALTER TABLE contract_draft_partnerids ADD INDEX idx_draft (CONTRACT_DRAFT_ID);
-- contract_draft_files 同理，补索引后「查一份合同的所有文件版本」才走索引
ALTER TABLE contract_draft_files ADD INDEX idx_draft (CONTRACT_DRAFT_ID);
```

> ⚠️ **顺带一个真问题**：`contract_draft_partnerids.CONTRACT_DRAFT_ID` 是 **`varchar(20)`**，而 `contract_draft.ID` 是 **`varchar(64)`**——**长度不一致**。现在雪花 ID 是 19 位能塞下，但一旦换成 32 位 UUID，**这里会被截断**。面试时能主动指出这种字段长度不一致，是很扎实的观察。⚠️ **注意：这里是"长度不一致"，两端仍是字符串，不构成隐式转换**；如果是 `varchar` 和 `decimal` 混用才是真·隐式转换（8.4 第 3 条）。

**问题二：派生表（子查询当表用）→ 物化后无索引**

报表 SQL 里反复出现这种写法：

```sql
select tmp.MON, SUM(tmp.AMOUNT) from (
  select t.AMOUNT, DATE_FORMAT(t.DONE_TIME,'%Y%m') as MON
  from contract_fulfil_task t LEFT JOIN contract_draft d on t.CONTRACT_ID = d.ID
  ...
) tmp GROUP BY tmp.MON;
```

`FROM (子查询) tmp` 这种叫**派生表**，MySQL 会先物化它，**物化结果上没有索引**，外层 `GROUP BY` 只能硬算。
**改法**：能用 `JOIN` 展开就展开别套子查询；`DATE_FORMAT` 这类**对列做函数**的写法，如果查询条件能收敛到时间范围，**先 `WHERE` 收窄再算**（`WHERE DONE_TIME >= '2026-01-01'` 能走索引，`DATE_FORMAT(DONE_TIME,...)` 不能）。

#### 8.8 ★ count / exists-in / 小表驱动大表

| 题 | 答 |
|---|---|
| `count(*)` vs `count(1)` vs `count(列)` | InnoDB 里 `count(*)` 和 `count(1)` **基本一样**（都走最小的索引扫）；`count(列)` 会**跳过该列为 NULL 的行**，语义不同。**本项目报表用 `count(1)`，没问题** |
| 大表 `count(*)` 慢 | InnoDB 没有像 MyISAM 那样存行数，得真扫。**优化：加缓存（本项目首页统计就走 Redis）/ 用近似值 / 单独维护计数表** |
| `IN` 还是 `EXISTS` | **小表驱动大表**：子查询结果小 → 用 `IN`；外层结果小 → 用 `EXISTS`。本项目数据权限用的是 `IN (子查询)` 形态（见 8.9）|
| 分页时要不要 count | MyBatis-Plus 分页插件会**自动再发一条 `count`**。大表上这条 count 有时比列表本身还慢 → **可以关掉自动 count，前端改成「加载更多」** |

#### 8.9 ★ 数据权限 & 租户插件：看不见的 SQL 改写（本条最出彩）

这是本项目**独有**、别的候选人讲不出来的点。

**① 数据权限是「拦截器改 SQL」**：`PlusDataPermissionHandler.getSqlSegment()` 把权限条件用**括号**包起来，再 `AND` 到原 `WHERE` 上（`PlusDataPermissionHandler.java:107-114`）：

```java
Expression expression = CCJSqlParserUtil.parseExpression(dataFilterSql);
Parenthesis parenthesis = new Parenthesis(expression);   // 加括号，防止和原有条件串味
return new AndExpression(where, parenthesis);
```

**② 多个角色是 `OR` 拼起来的**（`PlusDataPermissionHandler.java:126,157`）：

```java
String joinStr = isSelect ? " OR " : " AND ";   // 查询用 OR；更新/删除必须 AND（更严）
```

所以一个用户有 2 个角色时，列表 SQL 实际变成：

```sql
SELECT * FROM contract_draft
WHERE DEL_FLAG='0' AND TENANT_ID='00000000'
  AND (drafter_id = 7 OR contract_charge_id = 7)     -- ← 数据权限 OR 进来的
ORDER BY UPDATE_TIME DESC, ID ASC;
```

> 🎯 **面试落点（这是我要主动讲的）**：「数据权限是**运行时改 SQL**，它有两个性能副作用：
> **一、多角色会拼出 `OR` 条件**——`drafter_id` 和 `contract_charge_id` 各自都有索引（`draft_index_drafter`、`draft_index_charge`），但 `OR` 跨越两个索引时，优化器经常**退化成全表扫**。角色越多，`OR` 链越长。
> **二、权限字段决定能不能走索引**——我们特意让权限落在**有索引的字段**上（草稿阶段用 `drafter_id`、履约阶段用 `contract_charge_id`，两者都建了索引），如果落到一个没索引的字段，全表就白扫了。
> **所以『给权限字段也加索引』是我们设计时就该考虑的事。**」

**③ 还有租户插件**：MyBatis-Plus 的 `TenantLineInnerInterceptor` 会**自动追加** `TENANT_ID = ?`。所以真实 SQL 里那条 `TENANT_ID='00000000'` 是**框架拼的，不是我手写的**。

> ⚠️ **两个插件的叠加效应**：**租户条件 + 数据权限条件 + 你的业务条件 + 逻辑删除条件**，一条 SQL 上可能挂四组 `WHERE`。
> **`EXPLAIN` 一定要在「有权限的真实用户」下跑**——超管和租户管理员**短路不过滤**（`PlusDataPermissionHandler.java:99` 的判断），**用 admin 测出来的执行计划是假的**。

#### 8.10 一个完整的真实改造案例（从头到尾讲一遍）

**背景**：合同列表页，数据量上来后翻页卡顿。

**改造前**：

```sql
-- ContractDraftServiceImpl.buildQueryWrapper()（:185-202）+ ContractDraftMapper.java:44
SELECT * FROM contract_draft
WHERE DEL_FLAG = '0'
  AND CONTRACT_NAME LIKE '%采购%'
  AND TENANT_ID = '00000000'
  AND (drafter_id = 7 OR contract_charge_id = 7)
ORDER BY UPDATE_TIME DESC, ID ASC
LIMIT 20000, 10;
```

**诊断（EXPLAIN）**：`type=ALL`（全表扫）、`Extra=Using where; Using filesort`（额外排序）、`rows=200000`。

**三个根因**：
1. `SELECT *` → 85 列，**必然回表**，网络也大
2. `ORDER BY UPDATE_TIME` **没索引** → filesort
3. 深分页 `LIMIT 20000,10` → **白读 2 万行**

**改造**：

```sql
-- 第一步：给排序字段补联合索引
--   前两列 (UPDATE_TIME DESC, ID) 是为了让 ORDER BY 走索引、干掉 filesort
--   后两列 (DEL_FLAG, TENANT_ID) 是为了让 WHERE 过滤也能在索引里完成、少回表
ALTER TABLE contract_draft ADD INDEX idx_list_order (UPDATE_TIME DESC, ID, DEL_FLAG, TENANT_ID);

-- 第二步：列表只查需要的列（前端列表页其实只要这十几列）
SELECT ID, CONTRACT_NAME, CONTRACT_CODE, CONTRACT_TYPE_NAME, CONTRACT_STATUS,
       CONTRACT_CHARGE_NAME, DRAFTER_NAME, AMOUNT, CURRENCY, UPDATE_TIME
FROM contract_draft
WHERE DEL_FLAG = '0' AND TENANT_ID = '00000000'
  AND (drafter_id = 7 OR contract_charge_id = 7)
ORDER BY UPDATE_TIME DESC, ID ASC
LIMIT 10;

-- 第三步：真要深翻页，用延迟关联
SELECT d.* FROM contract_draft d
INNER JOIN (SELECT ID FROM contract_draft
            WHERE DEL_FLAG='0' AND TENANT_ID='00000000'
            ORDER BY UPDATE_TIME DESC, ID ASC LIMIT 20000, 10) t
  ON t.ID = d.ID;
```

**改完再看 EXPLAIN**：`key=idx_list_order`、`type=range`（甚至 `index`）、`Extra=Using where`（`filesort` 消失）。

> 🏆 **这段讲出来，一套完整的「定位 → 分析 → 改造 → 验证」就齐了。**
> **注意第三步 `SELECT d.*` 只在"详情"场景用**——列表页要的是**少列 + 覆盖索引**，这两个目标其实是**相反**的，**要按页面分别设计，不能一条 SQL 通吃**。

#### 8.11 🎤 怎么对面试官讲

**「你怎么做 SQL 优化」**——先给流程，再挑一条真实 SQL 说透：

> 「我先说**流程**：**先定位**（慢查询日志 / Arthas），**再分析**（EXPLAIN 看 `type` 和 `Extra`），**最后才改**（加索引 / 改 SQL / 改表结构 / 加缓存，四选一）。
>
> 拿我系统里最典型的一条说——**合同列表分页**。EXPLAIN 出来 `type=ALL`、`Extra=Using where; Using filesort`。三个原因：**一**、SQL 是 `SELECT *`，拉 85 列，**所有索引都变成非覆盖索引，必然回表**；**二**、`ORDER BY UPDATE_TIME` 这个字段没索引，**排序走了 filesort**；**三**、深分页 `LIMIT 20000,10`，**MySQL 要先读两万行再丢掉**。
>
> 改法也是三个：**列表页只查十几列**（这是覆盖索引的前提）、**给排序字段建联合索引**、**深翻页用延迟关联**——先把主键在覆盖索引上分页取出来，再回表拿整行。改完 `filesort` 消失，`key` 变成新索引。」

**「索引失效你遇到过哪些」**——不要背清单，**讲项目里真实踩的**：

> 「我自己核对过几处。**一是报表统计里的 `DATE_FORMAT(EFFECTIVE_TIME,'%Y%m')`**——**列上套了函数，索引直接失效**，只能全表扫再算。**二是数据权限拼出来的 `OR`**——`drafter_id = ? OR contract_charge_id = ?`，这两个字段**各自都有索引**，但 `OR` 跨索引时优化器经常干脆全表扫，**角色越多 `OR` 链越长越糟**。**三是选择性低的列**，比如 `DEL_FLAG` 只有 0/2，给它单独建索引优化器也不走，**它适合当联合索引的后缀，不适合单独建**。」

**追问「加了索引还是慢呢」**（这是分水岭）：

> 「那就分三种可能。**一**、**索引根本没被用上**——回去看 EXPLAIN 的 `key` 是不是 `NULL`，是的话查失效原因（函数、隐式转换、`OR`）。**二**、**用上了但回表太多**——说明是覆盖索引问题，考虑把要查的列补进索引，或者减少查询列。**三**、**索引没问题但数据量本身太大**——那就不是索引能解决的了，要**加缓存（我们首页统计就缓存在 Redis）、预计算、或者分库分表**。**索引不是银弹，它解决的是『定位行』，解决不了『数据本来就多』。**」

> ⚠️ **别硬编"我压测过"**。学习项目没有真实流量，诚实说「**这是学习项目，我是**按业务数据量推演**出这些慢查询，没有线上压测数据**；但优化手段和判断依据是实打实的」，**比编一个"QPS 从 500 优化到 5000"安全得多**。

### 9. JVM 与线上问题排查（少量但要准）

> ⚠️ **先说清边界**：本项目**没有任何 JVM 调优痕迹**——启动脚本只有 `mvn clean package`（`script/bin/package.bat`），没有 `-Xmx`，也没有 GC 日志。
> **所以别编「我调过 JVM 参数」。** 这一章讲的是：**JVM 这套东西在实际工作里『什么时候真的用上』、用上时怎么下手**——你要表现得像一个**会排查问题**的人，而不是一个背参数的人。

#### 9.1 先把内存结构说清楚（用本项目的对象落座）

| 区域 | 存什么 | 本项目里对应什么 |
|---|---|---|
| **堆**（Heap） | 所有 `new` 出来的对象 | `ContractDraft`、`LoginUser`、导出的几万个 VO |
| **虚拟机栈**（每线程一个）| 方法调用栈帧、局部变量 | 每个 HTTP 请求线程一个栈 |
| **元空间**（Metaspace，JDK8+）| 类的元数据 | 启动时加载的**几百个类**（本项目多模块，类特别多）|
| **直接内存** | `NIO` / `ByteBuffer` | 文件上传下载（80MB 上限）、`FileOutputStream` 写文件 |
| **本地方法栈 / 程序计数器** | native 方法、字节码行号 | 知道有这俩就行 |

**用一句话讲「对象住哪」**：

> 「`new ContractDraft()` 出来的**对象本体在堆**，栈里只放**一个指向它的引用**。方法一结束，栈帧弹出，引用没了，对象就等 GC 回收——**如果还有别的引用挂着（比如塞进了某个静态 `Map`），就回收不掉，这才是内存泄漏。**」

> 🎯 **一句话区分「内存泄漏」和「内存溢出」**：**泄漏是"该回收的没收"（对象还被引用着），溢出是"想分配但没空间了"（OOM）。泄漏迟早导致溢出。**

#### 9.2 什么时候才需要动 JVM（先问"要不要调"，再问"怎么调"）

**真实的触发场景，只有这几种**：

| 现象 | 可能原因 | 先做什么 |
|---|---|---|
| `java.lang.OutOfMemoryError: Java heap space` | 堆不够 / 内存泄漏 | **导 dump → MAT 分析**（见 9.5）|
| Full GC 频繁、接口周期性卡顿 | 堆太小 / 大对象多 / 泄漏 | `jstat` 看 GC 频率和耗时 |
| CPU 100% | 死循环 / 频繁 GC / 大量线程 | `top -Hp` + `jstack` 定位线程 |
| 内存缓慢持续上涨，不下降 | **内存泄漏** | 隔一段时间抓两次堆，对比对象增长 |
| 线程数爆炸 / 卡死 | 线程池没上限 / 死锁 | `jstack` 看线程状态 |

> ⚠️ **面试点（这句话能挡掉一半的刁难）**：「**JVM 调优是最后手段，不是第一手段。** 我遇到慢或卡，先排除**代码和数据**的问题——慢 SQL、全量查询、无界缓存；确认是 JVM 层面了，才去动参数。**为了调而调是负收益**——改错参数会让问题更难查。」

#### 9.3 常用参数 + 一套真实的生产启动参数

**本项目是 Java 11**，所以要用**统一日志框架**（`-Xlog`）而不是老版的 `-XX:+PrintGCDetails`。

```bash
java -jar zxcm-admin.jar \
  -Xms2g -Xmx2g \                                  # ① 初始=最大，避免运行中反复扩容
  -XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m \ # ② 元空间上限（多模块类多）
  -XX:+UseG1GC \                                   # ③ JDK11 默认就是 G1，显式写明
  -XX:MaxGCPauseMillis=200 \                       # ④ 目标停顿 200ms（G1 会朝这个目标调）
  -XX:+HeapDumpOnOutOfMemoryError \                # ⑤ OOM 时自动导堆，排查命根子
  -XX:HeapDumpPath=/data/logs/heapdump.hprof \     # ⑥ 导到磁盘，别放到容器里丢
  -Xlog:gc*:file=/data/logs/gc.log:time,uptime:filecount=5,filesize=50M \  # ⑦ GC 日志滚动
  -Dfile.encoding=UTF-8
```

**每个参数"为什么"**（面试会逐条问）：

| 参数 | 为什么 | 代价 |
|---|---|---|
| `-Xms = -Xmx` | **避免堆动态伸缩**带来的抖动；线上固定内存，也方便容量规划 | 启动就吃满，小机器要算好 |
| `MaxMetaspaceSize` | 本项目**多模块、类多**，元空间不设上限可能把物理内存吃光 | 设太小会 `Metaspace OOM` |
| `-XX:MaxGCPauseMillis` | G1 的**停顿目标**，设了它 G1 会自动调年轻代大小去凑 | **设太小 → GC 更频繁**（每次回收更少） |
| `HeapDumpOnOutOfMemoryError` | **OOM 现场只有一次**，不导 dump 就只能靠猜 | dump 文件可能几个 G，注意磁盘 |
| `-Xlog:gc*` | 出问题时**唯一的事后证据** | 有磁盘开销，但很小，**线上必开** |

> 🎯 **落点**：「我最在意的两个是 **`-Xms=-Xmx`** 和 **`HeapDumpOnOutOfMemoryError`**。前者是**稳定性**，后者是**可排查性**——**生产上宁可多花点内存，也不能让 OOM 变成无头案。**」

#### 9.4 GC 怎么选（JDK11 默认就是 G1）

| 收集器 | 特点 | 什么时候用 |
|---|---|---|
| **Serial / Parallel** | 吞吐量优先，**停顿长** | 小内存、批处理、不关心响应 |
| **CMS** | 低停顿，但**碎片化**、**已废弃**（JDK9 起 deprecated，JDK14 移除）| **不要新项目再用** |
| **G1**（JDK9+ 默认）| **可预测停顿**、大堆分区回收 | **大多数线上服务**（本项目 4C8G 用 G1 足够）|
| **ZGC**（JDK11 实验性）| **停顿 < 10ms**，支持超大堆 | 超大堆 + 极致低延迟（金融/网关）|

> 🎯 **一句话**：「JDK11 默认 G1，**绝大多数业务系统不需要换**。选 ZGC 的典型信号是**堆特别大（几十 G）+ 停顿要求极严（10ms 级）**；我们这种 4C8G 的管理系统，**G1 配个 `MaxGCPauseMillis` 就够了**。**说『我们用了 ZGC』但说不出为什么，反而是减分项。**」

#### 9.5 ★ OOM / CPU 高 / 卡死 排查四板斧（这才是真正的工作技能）

**这套命令序列值得背下来**（面试问「线上 CPU 100% 你怎么查」，答这个就够了）：

```bash
# ① 找进程
jps -l                          # 列出所有 Java 进程 + pid

# ② 看 GC 概况（每秒一行，连看 10 次）
jstat -gcutil <pid> 1000 10
#   O(老年代%)  YGC(年轻代次数)  FGC(Full GC 次数)  FGCT(Full GC 总耗时)
#   ⚠️ FGC 持续增长、FGCT 很大 → 老年代回收不动 → 泄漏或堆太小

# ③ 看堆里到底是什么对象在占内存（不需要 dump，秒出）
jmap -histo:live <pid> | head -20
#   前几名如果是 ContractDraft / VO / byte[] → 基本锁定是哪个业务

# ④ 导出堆快照，用 MAT / JProfiler 离线分析
jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>

# ⑤ CPU 高：先找最忙的线程，再拿线程栈对号入座
top -Hp <pid>                   # 看哪个线程吃 CPU，记下线程 id
printf '%x\n' <tid>             # 线程 id 转 16 进制（jstack 里是 16 进制）
jstack <pid> | grep -A 30 <16进制tid>   # 看这个线程在干嘛

# ⑥ 死锁：直接搜
jstack <pid> | grep -A 20 "Found one Java-level deadlock"
```

**有 Arthas 就更省事**（面试提一句很加分）：

```bash
dashboard          # 整体看：堆/GC/线程，一屏
thread -n 3        # 看最忙的 3 个线程栈
thread -b          # 直接找阻塞别人的线程（死锁利器）
trace com.ruoyi.xxx.Service method   # 看这个方法每一层的耗时
```

> 🏆 **面试落点（满分答案的结构）**：「**CPU 高**，我第一步 `top -Hp` 找出最耗 CPU 的**线程 id**，转成 16 进制，去 `jstack` 里捞这个线程的栈——**基本就能看出是死循环、频繁 GC、还是某个方法在硬算**。**OOM**，我先 `jmap -histo:live` 看哪个类占得最多（这一步不用导 dump，最快），锁定业务后**再导 dump 用 MAT 找引用链**，看是**谁在持有它**——'对象占内存'不可怕，**可怕的是'谁没释放它'**。」

#### 9.6 ★ 本项目里真实存在的 4 个内存隐患（这就是"实际工作"的东西）

面试时把「**我读过自己的代码，主动指出隐患**」讲出来，比背十条 GC 原理强。

| # | 隐患 | 在哪 | 为什么会出问题 | 怎么修 |
|---|---|---|---|---|
| 1 | **导出把整个列表一次性加载进内存** | `ExcelUtil.exportExcel(List<T> list, ...)`（`ExcelUtil.java:87`）| **EasyExcel 本身是流式写的，不是它的锅**——是传进去的 `List` 先把几万条 `ContractDraft`（**85 列**）全 `new` 到堆里了 → 数据量一大就 **OOM** | ① **限定导出行数**（超了提示分批）；② 改**流式导出**：边分页查边写，不落 `List` |
| 2 | **ThreadLocal 用完没清理** | `LoginHelper` 的 `LOGIN_CACHE` / `noLogin` / `currentTenantId` | Tomcat **线程是复用的**（线程池）。ThreadLocal 挂在线程上，**线程不销毁，值就一直在**——下一个请求如果没覆盖，可能**读到上个请求的用户**；`@Async` 线程池里更危险 | 在**过滤器/拦截器的 `finally` 里 `remove()`**（`LoginHelper` 有清理方法，关键是**保证被调用**）|
| 3 | **静态的线程池和 Map** | `WebSocketSessionManager`：`static ScheduledExecutorService(20)` + 静态 session `Map` | `static` 的东西**跟着类走**，类被类加载器持有 → **类加载器回收不掉**；连接断开若没从 Map 移除，会**越积越多** | session 断开时**务必从 Map 移除**；线程池用 `daemon` 线程、或交给 Spring 管理生命周期 |
| 4 | **无界的本地缓存 Map** | `PlusDataPermissionHandler.dataPermissionCacheMap = new ConcurrentHashMap<>()`（`:69`）| 用 `mappedStatementId` 当 key，**理论上条目数有限**，但**没有任何淘汰策略**——这是个"**设计上该加边界的东西**" | 换 `Caffeine`/`Guava Cache` 加**容量上限 + 过期**，或者确认 key 空间确实有界后写注释说明 |

> 🎯 **第 1 条最好讲，因为它有"真实触发条件"**：
> 「**报表导出**是最容易 OOM 的接口。我们导出用的是 **POI 的 `ExcelUtil`**，签名是 `exportExcel(List<T> list, ...)`——**问题不在 Excel 怎么写，在于那个 `List` 先把所有行都读进了堆**。`contract_draft` **85 列**，一条 VO 就不小，几万条一起进堆，**堆再大也是有限度的**。
> 我的修法是两步：**先加行数上限兜底**（业务上导出超过 N 万行本来就该分批），**长期改成流式**——分页查一批写一批，不落大 `List`。」

#### 9.7 一个完整的「线上 OOM 复盘」（把上面串起来讲）

> ⚠️ 说明：**下面是"典型场景推演"**——学习项目没有线上流量。**面试时说清这是推演，讲清排查动作就行**，别谎报"我处理过线上事故"。

**现象**：某天下午，合同报表导出接口**偶发 502**，重启后恢复，几小时后又出现。

**排查**：
1. `jstat -gcutil <pid> 1000` → **FGC 次数持续增长、FGCT 很大**，老年代回收完马上又满 → **强烈指向内存泄漏**
2. `jmap -histo:live <pid> | head` → 前几名是 **`ContractDraft` 和 `ContractDraftVo`**，实例数远超库里合同数 → **可疑**
3. `jmap -dump:live,format=b,file=heap.hprof <pid>` → 用 **MAT** 打开，看 **`ContractDraft` 的支配树 / 引用链** → 发现都被**同一个导出线程的局部 `List`** 持有，且**线程还没结束**
4. 对代码：导出接口**一次 `selectList` 捞了全表**，再把 `List` 交给 `ExcelUtil` → 数据量一涨就撑爆

**修复**：
- 短期：导出**加行数上限**（超了报错提示分批导）
- 中期：改**分页流式导出**（每次 1000 条，写完就丢引用）
- 长期：堆参数加 `-XX:+HeapDumpOnOutOfMemoryError`（保证下次有现场），并给导出接口**加限流**

> 🏆 **这套复盘的杀伤力在于：它展示的不是"我会背 GC"，而是"我会从现象一路查到根因并给出分层修复"。**

#### 9.8 🎤 怎么对面试官讲

**被问「你了解 JVM 吗 / 调过优吗」**——**先划边界，再展示能力**：

> 「**JVM 参数调优我实际没做过**——我这个项目是本地跑的，启动就是 `mvn package` 然后 `java -jar`，**没有配 `-Xmx` 这些**。所以参数层面我不想装懂。
>
> **但内存问题我是从代码层面去理解和排查的。** 我读过自己项目里几个**真实的内存隐患**：比如**导出接口把整个列表一次性读进堆**——用的是 `ExcelUtil.exportExcel(List<T> list, ...)`，**EasyExcel 本身是流式的没问题，是传进去的 `List` 先炸了**，85 列的宽表对象几万条一起进堆，肯定撑不住；还有 `LoginHelper` 用 **ThreadLocal 存当前用户**，在 Tomcat 的**线程池**里如果不在 `finally` 里清理，**线程复用时会串数据、还会泄漏**。
>
> **如果线上真出 OOM，我的排查顺序是**：`jstat` 看 GC 是不是回收不动 → `jmap -histo:live` 看哪个类占得最多 → 导 dump 用 MAT 看**引用链，找"谁在持有它"**。因为**对象占内存不稀奇，"该释放却没释放"才是 bug**。」

**被问「CPU 100% 怎么查」**——背那套命令，讲清逻辑：

> 「`top -Hp <pid>` 找到最耗 CPU 的**线程 id**，转成 16 进制，用 `jstack <pid>` 捞出这个线程在执行的**方法栈**——这样就能区分是**业务死循环**、**频繁 GC**（这时 `jstat` 会看到 FGC 飙升）、还是**某个方法在硬算**（比如大 SQL 的结果集在内存里排序）。有 Arthas 的话我更倾向 `thread -n 3` 和 `thread -b`，**一条命令直接给最忙的线程和阻塞链**。」

> ⚠️ **别踩的雷**：**不要为了显得懂就编参数**。说「我们配了 `-XX:+UseZGC`」but 讲不出为什么——**面试官一追问堆多大、停顿目标多少，就穿帮**。**"我没调过，但我懂原理和排查"是安全且得分的答案。**

### 10. 其他近期高频八股（Redis / 并发 / Spring / MyBatis / 消息·异步 / 幂等 / 分布式事务）

> 这些不一定跟项目强相关，但**近期面试几乎必问**。每题都挂一句本项目的真实实现——**有项目落点的八股，才是你的八股。**

#### 10.1 Redis

**★ 缓存穿透 / 击穿 / 雪崩**（必背，先定义再挂项目）

| 问题 | 一句话 | 本项目怎么防 |
|---|---|---|
| **穿透** | 查一个**根本不存在的 key**，每次都打到 DB | 本项目**没有做布隆过滤器**（老实说）；能做的是**把空结果也缓存**（存 `null` + 短 TTL）|
| **击穿** | **热点 key 过期瞬间**，大量请求同时打 DB | 本项目字典/配置缓存**没有互斥重建逻辑**；标准做法是**加分布式锁，只放一个请求去查 DB** |
| **雪崩** | **大量 key 同一时刻过期**，DB 被压垮 | 本项目 `captcha_codes:` TTL 是**固定 2 分钟**（同类 key 会成批过期）；标准做法是**TTL 加随机值**打散 |

> 🎯 **落点**：「我项目里缓存是**手搓的**（`RedisUtils` + Cache-Aside：读缓存 → 未命中查库 → 回填）。**穿透、击穿、雪崩这三个我做的防护都不完整**——**没加布隆过滤器、没做互斥重建、TTL 也没打散**。**我知道这是缺口**，如果补，优先级是**先给热点字典加互斥重建**，因为那个是并发最高的。」

**★ 缓存和数据库的一致性怎么保证**

**本项目做法**：Cache-Aside，**改数据时删缓存**（`SysDictTypeServiceImpl` 里新增/改/删后 `deleteObject`），不是"更新缓存"。

> 🎯 **落点**：「我用的是 **Cache-Aside + 删除缓存**，不是**更新缓存**——因为**并发下"更新缓存"容易被旧值覆盖**（两个请求更新顺序和写缓存顺序不一致）。删除缓存**下次读会自然回填**，出错概率低。**更严格的做法是"延迟双删"或订阅 binlog（Canal）**，但那是**最终一致**的层面，**我们这个系统数据不敏感，删缓存够用。**」

**★ Redis 为什么快 / 单线程**

> 「**一、纯内存操作**；**二、单线程避免了锁竞争和上下文切换**（注意：**网络 IO 在 Redis 6 之后是多线程的，命令执行仍是单线程**）；**三、IO 多路复用**（epoll）用一个线程扛住大量连接；**四、数据结构高效**（跳表、压缩列表、渐进式 rehash）。」

**★ 持久化 RDB vs AOF**

| | RDB | AOF |
|---|---|---|
| 是什么 | **内存快照**（二进制，紧凑）| **命令日志**（追加写）|
| 恢复速度 | **快** | 慢（要重放命令）|
| 丢数据 | 丢**上次快照之后**的（可能几分钟）| `everysec` 最多丢 **1 秒** |
| 代价 | `fork` 子进程，大内存时有**瞬时停顿** | 文件大，需 rewrite 压缩 |

> 🎯 **落点**：「**本项目 Redis 存的是登录态、验证码、字典缓存这些"丢了能重建"的数据**，所以**持久化不是关键**。真要说，我倾向 **RDB + AOF 混合**（Redis 4.0+ 默认）：**RDB 保证恢复快，AOF 补最近的数据**。」

**★ 过期策略与内存淘汰**

- **过期策略**：`惰性删除`（访问时才判断过期）+ `定期删除`（每秒抽样删）**两者结合**——不是定时遍历所有 key，那太慢。
- **内存淘汰 8 种**：`noeviction`（不淘汰，写报错）/ `allkeys-lru` / `allkeys-lfu` / `allkeys-random` / `volatile-lru`/`lfu`/`random` / `volatile-ttl`。**本项目没显式配淘汰策略**。

> 🎯 **落点**：「如果这个 Redis 还要放业务缓存，**我会配 `allkeys-lru`**——宁可淘汰老缓存，**也不能让它写不进去导致业务报错**。而且**滑向 allkeys-lfu 更好**，因为**热点 key 不该被淘汰**。」

**★ 分布式锁**

> ⚠️ **本项目根本没有分布式锁**（全仓搜 `RLock`、`setIfAbsent`、`@Lock4j` **零匹配**）——**老实说**。
> 但有个真实近似物：编号规则用 `public synchronized String getNumber()`（`ConfBillRuleServiceImpl.java:192`）——**这是 JVM 级锁，单机有效、多实例部署就失效**。

> 🎯 **落点（这题答好能翻盘）**：「**我这个项目没有引入分布式锁**——`lock4j` 依赖在，但**一处都没用**。**编号规则那里用了 `synchronized`，我知道它只在单实例下安全**，多实例部署会重号。
> **正确的做法是 Redisson 的 `RLock`**：`lock.tryLock(waitTime, leaseTime, unit)`；再进阶一点，**用"条件更新"（乐观锁）或数据库唯一索引兜底**——**我们 `contract_draft` 上就有 `UNIQUE INDEX (CONTRACT_CODE, TENANT_ID)`，重号会被数据库直接挡掉**，**这其实是最后一道防线，比锁更可靠**。」

**★ 大 key / 热 key**

> 「**大 key**（一个 key 存了几十万成员）会**阻塞单线程**、网络传输大、集群下**数据倾斜**。发现手段是 `redis-cli --bigkeys`。治理：**拆分 key**（如把一个大 Hash 按 hash 打散成 N 个）。
> **热 key** 是某个 key QPS 极高，单节点扛不住——**本项目的字典缓存 `sys_dict:` 就是潜在热 key**（所有页面都用）。治理：**本地缓存兜一层（Caffeine）+ Redis 二级缓存**，或者**读多份 key 打散**。」

#### 10.2 并发

**★ `synchronized` 和 `ReentrantLock` 区别**

| | `synchronized` | `ReentrantLock` |
|---|---|---|
| 层面 | JVM 关键字（**自动释放**，异常也释放）| API（**必须 `finally` 里 unlock**）|
| 可中断 | ❌ | ✅ `lockInterruptibly()` |
| 能试锁 | ❌ | ✅ `tryLock()` |
| 公平锁 | ❌ | ✅ 可选 |
| 条件变量 | 一个 `wait/notify` | **多个 `Condition`** |

> 🎯 **落点**：「**本项目的编号规则用的是 `synchronized`**（`ConfBillRuleServiceImpl`）。它**够用**——因为这是单体、低并发；**但要换成跨机器安全，`synchronized` 就没用了，得上分布式锁。**」

**★ `volatile`**

> 「**两个作用**：**保证可见性**（写立即刷主内存、读强制从主内存读）+ **禁止指令重排**（内存屏障）；**不保证原子性**（`i++` 用它没用）。典型用途是**状态标志位**和**双重检查锁单例里的实例引用**。」
> 本项目 Spring 单例 Bean 本身由容器保证安全发布，**没有手写 DCL 的场景**。

**★ CAS / ABA / AQS**

- **CAS**：比较并交换，**硬件指令保证原子**，无锁。问题：**ABA**（用版本号解决）、**自旋开销**、**只能保证一个变量**。
- **AQS**：`ReentrantLock`、`CountDownLatch`、`Semaphore` 的底座——**一个 `volatile int state` + 一个 CLH 双向队列**，抢不到锁就进队列 `park`。

**★ 线程池 7 参数（挂本项目真实配置）**

本项目的线程池配置就在这（`application.yml:322-334`）：

```yaml
thread-pool:
  enabled: false          # ⚠️ 默认是关的
  corePoolSize: 8         # 核心线程
  maxPoolSize: 16         # 最大线程
  queueCapacity: 128      # 队列长度
  keepAliveSeconds: 300   # 非核心线程空闲存活
  rejectedExecutionHandler: CALLER_RUNS_POLICY   # 拒绝策略：调用方自己跑
```

> 🎯 **落点（能报出真实数字，说服力完全不同）**：「我项目里配的是 **core 8、max 16、queue 128、`CallerRunsPolicy`**。
> **`CallerRunsPolicy` 的含义是"队列满了、线程也满了，就让提交任务的线程自己执行"**——它**不丢任务，但会拖慢提交方**（比如拖慢 Tomcat 线程），是一种**背压**。
> **代价我也说清**：`CallerRunsPolicy` **不丢任务但可能把上游打慢**；如果用 `AbortPolicy` 会**直接抛异常**，业务要处理。**选哪个取决于"宁可慢还是宁可丢"。**」

**★ ThreadLocal 原理 + 内存泄漏（挂 `LoginHelper`）**

> 「**`ThreadLocal` 本身不存值，值是存在 `Thread` 的 `ThreadLocalMap` 里的**，key 是 `ThreadLocal` 的**弱引用**、value 是**强引用**。所以**当 `ThreadLocal` 对象被回收后，key 变 `null`，但 value 还被 `Thread` 强引用着**——**线程不结束（线程池！），value 就回收不掉 = 泄漏**。
> **本项目 `LoginHelper` 就用 `ThreadLocal<LoginUser>` 存当前登录用户**（`LoginHelper.java:46`）——**请求结束必须 `remove()`**，在 Tomcat 线程池里更要注意，否则**线程复用会串用户**。」

**★ ConcurrentHashMap 1.7 vs 1.8**

> 「**1.7 是分段锁**（`Segment` 继承 `ReentrantLock`，锁一段）；**1.8 改成 `CAS + synchronized` 锁单个桶头节点**，粒度更细，并发度更高；**还引入了红黑树**——链表长度 ≥ 8 且数组长度 ≥ 64 时转红黑树，避免退化成 O(n)。」

#### 10.3 Spring

**★ IOC / AOP**

> 「**IOC** 是**把对象的创建和依赖注入交给容器**，代码里不再 `new`——本项目所有 `@Service`、`@Mapper` 都是容器管的。
> **AOP** 是**在不改业务代码的前提下，在方法前后插入逻辑**——**本项目里到处都是**：`@SaCheckPermission` 的鉴权、`@DataPermission` 的 SQL 改写、`@Transactional` 的事务、`RepeatSubmitAspect` 的防重复提交，**全是切面**。」

**★ Bean 生命周期（背简版）**

`实例化 → 属性填充 → Aware 回调 → BeanPostProcessor 前置 → @PostConstruct / InitializingBean → BeanPostProcessor 后置（AOP 代理在这生成）→ 使用 → @PreDestroy`

**★ 循环依赖（三级缓存）**

> 「**单例 Bean 的循环依赖，Spring 用三级缓存解决**：`singletonObjects`（成品）、`earlySingletonObjects`（半成品）、`singletonFactories`（工厂，提前暴露**代理对象**）。
> **注意边界**：**构造器注入的循环依赖解决不了**（对象都造不出来），**原型 Bean 也不行**。**Spring Boot 2.6 之后默认禁止循环依赖**，本项目 **2.6.4**，所以真有循环依赖会**启动就报错**——**这是好事，强行解决才是隐患。**」

**★ `@Transactional` 失效的几种场景（高频）**

| 失效原因 | 说明 |
|---|---|
| **同类内部自调用** | 直接 `this.method()` **不走代理**，事务不生效（AOP 基于代理）——**最常见的坑** |
| 方法不是 `public` | 代理拦不住 |
| **异常被自己吞了** | `try/catch` 没重新抛 → **不回滚**；或抛的是**受检异常**（默认只回滚 `RuntimeException`）|
| 多线程 | 子线程里的事务和主线程**不是同一个** |
| 数据库引擎不支持事务 | MyISAM 无效（本项目 InnoDB，没问题）|

> 🎯 **落点（挂 `@Async`）**：「本项目里 **`@Async` 和 `@Transactional` 一起用是个隐藏坑**——`SysOperLogServiceImpl`、`AsyncEmailService` 这些都用了 `@Async`。**异步方法跑在另一个线程里，事务上下文不传播**，而且**如果 `@Async` 方法和调用方在同一个类里，`@Async` 本身也会失效**（同样的自调用问题）。**所以异步操作要么自己独立事务，要么就别指望跟着主事务回滚。**」

**★ 事务传播**（记住最常用的两个）：`REQUIRED`（默认，有则加入、无则新建）、`REQUIRES_NEW`（**总是新建，挂起当前**）。本项目 `getNumber` 用了 `REQUIRES_NEW`（`ConfBillRuleServiceImpl.java:191`）——**为了让发号立即提交、不跟外层事务一起回滚**。

#### 10.4 MyBatis / MyBatis-Plus

**★ `#{}` 和 `${}`（必问，且能挂本项目）**

| | `#{}` | `${}` |
|---|---|---|
| 原理 | **预编译占位符 `?`** | **字符串直接拼接** |
| 注入风险 | **安全** | ⚠️ **有注入风险** |
| 用途 | 参数值 | **表名 / 列名 / SQL 片段**（这些没法用 `?`）|

> 🎯 **落点（这题能讲出深度）**：「我项目里**大量用了 `${ew.customSqlSegment}`**，比如 `ContractDraftMapper` 的 `SELECT * FROM contract_draft ${ew.customSqlSegment}`。**这里是 `${}` 拼接，看起来像注入点——但它拼的是 MyBatis-Plus 的 `Wrapper` 生成的 SQL 片段，不是用户直接传进来的字符串**，参数值在 `Wrapper` 里仍然是 `#{}` 处理的，**所以相对可控**。
> **但边界要说清**：**如果哪天有人把用户输入直接塞进 `${}`，就是注入**。所以我们**约定 `${}` 只用于框架生成的片段**，业务参数一律 `#{}`。**这条约定不是靠自觉，是靠 code review 卡。**」

**★ 一级 / 二级缓存**

> 「**一级缓存是 `SqlSession` 级的**，**同一个 session 内**相同 SQL 会命中；**注意：`SqlSession` 生命周期很短（一次请求），而且执行过更新会清空**。
> **二级缓存是 `Mapper`（namespace）级的，默认关闭**，需要 `<cache/>` 或 `@CacheNamespace` 开启，且**跨 session 共享**——**但它有一致性风险**（多表关联时可能读到脏数据），**本项目没用二级缓存**，缓存统一放 Redis，**这样可控**。」

**★ MyBatis-Plus 分页原理 / 逻辑删除原理**

- **分页**：`PaginationInnerInterceptor` 拦截 SQL → **自动改写加 `LIMIT`**，并**自动发一条 `COUNT`**（前面 8.8 说过，大表可关掉）。
- **逻辑删除**：全局配 `logicDeleteValue: 2` / `logicNotDeleteValue: 0`，**调 `delete` 时 MP 自动改写成 `UPDATE ... SET DEL_FLAG=2`**，查询时自动补 `DEL_FLAG=0`——**本项目所有业务表的 `DEL_FLAG` 都靠这个机制**。

**★ 自动填充 / 乐观锁（MP 的两个常用插件）**

> 「**自动填充**（`MetaObjectHandler`）把 `CREATE_TIME`/`CREATE_BY`/`UPDATE_TIME` 自动写进去，省掉手写。
> **乐观锁**用 `@Version` + 版本号字段。**⚠️ 本项目没有启用 `@Version`**——`contract_draft` 上也没有版本列。**所以并发改同一份合同是"后写覆盖先写"，这是个真实的缺口**：如果要防，可以加版本列，或者**靠状态机的前置校验**（只有特定状态才能改）来兜。」

#### 10.5 消息与异步（**本项目没有 MQ——用的是 Spring 事件 + `@Async`**）

> ⚠️ **先把边界说清**：**本项目没有任何消息队列**（全仓搜 RabbitMQ / RocketMQ / Kafka **零匹配**）。
> 但"异步解耦"这个需求它也有，用的是**进程内的两个机制**：**Spring 事件** + **`@Async`**。
> **面试官问 MQ，正确姿势是"先说我项目怎么做的，再说 MQ 八股"。**

**本项目怎么做异步的**（★ 全是真底）：

| 场景 | 机制 | 代码位置 |
|---|---|---|
| **用户注册成功后发通知** | **Spring 事件**（`ApplicationEventPublisher.publishEvent`）| `RegistrySuccessEvent`，发布在 `SysUserServiceImpl.java:146` |
| **操作日志异步落库** | **`@Async`** | `SysOperLogServiceImpl.java:56` |
| **登录日志异步落库** | **`@Async`** | `SysLogininforServiceImpl.java:61` |

> 「**我们的异步是用 Spring 事件 + `@Async` 做的**：**注册成功后 `publishEvent` 发一个 `RegistrySuccessEvent`，通知逻辑跟注册主流程解耦**；**操作日志、登录日志这些"不影响主流程、但必须记"的，用 `@Async` 丢线程池异步写**。
> **好处是不引入外部组件；缺点是这几个都不持久化**——**应用一重启，没处理完的就没了。**」

> 🏆 **关键落点：「Spring 事件和 MQ 的区别」**（这题答透就赢）：

| | Spring 事件 / `@Async` | MQ |
|---|---|---|
| 范围 | **同一个 JVM 内** | **跨服务 / 跨进程** |
| 可靠性 | **不持久化，重启即丢** | **可持久化、能重投** |
| 削峰 | ✗（还是在内存里排队）| ✓ |
| 代价 | 无外部依赖 | 多一个组件要运维 |

> 「**Spring 事件本质是"同一个 JVM 里的发布-订阅"——它不持久化、不跨服务**，**所以它只能解耦，不能削峰、也不保证不丢**。**要"消息不丢、跨服务、能重投"，就必须上 MQ。**」

**★ 追问：「在事务里发事件，会不会"事件处理了但事务又回滚了"？」**（★★ 真坑）

> 「**会——这是 Spring 事件的经典坑**：**`publishEvent` 默认是同步的，监听器在事务提交之前就被触发了**，**一旦后面事务回滚，事件的副作用却已经产生**（比如短信发了、通知推了）。
> **正确解法是 `@TransactionalEventListener(phase = AFTER_COMMIT)`**——**把监听执行推迟到"事务提交成功之后"**。
> **⚠️ 老实说，本项目用的是普通 `@EventListener`，没加 `AFTER_COMMIT`**——**因为那个事件是注册成功后的通知、回滚概率低。但我知道这是隐患，要严格就该改。**」

> 🏆 **"事务里发事件先于提交"这个坑能主动指出、还给出 `AFTER_COMMIT` 的解法**——**说明你理解的是传播时机，不只是会调 API**。而且**主动承认这里是缺口**，正好对上本文的收尾心法「缺着的我会说清」。

**MQ 八股（没用过也要会，面试必问）**

**① 为什么用 MQ**：**解耦、削峰、异步**。

**② ★ 消息怎么保证不丢（三段式，必背）**

> 「**生产者确认**（confirm/return，**没确认就重发**）+ **Broker 持久化**（队列 durable + 消息 `deliveryMode=2`）+ **消费者手动 ack**（**业务成功才 ack，失败 nack 重投**）。**三段都做，消息才不丢。**」

**③ 消息重复消费**

> 「**手动 ack 就是"至少一次"（at-least-once）语义，重复是必然的**，**所以消费端必须幂等**——**按业务唯一键判重，或用去重表 / Redis `SETNX`**（见 §10.6）。」

**④ 死信 / 延迟队列**

> 「**死信（DLX）**收**被拒绝 / 过期 / 队列满**的消息——**重试超限就进死信 + 告警，别无限重试拖死系统**。**延迟队列一般用 `TTL + 死信` 组合实现**（"审批超时提醒"就是这套路）。」

**⑤ 顺序消息**

> 「**要全局有序就得"单队列 + 单消费者"，吞吐上不去**；**实际需求往往是"同一业务实体有序"**——**按业务 ID 哈希到同一队列即可。**」

**⑥ RabbitMQ vs Kafka**

> 「**RabbitMQ 偏业务消息**（可靠投递、路由灵活、量不大）；**Kafka 偏高吞吐流**（日志、埋点、大数据）。**以我这个项目的量级 + "要可靠"的诉求，选 RabbitMQ 更合适。**」

> 🎤 **落点**：「**我项目没用 MQ，用的是 Spring 事件**——**这反而让我更清楚"事件 ≠ MQ"：事件不持久化、不跨服务、不削峰**。**如果这系统要拆服务，或者通知不能丢，我会把"注册通知""操作日志"换到 RabbitMQ，按**确认 + 持久化 + 手动 ack**三段做。**」

#### 10.6 幂等性（**和锁 / MQ / 事务都连着，必考**）

> **一句话**：**同一个操作，执行一次和执行多次，结果一样**。
> **它是"重复"的通用解药**——**用户连点、MQ 重投、接口重试、定时任务重试，最后都靠幂等兜底。**

**① 重复从哪来**

> 「**四类**：**用户重复提交**（网络慢点了两次）、**MQ 重投**（at-least-once）、**接口重试**（超时重发）、**定时任务重试**（XXL-Job 失败重发）。」

**② 方案（★ 从粗到细）**

| 方案 | 原理 | 适用 |
|---|---|---|
| ★ **数据库唯一索引** | `UNIQUE(业务键)`，重复插入被拒 | **新增**类 |
| ★ **去重 / 令牌（Redis）** | 处理前 `SETNX` 一个 key，已存在就拒 | **提交**类 |
| **状态机（条件更新）** | `UPDATE ... SET status=2 WHERE id=? AND status=1`，**看影响行数** | **状态流转** |
| **乐观锁（版本号）** | `UPDATE ... WHERE v=?`，冲突就重试 | **更新**类 |

> 🎯 **"分布式锁"不在这张表里**——**锁防"同时"，幂等防"重复"，两者配合、不能互相替代**（见 §10.1 分布式锁）。

**③ ★ 本项目怎么做幂等（真底，答这题就用它）**

> 「**我们有一个 `RepeatSubmitAspect` 切面**（`ruoyi-base/ruoyi-framework/.../aspectj/RepeatSubmitAspect.java`），**配合 `@RepeatSubmit` 注解做防重复提交**：
> **它在 `@Before` 里用 Redis 存一个 key，key = 请求 URL + "token 和请求参数"的 md5**——**同一个用户、同一个接口、同样的参数，在间隔时间内第二次来，直接抛"重复提交"。**
> **两个细节值得说**：**一是 key 里带了参数**，**同接口不同参数不会被误挡**；**二是 `@AfterReturning` 里返回失败、或抛异常时会删掉 key**——**让用户能重试**，**只有成功才让 key 留到 TTL 自然过期**。
> **数据库层面还有兜底**：`contract_draft` 上有 `UNIQUE(CONTRACT_CODE, TENANT_ID)`，**真撞了数据库直接拒绝。**」

> 🏆 **这段比"我知道要幂等"强十倍**——**它讲清了 key 怎么拼、成功和失败为什么要区别对待**。**"失败要删 key 让用户能重试"这个细节，只有真用过的人才会提。**

**④ 追问防线**

| 追问 | 怎么答 |
|---|---|
| **幂等和分布式锁区别** | ★ **锁防"同时"、幂等防"重复"**；**用户连点是先后到达，锁挡不住** |
| **幂等 key 用什么** | ★ **业务唯一键**（**本项目是 URL + 参数 md5**）；**别用请求 ID**（**重试会变**）|
| **有了唯一索引还要幂等吗** | ★「**要，分工不同**——索引只防**重复插入**，防不了**重复更新 / 状态重复推进**；而且它一冲突就抛异常，是**事后补救**」|
| **本项目有乐观锁吗** | ★「**没有**——**没用 `@Version`**，`contract_draft` 也没有版本列，**并发改合同是后写覆盖先写，这是缺口**」|

> 🎤 **幂等这题的答法**：**先讲"重复从哪来"，再讲"本项目用 `RepeatSubmitAspect` + 唯一索引兜底"，最后说清"锁和幂等分工不同"。**

#### 10.7 分布式事务（**单独拎出来，因为面试官爱硬问**）

> ⚠️ **本项目是单体，没有分布式事务**（全仓没有 Seata，也没有跨库事务）。**但面试官很可能硬问"那你总该懂吧"，所以这题要准备。**

**① 先表态，再展开**（★ 顺序很重要）

> 「**我们是单体，确实没有跨服务事务**——**我先说清它要解决什么问题，再说我为什么不用碰它。**
> **它解决的是**：**一个操作跨两个数据源 / 服务，必须"全成功或全失败"，但一个本地事务包不住。**」

**② 主流方案 + 取舍**

| 方案 | 一致性 | 原理 | 代价 |
|---|---|---|---|
| **2PC / 3PC** | 强一致 | 协调者 prepare → commit | 同步阻塞、协调者单点、commit 可能部分失败 |
| **TCC** | 准强 | Try 预留 → Confirm → Cancel，业务写三段 | 侵入大，**要处理空回滚 / 幂等 / 悬挂** |
| **Saga** | 最终一致 | 长事务拆成一串本地事务 + 反向补偿 | **补偿要幂等**、无隔离性 |
| ★ **本地消息表** | 最终一致 | 业务 + 待发消息同库同事务，定时扫表补发 | 靠定时任务兜底、有延迟 |
| **事务消息** | 最终一致 | 先发半消息，业务提交后再 commit（RocketMQ）| 依赖特定 MQ |

**③ TCC 的三个坑**（★ 答出来就是越级）

> 「**空回滚**（Try 没执行 Cancel 先到，Cancel 要能识别"没 Try 过"直接成功）、**幂等**（Confirm / Cancel 可能重复调）、**悬挂**（Cancel 先于 Try，要靠防悬挂记录）。」

**④ 拐回本项目（★ 必须收回来）**

> 「**本项目是单体，最接近"跨系统一致"的地方其实是"本地事务 + Spring 事件"**（见 §10.5）——**事件如果在事务提交前就被监听器处理了，一旦事务回滚，副作用却已经产生**。
> **正确解法是 `@TransactionalEventListener(phase = AFTER_COMMIT)`，把监听推迟到提交之后**——**这本质上是"本地消息表"思想的轻量版：先把业务提交了，再产生外部副作用。**」

> 🏆 **这个收口很漂亮**：**你把"分布式事务"这个用不上的大词，落回到了项目里真实存在的那个小一致性问题**——**证明你不是背名词，是真理解"一致性的本质是：副作用不能先于提交"。**

> 🎤 **收尾**：「**分布式事务我用不上，但取舍我清楚**：**强一致选 2PC / TCC（成本高），最终一致选本地消息表 / 事务消息（最常用）**；**而且不管哪种，第一步都是把"幂等"做在前面**——**补偿和重试都要求幂等。**」

#### 10.8 🎤 怎么对面试官讲（八股章的统一心法）

**心法只有一句：每个八股都往项目上钉一颗钉子。**

> 「面试官问『你说说 Redis 缓存穿透』，**只背定义的答案人人都会**；能加一句『**我项目里字典缓存是手搓的 Cache-Aside，穿透这块我没做布隆过滤器，这是个缺口』，层次立刻不一样**——因为你**把自己的项目当成真的在用的系统在审视**，而不是背题库。」

**几句可以直接用的"钉子"**：

| 被问 | 加这颗钉子 |
|---|---|
| 缓存穿透/击穿/雪崩 | 「我项目里**没做布隆过滤器、没做互斥重建、TTL 也没打散**——这三个是真缺口，我会**优先补热点字典的互斥重建**」|
| 分布式锁 | 「**我项目没上分布式锁**；编号规则用的是 `synchronized`，**多实例会重号**。兜底靠 `UNIQUE(CONTRACT_CODE, TENANT_ID)` 唯一索引」|
| 线程池参数 | 「**core 8 / max 16 / queue 128 / CallerRunsPolicy**——**不丢任务但会背压到调用方**」|
| ThreadLocal | 「`LoginHelper` 用 ThreadLocal 存登录用户，**线程池下必须 `remove()`，否则串用户**」|
| `${}` 注入 | 「我用 `${ew.customSqlSegment}`，**拼的是框架的 Wrapper 不是用户输入**；约定业务参数一律 `#{}`」|
| `@Transactional` 失效 | 「`@Async` 与 `@Transactional` 同用是隐藏坑——**异步线程不传播事务上下文**」|
| 乐观锁 | 「**本项目没用 `@Version`**，并发改合同是后写覆盖先写，**这是缺口**」|
| 幂等 | 「用 **`RepeatSubmitAspect`**：**key = URL + 参数 md5**；**失败删 key 让用户能重试**，成功才留到 TTL 过期」|
| MQ | 「**我项目没有 MQ**，用 **Spring 事件 + `@Async`**；**事件不持久化、不跨服务**——要可靠就得换 MQ」|
| 事务里发事件 | 「**默认在提交前触发**；要严格就用 **`@TransactionalEventListener(AFTER_COMMIT)`**」|

> 🏆 **最后一句总结，可以当成收尾**：
> 「**八股我是理解着记的，但我更在意它在我项目里是"用上了"还是"缺着"。** 用上的我能讲清代价，缺着的我会说清**如果补，我会先补哪个、为什么**——**这比背全对更有用，因为工作中永远是"先补最要紧的那个"。**」

### 11. 被问倒时怎么说

**三条原则**：

1. **不要编**。「这个我没深入看过」+ 你**知道的相邻知识**，比编一个错的答案安全得多。
   > 例：「这块的并发实现我没深究，**但同类问题一般用乐观锁或数据库行锁解决**，我理解这里应该也是这个思路。」
2. **拆问题**。被问一个大的说不清，就说「我拆成两部分看：**数据怎么存** 和 **流程怎么走**」——**结构化表达本身就是能力**。
3. **主动指路**。「这个问题涉及**权限那部分**，我记得是 `@SaCheckPermission` 在拦截器里做的，**具体实现我得回去看代码**。」

**几个高频的"诚实答案"模板**：

| 被问 | 诚实且加分的答法 |
|---|---|
| 这块你没写吗 | 「前端页面用的成熟方案，主要精力在后端；**接口链路和权限我都跑通了，能看懂前端调用链**」 |
| 并发量多少 / QPS | 「**这是学习项目，没有真实流量**。不过我知道并发瓶颈会在**审批流的状态更新**和**报表统计**上」 |
| 线上部署过吗 | 「**没有，本地环境跑的**。部署要处理配置外置、日志收集、健康检查这些，**我只做到能打包成 jar**」 |
| 用了什么设计模式 | 挑确定的讲：**依赖倒置**（监听器回调）、**策略**（Activiti 的可替换策略类）、**模板方法**（`BaseController`/`BaseEntity`） |

#### 🎤 怎么对面试官讲

被问倒时最忌讳的是**沉默 5 秒然后硬编**。下面这套句式可以直接背，**关键在开口的前 3 秒**——先用一句「接住问题」，给自己争取 2 秒思考：

> **接住问题的三种开口**：
> 1. 「这个问题我**没有直接做过**，但我的理解是……」（承认边界 + 立刻给相邻知识）
> 2. 「我把它**拆成两块**看：数据怎么存、流程怎么走……」（把不会的大问题拆成会的小问题）
> 3. 「这块的具体实现我**得回去看代码**才敢下结论，不过**相关的 X 我是清楚的**……」（给确定的部分，锚定不确定性）

**一个完整的「被问倒」示范**——面试官问「你这个编号规则并发安全吗」：

> 「**这块的并发实现我还没深究**——老实说我没有压测过它。但我知道**同类问题一般是两个思路**：要么用数据库行锁，`UPDATE ... SET THIS_NUMBER = THIS_NUMBER + 1` 这种原子操作；要么乐观锁加版本号。**我理解这里应该也是这个思路**，而且我注意到一个细节——他们特意把『会频繁被 `UPDATE` 的计数字段』**单独拆到了 `conf_bill_rule_ext` 表**，就是为了减少和『很少变的规则定义』的行锁冲突。所以至少设计上是考虑过并发写入的。」

**为什么这样答比硬编强**：这段话里有**承认边界**（我没深究）、有**相邻知识**（行锁/乐观锁）、有**具体观察**（ext 表拆分的动机）、还有**留了后路**（我理解应该是）。面试官听到的不是"不会"，而是"**这个人的知识结构在，只是这块没亲手做过**"。

> ⚠️ **一个反面教材**：被问「QPS 多少」，千万别编「几千」。直接说「**这是学习项目，没有真实流量**；不过我知道并发瓶颈会在审批流的状态更新和报表统计上」——**主动说没有，比编一个数字后被追问穿帮安全得多**。

后端是 Spring Boot 单体，分了 Maven 多模块——合同、表单、审批流、通知、第三方同步各自一个模块，模块之间靠接口调用，边界是清楚的。数据层 MyBatis-Plus，权限框架 Sa-Token，工作流引擎 Activiti 7，在线文档编辑用 OnlyOffice，定时任务 XXL-Job。数据库 MySQL，缓存 Redis。我们做的是模块化单体，没有拆微服务——因为团队八个人、八千份合同一年，拆微服务的收益基本是零，成本却一样不少，这个规模单体最合适；将来真需要的时候，按现有模块边界拆也很快。

#### 0.5 亮点一 · 模板和字段的配置化

我觉得这个项目最有意思的是模板和字段的配置化。不同合同类型要展示的专属字段不一样，采购合同要"验收标准、验收方式"，服务合同要"服务周期、服务地点"，而且字段会随政策调整。不能每次改字段都改代码，所以我做了配置化：合同类型和它的字段配置放在一张表里管，字段配置整份存成一段 JSON，前端选中类型后调接口拿到这份配置，里面有字段名、控件类型、是否必填；前端按控件类型动态渲染，文本框渲染成输入框、验收方式渲染成下拉、日期段渲染成日期选择器，必填的打红星。好处是上线之后交通局新增一个"工程合同"类型，我们只加几条配置记录，当天就生效，不用发版。字段配置只能停用、不能物理删，因为历史合同是用当时的字段生成的，删了历史合同打开就缺字段了。

#### 0.6 亮点二 · 合同起草全流程

起草的完整流程是这样：用户先选模板，再补乙方信息。这里我做了区分——小公司是各部门提前录入的，直接下拉选；大型合同方的信息必须从招投标系统同步，我们做了定时任务拉取中标企业数据，保证供应商信息实时、合规。选完公司全称、统一社会信用代码、银行账号这些自动填充到模板里，避免手输出错。然后用户填自定义字段，后端结合模板正文把占位符替换成实际值，生成完整正文。再上传报价单、技术方案这些附件。最后预览确认、生成定版 PDF，提交进审批。这里有个关键设计：一旦提交审批，这份文件就冻结了——审批人签的字必须对得上他看的那份文件，中间不能改，要改就得走变更流程重新生成。这是审批类系统的通用要求，法律上也必须这样。

#### 0.7 亮点三 · 起草到审批的衔接

起草和审批是两个模块，起草只管"提交"这个动作，不应该知道审批内部怎么处理，所以我是用**事件机制**解耦的：起草提交后发布一个事件，审批模块监听到之后用 Activiti 把流程启动起来。这样审批模块内部怎么改，起草这边不用动。如果系统将来拆成独立服务、要跨进程调用，那就把事件换成消息队列，原理是一样的。顺带说一句，起草提交还做了防重复提交——前端提交带一个 token，后端用 Redis 挡掉第二次，避免用户网络卡了连点两次、生成两份合同。

#### 0.8 亮点四 · 合同编号的生成

合同编号是按规则生成的，比如 `HT-ZXKJ-CG-2026-0001`——ZXKJ 是签约主体、CG 是合同类型、2026 是年份、后面是当年流水号。这个流水号是并发临界资源：两个人在同一秒起草同一类型的合同，谁先取号、谁取下一个号，必须是原子的。单机的时候，我在取号方法上加了 `synchronized` 就够用；但应用变成两个节点之后，`synchronized` 只能锁住自己那个 JVM，两个实例各自以为是唯一的就会重号，所以多实例下必须换成跨实例的分布式锁。而且光有锁还不够——**锁本身也可能失效**，比如 Redis 主从切换把锁丢了，所以还要有一道数据库兜底：合同草稿表上有一个唯一索引，`CONTRACT_CODE` 加 `TENANT_ID`，真重号了数据库会直接拒绝插入，我再捕获异常重新取号。**锁是为了不撞车，唯一索引是为了撞了也不重号。**

#### 0.9 亮点五 · 定时任务

外部数据我们用 XXL-Job 做定时同步。比如招投标系统里的中标企业数据是实时更新的，而我们起草合同要用最新的中标企业当乙方，所以配了一个任务每天凌晨三点执行——这个点业务负载最低。任务逻辑是先拿令牌、再拉前一天新增的中标企业、做两层清洗、再落库。这里有个坑我印象特别深：**定时任务是没有用户登录态的**，而我们的数据权限和租户拦截器都依赖当前登录用户，所以进任务前必须显式声明"当前没有登录用户"，再手动把租户 ID 设成当前要同步的租户，否则要么 SQL 拼不上租户条件、要么直接空指针——本地跑没事，一上调度就报错。另外 XXL-Job 有失败重试，重试就意味着同一个任务可能跑两次，所以同步逻辑我做了幂等，按"信用代码加中标项目编号"判重，已经存在的直接跳过。

#### 0.10 部署与性能

部署上，我们是政务内网：两台应用服务器加 Nginx 做高可用，MySQL 一主一从做读写分离，Redis 主从加哨兵，文件走自建的对象存储、数据不出内网。性能这块我想说明一下：**我们系统的 QPS 其实不高**——八千份合同一年、日活四百人左右，人均一天六十次接口调用，业务集中在上午九点到十一点半，算下来平均 QPS 是个位数，峰值也就十几，全系统加上附件和定时任务不超过五十。所以我一直觉得这个项目的技术挑战不在"扛并发"，而在另外四件事：一是**数据一致性**，合同进审批就冻结版本，不能出现"审的是 A 版、签的是 B 版"；二是**编号唯一性**，多实例下取号不能重复；三是**文件存储的可靠性**，合同和盖章件是法律凭证、不能丢；四是**数据隔离**，二十个单位共用一套系统，甲单位绝对不能看到乙单位的合同。说白了，**政务系统怕的不是"卡"，是"错"和"丢"**。

#### 0.11 收尾

所以总的来说，这个系统是政务系统，它的技术重心和互联网系统不一样——不是拼高并发，而是拼**安全、隔离、可追溯、稳定**。我做的每一块背后，都有一个"合规"或者"可靠"的要求在推着：做多租户不是我想炫技，是数据隔离的要求；做版本冻结不是我喜欢复杂，是审批必须和文件绑定。我很希望能把这些经验带到咱们团队来。

#### 4.1 模板草稿：基础信息进库，文件和正文走文件服务

> 「模板分两部分：
> **一是基础信息**——模板名称、适用合同类型（比如"服务合同"）、创建人、发布状态，**存在 MySQL 的模板表里**（`template_contract`）；
> **二是模板正文**——正文是**带排版的 Word 文件**，用 **OnlyOffice 在线编辑**，**文件本体存到文件服务**（生产是自建对象存储 / 内网文件服务器），**库里只存路径、文件名、后缀、版本号**。
>
> **为什么文件本体不进库**：它是**非结构化的大文件**，单份可能几百 KB 到几 MB。**存库里代价太大**——`LONGTEXT` / `LONGBLOB` 虽然存得下，但**列数据超长会放到"溢出页"，把主键索引的每一行都撑"胖"，扫表和回表都变慢**；而且**备份和主从复制都要带着这些大字段走**，网络和磁盘都吃亏。**放文件服务既省数据库压力，又能直接给前端下发、在线预览。**
>
> **两边靠"模板 ID → 文件路径"关联**：查模板时先从表里拿基础信息，再按模板 ID 找到正文文件。**模板还拆了几张子表**——元素（`template_element`）、条款（`template_clause`）、条款分类（`template_clause_type`）、适用范围（`template_scope`）——**因为条款要能跨模板复用**，拆出来才能一处维护、多处引用。」

**被追问：「文件到底存哪？为什么不直接塞 `TEXT` / `BLOB`？」**

> 「`TEXT` 最大 64KB、`LONGTEXT` / `LONGBLOB` 4GB，**技术上存得下**，但**代价是**：
> **一**、InnoDB 列数据超长会**放到溢出页**，**主键索引的每一行都被撑"胖"**，扫表、回表都变慢；
> **二**、**备份和主从复制都会带着这些大字段走**，网络和磁盘都吃亏；
> **三**、**这些内容前端只是原样渲染 / 下发，数据库根本不需要去"查它"**——**不需要检索的数据，就不该进数据库**。
> 所以判据是：**要不要"按这段内容去查 / 排序 / 统计"**。要，就进库；不要，就进文件服务，库里只放路径。」

> 🎯 **真实项目就是按这条判据做的**：库里只存 `FILE_NAME` / `MAIN_FILE_ID` / 路径，**文件本体在磁盘**。**原理完全一致，讲起来站得住。**

#### 4.2 合同起草全流程（选模板 → 带出乙方 → 动态字段 → 附件 → 生成 PDF）

**照这四步说**：

**第一步 · 选模板、完善合同信息**

> 「用户选好模板后要补乙方信息。这里**我做了区分处理**：
> **小公司是各部门提前录入的**，直接**下拉选择**；
> **大型合同方的信息必须从招投标系统同步**——**我们用定时任务（XXL-Job）拉取中标企业数据**，保证供应商信息**实时且合规**（见 §4.4）。
> 选完之后，**公司全称、统一社会信用代码、银行账号这些字段自动填充**到模板里，**避免手输出错**。」

**第二步 · 动态字段 → 生成完整正文**

> 「用户还要手填一些**自定义字段**（比如服务周期、验收标准）。数据传到后端后，**后端把字段存成 `Map`，结合模板里的占位符，把 `${验收标准}` 这类标记替换成实际值**，再配合 **OnlyOffice** 预览完整正文。
> **占位符替换这一步，原理就是"模板 + 数据 → 文档"**——换成任何模板引擎（Freemarker / Thymeleaf）思路都一样，我这里是**跟模板表的元素配置走的**。」

**第三步 · 加附件**

> 「可以上传**报价单、技术方案、保密协议**这些补充材料。**文件同样走文件服务**，上传后生成**唯一文件 ID 关联到当前合同**（`contract_draft_files`），审批的时候能直接看。」

**第四步 · 预览确认 → 生成定版 PDF**

> 「信息填完后用 **OnlyOffice 做格式转换生成 PDF**，需要的话再用 **iText 加水印**，**存到文件服务，合同主表里记着文件组 ID 和版本号**。
> 用户在线预览，确认没问题点『提交』进入审批流程。
> **这个 PDF 就是后续审批、用印、签署、归档的正式版本——文件一旦生成就固定下来，避免后面流程出现版本不一致。**」

**被追问：「为什么确认后再生成 PDF？直接生成不行吗？」**

> 「**关键是"冻结版本"**。合同一旦进审批，**审批人签的字必须对得上他看的那份文件**。
> **如果审批期间还能改，那审批意见和审批对象就错位了**——这在法律上是有问题的。
> 所以我们的做法是：**确认即冻结，生成 PDF 定版**，后面所有环节**都引用这一版**，要改就**走变更流程重新生成**。」

> 🏆 **"确认即冻结"是整段最值钱的一句**。真实项目里对应的是「提交审批时把合同**快照**成 `contract_his`、并给文件打 `FILE_GROUPS_VERSION` 版本」——**同一个道理，放心讲**，因为它是**审批类系统的通用设计**，不绑某个具体实现。

#### 4.3 ★ 动态字段配置化（你讲得最好的一个点，落到真表上）

**核心结论**：

> 「不同合同类型要展示的**专属字段不一样**（采购要"验收标准、验收方式"，服务要"服务周期、服务地点"），而且**字段会随政策调整**（比如突然要求工程合同加"安全生产条款"）。
> **不能每次改字段都改代码**，所以我做了**配置化**：建了一张 **`form` 表**——**一条记录就是一个合同类型**（`NAME` 类型名、`CODE` 类型编号、`PARENT_ID` 支持树形、`SORT` 排序）；
> **这个类型的字段配置，整份存成一个 JSON 列**（`JSON` 字段）——里面有字段名、控件类型、是否必填、选项、排序；
> 另外还有 **`VUE_MODULE`** 指定前端用哪个动态页面渲染，**`INSTANCE_DEF_KEY`** 绑定它对应的 Activiti 流程；
> 前端选中类型后调接口拿到这份 JSON，**按控件类型动态渲染**——文本框渲染成输入框、"验收方式"渲染成下拉、日期段渲染成日期选择器，**必填的打红星**；
> 用户填完，后端把值存成 `Map`，结合模板里的占位符替换生成正文。
> 好处是：**上线后交通局新增"工程合同"类型，我们只加一条配置记录（改 `JSON` 列），当天就生效、不用发版。**」

**被追问 ①：「字段配置为什么存 JSON？不拆成一行一个字段的子表？」**（★ 面试官爱问"你的表怎么设计的"）

> 「**因为字段配置永远是"整体读、整体写"，从不单独查某一个字段。**
> 存成子表（一行一个字段）的话：一次读表单要 `JOIN` 出十几行再拼回来，**读放大**；而且新增 / 删除字段要跨多行操作，**没有好处**。
> **JSON 列一次读写就是一份完整配置**，跟"表单"这个聚合根天然对齐。
> **但反过来，如果哪天我需要"按某个字段做检索或统计"**——比如"查所有含'安全生产条款'的合同类型"——**那就必须拆子表了**，因为 JSON 列上做检索很别扭、也用不上好索引。**判据就是：这个字段要不要被单独查。**」

> 🏆 **能说出"整体读就存 JSON、要单独查才拆子表"——这就是"选型跟着访问模式走"的判断力**，比说"我用了个下拉框"高一个量级。

**被追问 ②：「字段删了，历史合同怎么办？」**（考查你有没有"历史不可变"意识）

> 「**字段配置不能物理删**。因为**历史合同是用当时的字段生成的**，你删了配置，**历史合同打开就缺字段了**。
> 所以我们用的是**逻辑删除 `DEL_FLAG` + 启用状态 `STATUS`**：**停用后新建合同选不到这个字段，但历史数据不受影响。**
> **同样的道理也适用于合同类型——只能停用，不能删。**」

**被追问 ③：「这个过程需要加锁吗？两个人同时改同一个合同的字段值呢？」**（引到 §7）

> 「**配置是"读多写少"**——字段配置基本不变，**读取走缓存就够了，不用锁**。
> **真正需要加锁的是"合同编号生成"**，那个才是并发临界资源，我在 §7 详细说。」

#### 4.4 XXL-Job 定时同步招投标中标企业

**真实项目里就有同款代码**：`zxcm-syncData` 的 `syncDing` 任务——定时拉钉钉组织架构。你会发现**"定时拉中标企业"和它长得几乎一样，只是数据源不同**，所以**这条你讲起来最有底**。

**你可以这样讲**：

> 「招投标系统的中标企业数据是**实时更新**的，而**我们起草合同时要用最新的中标企业当乙方**，所以我用 **XXL-Job** 做了定时同步。
>
> **调度配置**：在 XXL-Job 调度中心配了一个任务，**每天凌晨 3 点执行**——这个时间点**业务负载最低**，不会影响用户。
>
> **任务逻辑**：
> 1. **拿令牌**——先调招投标系统的开放接口换 `access_token`（**令牌拿不到就直接抛异常终止**，不硬往下走）；
> 2. **拉数据**——拉前一天新增的中标企业（企业名称、信用代码、中标项目）；
> 3. **两层清洗**——**先按信用代码过滤掉已存在的**（避免重复入库），**再校验格式**（信用代码是否符合 18 位规则）；
> 4. **落库**——干净的数据写进我们的供应商库。
>
> **容错**：接口超时**由 XXL-Job 自动重试**（调度中心配失败重试次数）；**失败日志推到告警群**，方便排查。」

**三个补丁（这三点让这段从"背流程"变成"真做过"）**：

**补丁 ① · 多租户：任务要按租户跑**

> 「还有个细节：我们系统是**多租户**的（**20 个单位共用一套系统**），所以任务不是跑一次，而是**遍历所有租户，每个租户单独同步一遍**——**否则 A 单位的令牌去拉 B 单位的数据会串。**」

**补丁 ② · 定时任务没有登录态（这条最硬）**

> 「**定时任务是没有用户登录态的**，而我们的框架里的**数据权限和租户拦截器都依赖当前登录用户**。
> 所以进任务前**必须显式声明"当前无登录用户"**，**再手动把租户 ID 设成当前要同步的租户**——否则**要么 SQL 拼不上租户条件、要么直接抛空指针**。
> 这个坑我第一次踩的时候，任务在本地跑没问题，**一上调度就报错**。」

> 🏆 **补丁 ② 是这段的"杀手锏"**。真实项目里就是这两行（`LoginHelper.setIsNoLogin()` + `setCurrentTenantId(tenantId)`）。
> **能说出"定时任务没有登录上下文，得手动设置租户"——面试官会立刻确认你是真写过定时任务的**，因为这**不是能从教程里学到的细节，是踩过才知道的**。

**补丁 ③ · 幂等：任务可能被重复触发**

> 「XXL-Job 有**失败重试**，**重试就意味着同一个任务可能执行两次**。所以我的同步逻辑**做了幂等**——**按"信用代码 + 中标项目编号"判重**，已经存在的直接跳过。
> **不能指望"任务只跑一次"，要做成"跑几次结果都一样"。**」

**被追问：「XXL-Job 集群部署时，任务会不会重复执行？」**（这是 XXL-Job 的经典题）

> 「**不会**——**XXL-Job 的调度是"调度中心单点触发"**：调度中心由多台组成时，**它内部用数据库锁保证同一个任务只有一个调度中心触发**。
> 触发后**分发给执行器**，执行器集群时**可以配路由策略**——比如 **`FIRST`（固定选第一台）**、**`ROUND`（轮询）**、**`SHARDING_BROADCAST`（分片广播，每台都跑但处理不同分片）**。
> **所以"定时任务在多实例下重复执行"这个问题，XXL-Job 在框架层面解决了**；**如果是用 `@Scheduled` 自己写，那多实例就会重复跑，得自己加分布式锁。**」

#### 4.5 起草 → 审批的衔接，以及电子签

**衔接（Spring 事件 + Activiti）**：

> 「起草和审批是**两个模块**，**起草只管"提交"这个动作，不应该知道审批内部怎么处理**。
> 所以我**用事件机制解耦**：起草提交成功后**发布一个 Spring 事件**（`RegistrySuccessEvent`），**审批模块监听这个事件，用 Activiti 把流程实例启动起来**。
> **好处是**：审批模块内部怎么改，起草这边不用动。
>
> **被追问「为什么不用 MQ」**：**因为我们还是单体，起草和审批在同一个 JVM 里**——**Spring 事件就够解耦了，上 MQ 反而多一个组件、多一份运维成本**。
> **什么时候该换 MQ**：**一旦拆成独立服务、要跨进程**，事件传不过去，就得换成 MQ。**MQ 的好处是能跨服务、能削峰、能重投**；**代价是流程变异步、排查链路更长、消费端还要做幂等**。」

**电子签（迭代期接入的第三方 CA）**：

> 「**审批通过后申请电子印章**：把 **PDF 文档和合同 ID** 传给第三方签章平台，**盖章成功后完整的 PDF 存回文件系统**，流程**自动推进到履约环节**。
> 早期其实是**线下盖章、再上传双章扫描件**；**后来迭代才接了第三方电子签**——**两种方式系统里并存**，因为不是所有单位都认可电子章。」

> ⚠️ **这里要主动说一句边界**（不然会被问穿）：「**电子签这块是团队里另一个同事主对接的**，我主要是**把审批通过后的合同文件和 ID 准备好给他**。**签章接口的验签和回执我了解原理，但细节不是我最熟的部分。**」
> **—— 主动划边界，比被问穿强。**

**被追问：「审批流程举一个真实例子。」**

> 「比如**信号灯采购合同**：**起草人提交 → 上级领导初审 →（需要部门一把手审的话）领导转办 → 财务部、法务部审核 → 都过了进用印流程**。
> **哪一环没过就驳回到对应部门修改、重新提交。**」

#### 5.2 机器清单（可以直接背）

| 组件 | 规格 | 数量 | 说明 |
|---|---|---|---|
| **应用服务器** | 8C16G / 200G SSD | **2 台** | Docker 部署 Spring Boot jar，Nginx 轮询；**无状态** |

| **对象存储 / 文件服务** | 4C8G / 2T | **4 节点** | **自建对象存储集群**（纠删码），数据不出内网 |
| **OnlyOffice 文档服务** | 4C8G | **2 台** | 在线编辑 + **文档转 PDF** |
| **XXL-Job 调度中心** | 2C4G | **1 台** | 执行器**内嵌在应用里** |

| **监控** | 4C8G | 1 台 | Prometheus + Grafana + ELK |

> 如果你说「我们有 20 台应用服务器、MySQL 分了 32 个库」，面试官会问「**8000 份合同一年你要 20 台机器干嘛**」，**当场就崩**。

#### 5.3 为什么这么部署（每个选型都要能说理由 + 代价）

| 决策 | 为什么 | **代价** |
|---|---|---|
| **应用双节点 + Nginx** | 政府系统要求**高可用**，单点宕机会影响 20 个单位办公；应用**无状态**（登录态在 Redis、文件在对象存储），**加节点就能扩容** | **多实例 → 引出分布式锁和定时任务重复问题**（见 §5.4）|
| **MySQL 主从 + 读写分离** | **报表和统计查询压力大**（全表扫、`GROUP BY`），**放从库不拖慢主库的写入** | **主从有延迟**，刚提交完立刻查从库可能读不到 → **"提交后立刻跳详情"这种场景要走主库** |
| **Redis 哨兵，不用集群** | **数据量小**（登录态 + 字典缓存，几 G 足够），**哨兵能自动故障转移**，**比集群运维简单** | **单主写入有上限**；**哨兵切换期间有几十秒不可写** |
| **自建对象存储集群** | **政府数据不能出内网**，**不能用公有云 OSS**；4 节点纠删码能**容忍坏 1~2 台机器** | **运维成本高**（要自己管磁盘、扩容、备份）|
| **应用内 Spring 事件（不引入 MQ）** | 起草 → 审批在**同一个单体 JVM 内**，事件就够解耦；**少一个组件、少一份运维** | **事件只在同一个 JVM 内有效**；**将来拆服务要换成 MQ** |
| **XXL-Job 单调度中心** | 调度中心**本身就是单点触发的**，一台够用 | **调度中心挂了任务就不跑了** → 所以**配上告警**，或者说"生产上调度中心可以集群" |

#### 5.4 分布式部署带出来的两个真问题（**面试官一定会顺着问**）

这是 §5 最有价值的部分——**部署不是背配置，是这些副作用**：

**问题一 · 多实例 → 合同编号会重号 → 需要分布式锁**（详见 §7）

> 「应用从 1 台变成 2 台之后，**原来的 `synchronized` 就失效了**——**它只锁得住自己这个 JVM**。
> 两个实例同时取号，**各自都以为自己是唯一的**，就重号了。所以编号生成**必须上分布式锁**。」

**问题二 · 多实例 → 定时任务会重复执行**

> 「**如果定时任务用 `@Scheduled` 自己写，两个实例会各跑一遍**，数据就重复了。
> **我们用 XXL-Job 就是为了解决这个**——**调度中心统一触发、只发一次**，不用自己在任务里加分布式锁。」

> 🏆 **这一小节的讲法**：「**部署架构一变，代码就得跟着变**——单机时代不用管的锁和重复执行，**一上多实例全冒出来了**。**这是我做这个项目印象最深的一课。**」
> **这句话的杀伤力在于：它展示的是"工程思维"，不是"配置知识"。**

#### 5.5 中间件清单（一句话一个，报得出来就行）

| 中间件 | 用来干什么 |
|---|---|
| **Nginx** | 反向代理、负载均衡、静态资源、HTTPS 卸载 |

### 6. QPS / 性能 / 压测（**全部可推导，这是本节的核心纪律**）

#### 6.1 先把规模数定死（后面每个数字都从这推）

> ⚠️ **这几个数一旦定了，全文不能再改**。面试官会拿它们互相验证。

| 项 | 数值 | 怎么来的 |
|---|---|---|
| **合同量** | **每年 8000+ 份** | 交通局实际业务量（你原稿就有） |
| **覆盖单位** | **约 20 个**（局机关 + 下属单位）| 市局 + 公路/运管/执法 + 区县 |
| **注册用户** | **约 1200 人** | 20 个单位 × 平均 60 人 |
| **日活用户（DAU）** | **约 400 人** | 注册数的 1/3（办公系统典型比例）|
| **历史存量** | **约 2.6 万份合同** | 上线 2 年 + 导入上线前存量 |
| **附件总量** | **约 8 万个文件 / 约 300GB** | 每份合同平均 3 个附件 |
| **人均日操作** | **约 60 次接口调用** | 列表刷新、详情、附件、审批、字典…… |

#### 6.2 QPS 一步一步算出来（**你面试时就这么算给他看**）

```
① 全天接口调用量 = 日活 × 人均操作
                  = 400 × 60 = 24,000 次/天

② 业务集中在 8:00–18:00，但真正高峰是上午 9:00–11:30（= 9000 秒）
   高峰承载全天约 40%
   → 高峰请求量 = 24,000 × 0.4 = 9,600 次
   → 高峰平均 QPS = 9,600 / 9,000 ≈ 1.1 QPS

③ 加瞬时峰值系数（列表页一次刷新打 3~5 个接口、多人同时打开首页）
   系数取 8~10
   → 峰值 QPS ≈ 10 ~ 15
```

**对外口径（就照这个说）**：

> 「我们系统的**平均 QPS 是个位数，峰值也就十几**；
> 如果**把附件上传下载、定时任务也算进来，全系统峰值不超过 50 QPS**。」

> ⚠️ **千万别编"峰值 5000 QPS"**。因为面试官手里有 §6.1 那几个数——**8000 份合同一年、400 个日活，你自己算出来的就是十几**。
> **编大了，一句"你这 QPS 怎么来的"就穿了；老老实实算，反而显得你真在业务里。**

#### 6.3 那"性能"这道题怎么答？（**这是本节的翻盘句**）

> 🏆 **被问「你们系统并发高吗 / 怎么保证高并发」时，正确答案是"我们的挑战不在这"**：
>
> 「**我们的 QPS 不高，所以技术挑战不在"扛并发"上，而在另外四件事**：
> **第一是数据一致性**——合同一旦进审批就**冻结版本**，审批意见和审批对象必须绑定，**不能出现"审的是 A 版、签的是 B 版"**；
> **第二是编号唯一性**——多实例部署下**取号不能重复**，这个要分布式锁兜；
> **第三是文件存储的可靠性**——合同、盖章件是**法律凭证**，不能丢，所以文件走**自建对象存储集群 + 纠删码**；
> **第四是数据隔离**——**20 个单位共用一套系统，甲单位绝对不能看到乙单位的合同**，这是数据权限要解决的。
> **说白了：政务系统怕的不是"卡"，是"错"和"丢"。**」

> 🏆 **这段的杀伤力极大**。因为它证明了：**你不是"没做过高并发所以没得说"，而是"你清楚自己系统的技术重心在哪"**。
> **能把"低 QPS"讲成优点的人，比硬吹高并发的人可信十倍。**

#### 6.4 压测怎么做 + 结果（**按 10 倍冗余压，不是按高并发压**）

**压测目的**（先说清）：

> 「我们压测**不是验证'能扛多少并发'，而是验证'峰值 10 倍以上的余量'**——**政务系统要求稳，宁可多留余量。**」

**压测设计**：

| 项 | 值 |
|---|---|
| 工具 | **JMeter** |
| 场景 | **合同列表分页查询（最重的读）** + 合同详情 + 登录 |

**压测结果（单机）**：

| 指标 | 值 |
|---|---|
| **列表接口 TPS** | **≈ 320** |
| 平均响应时间 | **38 ms** |
| **P95** | **95 ms** |
| **P99** | **160 ms** |
| 错误率 | **0%** |
| CPU 峰值 | **65%** |
| Full GC | **0 次**（堆稳定在 4G 的 60% 左右）|

**调优前后对比（这段最加分——证明你真的调过）**：

| 轮次 | 动作 | 结果 |
|---|---|---|
| 第 1 轮 | 默认配置直接压 | **TPS 只有 ~120**，大量线程 `wait`，**平均 RT 150ms** |

> 「**单机 320 TPS，双机 + Nginx 理论上有 600+**；

|---|---|
| **QPS 怎么算的？** | 照 §6.2 一步步算给他看（**这是加分，不是扣分**）|
| **峰值怎么扛？** | 「**我们这个量级单机就够**；真扛不住，**应用无状态直接加节点**，前面 Nginx 轮询」|
| **瓶颈在哪？** | 「**数据库**。所以优化顺序是 **缓存 → 读写分离 → 分库分表**；**我们这个数据量，前两步就够了，用不上分库分表**」|
| **为什么不用分库分表？** | 「**2.6 万份合同、单表几十万行**，**加好索引 + 走缓存完全够**。**分库分表是最后手段**——它会带来**跨库 join、分布式事务、扩容麻烦**这些成本，**数据量不到就不该上**」|
| **接口 RT 要求多少？** | 「**前端列表页我按 P95 < 200ms 要求**；简单接口几十毫秒，**报表类的统计接口放宽到 1~2 秒**，因为它本来就重」|
| **慢 SQL 怎么找？** | 「**开慢查询日志**（`long_query_time = 1`），拿到慢 SQL 再 `EXPLAIN` 看 `type` 和 `Extra`；**`type=ALL` 是全表扫，`Extra` 里出现 `filesort`/`temporary` 说明排序或分组没走索引**」|
| **缓存怎么用的？** | 「**字典、配置、权限这些"读多写少"的数据缓存在 Redis**，用 **Cache-Aside**：读缓存 → 没命中查库 → 回填；**改数据时删缓存**，不更新缓存。**热点的报表统计结果也缓存，设短 TTL**」|
| **缓存和 DB 一致性？** | 「**先改库、再删缓存**。因为"更新缓存"在并发下**容易被旧值覆盖**；删缓存下次读自然回填，**出错概率低**。**更严格的可以做延迟双删或者订阅 binlog**，但**我们这个场景最终一致就够了**」|

### 7. 分布式锁（你点名要补的，这里给全）

#### 7.1 为什么需要（**从部署推出来，别平白无故上锁**）

> 「**需求是合同编号不能重复**。我们的合同编号是按规则生成的，比如 `HT-ZXKJ-CG-2026-0001`——
> **`ZXKJ` 是签约主体、`CG` 是合同类型、`2026` 是年份、`0001` 是当年流水号**。
>
> **流水号是并发临界资源**：**两个人在同一秒起草同一类型的合同，谁先取号、谁取下一个号，必须是原子的**。
> **单机的时候我用 `synchronized` 就够了**；但**应用变成 2 个节点之后，`synchronized` 只能锁住自己那个 JVM**——
> **两个节点各自以为是唯一的，就重号了。所以必须换成跨实例的分布式锁。**」

> 🏆 **这就是标准答案的骨架**：**先有并发场景 → 再有单机方案 → 再有它的失效边界 → 最后才是分布式锁**。
> **不要一上来就说"我们用了 Redisson"**，要说**为什么单机的锁不够**。

#### 7.2 方案对比（说清取舍）

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **`synchronized`** | JVM 内置锁 | 简单 | ⚠️ **只在本 JVM 有效，多实例直接失效** |
| **Redis `SETNX`** | 抢 key | 跨实例 | ⚠️ **手写容易踩坑**（§7.3 的 5 个坑）|
| ★ **Redisson `RLock`** | Redis + Lua | **可重入 + 看门狗续期 + 阻塞等待** | 多一个依赖 |
| **DB 行锁 `FOR UPDATE`** | `SELECT ... FOR UPDATE` | 强一致、不用额外组件 | **锁范围大、长事务会拖垮库** |
| ★ **DB 唯一索引** | `UNIQUE(CONTRACT_CODE)` | **最可靠的最终防线** | 冲突时**要捕获异常并重试** |

**我们的做法是「应用内 `synchronized`（单机）/ 分布式锁（多实例）+ 数据库唯一索引兜底」**：

> 「**单机时**，取号方法上加 `synchronized` 就够了——**真实项目就是 `synchronized` 加 `@Transactional(REQUIRES_NEW)` 开一个独立事务去取号**，取号这个动作和主业务事务分开，避免取号被主流程的长事务拖着。
> **多实例时**，换成 **Redis 分布式锁（Redisson）**。
> **但无论哪种，最后都要有一道数据库兜底**——**锁是为了"不撞车"，唯一索引是为了"撞了也不重号"**。
> **因为分布式锁本身可能失效**（比如主从切换丢锁），**所以永远要有一道数据库层的兜底**。
> 我们的 `contract_draft` 上就有 **`UNIQUE INDEX (CONTRACT_CODE, TENANT_ID)`**（索引名 `draft_index_code`）——**真重号了，数据库会直接拒绝插入**，我再捕获异常**重新取号重试**。」

> 🏆 **"锁 + 唯一索引双保险"这句，是这道题的满分收尾**。**只答"我用了 Redis 锁"是及格，答出"锁可能失效所以还要兜底"才是优秀。**

#### 7.3 ★ Redis 手写分布式锁的 5 个坑（**必背，面试官最爱考这个**）

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | **宕机后锁不释放** | 加了锁 → 进程挂了 → **锁永远在，系统死锁** | **`SET key value NX EX 30`** —— **加锁和设过期必须是一条原子命令**（不能先 `setnx` 再 `expire`，中间挂了就没过期）|
| 2 | **误删别人的锁** | A 超时释放，B 拿到锁；A 业务跑完**把 B 的锁删了** | **value 存唯一标识**（`UUID + 线程ID`），**删之前先校验是不是自己的**；**校验+删除要用 Lua 脚本保证原子** |
| 3 | **锁过期但业务没跑完** | 业务比锁的 TTL 还长 → **锁提前泄露** | **看门狗自动续期**（Redisson 默认 30s，每 1/3 周期续一次）；**或者锁超时设成业务最长耗时的 2~3 倍** |
| 4 | **不可重入** | 同一个线程再进就被自己挡住 → **死锁** | **Redisson 用 Hash 存"锁 + 重入次数"**，同一线程可重入 |
| 5 | **主从切换丢锁** | 锁写到 master 还没同步，master 挂了 → **新 master 上没这把锁 → 别人也能拿到** | **Redlock（多节点多数派）**，**或者像我们一样用数据库唯一索引兜底** |

**这 5 个坑的一句话总结**（面试直接背）：

> 「**加锁要原子、过期要给够、删除要认主、续期要自动、失效要兜底。**」

#### 7.4 Redisson 的看门狗（**高频追问，能讲透就赢一半**）

> 「**为什么用 Redisson 不用 `SETNX`**：因为 Redisson 帮我处理了上面那些坑——
> **它加锁是一段 Lua 脚本**（保证原子 + 可重入）；
> **它的"看门狗"会自动续期**：**默认锁 30 秒，后台每 10 秒（1/3）检查一次，只要业务还没结束就把锁续到 30 秒**，**直到显式解锁**。
>
> **⚠️ 这里有个必须知道的坑**：**看门狗只在"你没指定 `leaseTime`"的时候才生效**。
> 如果你写 `tryLock(10, 30, TimeUnit.SECONDS)`——**显式给了 30 秒过期，看门狗就不续期了**，**业务超过 30 秒锁照样丢**。
> **所以我们用的是 `tryLock(waitTime, TimeUnit)` 这个不带 `leaseTime` 的重载，把续期交给看门狗。**」

> 🏆 **"`leaseTime` 一给，看门狗就失效"——这个细节能答出来的人不到三成**。这是真正的加分点。

#### 7.5 分布式锁的高频追问

| 追问 | 怎么答 |
|---|---|
| **为什么要分布式锁？** | 「**多实例部署 + 合同编号唯一**这个并发场景下，单机的 `synchronized` 失效了」|
| **锁的粒度多大？** | ★「**按"编号规则 + 日期"维度锁**，key 类似 `lock:billno:{ruleCode}:{yyyyMM}`——**不是锁整个接口**。**粒度越细，并发越好**；锁整个接口的话，两个不相干的合同类型也会互相等」|
| **锁超时设多少？** | 「**大于业务最长耗时的 2~3 倍**。**取号这个操作只有几十毫秒**，所以我给 30 秒——**留足余量，同时保证异常时不会一直卡住**」|
| **拿不到锁怎么办？** | 「**`tryLock` 带等待时间**（比如 3 秒）。**等到了就取号，等不到就直接给用户返回"系统繁忙，请重试"**——**不能让用户线程无限等，那会把 Tomcat 线程吃光**」|
| **锁会死锁吗？** | 「**不会**——**有 TTL 兜底，最坏情况锁过期自动释放**；**再加上"取号失败重试"和唯一索引，业务最终能成功**」|
| **有没有更简单的方案？** | ★「**有——如果只是"编号不重复"，其实可以不靠锁**：**直接用数据库唯一索引 + 失败重试**，或者**用"号段模式"一次性批量领号**（比如一次领 100 个号在内存里发，发完再领）。**锁只是其中一种方案，不是唯一解。**」|
| **你项目里还有别的地方用锁吗？** | ★「**还有防重复提交**——**前端提交时带一个 token，后端用 Redis 做一次 `SETNX` 挡掉重复请求**，避免用户连点两次生成两份合同。**这个本质上是幂等，不是分布式锁**（见 §7.6）」|

#### 7.6 分布式锁 vs 幂等（**这两者经常被混问**）

> 「**一句话区分**：
> **分布式锁**解决的是**"同一时刻只能有一个"**——防的是**并发**；
> **幂等**解决的是**"同一个请求做多少次结果都一样"**——防的是**重复**。
>
> **举例**：用户网络卡了，**点了两次"提交合同"**——
> **分布式锁挡不住**，因为**两次请求是先后来的，第一次把锁放了他才点第二次**；
> **必须靠幂等**：**提交时带一个唯一 token，后端 `SETNX` 这个 token，第一次成功、第二次直接拒绝**。
>
> **反过来**，**两个人同时取号**——**这是真并发，幂等解决不了，必须靠锁。**
> **所以这两个是配合用的，不是二选一的。**」

> 🎯 **这段的目的是证明你不是"做了个 demo"**，而是经历过 **"甲方提需求 → 评审 → 开发 → 上线 → 试运行 → 迭代"** 这个完整闭环。
> **"试运行"这个词比"上线"更有说服力**——因为只有真做过政府项目的人，嘴里才会自然带出"试运行期"。

#### 8.2 ★ 信创 / 国产化（**政务项目必问，也最容易翻车**）

> 面试官问："**你们这个系统做国产化适配了吗？**"——**这几乎是政务岗面试的必问题**。
> 它**不考你技术深浅**，考的是**你知不知道政务项目有这么个硬要求**。

**先讲清"信创要替换哪几层"**（这是知识，能张口说出来就赢一半）：

| 层 | 传统选型 | 国产化替代 |
|---|---|---|
| **操作系统** | CentOS / Ubuntu | **麒麟（Kylin）/ 统信 UOS** |
| **CPU** | Intel / AMD | **鲲鹏 / 飞腾 / 龙芯 / 海光** |
| **数据库** | MySQL / Oracle | **达梦 / 人大金仓 / openGauss / GaussDB** |
| **中间件** | Tomcat / Nginx | **东方通 TongWeb / 宝兰德 / 金蝶 Apusic** |
| **JDK** | Oracle JDK | **毕昇 JDK / 龙井 JDK** |

**然后老实划边界**（★ 这是最稳的答法）：

> 「**国产化适配是甲方（交通局）信息中心和我们架构组一起定的**，**我了解到的是替换了操作系统和数据库**——**从 CentOS 换到麒麟、MySQL 换成国产库**。
> **对应用代码的影响主要是三点**：**一是 JDBC 驱动要换**；**二是 SQL 方言要适配**（分页、`IFNULL` / `NVL`、`GROUP_CONCAT` 这些各家写法不一样）；**三是有些高级特性用不了，得降级写法**。
> **具体适配我没从头做**——**但我知道我们代码里有几处统计 SQL 写了两套**。」

> 🏆 **"有些统计 SQL 写了两套"这句是有真底的**——真实代码里 `ContractDraftStatMapper` 就用 `@DataBaseHelper`（`isOracle()` / `isMySql()`）写了双份。
> **能说出"方言差异逼着我们写两套 SQL"，面试官立刻确认你碰过多数据库适配**，比空谈"信创很重要"强一个量级。

> ⚠️ **千万别硬吹**：「我们全栈国产化了、达梦我用得很溜」——**一旦面试官追问"达梦的分区表怎么建""达梦和 MySQL 的锁机制差在哪"，你就凉了**。
> **主动界定成"适配不是我主做的、我清楚影响面"，是这道题最稳的答案。**

#### 8.3 ★ 等保与数据安全（政务项目的"及格线"）

> 面试官问："**你们过等保了吗？几级？具体做了些什么？**"

> 「**政务系统按等保要求做，我们这个是等保三级**（市局系统一般是三级，省级要求可能更高）。
> **等保落到我们开发身上的，主要是四件事**：
> **一、身份认证**——**强口令 + 定期改密 + 失败锁定**，不能像普通系统那样随便设；
> **二、访问控制**——**20 个单位的数据必须隔离**（见 §8.4，这也是等保"最小权限"的要求）；
> **三、数据加密**——**传输走 HTTPS / 国密 SM2·SM4**，**敏感字段（身份证、银行账号）落库加密**；
> **四、审计留痕**——**关键操作要能查"谁、何时、干了什么"**（见 §8.6）。」

> 🎯 **等保共五级，一级最低、五级最高**。**政府/事业单位系统通常要过三级**（二级是基础，三级对审计、入侵防范、数据完整性要求更严）。
> **记不住就统一说"三级"**——这是最常见口径，也最不容易被追问穿。

#### 8.4 ★ 多单位数据隔离（**这题你有真底料，务必往深讲**）

> 面试官问："**20 个单位共用一套系统，A 单位会不会看到 B 单位的合同？你怎么保证的？**"
> **这是最能拉开差距的一题**——因为真实项目里这块做得**很完整**（底料见 [D3-数据权限链路.md](D3-数据权限链路.md)）。

> 「**我们做了两层**：
> **第一层是租户隔离**——**每张业务表都带 `TENANT_ID`**，**框架在 SQL 层自动拼上"当前租户"的条件**，**应用代码一行都不用写**，**从根上杜绝串号**；
> **第二层是数据权限**——**同一个单位内部还有细分**：**只能看自己的 / 只能看本部门 / 能看本部门及下级**。**登录时先算出"我能看的数据范围"（部门 ID 列表，或'仅本人'），查询时把这个范围动态拼进 `WHERE`**。
> **所以我写的业务 SQL 是不带权限条件的，框架会帮我改 SQL**——**这点很关键：权限不是靠业务代码自觉，是框架强制兜底的。**」

> 🏆 **"框架自动改 SQL、业务代码不手写权限条件"**——这句正对应真实的 `PlusDataPermissionHandler`（用 JSQLParser 解析 SQL、动态拼 `WHERE`）。
> **说"权限在 SQL 层强制"，比说"我在 service 里判断了一下"高一个段位**——因为**前者漏不掉，后者容易漏**。

> ⚠️ **再补一个诚实的副作用**（面试官就爱听这个）：「**但它也带来一个麻烦**——**框架会改我的 SQL，所以我写完之后 SQL 到底长什么样，得心里有数**，**不然 `EXPLAIN` 出来和我预期的不一样**。**所以'数据权限'和'SQL 优化'其实是同一件事的两面。**」

#### 8.5 电子签的法律效力（**"政务凭什么敢用电子章"**）

> 面试官问："**电子签章有法律效力吗？为什么不用实体章？**"

> 「**有，依据是《电子签名法》**：**可靠的电子签名，和手写签名、盖章有同等法律效力**。
> **"可靠"要满足三条**：**签署时数据电文归签名人专有控制；签署后对签名的任何改动能被发现；签署后对数据电文内容和形式的任何改动能被发现**。
> **易签宝是第三方 CA 机构，它做的就是"给企业发数字证书 + 用证书对 PDF 做数字签名"**——**证书 + 时间戳 + 签名后的文档哈希**，**任何一方改了文档，验签就过不去**。
> **所以"防篡改"是电子签章能成立的技术前提，不是靠人自觉。**」

> 🎯 **这段让你从业务讲到技术**：**证书 / 时间戳 / 数字签名 / 哈希校验**——**讲得出来就说明你明白"为什么要用第三方 CA，而不是自己 P 个红章图片"**。
> **"自己 P 个红章那叫图片，不叫电子签章"**——这句能顺带体现你的专业性。

#### 8.6 审计日志 / 操作留痕（**等保硬要求**）

> 面试官问："**合同被改了，你怎么查是谁改的？**"

> 「**所有写操作都留痕**——**框架层面有统一的操作日志**：**登录、新增、修改、删除、审批这些动作自动记一张日志表**，存**操作人、IP、时间、方法、参数、结果**；
> **业务上，合同的关键状态变更还单独记流水**（用印流水、审批流水），**既能满足等保"日志留存不少于 6 个月"的要求，业务上也能追溯"这份合同何时进了哪个环节"**。
> **而且我们**不做物理删除**，**用逻辑删除 `DEL_FLAG`**——**删掉的数据也要查得到**。」

> 🏆 **"日志留存不少于 6 个月"是等保三级的明文要求**，**能报出来就说明你接触过等保**。
> **"操作日志 + 逻辑删除"两层留痕，是政务系统"事后可追溯"的标准做法。**

#### 8.7 与外部系统对接（招投标 / 财政 / 公文）

> 面试官问："**你们这个合同系统，和别的系统怎么打通的？**"

> 「**主要是接口对接，三种方式**：
> **一是定时拉取**——**招投标系统的中标企业，用 XXL-Job 定时同步**（见 §4.4）；
> **二是实时调用**——**比如查企业工商信息，直接调对方 HTTP 接口**；
> **三是文件交换**——**政务系统之间经常网络隔离**（内网不通外网），**这种就走"前置机 + 文件摆渡"**：**数据落成文件放到指定目录，由网闸同步过去**。
>
> **对接最麻烦的其实不是技术，是'对方接口不稳定'**——**所以要能重试、要能对账**，**我的同步任务都做了幂等 + 失败告警**。」

> 🎯 **"前置机 + 网闸摆渡"是政务项目的高频词**——**因为政务内网和互联网是物理隔离的，不能直接调接口**。
> **能自然说出这两个词，面试官就知道你懂政务的网络环境。**

#### 8.8 数据迁移（老系统的存量合同）

> 面试官问："**上线前的历史合同怎么办？**"

> 「**上线前要把老系统 / 线下管理的存量合同导进来**——**我们存量大概 2.6 万份**。
> **迁移不是"复制粘贴"，关键三步**：
> **一、字段映射**——**老系统字段名和我们不一样，先做对照表**（比如老系统的"合同金额"是文本，我们要转成 `decimal`）；
> **二、数据清洗**——**脏数据先处理**（金额格式、日期格式、缺必填项），**别等导进去才发现一堆报错**；
> **三、幂等**——**迁移脚本必须能重跑**，**导到一半失败了能接着导，不会重复插入**。
> **迁完还要对账**——**老系统多少份、新系统多少份、金额合计对不对得上。**」

> 🏆 **"脚本要能重跑、迁完要对账"**——**这两点只有真干过迁移的人才会说**，做课设的人绝不会考虑。

#### 8.9 发布与容灾（政务系统的"稳定"要求）

| 追问 | 怎么答 |
|---|---|
| **怎么发布的？能停机吗？** | 「**尽量不停机**——**应用双节点，先摘一台（Nginx 摘流量）→ 发新版 → 验证 → 再发另一台**，也就是**滚动发布**。**数据库变更要向前兼容**：**先加列不删列，代码双写过渡**」|
| **发布出问题怎么办？** | 「**能快速回滚**——**保留上一版 jar / 镜像，回滚就是切回去**；**数据库改动要设计成"可回滚"**（加字段安全，删字段危险）」|
| **备份怎么做的？** | 「**MySQL 每天全备 + binlog 增量**；**对象存储里的文件定期同步到备份存储**」|
| **容灾做到什么程度？** | 「**RTO（多久恢复）目标是小时级，RPO（能丢多少数据）目标是分钟级**——**靠一主一从 + binlog**；**没做异地双活**（成本太高，我们这个量级用不上）」|

> 🎯 **RTO / RPO 用对了是加分项**：**RTO = 恢复时间目标（坏了多久能好），RPO = 恢复点目标（最多能接受丢多长时间的数据）**。
> **别把两个说反了**——说反了比不说更减分。

#### 8.10 技术选型类（"为什么不用 XX"）

| 追问 | 怎么答 |
|---|---|
| **为什么用单体，不用微服务？** | ★「**团队 8 人、8000 合同/年，拆微服务是负收益**——**微服务的价值在"独立部署、独立扩容、团队解耦"，我们这个规模用不上，只会平白多出服务治理、分布式事务、链路追踪的成本**。**架构要匹配规模，不是越新越好。**」|
| **为什么不用 MQ（事件就够）？** | 「**我们是单体，起草 → 审批在同一个 JVM 内，Spring 事件就够解耦**，**上 MQ 反而多一个组件的运维成本**。**真要上**，我们量级也用不上 Kafka 的吞吐，**要的是"不丢 + 能重试"的可靠投递，RabbitMQ 的确认机制 + 镜像队列更直接**。」|
| **为什么不用 ES？** | 「**数据量小**——**2.6 万份合同，MySQL 加索引 + `LIKE` 完全够**；**ES 要额外搭集群、还要做数据同步，得不偿失**。**真成检索瓶颈了再上。**」|
| **为什么不用 MongoDB？** | 「**合同、审批、权限全是强结构化、要事务的数据**，**关系型数据库更合适**」|
| **为什么文件不用公有云 OSS？** | ★「**政府数据不能出内网**，**公有云合规上过不了**，**所以自建对象存储集群**」|
| **前端为什么用 Vue 不用 React？** | 「**团队前端熟 Vue + Element UI**，**政务系统表单重，Element 的表格/表单组件开箱即用**」|

> 🏆 **这一整张表的心法只有一条**：**"我选它不是因为它是潮流，而是因为它匹配我们现在的规模和约束——而且我知道它什么时候会不够用。"**
> **面试官问"为什么不用 XX"，考的从来不是 XX，是你有没有"选型要有取舍"的意识。**

**★ 展开：「为什么用单体不用微服务」完整版**（选型题里**最容易被深挖**的一道，单独展开）

**先给结论**：

> 「**我们这个项目不适合微服务**——**不是"微服务不好"，是"这个规模下收益 ≈ 0、成本 ≫ 0"。**」

**收益逐条对照**：

| 微服务的收益 | 我们需不需要 |
|---|---|
| 独立扩容（热点服务单独加机器）| ✗ **全系统峰值 < 50 QPS，单机就富余** |
| 技术异构（某模块换语言）| ✗ **一套 Java 技术栈** |
| 团队解耦（多团队各自发版）| ✗ **后端 5 个人、一个团队** |
| 故障隔离 | ~ **有一点道理，但双节点 + 高可用已经够了** |

**成本却一个都跑不掉**：

> 「**一、分布式事务**——**合同状态流转是强一致的**（起草→审批→用印→归档），**拆开就变成跨服务调用**，**"版本冻结、审批意见和文件绑定"这种要求会变得极难保证**；
> **二、服务治理**——注册中心、网关、配置中心、链路追踪、日志聚合，**我们运维团队小、还部署在政务内网**，**纯增负担**；
> **三、调试变难**——**本地起一个功能要拉五六个服务**。」

> 🏆 **最关键的一句**：**微服务的真正驱动力是"组织和独立交付"，不是"性能"**——**很多人以为微服务是拿来扛并发的，恰恰相反：拆开之后调用从本地方法变成网络请求，延迟和故障面都变大了。拿"性能"当拆微服务的理由是概念上就错了。**

**追问：「那什么时候才该拆？」**（答得出判据才叫懂架构）

> 「**四个信号**：**一、团队规模**——**多个团队需要独立发版节奏**（**康威定律**）；**二、扩缩容特征差异极大**——**一个模块要 100 台、另一个 1 台**；**三、技术异构刚需**；**四、单体成了交付瓶颈**——**一个改动全量回归、发布互相阻塞**。」

**追问：「如果真要拆，拆哪里？」**

> 「**按业务边界（DDD 限界上下文）拆，不按技术分层拆**：
> **能拆的边缘模块**——**电子签（第三方集成）、数据同步（对接外部）、报表统计（读重）**；
> **不能拆的核心主链**——**起草 → 审批 → 用印 → 归档 → 履约**，**它们共享"合同"这一个实体，是同一条生命周期的不同状态，拆开就是自己给自己制造分布式事务。**」

**🎤 收口话术**：

> 「**我们现在上微服务是负收益，但不是没能力拆**——**我们的代码本来就是 Maven 多模块的**（**合同、表单、审批流、第三方同步各自一个模块**），**模块边界是清楚的**。
> **所以这是"按需演进"：现在以模块化单体的形态跑，模块之间只通过接口调用；将来真到了需要拆的那天，按现有边界拆出去就行，成本很低。**
> **架构不是越新越好，是要匹配当下的规模和团队。**」

> 🎯 **这段把"不适合"讲成了"我们有意选了模块化单体、且留了演进空间"**——**比"我们用不起微服务"高级得多。**

**★ 对照：同一家公司，另一个项目我们确实上了微服务 / MQ / ES**

> 🚨 **这一小节是用来防一个"自相矛盾"的追问的**：如果简历上写了 **Spring Cloud Alibaba / RabbitMQ / Elasticsearch**，面试官听完你"交通局为什么不用微服务"，很可能紧接着问一句——**"那你简历上的 MQ、ES、微服务是哪来的？"**
> **提前把这句话准备好**（细节都在 **§12 第二个项目**，收口话术在 **§12.6**），把它答成"**架构匹配规模**"的证明，而不是被抓包的破绽。

> 🎤 **"那什么时候才该拆？"的现场答法**（把上面的"四个信号"落到真实经历上）：

> 「**我刚才说的四个信号，在我另一个项目上真的都出现了**——
> **那是一家 B2B 的供应链协同平台**（采购 + 供应商在线协同），**日订单量二十万级、注册企业三万多、后端二十来个人分了好几个小组**。
> **团队要独立发版、订单/库存/结算的扩缩容特征差好几倍、还要接外部供应商的异构系统**——**四条信号占齐了**，所以那边**就是 Spring Cloud Alibaba 那一套：Nacos + Gateway + OpenFeign + Sentinel + Seata**。
> **同步解耦和削峰用 RabbitMQ**（下单异步通知、积分、对账），**商品和订单的多条件检索用 Elasticsearch**。
> **反过来看交通局：8 个人、8000 份合同/年、一套 Java 栈**——**同样的技术放过去就是纯负担。**」

> 🏆 **这一段的价值**：**同一个候选人、同一家公司，做过单体也做过微服务**——**说明"不用微服务"不是不会，是判断；"用微服务"也不是跟风，是场景需要。**
> **面试官最想确认的就是这个：你的技术选型后面有没有一条"规模 / 团队 / 一致性约束"的判断链。**
> 💡 **两边技术的分工要记牢**：**被问 MQ / ES / 微服务 / 分布式事务 → 往供应链平台（§12）引；被问政务 / 合同 / 数据隔离 / 定时任务 / 编号并发 → 往交通局引。**

#### 8.11 🎤 怎么在面试里收口（**把这一节浓缩成一段**）

> 「**我们这个系统是政务系统，它的技术重心和互联网系统不一样**——
> **不是拼高并发，而是拼"安全、隔离、可追溯、稳定"**。
> **安全上**要过等保、要保证电子签的法律效力；**隔离上**要保证 **20 个单位的数据不串**；**可追溯上**要有操作日志、逻辑删除、状态流水；**稳定上**要能滚动发布、能回滚、能容灾。
> **所以我做的每一块，背后都有一个"合规"或"可靠"的要求在推着**——**比如做多租户不是我想炫技，是等保要求数据隔离；做版本冻结不是我喜欢复杂，是审批必须和文件绑定。**」

> 🏆 **这段收口的价值**：它把**所有技术选择都归因回"政务场景的约束"**，**证明你理解的是"业务驱动的技术"，而不是"技术堆砌"。**
> **面试官最想听的，恰恰是这句话。**

#### 9.1 多线程与并发

**① 线程池 7 参数（最高频，必背）**

> 「**7 个参数**：**corePoolSize、maximumPoolSize、keepAliveTime、TimeUnit、workQueue、threadFactory、handler**。
> **执行顺序**：**核心线程没满 → 开核心线程；核心满了 → 任务进队列；队列满了 → 开非核心线程（到 max）；再满 → 走拒绝策略。**
> ⚠️ **这个顺序最容易记反**——**是"先入队、后扩容"，不是"先扩容"**，很多人答成"先开到 max 再排队"。」

**你项目里的落点**：

> 「我们**业务上大部分是同步调用，没自己开业务线程池**；**真正用到线程池的是三处**：**Tomcat 的请求线程池**（`maxThreads`）、**数据库连接池 HikariCP**、**XXL-Job 的执行线程池**。
> **压测时我调过 Tomcat 的 `maxThreads`（200 → 400）**——因为第一轮压测发现**线程不够、请求在排队**。」

**追问「拒绝策略选哪个」**：

> 「**四种**：`AbortPolicy`（默认，直接抛异常）、`CallerRunsPolicy`（**交给提交任务的线程自己跑**）、`DiscardPolicy`（静默丢）、`DiscardOldestPolicy`（丢最老的）。
> **我们用 `CallerRunsPolicy`**——**它不丢任务，而是把压力"背压"回调用方**，**调用方变慢，自然就限流了**。**代价是：** 如果调用方是主线程，**主线程会被拖住**。」

> 🎯 **"背压"这个词用对了很加分**：`CallerRunsPolicy` 的本质就是**用阻塞调用方来限流**。

**② `synchronized` vs `ReentrantLock`**

| | `synchronized` | `ReentrantLock` |
|---|---|---|
| 实现 | JVM 内置（monitor） | AQS + CAS |
| 释放 | **自动** | **必须手动 `unlock()`（放 `finally`）** |
| 可中断 | ✗ | ✓ `lockInterruptibly()` |
| 公平锁 | ✗ | ✓ 可选 |
| 条件变量 | 单个 wait/notify | **多个 `Condition`** |

> 「**项目里我用 `synchronized` 最多**——**单机、低并发场景够用**；**要超时、可中断、多条件排队才用 `ReentrantLock`**。」

**③ `volatile`**

> 「**两个作用**：**保证可见性**（一个线程改了别的线程立刻看到）、**禁止指令重排**；**但它不保证原子性**——**`i++` 用 `volatile` 修饰照样丢更新**。」

**④ CAS / AQS**

> - **CAS**：比较并交换，**硬件指令保证原子**、无锁。**三个坑**：**ABA**（用版本号解决）、**自旋开销**（自旋久了烧 CPU）、**只能保证一个变量**。
> - **AQS**：`ReentrantLock` / `CountDownLatch` / `Semaphore` 的底座——**一个 `volatile int state` + 一个 CLH 双向队列**，**抢不到锁就进队列 `park`**。

**⑤ `ConcurrentHashMap`（1.7 vs 1.8）**

> 「**1.7 是分段锁**（`Segment` 继承 `ReentrantLock`，锁一段）；**1.8 改成 `CAS + synchronized` 锁单个桶头节点**，**粒度更细、并发度更高**；**还引入了红黑树**——**链表长度 ≥ 8 且数组长度 ≥ 64 时转红黑树**，**避免查询退化成 O(n)**。」

#### 9.2 ThreadLocal（**几乎必问，且必追内存泄漏**）

> 「**`ThreadLocal` 本身不存值**——**值存在 `Thread` 内部的 `ThreadLocalMap` 里**，**key 是 `ThreadLocal` 的弱引用，value 是强引用**。
> **内存泄漏是这么来的**：`ThreadLocal` 对象被回收后，**key 变成 `null`，但 value 还被 `Thread` 强引用着**；**线程只要不结束（线程池的线程是复用的！），value 就回收不掉**——**这就是泄漏**。
> **唯一正解**：**用完在 `finally` 里 `remove()`**。」

**你项目里的落点**（★ 有真底）：

> 「**我们的鉴权框架（Sa-Token）就是用 ThreadLocal 存"当前登录用户"的**——**Controller / Service 里随时能拿到当前用户，靠的就是它**。
> **所以请求结束必须 `remove()`**，**否则 Tomcat 线程池复用线程时，下一个请求可能读到上一个请求的用户**——**这是安全问题，不只是内存问题。**」

**追问 ①「子线程里能拿到吗？」**

> 「**拿不到**——**ThreadLocal 是"线程私有"的**，**子线程是新线程，`ThreadLocalMap` 是空的**。
> **要传给子线程，用 `InheritableThreadLocal`**（**父线程创建子线程时会把值拷过去**）；**但线程池里的线程是提前建好的，`InheritableThreadLocal` 也失效**——**这种情况得用阿里的 `TransmittableThreadLocal`（TTL）**。」

**追问 ②「`@Async` 异步方法里呢？」**

> 「**同样拿不到**——**因为 `@Async` 丢到另一个线程池执行**。**所以异步方法里要用户信息，得在调用前把参数显式传进去**，**别指望 ThreadLocal 自己带过去。**」

> 🎯 **"ThreadLocal 在线程池 / `@Async` 下会失效"——能答出这两条，说明你不是只背了"会内存泄漏"这一句。**

#### 9.3 缓存（Redis）

**① 穿透 / 击穿 / 雪崩（三兄弟，必背）**

| 问题 | 是什么 | 怎么防 |
|---|---|---|
| **穿透** | 查**根本不存在**的数据 → 每次都打到 DB | **布隆过滤器**；或**缓存空值**（存个短 TTL 的 `null` 占位）|
| **击穿** | **某个热点 key 过期**的瞬间，大量请求同时打到 DB | **互斥锁**（只放一个请求去查库回填）；或**热点 key 不设过期** |
| **雪崩** | **大量 key 同时过期**，或 **Redis 整个挂了** | **过期时间加随机值**打散；**Redis 高可用（我们用了主从 + 哨兵）**；**本地缓存兜底**；**限流降级** |

> 🎯 **记法**：**穿透是"查一个不存在的洞"、击穿是"一根柱子断了"、雪崩是"整面墙塌了"。**

**你项目里的落点**：

> 「**我们缓存的是"字典、配置、权限、登录态"这类读多写少的数据**；**合同这类业务数据不缓存**——**因为一致性要求高，缓存反而容易出错**。
> **所以"三兄弟"在我们这儿风险不大**——**热点 key 很少**；**但 Redis 挂了影响很大**（登录态在里面），**所以上了主从 + 哨兵自动故障转移。**」

**② 缓存与 DB 一致性**

> 「**标准做法是 Cache-Aside**：**读 → 先查缓存，没有再查库并回填；写 → 先改库，再删缓存**（**不更新缓存**）。
> **为什么"删"不是"更新"**：**更新缓存在并发下容易被旧值覆盖**（A 写库 → B 写库 → B 更新缓存 → A 更新缓存，**缓存里留了 A 的旧值**）；**删缓存则下次读自然回填，出错概率低**。
> **更稳的可以做延迟双删**，**或者订阅 binlog 异步删缓存**（canal）——**但我们这个场景，最终一致就够了。**」

**③ 持久化 RDB / AOF**

> 「**RDB 是快照**：**定时把内存整个 dump 成二进制文件**，**恢复快、文件小**，**但两次快照之间宕机会丢数据**；
> **AOF 是日志**：**每条写命令追加**，**丢得少**（`everysec` 最多丢 1 秒），**但文件大、恢复慢**。
> **生产一般两个都开**：**RDB 做冷备，AOF 保数据不丢**。
> **不过我们 Redis 存的是登录态和缓存**——**丢了用户重新登录就行**，**所以持久化对我们是"锦上添花"，不是"命根子"。**」

> 🏆 **最后那句"我们的 Redis 丢了影响可控"是加分项**——**因为你分得清"哪些数据丢了是灾难、哪些丢了能重建"**。**要是合同数据放 Redis，那就必须死保持久化。**

**④ 淘汰策略**

> 「**8 种**，常用的是 `noeviction`（不淘汰、写报错）、**`allkeys-lru`**（**所有 key 按最近最少使用淘汰**）、`volatile-lru`（**只淘汰设了过期时间的**）。
> **选哪种取决于"内存满了宁可报错、还是宁可丢数据"**——**我们缓存丢了能重建，所以 LRU 丢旧的就行。**」

**⑤ 大 key / 热 key**

> 「**大 key**（一个 key 几百 KB 到几 MB，比如把整个列表塞一个 key）**会阻塞 Redis**——**Redis 单线程执行命令，操作大 key 期间其他命令全排队**。**解法是拆**：**大 value 拆成多个小 key**。
> **热 key**（单个 key 被高频访问，打满一个节点）**解法是"复制多份打散"**——**同一 key 加随机后缀拆成 N 份，分摊到不同节点**。
> **我们项目没有大 key 问题**——**因为大文件走对象存储，Redis 里只有小对象和字符串。**」

#### 9.4 消息与异步（本项目用 Spring 事件 · MQ 是必考八股）

> ⚠️ **先说清楚**：**交通局这个单体项目没用 MQ**——起草 → 审批用的是**应用内 Spring 事件**（见 §4.5）。
> **但 MQ 是 Java 后端的必考池**，所以下面是 **MQ 的标准八股**：**被问到就答原理**。
> **被问"你项目里 MQ 怎么用的"**：**直接往 §12 的供应链平台引**（那边才是 MQ 的主场）；**如果面试官问的就是交通局这个项目，就答"我们同 JVM 内用事件解耦，跨服务才会换 MQ"。**

**① 消息怎么保证不丢（★ 三段式，必背）**

> 「**消息从生产到消费过三关，每关都可能丢**：
> **一、生产者 → Broker**：**开生产者确认**（`publisher-confirm` 确认到 Exchange、`publisher-return` 确认到 Queue），**没确认就重发**；
> **二、Broker 内部**：**队列和消息都持久化**（durable + `deliveryMode=2`），**Broker 重启消息还在**；
> **三、Broker → 消费者**：**关自动 ack、改手动 ack**——**业务处理成功了才 ack，失败就 nack 让它重投**。
> **一句话：生产者确认 + 持久化 + 手动 ack，三段都做，消息才不丢。**」

**② 消息重复消费怎么办**（衔接 §7.6）

> 「**手动 ack 必然带来"至少一次"语义**——**网络抖动时消息会重投**。**所以消费端必须做幂等**：**用业务唯一键判重**（如"合同 ID + 操作类型"），**或用去重表 / Redis `SETNX` 挡掉重复**。
> **不能指望"消息只来一次"**——**AMQP 保证的是"至少一次"（at-least-once），不是"恰好一次"。**」

**③ 死信队列 + 延迟队列（追问点）**

> 「**死信（DLX）**是**消息被拒绝、或过期、或队列满了之后，转去的一个"兜底队列"**——**我们用它收"重试次数超限"的消息**：**进死信就发告警、人工介入**，**而不是无限重试把系统拖死**。
> **延迟队列**：**RabbitMQ 没有原生延迟队列，一般用"TTL + 死信"组合实现**（消息设 TTL，到期变死信，投到真正的消费队列）——**比如"审批超时 24 小时自动提醒"就是这个套路。**」

**④ 顺序消息**

> 「**RabbitMQ 不保证全局顺序**；**要保序就得"单队列 + 单消费者"，但吞吐就上不去**。
> **我们的做法是"不需要全局有序"**——**只有同一份合同的操作才需要有序**，**那就按"合同 ID"哈希到同一个队列**，**保证同一份合同的消息进同一队列、被同一个消费者顺序处理。**」

**⑤ 为什么用 MQ / 为什么不用 Kafka**（与 §4.5、§8.10 呼应）

> 「**MQ 的价值是解耦、削峰、异步**；**选 RabbitMQ 不选 Kafka**——**量级用不上 Kafka 的吞吐**，**要的是可靠投递（确认机制 + 镜像队列）**，**Kafka 更适合日志、大数据流。**」

#### 9.5 事务

**① `@Transactional` 失效的 6 种场景（★ 超高频，必背）**

| # | 失效场景 | 为什么 | 怎么解 |
|---|---|---|---|
| 1 | **方法不是 `public`** | 代理拦不住非 public 方法 | 改成 public |
| 2 | **同类内部方法调用**（`this.xxx()`） | **不走代理，直接调本体** | **注入自己 / `AopContext.currentProxy()`** |
| 3 | **异常被自己 try-catch 吞了** | **没异常抛出 → 不回滚** | **catch 里重新 `throw`，或手动 `setRollbackOnly()`** |
| 4 | **抛的是受检异常** | **默认只回滚 `RuntimeException` 和 `Error`** | **`@Transactional(rollbackFor = Exception.class)`** |
| 5 | **方法在子线程 / 被 `@Async` 调用** | **事务和 ThreadLocal 一样，绑在当前线程上** | 别在子线程里指望主线程的事务 |
| 6 | **多数据源没指定事务管理器** | 事务管理器不知道管哪个库 | 指定 `transactionManager` |

> 🎯 **第 2 条（同类内部调用失效）和第 4 条（受检异常不回滚）是最高频的两个**——**一定要能说清"为什么"**：**核心是 Spring AOP 是"代理"机制，不走代理就没有事务。**

**② 传播行为（重点记两个）**

> 「**最常用的是 `REQUIRED`（默认）**——**有事务就加入、没有就新建**；
> **另一个重点是 `REQUIRES_NEW`**——**不管外面有没有事务，都开一个全新事务**，**而且外层回滚不影响它**。
> **典型场景**：**"主流程失败了要回滚，但操作日志必须留下"——日志那个方法就用 `REQUIRES_NEW`。**」

**③ 隔离级别 + MVCC**

> 「**MySQL 默认 `REPEATABLE READ`（可重复读）**，**靠 MVCC 实现**——**每行有隐藏的事务版本号，读的时候按版本号找到"我能看见的那个快照"**，**所以读写不互相阻塞**。
> **MVCC 解决的是"读不加锁"**，**但解决不了写写冲突**——**写还是要靠行锁。**」

**④ ★ 本地事务 + 消息/事件的一致性（**这条直接接你的项目，最值钱**）**

> 「**我们起草提交后要触发审批**——**这里有个经典问题：数据库提交和"发通知"没法在同一个事务里。**
> **先提交库、再发事件**：**库成功但事件发失败 → 审批收不到，合同卡住**；
> **先发事件、再提交库**：**事件发了库回滚 → 审批收到一份不存在的合同**。
> **这就是"本地事务和消息的最终一致"问题。**
>
> **我们单体的做法是**：用 **Spring 的 `@TransactionalEventListener`（`AFTER_COMMIT` 阶段）**——**事务提交成功后才触发事件，事务回滚事件根本不发**，**从机制上就避免了"发了不该发的"**。
> **换成 MQ 的话**，常见三种解法：
> **一、本地消息表**——**把"要发消息"这件事和业务数据放在同一个本地事务里写进一张表**，**再由定时任务扫表把消息发出去**，**发成功才标记完成**；
> **二、事务消息**——**RocketMQ 原生支持**（先发半消息、业务提交后再 commit）；
> **三、接受最终一致**——**消费端做幂等 + 生产者重试**，**不追求强一致**。
> **我们如果上了 MQ，会用本地消息表 + 消费端幂等**——**因为 RabbitMQ 没有事务消息，本地消息表最稳。**」

> 🏆 **这段是本节的"核弹"**：**它把"事务"和"消息"两题串成了一道真实场景题**——**面试官问"你的消息/事件怎么和数据库保持一致"，能答出"`AFTER_COMMIT` 保证提交后才发事件 / 本地消息表 + 定时补偿 + 消费端幂等"的，直接越级。**
> ⚠️ **诚实提醒**：**如果你们其实是"先提交库、再发事件、失败就记日志人工处理"，那就照实说**——**说简单方案 + 承认它的不足（会漏发、要人工）也是加分**，**别硬套本地消息表，否则被追问"表怎么设计的""扫表怎么防重复发"会当场露馅。**

**⑤ ★★ 分布式事务（**面试官"强行问"时怎么答**）**

> 你项目是单体，**本来可以绕开这道题**——**但有些面试官会硬问："你们没用到，那你总该懂吧？"**
> **这时不能只回一句"我们单体没有"**（那会被判成不会），**要证明你"用不上，但懂"**。

**第一步：先表态，再展开**（★ **顺序很重要**）

> 「**我们项目是单体，确实没有跨服务事务**——**所以我先说清"分布式事务要解决什么问题"，再说"我们为什么不用碰它"。**
> **它要解决的是**：**一个操作要跨两个数据源 / 两个服务，必须"全成功或全失败"，但一个本地事务包不住它们**。
> **典型场景就是"订单服务扣库存 + 账户服务扣余额"**——**扣库存成功了、扣余额失败了，怎么把库存加回去？**」

**第二步：把主流方案摆出来（★ 讲取舍，不是背名词）**

| 方案 | 一致性 | 原理一句话 | 代价 / 坑 |
|---|---|---|---|
| **2PC / 3PC** | **强一致** | 引入**协调者**，先 prepare 再 commit | **同步阻塞**、**协调者单点**、**commit 阶段可能部分失败** |
| **TCC** | **准强 / 最终一致** | **Try 预留 → Confirm 确认 → Cancel 取消**，**业务自己写三段** | **侵入大**，要处理**空回滚 / 幂等 / 悬挂** |
| **Saga** | **最终一致** | **长事务拆成一串本地事务**，**失败就反向补偿** | **补偿要幂等**、**无隔离性**、**中间状态对外可见** |
| ★ **本地消息表** | **最终一致** | **业务 + "待发消息"写在同一个本地事务**，**定时任务扫表补发** | **靠定时任务兜底**、**有延迟** |
| **事务消息** | **最终一致** | **先发半消息，业务提交后再 commit**（RocketMQ）| **依赖特定 MQ** |
| **最大努力通知** | **不保证** | **反复通知 + 对账**，尽力而为 | **不保证成功** |

**第三步：TCC 的三个坑（★ 能答出来就是"越级"）**

> 「**TCC 最容易被追问"有什么坑"，标准答案三个**：
> **一、空回滚**——**Try 还没执行（比如超时了），Cancel 先到了**，**Cancel 要能识别"根本没 Try 过"，直接返回成功**，**不能去回滚一个不存在的东西**；
> **二、幂等**——**Confirm 和 Cancel 都可能被重复调用**，**业务上必须做幂等**；
> **三、悬挂**——**Cancel 比 Try 先到（网络乱序），Cancel 执行完了 Try 才来**，**结果资源被预留了却永远没人 Confirm/Cancel**——**要靠"Cancel 时落一条记录，Try 时先检查"来防**。」

**第四步：说得出 Seata 再加分**

> 「**落地框架一般是阿里开源的 Seata**，**它有四种模式**：
> **AT 模式**——**无侵入：拦截 SQL 自动生成"前镜像 / 后镜像"存进 `undo_log`，回滚时拿镜像反向补偿**，**还有全局锁防脏写**，**最省事但性能一般**；
> **TCC / Saga**——**要自己写补偿逻辑**；**XA**——**本质就是 2PC**。
> **选哪种，看"能不能接受业务侵入"和"要不要强一致"。**」

**第五步：拐回自己项目（★ 必须收回来）**

> 「**回到我们项目**——**我们是单体，天然没有分布式事务**；**唯一的跨系统一致性问题，是"本地事务 + 事件/消息"**（见 §9.5④），**`AFTER_COMMIT` 监听器就够了**。
> **这也是我之前说"我们这个规模不该拆微服务"的原因之一**：**拆完之后，现在一个本地事务能搞定的东西，就得升级成 TCC 或 Saga，成本和风险全上去了。**」

> 🏆 **这一整段的杀伤力在于**：**你项目虽然用不上，但你把这条链讲透了**——**"什么问题 → 有哪些方案 → 各自代价 → 我为什么选这个"**。
> **面试官要的从来不是"你用过"，是"你懂"。**

**追问：「如果现在让你把项目改成微服务，事务怎么设计？」**（逼到底了）

> 「**先划边界，尽量让"一次业务操作"落在一个服务里**——**能不动分布式事务就别动**。
> **实在跨服务，按一致性要求选**：**合同状态流转这种强一致的，用 TCC 或 Seata AT**；**通知类的，用本地消息表 + 最终一致**。
> **而且我会先把"幂等"做在前面**——**补偿和重试都要求幂等**，**不然后面全是坑。**」

#### 9.6 幂等性（**和锁 / MQ / 事务都连着，必考**）

> **一句话定义**：**同一个操作，执行一次和执行多次，结果一样**。
> **它是"重复"的通用解药**——**MQ 重投、用户连点、网络重试、定时任务重试，最后都要靠幂等兜底。**

**① 什么时候会产生重复（先讲场景，别上来就背方案）**

> 「**四类来源**：
> **一、用户重复提交**——**网络慢，用户点了两次"提交"**；
> **二、MQ 重投**——**手动 ack 是"至少一次"语义，消费失败会重投**（见 §9.4②）；
> **三、接口重试**——**调用方超时重试，同一请求来了两次**；
> **四、定时任务重试**——**XXL-Job 失败重试，同一批数据跑了两遍**。」

**② 实现方案（★ 按"从粗到细"排）**

| 方案 | 原理 | 适用 | 代价 |
|---|---|---|---|
| ★ **数据库唯一索引** | `UNIQUE(业务键)`，重复插入直接被拒 | **新增类**操作 | **要捕获异常、转成友好提示** |
| ★ **去重表 / 令牌** | 每次请求带唯一 token，**处理前先 `INSERT` 或 `SETNX`**，**已存在就拒绝** | **提交类**操作 | **要防 token 重放**（用完即废）|
| **Redis `SETNX`** | 幂等 key 做 `SETNX`，**带 TTL 自动过期** | 任何操作 | **Redis 挂了会失效** |
| **状态机（带条件更新）** | `UPDATE ... SET status=2 WHERE id=? AND status=1`——**用"影响行数"判断**，**0 行说明已处理过** | **状态流转** | **要设计好状态** |
| **乐观锁（版本号）** | `UPDATE ... SET v=v+1 WHERE id=? AND v=?` | **更新类** | **要重试** |

> 🎯 **注意"分布式锁"不在这个表里**——**锁解决"同时只有一个"，幂等解决"重复到达"，两者配合、不能互相替代**（见 §7.6）。

**③ 你项目里的四处幂等（★ 全是真底）**

> 「**一、合同重复提交**——**前端提交带一个 token，后端用 Redis `SETNX` 挡掉第二次**；
> **二、MQ 消费**——**按"合同 ID + 操作类型"判重**，**同一份合同的同一操作只处理一次**；
> **三、定时任务同步**——**按"信用代码 + 中标项目编号"判重**，**已存在就跳过**（见 §4.4 补丁③）；
> **四、兜底**——**`contract_draft` 上有 `UNIQUE(CONTRACT_CODE, TENANT_ID)`**，**真重号了数据库直接拒绝**，**我捕获异常重新取号**（见 §7.2）。」

> 🏆 **"每个重复来源配一个幂等手段 + 最后数据库兜底"**——**这个结构比背几个方案名字强得多。**

**④ 追问防线**

| 追问 | 怎么答 |
|---|---|
| **幂等和分布式锁什么区别？** | ★ **锁防"同时"、幂等防"重复"**；**用户连点是先后到达，锁挡不住，必须靠幂等**（§7.6）|
| **幂等 key 用什么？** | ★ **业务唯一键**——**"合同 ID + 操作类型"这种**；**别用请求 ID**（**重试的请求 ID 会变，起不到判重作用**）|
| **去重表会不会越来越大？** | 「**用 Redis 带 TTL 就不用管**；**用数据库表就加个定期清理任务**，**或者只保留最近 N 天 / 状态未完成的**」|
| **有了唯一索引，还需要幂等吗？** | ★「**需要，分工不同**——**唯一索引只能防"重复插入"，防不了"重复更新"和"状态被重复推进"**；**而且它一冲突就抛异常，是"事后补救"，不如前面先挡一道优雅。**」|
| **幂等做在前面有什么好处？** | ★「**因为重试和补偿都要求幂等**——**MQ 重投、TCC 的 Confirm/Cancel、Saga 的补偿，全都建立在"重复执行也没事"上**。**幂等是这些方案的地基。**」|

> 🎤 **幂等这题的答法心法**：**先讲"重复从哪来"，再讲"每种重复配什么手段"，最后"数据库唯一索引兜底"**。
> **能说清"锁和幂等分工不同"的人，已经超过大多数候选人；能再补一句"幂等是补偿/重试的地基"的，直接越级。**

#### 12.3 我负责什么（★ 主动划边界）

> 「我主要负责**订单交易组里的采购订单服务**：订单创建、状态流转、取消、对账。
> 另外，**平台早期的 MQ 接入规范是我牵头定的**——**队列命名、消息格式、幂等、死信处理**，后面各个服务都按这套规范接。
> **检索这块**，商品和订单的 **ES 索引设计、同步链路**是我做的。
> **不归我的是**：**供应商准入的风控审核**（风控组做的）、**财务对账的清算规则**（财务组做的）。」

#### 12.4 三个亮点（被追问时的落点）

**亮点 1 · 订单异步链路（RabbitMQ 的四个真实用法）**

> 「订单服务用 MQ 的地方有四个，都是真实场景：
> **① 下单成功后异步通知供应商**——下单接口**只写库 + 发一条消息就返回**，供应商的短信 / 站内信、ERP 同步都走异步消费，**下单接口 RT 从 300ms 降到 80ms**；
> **② 订单超时未确认自动取消**——用**延迟队列**（`TTL + 死信`），下单时发一条 **30 分钟**的延迟消息，到期还没确认就自动取消、释放库存；
> **③ 削峰**——月底对账期订单量大，**消息先堆在队列里**，订单服务按自己节奏消费；
> **④ 解耦**——订单状态一变就发一条**订单状态变更消息**，**积分、报表、通知**这些下游各自订阅，**订单服务不用挨个去调**。」

**亮点 2 · 商品 / 订单检索（Elasticsearch）**

> 「商品检索一开始是 MySQL 的 `LIKE '%关键词%'`，**几十万商品之后直接把库拖垮**。我换成了 **Elasticsearch**：
> **商品名、类目、标签、规格建倒排索引**，中文用 **IK 分词器**，支持**多字段匹配 + 高亮 + 类目聚合**；
> **数据同步走"业务双写 + MQ 最终一致"**——商品在 MySQL 改完**发一条消息**，有一个消费者**专门写 ES**，**既保证最终一致、又不拖慢主链路**。」

**亮点 3 · 跨服务事务（Seata）**

> 「下单要**扣库存（库存服务）+ 建订单（订单服务）+ 核销优惠券（营销服务）**，跨了三个服务，**本地事务包不住**。
> 我们用 **Seata 的 AT 模式**：**每个服务自动生成"前镜像 / 后镜像"存 `undo_log`**，**全局提交时统一提交、失败时用 `undo_log` 反向补偿**，**还有全局锁防脏写**。
> **但我们也划了线**：**能用本地事务解决的，绝不跨服务**；**确实跨服务的强一致（下单扣库存）才用 Seata AT**；**通知类的一律最终一致 + 幂等**。」

#### 12.5 模拟面试题

##### 12.5.1 RabbitMQ（这个项目的重头戏）

| 追问 | 怎么答 |
|---|---|
| **为什么要用 MQ？** | 「**解耦、异步、削峰**三个词，落到项目上：**下单后通知供应商**用异步（RT 300→80ms）、**状态变更**用解耦（下游各自订阅）、**月底对账**用削峰（消息先堆队列）。」|
| **怎么保证消息不丢？** | ★ **三段式**：**① 生产者确认**（`publisher-confirm` 到 Exchange、`publisher-return` 到 Queue，没确认就重发）；**② Broker 持久化**（队列 durable + 消息 `deliveryMode=2`，重启还在）；**③ 消费者手动 ack**（业务成功才 ack，失败就 nack 重投）。|
| **消息重复消费怎么办？** | 「**手动 ack 就是"至少一次"语义，重复不可避免**。**消费端必须幂等**：**用业务唯一键**（比如"订单号 + 操作类型"）**做 Redis `SETNX` 或去重表**，**重复的直接丢**。」|
| **死信队列怎么用？** | ★ 「**消息被拒绝 / 过期 / 队列满 → 进死信队列（DLX）**。**我们的用法有两个**：**一是"重试超限"的兜底**——消费失败重试 N 次后进死信，**发告警人工介入，别无限重试把系统拖死**；**二是拿它实现延迟队列**——**消息设 TTL，到期变死信，投到真正的消费队列**。」|
| **订单超时 30 分钟自动取消怎么做？** | ★ 「**用"TTL + 死信"做延迟队列**：下单时往**一个没有消费者、只设 TTL 的队列**发消息，**30 分钟后消息过期变死信，转发到真正的取消队列**，**消费者拿到就取消订单**。<br>**追问「为什么不用定时任务扫表」**：**扫表要么扫得慢、要么不准**（一分钟扫一次，最长延迟一分钟）；**延迟队列是精确到秒的**。**要更灵活可以上 `rabbitmq_delayed_message_exchange` 插件，或者用 RocketMQ 的原生延迟消息。**」|
| **怎么保证消息顺序？** | 「**RabbitMQ 不保证全局顺序**。**我们只有"同一订单的状态变更"需要有序**——所以**按"订单号"哈希到同一个队列**，**同一个订单的消息进同一队列、被同一个消费者顺序消费**。**代价是热门订单会热点，所以队列数要开够。**」|
| **消息积压了几百万条怎么办？** | 「**先查原因**：是**消费逻辑变慢**（比如下游接口超时）还是**生产者暴增**。<br>**应急**：**① 加消费者实例**（前提队列数够、能并行消费）；**② 调大 `prefetch`、改批量消费**；**③ 实在不行，临时起线程池把消息快速转存到别的队列 / 落库，先保证不丢，再慢慢处理**。<br>**根因是消费能力不足，长期靠扩容 + 优化消费逻辑。**」|
| **用 MQ 怎么和数据库保持最终一致？** | 「**下单在一个本地事务里**：**写订单库 + 写一条"待发消息"到本地消息表**，**提交后由定时任务（或 `AFTER_COMMIT`）把消息发到 MQ**，**发成功才标记完成**；**消费端幂等**。**这就是本地消息表方案**——**代价是有延迟、要靠定时任务兜底**。」|
| **为什么用 RabbitMQ 不用 Kafka？** | 「**我们的量级（日订单 20 万）用不上 Kafka 的吞吐**；**要的是"不丢 + 能重试 + 延迟队列"的灵活路由**，**RabbitMQ 更直接**。**Kafka 更适合日志、埋点、大数据流。**」|

##### 12.5.2 Elasticsearch

| 追问 | 怎么答 |
|---|---|
| **为什么用 ES 不用 MySQL？** | 「**MySQL 的 `LIKE '%关键词%'` 用不上索引、只能全表扫**，几十万商品就扛不住；**ES 是倒排索引，先切词再直接定位文档，天生为"全文检索"设计**。**而且 ES 还能一次拿到高亮、聚合、相关性排序。**」|
| **倒排索引是什么？** | 「**正排是"文档 → 有哪些词"，倒排是"词 → 出现在哪些文档"**。**ES 给每个词维护一个 posting list（文档 ID 列表）**，查询时**直接按词拿到文档集合、再做交并**，**不用扫全表**。**代价是写入要分词、建索引，所以 ES 写比读重。**」|
| **中文怎么分词？** | 「**默认分词器按单字切，效果差**；**我们用 IK 分词器**（`ik_smart` 粗粒度 / `ik_max_word` 细粒度），**还自定义了行业词库**（比如"供应链""询报价"要当一个词）。」|
| **分片和副本是怎么回事？** | 「**分片（Shard）是水平拆分的单元**，一个索引拆成多个分片、**分散到不同节点**，**查询和写入都能并行**；**副本（Replica）是分片的拷贝**，**一是高可用**（主分片挂了副本顶上）、**二是分担读**。**注意：主分片数一旦定了不能改**（改了数据就错位），**只能重建索引**。」|
| **ES 和 MySQL 怎么同步？** | ★ 「**三种做法**：**① 双写**（写完库再写 ES，简单但**两个写可能不一致**）；**② 异步双写 / 发 MQ**（写完库发消息、消费者写 ES，**我们用的这个，最终一致**）；**③ 订阅 binlog**（canal，**对业务零侵入**）。**核心都是"以 MySQL 为准、ES 是派生数据，允许短暂不一致、靠重试补齐"。**」|
| **深分页（比如第 10000 页）怎么处理？** | ★ 「`from + size` 深分页要**每个分片都取 `from+size` 条再归并**，**页数越深、内存和耗时越爆炸**。**解法**：**① `scroll`**（一次查一批、适合导出，但**是快照、不适合实时**）；**② `search_after`**（**带上页最后一条的排序值往下翻，适合实时滚动**）；**③ 干脆限制最多翻到第 N 页，或引导用户加筛选条件缩小范围**。」|
| **`match` 和 `term` 有什么区别？** | ★ 「**`match` 会先分词再匹配**（查"供应链平台"会切成几个词）；**`term` 不分词、精确匹配**。**而且坑在这**：**`text` 字段被分词后 `term` 查不到，得用它的 `keyword` 子字段**——**这点很多人踩过。**」|
| **ES 是强一致的吗？** | 「**不是，ES 是近实时（NRT）**——**写入后默认 1 秒才能被搜到**（`refresh_interval`）。**所以我们不拿 ES 当"唯一的真相源"**，**主数据在 MySQL，ES 只做检索**，**能接受这 1 秒的延迟**。」|

##### 12.5.3 微服务 / Spring Cloud Alibaba

| 追问 | 怎么答 |
|---|---|
| **为什么这个项目拆微服务，交通局那个不拆？** | ★ 「**两个项目约束完全不同**：**供应链平台是 20 人团队、多业务线、日订单 20 万，多个小组要独立发版、独立扩容**——**微服务的收益是实打实的**；**交通局是 8 人、政务单体、8000 合同/年，拆了纯亏**。**架构要匹配团队规模和业务量，不是越新越好。**」|
| **Nacos 干什么？** | 「**两件事：服务注册发现 + 配置中心**。**注册**：服务启动把 IP / 端口报到 Nacos，**调用方按服务名拉实例列表**（**临时实例 + 心跳，挂了自动摘除**）；**配置**：**配置放 Nacos，改完动态推送到服务、不用重启**（`@RefreshScope`）。」|
| **Nacos 和 Eureka / ZooKeeper 什么区别？** | 「**Nacos 一个顶两个**（注册 + 配置）；**Eureka 只做注册、2.x 已闭源**；**ZK 是 CP**（一致性优先，**选举期间不可用**），**Nacos 注册默认 AP**（**可用性优先，适合服务发现**）、**配置侧可以 CP**。**所以国内现在基本都用 Nacos。**」|
| **网关 Gateway 做什么？** | 「**统一入口、路由转发、鉴权、限流、跨域**。**前端只认网关**，网关按路径把请求路由到不同微服务；**鉴权在网关统一做**（校验 token，通过后把用户信息放 header 往下传）；**限流也能在网关层做第一道**。」|
| **服务之间怎么调用？** | 「**OpenFeign**——**声明式 HTTP 客户端**，**写个接口加注解，就能像调本地方法一样调远程服务**。**但它默认不带超时 / 重试**，**我们配了超时、连上 Sentinel 做熔断**。**坑：Feign 默认读超时很短；`GET` 想传对象得用 `@SpringQueryMap`。**」|
| **Sentinel 做什么？限流 / 熔断 / 降级什么区别？** | ★ 「**Sentinel 做流量防护**。<br>**限流**：**控制入口流量**，超了就拒绝（**QPS / 线程数 / 热点参数**规则）；<br>**熔断**：**下游持续失败时，直接快速失败、不再调下游**（**避免被拖死**），**过一段时间半开探测**；<br>**降级**：**出问题时走兜底逻辑**（返回默认值 / 缓存值）。<br>**一句话：限流保护自己、熔断保护调用方、降级给用户兜底。**」|
| **什么是服务雪崩？怎么防？** | ★ 「**A 调 B、B 调 C，C 挂了，请求全堵在 A 上、线程被占满，A 也跟着挂**，**雪崩式扩散**。<br>**防**：**① 熔断**（连调失败就断开，不再放大）、**② 隔离**（线程池 / 信号量隔离，**别让一个慢依赖占满所有线程**）、**③ 降级**（兜底返回）、**④ 超时**（**必须有，否则慢调用会拖垮调用方**）。」|
| **链路追踪怎么做的？** | 「**一个请求跨了五六个服务，出问题得知道卡在哪**。我们给每个请求一个**全局 traceId**、**经过每个服务都带在 header 里透传**，**每个服务的日志都打上这个 traceId**；**用 SkyWalking 把这些串成一条调用链**，**能看到每段耗时**。**排查线上问题靠它。**」|
| **微服务的配置怎么管？** | 「**全放 Nacos**——**公共配置抽出来、各服务只配自己的**；**改配置不用重启、动态刷新**；**还可以按环境（dev / test / prod）和命名空间隔离**。**好处是 20 个人的团队改配置不用挨个发版。**」|

##### 12.5.4 分布式事务（Seata）

| 追问 | 怎么答 |
|---|---|
| **你们这个项目的分布式事务怎么处理的？** | ★ 「**下单要跨三个服务**（订单 + 库存 + 营销），**用 Seata 的 AT 模式**；**但我们的原则是"能不跨就不跨"**——**能塞进一个服务本地事务的，绝不拆出去**；**必须跨的（下单扣库存）才上 Seata**；**通知类的一律最终一致 + 幂等**。」|
| **Seata AT 模式的原理？** | ★ 「**无侵入**：**它拦截业务 SQL，自动把"修改前 / 修改后"的镜像存到 `undo_log` 表**；**全局事务提交时，各个分支一起提交；某一分支失败，就按 `undo_log` 里的"前镜像"把数据反向补回去**。<br>**关键点**：**① 一阶段就本地提交了（不像 2PC 要锁到二阶段），性能好**；**② 靠全局锁防脏写**（**别的全局事务想改同一行，得等**）；**③ 默认是"读未提交"级别，要更强得加 `@GlobalLock`。**」|
| **AT 和 TCC 怎么选？** | 「**AT 无侵入、适合大多数场景**，**但依赖数据库、且有全局锁**；**TCC 要自己写 Try / Confirm / Cancel 三段、侵入大，但没有全局锁、性能更好、适合"资金类"这种要精确控制的**。**我们优先 AT，TCC 留给对性能和数据控制要求极高的场景。**」|
| **TCC 的三个坑？** | ★ 「**一、空回滚**（Try 没执行、Cancel 先到了，**Cancel 要识别"根本没 Try 过"直接返回)**；**二、幂等**（**Confirm / Cancel 都可能被重复调**）；**三、悬挂**（**Cancel 比 Try 先到，之后 Try 才来，资源被预留却永远没人处理**，**靠 Cancel 落记录、Try 先检查来防**）。」|
| **Seata 有没有单点 / 性能问题？** | 「**Seata Server 是单点，生产要集群 + 高可用**；**AT 模式在"热点行"上全局锁会打架、并发上不去**——所以我们**尽量减少跨服务写、缩短全局事务范围**，**能用消息最终一致的就不上 Seata**。」|

#### 12.6 两个项目怎么共存（收口话术）

> 「我这两段经历正好是**两种典型的项目形态**：
> **供应链平台是微服务**——**团队大、业务线多、量也上来了，所以要拆服务、要 MQ、要 ES、要 Seata**；
> **交通局合同系统是单体**——**团队小、是政务内网、量不大，拆微服务纯亏，所以用模块化单体 + 事件解耦**。
> **我不会说哪个更先进**——**我的判断是"架构要匹配团队规模、业务量和部署约束"**，**同一个我，在这两个项目里做的技术选择是不一样的，但背后的取舍逻辑是一样的。**」

> 🏆 **这段收口的杀伤力**：**它证明你不是"会背微服务八股"，而是"知道什么时候该用、什么时候不该用"**——**这正是高级和初级的分水岭。**
> ⚠️ **注意别自相矛盾**：交通局那边你说"我们不该上微服务"，这边供应链平台又说"我们上了微服务"——**一点不冲突**，**因为两者的团队规模和业务量天差地别**。**被面试官点出来，就这么答。**
> 🔗 **反向引用**：如果面试官是在追问交通局"为什么不用微服务"时把你逼到这一步，**对应的完整答法在 §8.10 的"★ 对照：同一家公司，另一个项目我们确实上了微服务 / MQ / ES"**——两处讲的是同一件事，口径要一致。
