# 第零部分 · 权限是什么

> **为什么放在最前面**：第四部分的「铁律 3」要讲 `v-hasPermi`，第三部分链路②要讲 `@SaCheckPermission`，它们都默认你已经知道"权限"是什么。这一节把这块地基补上。
>
> 如果你已经懂 RBAC，可以直接跳到 **0.3**（那里有个很多人会搞错的点）。

## 0.1 第一件事：认证 ≠ 权限

这两个词中文都带"权"，但完全是两件事，混在一起后面全乱。

| | **认证** Authentication | **授权** Authorization |
|---|---|---|
| 回答的问题 | **你是谁？** | **你能干什么？** |
| 生活类比 | 进大楼刷工牌，证明你是员工 | 财务室的门刷不开，因为你没这个权限 |
| 本项目实现 | 登录 → Sa-Token 发 token → 存 Redis | 权限码 + `@SaCheckPermission` |
| 失败时的报错 | `401 认证失败，无法访问系统资源` | `403 没有访问权限，请联系管理员授权` |
| 代码在哪 | `SysLoginService.login()` | `SysPermissionService` + `SaInterfaceImpl` |

**顺序是先认证后授权**：先刷工牌（拿到 token），每一次请求再检查你能进哪个房间。没有 token 时，系统连"你是谁"都不知道，根本谈不上"你能干什么"。

## 0.2 权限分三层，很多人只知道第一层

还是用办公楼打比方：

| 层 | 类比 | 本项目怎么实现的 | 涉及技术 |
|---|---|---|---|
| **① 功能权限** | 哪些房间你能进 | `sys_menu.perms` + `@SaCheckPermission` | Sa-Token |
| **② 数据权限** | 进了同一个房间，**你能开哪个文件柜** | `sys_role.DATA_SCOPE` + `@DataPermission` | MyBatis-Plus 插件（SQL 重写） |
| **③ 租户隔离** | 你属于**哪家公司** | 几乎所有表都有 `tenant_id` 列 | RuoYi 多租户 |

三层是**叠加**的：一个请求要先过租户隔离（只能碰本公司的数据），再过数据权限（本公司里只能碰本部门的），最后才看功能权限（这个接口你准不准调）。

### ① 功能权限：给每个"动作"起一个名字

系统把所有能干的动作都起了一个字符串名字，叫**权限码**。这是从数据库里查出来的真实数据：

```
MENU_ID   MENU_NAME   PERMS                 MENU_TYPE
100       用户管理     system:user:list      C
101       角色管理     system:role:list      C
```

权限码的命名是 `模块:对象:动作` 三段式，比如 `system:user:export` 一眼能看出是"系统模块-用户-导出"。

**⭐ 关键设计：权限码存在 `sys_menu` 表里。**

第一次看到会觉得很怪——权限码为什么存在"菜单表"里？因为 RuoYi 用**一张表同时存三样东西**，靠 `MENU_TYPE` 区分：

| `MENU_TYPE` | 是什么 | 出现在侧边栏吗 | 有权限码吗 |
|---|---|---|---|
| `M` | 目录（文件夹，如「系统管理」） | 是（作为折叠项） | 一般没有 |
| `C` | 菜单（有真实页面，如「用户管理」） | 是 | 有（`system:user:list`） |
| `F` | **按钮**（没有页面，如「导出」按钮） | **否** | 有（`system:user:export`） |

**`F` 类型是理解这套设计的关键**：一个按钮不需要出现在侧边栏，但它需要一个权限码——所以给它建一行 `MENU_TYPE='F'` 的记录，只填 `perms`，不填页面路径。

这也解释了一个数字上的疑惑：本项目的 `sys_menu` 表有 **75 行**，但 `/getRouters` 返回的侧边栏只有 **25 个节点**——差的那些大部分就是 `F` 类型的按钮权限。

**权限码怎么流到前端、怎么被用起来**：

```
数据库 sys_menu.perms
      ↓ 登录后调 /getInfo，后端一次性全查出来
【"system:user:list", "system:user:export", ...】   ← 这一串就是 getInfo 的 permissions
      ↓ 存进前端 Vuex（store/modules/user.js）
      ↓ 页面上写 <el-button v-hasPermi="['system:user:export']">
      ↓ 指令去名单里查：有 → 按钮保留；没有 → 把按钮从 DOM 里删掉
```

### ② RBAC：为什么要"角色"这一层

如果直接给每个用户单独配权限，1000 个用户就要配 1000 次，而且没法复用。所以引入**角色**作为中间层：

```
用户 ──< 用户角色关联 >── 角色 ──< 角色菜单关联 >── 权限（菜单/按钮）
```

配一次"法务负责人能看法务相关的页面"，然后所有法务岗的人挂上这个角色就行。这套模型叫 **RBAC**（Role-Based Access Control，基于角色的访问控制），是业界最通用的权限设计，不是 RuoYi 独创——**面试问"权限系统怎么设计"，答的就是 RBAC**。

本项目真实的表关系（5 张表）：

```
sys_user ──< sys_user_role >── sys_role ──< sys_role_menu >── sys_menu
                                  │                              │
                           DATA_SCOPE                      perms（权限码）
                         （数据权限范围）                    （功能权限）
```

中间两张 `sys_user_role` / `sys_role_menu` 叫**关联表**，专门存"谁和谁绑上了"。为什么需要它们：因为用户和角色是**多对多**——一个人可以身兼数职，一个角色可以有很多人。多对多关系在关系型数据库里必须用第三张表来存。

从数据库里查出来的真实角色：

```
ROLE_ID                ROLE_NAME     ROLE_KEY           DATA_SCOPE
1                      超级管理员     admin              1（全部数据）
2                      普通角色       common             2（自定义）
1578234240876015618    档案管理员     archive_manager    NULL
1578280440983580673    法务负责人     legal_affairs      1（全部数据）
1578576519985754114    财务负责人     finace             1（全部数据）
...
```

### ③ 数据权限：不拦接口，而是**改 SQL**

功能权限是"拦请求"（这个接口不让你调）。数据权限完全不同——**接口让你调，但我要偷偷在你查询的 SQL 上加一句 `WHERE`**。

配置写在 `sys_role.DATA_SCOPE` 列上，取值定义在 `DataScopeType.java`：

```java
ALL("1", "", ""),                                          // 不过滤，全部数据
CUSTOM("2", " #{#deptName} IN ( #{@sdss.getRoleCustom( #user.roleId )} ) ", ""),
DEPT("3", " #{#deptName} = #{#user.deptId} ", ""),         // 只看本部门
DEPT_AND_CHILD("4", " #{#deptName} IN ( #{@sdss.getDeptAndChild( #user.deptId )} )", ""),
SELF("5", " #{#userName} = #{#user.userId} ", " 1 = 0 ");  // 只看自己
```

中间那串 `#{#deptName} = #{#user.deptId}` 是 **SpEL 表达式**（Spring 的表达式语言）。系统会在运行时把它算成一个真实条件，拼到 SQL 的 `WHERE` 后面。所以叫 **SQL 重写**。

举例：一个 `DATA_SCOPE=3`（本部门）的用户去查用户列表，他实际执行的 SQL 会从

```sql
SELECT * FROM sys_user WHERE del_flag = '0'
```

变成

```sql
SELECT * FROM sys_user WHERE del_flag = '0' AND dept_id = 101
```

**同一个接口、同一份代码，不同的人看到不同的数据**——这就是数据权限的效果。

> 📌 **这条正好能解释本项目里一个"两个接口长得一样"的疑惑**：
> `SysUserMapper.java` 里有两个方法 `selectPageUserList()` 和 `selectPageUserListWithP()`，**唯一的区别就是后者的方法头上多了 `@DataPermission(...)` 注解**——加了它，SQL 就会被重写；不加就不重写。
> 前端用户管理页面调的是**带 P 的那个**（`/system/user/listWithP`），所以它是本学习版里**唯一还在跑的业务数据权限实例**。

## 0.3 ⭐ 容易搞错的一点：RuoYi 的"超管"是用户表上的一个标志，**不是角色**

**这一节是为了纠正一个我自己讲错过的说法**，也是个高频误解：很多人以为"超管"是靠 `sys_role.role_key = 'admin'` 判断的。

**不是。** 判定代码在 `SysUser.java:237`：

```java
public boolean isAdmin() {
    return ("1").equalsIgnoreCase(this.systemAdmin) || ("1".equalsIgnoreCase(this.tenantAdmin));
}
```

它读的是 **`sys_user` 表自己的两个字段**，跟 `sys_role` 表**一点关系都没有**：

| 字段 | 含义 | 权限范围 |
|---|---|---|
| `SYSTEM_ADMIN = 1` | 系统超级管理员 | 跨**所有**租户 |
| `TENANT_ADMIN = 1` | 租户管理员 | 只在**本租户**内最大 |

从数据库查出来的真实数据：

```
USER_ID   USER_NAME    NICK_NAME     SYSTEM_ADMIN   TENANT_ID
1         zxcmAdmin    超级管理员     1              00000000
```

**注意 `zxcmAdmin` 挂的角色**是「系统管理员」和「档案管理员」——它**并没有挂名叫"超级管理员"的那个角色**（`ROLE_ID=1`），但它百分之百是超管，因为 `SYSTEM_ADMIN=1`。

这个坑很实战：**你在角色管理页面里改任何角色的权限，都动不了 `zxcmAdmin`**——因为它的权限压根不走角色。

### 超管的"特权通道"：`*:*:*` 和"短路"

`SysPermissionService.java:58`：

```java
public Set<String> getMenuPermission(SysUser user) {
    Set<String> perms = new HashSet<String>();
    if (user.isAdmin()) {
        perms.add("*:*:*");                                          // ← 超管走这里
    } else {
        perms.addAll(menuService.selectMenuPermsByUserId(...));       // ← 普通用户走这里，会查数据库
    }
    return perms;
}
```

两个词解释一下：

- **`*:*:*`**：`*` 是通配符，代表"全部"。所以 `["*:*:*"]` 等于"所有权限都有"。
- **"短路"**（short-circuit）：编程里的说法——条件一成立就**立刻返回，后面的代码不执行了**。像电路短路，电流不走后面那段。

**为什么这么设计**：超管反正什么都能干，每次登录去数据库查它那几百个权限码纯属浪费，直接返回通配符更省事。

**但程序员得记得把 `*:*:*` 也认成"通过"**——否则超管反而会被权限校验拦在外面。所以前端指令里专门留了一个分支（`hasPermi.js`）：

```js
const hasPermissions = permissions.some(permission =>
  "*:*:*" === permission || value.includes(permission))
//   ↑ 这个分支就是给超管留的
```

### ⚠️ 由此得出的一个实用结论

**用 `zxcmAdmin` 登录，`/getInfo` 返回的 `permissions` 永远是 `["*:*:*"]`，你永远看不到真实的权限码。**

所以如果你想亲手验证"权限码真的来自 `sys_menu` 表"这条链路（比如面试前想确认自己真懂了），**必须用一个普通账号**。

> 📌 **但本项目目前 `sys_user` 表里只有 1 个用户**（就是 `zxcmAdmin`）。要验证的话，得先在「系统管理 → 用户管理」里新建一个用户、给它分配一个角色（比如「普通角色」），再拿它登录对比。
> 这件事顺便还能验证 `v-hasPermi` 真的会删按钮——因为你新建的用户肯定没有全部权限。

## 0.4 第三层：租户（tenant）是什么

**问题背景**：一套系统要卖给多家公司用，A 公司的员工绝不能看到 B 公司的合同。

这个"公司"就叫**租户**（tenant）。解决办法是：**几乎所有业务表都加一列 `tenant_id`**，每次查询自动带上 `WHERE tenant_id = 你公司的号`。RuoYi 把这个条件做成了全局的 SQL 拦截，业务代码里不用手写。

本项目真实的租户数据：

```
tenantId      name
00000000      系统默认租户
```

`00000000` 是**系统内置的租户号**，全 0，代表"系统本身"。

### token 里的 `loginId` 拆解

登录成功后，JWT 里解出来的 `loginId` 长这样：

```
00000000 : sys_user:1
    ↑          ↑
 租户号      表名:用户id
```

**为什么 token 里要带租户号**：后端每收到一个请求都要知道"你是谁 **并且** 你属于哪家公司"。把租户号直接编在 token 里，就不用每次都去查库了。

> 💡 对比一下 `0.3` 那张表：`zxcmAdmin` 的 `TENANT_ID` 是 `00000000`，正好对上 token 里的前 8 位。

## 0.5 一图看懂：这些词分别属于哪一层哪套技术

| 你听到的词 | 属于哪层 | 存在哪 | 谁在读它 | 技术栈 |
|---|---|---|---|---|
| token / 会话 | 认证 | Redis（db5） | Sa-Token 拦截器 | **Sa-Token** |
| `perms` 权限码 | 功能权限 | `sys_menu.perms` | `@SaCheckPermission` / `v-hasPermi` | **RBAC + Sa-Token** |
| 角色 | 功能权限的组织方式 | `sys_role` + 两张关联表 | 登录时算权限 | **RBAC** |

| `tenant_id` | 租户隔离 | 几乎所有表都有这列 | 全局 SQL 拦截器 | **RuoYi 多租户** |
| `SYSTEM_ADMIN` | 超级权限开关 | `sys_user.SYSTEM_ADMIN` | `SysUser.isAdmin()` | **RuoYi 自研** |

# 第一部分 · 先补 7 个前端最小概念

## 1.1 一个 `.vue` 文件长什么样

Vue 的组件文件（`.vue`）是**一个文件装三块东西**：

```vue
<template>   ← 页面长什么样（HTML + 指令），相当于"视图"
</template>

<script>     ← 这块是 JavaScript，写逻辑。相当于"后端 Controller + Service"
export default {
  data() { return { ... } },      // 相当于成员变量
  methods: { ... },               // 相当于方法
}
</script>

<style>      ← 样式（颜色、间距）。跟后端无关，可以完全忽略
</style>
```

**和后端的对应关系**：一个 `.vue` 文件 ≈ 一个 Controller 类。`data` 是成员变量，`methods` 是方法，`template` 是"这个类对外输出什么"。

> 为什么能一个文件装三块？这是 Vue 的"单文件组件"（SFC）设计，需要 webpack 编译才能被浏览器认识（见 1.3）。

## 1.2 `import` / `export`：前端的 `package` 和 `class`

先看一段真实的（`zxcm-learn/zxcm-ui/src/utils/auth.js` 全文）：

```js
import Cookies from 'js-cookie'        // ← 引入第三方库

const TokenKey = 'Admin-Token'          // ← 相当于 private static final String

export function getToken() {            // ← export = 对外暴露
  return Cookies.get(TokenKey)
}

export function setToken(token) {
  return Cookies.set(TokenKey, token)
}
```

用的时候：

```js
import { getToken, setToken } from '@/utils/auth'   // ← 相当于 Java 的 import
```

**Java 对照表：**

| 前端 | 后端 | 说明 |
|---|---|---|
| `import X from 'y'` | `import com.foo.Y;` | 引入 |
| `export function f()` | `public static void f()` | 暴露给别人用 |
| `export default {...}` | 整个类作为默认导出 | 一个文件只能有一个 |
| `@/utils/auth` | `com.ruoyi.utils.Auth` | **`@` 是路径别名**，代表 `src/` 目录 |

> **`@` 是什么**：不是 npm 包，是 `vue.config.js` 里配置的别名，等价于"`src/` 目录"。所以 `@/utils/auth` 就是 `src/utils/auth.js`。`.js` 后缀可以省略。

## 1.3 `npm` 和 `webpack`：前端的 Maven 和编译器

这两件事几乎就是后端的翻版：

| 前端 | 后端 | 干什么 |
|---|---|---|
| `package.json` | `pom.xml` | 声明依赖 |
| `npm install` | `mvn dependency:resolve` | 下载依赖到 `node_modules/`（= `.m2/repository`） |
| `npm run dev` | `mvn spring-boot:run` | 启动 |
| `npm run build:prod` | `mvn package` | 打包 |
| `webpack` | `javac` + `mvn` | **编译** |

**webpack 具体干了什么**（这是理解前端的关键）：

1. 从**一个入口文件**开始 —— 本项目的入口是 `zxcm-ui/src/main.js`
2. 读这个文件里的每一行 `import`，递归地把所有被依赖的文件找出来
3. 把 `.vue` 的 `<template>`/`<script>`/`<style>` 三块**拆开分别编译**（`<style>` 变 CSS，`<script>` 走 Babel 转译，`<template>` 编译成渲染函数）
4. 全部打包成 `static/js/app.js` 等文件，浏览器加载

**所以"复制文件不需要顺序"**：顺序是 webpack 在编译时自己算的。这和后端 `mvn compile` 一次性编译整个 `src/main/java`，由编译器解析引用关系，是**完全一样的道理**。

> ⚠️ **由此推出一个重要结论**：`import` 的路径**必须在编译时就能解析**。哪怕你写的是"懒加载"（`() => import('@/views/xxx')`），webpack 也会去检查 `@/views/xxx` 存不存在，不存在就直接报 `module not found`，整个构建失败。
>
> 这就是为什么 M0 删掉后端业务模块后，前端也必须同步清理引用已删页面的代码。

## 1.4 `Promise` / `async` / `await`：前端的异步

前端所有网络请求都是**异步**的（不能在等待时卡住浏览器）。写法有两种，本项目的 `api/` 目录用的是第一种：

```js
// 写法 A：Promise + .then（本项目主流）
export function getInfo() {
  return request({ url: '/getInfo', method: 'get' })
}

// 调用方
getInfo().then(res => {
  // res 是后端返回的数据
})
```

```js
// 写法 B：async / await（本项目 permission.js 用这种）
async function f() {
  const res = await getInfo()   // await = 等它返回，再往下走
}
```

**Java 对照**：`.then(...)` 类似 `CompletableFuture.thenAccept(...)`；`await` 类似 `future.get()`（但不会阻塞线程）。

> **`Promise` 的 `.catch()` 是异常处理**，相当于 `try/catch`。本项目 `utils/request.js` 的响应拦截器会统一处理错误并弹提示，所以业务代码里经常只写 `.then()`。

## 1.5 `this` 和 Vue 的几个固定"格子"

Vue 组件里，`this` 就是**当前这个组件实例**。你在下面几个固定位置写东西，Vue 会自动处理：

| 位置 | 什么时候触发 | 相当于 |
|---|---|---|
| `data()` | 初始化变量 | 成员变量声明 |
| `computed` | 派生值，依赖变了自动重算，带缓存 | `getXxx()` |
| `methods` | 手写的方法 | 普通方法 |
| `created()` | 组件**被创建**后立刻执行一次 | `@PostConstruct` |
| `mounted()` | 组件**被挂到页面上**后执行一次 | 初始化回调 |
| `watch` | 监听某个变量变化 | 监听器 |

**看个真实的**（`zxcm-ui/src/views/login.vue:189`）：

```js
created() {
  this.getCode()                                    // 一进登录页就拉验证码
  this.getCookie()                                  // 读"记住密码"的 Cookie
  this.$store.dispatch('settings/getCompanyConfig') // 拉公司名（决定页面标题）
}
```

**`this.$store`、`this.$router`、`this.$modal` 是什么**：Vue 会把一些全局能力挂在 `this` 上（在 `main.js` 里注册的）。可以理解为**注入的 Bean**：

| `this.$xxx` | 相当于 |
|---|---|
| `this.$store` | 全局状态容器（见 1.6） |
| `this.$router` | 路由跳转器（`this.$router.push('/index')` = 跳转页面） |
| `this.$modal` | 弹窗工具（`this.$modal.msgError('xxx')` = 弹错误提示） |

## 1.6 Vuex：前端的"全局单例 Bean"

Vuex 是**前端的全局状态容器**。因为前端有很多组件，它们之间要共享数据（比如"当前登录用户是谁"），总不能每个组件都去请求一遍。Vuex 就是干这个的。

**四个概念，和后端对照：**

| Vuex | 后端类比 | 关键约束 |
|---|---|---|
| `state` | 单例 Bean 的字段 | **只读**，不要直接改 |
| `mutation` | 唯一的 setter | **必须同步**，通过 `commit('SET_XXX', v)` 调用 |
| `action` | Service 方法 | 可以异步（发请求），内部 `commit()` 调 mutation |
| `getter` | 带缓存的查询方法 | 派生数据，集中放在 `getters.js` |

**为什么非要这么绕？** 因为所有状态变更都必须经过 `mutation`，这样浏览器的 **Vue DevTools 插件**能记录每一步、能回放。如果只是为了共享变量，`window.xxx = {...}` 也能干——**Vuex 存在的全部理由就是"可追踪"**。

**本项目的 store 结构**（`zxcm-ui/src/store/index.js`）：

```
store/
├── index.js              ← 注册所有模块，导出 store
├── getters.js            ← 所有 getter 集中在这里
└── modules/
    ├── user.js           ← 登录态：token / roles / permissions   ★最重要
    ├── permission.js     ← 动态路由：把后端菜单树转成 router 路由  ★最重要
    ├── app.js            ← UI 状态：侧边栏展开/收起
    ├── settings.js       ← 主题、公司名等配置
    └── tagsView.js       ← 页签栏
```

**怎么用**：

```js
// 读（在组件里）
this.$store.state.user.token
this.$store.getters.roles
this.$store.dispatch('GetInfo')      // 调 action

// 读（在普通 .js 文件里）
import store from '@/store'
store.getters.permissions
```

> **`dispatch` vs `commit`**：`dispatch('Action名')` 调 action，`commit('Mutation名')` 调 mutation。**你永远不会在组件里直接 commit**（除极少数情况），都是走 action。

## 1.7 Cookie：token 存在哪

前端把 token 存在 **Cookie** 里（一种浏览器本地存储，特点是可以设置过期时间，且同域名的请求会自动带上）。

`zxcm-ui/src/utils/auth.js` 全文就三行有效代码：

```js
const TokenKey = 'Admin-Token'
export function getToken()       { return Cookies.get(TokenKey) }
export function setToken(token)  { return Cookies.set(TokenKey, token) }
export function removeToken()    { return Cookies.remove(TokenKey) }
```

> **注意**：token 虽然在 Cookie 里，但**不会自动出现在请求头里**——`utils/request.js` 会手动读出来塞进 header（见第三部分链路 2）。

### ⭐ 这里有个必须理解的设计决策

`buildLoginUser` 在**登录的那一刻**就把 `menuPermission`（权限码集合）和 `rolePermission`（角色集合）**一次性查出来，塞进登录会话**。

- **好处**：每次请求省一次数据库查询，性能好
- **代价**：改了角色的权限，**必须重新登录才生效**
- **这是"性能换一致性"的经典取舍**，面试常问

### token 到底存在哪

```
Redis（虚拟机 192.168.56.10:6379，database 5）
  key:   token:login:token:<jwt字符串>          ← ⚠️ 前缀是 token: 不是 satoken:
  value: 登录会话信息（含 Session 里的 LoginUser）
```

Sa-Token 默认把会话存在内存里，本项目的 `PlusSaTokenDao`（`ruoyi-framework/.../satoken/dao/`）**重写了 DAO，改成存 Redis**。

> **意义**：会话不在单机内存里，所以可以**多实例部署**（Nginx 后面挂 3 台后端，token 都能认），也支持**强制下线**。这是 Sa-Token "可插拔 DAO" 设计的价值。

> 💡 **一句话说人话**：Sa-Token 默认把「谁登录了」记在自己进程的内存里，重启就没了、多台机器也互相不认。本项目实现了 `SaTokenDao` 接口（`PlusSaTokenDao`），把这份记录改存到 Redis——**等于把「登录状态」从单机内存搬到了所有实例都能访问的公共存储**。key 前缀是 `token:` 不是 `satoken:`，因为 `sa-token.token-name` 配成了 `token`（详见 D1 §1.5）。

## 链路 3 · 登录后进首页 → 菜单树渲染 ⭐

**这是整个项目最值得理解的一段**：它是"后端数据驱动前端界面"的样板。

### 第 1 步：路由守卫拦截

`views/login.vue:276` 执行 `this.$router.push({ path: '/' })` 之后，**页面并不会立刻跳转**，而是先进"路由守卫"。

守卫是 `zxcm-ui/src/permission.js`，全局生效。核心逻辑（`permission.js:14` 起）：

```js
router.beforeEach((to, from, next) => {
  NProgress.start()                       // 顶部进度条

  if (getToken()) {                       // ── 有 token（已登录）
    if (to.path === '/login') {
      next({ path: '/' })                 // 已登录还想去登录页 → 打回首页
    } else {
      if (store.getters.roles.length === 0) {     // 还没拉过用户信息（首次进来必为真）
        store.dispatch('GetInfo').then(() => {    //    ① 拉用户信息
          store.dispatch('GenerateRoutes').then(accessRoutes => {  // ② 拉菜单转路由
            router.addRoutes(accessRoutes)        //    ③ 动态注入路由
            next({ ...to, replace: true })        //    ④ 重新进入
          })
        })
      } else {
        next()                            // 已经拉过了 → 直接放行
      }
    }
  } else {                                // ── 没有 token（未登录）
    if (whiteList.indexOf(to.path) !== -1) {
      next()                              // 白名单（登录页/404等）→ 放行
    } else {
      next(`/login?redirect=${to.fullPath}`)   // 其余全部跳登录页，并记住来路
    }
  }
})
```

**`store.getters.roles.length === 0` 这个判断的意义**：它是"用户信息是否已加载"的标志位。首次进必为 0，所以会去拉数据；拉完之后 roles 有值了，后续路由跳转就直接 `next()` 放行，不会重复请求。

```
⑦ permission.js:50  router.addRoutes(accessRoutes)
```

### 所以，"加一行菜单数据就能多一个页面"

现在你理解了为什么：

```
往数据库 sys_menu 插一行
  → 后端 /getRouters 多返回一个节点
  → 前端 GenerateRoutes 多生成一条路由
  → router.addRoutes 注入
  → 侧边栏多一个菜单项，点进去就是这个页面
```

**前端一行代码都不用改。** 这就是"动态菜单"。

### ⭐ 这里有个特别值得注意的发现

同一个 Controller 里有**两个**用户列表接口（`SysUserController.java:90-102`）：

```java
//公用的查询用户，不做权限限制
@GetMapping("/list")
public TableDataInfo<SysUser> list(SysUser user, PageQuery pageQuery) {
    return userService.selectPageUserList(user, pageQuery);
}

//公用的查询用户，不做权限限制
@GetMapping("/listWithP")
public TableDataInfo<SysUser> listWithP(SysUser user, PageQuery pageQuery) {
    return userService.selectPageUserListWithP(user, pageQuery);
}
```

**两个接口都没有 `@SaCheckPermission`**，注释也明说了"不做权限限制"。

但它们**限制的维度不同**：

| 接口 | 功能权限（按钮级） | 数据权限（行级） |
|---|---|---|
| `/list` | 无 | **无**——能看到全部用户 |
| `/listWithP` | 无 | **有**——`@DataPermission` 自动加 WHERE，只能看有权限的那部分 |

**前端页面用的是 `/listWithP`**，所以界面上是被数据权限约束的。

> **面试可讲**：这里体现了两种权限的区别——**功能权限**管"能不能用这个功能"（`@SaCheckPermission`），**数据权限**管"能看到哪些数据"（`@DataPermission` 自动改写 SQL）。
>
> 同时也要知道：`/list` 是个完全的开放接口，只要有登录态就能拉全量用户。**能主动说清楚"哪些接口做了权限、哪些没做、为什么"，比背"我们用了 Sa-Token"有说服力得多。**

# 第四部分 · 三条铁律

这三条贯穿全程，**不一致就出 bug**，也是面试高频：

## 铁律 1：请求头名是 `token`，值是 `Bearer <jwt>`

| 位置 | 内容 |
|---|---|
| 前端 `utils/request.js:33` | `config.headers['token'] = 'Bearer ' + getToken()` |
| 后端 `application.yml` | `sa-token.token-name: token`<br>`sa-token.token-prefix: Bearer` |

**三者必须严格对应**。写成 `Authorization` → 后端读不到 → 401。

> 这也是为什么 Task 5 的端到端验证里，`curl` 必须写 `-H "token: Bearer <jwt>"` 而不是 `-H "Authorization: ..."`。

## 铁律 2：响应拦截器 `return res.data`

`utils/request.js:110` 最后一行是 `return res.data`。

所以组件里 `.then(res => ...)` 拿到的**已经是后端 JSON 的主体**：

```js
// 分页数据
res.rows      // 列表
res.total     // 总数

// 单条数据
res.data

// ❌ 常见错误：写成 res.data.data
```

**新手最容易被这里绕晕，因为少了一层"data"反而看着不对。**

## 铁律 3：前端隐藏按钮 ≠ 安全，真正的校验在后端

> 📖 **没读过「第零部分 · 权限是什么」的话，先回去读 0.1~0.2**——那条铁律讲的是"功能权限"这一层，第零部分把三层权限的整体框架和 `sys_menu.perms` 的来源讲清楚了。这里只讲**为什么前端不可信**。

`views/system/user/index.vue` 里的按钮是这样写的：

```html
<el-button v-hasPermi="['system:user:export']" ...>导出</el-button>
```

`v-hasPermi` 是自定义指令（`directive/permission/hasPermi.js:9`）：

```js
export default {
  inserted(el, binding) {
    const permissions = store.getters && store.getters.permissions
    const hasPermissions = permissions.some(p =>
      "*:*:*" === p || binding.value.includes(p))
    if (!hasPermissions) {
      el.parentNode && el.parentNode.removeChild(el)   // 把按钮从 DOM 里删掉
    }
  }
}
```

**它只做了一件事：没权限就把按钮从页面上删掉。**

**这纯粹是体验优化，不是安全措施**——用户完全可以自己构造一个 HTTP 请求打你的接口。

真正的安全边界在后端：

```
sys_menu.perms（数据库里的权限码字符串）
   │
   ├──→ 前端路径（体验层）：
   │      /getInfo 返回 permissions 数组
   │      → Vuex 的 user.permissions
   │      → v-hasPermi 比对 → 删 DOM
   │
   └──→ 后端路径（安全层）：
          SaInterfaceImpl.getPermissionList() 从会话取
          → @SaCheckPermission 经 SaAnnotationInterceptor 校验
          → 不通过则抛异常，请求被拒
```

**同一条数据，两条路，一前一后。前端管体验，后端管安全。**

# 第六部分 · 面试问答

**Q：前后端是怎么交互的？**
> 前端用 axios 封装了统一的请求实例（`utils/request.js`），请求拦截器负责注入 token、拼接 GET 参数；响应拦截器统一处理错误码并剥掉一层 data。后端用 Sa-Token 的拦截器做登录校验，用 `@SaCheckPermission` 注解做接口级权限校验。两端的契约就是前端 `api/` 目录里的 url 和后端 Controller 的映射路径。

**Q：登录之后是怎么知道这个用户有哪些菜单的？**
> 登录时 `SysLoginService.buildLoginUser()` 就把权限码查好放进 `LoginUser`，随会话存进 Redis。前端登录成功后，路由守卫会依次调 `/getInfo` 拿角色和权限码、调 `/getRouters` 拿菜单树，然后 `router.addRoutes()` 动态注入路由，侧边栏遍历这份路由数据渲染。**菜单不在前端写死，完全由数据库 `sys_menu` 驱动。**

**Q：`"component": "system/user/index"` 这样的字符串前端怎么处理？**
> 用 `loadView()` 把它转成动态 `require`/`import`，实际加载 `src/views/system/user/index.vue`。特殊值 `Layout`、`ParentView`、`InnerLink` 会被替换成对应的框架组件。

**Q：前端权限和后端权限是什么关系？**
> 前端 `v-hasPermi` 只是把没权限的按钮从 DOM 里删掉，是体验优化，不是安全边界。真正的校验在后端 `@SaCheckPermission`，它通过 `StpInterface` 的实现类从登录会话里取权限码来比对。**前端隐藏的按钮，用户照样可以直接发请求。**

**Q：功能权限和数据权限有什么区别？**
> 功能权限管"能不能用这个功能"，实现是 `@SaCheckPermission`；数据权限管"能看到哪些数据"，实现是 MyBatis-Plus 的 `@DataPermission`，它在 SQL 层面自动加 WHERE 条件。本项目 `SysUserMapper.selectPageUserListWithP()` 是唯一还在跑的数据权限实例。

**Q：为什么改完权限要重新登录？**
> 因为权限码是在登录时一次性查出来存在会话里的，后续请求不查库。这是"性能换一致性"的取舍——好处是每次请求少一次数据库查询。

**Q：RuoYi 怎么判断一个用户是不是超级管理员？**
> ⚠️ **不是靠角色**——这是个常见误解。判定在 `SysUser.isAdmin()`，读的是 `sys_user` 表自己的 `SYSTEM_ADMIN` 字段（`=1` 即系统超管），另外还有 `TENANT_ADMIN` 字段代表"租户内管理员"。
> 所以改角色权限**动不了超管**，因为它的权限压根不走角色表。本项目 `zxcmAdmin` 挂的角色是「系统管理员」「档案管理员」，并**没有**挂那个叫「超级管理员」的角色，但它仍然是超管。
> 对应的权限计算在 `SysPermissionService`：超管**短路**返回 `*:*:*`（通配符，"全部"），根本不查 `sys_menu`；普通用户才走 `selectMenuPermsByUserId()` 查库。

**Q：功能权限和数据权限分别怎么实现？**
> **功能权限**是"拦请求"：`@SaCheckPermission("system:user:export")` + Sa-Token 的注解拦截器，不通过就拒绝调用。
> **数据权限**是"改 SQL"：`@DataPermission` 注解标在 Mapper 方法上，由 MyBatis-Plus 插件解析 `sys_role.DATA_SCOPE`（1 全部 / 2 自定义 / 3 本部门 / 4 本部门及以下 / 5 仅本人），把对应的 SpEL 模板求值后拼进 `WHERE` 子句。
> 一句话区分：**一个管"能不能调这个接口"，一个管"这个接口能看到哪些行"。**

**Q：RBAC 是什么？**
> Role-Based Access Control，基于角色的访问控制。核心是**在用户和权限之间插入"角色"这一层**，避免给每个用户单独配权限。落库是 5 张表：`sys_user`、`sys_role`、`sys_menu` 三张主表，加 `sys_user_role`、`sys_role_menu` 两张关联表（因为用户↔角色、角色↔菜单都是多对多，多对多在关系型数据库里必须用第三张表存）。

# 第七部分 · 🎤 一分钟讲法（对着面试官讲）

被问「你们前后端是怎么交互的」，照这段讲，**一分钟内讲完**：

> 「就三件事：**契约、认证、菜单驱动**。
>
> **契约**：前端每个 `api/xxx.js` 里的 url，在后端都能 `grep` 到一个 `@GetMapping` / `@PostMapping`，这是两端唯一的约定。
>
> **认证**：前端用 axios 封装了一个统一请求实例 `utils/request.js`——请求拦截器负责注入 `token: Bearer xxx`、把 GET 的 `params` 拼到 URL 上；响应拦截器统一处理错误码、**剥掉一层 `data`**。后端用 Sa-Token 的两道拦截器，一道管登录、一道管 `@SaCheckPermission` 权限校验。
>
> **菜单驱动**：登录后前端先调 `/getInfo` 拿角色和权限码，再调 `/getRouters` 拿菜单树。菜单树里每个节点的 `component` 是个**字符串**（比如 `system/user/index`），前端 `loadView()` 把它变成动态 `import('@/views/system/user/index')`，再用 `router.addRoutes()` 动态注入到路由表，侧边栏遍历这份路由数据渲染——**所以往 `sys_menu` 插一行数据就能多一个页面，前端一行代码都不用改。**」

如果只给 30 秒，就讲这一句：

> 💡 **一句话说人话**：**前端负责「显示和发请求」，后端负责「数据和权限」；两端的桥是 `api/*.js` 里的 url；菜单不是前端写死的，是后端从 `sys_menu` 查出来、前端动态生成路由的。**

**⚠️ 这段里三个必踩的坑，能主动说出来很加分**：

1. **响应拦截器最后一行是 `return res.data`**（`utils/request.js`）。所以组件里 `.then(res => ...)` 拿到的**已经是后端 JSON 的主体**，写 `res.data.data` 反而错——这是新手最容易被绕晕的地方。
2. **请求头名是 `token`、值是 `Bearer <jwt>`**（前端 `config.headers['token'] = 'Bearer ' + getToken()`，后端 `sa-token.token-name: token`）。写成 `Authorization` → 后端读不到 → **401**。
3. **路由守卫里必须写 `next({ ...to, replace: true })`**。动态注入路由之后如果直接 `next()`，此时新路由**还没生效**，会命中 404（见链路 3 第 ⑧ 步的警告）。
